# 098: Plannotator

- **Manifest resolution:** Index 98 is `Plannotator`, canonical repository `https://github.com/backnotprop/plannotator`, clone `.research/opencode-plugin-corpus/repos/backnotprop--plannotator`, with analysis subdirectory `apps/opencode-plugin` (`.research/opencode-plugin-corpus/repo-map.json:1492-1504`). The clone audit marks the root and analysis path verified. This report is limited to that clone and its declared analysis subdirectory, with the repository root consulted only for workspace/build context.
- **Purpose:** The package provides an interactive browser plan-review tool, annotation commands, and code review. The README describes the review loop as `submit_plan` -> browser annotations -> approval or structured feedback (`apps/opencode-plugin/README.md:1-7`, `163-168`).

## OpenCode integration patterns

### Separate V1 and V2 entrypoints

- The package deliberately maps OpenCode 1 to `main: dist/index.js` and OpenCode 2 to the package-root export `./dist/server.js`; the package comment warns not to add a `./server` subpath because OpenCode 1 probes it before `main` (`apps/opencode-plugin/package.json:25-29`). The package-boundary test freezes this routing and the absence of the subpath (`apps/opencode-plugin/package-boundary.test.ts:4-11`).
- V1 exports only the default plugin function, which is checked explicitly to prevent accidental export-shape changes (`apps/opencode-plugin/export-shape.test.ts:3-11`). V2 instead exports a stable object with `id: "plannotator"` and `setup` (`apps/opencode-plugin/server.ts:55-60`; `apps/opencode-plugin/server.test.ts:60-64`).
- V1 uses `@opencode-ai/plugin/v1` and mutating hooks such as `config`, `experimental.chat.messages.transform`, `tool.definition`, `experimental.chat.system.transform`, and `command.execute.before` (`apps/opencode-plugin/index.ts:18`, `309-317`, `357-371`, `438-448`). V2 uses `ctx.session.hook("context")` and `ctx.tool.transform` to alter per-session visibility and register a JSON-schema tool (`apps/opencode-plugin/server.ts:79-87`, `136-174`).

### Workflow and permission control

- Four explicit modes (`manual`, `user-managed`, `plan-agent`, `all-agents`) and three runtime choices (`auto`, `embedded`, `cli`) are normalized with safe defaults (`plan-agent`, `auto`); unknown values fall back rather than propagating malformed configuration (`apps/opencode-plugin/workflow.ts:3-23`, `41-65`). Planning agents are deduplicated and always include the built-in `plan` agent (`apps/opencode-plugin/workflow.ts:68-83`).
- Config mutation is narrow and mode-aware. Non-manual workflows add `submit_plan` to `experimental.primary_tools`, grant planning agents `submit_plan` plus `*.md` edit permission, deny the tool to `build` and other primary-capable agents, and optionally include subagents only when `PLANNOTATOR_ALLOW_SUBAGENTS` is enabled (`apps/opencode-plugin/workflow.ts:154-195`, `197-210`, `251-255`).
- The permission helper handles OpenCode's transformed string form (`permission.edit: "deny"`) before merging path rules; without it, spreading a string would create numeric character keys and corrupt validation (`apps/opencode-plugin/plan-mode.ts:5-21`). This is both a compatibility pattern and a concrete configuration pitfall.
- V2 removes `submit_plan` from non-planning sessions at context time, and blocks subagents by default even in `all-agents` (`apps/opencode-plugin/server.ts:79-95`). The tests cover planning visibility, build exclusion, and the subagent opt-in (`apps/opencode-plugin/server.test.ts:121-201`).

### Prompt transformation

- The integration strips conflicting native plan-mode instructions, including blanket edit prohibitions, on-disk plan-path instructions, and `plan_exit`, then composes the host prompt and Plannotator additions into one text part (`apps/opencode-plugin/plan-mode.ts:24-60`).
- Single-part composition is intentional: the V2 source documents that multiple system parts corrupt Qwen3.x Jinja templates; it also emphasizes composing before truncating so the host system prompt is not silently lost (`apps/opencode-plugin/server.ts:347-384`). Regression tests assert order, preservation, and one-part output (`apps/opencode-plugin/server.test.ts:142-181`, `229-264`).
- V1 command interception clears `output.parts` **in place**, not by assigning a new array, so OpenCode's caller sees the suppression. This prevents command text and arguments, including file paths, from being re-resolved into context/file parts before the UI opens (`apps/opencode-plugin/index.ts:438-461`).

### Review execution and host handoff

- Plans are represented as line-range edits against a plugin-managed backing file outside the workspace, so the agent does not edit the backing file directly. The first call can replace from line 1; later denial responses return line-numbered content for surgical edits (`apps/opencode-plugin/plan-edits.ts:11-17`, `21-29`, `93-103`; `apps/opencode-plugin/submit-plan-executor.ts:111-118`).
- `executeSubmitPlan` validates edits, applies them in sorted order, rejects empty or over-5-MB plans, persists before review, preserves the backing state if review startup fails, deletes it after approval, validates the requested target agent, and sends an implementation handoff only to a non-planning target (`apps/opencode-plugin/submit-plan-executor.ts:23-38`, `58-109`, `121-165`).
- Approved annotation notes are deliberately framed as non-blocking guidance while annotated feedback takes the revision-request path. The bridge maps review and annotation outcomes into OpenCode session prompts and validates target agents against the host's agent list (`apps/opencode-plugin/cli-bridge.ts:552-621`, `624-756`; `apps/opencode-plugin/agent-switch.ts:49-72`).
- Embedded mode imports the shared server lazily, waits for a decision, supports timeout and abort signals, delays close briefly for the UI, and always stops the server in `finally` (`apps/opencode-plugin/embedded.ts:31-39`, `69-105`). The lifecycle tests prove cancellation releases a fixed port, approval remains alive, timeout returns a retryable result, and ready-callback failure still releases the server (`apps/opencode-plugin/plan-review-lifecycle.test.ts:67-190`).
- Runtime selection prefers the embedded Bun server when available, falls back to the CLI in `auto`, and fails clearly when `embedded` is forced on a host without Bun (`apps/opencode-plugin/index.ts:104-120`, `179-231`; `apps/opencode-plugin/server.ts:294-344`). The README documents the same runtime behavior and the OpenCode 2 feature gaps (`apps/opencode-plugin/README.md:41-48`, `92-103`).

## Security and reliability lessons

- The CLI bridge uses `spawn` with an argument array and `shell: false`; Windows resolution prefers executable files and deliberately avoids `.cmd`/`.bat` shims that would reintroduce shell tokenization (`apps/opencode-plugin/cli-bridge.ts:145-194`). This is the correct baseline for user-controlled paths and flags.
- Child processes inherit the environment but receive an explicit origin, working directory, bridge settings, and a random ready-file path in the OS temp directory. Abort sends SIGTERM, escalates to SIGKILL after one second, kills a detached process group on non-Windows, clears polling/timers/listeners, flushes stderr, reads final ready metadata, and removes the ready file (`apps/opencode-plugin/cli-bridge.ts:323-451`).
- CLI bridge failures are fail-closed: nonzero CLI exits become errors, missing binaries get an actionable install message, malformed JSON is rejected, and prompt-delivery failures are classified so embedded fallback cannot hide a host delivery failure (`apps/opencode-plugin/cli-bridge.ts:197-205`, `412-429`, `471-499`; `apps/opencode-plugin/embedded.test.ts:26-51`).
- Agent switching is validated against the current agent list; lookup failure or stale names omit the switch rather than sending an invalid target, while warning through best-effort log/toast paths (`apps/opencode-plugin/agent-switch.ts:23-47`, `49-72`). OpenCode 2 explicitly cannot switch agents through its plugin API and warns while approving without switching (`apps/opencode-plugin/server.ts:197-209`).
- The README is candid that local data stays local by default but update checks and selected sharing/URL/hosted-review/AI features use the network; legacy small shares are compressed and unencrypted in URL fragments (`apps/opencode-plugin/README.md:170-178`). Operators should treat share URLs and remote mode as disclosure boundaries, not as private transport.
- Container operation requires both remote mode and a fixed forwarded port; setting only the port is insufficient (`apps/opencode-plugin/devcontainer.md:5-24`). The README also documents the 96-hour default review timeout and the `PLANNOTATOR_BIN` override (`apps/opencode-plugin/README.md:180-190`).
- Command handling validates active-session requirements for gated annotation, resolves paths relative to the agent directory, caps local annotation files at 2 MB, rejects folders with no annotatable files, and distinguishes raw HTML from converted Markdown (`apps/opencode-plugin/cli-bridge.ts:455-469`; `apps/opencode-plugin/commands.ts:237-268`, `297-363`). URL annotation intentionally fetches external content through configured Jina or fetch/Turndown paths (`apps/opencode-plugin/commands.ts:280-295`).

## Testing lessons

- Tests target observable regressions rather than only implementation calls: export/package routing, permission normalization, prompt preservation/order, tool visibility, edit validation and persistence, process/abort behavior, outcome wording, Windows spawning, path quoting, and server lifetime are all covered (`apps/opencode-plugin/package-boundary.test.ts:4-11`; `apps/opencode-plugin/plan-mode.test.ts:8-89`; `apps/opencode-plugin/submit-plan-executor.test.ts:25-121`; `apps/opencode-plugin/cli-bridge.test.ts:19-262`).
- The test suite treats Bun's single-process behavior as a hazard. It restores environment variables and removes temporary data directories after each test (`apps/opencode-plugin/submit-plan-executor.test.ts:1-23`; `apps/opencode-plugin/server.test.ts:1-12`). Command tests use dependency injection for the annotate server because process-global Bun module mocks would leak into other suites (`apps/opencode-plugin/commands.test.ts:8-19`).
- Integration tests use temporary project/data directories, fixed-port allocation, browser-open suppression, and explicit port-reuse checks instead of relying on timing or real user state (`apps/opencode-plugin/plan-review-lifecycle.test.ts:6-32`, `46-65`). This is a useful model for plugin tests involving servers, signals, and persistent state.
- The repository's target-specific tests are substantial, but the package itself does not show a dedicated `test` script in its package manifest; the workspace root owns `bun test` and `build:opencode` (`apps/opencode-plugin/package.json:37-41`; repository `package.json:19-37`). A consumer or release pipeline must therefore run tests/builds from the workspace or invoke Bun directly in the app directory.

## Packaging and release pitfalls

- The build copies the two prebuilt HTML applications into the package, bundles `embedded.ts` for Bun and both entrypoints for Node, and keeps `@opencode-ai/plugin` external. `prepublishOnly` runs this build (`apps/opencode-plugin/package.json:30-41`). Missing `plannotator.html` or `review-editor.html` is a runtime error in the entrypoint (`apps/opencode-plugin/index.ts:53-87`; `apps/opencode-plugin/server.ts:282-291`).
- The published allowlist includes `dist`, command stubs, README, and both HTML assets; omitting any of these breaks an otherwise valid install (`apps/opencode-plugin/package.json:30-35`). The package is ESM, Bun >= 1.0, and depends on workspace-local server/shared packages during development (`apps/opencode-plugin/package.json:2-7`, `43-50`).
- `postinstall` copies command stubs into `${XDG_CONFIG_HOME:-$HOME/.config}/opencode/commands`, suppressing copy errors. This makes installation convenient but is a write outside the package and should be treated as a side effect requiring clear user consent and careful installer testing (`apps/opencode-plugin/package.json:39-41`).
- The command files intentionally contain only frontmatter descriptions; execution is intercepted by the plugin rather than delegated to model-mediated command text (`apps/opencode-plugin/commands/plannotator-review.md:1-3`; `apps/opencode-plugin/index.ts:438-485`). The README warns that OpenCode 2 cannot provide the native slash-command execution hook, so these remain OpenCode 1-only (`apps/opencode-plugin/README.md:43-48`).
- The root workspace builds the hook before the OpenCode package, because the OpenCode build copies the hook/review HTML artifacts; the root `build` script encodes `build:hook && build:opencode` (`package.json:25-31`). A packaging pipeline that runs only the OpenCode bundle step can ship stale or missing UI assets.

## Bottom line

Plannotator demonstrates a production-grade OpenCode plugin boundary: preserve host-specific entrypoint contracts, normalize and scope permissions, mutate host hook data in place, consolidate prompt parts before replacing arrays, keep UI/server execution cancellable, and bridge CLI processes without a shell. Its main operational risks are the broad side effects of `postinstall`, network/disclosure behavior in sharing and remote modes, dependency on workspace-generated HTML artifacts, and OpenCode API differences that make V2 slash commands, toasts, cancellation, and agent switching incomplete. The tests are strongest where those risks are concrete: package routing, process lifetime, environment isolation, prompt shape, and failure cleanup.
