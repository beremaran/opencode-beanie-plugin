## Architecture and OpenCode patterns

- The plugin exports an async `Plugin` factory and registers configuration, tools, a `chat.message` hook, and an event hook in one returned object (`src/plugin.ts:44-102`). This is a compact pattern for keeping client and project-directory dependencies in the plugin context rather than using globals.
- Configuration mutates or creates `config.command` and adds a named command while preserving existing commands (`src/plugin.ts:47-54`; `test/plugin.test.ts:24-49`). The command template gives the model explicit XML sections, tells it to select relevant files, and requires an immediate `handoff_session` call (`src/plugin.ts:5-42`).
- Tools are factory functions receiving `PluginInput["client"]`, which makes SDK calls injectable in tests (`src/tools.ts:9-19`; `test/tools.test.ts:18-33`). Zod-backed tool schemas validate the prompt, optional file list, session ID, and transcript limit at the tool boundary (`src/tools.ts:20-25`, `112-118`).
- `handoff_session` creates a session through `client.tui.executeCommand`, waits 150 ms for the UI to mount, appends an editable prompt, then displays a success toast (`src/tools.ts:35-52`). The changelog records that this delay fixed a real prompt-loss race (`CHANGELOG.md:27-31`), illustrating that fire-and-forget TUI APIs need explicit sequencing (`src/tools.ts:35-41`).
- The handoff prompt embeds the originating session ID and normalizes each supplied file to an `@` reference (`src/tools.ts:27-33`). The receiving session's `chat.message` hook ignores synthetic text, requires the session-reference marker, deduplicates processing by session ID, parses references, and injects them with a no-reply prompt while preserving the current model and agent (`src/plugin.ts:61-95`).
- File injection intentionally creates synthetic text matching OpenCode's Read-tool output, including a tool-call header and numbered `<file>` content (`src/files.ts:37-46`, `68-80`; `src/vendor.ts:67-101`). Copying compatibility constants and formatting into a small vendor module isolates the dependency on OpenCode internals (`src/vendor.ts:1-9`).
- Session retrieval uses `client.session.messages`, formats visible user/assistant text and completed tools, and caps the requested limit at 500 (`src/tools.ts:64-105`, `119-137`). Errors become tool-readable strings instead of escaping as opaque failures (`src/tools.ts:122-135`).

## Security and reliability pitfalls

- **High: file references are not constrained to the project.** `path.resolve(directory, ref)` is used directly, with no check that the result remains under `directory` (`src/files.ts:54-56`). A handoff containing `@../../secrets` or an absolute path can cause arbitrary readable files to be loaded into the next session's context. Because references are extracted from model-generated text (`src/plugin.ts:78-82`), this is an important prompt-injection/data-exfiltration boundary. Enforce a project-root containment check, reject absolute paths and traversal, and consider symlink resolution before reading.
- **Medium: file-size/resource limits are absent.** `isBinaryFile` reads the entire file to inspect at most the first 4096 bytes (`src/vendor.ts:40-61`), then `buildSyntheticFileParts` reads the entire file again (`src/files.ts:65-66`) before truncating output to 2,000 lines and 2,000 characters per line (`src/vendor.ts:17-20`, `74-80`). A large text file can therefore consume substantial memory and I/O even though the resulting context is bounded. Stat-based size limits and bounded streaming/reads would reduce the exposure.
- **Medium: the session reader intentionally exposes transcript content.** `read_session` accepts any caller-supplied session ID and returns user text, attached-file names, assistant text, and completed tool titles (`src/tools.ts:112-135`; `src/tools.ts:70-95`). This is the advertised feature (`README.md:55-71`), but deployments should rely on OpenCode client authorization and avoid treating the tool as a general-purpose secret-safe export mechanism.
- **Low: the limit clamp does not enforce a lower bound.** `Math.min(args.limit ?? 100, 500)` caps high values but permits zero or negative values (`src/tools.ts:119-121`). The schema also only says “number” (`src/tools.ts:116-118`). Use an integer schema with a positive lower bound and clamp both ends.
- **Low: the 150 ms UI synchronization is empirical.** The delay addresses the documented race (`src/tools.ts:36-41`; `CHANGELOG.md:29-31`) but can still be flaky on slower or unusual TUI transitions. A completion signal or retry would be more deterministic if the API permits it.

## Testing lessons

- Tests are fast and isolated with Bun's test runner, temporary directories, and mocked OpenCode clients (`test/plugin.test.ts:1-20`, `51-144`; `test/files.test.ts:1-5`). They verify command registration without losing existing config, one-time injection, reset on session deletion, model/agent preservation, and skipping missing/binary/directory references (`test/plugin.test.ts:23-49`, `91-140`; `test/files.test.ts:22-59`).
- Tool tests assert the exact TUI call order and generated prompt, transcript filtering, default/capped limits, empty sessions, and converted client errors (`test/tools.test.ts:18-86`, `89-193`). Vendor tests cover both line-length truncation and the 2,000-line boundary (`test/vendor.test.ts:4-19`).
- CI runs frozen-lockfile installation followed by `bun test` (`.github/workflows/test.yml:25-34`) and a separate strict TypeScript check (`.github/workflows/lint.yml:25-34`). The “lint” workflow is typecheck-only; there is no formatter or linter command in `package.json` (`package.json:20-23`).
- Missing coverage includes traversal/absolute/symlink paths, permission errors, very large files, malformed or adversarial `@` references, concurrent messages for the same session, failures from TUI calls, and integration behavior against a real OpenCode TUI. Those cases matter most because they exercise the resource and security boundaries above.

## Packaging and supply-chain lessons

- The package is a direct TypeScript plugin entrypoint (`main: "src/plugin.ts"`) and publishes only `src` and `README.md` (`package.json:18-20`). Runtime dependencies are explicit OpenCode plugin/SDK packages plus Zod, with Bun as the supported engine (`package.json:24-36`). This keeps the npm payload small, but excludes tests, changelog, and TypeScript config from the published artifact.
- The README documents both unpinned and pinned plugin installation and warns that unpinned plugins are fetched from npm on startup (`README.md:20-38`). Pinning is therefore a practical stability and supply-chain control for users.
- Release CI uses frozen dependencies, typechecks, packs the npm artifact, generates build provenance, uploads the tarball, and publishes to npm (`.github/workflows/release.yml:20-57`). GitHub Actions are SHA-pinned in the workflows (`.github/workflows/release.yml:16-22`, `.github/workflows/test.yml:21-27`), and Zizmor scans workflow security (`.github/workflows/zizmor.yml:18-43`).
- Workflow jobs default to no permissions and request narrow read permissions for validation (`.github/workflows/test.yml:13-20`; `.github/workflows/lint.yml:13-20`). Release necessarily requests contents, OIDC, and attestations (`.github/workflows/release.yml:9-14`), so the protected `release` environment and published-release trigger are important safeguards.
- Dependabot updates GitHub Actions weekly with a seven-day cooldown and groups them (`.github/dependabot.yml:1-15`). CODEOWNERS assigns all files to the maintainer (`.github/CODEOWNERS:1`).

## Overall assessment

This is a focused, well-tested example of OpenCode plugin composition: command configuration, dependency-injected tools, lifecycle hooks, synthetic context parts, and explicit preservation of model/agent state. The main adoption blocker is the file loader's unrestricted `path.resolve` behavior; fix containment and add adversarial path/resource tests before using the automatic file-injection feature with untrusted or model-controlled handoff content.
