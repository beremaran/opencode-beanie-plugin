## What the plugin does

`opencode-tts` speaks assistant output when a session becomes idle. The README describes the flow as capturing the latest assistant message, optionally summarizing it, and sending it to a local TTS engine (`README.md:7-13`). It exposes persistent summary/full modes and enable/disable/repeat/speak/uninstall commands (`README.md:31-50`). Configuration is read from `~/.config/opencode/plugins/opencode-tts.jsonc`, with a legacy singular `plugin` path also accepted by the implementation (`README.md:52-74`; `src/index.ts:51-63`, `105-115`).

## OpenCode integration patterns

- Export a value typed as the SDK `Plugin`, and return a hooks object from the async plugin initializer (`src/index.ts:1-2`, `491-497`, `682`). This gives compile-time checking while keeping the runtime entrypoint small.
- Use the `event` hook to maintain a per-session latest assistant message and a per-message text cache. `message.updated` records message/provider/model identity, `message.part.updated` records non-filtered text parts, and `session.idle` consumes the cache (`src/index.ts:498-519`, `521-577`). This avoids a second fetch at idle time and preserves the source model for summary fallback.
- Use the `config` hook to inject command definitions into `input.command` (`src/index.ts:578-583`). The implementation registers separate names such as `tts-mode-summary`, `tts-off`, and `tts-repeat`, rather than relying on a single command parser (`src/index.ts:481-489`).
- Handle registered commands in `command.execute.before`, perform the action, and throw a sentinel-style error (`"Command handled by TTS plugin"`) to stop normal command processing (`src/index.ts:584-636`). This is a useful interception pattern, but the UI feedback behavior should be verified against the host version.
- Keep process-wide state in module-level sets/maps for de-duplication and concurrency control: `spokenAssistantMessages` prevents repeat idle speech, while `inFlightSessions` prevents overlapping idle work (`src/index.ts:42-45`, `525-527`, `574-576`).
- Resolve summary models progressively: explicit plugin provider/model, OpenCode `small_model`, OpenCode `model`, then the originating assistant model (`src/index.ts:276-300`). If summarization fails, degrade to the first 40 sanitized words (`src/index.ts:460-478`, `263-266`).

## Configuration and external-process design

- The default backend auto-creates `~/.config/opencode/tts-venv`, locates Python, creates a virtualenv, and runs `pip install --quiet edge-tts` (`src/index.ts:149-177`). It then prefers the managed venv and falls back to PATH/module discovery (`src/index.ts:179-196`). This is convenient for users but makes first speech depend on Python, network access, package-index availability, and mutable dependency resolution.
- TTS commands are passed through the SDK shell helper. Configured command elements and all generated arguments are escaped before being assembled into the edge-tts invocation (`src/index.ts:386-403`). The `say`, `afplay`, `ffplay`, `mpg123`, `spd-say`, and `espeak` paths use tagged shell interpolation (`src/index.ts:407-457`). Treat custom command configuration as intentionally privileged, and retain argument escaping if this code is extended.
- The implementation deletes temporary MP3 output in a `finally` block (`src/index.ts:391-431`), including after playback failure. This is a good resource-cleanup pattern.
- Summarization makes a direct OpenAI-compatible `/chat/completions` request using the configured provider base URL and API key (`src/index.ts:322-359`). The source response is sanitized for thinking/reflection tags before being placed into the prompt (`src/index.ts:65-79`, `331-341`).

## Security and privacy lessons

- Debug mode logs the generated summary text and, on idle success, the spoken text (`src/index.ts:366-371`, `556-559`). Because logs are written under the user’s OpenCode directory (`src/index.ts:62`, `90-98`), debug mode can persist sensitive assistant content. A safer design would log lengths/identifiers by default and make content logging an explicit, separately named option.
- The first-use installer executes an unpinned package install from the network (`src/index.ts:162-170`). Production plugins should pin or otherwise verify the dependency, make network installation explicit, and report actionable failure rather than silently falling back to a command that may not exist (`src/index.ts:189-196`).
- `stripJsonComments` removes `//...` text naively across the whole file (`src/index.ts:81-83`). It can corrupt valid JSON strings containing `//` (for example URLs), after which config loading silently falls through to defaults (`src/index.ts:105-115`). A JSONC parser or a string-aware comment stripper would avoid this reliability/security boundary.
- The uninstall command rewrites `~/.config/opencode/opencode.json` after parsing with the same naive comment removal and removes every plugin entry whose string merely contains `opencode-tts` (`src/index.ts:651-662`). This is broad matching plus destructive rewriting of a user-owned config; it should match exact package/file references, preserve formatting/comments where possible, and provide a backup or confirmation.
- Uninstall removes selected generated files and the npm cache dependency but does not remove the managed TTS virtualenv or log file (`src/index.ts:638-675`). The README’s “remove plugin files and clean up” wording therefore overstates cleanup (`README.md:46-48`).
- Error handling intentionally suppresses many failures, including config parsing, config writes, dependency setup, and uninstall operations (`src/index.ts:105-115`, `121-131`, `162-176`, `647-673`). This keeps the host alive but can leave users believing a change succeeded when it did not; debug diagnostics and user-visible command results should distinguish skipped, failed, and completed operations.

## Testing and correctness lessons

- There is no test script in `package.json`; scripts are only `build`, `prepare`, and `typecheck` (`package.json:13-17`). The repository’s design explicitly lists tests as out of scope because no test infrastructure exists (`docs/superpowers/specs/2026-03-22-tts-slash-commands-design.md:142-146`). This leaves event sequencing, command interception, filesystem cleanup, shell argument handling, summary fallback, and platform branches unautomated.
- The implementation tracks latest message and text separately. A `message.updated` event can arrive before its text part, and idle returns if the cache is empty (`src/index.ts:501-539`). A test should cover event ordering and late parts; otherwise a valid response can be skipped permanently for that message.
- `tts-speak` and `tts-repeat` launch speech without awaiting it and immediately throw the handled-command error (`src/index.ts:611-635`). This avoids blocking command dispatch but makes completion/failure invisible to the command response and permits overlap with idle speech. The design document’s proposed `/tts` implementation instead awaits and emits synthetic feedback (`docs/superpowers/specs/2026-03-22-tts-slash-commands-design.md:71-92`, `108-114`), revealing an important behavioral contract to test.
- The design document describes a single `/tts full|summary|off|repeat|say` command and says `/tts uninstall` is out of scope (`docs/superpowers/specs/2026-03-22-tts-slash-commands-design.md:12-20`, `142-145`), while the shipped source implements separate `tts-*` commands plus uninstall (`src/index.ts:481-489`, `584-677`). README, generated command names, design, and implementation should be kept synchronized.
- `tsconfig.json` enables strict checking and no emit (`tsconfig.json:1-17`), while esbuild bundles the TypeScript entrypoint to Node 22 ESM and leaves OpenCode SDK packages external (`build.mjs:1-12`). This is a sound separation, but only typecheck/build commands are declared; there is no automated runtime smoke test.

## Packaging and release lessons

- `package.json` declares ESM, `dist/index.js` as both `main` and the package export, and restricts the published file set to `dist` (`package.json:2-12`). The build produces `dist/index.js` plus a source map, bundles application dependencies, and externalizes `@opencode-ai/plugin` and `@opencode-ai/sdk` (`build.mjs:3-12`).
- `prepare` rebuilds on install, which helps consumers receive the generated entrypoint, while the README also documents a local `file://.../dist/index.js` configuration (`package.json:13-16`; `README.md:103-118`).
- The lockfile records exact resolved dependency versions and integrity values, including OpenCode plugin `1.2.27` (`package-lock.json:1-18`, `437-447`). The manifest uses caret ranges, so repeatable installs depend on honoring the lockfile; published plugin consumers may resolve newer compatible SDK versions.
- The repository does not declare a publish/release script or an engines field (`package.json:13-25`). Release verification is consequently manual, as reflected by the plan’s rebuild, `dist` inspection, and live OpenCode smoke-test checklist (`docs/superpowers/plans/2026-03-22-tts-slash-commands.md:475-510`).

## Bottom line

The strongest reusable pattern is a small typed plugin initializer combining event caches, `session.idle` work gating, command registration/interception, sanitized input, and explicit subprocess cleanup. The main risks are the absence of tests, silent/best-effort failure paths, content-bearing debug logs, naive JSONC handling, and unpinned network installation. The design/spec drift around slash-command UX is also a concrete maintenance warning: host-facing command names and completion behavior need a single tested source of truth.
