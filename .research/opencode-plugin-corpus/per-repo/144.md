## What the plugin does

This is deliberately a thin OpenCode plugin. The README says it registers the
vendored skills at load time and adds a JFrog Platform MCP server, with no
runtime download or network call on load (`README.md:1-6`, `README.md:81-92`).

The entrypoint exports the same implementation under OpenCode's `server` export
and a compatibility-named export (`src/index.ts:168-171`, `src/index.ts:228-229`).
The plugin uses two hooks:

- `config` creates `config.skills.paths` as needed, validates that the bundled
  directory is a non-empty directory, appends it only once, and independently
  attempts MCP registration (`src/index.ts:118-140`, `src/index.ts:209-215`).
- `tool.execute.before` watches only Bash commands and detects a standalone
  `jf` invocation. If the CLI was absent at plugin load, it shows a one-time
  installation hint (`src/index.ts:191-207`, `src/index.ts:216-224`). The CLI
  presence check is cached once per session, keeping the per-tool hook cheap
  (`src/index.ts:191-195`).

MCP registration is config mutation rather than connection work. It accepts
  new and legacy environment variable names in explicit precedence order,
  normalizes a missing scheme to HTTPS and strips trailing slashes, and skips
  registration when disabled or when either credential is absent
  (`src/index.ts:22-24`, `src/index.ts:71-95`). It creates a remote `/mcp`
  entry with bearer authentication and `oauth: false` (`src/index.ts:98-110`).
  A user-defined `config.mcp.jfrog` entry wins, and repeated config-hook calls
  do not replace it (`src/index.ts:142-165`).

## Evidence-backed OpenCode patterns

1. **Use the `config` hook to extend, not replace, user configuration.** The
   implementation initializes missing objects, appends the skill path, and
   leaves existing MCP configuration untouched (`src/index.ts:119-138`,
   `src/index.ts:160-164`). This is a safe pattern for plugins that need to
   contribute defaults.
2. **Register skills through `config.skills.paths` object form.** The README
   documents that OpenCode discovers the skills through the normal skill system
   (`README.md:81-87`) and explicitly requires OpenCode 1.17.7 or newer because
   that is the first verified version honoring this form (`README.md:288-291`).
3. **Make config hooks idempotent.** The path check prevents duplicate skill
   paths (`src/index.ts:135-138`), while the MCP guard prevents overwriting a
   named server (`src/index.ts:160-165`). Tests exercise both repeated config
   calls and preservation of a user entry (`src/index.test.ts:92-99`,
   `src/index.test.ts:376-395`).
4. **Keep bootstrap side effects local and observable.** Load-time behavior
   only checks the filesystem and mutates in-memory config; debug logs are
   opt-in and written under the project `.opencode` directory
   (`src/index.ts:17-20`, `src/index.ts:170-189`; `README.md:195-206`). The
   toast is deliberately fire-and-forget because awaiting it can hang headless
   sessions (`src/index.ts:182-187`).
5. **Separate skill descriptions from detailed instructions.** The vendored
   skills use YAML frontmatter for name/description and put the workflow body
   and references below it (`skills/jfrog/SKILL.md:1-24`,
   `skills/jfrog-mcp-management/SKILL.md:1-16`). The MCP workflow routes
   OpenCode-specific details to exactly one harness reference, rather than
   hard-coding every harness format into the shared skill
   (`skills/jfrog-mcp-management/SKILL.md:27-40`).

## Security lessons and pitfalls

- **Do not put raw secrets in persistent config.** This plugin reads the token
  from the process environment and materializes the bearer header only in the
  in-memory injected config because plugin-injected `{env:...}` references are
  not expanded (`src/index.ts:98-104`; `README.md:142-146`). The repository
  also explicitly forbids committed credentials and local-cache data
  (`SECURITY.md:11-15`). Short-lived tokens are recommended
  (`README.md:142-146`).
- **A token-shape warning is not authentication.** `looksLikeJwt` only checks
  for the `eyJ` prefix and registration proceeds even when it fails
  (`src/index.ts:82-83`, `src/index.ts:152-165`). This avoids silently hiding
  configuration errors but means the remote MCP can still be configured with
  an unusable token; the README correctly calls out JWT versus reference-token
  behavior and the likely 401 (`README.md:122-146`, `README.md:205-206`).
- **Honor explicit transport schemes.** The URL helper defaults unschemed hosts
  to HTTPS but preserves explicit HTTP (`src/index.ts:74-78`). That supports
  internal deployments, but allowing an environment-controlled HTTP endpoint
  is a security decision and should not be treated as automatic TLS protection.
  The behavior is covered by tests (`src/index.test.ts:313-328`).
- **Do not clobber user-controlled MCP entries.** The named-server preservation
  rule is both implemented and tested (`src/index.ts:160-164`,
  `src/index.test.ts:376-384`). This is especially important because injected
  headers contain credentials.
- **Vendored skill content is executable guidance.** The skill metadata permits
  selected Bash commands and file operations (`skills/jfrog-mcp-management/SKILL.md:1-14`),
  and the workflow insists MCP servers be installed only through Agent Guard
  (`skills/jfrog-mcp-management/SKILL.md:16-21`). Consumers should review
  vendored skill updates as code/policy changes, not just documentation.
- **The sync script has a supply-chain boundary.** It fetches a GitHub tarball
  for the configured ref and replaces the selected path, without a checksum or
  signature verification step (`scripts/sync-skills.mjs:15-20`,
  `scripts/sync-skills.mjs:44-61`). The tag pin improves reproducibility but is
  not equivalent to pinning and verifying an immutable digest.

## Testing lessons

- The test suite is focused and directly models OpenCode plugin inputs: a small
  fake client, config hook invocation, and tool-hook invocation
  (`src/index.test.ts:19-37`, `src/index.test.ts:62-67`). This makes hook behavior
  testable without starting OpenCode.
- Important edge cases are covered: missing versus present `jf`, one-time toast
  behavior, command/tool filtering, environment aliases, URL normalization,
  disabled MCP, non-JWT warning behavior, user-entry preservation, and
  idempotence (`src/index.test.ts:158-211`, `src/index.test.ts:294-395`).
- The repository validates vendored assets, not just TypeScript. It asserts the
  exact flat skill directory set and checks every `SKILL.md` has frontmatter
  whose name matches its directory (`src/index.test.ts:214-253`). This guards
  the runtime discovery contract described in `VENDOR.md:78-84`.
- CI combines synchronization, lint, typecheck, tests, build, package metadata,
  and package-content checks (`.github/workflows/pr.yml:31-40`). In this
  snapshot, `bun test` independently passed all 32 tests. No network-dependent
  skill or MCP runtime behavior is tested, so endpoint authentication and
  Agent Guard behavior remain integration-test gaps.

## Packaging and release lessons

- The npm package is intentionally minimal: its published files are `dist`,
  `skills`, and the vendor manifest (`package.json:32-37`). The README explains
  that the runtime tarball must contain both the built module and vendored skills
  (`README.md:90-92`). This prevents the common failure where a plugin entrypoint
  ships but its discovered skills do not.
- The package uses ESM and exposes `dist/index.js` plus a declaration path
  (`package.json:9-15`, `package.json:37-38`). However, the checked-in build task
  invokes only `bun build ./src/index.ts --outdir dist --target bun`
  (`.mise/tasks/build:1-7`), while TypeScript has `noEmit: true`
  (`tsconfig.json:7-12`). The release/package check should explicitly verify
  whether `dist/index.d.ts` is generated or remove the declaration export; this
  is a concrete packaging contract to test, not an assumed runtime failure.
- Skill updates are pinned and committed, and a sync check is intended to fail
  on drift (`sync-skills-vendor.json:1-7`, `VENDOR.md:29-53`, `VENDOR.md:75-84`).
  The tradeoff is that updates require a new plugin release
  (`VENDOR.md:3-9`).
- Release automation separates versioning from publishing: release-please runs
  on `main`, then dispatches the OIDC-enabled publish workflow only after a
  release is created (`.github/workflows/release.yml:1-41`; 
  `.github/workflows/publish-as-is.yml:8-35`). The package is public and npm
  publishing is configured accordingly (`package.json:24-35`).
- The README documents explicit compatibility, install, local `file://` testing,
  upgrade changes, and development commands (`README.md:39-77`,
  `README.md:238-271`). This is useful because the plugin intentionally changed
  skill names, removed runtime downloads, and removed automatic package-manager
  setup in the 0.0.3 transition (`README.md:238-246`).

## Bottom line

The strongest reusable pattern is a small, idempotent OpenCode config hook that
adds a packaged skill directory and an opt-in MCP entry without network work or
overwriting user configuration. The repository pairs that runtime design with
good hook-level tests and vendored-tree validation. The main risks to carry into
other plugins are secret materialization in injected config, the distinction
between token-shape checks and real authentication, executable vendored skill
updates, unchecked upstream tarball contents, and the unresolved declaration-file
contract between `package.json` and the build task.
