## README and OpenCode Integration

The README defines the product as Bun/Tmux-backed interactive calendar, document, flight, and custom terminal canvases (`README.md:1-20`). Installation is via npm or source build, and configuration registers `@mailshieldai/opencode-canvas` plus an allow rule for `canvas_*` permissions (`README.md:24-51`). The documented public tools are `canvas_spawn`, `canvas_update`, `canvas_selection`, and `canvas_close` (`README.md:54-105`).

The plugin entrypoint uses the official `@opencode-ai/plugin` `Plugin` and `tool` APIs (`src/index.ts:12-14`). It returns tool registrations, dynamically loaded skills, and a `config` hook that merges generated command definitions into `config.command` (`src/index.ts:421-448`). This is a useful pattern for packaging a plugin with both executable tools and repository-local OpenCode skills/commands. The implementation loads `.opencode/skill/**/SKILL.md` and `src/command/**/*.md`, with small frontmatter parsers and graceful absence handling (`src/index.ts:32-82`, `src/index.ts:103-153`).

The repository also keeps explicit workflow guidance in `.opencode/skill/canvas/SKILL.md:28-124` and `.opencode/skill/document/SKILL.md:22-149`. The skills make tool arguments and IPC message shapes discoverable, but the docs are not fully synchronized: the skill documents `canvas_content` (`.opencode/skill/canvas/SKILL.md:78-84`), while the plugin registers no `canvas_content` tool (`src/index.ts:421-427`). The README similarly says selection is the document retrieval operation (`README.md:87-95`), so consumers should treat the source registration as authoritative.

## Architecture and Patterns

- The controller generates a canvas ID, writes configuration to a temporary file, and launches `run-canvas.sh` in a tmux split (`src/index.ts:190-230`). The canvas and controller communicate with newline-delimited JSON over a Unix socket, a simple protocol suitable for streaming partial reads (`src/canvas/ipc/server.ts:39-55`, `src/canvas/ipc/client.ts:35-50`).
- The IPC types make controller-to-canvas and canvas-to-controller messages explicit, including update, close, selection, content, ready, cancellation, and error messages (`src/canvas/ipc/types.ts:3-19`). This is a good contract boundary for interactive tools.
- Scenario behavior is separated from rendering and centrally registered by `canvasKind:scenarioName` (`src/canvas/scenarios/registry.ts:10-40`). Typed scenario definitions describe interaction mode, close behavior, defaults, and result types (`src/canvas/scenarios/types.ts:3-17`).
- Document selection tracks source offsets rather than only rendered terminal coordinates, allowing formatted markdown to map back to the original content (`src/canvas/canvases/document/components/markdown-renderer.tsx:178-220`; `src/canvas/canvases/document/types.ts:38-75`).
- The terminal abstraction checks `TMUX`, reuses a recorded pane when possible, verifies stale pane IDs with `tmux display-message`, and otherwise creates a new pane while capturing its ID (`src/canvas/terminal.ts:24-59`, `src/canvas/terminal.ts:65-105`, `src/canvas/terminal.ts:129-145`).

## Pitfalls and Security Lessons

1. **Shell injection and quoting risk.** `canvas_spawn` builds a shell command by interpolating `id`, `socketPath`, and `scenario` into a string passed to `tmux split-window` (`src/index.ts:209-217`). The standalone terminal path does the same for the run script, ID, socket path, scenario, and a config-file command substitution (`src/canvas/terminal.ts:43-54`, `src/canvas/terminal.ts:111-123`). IDs generated by the plugin reduce risk for the normal path, but the CLI accepts these values directly (`src/canvas/cli.ts:16-33`), so untrusted command-line values can alter the shell command. Prefer argv-based execution or strict validation and shell quoting.
2. **Predictable, unauthenticated IPC.** Socket names are `/tmp/canvas-${id}.sock` (`src/canvas/ipc/types.ts:21-24`), and update/selection/close connect solely by that path without peer authentication (`src/index.ts:247-299`, `src/index.ts:318-375`, `src/index.ts:387-417`). Any local process able to guess an ID can send control messages or read selection/content responses. Use a private runtime directory, restrictive permissions, unguessable capability tokens, and message validation.
3. **IPC implementation/API drift appears to break the high-level API.** `createIPCServer` returns `Promise<IPCServer>` and accepts `onClientConnect`/`onClientDisconnect` (`src/canvas/ipc/server.ts:7-20`), but `spawnCanvasWithIPC` passes `onConnect`/`onDisconnect`, assigns the promise to `server`, and calls `server.close()`/`server.send()` as if it were resolved (`src/canvas/api/canvas-api.ts:40-57`, `src/canvas/api/canvas-api.ts:97-125`). This should be caught by a build or type test; as written, the convenience API is not consistent with its lower-level implementation.
4. **Runtime validation is thin.** JSON is parsed, then cast to `ControllerMessage` or canvas config without schema validation (`src/canvas/ipc/server.ts:46-52`, `src/canvas/ipc/client.ts:42-49`, `src/canvas/canvases/index.tsx:40-62`). Malformed configs can reach renderers, and arbitrary message objects are forwarded to callbacks. Validate discriminated unions and config bounds at the IPC boundary.
5. **Socket cleanup can be destructive when the CLI is used with arbitrary paths.** The IPC server unlinks any existing `socketPath` before listening and again during close (`src/canvas/ipc/server.ts:20-26`, `src/canvas/ipc/server.ts:77-82`). The plugin normally supplies a fixed `/tmp` convention, but the CLI exposes `--socket <path>` (`src/canvas/cli.ts:16-21`); validate that paths are socket files in an owned runtime directory before unlinking.

## Testing and Verification

The repository provides a `bun test` task (`.mise/tasks/test:1-3`) and documents `bun test` alongside build and lint commands (`README.md:132-146`), but the clone contains no test files or test-specific configuration. That leaves protocol framing, timeout/cleanup behavior, scenario dispatch, selection offset mapping, malformed JSON, tmux absence, and packaging contents unverified. The high-level API mismatch above is especially important evidence that a compile/typecheck gate is missing or not run.

The TypeScript configuration is strict and bundler-oriented (`tsconfig.json:2-12`), while ESLint enforces Prettier and treats console use as an error (`eslint.config.js:33-41`). However, `package.json` exposes a `types` entry at `dist/index.d.ts` but the build script only invokes Bun bundling and does not emit declarations (`package.json:11-23`; `.mise/tasks/build:1-3`). Consumers may therefore receive a missing declaration file, and strict compilation should be run as an explicit CI gate.

## Packaging and Release Lessons

The package declares `main: ./dist/index.js`, a Bun-specific source export, public npm access, and a files allowlist of only `dist`, `src`, and `media` (`package.json:9-16`, `package.json:25-35`). The allowlist omits `run-canvas.sh` and `.opencode/skill`, even though the runtime entrypoint expects the script at the package root (`src/index.ts:160-166`, `src/index.ts:209-217`) and the plugin loads skills from `.opencode/skill` (`src/index.ts:57-66`). A published npm install can consequently fail to spawn canvases and silently expose no bundled skills. Include required runtime assets in `files` or copy them into the build output, then test an actual packed tarball.

The publish workflow uses least-privilege `contents: read` and npm trusted publishing with `id-token: write`, builds before publishing, checks whether the version already exists, and publishes with provenance (`.github/workflows/publish.yml:11-17`, `.github/workflows/publish.yml:26-56`). Release guidance documents conventional commits, Release Please, pre-1.0 minor bumps for breaking changes, and OIDC provenance (`RELEASE.md:10-31`, `RELEASE.md:129-153`). These are strong supply-chain practices, but the workflow runs no tests or lint before release (`.github/workflows/publish.yml:26-30`), and its path filter ignores markdown-only changes rather than enforcing behavioral gates.

## Bottom Line

Opencode Canvas demonstrates a practical OpenCode plugin shape: typed tool registration, config-hook command injection, bundled skills, scenario registries, and newline-framed Unix-socket IPC for a separate TUI process. Its main reusable cautions are to avoid shell-string process launching, authenticate local IPC, validate messages/configuration, keep API and async types aligned, add real protocol tests, and verify the npm tarball contains every runtime asset and declared type file.
