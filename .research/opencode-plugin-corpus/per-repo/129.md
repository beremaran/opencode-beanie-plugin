## Summary

This is a Bun/TypeScript OpenCode plugin exposing one `websearch_cited` custom tool. It selects the first valid provider configuration in `config.provider` order, obtains credentials through OpenCode auth loaders, calls Google, OpenAI, or OpenRouter over `fetch`, and returns model-produced text with citations where the provider supplies them. The README explicitly describes the plugin as a single custom tool backed by the three providers and citation output (`README.md:1-13`).

## OpenCode Patterns

- **Custom tool registration:** The default plugin returns a `tool.websearch_cited` definition using `tool.schema.string()` for its query argument (`index.ts:167-210`). The tool receives OpenCode’s abort signal and passes it to each provider client (`index.ts:232-259`), a useful cancellation pattern for network-backed tools.
- **Separate auth hook exports:** The default export registers OpenRouter auth, while named `WebsearchCitedGooglePlugin` and `WebsearchCitedOpenAIPlugin` exports register the other providers (`index.ts:265-301`). This lets OpenCode load multiple plugin exports from one module, and the tests explicitly validate that all exports are functions and initialize as plugin instances (`websearch.test.ts:802-825`).
- **Auth loader registry:** Provider loaders register `getAuth` functions in a module-level map (`index.ts:32-40`, `index.ts:173-185`). Tool execution resolves the selected provider’s loader and fails before making a request when auth is absent (`index.ts:232-257`).
- **Config-time provider selection:** `config` scans provider entries in insertion order and selects the first non-empty `options.websearch_cited.model`; malformed, blank, or unsupported entries become a deferred configuration error (`index.ts:52-104`). The README documents the ordering behavior and its importance (`README.md:59-92`). This avoids failing plugin initialization while still producing an actionable tool error.
- **Runtime argument hardening:** Although the schema exposes only `query`, execution also rejects unknown keys and blank queries (`index.ts:210-230`). This is a useful defense against callers bypassing or weakening schema validation.
- **Provider abstraction:** The common `WebsearchClient` interface takes `query`, `AbortSignal`, and `getAuth` (`src/types.ts:1-7`). Provider-specific modules then normalize inputs, resolve credentials, perform the request, and return text (`src/google.ts:727-746`, `src/openai.ts:234-264`, `src/openrouter.ts:164-189`).
- **Citation formatting:** Google grounding metadata is converted to inline markers plus a `Sources:` section (`src/google.ts:155-184`). Insertions are performed against UTF-8 byte indices, not JavaScript code-unit offsets (`src/google.ts:238-265`), with a regression test covering Japanese text and emoji (`websearch.test.ts:81-126`).

## Pitfalls And Security Lessons

- **Credential exposure risk in source:** Google OAuth refresh requests include a literal client ID and client secret in the source (`src/google.ts:104-107`, `src/google.ts:331-343`). Even if the OAuth client is intended for a public client, embedding a secret in a distributable plugin should be treated as non-secret and reviewed against provider policy; private credentials must not be shipped this way.
- **Sensitive data in errors:** OpenAI failures include the request URL, serialized request body, and raw response body in the thrown error (`src/openai.ts:315-356`). The request body includes the user query and potentially long prompt/configuration data (`src/openai.ts:146-187`). This is useful for diagnosis but can leak user searches or provider responses into OpenCode logs/UI; production integrations should redact or bound those fields and avoid returning raw upstream bodies by default. OpenRouter similarly includes the serialized request and raw response body (`src/openrouter.ts:146-151`).
- **Module-global credential caches:** Google access tokens and resolved projects are cached in module-level maps keyed by refresh token (`src/google.ts:117-118`, `src/google.ts:310-329`, `src/google.ts:446-475`). The cache improves repeated calls and is tested (`websearch.test.ts:578-617`), but long-lived process state requires expiry/invalidation discipline and makes multi-user or shared-process isolation an important deployment consideration.
- **Provider precedence can surprise users:** The first valid provider wins rather than selecting by tool call or model availability (`index.ts:60-101`). The README warns that configuration order matters (`README.md:90`), but this remains a behavioral pitfall when users configure several providers.
- **Citation trust boundary:** Google source titles and URIs are copied directly into Markdown output (`src/google.ts:175-181`). OpenRouter asks the model to produce indexed citations in a prompt (`src/openrouter.ts:44-46`) and returns model text without independently reconstructing annotations (`src/openrouter.ts:61-103`, `src/openrouter.ts:154-161`). Consumers should treat citations as provider/model output, not as independently verified provenance.
- **OAuth compatibility coupling:** The Google OAuth path uses several hard-coded Code Assist endpoints, client metadata, a default project, and a refresh-token encoding convention (`src/google.ts:87-115`, `src/google.ts:294-307`, `src/google.ts:390-475`). This supports a practical integration but is brittle against undocumented endpoint or client changes; the fallback endpoint loop deliberately suppresses endpoint errors (`src/google.ts:407-426`), which can obscure the root cause.
- **JSONC parser limitation in the auxiliary CLI:** The CLI removes only whole-line `//` comments before calling `JSON.parse` (`cli.ts:78-95`). Inline comments, block comments, and JSONC strings containing comment-like text are not handled, despite the default path being `opencode.jsonc` (`cli.ts:60-63`).

## Testing Lessons

- The repository’s prescribed command, `AGENT=1 bun test --bail`, passed: 30 tests, 0 failures, 91 assertions.
- Tests cover configuration errors and precedence, unknown arguments, missing auth, successful Google/OpenAI/OpenRouter calls, endpoint and header selection, model propagation, OAuth refresh and project resolution, caching, provider failures, citation formatting, UTF-8 offsets, and plugin export initialization (`websearch.test.ts:23-126`, `websearch.test.ts:141-257`, `websearch.test.ts:400-617`, `websearch.test.ts:619-825`).
- Mocking global `fetch` and restoring it after each test isolates network behavior (`websearch.test.ts:129-139`). The tests assert both returned text and request details such as URL, headers, body, and provider-specific flags (`websearch.test.ts:227-296`, `websearch.test.ts:716-765`).
- Remaining coverage gaps are visible from the implementation/test shape: OpenRouter citation annotations are typed but not used to build citations (`src/openrouter.ts:17-29`, `src/openrouter.ts:61-103`), and the test suite does not exercise the standalone CLI’s JSONC parsing, filesystem errors, or auth-file validation (`cli.ts:70-161`). Tests also do not appear to assert that thrown errors redact query/response content, which would be valuable given the diagnostic behavior above.

## Config And Packaging

- README installation requires adding the package to the user config and recommends pinning a version; it also warns to put the plugin last because of auth-process interactions (`README.md:29-47`). Provider configuration is nested under `provider.<id>.options.websearch_cited.model` (`README.md:51-90`).
- Package metadata exposes ESM runtime output from `dist/index.js`, declarations from `index.d.ts`, and restricts published files to `dist`, declarations, README, and LICENSE (`package.json:1-35`). The build externalizes OpenCode SDK packages and `prepack` runs the build (`package.json:48-59`). This is a small dependency footprint: only `@opencode-ai/plugin` is a runtime dependency (`package.json:56-59`).
- TypeScript uses strict checking, bundler module resolution, explicit `.ts` imports, and `noUncheckedIndexedAccess` (`tsconfig.json:11-32`). Biome is the formatter/linter, and staged files run Biome plus `tsgo` (`biome.json:28-59`, `lint-staged.config.ts:1-4`).
- `cli.ts` is a useful local integration harness with explicit config/auth overrides and a `--query` interface (`cli.ts:245-323`), but it is not exposed as a package binary: `package.json` has no `bin` field and the published `files` list excludes `cli.ts` (`package.json:9-35`).
- The prompt synchronization script reads from a sibling OpenCode checkout and writes `src/codex_prompt.txt` (`scripts/sync-codex-prompt.ts:5-14`). That workflow is repository-layout dependent and should be run only where the expected sibling source exists; the generated prompt is imported as text by the OpenAI client (`src/openai.ts:1-3`).

## Reusable Takeaways

1. Use OpenCode auth loaders as the credential boundary and pass `AbortSignal` through every external request.
2. Validate tool arguments at execution time as well as through the declared schema, especially when tool calls can arrive from multiple clients.
3. Keep provider-specific HTTP and response parsing behind a small common client interface.
4. Test provider selection, auth modes, request headers/bodies, failure propagation, and Unicode citation offsets with mocked `fetch`.
5. Treat hard-coded OAuth material, module-global token caches, raw upstream error bodies, and model-generated citations as explicit security/reliability review items.
