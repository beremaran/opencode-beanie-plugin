## Summary

CC Safety Net is a multi-host coding-agent safety package. Its OpenCode surface is a typed `@opencode-ai/plugin` plugin that blocks destructive commands and secret-path access before tool execution. The README describes semantic command analysis, fail-closed behavior, policy presets, audit logging, and an OpenCode installation path rather than an OpenCode-only product (`README.md:32-35`, `README.md:165-175`).

## SDK and Registration

- The package depends on `@opencode-ai/plugin` as both a development dependency and optional peer dependency, and exports a normal ESM package entry (`package.json:5-13`, `package.json:61-77`).
- The entrypoint imports the SDK `Plugin` type and exports `CCSafetyNetPlugin`, created by a factory (`src/index.ts:1-4`). This keeps the public registration surface minimal while allowing tests/internal callers to inject guard dependencies through the factory (`src/integrations/opencode/plugin.ts:24-27`).
- The factory returns an async plugin initializer accepting OpenCode `PluginInput`; it uses `directory` as the project/config working root and optionally receives `homeDir` for policy/audit integration (`src/integrations/opencode/plugin.ts:17-29`).
- The initializer returns two hooks: `config` and `tool.execute.before` (`src/integrations/opencode/plugin.ts:31-43`).

## Hooks, Events, and Context

- `config` retains the current mutable OpenCode config object so later tool calls observe the final shell value, then merges the built-in `cc-safety-net` command with existing commands (`src/integrations/opencode/plugin.ts:32-41`). Existing commands win on name collision because they are spread after built-ins (`src/integrations/opencode/plugin.ts:34-40`).
- `tool.execute.before` rejects a missing/blank tool name and extracts a command from tool arguments before evaluating the request (`src/integrations/opencode/plugin.ts:43-68`).
- The adapter maps only exact `bash` to the command route; all other tool names are classified as patch/path/grep/glob/unknown (`src/integrations/opencode/plugin.ts:130-136`; `src/parser/tool-input.ts:84-95`). Tests explicitly ensure names such as `Bash`, `PowerShell`, and `shell` are not promoted to command executors (`tests/integrations/opencode/plugin.test.ts:247-257`).
- OpenCode’s configured shell is normalized by basename, with PowerShell and POSIX executable allowlists; unknown values use `auto` (`src/integrations/opencode/plugin.ts:114-127`). The real `bash` tool is therefore analyzed using the configured PowerShell route when appropriate (`tests/integrations/opencode/plugin.test.ts:206-245`).
- `workdir` is resolved beneath the configured project directory, with documented Windows `/c`, `/C:`, `/cygdrive`, and `/mnt` forms normalized. Invalid, inaccessible, or non-directory contexts fail closed (`src/integrations/opencode/plugin.ts:138-169`; `tests/integrations/opencode/plugin.test.ts:182-189`).
- The guard receives both `configCwd` and `executionCwd`, preserving distinction between project policy context and actual tool execution context (`src/integrations/opencode/plugin.ts:71-85`).

## Tools and Commands

- The plugin injects one built-in OpenCode command, `cc-safety-net`, whose description and template guide rulebook management (`src/integrations/opencode/builtin-commands/commands.ts:8-22`). The template is derived from the shared workflow section rather than duplicated (`tests/integrations/opencode/builtin-commands.test.ts:11-16`).
- The shipped skill instructs the agent to use `npx -y cc-safety-net rule doc`, inspect existing rules with `rule verify`/`rule list`, edit scope-specific rulebooks, and validate with `rule sync`, `rule verify`, and `rule list` (`skills/cc-safety-net/SKILL.md:8-35`).
- Tool input handling is defensive: it recognizes command and path-like shapes, rejects proxies/accessors/nonstandard prototypes, tracks cycles, and bounds depth, nodes, keys, and string sizes (`src/parser/tool-input.ts:49-64`, `src/parser/tool-input.ts:193-228`). Exceeding limits produces a fixed `tool input traversal limit exceeded` error (`src/parser/tool-input.ts:49-54`, `src/parser/tool-input.ts:227-229`).

## Auth and Providers

- No OpenCode auth, model provider, OAuth, API-key, or provider registration code was found. This plugin is a local pre-execution guard and does not call an AI provider.
- `homeDir` is used as trusted host context for policy/audit paths, not as an authentication mechanism (`src/integrations/opencode/plugin.ts:27-29`, `src/integrations/audit.ts:103-137`).

## State and Processes

- Runtime evaluation is synchronous within the pre-tool hook from the adapter’s perspective: it builds an invocation and calls `evaluateRuntimeGuard`; no background worker, daemon, network request, or process supervisor is used in this OpenCode path (`src/integrations/opencode/plugin.ts:78-106`).
- Session state is limited to the current config reference and the OpenCode `sessionID` supplied to audit callbacks (`src/integrations/opencode/plugin.ts:28-30`, `src/integrations/opencode/plugin.ts:87-94`).
- The broader package persists policy snapshots, rulebook locks/caches, and local JSONL audit logs, while runtime evaluation deliberately performs no repair writes or network requests (`SECURITY.md:20-23`).
- Installation/uninstallation edits `~/.config/opencode/opencode.json` or `.jsonc`, removes managed package-cache state, and uses atomic writes; it scans both candidate config filenames (`src/integrations/opencode/install.ts:12-29`, `src/integrations/opencode/install.ts:188-213`).

## Configuration

- Safety configuration is policy-driven with `standard`, `strict`, and `paranoid` levels. Environment variables can only raise protection; the resolver records capability sources for diagnostics (`src/policy/env.ts:13-25`, `src/policy/env.ts:27-44`, `src/policy/env.ts:76-169`).
- Supported environment controls include level, strict/paranoid modes, worktree mode, debug, and audit scope, with selected legacy aliases (`src/policy/env.ts:13-25`). Allowed-command audit recording is separately controlled; denials are always recorded (`src/policy/env.ts:56-65`).
- OpenCode config detection checks both `opencode.json` and `opencode.jsonc`, strips comments, and reports `configured` or `n/a`; there is intentionally no disabled state (`src/integrations/opencode/detect.ts:11-18`, `src/integrations/opencode/detect.ts:19-50`).
- The skill documents that custom rules live in `rulebook.json`, must be synchronized, and cannot weaken built-in protections (`skills/cc-safety-net/SKILL.md:37-49`).

## Errors and Security

- The adapter fails closed for malformed tool identity, unsafe/unusable working directories, and bounded-input violations (`src/integrations/opencode/plugin.ts:57-77`).
- Guard denials are typed internally, projected with optional command evidence, and formatted through a secret-redacting formatter (`src/integrations/denial.ts:11-39`, `src/integrations/denial.ts:42-60`). Policy/config-stage and secret-protection failures rethrow their underlying cause; other guard evaluations become formatted blocks (`src/integrations/opencode/plugin.ts:86-106`).
- Every preflight denial is audited with agent, tool, cwd, home, and session context before the error is thrown (`src/integrations/opencode/plugin.ts:45-55`). Audit serialization redacts recognized credential forms (`src/integrations/audit.ts:121-137`; `SECURITY.md:24`).
- The security model explicitly says this is a best-effort static gate, not an OS sandbox or privilege boundary; commands that bypass an installed integration remain outside its protection (`SECURITY.md:9-12`). Known boundaries include partial PowerShell path extraction and best-effort exact-path policy protection (`README.md:214-218`).
- Always-on protections cover root/home recursive deletion, Git metadata mutation, and canonical user policy mutation regardless of overrides (`SECURITY.md:40-42`). Resource limits cover recursive input, stdin, Git environment entries, rule synchronization, network responses, and rulebook validation (`SECURITY.md:27-30`).

## Pitfalls

- Treating arbitrary tool names as shells would create a bypass or false positive; the adapter deliberately grants command semantics only to exact `bash` (`src/integrations/opencode/plugin.ts:130-136`; `tests/integrations/opencode/plugin.test.ts:247-257`).
- Reading `workdir` without validating its root, existence, and platform spelling would evaluate policy against the wrong directory; the adapter rejects unusable paths and has Windows-specific normalization tests (`src/integrations/opencode/plugin.ts:138-169`; `tests/integrations/opencode/plugin.test.ts:182-189`).
- Blind JSON parsing/editing would corrupt JSONC or nested config structures; installation uses a comment/string-aware scanner and validates the rewritten document (`src/integrations/opencode/install.ts:32-128`, `src/integrations/opencode/install.ts:158-185`).
- Passing raw command/evidence into errors or audit logs risks secret exposure; projection and audit paths explicitly redact evidence (`src/integrations/denial.ts:54-60`; `src/integrations/audit.ts:121-137`).
- Relying on mutable config captured only at initialization would stale shell routing; the config hook stores the object reference and tests mutate it after registration (`src/integrations/opencode/plugin.ts:28-35`; `tests/integrations/opencode/plugin.test.ts:191-204`).
- The OpenCode adapter is only as complete as the host’s integration coverage. The project’s own model says unknown tools may receive conservative sensitive-path inspection but not arbitrary command execution semantics (`SECURITY.md:13-18`).

## Reusable Lessons

- Keep the host adapter thin: normalize host input, establish trusted execution context, construct a shared invocation, and delegate policy to one guard engine (`src/integrations/opencode/plugin.ts:61-105`).
- Make capability routing explicit and conservative. Exact tool-name grants avoid accidentally treating a lookalike tool as a shell (`src/integrations/opencode/plugin.ts:130-136`).
- Preserve user config and comments during installation by editing only the managed array range and validating the result (`src/integrations/opencode/install.ts:176-185`).
- Separate denial projection from engine decisions so each host chooses whether command evidence and tool names are exposed (`src/integrations/denial.ts:22-39`; `tests/integrations/denial.test.ts:17-43`).
- Bound every recursive/untrusted input before semantic analysis and return fixed diagnostics that do not echo attacker-controlled payloads (`src/parser/tool-input.ts:57-64`, `src/parser/tool-input.ts:174-229`; `tests/integrations/opencode/plugin.test.ts:68-109`).
- Test integration contracts at the host boundary, including configuration mutation, malformed input, platform path forms, preservation of unrelated config, and secret redaction (`tests/integrations/opencode/plugin.test.ts:111-245`; `tests/integrations/opencode/install.test.ts:38-180`; `tests/integrations/denial.test.ts:39-64`).
