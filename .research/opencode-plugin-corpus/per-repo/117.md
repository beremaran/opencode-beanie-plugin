UNMOJI removes RGI Unicode emoji from completed agent text and from Markdown `write`, `edit`, and `apply_patch` tool arguments. README documents the three output targets and explicitly excludes thinking tokens (`README.md:32-44`).

## OpenCode integration patterns

- Export a standard async `Plugin` factory and return a hook map. The entrypoint loads configuration, initializes shared runtime state, registers `experimental.text.complete`, and conditionally registers `tool.execute.before` (`src/index.ts:7-16`, `src/index.ts:34-78`). This is a clean separation between host integration and transformation code.
- Keep long-lived hooks independent of the complete `PluginInput`. The entrypoint captures only `directory` and a bounded diagnostic reporter backed by `client.app.log` (`src/index.ts:20-31`, `src/index.ts:34-43`). The integration test verifies that later hook execution does not retain or access the original client capability (`tests/integration/plugin.test.ts:60-99`).
- Mutate host hook outputs in place only after a successful transformation. Completion writes `output.text` only when removals occurred (`src/opencode/completion-hook.ts:73-89`); tool adapters leave the original arguments unchanged for invalid, no-op, oversized, or failed transformations (`src/opencode/tool-adapters.ts:61-107`, `src/opencode/tool-hook.ts:20-52`).
- Use per-tool adapters rather than one permissive argument mutation path. `write` targets `content`, `edit` targets `newString`, and `apply_patch` parses patch structure and rewrites only added Markdown lines (`src/opencode/tool-adapters.ts:69-107`, `src/opencode/tool-adapters.ts:391-565`). This reduces accidental changes to unrelated tools or patch context.
- Treat unsupported or malformed host input as a no-op. The tool hook dispatches only known tool names and catches adapter errors without rejecting the hook (`src/opencode/tool-hook.ts:25-52`); integration tests cover unknown tools, invalid args, disabled processing, and failed transformations (`tests/integration/tool-hook.test.ts:24-51`, `tests/integration/tool-hook.test.ts:87-119`).

## Configuration and behavior

- Configuration precedence is explicit: defaults, global `~/.config/opencode/unmoji.json`, project `.opencode/unmoji.json`, then inline plugin options (`src/config.ts:1-5`, `src/config.ts:171-202`). README gives the same locations and precedence, including inline array options (`README.md:46-90`).
- Validate every layer independently, reject unknown keys and invalid types, require a non-empty `.md`/`.markdown` extension list, and deduplicate extensions while retaining first-seen order (`src/config.ts:69-134`). Invalid or unreadable layers are non-fatal diagnostics, so a bad global file does not prevent later valid configuration (`src/config.ts:137-157`, `src/config.ts:171-202`; `tests/contract/config.test.ts:138-200`).
- Disable cheaply and safely. A disabled plugin returns `{}` before runtime initialization or hook registration (`src/index.ts:39-57`); the test also proves it does not access host services when disabled (`tests/integration/plugin.test.ts:38-50`).
- Make Unicode processing portable by generating a grapheme scanner and RGI expression from pinned data rather than requiring `Intl.Segmenter` (`src/runtime.ts:29-57`; `tests/integration/plugin.test.ts:189-217`). The stripping engine first performs broad candidate detection, then strict RGI classification, and scans protected Markdown spans only for candidates that can actually be removed (`src/text/strip.ts:26-69`).
- Preserve Markdown semantics through a stateful protected-span cursor. The scanner protects code fences, indented code, inline code, blockquotes according to policy, HTML comments/elements, links, autolinks, and ANSI escapes (`src/text/protected-spans.ts:1-5`, `src/text/protected-spans.ts:37-42`; `src/text/protected-html.ts:65-70`).

## Security and reliability lessons

- Fail open on transformation failures: preserve the original output/arguments, report a bounded diagnostic, and let the host continue (`src/opencode/completion-hook.ts:54-97`, `src/opencode/tool-hook.ts:25-52`). This is appropriate for a cosmetic plugin that must not corrupt agent work.
- Bound resource use at every long-lived boundary. Completion rejects text over 4,000,000 UTF-16 units and caps cumulative fixed-point work at 16,000,000 units (`src/opencode/completion-hook.ts:17-33`, `src/opencode/completion-hook.ts:54-85`); tool text is capped at 1,000,000 units (`src/opencode/tool-adapters.ts:25-27`, `src/opencode/tool-adapters.ts:61-67`).
- Bound diagnostic memory and logging risk. Diagnostic messages/kinds are normalized and capped, at most four wait behind a stuck logger, repeated kinds replace queued entries, and overflow is coalesced (`src/opencode/diagnostic-sink.ts:25-49`, `src/opencode/diagnostic-sink.ts:89-145`). Reporting is detached from hook completion and reporter failures are suppressed (`src/opencode/diagnostic-sink.ts:62-87`).
- Avoid leaking arbitrary thrown values. Error extraction is guarded, control characters are replaced, messages are truncated, and hostile error objects are covered by tests (`src/opencode/diagnostic-sink.ts:31-59`; `tests/integration/completion-hook.test.ts:98-146`, `tests/contract/config.test.ts:202-231`).
- Parse `apply_patch` conservatively. The adapter requires a complete Begin/End envelope, validates section/hunk markers, preserves context and deletion lines, and returns original args for malformed structures (`src/opencode/tool-adapters.ts:401-430`, `src/opencode/tool-adapters.ts:479-564`). It also uses typed-array line indexes and bounded fragment batches to limit peak memory on large patches (`src/opencode/patch-lines.ts:1-17`, `src/opencode/patch-lines.ts:141-181`).
- A remaining operational tradeoff is that both completion and tool processing silently preserve unmodified content when size/work limits are exceeded; diagnostics distinguish skipped work, but callers must decide whether that is acceptable for their policy (`src/opencode/completion-hook.ts:65-85`, `src/opencode/tool-adapters.ts:61-67`).

## Packaging and maintenance lessons

- Publish only `dist`, expose explicit ESM `main`, `types`, and conditional `exports`, and declare the OpenCode plugin as a peer dependency compatible with 1.x (`package.json:6-17`, `package.json:47-62`).
- Separate declaration and JavaScript builds. Type declarations are emitted from `src` into `dist`, while Bun bundles/minifies the runtime and externalizes `@opencode-ai/plugin` (`package.json:23-25`; `tsconfig.build.json:1-13`).
- Verify the actual packed artifact, not only the source tree. `verify-package.ts` packs with Bun, checks tarball/unpacked size, exact top-level files and `dist` contents, declaration contents, JS/gzip budgets, absence of development artifacts, runtime exports, and a strict NodeNext consumer type-check (`scripts/verify-package.ts:66-194`).
- Preserve cleanup failures instead of allowing temporary-directory cleanup to hide package verification failures; the helper uses `AggregateError` when both fail (`scripts/verify-package.ts:43-64`; `tests/contract/package-verification.test.ts:13-39`).
- Generated Unicode sources have a reproducible workflow: the fixture and checksum are pinned, generation is checked in CI/check commands, and contributors are told not to edit generated output directly (`CONTRIBUTING.md:38-47`; `package.json:43-45`).
- Release gates combine lint/typecheck/format/generated checks, expanded property tests, build, distribution tests, and package verification (`package.json:37-45`). This is stronger than relying on a source-only test run, especially for an ESM plugin whose consumer-facing declarations and export map can fail independently.

## Notable pitfalls

- The repository guidance requires `vp`, but `vp` was not available in the analysis environment (`AGENTS.md:1`; attempted `vp test run` returned `command not found`). No clone files were changed by that attempt.
- The package is tightly coupled to the OpenCode hook names and plugin API version range; upgrading OpenCode should be accompanied by integration/E2E verification (`src/index.ts:64-76`; `package.json:47-58`).
- Markdown parsing is intentionally a custom approximation rather than a full CommonMark parser. The broad protected-span surface is valuable, but changes to syntax handling should be accompanied by fixture/property tests because false positives can either remove user content or leave emoji behind (`src/text/protected-spans.ts:1-5`; `CONTRIBUTING.md:12-19`).
- The default `markdownExtensions` is only `[".md"]`, despite the README documenting support for `.md` and `.markdown`; `.markdown` requires explicit configuration (`README.md:68-90`, `src/config.ts:20-27`). This is documented behavior, but it is an easy deployment assumption to miss.

## Reusable takeaways

1. Keep OpenCode hooks thin and put transformation logic behind injectable, directly testable adapters.
2. Preserve host data on every failure and make diagnostics asynchronous, bounded, sanitized, and fail-open.
3. Bound text size, cumulative work, queued diagnostics, and patch assembly memory before processing untrusted model/tool output.
4. Validate layered configuration independently so one malformed optional file does not disable the plugin.
5. Test the packed package as a consumer, including runtime exports, declaration resolution, exact contents, and size/artifact budgets.
