## OpenCode patterns worth reusing

### Declarative registration and typed tool factories

- The entrypoint receives `client` and `directory`, builds a small workflow context, and returns a declarative `tool` map (`plugins/index.ts:13-43`). Each feature owns a factory that defines its schema and execution wiring, using `@opencode-ai/plugin`'s `tool.schema` (`plugins/tools/story-task.ts:15-24`, `plugins/tools/setup.ts:59-68`). This keeps registration thin and makes individual tools testable in isolation.
- The plugin separates OpenCode API interaction, filesystem storage, pure parsing, and orchestration. The stated boundary is explicit: `session/` owns API calls, `storage/` I/O, `parsers/` pure transformations, and `tools/` orchestration (`README.md:271-283`; `plugins/ARCHITECTURE.md:50-57`). This is a useful shape for plugins with many workflows.

### Child sessions and recursion control

- Agent work runs in a child session with `parentID`, an agent name, a prompt, and a tool map; the parent waits for idle and then extracts the last assistant text (`plugins/session/agent.ts:75-104`). Workflow tools are disabled in child sessions to prevent recursive workflow invocation (`plugins/session/agent.ts:7-22`).
- Direct-output agents receive an explicit plain-text/no-tools instruction, while dev agents retain project tools (`plugins/session/agent.ts:4-5`, `plugins/session/agent.ts:106-125`). Local-model mode additionally disables `read`, `glob`, `grep`, `webfetch`, and `task` after inlining context (`plugins/session/agent.ts:24-31`, `plugins/tools/story-task.ts:96-101`).
- The plugin uses a bounded polling loop with a five-minute timeout rather than waiting indefinitely (`plugins/session/polling.ts:3-19`). It resolves the current root session by excluding sessions with `parentID` (`plugins/session/context.ts:5-10`).

### Human review and deterministic state changes

- Document-producing workflows deliberately use preview then save. Preview files can be edited, save prefers the edited preview, and successful save removes the preview (`plugins/workflows/preview-save.ts:9-41`; `plugins/tools/review.ts:80-139`). The README documents this as a general safety invariant (`README.md:55-62`).
- The single-task workflow is interruptible: it resolves one unchecked task, builds a bounded prompt, runs one dev child session, then marks the task checkbox programmatically (`plugins/tools/story-task.ts:67-125`). This avoids relying on an LLM to update workflow state, a reliability improvement also recorded in the changelog (`README.md:329-335`).
- Status updates are intentionally non-LLM and patch both the YAML index and story file (`plugins/tools/story-update.ts:21-35`, `plugins/tools/story-update.ts:43-76`). Centralized path constructors reduce path-string drift (`plugins/constants/paths.ts:1-26`).

### Local-model resilience

- The local path uses deterministic, dependency-free prompt estimation (`plugins/parsers/tokens.ts:1-29`), a 60% soft budget gate and an automatic retry with aggressive shrinking (`plugins/tools/story-task.ts:156-170`). Stories keep only the target task block, relevant acceptance criteria/dev notes, and the final agent record when appropriate (`plugins/parsers/shrink.ts:26-61`).
- The design is conservative when relevance filtering finds too little: it retains all acceptance criteria or all dev notes instead of silently producing an empty context (`plugins/parsers/shrink.ts:103-125`, `plugins/parsers/shrink.ts:196-224`).

## Pitfalls and security lessons

- **Relative paths are trusted.** `readDoc`, `writeDoc`, and preview cleanup join caller-provided relative paths to the project directory without normalization or containment checks (`plugins/storage/docs.ts:4-20`; `plugins/workflows/preview-save.ts:40-42`). Most paths are constants, but review scope becomes part of a slug and future tool inputs could enable traversal. Validate that resolved paths remain under the project root before reading, writing, or deleting.
- **Installer mutates global user configuration and executes package-manager commands.** The installer copies commands/plugins/agents into the selected OpenCode config directory, writes `opencode.json`, and runs `bun install --silent` or `npm install --silent` in that directory (`install.js:91-109`, `install.js:173-200`). This is an intentional installation model, but it needs clear consent/backup behavior and should be tested against malformed or pre-existing config directories.
- **Config parsing only accepts strict JSON.** A JSON parse failure causes registration to be skipped with a manual instruction (`install.js:61-72`), so JSONC/comments or another valid OpenCode config syntax would not be preserved. The installer also rewrites valid JSON formatting when it patches the plugin list (`install.js:75-86`).
- **Broad catch blocks hide operational failures.** Missing files, malformed workflow config, and other read errors all collapse to empty/default values (`plugins/storage/docs.ts:4-10`; `plugins/storage/config.ts:7-13`; `plugins/storage/stories.ts:20-27`). This is convenient for first-run behavior but can turn permissions, corruption, or I/O failures into misleading "not found" results.
- **Regex-based YAML mutation is fragile.** The architecture explicitly avoids a YAML parser and delegates manipulation to string logic (`plugins/ARCHITECTURE.md:271-279`). In addition, the optional status note is inserted through a JavaScript replacement string (`plugins/tools/story-update.ts:56-61`), so replacement metacharacters in user text can alter the replacement result. Use a replacement callback and validate/parse YAML when correctness or untrusted input matters.
- **Session selection assumes one active root.** `findLast` chooses the last root session returned by the API (`plugins/session/context.ts:5-10`). If multiple concurrent root sessions exist, a tool can attach work to the wrong parent. Prefer an explicit current-session identifier when the host exposes one.
- **Prompt shrinking is heuristic, not a security boundary.** It uses lowercase token overlap and a character-based token estimate (`plugins/parsers/shrink.ts:227-240`; `plugins/parsers/tokens.ts:6-10`). It can omit semantically important notes or under-estimate model overhead. The documented 60% gate is a practical guard, not proof that the provider will accept the request (`README.md:82-98`).

## Testing and verification

- The repository has pure parser tests for sections, shrinking, and token budgeting; tests use Bun's runner (`plugins/parsers/sections.test.ts:1-57`; `plugins/parsers/shrink.test.ts:42-181`; `plugins/parsers/tokens.test.ts:1-41`). The clone's `bun test plugins/parsers` passes: 27 tests, 0 failures.
- Packaging has explicit gates: `prepublishOnly` runs tests then builds `plugins/index.ts` to ESM with Bun (`package.json:13-17`). `bun run build` succeeds in this clone, and `bunx tsc --noEmit` succeeds. The generated `dist/` output was removed after verification so the clone remained unmodified.
- Coverage is concentrated in pure transformations. There are no checked-in integration tests for OpenCode session creation/prompting/polling, tool schemas, installer behavior, config patching, preview/save persistence, or status updates. Those are the highest-value missing tests because they cross API, filesystem, and user-state boundaries.
- The dev-agent contract asks agents to read before editing, write tests, avoid scope creep, and record modified files (`agents/dev.md:7-48`); the local-model guide independently recommends diff, compile, scope, and smoke-test gates (`docs/LOCAL_MODELS.md:165-204`). These are good operational controls, but most are documentation/prompt requirements rather than enforced checks.

## Packaging and distribution

- The package is ESM, exposes `dist/index.js`, and publishes a CLI bin named `opencode-bmad-workflow`; runtime dependencies pin the OpenCode plugin package to `1.4.7` and SDK to `1.4.1` (`package.json:1-11`, `package.json:31-38`).
- `npx opencode-bmad-workflow` is the intended install path because the installer copies files into `~/.config/opencode/` and registers the plugin rather than relying on a project `node_modules` lookup (`README.md:104-131`). Agents are copied only when absent, while commands and plugins are overwritten on reinstall (`install.js:173-189`); this asymmetric behavior should be documented as a possible customization-loss risk.
- `.npmignore` excludes lockfiles, `opencode.json`, and local config files but does not exclude source, README, agents, commands, or plugins (`.npmignore:1-7`). The package therefore contains the installer inputs needed for a self-contained npx installation.

## Bottom line

The strongest pattern is a thin OpenCode entrypoint backed by typed tool factories, isolated child sessions, pure transformation modules, preview/save boundaries, and deterministic state updates. The main production risks are the installer’s broad filesystem/config mutation, unchecked path composition, silent I/O fallback, heuristic YAML editing, and lack of integration coverage around session and persistence behavior.
