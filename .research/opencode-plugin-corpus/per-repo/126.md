## What the project does

This is a Bun monorepo with four separately published surfaces: a shared extraction library, an MCP server, a Claude Code hook, and an OpenCode plugin (`README.md:296-305`). The README describes the core behavior as injecting TypeScript signatures into reads, reporting type errors after writes, and exposing lookup tools (`README.md:1-3`). The OpenCode package is the full plugin; the documented alternative is MCP-only operation without automatic injection (`README.md:7-27`).

## OpenCode patterns

- **Keep the adapter thin and put behavior in a reusable core.** The plugin imports `TypeExtractor`, `ContentFormatter`, `TypeLookup`, prioritization, filtering, and diagnostics from `@nick-vi/type-inject-core` rather than implementing parsing in the hook (`packages/opencode/.opencode/plugin/type-inject.ts:3-18`). This makes the same behavior available to MCP and Claude integrations.
- **Fail closed at initialization when the project is not applicable.** The plugin checks `config.enabled` and returns an empty plugin, then checks for a root `tsconfig.json` and returns an empty plugin if it is absent (`packages/opencode/.opencode/plugin/type-inject.ts:20-41`). This avoids installing hooks into non-TypeScript projects, though it also means nested-only configs are not supported by the OpenCode adapter.
- **Correlate before/after tool lifecycle events with the tool call ID.** `tool.execute.before` records the read path and range in `currentReads` keyed by `input.callID`; `tool.execute.after` retrieves and deletes that entry before processing (`packages/opencode/.opencode/plugin/type-inject.ts:51-56`, `packages/opencode/.opencode/plugin/type-inject.ts:250-279`). This is a useful pattern when the after hook receives output but not the original arguments.
- **Preserve the original read and prepend explicit context.** The after hook skips unsupported extensions, extracts only relevant types, filters types already visible in the returned content, and assigns the formatted result back to `output.output` (`packages/opencode/.opencode/plugin/type-inject.ts:288-360`). The formatter uses `<types>` markers, counts, an estimated token total, and a separator before the original content (`packages/core/lib/formatter.ts:19-45`, `packages/core/lib/formatter.ts:48-60`).
- **Make injected references actionable.** Function/class signatures carry read-compatible offsets, while transitive imports additionally carry `filePath` hints (`packages/core/lib/formatter.ts:109-132`). Tests lock down direct versus transitive behavior (`packages/core/tests/formatter.test.ts:103-186`).
- **Bound context by policy rather than raw extraction size.** Defaults enable import traversal only to depth 4, include only used/transitive types, skip barrel files, and cap injection at 10,000 tokens (`packages/core/lib/config.ts:21-35`). Prioritization guarantees functions first, then signature dependencies, transitive dependencies, local types, and remaining imports (`packages/core/lib/prioritizer.ts:1-10`, `packages/core/lib/prioritizer.ts:69-102`).
- **Support partial reads as a first-class case.** The extractor accepts an offset/limit range and filters types against that range (`packages/core/lib/extractor.ts:65-73`, `packages/core/lib/extractor.ts:146-157`); the plugin passes the same range through from the read tool (`packages/opencode/.opencode/plugin/type-inject.ts:307-314`).
- **Expose narrowly shaped tools with schema validation.** The OpenCode tools use `tool.schema` enums for type kinds and typed optional arguments (`packages/opencode/.opencode/plugin/type-inject.ts:57-94`, `packages/opencode/.opencode/plugin/type-inject.ts:160-180`). MCP mirrors this with Zod schemas (`packages/mcp/src/index.ts:36-57`, `packages/mcp/src/index.ts:125-135`).
- **Return bounded, navigable results.** Lookup defaults to five results, usage output is capped at ten files, and list output defaults to 100 names (`packages/opencode/.opencode/plugin/type-inject.ts:84-101`, `packages/opencode/.opencode/plugin/type-inject.ts:132-151`, `packages/opencode/.opencode/plugin/type-inject.ts:177-186`).

## Pitfalls and security lessons

- **Do not assume a root config covers every project layout.** The plugin requires `path.join(directory, "tsconfig.json")` at startup (`packages/opencode/.opencode/plugin/type-inject.ts:33-41`), while its type-check tool separately finds a nearest config for a supplied file (`packages/opencode/.opencode/plugin/type-inject.ts:204-220`). This behavior is inconsistent for monorepos or nested packages: diagnostics can locate a nested config, but automatic injection never starts unless the workspace root has one.
- **Validate and constrain user-supplied paths.** `type_check.file` is accepted as an arbitrary string and passed to `findNearestTsconfig` and TypeScript diagnostics (`packages/opencode/.opencode/plugin/type-inject.ts:204-220`). The checker resolves paths relative to `cwd` and runs `tsc` with the selected project (`packages/core/lib/checker.ts:25-41`, `packages/core/lib/checker.ts:81-92`). A production plugin should enforce project-root containment, reject traversal/absolute paths where inappropriate, and avoid exposing diagnostics for unrelated files.
- **Avoid unbounded or stale lifecycle state.** The `currentReads` map is deleted in the after handler, but there is no timeout or cleanup path if the after event never arrives (`packages/opencode/.opencode/plugin/type-inject.ts:51-56`, `packages/opencode/.opencode/plugin/type-inject.ts:271-279`). A long-lived process should add bounded cleanup to prevent memory growth.
- **Treat hook input as hostile and preserve hook availability.** The Claude hook parses all stdin with `JSON.parse` outside a try/catch (`packages/claude-hook/src/index.ts:15-21`), so malformed hook input can terminate the process noisily. Later read/write processing catches extraction/checking failures and exits silently (`packages/claude-hook/src/index.ts:52-97`, `packages/claude-hook/src/index.ts:124-155`), a good availability policy but one that should be paired with safe input parsing and optional diagnostics logging.
- **Review installer supply-chain tradeoffs.** The README recommends piping a remotely fetched shell script directly to Bash (`README.md:30-36`). The script then installs tools using `npx -y` and edits the global Claude settings file (`scripts/claude-install.sh:12-24`, `scripts/claude-install.sh:53-94`). This is convenient, but installers should preferably pin versions, show the fetched source or checksum, make a backup, and use a structured JSON merge that cannot be affected by shell interpolation.
- **Do not let type extraction become a hidden resource sink.** Index construction scans project TypeScript files and recursively finds Svelte files, skipping only selected directories (`packages/core/lib/lookup.ts:186-220`, `packages/core/lib/lookup.ts:222-280`). The lazy index is useful (`packages/core/lib/lookup.ts:119-144`), but large repositories need explicit file/size/time limits and cache invalidation policy.
- **Regex-based semantic heuristics can misclassify types.** Prioritization identifies references using PascalCase matching and a hard-coded built-in set (`packages/core/lib/prioritizer.ts:234-291`). This is lightweight and fast, but aliases, namespaced types, quoted strings, and unusual naming can produce false dependencies or omit required context.

## Testing lessons

- The tests use Bun's native test runner and fixture-driven assertions (`packages/core/tests/extractor.test.ts:1-3`, `packages/core/tests/extractor.test.ts:23-29`). Coverage includes import depth, JSDoc, line ranges, typed versus untyped arrow functions, and Svelte instance/module scripts (`packages/core/tests/extractor.test.ts:48-80`, `packages/core/tests/extractor.test.ts:82-134`, `packages/core/tests/extractor.test.ts:147-227`).
- Lookup tests cover exact/partial matching, kind filtering, result limits, stats, Svelte indexing, and line offsets (`packages/core/tests/lookup.test.ts:25-69`, `packages/core/tests/lookup.test.ts:72-130`). Prioritizer tests cover mandatory function inclusion, budget exclusion, dependency ordering, and barrel detection (`packages/core/tests/prioritizer.test.ts:8-93`). Formatter tests cover navigation comments, transitive import paths, and missing line metadata (`packages/core/tests/formatter.test.ts:26-211`).
- There are important gaps: no OpenCode plugin lifecycle tests, no MCP protocol/stdio integration test, no malformed hook-input test, no path-containment test, and no installer test. The repository's CI runs only install, typecheck, and test (`.github/workflows/ci.yml:7-15`).
- Verification at the audited checkout was not green: `bun test` ran four files but reported 0 passing and failed before execution because `ts-morph` was unavailable; `bun run typecheck` reported missing dependencies plus numerous strict-mode implicit-`any` errors in `packages/core/lib/extractor.ts` and `packages/core/lib/lookup.ts`. These failures indicate the checkout was not dependency-installed/build-ready, not that the individual assertions necessarily fail.

## Packaging and release lessons

- The OpenCode package publishes only `.opencode/`, points `main` directly at the plugin entrypoint, declares `@opencode-ai/plugin` and TypeScript as peers, and marks Svelte optional (`packages/opencode/package.json:5-29`). This is a compact OpenCode distribution pattern, but the published entrypoint is source TypeScript, so compatibility with the OpenCode loader must be verified for every release.
- Core and CLI packages publish build output through `files`, `exports`, and `bin`; build scripts use Bun bundling and `prepare` builds on installation (`packages/core/package.json:6-42`, `packages/mcp/package.json:5-15`, `packages/claude-hook/package.json:5-15`). This keeps tarballs small and gives CLI packages executable entrypoints.
- Workspace dependencies are intentionally rewritten before publish because npm does not understand `workspace:` (`scripts/resolve-workspace-deps.ts:3-6`). The release script runs that rewrite before `changeset publish` (`package.json:11-13`). This is practical, but it mutates package manifests during release; CI should inspect the resulting package metadata and ensure the rewritten version ranges match the intended compatibility policy.
- Release gating runs typecheck and tests before the Changesets action, uses npm provenance, and grants publish-related GitHub permissions (`.github/workflows/release.yml:9-26`, `.github/workflows/release.yml:38-48`). The workflow is a useful baseline, but it does not build/install-test each package's packed artifact before publication.

## Bottom line

The strongest reusable pattern is a small OpenCode event adapter over a shared, independently testable analysis core, with explicit token budgeting and read-compatible source locations. The highest-priority hardening work would be project-root path validation, lifecycle-state expiry, safe hook input parsing, installer/version pinning, and CI coverage for plugin/MCP boundaries plus packed-package smoke tests. The audited checkout's dependency and strict typecheck failures should also be resolved before treating the release pipeline as a reliable quality gate.
