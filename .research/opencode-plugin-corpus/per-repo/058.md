## Architecture and OpenCode Patterns

- The plugin is a single exported `Plugin` implementation. It selects `worktree` over `directory`, making the git worktree the policy root when available (`index.ts:239-242`). This is a useful multi-worktree pattern, but it means `.ignore` is not read from `directory` when the two differ.
- `.ignore` is loaded with `Bun.file(...).exists()` and parsed by the `ignore` package; a missing file returns `null` and permits access (`index.ts:12-21`, `index.ts:77-86`). This gives an explicit fail-open compatibility mode, documented as “missing `.ignore`, all access allowed” (`README.md:153-170`).
- `tool.execute.before` maps `read`, `write`, and `edit` to `args.filePath`, and `glob`, `grep`, and `list` to `args.path` with `.` as the default (`index.ts:201-215`). Unsupported tools are intentionally skipped (`index.ts:213-214`).
- The pre-execution hook blocks matched paths by throwing an error, while always allowing the exact project-root path `.` (`index.ts:248-261`). The README clearly separates pre-execution blocking from post-execution filtering (`README.md:130-149`).
- The post-execution hook filters `glob` file arrays and `grep` match arrays, removing blocked entries rather than returning partial secret content (`index.ts:263-273`, `index.ts:97-145`). This is an important defense-in-depth pattern because searches rooted at `.` are allowed while their results can still contain protected descendants.
- Path normalization makes absolute paths relative to the policy root, removes `./`, converts backslashes, adds directory slashes, and validates the result with `isPathValid` (`index.ts:39-66`). The README exposes these semantics to users (`README.md:179-187`).

## Security Lessons and Pitfalls

- The two-phase design is the strongest security lesson: direct file operations are denied before execution, and `glob`/`grep` outputs are filtered after execution (`index.ts:248-273`). Tests explicitly verify that grep output containing credentials, private-key markers, and secret values is removed (`index.spec.ts:619-643`).
- Negation is delegated to the established `ignore` implementation instead of reimplemented. The fixture demonstrates sensitive defaults plus deliberate exceptions such as public files, local config, and `target` (`test-data/.ignore:1-66`).
- The implementation fails open when `.ignore` is absent (`index.ts:77-81`), which is operationally convenient but should be treated as a deployment/security prerequisite rather than a secure default. The README advertises this behavior (`README.md:167-170`).
- There is no explicit containment check that rejects a path outside `projectRoot`. `relative(projectRoot, absolutePath)` can produce a parent-relative path, after which only the ignore-library validator is consulted (`index.ts:40-64`). A caller supplying `../...` therefore relies on library validation and hook error behavior rather than a clear “outside project” policy.
- `filterGrepResults` preserves matches with no `file` property (`index.ts:130-144`). That accommodates malformed or metadata-light results, but it weakens the guarantee that every post-hook match is attributable to an allowed file; callers should ensure the OpenCode result schema cannot carry sensitive content in such records.
- Filtering errors are fail-closed for individual glob/grep entries: normalization failures remove the entry or match (`index.ts:104-111`, `index.ts:132-141`). This is safer than exposing uncertain paths, but the pre-hook path-validation error is not converted into the plugin’s documented `Access denied` message (`index.ts:61-64`, `index.ts:257-260`).
- `.ignore` is parsed on every before/after-hook operation (`index.ts:77-86`, `index.ts:164-166`). That keeps changes visible immediately, but repeated filesystem reads and parsing can add latency to every native tool call. A cache would need an explicit invalidation strategy if live edits to `.ignore` are required.

## Testing Lessons

- The tests use extensive `any` casts and untyped hook helpers (`index.spec.ts:9-25`, `index.spec.ts:81-87`). That makes fixture setup easy, but it reduces compile-time detection of OpenCode API drift. The source has the same issue for filter inputs and outputs (`index.ts:97-101`, `index.ts:125-129`, `index.ts:156-160`).

## Overall Assessment

`opencode-ignore` demonstrates a focused OpenCode plugin pattern: use `tool.execute.before` for hard path denial, use `tool.execute.after` to sanitize search results, normalize paths before applying gitignore semantics, and test both phases independently. Its main operational/security caveats are fail-open absence of `.ignore`, reliance on library validation rather than explicit project-boundary enforcement, preservation of file-less grep matches, repeated parsing, and a likely declaration-package mismatch. The repository is small, documented, MIT-licensed, and has a passing Bun test/build workflow, but its tests mock hook inputs rather than exercising the live OpenCode tool runtime.
