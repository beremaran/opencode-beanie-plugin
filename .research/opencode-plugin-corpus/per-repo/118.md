## What It Does

This repository is primarily a Python Slack/Feishu notifier, with a separately packaged OpenCode plugin. The README describes remote-safe completion alerts and identifies Slack Web API plus Feishu/Lark incoming webhooks as the two providers (`README.md:6-12`, `README.md:19-22`). The OpenCode package listens for `session.idle`; the documentation says it sends to one or both configured providers (`docs/opencode_plugin.md:3-9`).

## OpenCode Integration Patterns

- **Conventional npm package surface:** `package.json` uses an ESM package, points `main` and `types` at the nested plugin files, and exposes the same entrypoint through conditional `exports` (`package.json:1-13`). The package is intentionally limited to `opencode-plugin` by its `files` allowlist (`package.json:15-16`).
- **Typed plugin export:** The declaration file imports OpenCode's `Plugin` type and declares canonical, compatibility, and default exports (`opencode-plugin/index.d.ts:1-5`). The runtime implements the canonical plugin, aliases the old name, and exports it as default (`opencode-plugin/index.js:292-356`).
- **Event filtering:** The returned plugin object uses an `event` handler and ignores every event except `session.idle` (`opencode-plugin/index.js:292-301`, `opencode-plugin/index.js:119-122`). This is a minimal pattern for side-effect integrations that should not react to the full event stream.
- **Useful runtime context:** The handler prefers `worktree`, then `directory`, then `process.cwd()` for the repository label and includes `sessionID` when available (`opencode-plugin/index.js:323-325`, `opencode-plugin/index.js:139-144`).
- **Non-blocking provider isolation:** Slack and Lark delivery are attempted independently, and each provider error is caught and logged rather than escaping the event handler (`opencode-plugin/index.js:327-349`). A failed Slack send therefore does not prevent a configured Lark send.
- **Operational controls:** Timeout, retry, debounce, and debug behavior are environment-configurable with positive-integer parsing and defaults (`opencode-plugin/index.js:5-7`, `opencode-plugin/index.js:22-28`, `opencode-plugin/index.js:41-46`, `opencode-plugin/index.js:292-296`).
- **User-level configuration:** The plugin searches an explicit env-file override, a legacy override, then `~/.config/opencode/agent-notifier.env` and its legacy path; it loads the first readable regular file once (`opencode-plugin/index.js:48-63`, `opencode-plugin/index.js:76-117`). The documented OpenCode config uses the package name in the `plugin` array (`docs/examples/opencode/opencode.json:1-4`).
- **Provider response validation:** Slack checks both HTTP success and the API-level `ok` flag (`opencode-plugin/index.js:175-185`); Lark accepts an empty response but rejects malformed JSON and nonzero `code` or `StatusCode` responses (`opencode-plugin/index.js:194-220`, `opencode-plugin/index.js:257-264`).
- **Retry and timeout behavior:** Both transports use `AbortController`, clear their timers in `finally`, retry one 429 according to `Retry-After`, and retry one 5xx after one second (`opencode-plugin/index.js:146-191`, `opencode-plugin/index.js:224-270`).

## Security And Reliability Lessons

- **Do not treat env files as secret storage:** The README explicitly calls the setup lightweight rather than secure and recommends an OS keychain or credential helper for stronger protection (`README.md:40-63`). The plugin reads arbitrary paths supplied by `OPENCODE_AGENT_NOTIFIER_ENV_FILE` and does not check ownership or mode (`opencode-plugin/index.js:48-60`, `opencode-plugin/index.js:82-105`). A production plugin should document and/or enforce restrictive permissions for token files.
- **Webhook URLs are bearer secrets:** Lark webhook URLs are accepted directly from environment variables and posted without validation or signing (`opencode-plugin/index.js:305-309`, `opencode-plugin/index.js:232-244`). The setup documentation says signature verification is disabled for this notifier version (`README.md:128-133`). This is a clear deployment tradeoff: protect the URL like a credential and prefer signed webhooks where the provider supports them.
- **Avoid marking delivery complete before delivery succeeds:** `shouldNotify` records the session timestamp before either provider request is made (`opencode-plugin/index.js:129-136`), then network failures are swallowed (`opencode-plugin/index.js:333-347`). A transient failure can therefore suppress a retry for the debounce window. Recording only after successful delivery, or tracking in-flight/failed states separately, would improve at-least-once behavior.
- **Bound process-global state:** Debounce timestamps live in a module-global `Map` keyed by session ID and are never evicted (`opencode-plugin/index.js:14`, `opencode-plugin/index.js:124-136`). Long-lived OpenCode processes with many sessions can accumulate entries; TTL cleanup or bounded storage is safer.
- **Be careful with diagnostic content:** Slack non-2xx errors include up to the complete response body in the thrown message (`opencode-plugin/index.js:175-178`), and that detail is logged (`opencode-plugin/index.js:333-335`). Error bodies can contain provider or proxy data; logs should be bounded and redacted if they may contain sensitive content. Lark explicitly truncates malformed response previews to 500 characters (`opencode-plugin/index.js:194-205`), which is a useful pattern not applied consistently to Slack.
- **Environment parsing is intentionally simple:** The loader handles comments, optional `export`, and simple quoted values but does not implement full dotenv escaping or multiline values (`opencode-plugin/index.js:87-105`). This is reasonable for a tiny integration, but the supported syntax should remain documented and tested.
- **Payload/debug paths need trust boundaries:** The generic shell wrapper accepts a file path or inline JSON, falls back to stdin, and can write the selected payload to a caller-provided debug path (`scripts/notifier/agent_notify_wrapper.sh:7-29`, `scripts/notifier/agent_notify_wrapper.sh:35-45`, `scripts/notifier/agent_notify_wrapper.sh:91-97`). Hook configuration should only use trusted paths because payloads may include project or transcript metadata.

## Testing Lessons

- **Good contract coverage:** `test_opencode_plugin.py` checks package metadata and entrypoint files, including canonical/default/legacy exports and provider markers (`tests/notifier/test_opencode_plugin.py:18-70`). This catches accidental packaging or rename regressions.
- **Good network isolation:** The OpenCode tests replace `globalThis.fetch`, exercise both providers, assert endpoint order and payloads, and verify worktree/session formatting (`tests/notifier/test_opencode_plugin.py:73-159`). They also cover Lark API errors and successful non-JSON responses (`tests/notifier/test_opencode_plugin.py:161-272`).
- **Python tests model provider behavior without real network calls:** Fake sessions/responses cover Slack DM sequencing, rate-limit retry, Lark payloads, API errors, payload validation, env-file precedence, and legacy aliases (`tests/notifier/test_slack_notify.py:20-88`, `tests/notifier/test_slack_notify.py:207-299`, `tests/notifier/test_slack_notify.py:302-421`).
- **Coverage gap for the OpenCode-specific state machine:** The checked-in JS tests do not exercise ignored event types, repeated same-session debounce, missing-credential warning-once behavior, env-file candidate precedence, timeout/5xx retry, or the failure-then-retry consequence of pre-delivery timestamping (`tests/notifier/test_opencode_plugin.py:73-272`; implementation at `opencode-plugin/index.js:119-136`, `opencode-plugin/index.js:304-320`). These are the highest-value additions for a plugin test suite.
- **Runtime availability is not guaranteed by the repository's declared CI:** The only workflow runs pre-commit on Python 3.12 (`.github/workflows/pre-commit.yml:1-23`); it does not run pytest, Node tests, npm packaging, or an OpenCode smoke test. In this audit environment, `pytest -q` could not run because `pytest` was not installed. `npm pack --dry-run --json` did succeed and showed a five-file package containing `LICENSE`, `README.md`, `package.json`, and both `opencode-plugin` files.

## Packaging And Maintenance

- **Dual-language packaging is explicit:** Python metadata requires Python 3.12 and `requests`, with pytest/ruff/pre-commit as dev dependencies (`pyproject.toml:5-20`); setuptools maps packages from `src` and includes the canonical plus legacy Python package names (`pyproject.toml:22-24`).
- **The npm package is dependency-light:** It declares only an OpenCode peer dependency (`package.json:37-39`) and uses built-in Node modules plus global `fetch` in the source (`opencode-plugin/index.js:1-4`, `opencode-plugin/index.js:154-161`). This reduces install complexity but makes the supported Node/fetch runtime an important undocumented compatibility contract.
- **Package contents are controlled, but reproducibility is weak:** The `files` allowlist is a strong safeguard against publishing Python sources and local material (`package.json:15-16`), while `package-lock.json` is explicitly ignored (`.gitignore:205-207`) and there is no npm test/script declaration (`package.json:1-40`). A release workflow should run a clean pack/install smoke test and verify the tarball's entrypoint.
- **Documentation is unusually complete for hook integrations:** The README links dedicated setup, provider, integration, and plugin docs (`README.md:9-14`), provides official OpenCode install/config examples (`README.md:98-126`), and documents migration aliases (`README.md:200-206`). Keeping compatibility names visibly secondary helps future renames without making them the primary API.
- **License and repository metadata are present:** The npm package declares MIT, repository, bugs, and homepage metadata (`package.json:28-36`), and the repository includes the MIT license text (`LICENSE:1-21`).

## Bottom Line

The strongest reusable pattern is a small OpenCode `event` plugin with strict event filtering, explicit context selection, isolated provider failures, bounded HTTP attempts, and a narrow npm package allowlist. The most important hardening work would be to test and redesign debounce semantics around failed delivery, bound the session map, secure env-file handling, redact provider error bodies, and add CI coverage for Python tests plus Node/plugin packaging and runtime smoke tests.
