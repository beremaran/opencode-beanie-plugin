- The README describes the plugin as a CCS configuration synchronizer that manages only `ccs-*` providers, preserves unrelated OpenCode config/comments, selects one deterministic default, and syncs at startup and on file changes (`README.md:10-21`).

## SDK and registration

- The package uses the OpenCode plugin SDK types and `tool()` helper. `createServer()` returns an async `Plugin` factory, and the module exports both a `PluginModule` (`id: 'opencode-ccs-sync'`, `server`) and the server as default/named exports (`src/index.ts:1-2`, `99-120`, `169-177`).
- Registration is deliberately small: one tool named `ccs_sync` with optional boolean `dryRun` and `watch` schema arguments (`src/index.ts:120-127`). The design explicitly requires one plugin entrypoint and one machine-oriented tool (`docs/superpowers/specs/2026-04-04-opencode-ccs-sync-design.md:84-115`, `117-175`).
- Tool execution receives OpenCode tool context, including `sessionID`, `messageID`, `directory`, and `abort`; these are logged and the abort signal is passed into runtime work (`src/index.ts:128-142`). Results are serialized as indented JSON, while failures are logged and rethrown (`src/index.ts:144-161`).

## Hooks, events, and lifecycle

- There are no OpenCode event hooks or chat/message handlers. The plugin uses the async plugin-load callback as its lifecycle entrypoint and immediately starts `runWatchMode` in the background (`src/index.ts:99-118`).
- Watch mode performs an initial sync, watches the resolved CCS config, OpenCode config, and CCS directory with Chokidar, then re-syncs on relevant `change`/`add` events (`src/watch/watch.ts:112-118`, `157-207`). Relevant CCS-directory files are top-level `*.settings.json`; unrelated nested/log files are ignored (`src/watch/watch.ts:61-98`).
- Self-generated OpenCode writes are suppressed for 1.5 seconds using a SHA-256 content hash, preventing the watcher from immediately reprocessing its own output (`src/watch/watch.ts:24-46`, `150-185`). A single `running` promise prevents concurrent sync bodies, but a changed event arriving during a run is discarded rather than queued (`src/watch/watch.ts:161-190`), a possible missed-update pitfall.
- If startup sync fails, watch mode clears managed providers (unless dry-run), synthesizes a failed result, and continues watching for CCS recovery (`src/watch/watch.ts:117-148`). Watcher errors reject the waiting promise and are closed in `finally` (`src/watch/watch.ts:200-207`), but the startup caller only logs a failed background promise (`src/index.ts:102-118`).

## Tools and commands

- `ccs_sync` supports two modes: normal `runSync` and long-lived `runWatchMode`; both share dependency construction and options (`src/index.ts:74-96`, `137-143`). There is no standalone CLI or shell command. The design intentionally rejected a CLI-first application and keeps watch mode in the shared runtime (`docs/superpowers/specs/2026-04-04-opencode-ccs-sync-design.md:32-76`, `221-235`).
- Sync resolves project `opencode.json`/`opencode.jsonc` before global equivalents, and defaults CCS input to `~/.ccs/config.yaml` (`src/config/paths.ts:38-68`). The README documents package installation through the OpenCode `plugin` array and local `.opencode/plugins` or global plugin directories (`README.md:88-113`).
- The service reads CCS YAML plus live `~/.ccs/*.settings.json`, discovers models from CLIProxy, filters discovered models to explicitly selected live settings, detects each provider protocol, builds provider-local model records, and patches OpenCode (`src/sync/service.ts:218-268`, `276-377`).

## Auth and providers

- This is not an OAuth/auth-provider plugin. It creates OpenCode custom provider records and supplies a fixed bearer token, `ccs-internal-managed`, to CLIProxy (`src/config/ccs.ts:4-10`, `224-242`; `src/sync/service.ts:178-201`). The same token is sent as an `Authorization: Bearer` header during model discovery (`src/cliproxy/client.ts:107-124`).
- Provider discovery prefers live settings files whose `env` contains `ANTHROPIC_BASE_URL` or `ANTHROPIC_MODEL`; files with only hooks are ignored. It extracts the four Anthropic model selection variables, deduplicates/sorts them, and retains only models found by CLIProxy (`src/config/ccs.ts:101-164`, `167-213`; `src/sync/service.ts:301-331`).
- Each managed provider is named `ccs-<provider>`. Protocol probing checks the base URL, `/models`, and `/v1/models`, classifies SSE as Anthropic and JSON as OpenAI-compatible, and caches the result in memory by URL/plugin version (`src/sync/protocol.ts:13-35`, `69-118`, `132-163`). The service selects `@ai-sdk/anthropic` for Anthropic protocol and `@ai-sdk/openai-compatible` otherwise, with protocol-specific base URL normalization (`src/sync/service.ts:178-201`).
- The global OpenCode default is deterministic: lexicographically first provider, then its preferred `ANTHROPIC_MODEL` if discovered, otherwise its first sorted model (`src/sync/service.ts:77-103`, `334-338`; `README.md:263-278`).

## State and processes

- Persistent state is OpenCode configuration itself; runtime state is limited to the in-memory protocol cache and watcher/write-loop guard (`src/sync/protocol.ts:136-163`; `src/watch/watch.ts:24-41`). No database, session store, worker, or child process is used by the implementation.
- Model discovery retries transient network/5xx failures up to five attempts in the current implementation, with exponential backoff capped at 30 seconds; 4xx errors fail immediately and abort cancels retrying (`src/cliproxy/client.ts:59-88`, `107-147`; `src/utils/backoff.ts:1-5`). This matches the changelog’s startup retry cap (`CHANGELOG.md:3-8`) but differs from the design document’s older “retry indefinitely” constraint (`docs/superpowers/specs/2026-04-04-opencode-ccs-sync-design.md:19-30`).
- Provider discovery is serial per provider, while protocol probing is parallelized across selected providers (`src/sync/service.ts:309-321`, `340-353`). This limits request fan-out for model discovery but still allows simultaneous protocol probes.

## Configuration and patching

- YAML is parsed with `yaml` and normalized to sorted, deduplicated providers, a local CLIProxy port-derived URL, and the fixed token; invalid YAML parser errors are propagated (`src/config/ccs.ts:215-242`).
- JSONC patching uses `jsonc-parser`. It removes/replaces only provider keys beginning `ccs-`, preserves non-managed providers, sorts the merged provider object, removes the root `models` field, and writes the global `model` field (`src/opencode/patch.ts:17-54`). Tests verify comment and unrelated-provider preservation plus second-pass idempotence (`tests/opencode/patch.test.ts:4-47`, `49-80`).
- Writes are direct `writeFile` calls with no temporary file, atomic rename, backup, or locking (`src/sync/service.ts:370-378`; `src/watch/watch.ts:100-109`). A crash or competing OpenCode/plugin instance could leave a partial or last-writer-wins config. This is the main reliability gap in an otherwise narrowly scoped patcher.
- The README correctly emphasizes provider-local `models`, not a root-level models map (`README.md:280-316`), and tests cover this shape (`tests/sync/service.test.ts:183-205`).

## Errors and security

- Plugin logging is structured through `client.app.log`, includes operation mode/session/path metadata, normalizes unknown errors to strings, and logs startup/tool failures (`src/index.ts:25-56`, `128-161`). The returned tool payload remains JSON-only (`src/index.ts:144-153`).
- Malformed settings JSON is ignored during provider inference rather than aborting the complete scan (`src/config/ccs.ts:109-118`, `135-157`, `178-205`), whereas malformed CCS YAML and unreadable primary config files fail the sync. This gives graceful handling for individual optional provider files but can make configuration mistakes look like absent providers.
- The bearer token is written into OpenCode config as `options.apiKey` and embedded in discovery requests (`src/sync/service.ts:193-200`, `src/cliproxy/client.ts:118-123`). Although it is described as an internal local token, persisting a credential-like value in user config and exposing it to any config reader should be documented as a trust boundary; a configurable secret source would be safer.
- Provider base URLs are accepted from live settings and written into config with only slash normalization (`src/sync/service.ts:356-366`, `169-176`). The code does not restrict schemes/hosts, so a malicious or compromised settings file could redirect model discovery and runtime traffic. The repository should treat CCS settings as trusted input or validate allowed endpoints.
- The protocol probe performs unauthenticated GET requests with a 2.5-second timeout and reads at most 256 bytes, which limits response consumption but still contacts arbitrary configured URLs (`src/sync/protocol.ts:11-12`, `37-67`, `69-99`).

## Reusable lessons and pitfalls

- Keep an OpenCode plugin’s public surface small: one typed async factory, one structured tool, and dependency injection make startup, manual execution, and unit tests straightforward (`src/index.ts:13-23`, `99-165`).
- Use a narrow ownership convention such as `ccs-*`, merge only managed keys, and preserve JSONC with a syntax-aware editor instead of parse/stringify (`src/opencode/patch.ts:23-54`).
- Prefer live provider settings over a broad provider pool, then intersect explicit user selections with runtime discovery. This avoids writing misleading model inventories (`src/config/ccs.ts:124-164`; `src/sync/service.ts:323-331`).
- Deterministic sorting and default selection make repeated automation predictable (`src/sync/service.ts:63-75`, `77-103`, `161-166`).
- Watchers need both self-write suppression and explicit handling for event coalescing, queued updates, close/error behavior, and atomic writes. This implementation demonstrates the first two mechanisms but drops events during an active run and writes configs non-atomically (`src/watch/watch.ts:150-207`; `src/sync/service.ts:376-378`).
- Keep documentation and implementation constraints synchronized: the design says indefinite transient retry, while the shipped implementation caps attempts at five. Tests and changelog support the cap, so the design is stale (`docs/superpowers/specs/2026-04-04-opencode-ccs-sync-design.md:19-30`; `src/cliproxy/client.ts:114-147`; `CHANGELOG.md:3-8`).
