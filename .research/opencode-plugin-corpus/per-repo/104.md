## What it is

This is an instruction bundle, not a conventional executable OpenCode plugin. The README describes the project as OpenCode instructions for safely running shell commands in a non-interactive environment (`README.md:1-7`). Installation is by adding the raw `shell_strategy.md` URL to OpenCode’s `instructions[]` configuration and restarting OpenCode (`README.md:9-23`). The strategy file explicitly says it is loaded as an OpenCode instruction file and is portable to comparable headless hosts (`shell_strategy.md:1-5`).

`package.json` is metadata-only: it declares version `1.1.0`, an MIT license, keywords, and `shell_strategy.md` as `main`, but no dependencies, scripts, or JavaScript entrypoint (`package.json:1-16`). This makes the artifact easy to consume without installation, while the npm shape may be misleading to tooling that expects `main` to be executable code.

## OpenCode patterns worth reusing

### Headless-shell policy

- State the execution constraint first: no TTY/PTY means prompts, pagers, and editors can hang until timeout (`README.md:3-7`; `shell_strategy.md:1-5`).
- Prefer command-specific non-interactive flags over generic force flags, and fail visibly when authorization or user choice is unavailable (`shell_strategy.md:7-13`, `15-40`).
- Treat editors, pagers, interactive git modes, REPLs, and interactive shells as explicit hazards (`shell_strategy.md:7-13`; `README.md:40-49`).
- Prefer host tools such as `Read`, `Write`, and `Edit` for file operations instead of shell text manipulation (`shell_strategy.md:11-13`). This is a useful OpenCode-specific guardrail because it steers agents toward tool-mediated, inspectable edits.
- Use per-command environment variables rather than global profile mutation; the document specifically warns not to set anti-hang variables globally (`shell_strategy.md:105-120`).

### Security-sensitive command guidance

- SSH guidance combines `BatchMode=yes`, `StrictHostKeyChecking=accept-new`, and a short `ConnectTimeout`; changed host keys still fail, while unknown keys can be accepted only for explicitly trusted first contact (`shell_strategy.md:42-50`).
- The policy explicitly prohibits `StrictHostKeyChecking=no`, password piping, and `sudo -S`; privileged commands should use `sudo -n` and fail immediately if a password is needed (`shell_strategy.md:52-60`).
- It rejects blanket prompt approval such as `yes | ...` or heredocs and instead requires an authorized flag, fail-fast mode, or visible stop/report (`shell_strategy.md:15-40`; `README.md:52-56`). This preserves user authorization boundaries rather than trading safety for automation.
- The examples distinguish safe command-specific forms such as `npm init -y`, `apt-get install -y`, `pip install --no-input`, `git --no-pager log`, and `git commit -m`/`--no-edit` (`shell_strategy.md:19-36`, `62-87`).

### Installation and distribution

- The README also documents local use as an optional contribution/editing workflow rather than requiring a local plugin directory (`README.md:21-23`).
- Release notes record behavior changes and explicitly state that the verification script is dependency-free and that no runtime dependencies were added (`README.md:82-89`).

## Testing lessons

`test.sh` is a POSIX shell fixture with three modes (`red`, `green`, and `verify`) and uses only POSIX shell, `awk`, and `grep` (`test.sh:1-11`). It validates that both documents exist, extracts fenced `sh`/`bash`/`zsh` blocks, rejects selected unsafe patterns, requires key safe forms, and checks that README installation uses `instructions[]` with a raw `trunk/shell_strategy.md` URL (`test.sh:26-33`, `42-61`, `73-111`, `113-143`). The repository’s `./test.sh verify` run passed all assertions.

The test has a notable coverage pitfall: in the awk block it strips `content` down to the first non-empty line before checking prohibited patterns (`test.sh:73-86`). Consequently, prohibited text on later lines of a fenced shell block is not checked, despite the surrounding comment claiming block-level scanning (`test.sh:42-43`). Required-form checks do use the complete extracted blocks (`test.sh:95-111`), so positive coverage and negative coverage are asymmetric. A stronger fixture should scan the full block content, while still preserving any explicit negative-example exemption.

The checker also validates exact README installation conventions, including rejection of the old local plugin path and clone-based primary installation (`test.sh:113-143`). This is a good example of testing documentation as an integration surface, but those assertions are coupled to a particular URL branch (`trunk`) and file name (`shell_strategy.md`), so a legitimate hosting/layout change would require synchronized test updates.

## Pitfalls and limitations

- The policy is advisory text loaded through `instructions[]`; it has no runtime enforcement or capability boundary (`README.md:9-23`; `shell_strategy.md:1-5`). A model or tool caller can still violate it, so higher-risk environments need host-level command policy and timeouts as defense in depth.
- The command tables are curated examples, not a complete shell grammar or threat model. For example, the prohibited-pattern test list is short (`test.sh:42-61`), and the strategy itself says “similar TTY tools” without enumerating every tool (`shell_strategy.md:7-10`).
- The test’s first-line-only negative scan can produce false confidence for multiline examples (`test.sh:73-86`).
- `package.json` has no `test` script and no dependency declarations (`package.json:1-16`), so npm consumers do not get a standard test entrypoint; verification currently requires invoking `./test.sh verify` directly.
- The README points at a mutable branch URL (`README.md:15-17`). Pinning a release/tag or commit would improve reproducibility and reduce supply-chain drift, at the cost of requiring explicit updates for new guidance.
- File operations in the policy correctly warn that destructive commands should verify targets, but the examples still include commands such as `rm -rf` in test cleanup (`shell_strategy.md:89-96`; `test.sh:35-40`). The cleanup is bounded to a generated temp path, yet a future fixture should preserve that target-safety discipline.

## Packaging and licensing

The project is MIT-licensed in both package metadata and the repository license (`package.json:14-15`; `LICENSE:1-21`). `.gitignore` is minimal and excludes `node_modules`, macOS metadata, and logs (`.gitignore:1-3`). There is no build step, generated artifact, runtime dependency, or package script in the inspected tree. The practical distribution unit is the Markdown instruction file, with README installation and the raw URL serving as the package interface.

## Bottom line

The strongest reusable pattern is a narrowly scoped instruction file that translates headless execution constraints into explicit, command-specific safety rules and visible authorization failures. It is unusually clear about SSH host-key behavior and password handling. Its main engineering weakness is verification coverage: the dependency-free test is useful and currently green, but its negative-pattern scanner checks only the first non-empty line of each fenced block, so it should not be treated as comprehensive safety validation.
