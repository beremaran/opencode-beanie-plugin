# Manifest 120: Warcraft Notifications

## Scope and Snapshot

- Manifest index 120 resolves to `Warcraft Notifications`, repository `https://github.com/pantheon-org/opencode-warcraft-notifications`, with analysis at the repository root and no separate manifest subdirectory (`.research/opencode-plugin-corpus/repo-map.json:1822-1834`). The reviewed clone is pinned to commit `2f0b9e2e48daa97553b39a8089f0b50d75ac9235`.
- The repository is a Bun/TypeScript OpenCode plugin with bundled WAV assets, source tests, documentation, GitHub Actions, and release tooling. The package publishes `index.ts`, `src/`, `data/`, README, and LICENSE (`package.json:27-34`).

## OpenCode Patterns

- **Minimal entrypoint plus named plugin export.** The package entrypoint re-exports `NotificationPlugin` from `src/notification` (`index.ts:1`). The plugin factory consumes OpenCode's `client` and shell runner `$`, then returns an `event` hook (`src/notification.ts:35-40`, `231-252`). This is a small, recognizable pattern for event-only plugins.
- **Event-to-state-to-side-effect flow.** Text from `message.part.updated` is retained as the latest message, and `session.idle` derives a bounded summary before playing a sound and showing a toast (`src/notification.ts:238-249`; `src/notification-utils.ts:23-62`). The summary extractor recognizes Markdown `Summary:` lines and truncates ordinary text to 80 characters (`src/notification-utils.ts:46-62`).
- **Graceful optional UI side effects.** Installation and toast operations are isolated so a toast failure does not prevent plugin initialization or sound handling; errors are logged and fallback notifications are attempted (`src/notification.ts:46-82`, `121-138`, `201-223`). This is a useful reliability boundary for non-essential TUI work.
- **Local bundled assets avoid runtime network dependency.** Initialization copies missing WAV files from the package's `data/` directory into user storage, skips existing files, ignores non-WAV entries, and processes entries with `Promise.allSettled` (`src/bundled-sounds.ts:217-220`, `252-286`). The README makes the same operational promise (`README.md:19-23`, `88-90`, `224-231`).
- **Platform-specific playback with fallback.** macOS uses `afplay`, Linux tries `paplay` then `aplay`, and missing-file fallback uses `Glass.aiff` on macOS or `canberra-gtk-play` on Linux; Windows logs that playback is unsupported (`src/notification.ts:147-179`). The documented support status accurately calls Windows partial (`README.md:201-217`).
- **Configuration is project-first and strict.** The loader searches the current working directory's `.opencode/plugin.json` before the global config (`src/config/loader.ts:76-83`, `123-155`). Zod accepts only `soundsDir`, `faction`, and `showDescriptionInToast`, rejects unknown keys, and formats actionable errors (`src/schema-validator.ts:25-40`, `111-127`, `164-207`).
- **Package identity is resolved defensively.** Storage naming prefers the plugin-root `package.json` and only falls back to the current working directory, then verifies the expected scoped package name before constructing the default path (`src/config/package.ts:41-83`; `src/config/paths.ts:65-100`). This avoids accidentally using the host project's package name when OpenCode changes the working directory.
- **Structured logging follows a useful plugin convention.** Logs include level, module, timestamp, and optional context; warnings/errors go to stderr and info/debug to stdout, with debug gated by `DEBUG_OPENCODE` (`src/logger.ts:22-45`, `59-75`).

## Security and Pitfalls

- **Custom storage paths are not constrained.** `soundsDir` is accepted as any string (`src/schema-validator.ts:25-30`), and installation creates directories and writes files beneath it (`src/bundled-sounds.ts:252-267`). The security document recommends that users keep overrides inside their user directory, but the implementation does not enforce that recommendation (`SECURITY.md:168-180`). A hostile or mistaken config can therefore cause writes outside the normal user data root.
- **`path.join()` is not a complete security boundary.** The security policy claims that joining paths prevents traversal (`SECURITY.md:16-21`), but the actual boundary is the configured base directory plus fixed bundled filenames (`src/bundled-sounds.ts:37-55`, `114-147`). If future code accepts arbitrary filenames or symlinked target directories, canonical-path checks and safer file creation would still be required.
- **Debug logging can disclose configuration paths and config values.** The loader logs search paths and the validated config when `DEBUG_OPENCODE` is enabled (`src/config/loader.ts:124-132`, `56-65`), while path resolution prints package paths and the selected sounds directory (`src/config/package.ts:50-59`, `67-90`; `src/config/paths.ts:70-98`). This is reasonable for diagnosis, but debug output should be treated as potentially sensitive in CI or collected logs.
- **Environment-dependent constants can become stale.** `DEFAULT_DATA_DIR` captures `SOUNDS_DATA_DIR` at module evaluation (`src/config/paths.ts:103-112`), and sound/bundled-sound modules import and use that constant (`src/sounds/index.ts:1-4`, `30-36`; `src/bundled-sounds.ts:3-6`, `252-254`). The same module also exposes a call-time resolver (`src/config/paths.ts:109-112`), but the main runtime path does not consistently use it. Tests or embedders that set the environment after import can observe surprising behavior.
- **The advertised security examples and implementation have drifted.** `SECURITY.md` shows an `osascript`-based macOS command and a separate notification command (`SECURITY.md:37-82`), while the current plugin uses Bun `$` directly for playback and OpenCode `client.tui.showToast` for notifications (`src/notification.ts:147-179`, `201-220`). Security documentation should be generated or tested against the actual command paths to avoid relying on obsolete escaping claims.
- **The package is Bun-oriented despite a Node engine declaration.** The source relies on Bun's `$` shell template and `Bun.file` (`src/notification.ts:35-48`, `src/config/loader.ts:43-46`), while `package.json` declares both Node >=18 and Bun >=1 (`package.json:87-90`). The package main is TypeScript and the build uses `tsc` with `noEmit`, so this is not a conventional Node-consumable compiled package (`package.json:27`, `35-60`; `tsconfig.json:7-10`). Consumers should verify the OpenCode/Bun loader contract rather than infer Node compatibility from `engines`.
- **Documentation quality affects operational trust.** Several README links are malformed or missing closing parentheses (`README.md:39-46`, `96`, `171-175`, `257-260`, `326`, `334-344`), and the documented `test-toast-manual.ts` path is not present in the inspected file inventory. The repository has dedicated link-validation scripts, but the snapshot still contains these defects (`package.json:51-54`; `scripts/validate-docs-links.cjs`).

## Testing Lessons

- **The repository has unusually broad unit coverage for a small plugin.** The package exposes test, coverage, watch, type-check, lint, schema, documentation-link, and package-verification scripts (`package.json:35-60`). Tests cover configuration errors with file context (`src/config/loader.coverage.test.ts:8-42`), unknown and malformed values (`src/schema-validator.coverage.test.ts:15-57`, `115-157`), bundled-file failures and non-WAV filtering (`src/bundled-sounds.failures.test.ts:7-51`), and faction edge cases plus injectable existence checks (`src/sounds/index.edge.test.ts:4-29`).
- **Tests use dependency seams effectively in pure modules.** `soundExists` accepts an injected existence function (`src/sounds/index.ts:46-55`), and the test supplies a throwing checker to verify error propagation (`src/sounds/index.edge.test.ts:12-28`). Temporary directories, cwd/env/platform helpers, and cleanup are centralized (`src/test-utils.ts:24-41`, `81-133`), which is a reusable pattern for filesystem/platform plugins.
- **The main integration test does not exercise the main integration path.** It verifies that the export is a function and checks the function name, but does not call `NotificationPlugin` with a context or invoke its returned event hook (`src/notification.integration.test.ts:12-32`). The separate `scripts/verify-plugin.cjs` does attempt initialization and event delivery (`scripts/verify-plugin.cjs:49-87`), but it is not wired into `package.json` and uses CommonJS `require` against an ESM/TypeScript source path (`scripts/verify-plugin.cjs:14`; `package.json:26-27`). A true Bun integration test with mocked `$`, TUI, config, and filesystem would provide stronger regression evidence.
- **Several behavioral tests assert re-created literals rather than production behavior.** For example, toast durations and shell command strings are constructed in the test itself (`src/notification.behavior.test.ts:75-123`, `239-257`) instead of observing calls from the plugin. Such tests document intent but can pass while implementation wiring regresses.
- **The checked snapshot has a portability-sensitive test failure.** Running `bun test src` produced 263 passing tests and one failure in `withCwd`: the temporary path returned under `/var/folders` was reported by `process.cwd()` under `/private/var/folders` (`src/test-utils.test.ts:52-73`). The helper itself correctly restores cwd in `finally` (`src/test-utils.ts:104-115`), but the test compares path spellings rather than canonical paths. The failure did not modify the clone.
- **Independent static gates passed locally.** `bun run type-check` and `bun run build` completed successfully. CI also runs formatting, Markdown lint, ESLint, type-check, coverage tests, build, filesystem Trivy scanning, and Codecov upload (`.github/workflows/1-validate.yml:16-67`, `69-91`). The workflow pins third-party action SHAs and limits pull-request token permissions (`.github/workflows/1-validate.yml:8-10`, `23-34`), which is a strong supply-chain pattern.

## Packaging and Maintenance Lessons

- **Ship the assets explicitly.** The `files` allowlist includes both `src/` and `data/`, which is essential because runtime installation depends on packaged WAV files (`package.json:28-34`; `src/bundled-sounds.ts:177-196`). A package verification step is included in `prepublishOnly` (`package.json:59-60`), but an actual `npm pack --dry-run` result was not used as evidence in this review.
- **Lockfile and automated release hygiene are present.** `bun.lock`, Dependabot configuration, release-please configuration, and a PR validation workflow are checked in (repository inventory; `package.json:62-85`; `.github/dependabot.yml`; `.github/release-please-config.json`). This supports reproducible development and automated versioning, though CI uses `bun-version: 'latest'` rather than a fixed version (`.github/workflows/1-validate.yml:28-32`), which can introduce moving toolchain behavior.
- **Keep runtime behavior local and bounded.** The plugin does not download sounds at runtime, installs only missing `.wav` files, and uses fixed toast durations (`src/notification.ts:16-21`, `46-58`; `src/bundled-sounds.ts:217-220`). These constraints reduce network, overwrite, and unbounded-output risk.

## Bottom Line

This is a good example of a focused OpenCode event plugin: a minimal named entrypoint, explicit hook lifecycle, local bundled resources, strict config validation, platform fallbacks, structured logs, and strong static/CI hygiene. The main lessons are to test the actual hook and side-effect wiring rather than only data shapes, make path policy enforceable rather than documentary, avoid import-time environment capture, align security documentation with current code, and make the package/runtime contract explicit for Bun versus Node. The snapshot is statically healthy but has one macOS path-normalization-sensitive test failure.
