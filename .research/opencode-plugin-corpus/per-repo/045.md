## OpenCode Patterns

- **Primary router plus hidden workers:** The config hook creates a visible `conclave` primary agent whose prompt always invokes the `conclave` tool, and registers Captain/Harper/Benjamin/Lucas as `subagent` agents (`src/index.ts:40-50`, `src/index.ts:67-101`; `src/agents/prompts.ts:1-7`). This gives users one TUI entry while preserving named child-session targets.
- **Use host child sessions instead of direct provider calls:** Each worker and Captain call creates a child session with `parentID`, prompts it with an explicit agent/model, and deletes it in `finally` (`src/orchestrator/subagent.ts:21-35`, `src/orchestrator/subagent.ts:53-81`; `src/orchestrator/captain.ts:27-50`). The ADR correctly identifies the benefits: host-managed authentication, rate limiting, cost tracking, retries, and model routing (`docs/adrs/ADR-001-opencode-plugin-architecture.md:18-32`).
- **Parallel fan-out:** The debate loop invokes all configured sub-agents with `Promise.all`, then sends their answers to a Captain critique (`src/orchestrator/captain.ts:83-124`). This is a useful orchestration pattern, but it means one rejected worker aborts the whole round because there is no per-worker error isolation around the `Promise.all`.
- **Runtime config resolution:** The plugin reads `client.config.get()` at tool-call time, resolves per-agent `provider/model` strings, and falls back to the global model or a hard-coded GitHub Copilot model (`src/config/loader.ts:33-60`). This preserves user model configuration without a plugin-specific file. The parser treats a string without `/` as `{ providerID: 'unknown', modelID: ... }` rather than rejecting it (`src/config/loader.ts:23-30`), so invalid model configuration can reach the SDK.
- **Config hook preserves overrides:** Existing agent config is snapshotted before defaults are written; user fields such as model and persona are preserved, while persona is rebuilt into both `prompt` and `options.persona` to handle OpenCode’s two internal paths (`src/index.ts:28-38`, `src/index.ts:50-64`). The format section is kept separate from the replaceable persona (`src/config/loader.ts:5-20`; `src/agents/prompts.ts:46-56`).
- **Bounded orchestration:** The tool schema constrains `maxRounds` to an integer from 1 to 10, and the loop has a hard cap (`src/tools/orchestrate.ts:14-27`, `src/orchestrator/captain.ts:72-85`). It also checks the host abort signal before starting and before each round (`src/orchestrator/captain.ts:77-85`).
- **Useful secondary entry points:** The plugin registers `/conclave` with `config.command`, allowing invocation outside the primary tab (`src/index.ts:103-109`). The README documents TUI, CLI, slash-command, and direct-tool usage (`README.md:164-202`).

## Reliability and Pitfalls

- **LLM output is only shape-cast, not validated:** Sub-agent JSON is parsed and cast directly to `AgentResponse`; missing or wrong-typed fields are accepted. Only absent code fences and JSON syntax errors use the raw-text fallback (`src/orchestrator/subagent.ts:63-77`). Captain critique has the same issue: `JSON.parse` is not guarded, and a fenced but malformed critique can throw out of the orchestration (`src/orchestrator/captain.ts:127-135`). Use schema validation and a safe parse path for every model response.
- **Prompt injection/data exposure surface:** The original query and prior Captain synthesis are interpolated into worker prompts, and all worker answers are interpolated into Captain prompts without delimiting or provenance rules (`src/orchestrator/subagent.ts:38-51`, `src/orchestrator/captain.ts:113-117`). For untrusted repository/user content, explicitly separate instructions from quoted data and bound prompt sizes.
- **Sensitive configuration is logged:** The config hook writes all agent keys and the complete raw Harper configuration to stderr (`src/index.ts:28-32`). A persona or future config field could contain private instructions or secrets. Remove these diagnostics or gate/redact them behind an opt-in debug flag.
- **Cleanup failures are silently discarded:** Child-session deletion is best effort in both runners (`src/orchestrator/subagent.ts:78-81`, `src/orchestrator/captain.ts:48-50`). This prevents cleanup errors from hiding useful results, but abandoned sessions can accumulate; production code should at least log cleanup failures and consider bounded cleanup/reconciliation.
- **Stopping contract has drift:** The implementation stops immediately at `0.83` and uses `0.75` plus two secondary signals (`src/orchestrator/stopping.ts:3-5`, `src/orchestrator/stopping.ts:14-35`), while the comments claim `0.92`/`0.88` (`src/orchestrator/stopping.ts:9-13`). The README says the default is three rounds and consensus `>= 0.83` (`README.md:11-14`), but the tool and orchestrator default to five rounds (`src/tools/orchestrate.ts:16-22`, `src/tools/orchestrate.ts:33-38`; `src/orchestrator/captain.ts:72-74`). Keep docs, comments, and runtime defaults generated from one source.
- **Dead or stale API promises:** `OrchestrateArgs` includes `subAgents`, but the tool never exposes or consumes it (`src/types.ts:72-78`, `src/tools/orchestrate.ts:14-39`). `StopReason` includes four semantic reasons that `evaluateStopping` never returns (`src/types.ts:52-62`, `src/orchestrator/stopping.ts:14-35`). The Captain prompt describes a DECOMPOSE task (`src/agents/prompts.ts:11-18`), but the runtime goes directly into parallel workers and never performs decomposition (`src/orchestrator/captain.ts:83-124`). Remove stale contracts or implement them.
- **Similarity-based novelty is approximate:** Novelty uses character-bigram Jaccard similarity across concatenated answer/reasoning/claim text (`src/orchestrator/debate.ts:3-25`, `src/orchestrator/debate.ts:28-33`, `src/orchestrator/debate.ts:56-63`). It is inexpensive and deterministic, but sensitive to wording and not semantic agreement; it should not be treated as a strong safety or correctness signal.
- **No timeout around SDK calls:** Abort is checked only between stages; an in-flight `session.prompt` can wait indefinitely unless the SDK itself honors the signal, which is not passed in the request (`src/orchestrator/captain.ts:77-107`, `src/orchestrator/subagent.ts:53-61`). Add request-level cancellation/timeouts and tests for hung calls.

## Testing Lessons

- The repository uses Vitest and has focused unit coverage for plugin registration, config merging, model parsing, prompt composition, child-session lifecycle, debate history, stopping, tool output, debug output, and abort-before-start (`package.json:27-33`; `src/index.test.ts:15-69`; `src/config/loader.test.ts:29-113`; `src/orchestrator/subagent.test.ts:42-97`; `src/orchestrator/debate.test.ts:29-135`; `src/tools/orchestrate.test.ts:31-60`; `src/orchestrator/captain.test.ts:66-133`).
- The test suite passed locally with `bun test`: **56 pass, 0 fail, 113 expect() calls across 8 files**. The CI workflow runs setup, lint, test, and build for pull requests (`.github/workflows/pr.yml:16-37`), which is a good minimum packaging gate.
- The tests mostly use happy-path mocks. There is coverage for raw text fallback and abort-before-start, but not malformed fenced Captain JSON, malformed structured worker objects, prompt-size limits, prompt rejection in one of several parallel workers, mid-call abort, timeout, deletion failure logging, or config logging redaction (`src/orchestrator/subagent.test.ts:78-86`; `src/orchestrator/captain.test.ts:120-133`). Those cases should be added before relying on the orchestrator in unattended workflows.
- Some fixtures indicate contract drift: `subagent.test.ts` passes a `subtasks` property not present in `SubAgentInput` (`src/orchestrator/subagent.test.ts:8-14`, `src/types.ts:64-70`), and type-only tests assert stale stop reasons (`src/types.test.ts:65-86`). Strict typechecking should be run as a distinct CI step, not inferred from the runtime test result.
- `vitest.config.ts` aliases `@opencode-ai/plugin` directly to an internal `dist/tool.js` because the package’s extensionless re-export is not Node ESM-resolvable (`vitest.config.ts:4-11`). This makes tests workable, but it couples them to package internals; include a smoke test against the actual published/bundled artifact.

## Packaging and Security

- The package is ESM-only, exposes bundled runtime/declaration paths, and publishes only `dist` and `src/version.ts` (`package.json:9-15`, `package.json:23-33`). `prepublishOnly` runs tests and build (`package.json:27-30`), and the release manifest/config use Release Please with pre-1.0 minor bumps for breaking changes (`.release-please-manifest.json:1-3`, `release-please-config.json:1-12`, `RELEASE.md:18-32`). Verify the packed tarball contains the runtime entry and required metadata because the allowlist is narrow.
- The publish workflow requests OIDC permission but also writes `${{ secrets.NPM_TOKEN }}` to `~/.npmrc` before publishing (`.github/workflows/publish.yml:16-18`, `.github/workflows/publish.yml:41-55`). Meanwhile, the release guide says no npm tokens are needed and describes trusted publishing (`RELEASE.md:125-153`). Choose one authentication model, remove contradictory credential handling, and ensure workflow conditions are restricted to trusted automation contexts.
- `pull_request_target` is enabled alongside `pull_request`, while the workflow checks out the pull request head SHA and executes repository tooling (`.github/workflows/pr.yml:3-6`, `.github/workflows/pr.yml:20-37`). Because `pull_request_target` runs with the base repository context, review this carefully before allowing untrusted fork code to execute in a privileged workflow; keep permissions minimal and avoid secrets in that job.
- The plugin relies on OpenCode for provider authentication rather than handling API keys itself (`docs/adrs/ADR-001-opencode-plugin-architecture.md:24-32`, `docs/adrs/ADR-001-opencode-plugin-architecture.md:101-105`). This is preferable for credential centralization, but arbitrary configured personas and query text still become model prompts, so prompt/data-boundary handling remains the plugin’s responsibility.

## Reusable Takeaways

- Register one user-facing primary agent and use `mode: 'subagent'` plus parent-linked sessions for internal specialization (`src/index.ts:40-50`, `src/orchestrator/subagent.ts:31-35`).
- Resolve models through `client.config.get()` at execution time, but reject malformed provider/model identifiers instead of forwarding an `unknown` provider (`src/config/loader.ts:23-30`, `src/config/loader.ts:42-60`).
- Preserve host config overrides while keeping machine-required output format instructions immutable (`src/index.ts:55-64`, `src/config/loader.ts:14-20`).
- Parallelize independent model calls, but define partial-failure behavior, per-call timeouts, cancellation, and cleanup observability before shipping (`src/orchestrator/captain.ts:90-107`, `src/orchestrator/subagent.ts:78-81`).
- Treat model output as untrusted input: parse with a schema, cap prompt/transcript size, delimit quoted content, and test malformed and adversarial responses (`src/orchestrator/subagent.ts:67-77`, `src/orchestrator/captain.ts:127-135`).
- Keep runtime defaults, comments, README examples, type unions, and tests synchronized; this repository demonstrates how drift in all five can survive a passing suite (`README.md:11-14`, `src/tools/orchestrate.ts:16-22`, `src/orchestrator/stopping.ts:9-13`, `src/types.ts:52-62`).
