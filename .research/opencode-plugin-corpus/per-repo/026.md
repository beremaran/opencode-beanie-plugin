## Summary

This is a compact OpenCode plugin that exposes two tools: `suggest_bump` analyzes commits and recommends a semantic-version bump, while `create_release` mutates the local repository, pushes a tag, and invokes `gh release create` (`src/index.ts:28-39`, `src/index.ts:88-100`, `src/index.ts:183-193`). Its strongest patterns are a small typed plugin surface, explicit user confirmation guidance for inferred releases, and use of tagged shell templates for command arguments. Its main risks are that the release operation is intentionally high-impact, several external-command failures are suppressed, version validation is permissive, and there are no automated tests in the clone.

## OpenCode Patterns

- **Minimal plugin factory:** The entrypoint imports `Plugin` and `tool`, then returns a `tool` map from an async plugin factory receiving the shell client (`src/index.ts:1`, `src/index.ts:28-30`). This is a useful baseline for a focused plugin with no global initialization.
- **Tool descriptions encode orchestration policy:** `suggest_bump` explicitly says to call it when no bump/version is supplied and to ask for confirmation before `create_release`; `create_release` repeats the routing rule (`src/index.ts:31-38`, `src/index.ts:88-94`). This reduces ambiguity for the model without adding a separate command router.
- **Typed schemas plus runtime guard:** The release tool constrains `bump` to `patch`, `minor`, or `major`, and makes version, notes, and force optional (`src/index.ts:95-100`). It still checks that at least one of bump/version exists at runtime (`src/index.ts:109-111`), which is appropriate because the schema permits both fields to be absent.
- **Progress metadata for long-running work:** The implementation updates tool metadata before fetching, checking, pushing, tagging, and creating the release (`src/index.ts:40-41`, `src/index.ts:113-124`, `src/index.ts:155-188`). This is a practical UX pattern for operations involving multiple networked commands.
- **Structured tool results for recoverable conditions:** Dirty trees and tag-prefix mismatches return a title/output response with a corrective next step instead of throwing (`src/index.ts:113-121`, `src/index.ts:133-148`). Hard precondition failures, such as missing release arguments, throw an error (`src/index.ts:109-111`).

## Functional Design

- The suggestion algorithm defaults to patch, upgrades to minor for any `feat`, and stops at major for breaking commits (`src/index.ts:63-67`). Commit classification recognizes `feat`, `fix`, `BREAKING CHANGE:`, and `!` forms (`src/index.ts:17-25`).
- The plugin preserves the repository's existing `v` tag convention when bumping and refuses an explicit version with a mismatched prefix when tags already exist (`src/index.ts:3-14`, `src/index.ts:129-150`).
- It checks for a dirty worktree, fetches tags, computes a release tag, updates `package.json` when present, pushes the branch/tag, and creates a GitHub release (`src/index.ts:113-124`, `src/index.ts:170-193`). It also reports commits pushed during the operation (`src/index.ts:158-168`, `src/index.ts:195-214`).
- README documentation accurately presents installation through the OpenCode `plugin` array, the two tools, prerequisites, and the development checks (`README.md:9-19`, `README.md:21-24`, `README.md:90-103`).

## Pitfalls and Reliability

- **Suppressed fetch errors:** Both tools run `git fetch --tags --force ... || true`, so a network/authentication failure is hidden and the plugin may operate on stale tags (`src/index.ts:40-43`, `src/index.ts:123-127`). A failed `git describe` is also converted to `v0.0.0`, which can produce a misleading first release or duplicate/conflicting version (`src/index.ts:43-46`, `src/index.ts:126-127`).
- **Missing remote/branch assumptions:** README requires an `origin` remote (`README.md:90-95`), but the source does not preflight it. Branch pushes and unpushed-commit inspection assume `origin/${branch}` exists (`src/index.ts:156-162`, `src/index.ts:178-181`). Detached HEAD skips the branch push, but tag/release mutation still proceeds (`src/index.ts:156-161`, `src/index.ts:183-193`).
- **Partial-failure state:** The plugin changes `package.json` via `npm version`, stages/commits it, then pushes, tags, and publishes in separate steps (`src/index.ts:170-193`). A failure after the version commit or tag push can leave a local commit/tag or remote tag without a GitHub release; there is no rollback or reconciliation path.
- **Potential empty release commit:** The code always attempts `git commit` after `git add ... || true` when `package.json` exists (`src/index.ts:170-176`). Depending on the existing version and files, this can fail as an empty commit and stop the release flow.
- **Semver parsing is intentionally narrow:** Auto-bumping accepts only a numeric `major.minor.patch` prefix and ignores prerelease/build semantics (`src/index.ts:3-14`). Explicit versions are not validated before being used as tags (`src/index.ts:132-152`), so malformed or policy-incompatible versions can reach later commands.
- **Commit parsing is heuristic:** `git log --oneline` subjects are parsed by splitting on whitespace and regular expressions (`src/index.ts:46-60`). Merge commits, non-conventional messages, and unusual subjects are classified as `other`, and the README correctly frames conventional commits as a prerequisite for accurate suggestions (`README.md:63-70`).

## Security Considerations

- The tool can push commits, create annotated tags, and publish a GitHub release with one model-mediated action (`src/index.ts:178-193`). `force: true` bypasses the dirty-tree safety check (`src/index.ts:113-121`); the tool description and README document this escape hatch, but it should remain an explicit confirmation boundary.
- Shell arguments are passed through Bun's tagged shell-template interpolation rather than concatenated command strings (`src/index.ts:41-46`, `src/index.ts:161-186`, `src/index.ts:189-192`). That is the right injection-resistant pattern for user-controlled version/notes/branch values, but the report cannot establish the runtime shell escaping implementation from this repository alone.
- Credentials are delegated to the local Git and GitHub CLI configuration; the README requires authenticated `gh` (`README.md:90-94`). The plugin does not log tokens, but it also does not provide an explicit preflight or redact external-command diagnostics.
- The workflow grants only `contents: read` and `id-token: write`, uses npm provenance, and supplies the npm token only to the publish step (`.github/workflows/release.yml:8-24`). This is a good packaging boundary, though action references are major tags rather than immutable SHAs (`.github/workflows/release.yml:15-16`).

## Packaging and Maintenance Lessons

- The package exposes compiled ESM and declarations through `main`, `types`, and conditional `exports`, while publishing only `dist`, README, and LICENSE (`package.json:9-21`). This keeps the npm artifact small and avoids shipping source or repository metadata.
- `tsup` builds `src/index.ts` as ESM with declarations, and TypeScript uses strict mode, bundler resolution, and source/declaration maps (`package.json:23-28`, `tsconfig.json:2-15`). The lockfile pins the dependency graph for CI reproducibility (`package-lock.json:1-18`).
- Publishing is tag-triggered only for `v*`, matching the README's default tag examples and the plugin's prefix logic (`.github/workflows/release.yml:3-6`, `README.md:71-82`, `src/index.ts:3-14`). A repository using unprefixed tags would not trigger this workflow without changing its trigger.
- The package declares the OpenCode plugin SDK as a runtime dependency (`package.json:40-42`) and uses a public npm publish configuration (`package.json:36-39`). The workflow's `npm publish --provenance --access public` provides a reproducible release path (`.github/workflows/release.yml:20-24`).
