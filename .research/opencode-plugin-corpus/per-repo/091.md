## What it does

`opencode-snip` is an OpenCode plugin that prefixes shell commands with the external `snip` CLI to reduce the amount of command output sent to the model. The README describes `snip` as an output-filtering proxy and claims 60–90% token reduction in typical commands (`README.md:3-13`). Installation deliberately separates the external binary installation from OpenCode configuration (`README.md:15-34`).

The plugin registers the `tool.execute.before` hook and only transforms the `bash` tool (`src/index.ts:40-45`). At plugin initialization it checks for `snip` with the SDK shell helper; if the binary is unavailable it warns and returns an empty plugin object (`src/index.ts:67-73`). This is a useful graceful-degradation pattern for an optional external executable.

## OpenCode integration patterns

- Import the plugin types from `@opencode-ai/plugin` and type the hook as `NonNullable<Hooks["tool.execute.before"]>` (`src/index.ts:1`, `src/index.ts:40`). This gives the hook implementation an SDK-checked shape without duplicating the event contract.
- Export both a named plugin and a default plugin (`src/index.ts:67-80`). The `.opencode/plugins/index.ts` manifest re-exports both from the source module (`.opencode/plugins/index.ts:1-2`).
- Keep the manifest entrypoint thin and put behavior in `src/`; this allows the same implementation to be tested directly while the OpenCode loader consumes the `.opencode` entrypoint (`package.json:5`, `.opencode/plugins/index.ts:1-2`).
- Mutate `output.args.command` in the before hook rather than returning a replacement event (`src/index.ts:43-65`). A plugin using this pattern should preserve unrelated tool calls and malformed argument shapes, as this one does (`src/index.ts:41-45`).

## Source behavior and pitfalls

The rewriter preserves leading environment assignments using `ENV_VAR_RE`, skips a list of shell builtins that should not be proxied, and prefixes ordinary commands (`src/index.ts:3-6`, `src/index.ts:32-38`). It recognizes `&&`, `||`, `;`, and background `&` separators, applying `snip` to each segment (`src/index.ts:7`, `src/index.ts:55-65`). It separately scans for the first unquoted single pipe, so a producer such as `git log` is proxied while the consumer remains outside the proxy (`src/index.ts:9-30`, `src/index.ts:47-53`).

Important limitations follow from the intentionally lightweight parsing:

- The `command.startsWith("snip ")` guard applies to the complete command, not each operator-separated segment (`src/index.ts:43-46`, `src/index.ts:55-65`). Therefore a command beginning with `snip` and containing a later segment, such as `snip git log && go build`, bypasses transformation of `go build`. Conversely, whitespace or another shell form around an existing prefix is not covered.
- Pipe handling only transforms the first detected unquoted pipe and treats the remainder as opaque (`src/index.ts:47-53`). A command with multiple real pipelines will not receive the same behavior for later producers. The quote scanner also tracks only single and double quote state and does not account for shell escapes or other shell syntax (`src/index.ts:9-30`).
- Operator splitting is regex-based, and environment-prefix parsing accepts only assignments with non-whitespace values (`src/index.ts:3`, `src/index.ts:55-65`). Shell constructs outside the tested subset can be classified as command text or separators incorrectly. This is a correctness and potentially execution-semantics risk because the hook rewrites commands immediately before execution.
- The list of unproxyable commands is explicit and narrow (`src/index.ts:4-6`). That is easy to audit, but it means additional shell builtins, shell functions, compound commands, and commands whose output must not be filtered require deliberate policy decisions rather than being handled generically.
- Availability is checked once when the plugin is initialized (`src/index.ts:67-73`). A later `PATH` change, binary replacement, or runtime failure is not handled by this plugin. The external `snip` dependency is therefore a runtime prerequisite even though it is not an npm dependency (`README.md:17-23`, `package.json:10-12`).

The plugin does not appear to interpolate untrusted strings into a newly constructed shell command beyond preserving the original command and adding a fixed `snip` token (`src/index.ts:32-38`). That reduces injection risk from the transformation itself. However, any command-rewriting layer should be treated as security-sensitive: malformed parsing can alter which executable receives arguments, and `snip` becomes part of every eligible command path (`README.md:36-39`, `src/index.ts:40-65`).

## Tests and verification

The test suite is unusually focused on the rewriter’s edge cases. It covers simple commands, multiple environment assignments, all supported operators, non-bash calls, idempotency, and shell builtins (`src/index.test.ts:13-134`). It also covers redirections such as `2>&1` and quoted pipe expressions, including pipes embedded in `jq` strings (`src/index.test.ts:136-198`). These tests document intended command-shaping behavior well.

Gaps remain around multiple real pipes, escaped quotes, command substitutions, subshells, newline-separated commands, leading whitespace, quoted or spaced assignment values, existing `snip` prefixes in later chained segments, and failure behavior of the external binary. The tests assert only mutation of the hook output; they do not exercise plugin initialization or the `which snip` availability path (`src/index.test.ts:4-11`, `src/index.ts:67-73`).

The declared CI workflow installs from the lockfile, runs typecheck, and runs the test command (`.github/workflows/ci.yml:19-26`). In this inspection environment the clone had no `node_modules`: `npm test` failed with `vitest: command not found`, and `npm run typecheck` failed because the test file could not resolve `vitest`. These are environment verification failures, not evidence that the pinned source fails after `npm ci`.

## Packaging and release lessons

- `package.json` declares ESM, a `.opencode/plugins/index.ts` main entrypoint, the OpenCode SDK dependency, and `src` plus `.opencode` in the published file list (`package.json:2-15`, `package.json:34-37`). Explicitly including the manifest directory is important because the declared `main` lives there.
- The package targets Node `^24` (`package.json:31-33`) and uses strict TypeScript with bundler module resolution, declarations, and source-root output settings (`tsconfig.json:1-18`). Consumers and CI should agree with that runtime requirement.
- CI uses `node-version-file: "package.json"` and `npm ci` (`.github/workflows/ci.yml:12-20`). The lockfile records the resolved OpenCode SDK and Vitest versions (`package-lock.json:11-15`, `package-lock.json:470-472`, `package-lock.json:1531-1544`), providing reproducible dependency installation.
- Releases use semantic-release configuration in `package.json` and a workflow triggered only after successful main-branch CI (`package.json:38-47`, `.github/workflows/cd.yml:3-15`). The CD job checks out full history, then runs `npx semantic-release` with GitHub and npm credentials (`.github/workflows/cd.yml:18-33`). Least-privilege write permissions are limited to `contents` and `id-token`, but the release workflow still depends on the repository’s npm and GitHub secret configuration.
- The semantic-release plugins are configured but not listed in `dependencies` or `devDependencies` (`package.json:10-16`, `package.json:38-47`). Relying on `npx` to obtain the release tool without pinning/configuring those plugin packages can make release behavior less reproducible than the CI build. This is a packaging/release risk rather than an OpenCode runtime issue.
- The project documents Conventional Commit types needed for automated versioning (`README.md:40-47`) and includes MIT licensing metadata (`package.json:25`, `LICENSE`).

## Reusable lessons

1. Use the SDK hook types and a thin `.opencode/plugins` re-export so implementation code remains directly testable (`src/index.ts:1`, `.opencode/plugins/index.ts:1-2`).
2. For optional command-line integrations, detect the binary at startup and disable cleanly with a visible warning instead of making every tool call fail (`src/index.ts:67-73`).
3. If transforming shell commands, define and test a conservative grammar. This repository’s broad operator and quote coverage is a good baseline, but the remaining parser gaps show why a shell-aware parser or an explicit unsupported-command policy may be safer than regex splitting (`src/index.ts:3-30`, `src/index.test.ts:136-198`).
4. Test initialization, runtime binary failure, and all forms of chaining separately from pure string-rewrite tests; otherwise the most operationally important failure mode remains unverified (`src/index.ts:67-77`, `src/index.test.ts:4-11`).
5. Make release tooling part of the lockfile-backed dependency graph, or explicitly pin the tool and plugins used by the release workflow; `npx semantic-release` with only config references weakens reproducibility (`package.json:38-47`, `.github/workflows/cd.yml:27-33`).
