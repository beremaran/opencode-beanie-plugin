## OpenCode integration patterns

- The package exposes the plugin entrypoint directly as TypeScript: `main` and the default export both point to `plugins/forloop-plugin.ts`; a second `./exports` subpath exposes reusable client/config/token/context APIs (`package.json:22-31`, `plugins/exports.ts:1-14`). This is a useful pattern when the host can load source and a CLI or companion package needs shared primitives.
- The default plugin function constructs configuration, loads a token, creates one API client, and injects that client into all tool factories (`plugins/forloop-plugin.ts:78-95`). This keeps authentication and transport centralized while allowing many small tool modules.
- Tools use `tool({ description, args, execute })` with `tool.schema` input definitions and descriptions (`plugins/tools/sprint-tools.ts:7-24`). Each operation validates the token before making the API call and updates the client token (`plugins/tools/sprint-tools.ts:24-31`), giving tools a consistent failure path and runtime argument contract.
- The plugin returns the standard `tool` map plus event, `chat.message`, `shell.env`, and before/after tool-execution hooks (`plugins/forloop-plugin.ts:96-190`). This demonstrates that an integration can combine callable tools with lifecycle/event synchronization.
- Sprint context can come from an explicit argument, `FORLOOP_SPRINT_ID`, or a `sprint-XXX` branch (`plugins/tools/sprint-tools.ts:31-41`). The shell hook independently derives the same branch convention with `git rev-parse` and places the result in the tool environment (`plugins/hooks/shell-env.ts:45-59`).
- The event hook buffers user and assistant text, correlates it by session, and writes conversation turns with bounded retries (`plugins/hooks/message-recorder.ts:45-69`, `:253-288`). Lambda streaming is separated behind explicit environment gates (`plugins/hooks/message-recorder.ts:135-173`), a good example of keeping optional remote execution behavior opt-in.
- A compatibility workaround is documented in source: named exports were moved to a separate file because a specific OpenCode/Bun transpiler failed when a default async export and additional exports shared a file (`plugins/forloop-plugin.ts:74-76`, `plugins/exports.ts:1-6`). Host transpiler quirks should be tested and isolated rather than assumed away.

## Configuration and packaging lessons

- Configuration has an explicit precedence chain: `FORLOOP_API_URL`/`FORLOOP_API_BASE`, `FORLOOP_ENV`, project `opencode.json`, global config, then production default (`plugins/capabilities/config.ts:80-120`; documented at `docs/CONFIGURATION.md:14-20`). This is a clear model for project-overrides-global behavior.
- Development endpoints are fail-closed unless `FORLOOP_ALLOW_DEV=true` or config enables `allowDev`; otherwise the resolver warns and returns production (`plugins/capabilities/config.ts:72-78`, `:82-118`; `docs/CONFIGURATION.md:22-30`). Custom URLs are still accepted when not identified as dev, so deployments should decide whether custom-host allowlisting is needed.
- The installer uses strict shell settings, checks `jq`, backs up the target config, merges a unique plugin entry with `jq`, and restores the backup if the temporary result is empty (`install.sh:1-2`, `:72-105`, `:130-165`). This is a practical pattern for idempotent config mutation.
- Installation is intentionally declarative: it adds a git or npm plugin reference and relies on OpenCode to download/cache the plugin (`install.sh:7-13`, `README.md:42-57`). It also clones a separate agents/skills repository and creates symlinks into project or global OpenCode directories (`install.sh:168-209`). The extra repository is a supply-chain and availability dependency that should be surfaced and pinned or verified in production installers.
- `package.json` declares a public package, OpenCode peer/dependency, Node >=18, source exports, and a `prepublishOnly` typecheck/lint gate (`package.json:22-31`, `:48-77`, `:61-68`). The `files` allowlist includes plugin source and user docs (`package.json:33-46`), while `.npmignore` excludes `tsconfig.json` and CI metadata (`.npmignore:37-45`, `:52-53`). Verify the actual packed tarball because allowlists and ignore rules can interact unexpectedly.
- Documentation is inconsistent about the npm package: metadata names `@forloop-cc/forloop-opencode-plugin-planner` (`package.json:3-5`), but the non-developer quickstart instructs `npm install @forloop/opencode-plugin` (`docs/QUICKSTART-NON-DEV.md:29-32`). The README also references multiple repository names in install/config examples (`README.md:45-57`, `docs/CONFIGURATION.md:52-64`). Installation instructions should be generated or checked against package metadata.
- The release workflow is entirely commented out (`.github/workflows/release.yml:1-49`), so the package's declared publication flow is not currently automated. CI only runs install, typecheck, and lint across Node 18/20/22 (`.github/workflows/test.yml:9-33`).

## Security findings and pitfalls

- Tokens are stored under `~/.config/forloop/tokens.json`, created with mode `0o600` (`plugins/capabilities/token-storage.ts:12-18`, `:39-49`), and the installer also applies `chmod 600` (`install.sh:240-246`). The README and security policy recommend minimum scopes and rotation (`README.md:65-69`, `SECURITY.md:31-59`). This is a strong baseline, but existing files' permissions are not tightened when merely read.
- Token format checks distinguish `floop_` API keys from three-part base64url-looking JWTs, and reject JWT use outside detected Lambda execution (`plugins/capabilities/auth.ts:29-54`, `:63-105`). This is useful context-sensitive validation, but it is syntactic validation rather than cryptographic JWT verification; trust still resides with the API/token exchange.
- Lambda JWTs are exchanged for a seven-day API token with a broad list of read/write/delete scopes and persisted via the normal token store (`plugins/capabilities/api-client.ts:120-177`). The short lifetime helps, but persistence and broad scope make the exchange endpoint and token file high-value security boundaries.
- The security policy claims "No sensitive data in logs" (`SECURITY.md:51-59`), but the implementation logs user-message previews up to 300 characters (`plugins/hooks/message-recorder.ts:87-93`), assistant previews up to 500 characters (`plugins/hooks/message-recorder.ts:181-187`), and serialized tool arguments up to 400 characters (`plugins/forloop-plugin.ts:174-188`). This is a direct policy/implementation mismatch: production logging should redact, hash, or disable content logging by default.
- The shell hook executes a fixed `git rev-parse` command with a caller-supplied working directory (`plugins/hooks/shell-env.ts:49-60`). The command itself is not interpolated, which avoids shell injection here, but errors are silently swallowed and the hook exposes environment values to downstream execution; directory and environment boundaries should be tested.
- API requests use a 30-second timeout, retry transient failures up to three times with exponential delays, and do not retry 4xx `APIError`s (`plugins/capabilities/api-client.ts:101-113`, `:199-238`). This is a good default, though there is no visible jitter or explicit idempotency protection for retried mutating requests.

## Testing and maintenance lessons

- `package.json` advertises unit, integration, skills, agents, watch, and coverage commands (`package.json:54-60`), but the inspected clone contains no `test/` directory or test files. Running the advertised test commands would therefore be expected to fail or provide no meaningful coverage; CI does not invoke them (`.github/workflows/test.yml:26-33`). The test surface should be restored or scripts removed, and CI should exercise token/config precedence, tool schemas, API retry/error behavior, event correlation, and installer idempotence.
- Strict TypeScript settings are enabled, including declarations and bundler module resolution (`tsconfig.json:1-16`), while the code still uses several `any`-typed OpenCode/event/API boundaries (`plugins/forloop-plugin.ts:78`, `plugins/hooks/message-recorder.ts:9-12`, `plugins/capabilities/api-client.ts:60-81`). Keep strict compilation, but add typed adapters for host event payloads and API responses where correctness matters.
- The source has multiple asynchronous side effects that intentionally do not await network writes, such as stream chunks and conversation writes (`plugins/hooks/message-recorder.ts:114-128`, `:202-219`). Tests should cover shutdown/race behavior and verify that buffers are deleted or bounded; the module-level user buffer (`plugins/hooks/message-recorder.ts:45-45`) can retain entries when a matching assistant event never arrives.

## Bottom line

The strongest reusable pattern is a thin OpenCode entrypoint that registers many schema-described tools over one authenticated client, with explicit configuration precedence and context-aware token handling. The highest-priority improvements are to reconcile package/install documentation, restore real tests to CI, and remove or redact message and argument previews from logs so the implementation matches its stated security policy.
