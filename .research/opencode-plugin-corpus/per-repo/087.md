## What it does

This is a configurable personality and mood plugin. It stores multiple named personalities, injects the active personality into the system prompt, and optionally drifts a per-personality mood over time. The README describes global/project merging, project-over-global overrides, toast notifications, interactive commands, and legacy single-personality migration (README.md:31-39).

## OpenCode patterns

### Entrypoint and hooks

- The default export is an async `Plugin` implementation. It reads `directory` and `client` from `PluginInput`, loads configuration once, and returns only the hooks/tools appropriate to the resolved state (src/index.ts:20-47).
- The plugin uses `experimental.chat.system.transform` to append a clearly delimited `<personality>` section to `output.system` (src/index.ts:75-92). This is a simple, composable pattern for prompt augmentation rather than replacing the host system prompt.
- It uses `event` and filters `message.updated` events to assistant messages before drifting mood (src/index.ts:94-109). The event payload is narrowed locally to the fields needed by the plugin (src/index.ts:96-99).
- It handles slash commands through `command.execute.before`, dispatching `mood` and `personality` and pushing response parts into command output (src/index.ts:54-73; src/types.ts:139-142). The README explicitly notes that commands must currently be declared in user config because programmatic registration is not available (README.md:42-62).
- When no config exists, the plugin remains useful by exposing `savePersonality` and the `/personality` command while omitting mood/prompt hooks (src/index.ts:26-38). This no-op-safe startup behavior avoids making the plugin unusable before setup.

### Tools and command UX

- Tools are factory functions that close over resolved paths, config, mood definitions, the OpenCode client, and active personality key. They use `tool()` and `tool.schema` for typed argument schemas (src/tools/setMood.ts:5-22; src/tools/savePersonality.ts:10-63).
- `setMood` validates the requested mood against resolved definitions before writing state, logs the operation through `client.app.log`, and supports message/session/permanent duration semantics (src/tools/setMood.ts:23-48).
- `savePersonality` trims required text, applies defaults, supports project/global scope, persists the definition, sets it active, and provides a success toast (src/tools/savePersonality.ts:64-104). This is a useful pattern for LLM-mediated configuration: validate the required field, normalize values, then perform one explicit persistence operation.
- Command parsing is deliberately small and dependency-free: it supports quoted tokens, `--flag value`, boolean flags, and `key=value` values (src/commands/personality.ts:24-88). Destructive reset requires `--confirm`, with a preview instruction otherwise (src/commands/personality.ts:326-345).
- Personality switching and editing persist to disk but tell the user to restart for the change to fully apply (src/commands/personality.ts:232-271). This accurately reflects the current design, since configuration is loaded during plugin initialization.

### Configuration and state

- Global (`~/.config/opencode/personality.json`) and project (`.opencode/personality.json`) paths are explicit, and project personality definitions/states override same-named global entries (src/config.ts:213-269; README.md:159-167).
- Legacy files are detected by the presence of `description` without `personalities`, converted in memory, and migrated into a named `personalities` map with state moved under `states` (src/config.ts:100-123; README.md:232-238).
- Pure multi-personality operations return new objects for add/remove/switch, and removal prevents deleting the last personality in memory while selecting a replacement active key when needed (src/config.ts:141-193).
- Defaults are centralized, then recursively merged into supplied configuration; custom mood arrays replace defaults while nested mood configuration is merged (src/config.ts:18-24, 26-52, 272-290; src/config.ts:343-355).
- Mood state is persisted alongside the personality file under a per-personality key. Loading supports both the new `states` map and legacy `state`, and normalizes invalid current/override mood names (src/config.ts:358-395, 397-413, 448-468).
- Seeded random drift is exposed for deterministic behavior, while unseeded operation uses `Math.random()`; the README documents `mood.seed` as a testing aid (src/mood.ts:28-59; README.md:131-139).

## Security and robustness lessons

### Positive controls

- Reset operations require an explicit confirmation flag before deleting a scope file (src/commands/personality.ts:326-345, 383-395).
- Scope resolution is constrained to the two known config locations rather than accepting arbitrary paths (src/config.ts:415-432).
- Mood tool input is allow-listed against configured mood names (src/tools/setMood.ts:24-28), and state normalization rejects unknown current/override names (src/config.ts:453-462).
- The README clearly disclaims OpenCode affiliation, which reduces supply-chain/user-confusion risk for a third-party plugin (README.md:7).

### Gaps and pitfalls

- Numeric ranges are documented but not enforced. `slangIntensity`, `mood.drift`, and tool-provided values are accepted as arbitrary numbers; `savePersonality` only checks that description is non-empty (README.md:122-139; src/tools/savePersonality.ts:64-90; src/commands/personality.ts:164-179). Invalid values can alter prompt behavior or make drift nonsensical. Validate finite values and documented bounds at the tool and file boundaries.
- Custom mood definitions are not structurally validated for unique names, finite scores, or non-empty hints. Duplicate names make lookup/order-dependent behavior possible, while non-finite scores can poison drift calculations (src/tools/savePersonality.ts:49-58, 86-90; src/config.ts:343-355; src/mood.ts:10-25, 48-59).
- JSON parsing casts arbitrary data directly to `PersonalityFile` after only a shallow legacy check (src/config.ts:81-90, 200-209). Malformed or hostile config can fail later in less diagnosable code. Runtime schema validation and friendly errors would improve resilience.
- File writes use synchronous read/modify/write without atomic temp-file replacement or locking (src/config.ts:298-325, 331-338, 397-413). Concurrent OpenCode processes or overlapping hooks can lose updates or leave a truncated file after interruption.
- Personality descriptions and mood hints are inserted into the system prompt verbatim (src/prompt.ts:11-39). That is the intended feature, but it makes config content a direct prompt-injection boundary. Treat project-level personality files as trusted input, document that risk, and consider delimiting/instruction-prioritization guidance.
- The plugin drifts in both the system transform and assistant `message.updated` event paths (src/index.ts:75-109). A single response may therefore cause two state updates, depending on event ordering. The design should define one authoritative tick or add deduplication keyed by message/session.
- `setMood` implements message duration as `Date.now() + 1` (src/tools/setMood.ts:30-35). This is timing-sensitive rather than explicitly consumed after the next response; the system-transform path can observe it as already expired. A message/session lifecycle marker would be more reliable.
- `saveMoodState` silently returns when the state path has no loadable personality file (src/config.ts:407-412). A user can receive a successful mood operation while state is not persisted if the underlying file disappeared or scope resolution changed.
- The plugin captures config and active personality at initialization, so edits/switches require restart (src/index.ts:20-23, 40-46; src/commands/personality.ts:267-271). This is documented, but it is an important operational limitation for a command-driven plugin.
- Command-generated text includes user-controlled personality names and config JSON without escaping beyond Markdown/code fences (src/commands/personality.ts:275-285, 331-340). This is mostly a presentation concern, but names containing formatting/control text can confuse command output.

## Testing and verification lessons

- No test files or test script are present in the inspected clone. `package.json` exposes `typecheck`, `lint`, `build`, and `prepublishOnly`, but no `test` command (package.json:18-24). The repository therefore lacks automated coverage for config merging, migration, command parsing, mood expiry, persistence, or hook behavior.
- The implementation has test-friendly seams: pure helpers for merge/migration/personality operations, exported mood scoring/drift functions, and seeded drift (src/config.ts:56-79, 112-193; src/mood.ts:10-59; README.md:131-139). These should be covered with unit tests before relying on the plugin in persistent config environments.
- CI runs dependency installation, type checking, linting, and build on PRs/pushes, but not tests ( .github/workflows/pr.yml:9-29). This catches compile/package regressions, not behavioral regressions.
- Strict TypeScript settings include `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, isolated modules, and no unchecked side-effect imports (tsconfig.json:8-26). This is a strong baseline for plugin code and makes the explicit local type guard in the entrypoint valuable (src/index.ts:11-18).
- The README's `mood.seed` testing documentation and the implementation's deterministic formula are aligned, but there is no test proving repeatability or boundary clamping (src/mood.ts:28-59; README.md:131-139).

## Packaging and release lessons

- The package is ESM-first, exports built JS and declarations, and ships only `dist` and `src` (package.json:5-16). The build emits an ESM bundle, external sourcemap, and declaration files (package.json:18-24).
- `@opencode-ai/plugin` is correctly declared as a peer dependency with a development copy for local compilation (package.json:44-53). Node 18+ is declared even though the development workflow uses Bun (package.json:55-57).
- The package includes source in the published files, which helps debugging and transparency but increases artifact size and exposes implementation details (package.json:14-17).
- PR CI uses Bun and runs typecheck/lint/build ( .github/workflows/pr.yml:15-29). The publish workflow switches to npm, runs `npm ci`, builds, and publishes on version tags with `id-token: write` for OIDC ( .github/workflows/publish.yml:3-27). The separate release workflow also triggers on the same `v*` tags and builds a GitHub release ( .github/workflows/release.yml:3-30).
- Release tooling is not fully reproducible: workflows use `bun-version: latest`, install `npm@latest`, and invoke an unpinned `softprops/action-gh-release@v1` ( .github/workflows/publish.yml:17-26; .github/workflows/release.yml:17-30). Pin tool/action versions and avoid upgrading npm dynamically during a release.
- There are two tag-triggered workflows, so publishing and GitHub release creation are coupled only by the shared tag trigger, with no explicit artifact handoff or verification step ( .github/workflows/publish.yml:3-27; .github/workflows/release.yml:3-30). A single release pipeline or explicit provenance/checksum validation would reduce drift.
- The changelog follows Keep a Changelog and SemVer conventions and records the plugin hook/API surface and build approach (CHANGELOG.md:1-35). The package version is `1.2.0`, while the checked-in changelog shown here only contains `1.0.0` (package.json:1-4; CHANGELOG.md:8-35), suggesting release metadata may be stale.

## Reusable takeaways

1. Return a minimal no-config plugin surface so setup can happen through a tool without requiring pre-existing state (src/index.ts:26-38).
2. Keep configuration precedence, migration, pure collection operations, and file I/O separate; this makes behavior understandable and testable (src/config.ts:100-193, 211-339).
3. Use schema-defined tools plus explicit allow-list checks for user/LLM inputs, and add confirmation gates for destructive commands (src/tools/setMood.ts:12-28; src/commands/personality.ts:326-345).
4. Make stateful stochastic behavior deterministic under an optional seed and expose pure scoring/drift helpers for tests (src/mood.ts:10-59).
5. For production hardening, add runtime config validation, atomic/locked persistence, event deduplication, range checks, and actual behavioral tests before treating compile/lint/build CI as sufficient.
