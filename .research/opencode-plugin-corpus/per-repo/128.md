## What the plugin does

DCP reduces the context sent to the model without rewriting the stored session history: it replaces pruned content with placeholders before requests are made (`README.md:31-37`). It supports range compression and experimental per-message compression, while nesting overlapping summaries and preserving protected tool outputs/files (`README.md:39-44`). Automatic deduplication keeps the newest output for repeated tool calls, and purge-errors removes large errored-tool inputs after a configurable number of turns while retaining the error message (`README.md:46-52`).

The entrypoint is an async `Plugin` factory. It loads configuration, exits early when disabled, creates logger/session/prompt state, optionally configures authenticated SDK requests, starts auto-update, and returns OpenCode hooks and tools (`index.ts:22-56`). The returned integration covers system prompt transformation, chat-message transformation, text completion cleanup, command execution, events, a mode-selected `compress` tool, and OpenCode config mutation (`index.ts:56-135`).

## OpenCode integration patterns

- **Use the plugin lifecycle to compose focused handlers.** The entrypoint delegates each hook to a factory rather than embedding behavior in the registration object (`index.ts:57-80`). This keeps the OpenCode-facing surface discoverable and lets handlers be unit-tested independently.
- **Treat message transforms as an untrusted boundary.** The chat transform filters malformed message shapes, logs received versus usable counts, initializes/synchronizes session state, then applies stripping, cache synchronization, pruning, subagent-result injection, nudges, IDs, and stale-metadata cleanup (`lib/hooks.ts:99-155`). The tests verify that a malformed message is dropped rather than crashing (`tests/hooks-permission.test.ts:144-180`).
- **Cache model capabilities from hook input.** The system-prompt handler records the model context limit before deciding whether to inject prompts, enabling percentage-based thresholds (`lib/hooks.ts:55-62`; `tests/hooks-permission.test.ts:92-115`).
- **Respect host permissions instead of assuming plugin config is authoritative.** The config hook disables compression when OpenCode denies it, only adds the command/tool when effective permission permits, adds `compress` to experimental primary tools when appropriate, and preserves explicit host permission entries (`index.ts:89-133`). Tests cover wildcard precedence, agent-level denial, glob matching, and compatibility without `findLast` or `Object.hasOwn` (`tests/host-permissions.test.ts:9-104`).
- **Protect high-value context explicitly.** The default protected tool set includes task/skill/todo/planning and write/edit tools (`lib/config.ts:78-91`), while the README documents configurable protected tools and protected file patterns (`README.md:114-121`, `README.md:214-221`). This is a useful model for any plugin that mutates or filters conversation context: define safety exclusions centrally and make extensions additive.
- **Avoid injecting into internal summarization agents.** The system hook checks known internal-agent signatures and skips prompt injection (`lib/hooks.ts:64-72`). Subagent processing is also disabled by default unless the experimental flag is enabled (`lib/hooks.ts:64-66`; `dcp.schema.json:102-120`).
- **Make manual commands produce model-visible prompts.** `/dcp` and `/dcp-compress` are registered through the command hook; a manual compression request replaces command output with a text part that asks the model to perform the pass (`lib/hooks.ts:159-259`). The README documents the two user-facing commands (`README.md:188-193`).

## Configuration and state

Configuration is layered global -> `OPENCODE_CONFIG_DIR` -> project `.opencode`, with later layers overriding earlier values (`lib/config.ts:728-766`, `lib/config.ts:977-1006`; `README.md:54-62`). JSONC parsing allows trailing commas and invalid files produce delayed warning toasts while retaining prior/default values (`lib/config.ts:785-801`, `lib/config.ts:954-966`). The schema rejects unknown properties (`dcp.schema.json:1-8`) and describes defaults, enums, and safety-related options such as manual mode and subagent handling (`dcp.schema.json:40-120`).

The plugin creates a global default config file automatically when none exists (`lib/config.ts:768-778`). Session state is persisted under `$XDG_DATA_HOME/opencode/storage/plugin/dcp/{sessionId}.json`, or the corresponding path below `~/.local/share` (`lib/state/persistence.ts:1-5`, `lib/state/persistence.ts:45-60`). Loading validates the broad shape and filters malformed/duplicate nudge anchors (`lib/state/persistence.ts:115-198`).

### Configuration/state pitfalls

- **Global side effects happen at initialization.** A disabled/missing global config causes directory and file creation (`lib/config.ts:969-975`, `lib/config.ts:768-778`). Installations should document this and tests should isolate `HOME`/XDG paths.
- **Config merge semantics are intentionally asymmetric.** Protected-tool and protected-file arrays are unioned across layers, while scalar options use the later value (`lib/config.ts:804-858`, `lib/config.ts:932-950`). This is safe for preserving protections but means users cannot remove a default/earlier protected entry through a later config.
- **Persisted JSON is only partially validated.** The loader checks object presence and nudge-anchor types but casts the remaining parsed value to `PersistedSessionState` (`lib/state/persistence.ts:126-143`). A stronger schema/version check would reduce corruption-induced runtime surprises.
- **Session IDs become filenames directly.** The path is formed as `join(STORAGE_DIR, `${sessionId}.json`)` (`lib/state/persistence.ts:59-61`). OpenCode-generated IDs are presumably constrained, but a plugin should validate IDs before using them in filesystem paths if IDs can be influenced externally.

## Security and privacy lessons

- **Secure-server authentication is propagated to SDK requests.** When `OPENCODE_SERVER_PASSWORD` is set, the plugin builds Basic authentication from username/password and installs a request interceptor only when no Authorization header already exists (`lib/auth.ts:1-13`, `lib/auth.ts:15-36`). This preserves caller-supplied credentials, but it relies on private-ish client properties (`_client`/`client`) and uses `any`; an SDK change could silently remove authentication.
- **Auto-update is networked and destructive by design.** It fetches `https://registry.npmjs.org/<name>/latest` with a ten-second abort timeout (`lib/update.ts:19-40`, `lib/update.ts:130-145`), accepts only semver-like newer versions, and removes the OpenCode npm wrapper directory so the host can reinstall (`lib/update.ts:42-67`, `lib/update.ts:82-118`). Tests specifically reject pinned and non-registry specs and cover wrapper selection (`tests/update.test.ts:15-56`). This is a strong example of narrowing update scope, but deleting an installation directory remains a high-impact side effect and should stay opt-in or clearly surfaced.
- **Custom prompts are executable behavior in practice.** When enabled, prompt defaults and overrides are written as plain text in global/config directories (`README.md:195-212`; `lib/prompts/store.ts:419-459`). The feature is disabled by default (`dcp.schema.json:112-120`), a sensible trust boundary for user-editable prompt content.
- **Pruning can expose sensitive context to a summarizer.** The README promises high-fidelity technical summaries and preservation of protected content (`README.md:35-44`), while the implementation writes session context and persistent state to local storage (`lib/hooks.ts:153-155`; `lib/state/persistence.ts:63-77`). Deployments should consider filesystem permissions, retention, and whether debug/context logs contain secrets.
- **Prompt-cache tradeoff is explicit.** DCP acknowledges that changing messages invalidates cached prefixes and reports approximate cache-hit degradation (`README.md:223-230`). This is an operational cost, not just a correctness concern, and should be part of plugin telemetry/documentation.

## Testing lessons

The test suite is broad and behavior-oriented: compression range/message flows, placeholder validation, grouping, token accounting, message shape/priority/IDs, prompt behavior, host permissions, update semantics, and cache behavior are represented by files under `tests/` (for example `tests/compress-range.test.ts`, `tests/compress-message.test.ts`, `tests/compress-range-placeholders.test.ts`, `tests/token-usage.test.ts`, and `tests/hooks-permission.test.ts`). Placeholder tests verify that valid references are retained, invalid references are ignored, and omitted prior summaries are appended (`tests/compress-range-placeholders.test.ts:46-119`). Compatibility tests deliberately remove newer built-ins before exercising permission logic (`tests/host-permissions.test.ts:70-104`).

The package test command is `node --import tsx --test tests/*.test.ts` (`package.json:23-34`). CI runs format check, typecheck, build, and a high-severity npm audit (`.github/workflows/pr-checks.yml:7-36`); publish CI additionally runs the test suite (`.github/workflows/publish.yml:49-67`). In this inspection clone, `node_modules` is absent, so `npm test` was not run and no dependencies were installed.

Testing gaps suggested by the code:

- No runtime test was executed here, and the repository’s visible CI PR workflow does not run `npm test` (`.github/workflows/pr-checks.yml:25-36`).
- The authentication interceptor’s behavior and the fallback between `client._client` and `client.client` deserve tests (`lib/auth.ts:15-35`).
- Config layering, automatic default-file creation, malformed JSONC, and filesystem permission failures are important side-effect cases but are not evident in the reviewed test names.
- Persistence validation tests should cover malformed nested prune state, unsafe session IDs, and concurrent writes (`lib/state/persistence.ts:63-72`, `lib/state/persistence.ts:115-205`).
- Auto-update tests cover selection/version logic but not the actual fetch timeout, registry response validation, or failure after wrapper removal (`tests/update.test.ts:8-56`; `lib/update.ts:130-145`).

## Packaging and release

The package is ESM, exposes `dist/index.js` as the main/server entry and `tui.tsx` as the TUI export, and declares OpenCode/plugin and OpenTUI peer compatibility (`package.json:3-21`, `package.json:55-60`). Build uses tsup for ESM plus a separate declaration-only TypeScript pass (`package.json:23-31`; `tsup.config.ts:1-10`). `jsonc-parser` is bundled because the repository identifies broken ESM imports in that dependency (`tsup.config.ts:8-10`).

The `files` allowlist ships only `dist/`, `lib/`, `tui.tsx`, README, and LICENSE (`package.json:81-87`). The package verifier checks required files and export paths, walks the runtime import graph for unresolved local imports/CommonJS-style imports, and runs `npm pack --dry-run --json` to reject tests, scripts, source, assets, lockfiles, and other forbidden paths (`scripts/verify-package.mjs:16-46`, `scripts/verify-package.mjs:177-245`). `prepublishOnly` runs the package build/audit check (`package.json:23-31`). Publish uses npm provenance and least-privilege GitHub permissions (`.github/workflows/publish.yml:9-15`, `.github/workflows/publish.yml:49-67`).

One packaging caveat is that `exports["./tui"].import` points at source `./tui.tsx`, while the main/server exports point at built `dist/index.js` (`package.json:9-21`). The verifier intentionally enforces this arrangement (`scripts/verify-package.mjs:63-87`); consumers and runtimes therefore need TypeScript/TSX handling for the TUI subpath even though the server path is compiled.

## Reusable takeaways

1. Keep OpenCode hook registration thin and isolate each lifecycle concern behind a factory.
2. Resolve effective host permission at runtime, including wildcard and agent-level rules; never let plugin defaults override explicit host denial.
3. Filter and log malformed hook payloads before mutation so plugin failures do not crash the host session.
4. Treat context pruning as a data-integrity feature: protect tools/files, validate summary placeholders, preserve nested summaries, and test omitted/invalid references.
5. Make filesystem, network, auto-update, and prompt-override side effects visible, bounded, and independently testable.
6. Pair `package.json` allowlists with an executable tarball/import-graph verifier, and run tests in every release-gating workflow.
