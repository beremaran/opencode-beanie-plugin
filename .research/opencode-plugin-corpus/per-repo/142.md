## OpenCode Patterns

- The plugin uses the standard typed plugin entrypoint: it imports `Plugin` and `PluginInput`, exports a named plugin and default plugin, and returns hook handlers from an async initializer (`src/index.ts:1-9`, `src/index.ts:735-762`, `src/index.ts:1290`).
- It wires both lifecycle hooks and the event stream. `chat.params` records provider/model metadata; `tool.execute.before` and `tool.execute.after` create and finish nested tool spans; `event` handles sessions, errors, messages, and message parts (`src/index.ts:762-798`, `src/index.ts:798-947`, `src/index.ts:949-1286`). This is a useful pattern for correlating request, tool, and session-level telemetry without wrapping tool implementations.
- Session spans are created lazily and reused per session, with model/provider/project/session attributes and custom tags (`src/index.ts:477-508`). Tool spans use a composite `sessionID:callID` key and a per-session index so dangling spans can be closed during lifecycle cleanup (`src/index.ts:447-471`, `src/index.ts:809-844`).
- The implementation tolerates SDK/event-shape variation with runtime type guards rather than trusting event payloads. It checks message identity/role, assistant completion timestamps, and text-part fields before using them (`src/index.ts:554-631`). Hook and event failures are caught and logged instead of propagating into OpenCode (`src/index.ts:845-862`, `src/index.ts:931-946`, `src/index.ts:1280-1285`).
- Flushes are lifecycle-aware: idle flushes are coalesced and cooled down for 1.2 seconds, while deletion and errors force a flush (`src/index.ts:291-354`, `src/index.ts:963-1034`). This avoids turning every event into a network flush while still giving terminal events stronger delivery semantics.
- Message text is assembled from incremental `message.part.updated` events and removed on corresponding removal events; synthetic and ignored parts are excluded (`src/index.ts:1228-1275`). The cache has explicit per-session/message/part bounds (`src/index.ts:29-32`, `src/index.ts:147-214`).

## Configuration and Integration Lessons

- Configuration is intentionally sidecar-based. The README documents project and user config locations plus an explicit `OPENCODE_SENTRY_CONFIG` override (`README.md:41-59`, `README.md:61-87`), and the resolver checks the explicit file first, then project and platform config directories (`src/config.ts:288-324`). Environment variables are applied after file loading, so deployment-specific values can override a checked-in sidecar (`src/config.ts:327-420`, `src/config.ts:423-457`).
- A missing DSN disables the plugin by returning `{}` rather than failing plugin startup (`src/config.ts:445-457`, `src/index.ts:735-742`). This is a good optional-integration behavior for local OpenCode use.
- Runtime validation is stronger than TypeScript-only validation: it checks DSN URL/protocol, sample-rate bounds, attribute length, flush timeout, booleans, strings, and tag value types (`src/config.ts:82-140`, `src/config.ts:192-263`). JSONC is supported through `strip-json-comments` (`src/config.ts:174-189`).
- Config precedence has an important operational pitfall: the first existing candidate is read and parsed, and a malformed higher-priority file throws rather than falling through to a valid lower-priority file (`src/config.ts:432-441`). Operators should remove or repair stale files instead of assuming fallback will occur.
- Sentry is initialized once per process. If another plugin initialization requests a different DSN, the original client is retained and the requested/initialized DSNs are logged (`src/index.ts:671-696`). This prevents reinitialization races but makes multi-project or multi-config use in one process unsupported; logging DSNs is also unnecessary even though the README describes a DSN as non-secret (`README.md:152-156`).

## Security and Privacy

- The default configuration records both tool inputs and outputs, and the README's reference configuration explicitly enables both (`src/config.ts:19-29`, `README.md:89-109`). This is a high-impact privacy default for prompts, source code, command arguments, and tool results; deployments should opt out unless capture is required.
- Redaction is recursive and handles sensitive-looking key names, circular references, depth, array/object cardinality, traversal budget, string size, and JSON serialization failures (`src/serialize.ts:1-12`, `src/serialize.ts:24-111`, `src/serialize.ts:127-149`). Inputs/outputs are serialized before being attached to Sentry spans (`src/index.ts:835-840`, `src/index.ts:886-897`, `src/index.ts:1092-1145`).
- Redaction is heuristic, not a confidentiality boundary. It matches key names such as `token`, `secret`, `authorization`, and `cookie`, but secrets embedded in free-form strings or under an unrecognized key can remain; truncation also preserves the beginning of a value (`src/serialize.ts:1-2`, `src/serialize.ts:37-39`, `src/serialize.ts:96-103`, `src/serialize.ts:114-124`). The README appropriately calls out redaction/truncation but does not promise complete scrubbing (`README.md:27-29`, `README.md:154-155`).
- Sentry is configured with `sendDefaultPii: false` (`src/index.ts:671-680`), but explicit captured attributes, breadcrumbs, error extras, and metrics can still contain user data. Session errors always serialize their payload, and tool errors serialize output even when normal output recording is disabled (`src/index.ts:698-713`, `src/index.ts:886-913`).
- The plugin limits caches to reduce unbounded memory growth, but the primary `sessions` map is cleaned on `session.deleted`; sessions that never receive deletion remain resident (`src/index.ts:21-32`, `src/index.ts:510-524`). Hosts should ensure terminal events are delivered, or the implementation should add an independent expiry if long-lived processes are a concern.

## Testing and Reliability

- There is no automated test suite, test script, or test dependency in the checked-in package metadata (`package.json:19-23`, `package.json:41-45`; repository file inventory contains only the three source modules). This leaves critical behavior unverified: config precedence and malformed JSON, redaction edge cases, duplicate message events, missing tool spans, event-shape compatibility, flush coalescing, and Sentry initialization.
- The source does include defensive runtime checks and bounded-state logic that are good candidates for unit tests (`src/index.ts:554-631`, `src/index.ts:716-733`, `src/serialize.ts:24-149`). A minimal test plan should isolate `config.ts` and `serialize.ts`, then exercise hook/event handlers with mocked Sentry and representative OpenCode payloads.
- Duplicate completed assistant messages are suppressed with a bounded insertion-ordered set (`src/index.ts:716-733`). This avoids double-counting repeated `message.updated` events, but the bound means an old message ID can eventually be processed again; that tradeoff should be documented and tested.
- Cleanup is generally fail-safe, but closing pending tool spans on idle/deletion marks them as errors (`src/index.ts:122-144`, `src/index.ts:963-1013`). This may conflate cancellation/incomplete execution with actual tool failure in downstream metrics.

## Packaging and Release

- The package is ESM with explicit runtime and type entrypoints, an exports map, and a restricted published file list containing `dist`, README, and LICENSE (`package.json:5-18`). TypeScript emits declarations, maps, and source maps under `dist` (`tsconfig.json:3-22`), making the package consumable by typed OpenCode installations.
- `prepublishOnly` runs typecheck and build, and the README documents the same local commands before `npm publish` (`package.json:19-23`, `README.md:138-150`). This is a useful release gate, although it validates compilation only, not behavior.
- Runtime dependencies are correctly separated from the OpenCode plugin SDK, which is a dev dependency (`package.json:37-45`). However, the SDK is declared as `"latest"` (`package.json:42-44`, `package-lock.json:15-18`), making fresh installs and future publishes non-reproducible even though the committed lockfile records one resolved tree. Pinning a tested SDK range or exact version would reduce compatibility surprises.
- The clone contains six versioned `.tgz` package artifacts, and each archive lists only `package/LICENSE`, `package/README.md`, `package/package.json`, and compiled `dist` files. This confirms the intended publish surface, but retaining generated release archives in the repository increases noise and can make it unclear which artifact is authoritative.
- `dist/` and dependency/log artifacts are ignored (`.gitignore:1-7`), so published output must be generated during release rather than expected in source control. The package's `files` allowlist provides the stronger protection against accidentally shipping source or local configuration (`package.json:14-18`).

## Bottom Line

This is a strong reference pattern for an optional OpenCode telemetry plugin: lazy initialization, lifecycle/event correlation, runtime payload guards, bounded caches, configurable capture, and defensive serialization. The main lessons for reuse are to make prompt/tool capture opt-in for privacy-sensitive deployments, treat redaction as best-effort only, add tests before relying on event semantics, avoid global initialization surprises, and pin the OpenCode SDK used to build and publish the plugin.
