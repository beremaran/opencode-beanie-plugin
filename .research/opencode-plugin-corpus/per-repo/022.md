## SDK and registration

- The package entry is ESM `dist/index.js` with generated declarations; the package exports the root module and exposes a `flowdeck` binary (`package.json:1-16`). Runtime compilation externalizes `@opencode-ai/plugin` and `@opencode-ai/sdk`, while the plugin package is a runtime dependency and the SDK is a peer dependency (`package.json:26-36`, `package.json:55-67`).
- The plugin factory receives OpenCode's `directory` and `client`, returns a named plugin, and registers agents, MCPs, tools, `config`, tool lifecycle hooks, and an event handler (`src/index.ts:76-90`, `src/index.ts:140-202`). This is a useful single-entrypoint pattern: all OpenCode-facing wiring is inspectable in one place.
- `config` mutates the supplied OpenCode config to set `default_agent`, shallow-merge generated agent definitions without overwriting user fields, merge MCPs, load Markdown command frontmatter, add the packaged skills directory, and append selected instruction paths without duplicates (`src/index.ts:91-138`). The per-agent merge order is explicit: plugin defaults first, user overrides win (`src/index.ts:97-106`).
- Agent factories are kept in a canonical registry. `AGENT_NAMES` is the source list, `getAgentConfigs` maps definitions to SDK `AgentConfig` objects and mode/hidden flags, and `getAgentRoutes` deterministically excludes the orchestrator and sorts routes (`src/agents/index.ts:25-39`, `src/agents/index.ts:140-195`). This reduces drift between registered agents and routing prompts.
- Markdown commands are runtime data: the loader parses a simple `description` frontmatter field and preserves the remaining body as the command template (`src/index.ts:58-73`). This makes command authoring approachable, but the parser silently returns an empty set on any directory/read failure (`src/index.ts:60-73`), which can turn packaging or permission errors into missing commands.

## Configuration and OpenCode integration patterns

- Configuration lookup is project-first: `.flowdeck.jsonc`, `.flowdeck.json`, `.opencode/flowdeck.jsonc`, `.opencode/flowdeck.json`, then global `flowdeck.json` (`src/config/agent-models.ts:107-129`). JSONC comments are stripped with string-awareness, and malformed candidates are skipped before falling back to defaults (`src/config/agent-models.ts:29-81`, `src/config/agent-models.ts:130-141`).
- Unknown top-level configuration keys are discarded by `sanitizeConfig`; `agentModels` takes precedence over the legacy `agents` key when resolving model strings (`src/config/agent-models.ts:84-104`, `src/config/agent-models.ts:144-163`). Tests cover precedence, malformed fallback, comment-like strings, and `provider/model` parsing (`tests/config/agent-models.test.ts:29-103`, `tests/config/agent-models.test.ts:106-139`).
- Lifecycle integration is deliberately narrow: session creation/start invokes startup state loading, idle/error events persist session outcomes, and tool execution invokes the guard plus loop detector before logging/completing after execution (`src/index.ts:168-202`). Entry integration tests assert the registration shape, surviving tools, event wiring, and absence of removed tools (`tests/index.test.ts:61-125`, `tests/index.test.ts:127-229`).

## Security lessons and pitfalls

- Strong pattern: enforce workflow policy at `tool.execute.before`, not only in prompts. The guard blocks sensitive reads, `node_modules` writes, and `rm -rf`, then applies architectural, phase, design, TDD, agent-contract, audit, and verification checks (`src/hooks/tool-guard.ts:1-7`, `src/hooks/tool-guard.ts:23-27`, `src/hooks/tool-guard.ts:161-263`). It defaults on and has an explicit opt-out environment variable (`src/hooks/tool-guard.ts:9-10`).
- The write budget counts unique paths per session and records/reset counters through lifecycle events (`src/hooks/tool-guard.ts:48-91`; `tests/hooks/tool-guard.test.ts:102-184`; `tests/index.test.ts:215-229`). This is a practical guard against runaway agent edits, with tests for the 15th allowed and 16th blocked write.
- The built-in `hash-edit` tool provides stale-edit protection by requiring target-content presence and optionally comparing an MD5 of the target before replacement (`src/tools/hash-edit.ts:5-36`). However, it resolves relative paths by string concatenation and permits absolute paths (`src/tools/hash-edit.ts:13-15`); there is no worktree containment or symlink/canonical-path check. A malicious or mistaken tool call could therefore edit outside the project. The hash also covers only the target substring, not the whole file, so it is an anchor check rather than a complete concurrent-file version check.
- The basic guard uses substring matching with no path filtering, regex, or glob semantics (`src/hooks/tool-guard.ts:1-6`, `src/hooks/tool-guard.ts:39-45`). This is simple and predictable, but it can over-block names containing `.key` or `node_modules`, while missing alternate argument shapes or destructive commands expressed without the exact `rm -rf` substring. `getFilePath` recognizes only four path keys (`src/hooks/tool-guard.ts:29-36`), so every OpenCode tool shape must be audited before relying on the generic guard.
- MCPs expose a large default trust surface: four remote endpoints and five `npx -y` local servers are configured, with disable-by-environment controls (`src/mcp/index.ts:1-20`, `src/mcp/index.ts:98-213`). API keys are correctly sent as headers rather than URLs (`src/mcp/index.ts:104-125`, `src/mcp/index.ts:151-159`), but the documentation claim that FlowDeck “does not read any API keys” conflicts with this implementation (`docs/configuration/opencode-settings.md:71-81`). Local `@latest` resolution also creates a reproducibility and supply-chain risk (`src/mcp/index.ts:170-205`).

## Packaging and delivery lessons

- The published `files` list includes `dist`, the CLI, commands, rules, skills, docs, and `postinstall.mjs`, but not `src/agents`, `src/tools`, `src/hooks`, or `crates` (`package.json:17-24`; `docs/configuration/opencode-settings.md:20-35`). The compiled `dist/index.js` can still contain bundled logic, while `postinstall` may need Rust sources that are absent from the npm package.
- Installation is highly stateful: `postinstall.mjs` checks OpenCode's version, optionally clones or pulls the GitHub repository, builds `fdx` with Cargo, and then edits the global OpenCode config (`postinstall.mjs:132-184`, `postinstall.mjs:361-407`). The script intentionally never fails npm installation (`postinstall.mjs:409-412`), which improves install resilience but can leave a partially functional plugin while reporting success.
- Security/reproducibility caveat: the installer can run `git pull`, clone a mutable repository, and on Unix executes a downloaded `curl | sh` Rust installer when prompted/automated (`postinstall.mjs:138-167`, `postinstall.mjs:330-339`). Pinning repository revisions and verifying downloaded artifacts would materially reduce supply-chain exposure.
- Registration is idempotent for versioned/unversioned plugin entries and preserves an existing `default_agent` (`postinstall.mjs:375-403`). This is a useful deployment pattern, but it parses malformed JSON by silently replacing the in-memory config with `{}` (`postinstall.mjs:380-383`), then rewrites the file; a corrupt existing OpenCode config can therefore be destructively overwritten.
- Publish CI uses npm provenance and restricts the publish job's GitHub permissions to read contents plus OIDC identity (`.github/workflows/publish.yml:11-18`, `.github/workflows/publish.yml:46-52`). Build and test happen before publication, and the package has a `prepublishOnly` build gate (`package.json:26-36`).

## Reusable OpenCode patterns

- Keep the plugin factory as the integration boundary: merge user config conservatively, register tools/hooks/events in one returned object, and keep domain services outside the entrypoint (`src/index.ts:76-202`).
- Treat Markdown commands, skills, and language rules as packaged runtime assets and inject their paths during `config`, while deduplicating user instructions (`src/index.ts:113-138`).
- Use typed `tool.schema` arguments and bounded child-process wrappers: `fdx` uses `execFileSync`, a 30-second timeout, and a 50 MB output cap (`src/tools/fdx.ts:14-35`, `src/tools/fdx.ts:40-65`). Prefer argument arrays over shell interpolation for tool parameters.
- Make safety behavior observable and testable: return actionable block reasons, keep per-session counters, and assert both registration and lifecycle side effects (`src/hooks/tool-guard.ts:73-91`; `tests/index.test.ts:191-229`).
- For production hardening, pair these patterns with canonical path containment for every filesystem-writing tool, explicit MCP opt-in or pinned versions, non-destructive config migration, and tests for the negative/security boundary cases.
