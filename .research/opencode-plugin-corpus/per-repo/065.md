## Architecture And OpenCode Patterns

1. **Use the OpenCode plugin type at the boundary.** The default export is explicitly typed as `Plugin`, and the plugin receives `input` before delegating to the SDK (`src/index.ts:1`, `src/index.ts:14-21`). This keeps host integration type-checked while leaving event routing to a reusable layer.
2. **Make a plugin a thin backend adapter when behavior is reusable.** The entrypoint loads SDK config, extracts the `ntfy` backend section, validates it, constructs the backend with OpenCode's shell, and calls `createNotificationPlugin` with `backendConfigKey: "ntfy"` (`src/index.ts:2-20`). The README clearly assigns routing, subagent suppression, and top-level config handling to the SDK, while retaining ntfy-specific formatting and transport in this repository (`README.md:15-29`).
3. **Keep transport behind a small interface.** `createNtfyBackend()` returns only `send(context): Promise<void>` and derives title, message, tags, headers, and body at send time (`src/backend.ts:62-113`). This is a useful OpenCode pattern for notification providers: the host-facing hook stays stable while provider-specific HTTP details remain isolated.
4. **Pass OpenCode's `$` capability explicitly.** The entrypoint passes `input.$` into backend construction (`src/index.ts:14-20`), and command templates fail explicitly if that capability is absent (`src/backend.ts:50-59`). This makes shell access an explicit dependency rather than reaching for a process-global shell.
5. **Validate untyped SDK configuration at the adapter boundary.** `parseNtfyBackendConfig()` accepts `Record<string, unknown>`, checks the required topic, applies defaults, validates priority and event names, parses durations, and enforces exactly one template form (`src/config.ts:73-127`, `src/config.ts:130-170`). The JSON Schema mirrors the same boundary with `additionalProperties: false`, enums, required topic, and `oneOf` content templates (`notification-ntfy.schema.json:34-58`, `notification-ntfy.schema.json:93-165`).
6. **Use the SDK for filtering and template semantics rather than duplicating host logic.** The README documents SDK-owned event routing, enabled flags, and child-session suppression (`README.md:17-29`), while the backend calls SDK `renderTemplate` and `execTemplate` for content (`src/backend.ts:50-59`). This reduces the chance that several notification plugins implement inconsistent OpenCode event behavior.

## Evidence-Backed Lessons

### Configuration And UX

- A minimal install is discoverable: users add the package to the OpenCode `plugin` array (`README.md:51-62`), and configuration is placed in `~/.config/opencode/notification-ntfy.json` (`README.md:64-79`).
- The README documents both SDK-level controls and provider-level fields, including topic, server, token, priority, icon, timeout, and per-event content (`README.md:81-116`). It also documents environment/file substitution for keeping secrets out of committed JSON (`README.md:118-141`).
- The schema is shipped and tested as a first-class user artifact. Tests verify schema existence, top-level shape, backend fields, template references, required topic, and package inclusion (`tests/config.test.ts:287-375`).
- Defaults are centralized in the backend for titles, messages, and ntfy emoji tags (`src/backend.ts:14-31`), and tests cover all three event types (`tests/backend.test.ts:154-257`).

### Testing

- HTTP behavior is tested at the network boundary with MSW rather than mocking `fetch`; helpers capture URL, method, headers, and body (`tests/msw-helpers.ts:1-31`). This makes assertions close to the ntfy contract.
- Tests cover success, custom server/topic, headers, optional bearer auth, timeout aborts, non-OK responses, value templates, command templates, fallback content, and unknown placeholders (`tests/backend.test.ts:141-527`).
- Configuration tests cover malformed and missing required values, defaults, enum validation, icon selection, duration parsing, and mutually exclusive template fields (`tests/config.test.ts:11-284`).
- Compile-time tests verify both the exported plugin and backend interface, and verify temporary typecheck files do not leak into build output (`tests/typecheck.test.ts:8-97`). The build excludes those files explicitly (`tsconfig.json:14-15`), while coverage excludes them too (`vitest.config.ts:7-11`).
- CI runs frozen dependency installation, lint, build, and coverage tests before publishing (`.github/workflows/ci.yml:21-39`). This is a strong release gate for a small plugin.

### Security And Reliability

- Tokens are only added to the request when configured (`src/backend.ts:86-94`), and request failures become thrown errors for the SDK to contain (`src/backend.ts:105-111`; `PROMPT.md:312-314`).
- Timeout support is explicit and tested: an ISO duration is converted to milliseconds (`src/config.ts:62-70`, `src/config.ts:113-117`) and passed to `AbortSignal.timeout` (`src/backend.ts:96-103`).
- Command templates are an intentional privileged feature. The README says they are rendered and executed as shell commands (`README.md:143-156`), and the implementation executes them through the OpenCode shell (`src/backend.ts:50-59`). Treat command-capable configuration as trusted code: event-derived values such as project, error, and permission fields are interpolated before execution (`README.md:158-168`). The documentation should make this trust boundary and shell-injection implications prominent; the implementation delegates escaping/execution semantics to the SDK, so this clone alone does not establish that interpolation is safe.
- The request URL is built by string concatenation from `server` and `topic` (`src/backend.ts:67-69`). The parser checks that topic is non-empty but does not validate the server URL, normalize trailing slashes, or encode the topic (`src/config.ts:76-85`). A malformed or attacker-controlled configuration can therefore produce surprising destinations or paths; URL validation and a documented trust model for custom servers would improve hardening.
- Custom icon URLs are accepted as arbitrary strings (`src/config.ts:106-111`), although the schema description says they should point to JPEG/PNG images (`notification-ntfy.schema.json:71-83`). There is no URL or scheme validation in the parser. Since ntfy clients fetch these URLs, a safe deployment should treat icon URLs as outbound-fetch destinations and consider restricting schemes/hosts if configuration is not fully trusted.
- Default icons are fetched from a GitHub raw URL whose tag is taken from the package version (`src/config.ts:39-45`, `src/config.ts:51-60`). This is convenient and keeps assets out of the npm package, but notification rendering depends on GitHub availability and the corresponding release tag. The plan explicitly acknowledges that assets are not published (`PLAN.md:108-118`), and the package only ships `dist` and the schema (`package.json:33-35`).

## Pitfalls And Packaging Gaps

1. **Command execution needs stronger security documentation and tests.** README examples encourage command templates (`README.md:236-250`), but do not clearly state that configuration grants shell execution. Add tests around hostile event values and document whether the SDK quotes or otherwise isolates substitutions; otherwise users may assume templates are inert strings.
2. **Transport destination validation is incomplete.** `server` defaults but accepts any string, and `topic` is concatenated directly (`src/config.ts:82-85`, `src/backend.ts:67-69`). Validate a URL, handle trailing slashes, and define whether topics may contain path/query characters.
3. **Schema and parser are not fully equivalent.** The schema rejects unknown properties and restricts `icon.mode` to `light`/`dark` (`notification-ntfy.schema.json:60-85`), while the runtime parser silently coerces an invalid icon mode to dark (`src/config.ts:100-105`). Decide whether runtime behavior should reject invalid values to match editor validation, or document intentional leniency.
4. **Bun/npm instructions are mixed.** The repository says Bun is the runtime/package manager and CI installs with Bun (`PROMPT.md:316-320`, `.github/workflows/ci.yml:16-31`), but typecheck tests invoke `npx tsc` (`tests/typecheck.test.ts:24-27`, `tests/typecheck.test.ts:43-47`, `tests/typecheck.test.ts:89-92`) and publishing invokes `npm publish` (`.github/workflows/ci.yml:52-65`). This may work on hosted runners, but it weakens the claimed single-toolchain guarantee and should be made deliberate.
5. **Lockfile policy is confusing.** Both `bun.lock` and `yarn.lock` are present in the clone, while `bunfig.toml` sets lockfile printing to `yarn` (`bunfig.toml:1-2`). CI uses `bun install --frozen-lockfile` (`.github/workflows/ci.yml:21-23`). A single authoritative lockfile and an explicit rationale would reduce reproducibility ambiguity.
6. **The package intentionally excludes runtime icon assets.** This is valid only because the implementation uses versioned public raw GitHub URLs (`src/config.ts:45-60`). Releases must keep those tags and asset paths stable; otherwise installed packages can silently send broken icon URLs.
7. **The package export is import-only.** `package.json` exposes `./dist/index.js` and declarations under an `import` condition (`package.json:6-12`). That is appropriate for the ESM plugin, but consumers or tooling expecting a `require` condition will not have a CJS fallback.

## Packaging And Release Model

- The package is ESM (`type: module`), exposes compiled JavaScript and declarations, and publishes only `dist` plus the schema (`package.json:5-12`, `package.json:33-35`).
- `prepublishOnly` builds TypeScript, and CI also builds before publishing (`package.json:14-20`, `.github/workflows/ci.yml:60-65`).
- Publishing is tag-gated and follows successful CI (`.github/workflows/ci.yml:41-47`). npm provenance and public access are enabled (`.github/workflows/ci.yml:64-65`).
- The package declares the OpenCode plugin API as a dev dependency and the notification SDK plus duration parser as runtime dependencies (`package.json:22-31`, `package.json:56-59`). This correctly keeps host typing/build tooling out of runtime dependencies while shipping the SDK needed by the entrypoint.
- MIT licensing and repository metadata are present in package metadata (`package.json:37-54`) and the README advertises CI, coverage, license, and Snyk status (`README.md:3-6`).
- A scheduled Snyk workflow uploads SARIF, but its vulnerability step is explicitly non-blocking (`.github/workflows/snyk.yml:24-35`). This is useful visibility, not a hard security gate.

## Overall Assessment

This is a well-factored OpenCode notification-provider pattern: keep the plugin entrypoint small, rely on a shared SDK for event semantics, validate provider configuration at the boundary, and test the actual HTTP contract. Its biggest operational risks are not OpenCode API misuse but trust-boundary ambiguity around shell templates and permissive network destinations. The release process is solid for an npm ESM package, though the Bun/Yarn/npm mixture and external icon hosting should be made explicit and consistently enforced.
