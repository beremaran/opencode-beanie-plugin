## What It Does

Mission Control creates one git worktree and tmux session per spawned coding job, monitors those jobs, and provides tools for capture, diff, merge, sync, cleanup, and PR creation (`README.md:30-38`, `README.md:69-72`). Its plan system adds dependency ordering, bounded parallelism, an integration branch, a merge train, test gating, rollback, and automatic PR creation (`README.md:521-554`). The README clearly separates simple independent work (`mc_launch`) from dependency-aware work (`mc_plan`) and explains the shared-file scaffold strategy (`README.md:224-325`).

## OpenCode Patterns

### Entrypoint and context-aware registration

- The plugin uses the standard `Plugin` type and returns hooks, commands, tools, and events from one async entrypoint (`src/index.ts:1`, `src/index.ts:121-126`, `src/index.ts:216-312`).
- It detects whether the current process is inside a managed worktree and gives spawned agents only `mc_report` and `mc_status`; the command-center session receives the full tool set (`src/index.ts:121-124`, `src/index.ts:261-264`). This is a useful least-privilege pattern for subagents.
- Main sessions start monitoring, notifications, and plan-resume behavior, while job agents do not (`src/index.ts:168-175`, `src/index.ts:194-213`). The plugin tests these branches explicitly (`tests/plugin-init.test.ts:47-121`, `tests/plugin-init.test.ts:124-198`).
- Lifecycle integration uses `tool.execute.before`, `chat.message`, `chat.params`, `event`, and `experimental.session.compacting` (`src/index.ts:222-311`). The compaction hook mutates `output.context` in place, with a comment documenting that reassignment is ignored by the SDK proxy (`src/index.ts:306-310`).

### Tool and state design

- Tools are split one-per-file under `src/tools`, with shared orchestration under `src/lib`; the repository guidance makes this boundary explicit (`AGENTS.md:13-19`, `AGENTS.md:21-27`).
- Tool arguments use the plugin schema helpers and constrained enums for placement, execution mode, and plan mode (`src/tools/launch.ts:77-117`, `src/tools/plan.ts:11-60`). Plan execution validates unique names, dependency references, and circular dependencies before persisting or starting work (`src/tools/plan.ts:64-103`).
- Persisted jobs, plans, permission policies, and config are represented by Zod schemas with explicit enum/state domains (`src/lib/schemas.ts:3-29`, `src/lib/schemas.ts:31-139`, `src/lib/schemas.ts:152-175`). Config loading parses JSON through the partial schema, merges defaults, and reports path-specific validation failures (`src/lib/config.ts:46-72`).
- State is project-scoped below `~/.local/share/opencode-mission-control/<project>/state`, and project identity is derived from git’s common directory so linked worktrees share state (`src/lib/paths.ts:16-51`).

### Isolation and integration

- Worktrees isolate concurrent filesystem changes, while tmux provides process/session isolation and monitoring (`README.md:34-38`, `README.md:78-84`). The launch tool checks tmux, rejects duplicate jobs, sanitizes the tmux display name, and cleans up the worktree on several setup failures (`src/tools/launch.ts:119-180`, `src/tools/launch.ts:214-329`).
- Git operations are routed through a mutex-protected helper, serializing access to shared git metadata (`src/lib/git.ts:1-5`, `src/lib/git.ts:18-40`).
- The merge train validates an optional `touchSet` against the branch diff before merge (`src/lib/merge-train.ts:56-94`), detects conflicts with a temporary merge, and restores a clean worktree (`src/lib/merge-train.ts:96-120`).
- A successful merge can be gated by dependency setup and a detected/configured test command; failures, timeouts, and failed setup roll back to the pre-merge commit (`src/lib/merge-train.ts:498-566`, `src/lib/merge-train.ts:569-632`).

## Security Lessons and Pitfalls

### Positive controls

- Default permission policy auto-approves edits and shell commands inside a job worktree, denies file edits outside it, asks before outside-worktree shell commands and package installs, and denies network access (`src/lib/permission-policy.ts:97-106`). Decisions are logged with timestamps, action, target, reason, and outcome (`src/lib/permission-policy.ts:109-186`).
- Copy and symlink paths reject absolute paths and `..` traversal, always include `.opencode`, and deduplicate normalized paths (`src/lib/worktree-setup.ts:84-97`, `src/lib/worktree-setup.ts:99-136`). The corresponding tests cover absolute paths, traversal, merging, and normalization (`tests/lib/worktree-setup.test.ts:4-78`).
- PR creation passes title, body, branch, and base as argument-array values to `gh`, rather than building one shell command (`src/tools/pr.ts:5-20`, `src/tools/pr.ts:106-133`).

### Risks to carry forward

- Worktree setup validates commands but only emits a warning unless `allowUnsafeCommands` is configured; every command is still executed with `sh -c` (`src/lib/worktree.ts:137-164`). The validator treats unknown simple commands as safe, and its own test locks in that behavior (`src/lib/worktree-setup.ts:49-72`, `tests/lib/worktree-setup.test.ts:208-225`). This is warning-based defense, not a sandbox or allowlist.
- Merge-train setup and test commands also execute through `sh -c` (`src/lib/merge-train.ts:195-225`). Configured test commands are therefore trusted code execution and should be treated as a privileged configuration surface. The README documents that setup commands may install packages and explicitly describes the unsafe-command bypass (`README.md:761-769`).
- Launcher scripts interpolate the discovered `opencode` path, model, and server password into shell source (`src/lib/prompt-file.ts:33-64`). The prompt itself is safely written to a file and read at runtime, but model/password quoting is not shell-escaping; values containing shell metacharacters can alter the generated script.
- `mc_pr` pushes the job branch to `origin` before creating a PR (`src/tools/pr.ts:91-101`). This is an important side effect that should remain explicit in UX, permission review, and tests.
- The permission policy implementation is not visibly wired into OpenCode’s `permission.ask` hook in the entrypoint: the entrypoint registers lifecycle hooks and tools but no `permission` hook (`src/index.ts:216-312`), while the policy is primarily a library used in persisted plan/job types (`src/lib/schemas.ts:86-109`, `src/lib/schemas.ts:120-139`). Treat the policy as advisory unless the integration path is verified elsewhere.
- The source contains `as any` casts despite repository guidance forbidding them (`src/index.ts:159`, `src/index.ts:216-217`, `src/index.ts:262`; `AGENTS.md:21-27`). These casts weaken the type boundary exactly where SDK shape compatibility and tool registration matter.

## Testing Lessons

- The suite is broad: unit tests cover config, git, worktrees, mutexes, state, orchestration, hooks, tools, and integration workflows; the repository contains dedicated test files under `tests/lib`, `tests/hooks`, `tests/tools`, and `tests/integration`.
- Tests build temporary git repositories and real worktrees for merge-train behavior (`tests/lib/merge-train.test.ts:56-81`). They verify FIFO merging, conflict cleanup, dependency installation, skipped tests, setup failures, failed tests, timeout rollback, touch-set violations, and fix-before-rollback behavior (`tests/lib/merge-train.test.ts:97-188`, `tests/lib/merge-train.test.ts:191-387`, `tests/lib/merge-train.test.ts:417-521`, `tests/lib/merge-train.test.ts:524-725`). This is a strong model for testing process and git orchestration without mutating the developer’s repository.
- Security-oriented path and command tests cover traversal, dangerous shell operators, command substitution, remote-script piping, root deletion, and redirects (`tests/lib/worktree-setup.test.ts:81-205`).
- CI pins Bun, installs with the frozen lockfile, builds, then runs each test file individually (`.github/workflows/ci.yml:9-35`).
- A reproducibility concern is that `tests/plugin-init.test.ts` imports `vitest` (`tests/plugin-init.test.ts:1`), while the package declares Bun test scripts and does not declare Vitest in `package.json` (`package.json:19-33`). CI invokes those files with `bun test` (`.github/workflows/ci.yml:28-35`). This should be reconciled and verified from a clean install.
- The manual plan is unusually operational: it defines idempotent cleanup for tmux sessions, worktrees, branches, state, ports, and leaked processes before/after E2E runs (`MANUAL_TEST_PLAN.md:15-94`), and uses a test-job naming convention (`MANUAL_TEST_PLAN.md:118-120`).

## Packaging and Release

- The package exports only `dist/index.js` and `dist/index.d.ts`, publishes only `dist`, builds with Bun, and runs the build before publish (`package.json:6-24`). This keeps the npm artifact small and makes the runtime entrypoint unambiguous.
- Public npm provenance is enabled (`package.json:14-18`). The package declares the OpenCode plugin and SDK as runtime dependencies and Zod for schema validation (`package.json:25-33`).
- CI builds and tests before release; the publish workflow uses frozen dependencies and full git history (`.github/workflows/publish.yml:29-60`). Semantic-release publishes npm and creates the GitHub release (`.releaserc.json:2-21`).
- Release hygiene depends on Conventional Commit messages, documented both for semantic-release and PR validation (`README.md:876-889`, `AGENTS.md:47-67`). GitHub Actions permissions are explicitly scoped for contents, issues, pull requests, and npm provenance (`.github/workflows/publish.yml:15-19`).

## Reusable Takeaways

1. Register fewer tools inside spawned-agent contexts; expose only status/reporting capabilities needed for the job.
2. Use typed schemas and early graph validation before creating persistent orchestration state.
3. Serialize git operations when multiple worktrees and merge operations share repository metadata.
4. Treat worktree setup, test commands, package installs, and PR pushes as privileged side effects; validation and warnings do not replace a real approval boundary.
5. Test orchestration against temporary real git repositories, including rollback and cleanup assertions, not only mocked command results.
6. Keep the npm surface limited to built output, pin CI runtime versions, use frozen lockfiles, and verify that the test runner used in CI is actually declared by the package.
