## What it does and notable OpenCode patterns

- TokenScope exposes one OpenCode `tokenscope` tool from a typed `Plugin` factory. It receives `client`, `serverUrl`, and the plugin directory, loads pricing/config once, and constructs analysis collaborators per invocation (`plugin/tokenscope.ts:27-58`). This is a useful separation between plugin registration and request-scoped state.
- Tool arguments use SDK schemas: optional `sessionID`, bounded integer `limitMessages` from 1 through 10, and optional `includeSubagents` (`plugin/tokenscope.ts:36-50`). The command prompt deliberately leaves `sessionID` unset unless the user requests another session and tells the model to return the exact report file verbatim (`command/tokenscope.md:1-8`). This reduces accidental cross-session analysis and prompt-added formatting.
- Session, child-session, tool, and provider calls carry the active directory/workspace routing. The compatibility helper tries current and legacy SDK request shapes, but only falls back between shapes and does not silently use unrouted metadata when routing was requested (`plugin/tokenscope-lib/opencode.ts:46-73`, `:76-131`; `plugin/test/opencode.test.ts:178-234`). This is a strong host-integration pattern for plugins that must support evolving SDKs without crossing project boundaries.
- The analysis distinguishes persisted OpenCode step telemetry, locally tokenized retained content, and explanatory API-rate estimates instead of presenting all numbers as billable facts (`README.md:105-123`). It warns on session aggregate mismatches and active reverts (`plugin/test/session-workflow.test.ts:29-66`), and the changelog records fixes for per-step aggregation, tiered pricing, compaction/revert limits, and cyclic child traversal (`CHANGELOG.md:21-56`).
- Failures are intentionally non-fatal to the host session. Missing session IDs, empty sessions, write failures, and unexpected analysis errors return a short fallback report or explicit inline error rather than throwing through the OpenCode tool (`plugin/tokenscope.ts:60-86`, `:107-156`). This is appropriate for observability/reporting functionality that should not break the user’s primary coding session.

## Security and privacy lessons

- Sensitive reports are isolated from the analyzed worktree. The implementation creates `os.tmpdir()/opencode`, requires it to be a real non-symlink directory, checks Unix ownership and group/world writability, creates a per-invocation directory, writes with mode `0600`, and uses an exclusive temporary file followed by rename (`plugin/tokenscope-lib/report.ts:21-55`). Tests verify path isolation, directory mode `0700`, file mode `0600`, and separator sanitization (`plugin/test/report.test.ts:9-30`).
- Report filename components are sanitized and length-limited before being joined under the generated temporary directory (`plugin/tokenscope-lib/report.ts:9-18`). The summary shell-quotes the path, including embedded single quotes, and has regression coverage against command-substitution-shaped input (`plugin/tokenscope-lib/report.ts:57-60`, `:90-124`; `plugin/test/report.test.ts:33-46`). Do not regress this by returning a fixed filename or interpolating an unquoted path into user instructions.
- The privacy boundary is explicit but not “offline”: session text stays local and reports are owner-only, while the plugin calls the OpenCode client/server and may download mapped tokenizer JSON from Hugging Face; configured Hugging Face credentials can be sent in the request (`README.md:227-233`; `plugin/tokenscope-lib/tokenizer.ts:135-153`). Operators should treat tokenizer configuration and network policy as data-exfiltration controls.
- Tokenizer failures fall back to an approximate count with a warning rather than silently claiming precision (`plugin/tokenscope-lib/tokenizer.ts:16-35`, `:112-163`). However, the user config loader accepts any parsed JSON object and merges it without runtime type validation (`plugin/tokenscope-lib/config.ts:64-86`). The README says only JSON syntax is validated (`README.md:129-137`); malformed flag types should be rejected or normalized before feature checks.
- The documented one-line installer executes remote shell code (`README.md:54-60`). The script downloads mutable `main`-branch files with `curl`, installs dependencies, and builds them (`plugin/install.sh:41-44`, `:93-169`). Prefer a versioned release/package install or checksum/signature verification for higher-trust environments; if retaining the script, pin a commit and validate downloaded file manifests.

- The suite is broad and focused: the audited `npm test` run passed 86 tests across 12 files. Tests cover plugin session-ID precedence and private report behavior (`plugin/test/tokenscope.test.ts:26-95`), asset resolution in source and compiled layouts plus pricing/config loading (`plugin/test/config.test.ts:11-39`), SDK routing/compatibility/error-response handling (`plugin/test/opencode.test.ts:5-234`), metadata/tier pricing (`plugin/test/metadata.test.ts:5-200`), formatter snapshots and cost-label precision (`plugin/test/formatter.test.ts:13-114`), and aggregate/revert warnings (`plugin/test/session-workflow.test.ts:6-66`).
- The package test command also builds and imports the compiled ESM entrypoint (`plugin/package.json:9-15`), catching missing `.js` extensions and distribution-only loader failures. TypeScript uses strict mode, declarations, source maps, and an explicit `dist` output (`plugin/tsconfig.json:4-27`). This source-plus-built-artifact testing is a reusable packaging pattern.
- Coverage is primarily unit and fixture-based; there is no evidence in the inspected tree of an end-to-end test against a real OpenCode server, real child-session graph, or a networked Hugging Face tokenizer. Add deterministic contract tests for client response shape changes and optional network failure, while keeping network-free unit tests as the default.
- The report-path test exercises a crafted path string, but the implementation’s parent-directory validation is performed only on the fixed `os.tmpdir()/opencode` parent. Environments with hostile or unusual temporary-directory ownership/symlink setup should be tested at process/integration level, not only with normal temporary directories (`plugin/tokenscope-lib/report.ts:26-41`; `plugin/test/report.test.ts:15-30`).

## Packaging and maintenance lessons

- The npm package declares `@opencode-ai/plugin >=1.1.48` as a peer dependency, ships ESM with `dist/tokenscope.js` as `main`, and includes only `dist/`, `models.json`, `tokenscope-config.json`, README, and LICENSE (`plugin/package.json:3-15`, `:36-55`). The `.npmignore` excludes TypeScript sources, library sources, build config, and the installer (`plugin/.npmignore:1-20`), keeping the published artifact small while retaining runtime assets.
- The installer is a separate source-install path: it enumerates every split library file, downloads the package metadata/assets and command, runs `npm install`, builds `dist`, and verifies required outputs/dependencies (`plugin/install.sh:96-122`, `:148-200`). Keeping this manifest explicit prevents a split-file refactor from silently producing an incomplete script installation, but it also creates a maintenance obligation to update the list with every new runtime file.
- `models.json` is a large bundled catalog and is explicitly tested as loaded rather than replaced by the small fallback table (`plugin/test/config.test.ts:25-30`). Live provider metadata takes precedence over bundled data in the resolver (`plugin/test/metadata.test.ts:5-57`), which is a good freshness strategy, but the bundled catalog and mutable remote tokenizer assets are still release/versioning inputs.
- The package has no lockfile in the inspected clone. `npm install` in the installer therefore resolves ranges at installation time (`plugin/package.json:39-47`; `plugin/install.sh:148-169`). For reproducible releases, publish a tested lockfile or use an npm-packaged artifact with CI validating the exact dependency graph.
- Documentation is unusually explicit about snapshot boundaries, compaction/revert limits, pricing semantics, fallbacks, privacy, and runtime requirements (`README.md:77-81`, `:105-137`, `:220-246`). The changelog ties those explanations to concrete fixes and security changes (`CHANGELOG.md:31-61`), making it a good model for documenting measurement uncertainty rather than hiding it.

## Bottom line

TokenScope demonstrates a strong OpenCode observability-plugin pattern: narrow schema-validated tooling, directory-routed SDK access, request-local analyzers, explicit uncertainty, non-fatal degradation, and secure unique report files. The main risks are operational rather than core-hook design: the remote `curl | bash`/mutable-branch installer, unpinned dependency installation, runtime-unvalidated JSON flags, and reliance on external Hugging Face tokenizer downloads. Preserve the report isolation and uncertainty contracts, and harden the installer/config/network boundary before using the pattern in a higher-trust deployment.
