## Shape and OpenCode integration

This is a thin, OS-backed scheduler plugin. The README describes the intended model as natural-language scheduling, persistent job files, an OS timer invoking a supervisor, and append-only logs (`README.md:55-64`). The plugin exports an async `Plugin` object whose `tool` map contains scheduling, listing, version, skill, CRUD, cleanup, immediate-run, and log tools (`src/index.ts:2535-2540`, `src/index.ts:2728-2790`, `src/index.ts:2815-2905`, `src/index.ts:2907-3315`). This is a useful OpenCode pattern: expose one conceptual operation per tool, while keeping the underlying job model explicit and returning both human-readable output and structured data.

The tool result contract is deliberately consistent: text or JSON output, `success`, `output`, `shouldContinue`, and optional `data` (`src/index.ts:430-453`). Success terminates the tool loop (`shouldContinue: false`), while errors are recoverable (`true`). This is a strong agent-facing convention because callers do not need to infer completion from prose.

The job model maps OpenCode run options into a stable invocation snapshot: prompt/command, files, agent, model, variant, title, session, format, attach URL, and port are normalized and validated (`src/index.ts:372-428`, `src/index.ts:1836-1940`). The generated argument list uses separate process arguments rather than a shell command string (`src/index.ts:2170-2228`), reducing quoting ambiguity for normal job execution.

The repository also ships a built-in skill template. It recommends runtime date computation, non-interactive operation, idempotency, observable summaries, preflight checks, and minimal durable side effects (`src/index.ts:464-550`). This is a reusable pattern for scheduled-agent products: encode operational guidance as an installable skill instead of silently rewriting user prompts.

## Storage, scheduling, and reliability patterns

- Workdir-derived scopes isolate jobs, locks, run history, logs, and scheduler unit names. The scope combines a readable basename with a 48-bit prefix of FNV-1a over the normalized absolute path (`src/index.ts:65-93`, `src/index.ts:95-120`). The README documents the resulting layout and legacy locations (`README.md:156-187`). This is a practical multi-project collision-avoidance pattern.
- Cron is parsed into a deliberately small five-field subset, with range checks and support for `*/n`, comma lists, and Sunday `7` normalization (`src/index.ts:675-746`). Backend-specific expansion handles launchd and systemd day-of-month/day-of-week OR semantics (`src/index.ts:748-795`, `src/index.ts:817-857`). Windows rejects expressions it cannot represent and returns guidance rather than silently changing schedules (`src/index.ts:916-1004`; `README.md:81-85`).
- Native backend selection is platform-aware: macOS uses launchd, Windows uses Task Scheduler, Linux prefers systemd user timers and falls back to cron (`src/index.ts:1284-1457`). Systemd installation failure can fall back to cron (`src/index.ts:1459-1479`). The README correctly documents that cron lacks missed-run catch-up and Windows does not receive the Unix supervisor guarantees (`README.md:74-85`).
- Scheduled Unix-like runs use a generated Perl supervisor. It creates directories, appends stdout/stderr to a scoped log, checks a PID lock to skip overlap, atomically writes job metadata, forces `question: deny`, runs from the stored workdir, supports timeout escalation, records JSONL history, and removes the lock (`src/index.ts:127-350`). The corresponding code is a concrete implementation of the earlier PRD's proposed supervisor, which had described those responsibilities as future work (`PRD-resilient-execution.md:38-95`).
- Job definitions are sanitized before JSON persistence, and invocation snapshots preserve the executable/arguments selected when a job is scheduled (`src/index.ts:1958-2015`, `src/index.ts:2661-2682`). Update rebuilds the snapshot and attempts rollback if reinstall fails (`src/index.ts:3061-3105`). These are good durability patterns, although rollback is explicitly best effort.
- Global cleanup plans all discovered artifacts and defaults to dry-run; deletion requires `confirm: true`, with logs/history additionally gated by `includeHistory` (`src/index.ts:1666-1755`, `src/index.ts:3139-3170`; `README.md:132-154`). Destructive agent tools should follow this preview-then-confirm design.

## Security and operational pitfalls

1. **Generated scheduler files are not consistently escaped.** launchd XML escapes workdir and fixed arguments (`src/index.ts:797-809`, `src/index.ts:1051-1094`), and systemd arguments are escaped (`src/index.ts:801-803`, `src/index.ts:1153-1177`), but the systemd `WorkingDirectory` and `Description` interpolate job-controlled values without the same treatment (`src/index.ts:1164-1170`). A name or path containing newline/control syntax can produce malformed or semantically altered units. Validate or escape every generated field and test adversarial names/workdirs.
2. **Shell interpolation remains in some administrative paths.** launchctl and systemctl calls use template strings (`src/index.ts:1114-1129`, `src/index.ts:1207-1220`, `src/index.ts:1229-1250`), and `isCommandAvailable` interpolates its command into `command -v` (`src/index.ts:1288-1296`). Current callers mostly provide fixed or slug-derived values, but this is a fragile boundary for future refactors. Prefer `execFileSync` with argument arrays wherever possible.
3. **Attach URLs are only syntactically validated.** `normalizeAttachUrl` accepts any URL parseable by `new URL` (`src/index.ts:1804-1814`). The URL is persisted and printed in job details and run output (`src/index.ts:2418-2422`, `src/index.ts:2699-2701`, `src/index.ts:3260-3267`). If attach URLs can contain credentials or point to untrusted services, this creates disclosure and SSRF-like operational risk; consider restricting scheme/host policy and redacting sensitive components.
4. **Manual execution is fire-and-forget without supervisor controls.** `run_job` calls `spawn`, returns the PID immediately, and does not apply the scheduled timeout or overlap lock (`src/index.ts:2299-2361`, `src/index.ts:3173-3274`). This is intentional and documented (`README.md:62`, `README.md:66-70`), but users can reasonably assume the same reliability guarantees. The interface should make this distinction prominent or offer a supervised manual mode.
5. **Environment policy is powerful and partly user-configurable.** Scheduled execution forces `question: deny`, strips most `OPENCODE_*` variables by default, then applies configured `env.set` values (`src/index.ts:2231-2273`). This is a thoughtful secret/permission boundary, but `env.set` is not schema-validated and can override the final environment policy except for the later `OPENCODE_PERMISSION` assignment. Document trusted-user assumptions and validate config shape.
6. **Cleanup has broad filesystem authority by design.** Global cleanup enumerates all scope and legacy job artifacts and can call recursive `rmSync` on planned paths (`src/index.ts:1666-1717`, `src/index.ts:1720-1748`). The dry-run default is an important mitigation; retain it and consider explicit confirmation details or path-root assertions before deletion.
7. **The source comment and README are not fully aligned with the implementation history.** The source header claims missed-run catch-up (`src/index.ts:7-12`), while README says cron does not catch up and only native backends do (`README.md:74-79`). Treat backend-specific guarantees as authoritative and keep feature comments synchronized.

## Testing and verification lessons

- There are no test files, no test script, and no test/coverage/lint tooling in the repository. `package.json` only defines build, clean, publish, release, and typecheck scripts (`package.json:17-24`), while the tree contains only `src/index.ts` as source and generated `dist` output. This is the largest quality gap for a plugin whose behavior is dominated by platform-specific rendering and destructive side effects.
- The highest-value tests would isolate pure functions for cron validation/translation, scope derivation, Windows representability, escaping, job normalization, invocation construction, and cleanup planning. Then use mocked `execFileSync`/filesystem boundaries for install/uninstall and supervisor integration tests with temporary HOME directories.
- Cross-platform contract tests should verify launchd XML, systemd unit syntax, cron managed-block preservation, and Windows task argument arrays. Include names/workdirs containing spaces, quotes, XML metacharacters, newlines, Unicode, and path separators.
- Reliability tests should cover stale locks, live-lock overlap skips, atomic metadata writes, timeout exit `124`, child process groups, malformed job files, concurrent updates, and supervisor failure before `invocation` validation. The implementation has explicit branches for these cases (`src/index.ts:209-350`, `src/index.ts:1982-1998`), but no repository tests demonstrate them.
- The checked-in generated bundle is very large and includes bundled dependency code (`dist/index.js:1-13` onward), so a release check should build from source, typecheck, inspect the npm tarball, and verify that the exported default and named plugin match the declaration (`dist/index.d.ts:14-16`).

## Packaging and maintenance

`package.json` points consumers at `dist/index.js` and `dist/index.d.ts`, uses ESM exports, publishes only `dist`, and declares `@opencode-ai/plugin` as both a dependency and peer dependency (`package.json:2-15`, `package.json:46-55`). `prepublishOnly` cleans and rebuilds (`package.json:17-24`), which reduces stale-artifact risk. The declaration exposes only the plugin value, keeping the public API narrow (`dist/index.d.ts:14-16`).

The package has a lockfile but `.gitignore` excludes `bun.lock` and tracks `package-lock.json` (`.gitignore:1-4`, `package.json:46-55`). `bun-types: "latest"` is not pinned (`package.json:49-51`), which can make typechecking and builds drift over time. Pin toolchain dependencies or use a reproducible lock strategy, and add CI that runs typecheck plus a clean build. The release scripts invoke `npm version`/`npm publish` despite the project build using Bun (`package.json:18-24`); this mixed toolchain should be intentional and documented.

## Reusable takeaways

- Use scoped durable state keyed by normalized workdir when a plugin operates across multiple OpenCode projects.
- Return explicit structured completion/error signals from every tool, while retaining concise text for conversational use.
- Snapshot executable invocations at schedule time so later configuration changes do not silently mutate installed OS jobs.
- Treat OS scheduler translation as a compatibility layer: reject unrepresentable schedules with actionable errors.
- Make destructive global operations dry-run by default and separate job-definition removal from history/log removal.
- For unattended agent work, enforce non-interactive permissions, bounded execution, overlap control, append-only logs, and atomic metadata updates.
- Keep the plugin thin, but test the platform boundary heavily. The absence of tests here means the strongest claimed behavior is currently supported by code inspection and documentation rather than executable evidence.
