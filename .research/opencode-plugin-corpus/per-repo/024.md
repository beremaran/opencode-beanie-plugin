## OpenCode patterns

### Native registration through `config`

- Startup loads bundled agents, commands, and skills from paths relative to the compiled entrypoint, then loads global and project hooks using `ctx.directory` (`src/index.ts` lines 75-94).
- The `config` callback merges loaded agents after existing runtime agent config, merges commands without overwriting existing commands, and appends the bundled skill directory to `config.skills.paths` without duplicating it (`src/index.ts` lines 282-309). This is a useful pattern for shipping Markdown assets while preserving host configuration.
- The changelog records a migration to OpenCode native skill discovery through `config.skills.paths` and bundled `.opencode` commands/skills (`CHANGELOG.md` lines 7-10). This is evidence that native discovery is preferable to a custom tool/injection path when the host supports it.
- The package exposes `dist/index.js` and declarations as its module entrypoint, uses ESM, and declares `@opencode-ai/plugin` as both a development dependency and peer dependency (`package.json` lines 2-7, 40-55). The published file list includes runtime assets needed by the loader (`package.json` lines 8-15).

### Filesystem Markdown conventions

- Agents are Markdown files with YAML frontmatter; the loader derives the agent name from the filename, defaults mode to `all`, maps singular `permission` to plural `permissions`, and preserves optional fields only when defined (`src/loaders.ts` lines 9-19, 131-162).
- Skills are directories containing `SKILL.md`; the directory name is a fallback name and `use_when` is normalized to `useWhen` (`src/loaders.ts` lines 21-28, 164-187). Commands use one Markdown file per command and derive the command name from the filename (`src/loaders.ts` lines 30-43, 190-214).
- Frontmatter parsing is deliberately best-effort: missing delimiters leave the entire content as the body, and invalid YAML returns empty data plus the original body (`src/loaders.ts` lines 110-125). This avoids taking down plugin startup for one malformed asset, but it can also silently discard configuration.

### Hook model

- Hooks are read from `<global config>/opencode/hook/hooks.md` and `<project>/.opencode/hook/hooks.md`; global definitions are merged before project definitions (`src/config-paths.ts` lines 34-40; `src/index.ts` lines 92-94, 248-261`). The README documents the same precedence and ordering (`README.md` lines 711-729).
- The loader accepts session events plus `tool.before.*` and `tool.after.*`, rejects unknown events and malformed action lists, and preserves declaration order (`src/loaders.ts` lines 57-91, 216-249).
- Tool hooks run wildcard first, then the tool-specific event. Only `before` hooks can block (`src/index.ts` lines 264-279). A bash exit code of 2 stops the hook and throws from `tool.execute.before`, preventing the tool call (`src/index.ts` lines 224-240, 324-339). Other action failures are logged and later actions continue (`src/index.ts` lines 157-185, 239-245); the README makes this contract explicit (`README.md` lines 763-774, 867-890).
- The plugin tracks paths passed to `write` and `edit` per session, uses them for `hasCodeChange`, and clears the set on idle or deletion (`src/index.ts` lines 341-353, 384-409). This is a practical event-state pattern, but it tracks the supplied path string rather than resolving or validating the filesystem target.
- The checked-in example is intentionally small: on main-session idle after a code change it runs `npm run test` (`.opencode/hook/hooks.md` lines 1-7).

### Context-rich shell hooks

- Bash actions run with `bash -c`, the project directory as cwd, two OpenCode environment variables, and a JSON context on stdin (`src/bash-executor.ts` lines 20-37, 56-58; `README.md` lines 826-865). A default 60-second timeout sends SIGTERM and reports a failure (`src/bash-executor.ts` lines 18, 43-66).
- Hook results are fed back into the session with exit code, duration, and up to 500 characters of stdout/stderr (`src/index.ts` lines 202-221; `README.md` lines 875-885). Truncation is a useful observability guard.

### Skill activation and bundled OpenSpec assets

- Skills with `use_when` produce a system-message block containing mandatory `skill({ name: ... })` calls (`src/index.ts` lines 99-102, 412-420; `src/skill-activation.ts` lines 3-13). The bundled `.opencode/` assets include OpenSpec commands and skills; for example, the apply command requires status/instruction queries, reads declared context files, and pauses on ambiguity or errors (`.opencode/commands/opsx-apply.md` lines 5-18, 20-49, 60-81).
- The same instructions are duplicated in `.opencode/skills/openspec-apply-change/SKILL.md` (`lines 12-54, 67-80`). Duplication makes the feature self-contained but creates a documentation-drift surface.

## Security and reliability pitfalls

1. **Configured shell execution is a privileged trust boundary.** Hook configuration can execute arbitrary `bash -c` commands in the project cwd (`src/bash-executor.ts` lines 20-37), and both global and project hook files are loaded automatically (`src/index.ts` lines 92-94). This should be treated as code execution, with clear trust/consent expectations. The README's sensitive-file blocking example is only an optional user hook, not an enforced safeguard (`README.md` lines 963-984).
2. **Tool-action hooks are indirect LLM execution.** A configured tool action is converted into a natural-language prompt asking the session to use a named tool, with JSON arguments interpolated into the prompt (`src/index.ts` lines 177-184). This is less deterministic than direct tool invocation and makes the model part of the hook's enforcement path.
3. **Prompt-session accepts a caller-supplied session ID without a child check.** When no ID is supplied it selects the last child, but a supplied `sessionId` is sent directly to `client.session.prompt` (`src/tools/prompt-session.ts` lines 19-43`). If the tool is exposed to an untrusted actor, authorization should be enforced before allowing arbitrary session targeting.
4. **External URL input is not constrained in the gitingest tool.** The schema describes a GitHub URL, but `fetchGitingest` posts the caller's string to a third-party service without URL validation or an allowlist (`src/tools/gitingest.ts` lines 16-33, 36-57). Validate the URL and document the data-disclosure implications before treating this as a safe repository-only tool.
5. **Frontmatter is typed but not schema-validated.** `js-yaml` output is cast to TypeScript interfaces and only a few structural checks are performed for hooks (`src/loaders.ts` lines 110-123, 216-239). Unexpected scalar values can survive until runtime; explicit validation would make malformed user-controlled configuration safer.
6. **Prompt activation interpolates metadata into system text.** Skill names and trigger text are inserted without escaping (`src/skill-activation.ts` lines 7-13). Because skills can be discovered from project-level locations and the plugin appends this block to the system prompt (`src/index.ts` lines 412-420), untrusted skill metadata can influence instructions. Treat project skill metadata as trusted or constrain/escape it.

## Testing lessons

- Tests are colocated under `src/**/*.test.ts`, use Vitest globals, and the config makes that scope explicit (`vitest.config.ts` lines 1-8). The main suite uses temporary directories with cleanup for loader tests (`src/index.test.ts` lines 70-85, 211-221), a good pattern for filesystem-backed plugin assets.
- Loader tests cover missing directories, Markdown filtering, defaults, permission-key compatibility, fallback skill names, malformed YAML, hook event validation, action validation, and merge ordering (`src/index.test.ts` lines 19-68, 70-209, 376-842, 1122-1196). This is unusually strong coverage for configuration edge cases.
- Bash executor tests cover success, nonzero exit, blocking exit 2, stderr, injected environment, stdin JSON, timeout, cwd, quoting, and empty context fields (`src/index.test.ts` lines 843-1020). These tests document the process contract without requiring network access.
- Network-facing Etherscan tests stub `fetch`, restore environment variables, and assert URL parameters and API/HTTP failures (`src/tools/blockchain/etherscan-client.test.ts` lines 4-19, 22-49, 52-136). PDF tests generate a small in-memory PDF and use temporary files, avoiding fixture and network dependence (`src/tools/pdf-to-markdown.test.ts` lines 14-80, 84-119).
- CI runs `npm ci`, strict typecheck, build, and tests on Node 20 (`.github/workflows/ci.yml` lines 9-21). The repository guidance notes there is no lint script or ESLint configuration, so typecheck is the closest lint gate (`AGENTS.md` lines 14-28).
- A gap remains: the tests exercise loader and helper contracts but do not appear to instantiate the full plugin and assert OpenCode callback behavior, especially hook blocking, wildcard/specific ordering, session cleanup, or config merge precedence. Those are high-value integration tests suggested by the runtime paths above.

## Packaging and release lessons

- `npm run build` is plain `tsc`, producing declarations into `dist`; `npm test` is `vitest run` (`package.json` lines 16-19; `tsconfig.json` lines 1-16). Keeping build/typecheck/test commands simple helps consumers and CI reproduce releases.
- The package explicitly ships runtime Markdown directories alongside compiled code (`package.json` lines 8-15), which is essential because the entrypoint loads those assets relative to `dist` (`src/index.ts` lines 75-81).
- Publish workflow checks the tag version against `package.json`, reruns typecheck/build/tests, publishes publicly, and requires a matching changelog section (`.github/workflows/publish.yml` lines 24-49). This is a strong release gate. The workflow grants `id-token: write` and `contents: write` (`lines 8-10`), so those permissions should remain limited to the publishing job and reviewed when changing release automation.
- The package uses a lockfile and CI uses `npm ci` (`package-lock.json` exists; `.github/workflows/ci.yml` lines 13-20), while the repository's local guidance correctly distinguishes Node/npm setup from the project's Vitest commands (`AGENTS.md` lines 5-28).

## Bottom line

The strongest reusable pattern is a small ESM plugin entrypoint that registers Markdown-defined agents, commands, and skills through the host `config` callback, while keeping hooks in standard global/project configuration paths and making ordering/blocking semantics explicit. Its tests are broad at the loader/process/tool-helper level and its release workflow is disciplined. The main risks are inherent privilege and trust-boundary issues: arbitrary configured shell execution, indirect model-mediated hook tools, unconstrained external ingestion, and session targeting without an explicit child authorization check.
