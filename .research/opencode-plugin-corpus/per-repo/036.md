## OpenCode Patterns

### MCP integration instead of an OpenCode plugin API

- The README documents installation as an OpenCode `mcpServers` entry that runs `npx -y lemma-mcp@latest` (`README.md:19-41`). This is a useful compatibility pattern when a feature can be exposed as a standalone MCP server rather than depending on OpenCode internals.
- The entrypoint defaults to the MCP server when invoked without arguments, supports library and visualizer modes, validates ports, and reports fatal errors without a stack trace (`src/index.ts:8-13`, `src/index.ts:30-39`, `src/index.ts:42-93`).
- The server uses the MCP SDK's stdio transport and registers handlers for tools, resources, and tool calls (`src/server/index.ts:1-25`, `src/server/index.ts:36-59`, `src/server/index.ts:61-140`, `src/server/index.ts:142-223`). This is a concrete pattern for an OpenCode-compatible process: keep protocol I/O on stdio and put user-facing diagnostics on stderr.
- Memory is injected at protocol surfaces rather than written into the project. `tools/list` rebuilds tools with project-specific memory (`src/server/index.ts:55-59`), while instructions are built with a token budget and dynamic memory index (`src/server/system-prompt.ts:192-255`). The README explicitly states that the system does not write `AGENTS.md` or other project files (`README.md:55-68`).
- The implementation separates static teaching instructions from dynamic context and preserves the static template when the configured budget is too small (`src/server/system-prompt.ts:192-255`). The tests verify both budget compliance and preservation of the static template (`tests/server/memory-injection.test.ts:78-99`).
- A small hook abstraction supports lifecycle callbacks and prompt modifiers, with unregister functions and per-callback error isolation (`src/server/hooks.ts:18-57`, `src/server/hooks.ts:69-101`). This is reusable for optional integrations, but the global mutable registries require cleanup in tests and careful process-lifetime assumptions.

## Architecture and Implementation Lessons

- The project uses one local SQLite database with FTS5, migrations, statement caching, and targeted stores; the development guide describes the database and migration layout (`docs/development/DEVELOPMENT.md:24-43`, `docs/development/DEVELOPMENT.md:75-81`). Local persistence is a practical default for memory features that should work across MCP clients.
- Context ranking is explicit: injection uses confidence/recency scoring, limits, and a diversity filter to avoid spending the token budget on near-duplicates (`docs/development/DEVELOPMENT.md:83-91`, `src/server/system-prompt.ts:63-116`). The same design principle applies to OpenCode prompts and tool descriptions: rank, cap, and deduplicate before injection.
- Tool-call handling records lifecycle/session state, appends reminders and session messages, and treats failures in optional recording as non-fatal (`src/server/index.ts:160-223`). This shows how cross-cutting behavior can be layered around MCP handlers without changing each individual tool implementation.
- The config loader creates a default config on first use, supports a test override directory, deep-merges user values, and rejects prototype-pollution keys (`src/memory/config.ts:52-105`). However, it does not visibly validate value types or ranges after parsing; malformed values can therefore flow into later logic. A production plugin should schema-validate user configuration, not only protect object keys.

## Security and Privacy

- The README claims local-only storage, secret redaction, and visualizer hardening (`README.md:185-191`). The implementation backs up those claims in several places:
  - Redaction covers common API keys, GitHub/Slack tokens, private keys, database URLs, cloud keys, webhook secrets, passwords, and bearer tokens (`src/memory/privacy.ts:8-33`). Redaction resolves overlapping matches by choosing the longest match and performs one left-to-right replacement pass (`src/memory/privacy.ts:47-66`).
  - Traffic logs redact the complete serialized body before truncation, explicitly avoiding persistence of the raw match metadata (`src/server/traffic-log.ts:27-39`). The log rotates to at most three daily files (`src/server/traffic-log.ts:41-53`).
  - Tests cover a secret near the truncation boundary and a MongoDB URI password, not merely a short happy-path key (`tests/server/traffic-log.test.ts:34-73`).
  - The visualizer binds only to `127.0.0.1`, uses a per-startup random token, restricts CORS origins to the local port, and requires the token for API routes (`src/server/visualize.ts:15-39`, `src/server/visualize.ts:123-130`, `src/server/visualize.ts:248-280`).
- Security pitfalls remain. The visualizer accepts the token in a URL query parameter for export because `window.open` cannot set headers (`src/server/visualize.ts:25-39`, `src/server/visualize.ts:228-241`). Query tokens can leak through browser history, referrers, or copied URLs, so an OpenCode-facing implementation should minimize this compatibility exception and document the tradeoff.
- Visualizer request bodies are parsed with no visible size limit (`src/server/visualize.ts:45-51`), and JSON parse errors are converted to a generic 500 response (`src/server/visualize.ts:261-266`). Add request-size limits and explicit 400 handling before exposing a similar local admin surface.
- The traffic logger is enabled by default and logs tool names, arguments, resource URIs, and response text, albeit with truncation/redaction (`src/server/traffic-log.ts:6-14`, `src/server/traffic-log.ts:72-101`, `src/server/traffic-log.ts:174-197`). Sensitive operational metadata can still be retained, so a plugin should make logging opt-in or provide a clearly documented disable setting.
- The background visualizer launch uses `spawn` with a detached child and ignored stdio (`src/index.ts:58-74`). It is simple and cross-platform, but lifecycle supervision, stale process handling, and user-visible startup failures are limited.

## Testing Lessons

- CI runs on Node 20 and 22 and gates dependency installation, type checking, build, and tests (`.github/workflows/ci.yml:9-35`). This is a good minimum release gate for a TypeScript MCP package.
- The test command uses Node's built-in test runner with `tsx` and explicitly enumerates test directory globs (`package.json:25-41`). The test TypeScript config includes both source and tests with `noEmit` (`tsconfig.test.json:1-18`).
- Tests use temporary directories for persistent state and restore global directory configuration in teardown (`tests/server/memory-injection.test.ts:14-28`). The global setup disables the logger to prevent test disk I/O (`tests/_setup.ts:1-3`). This is especially important for MCP plugins that otherwise write to a user's home directory during imports or initialization.
- The injection tests assert behavior rather than only snapshots: project/global scoping, no `AGENTS.md` pointer, token limits, tool count, non-mutation of base tool definitions, and memory content placement (`tests/server/memory-injection.test.ts:30-169`).
- Skill installation tests cover creation, idempotence, upgrade replacement, nested directories, error swallowing, frontmatter, tool inventory, and version stamps (`tests/server/install-skill.test.ts:21-128`). This is a strong model for testing package side effects.
- The repository also includes manual MCP smoke and multi-wave scripts under `tests/manual/`; these are available as separate npm scripts rather than part of the default unit suite (`package.json:37-41`). Manual protocol tests are useful, but the release gate should ideally include a deterministic automated stdio handshake as well.

## Packaging and Distribution

- `package.json` exposes the compiled CLI as both `main` and `bin`, and provides subpath exports for memory, guides, and server modules (`package.json:1-15`). It limits the npm payload to `dist`, the postinstall script, visualizer assets, README/docs, and license (`package.json:16-23`).
- The build compiles TypeScript and copies `assets/visualizer.html` into `dist/server/`; `prepare` and `prepublishOnly` ensure the build occurs (`package.json:25-31`). The visualizer asset copy is a packaging-critical step and should be checked in a packed-artifact test, not only a local build.
- The package declares Node >=20 and relies on `@modelcontextprotocol/sdk` plus native `better-sqlite3` (`package.json:54-69`). Native SQLite dependencies make runtime/ABI support and platform CI important considerations for consumers.
- The postinstall script is deliberately guarded when `dist` is absent and swallows errors so a skill-file side effect cannot break installation (`scripts/postinstall.mjs:1-21`). The runtime installer is idempotent and version-aware, writes under `~/.agents/skills/lemma`, and treats failure as non-fatal (`src/server/install-skill.ts:1-13`, `src/server/install-skill.ts:43-71`). This is a useful packaging pattern, but any install-time home-directory write should be clearly disclosed and offer a disable path.
- The README's quick start uses `@latest` (`README.md:28-41`). That improves freshness but harms reproducibility and can introduce unreviewed behavior changes; production OpenCode configurations should pin a version or lock the package through a controlled installation.

## Main Pitfalls and Transferable Guidance

- Do not assume an MCP server is equivalent to an OpenCode plugin: this repository has no OpenCode plugin entrypoint or plugin API usage; its integration is a separately launched MCP process configured in `opencode.json` (`README.md:19-41`, `src/server/index.ts:1-9`).
- Dynamic prompt/tool injection must be bounded and tested for both scope and budget (`src/server/system-prompt.ts:192-255`, `tests/server/memory-injection.test.ts:78-169`).
- Local-first storage still needs privacy controls because traffic logs and prompts may contain user data. Redact before truncating, test overlap/boundary cases, and rotate or disable logs (`src/server/traffic-log.ts:27-53`, `tests/server/traffic-log.test.ts:34-73`).
- Side effects should be idempotent, version-aware, sandboxable in tests, and non-fatal when optional (`src/server/install-skill.ts:37-71`, `tests/server/install-skill.test.ts:21-93`).
- Treat local HTTP admin tooling as an attack surface. Bind narrowly, authenticate every data-changing route, restrict origins, cap bodies, and avoid query-string credentials where possible (`src/server/visualize.ts:20-39`, `src/server/visualize.ts:123-130`, `src/server/visualize.ts:248-280`).
- Pin published versions for reproducible OpenCode deployments rather than copying the README's `@latest` recommendation (`README.md:32-39`).
