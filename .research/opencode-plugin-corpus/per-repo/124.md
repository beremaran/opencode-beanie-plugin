# Repository 124: Zellij Namer

## Scope and identity

- Manifest index 124 is **Zellij Namer**, repository `24601/opencode-zellij-namer`; the manifest pins clone `.../repos/24601--opencode-zellij-namer` at commit `520862a679ba7236678ebdedc7073cb65408f587` (`repo-map.json:1882-1894`). This review is limited to that clone and its `.github/` and `src/` subdirectories.
- The package is an OpenCode plugin that renames Zellij sessions from project/activity context, with Gemini naming and heuristic fallback (`README.md:1-5`, `src/index.ts:351-457`).

## OpenCode patterns worth reusing

- **Factory-scoped state:** `ZellijNamer` keeps debounce/cooldown timestamps, current name, and a bounded signal list inside each plugin instance rather than module-global state (`src/index.ts:351-360`). This is a good isolation pattern for multiple plugin instances and tests.
- **Event adapter with runtime validation:** The exported plugin returns an `event` handler and first checks that the unknown payload is a non-null object with a string `type` (`src/index.ts:422-441`). It then extracts only the supported event fields for `session.idle`, `file.edited`, `command.executed`, and `todo.updated` (`src/index.ts:429-453`).
- **Non-blocking lifecycle work:** Initial naming is scheduled with `process.nextTick`, and idle-triggered naming is also deferred rather than awaited by the event handler (`src/index.ts:371-378`, `src/index.ts:429-436`). This preserves responsiveness, but requires explicit lifecycle/error tests.
- **Stable side-effect throttling:** Separate debounce and rename cooldown checks prevent repeated checks and name churn (`src/index.ts:380-419`); the README explains the intended five-second/five-minute defaults (`README.md:145-149`).
- **Graceful optional integration:** Missing Gemini credentials skip AI and use deterministic heuristic naming (`src/index.ts:254-265`, `src/index.ts:400-408`), while missing Zellij or non-Zellij execution is logged and skipped (`src/index.ts:116-146`, `src/index.ts:394-398`).
- **Bounded context:** Signals are truncated to 200 characters and retained only up to `maxSignals` (`src/index.ts:343-349`). AI receives at most five signals, each truncated to 100 characters (`src/index.ts:271-275`).

## Implementation and integration pitfalls

- **Trigger behavior does not match the README.** The README says the plugin listens to all four event types (`README.md:137-143`), but only `session.idle` schedules `maybeRename`; file, command, and todo events merely append signals (`src/index.ts:429-453`). In practice those events influence a later idle event rather than independently triggering a rename.
- **Configuration names drift.** The README documents `OPENCODE_ZELLIJ_DEBUG`, `OPENCODE_ZELLIJ_COOLDOWN_MS`, `OPENCODE_ZELLIJ_DEBOUNCE_MS`, `OPENCODE_ZELLIJ_MODEL`, and `OPENCODE_ZELLIJ_MAX_SIGNALS` (`README.md:41-53`), while the implementation reads `OPENCODE_ZN_DEBUG`, `OPENCODE_ZN_COOLDOWN_MS`, `OPENCODE_ZN_DEBOUNCE_MS`, `OPENCODE_ZN_MODEL`, and `OPENCODE_ZN_MAX_SIGNALS` (`src/index.ts:34-44`). Users following the README cannot configure those settings.
- **Documented timeout is not implemented as configuration.** README advertises `OPENCODE_ZELLIJ_TIMEOUT_MS` with a 3,000 ms default (`README.md:49-52`), but the code has no timeout field and hard-codes a 2,000 ms Promise timeout (`src/index.ts:292-295`).
- **Detached process success is optimistic.** `renameSession` returns `true` immediately after `spawn(...).unref()` and therefore updates `currentName` and cooldown state before Zellij reports whether the command actually succeeded (`src/index.ts:319-336`, `src/index.ts:415-419`). A failed rename can suppress retries for the full cooldown.
- **AI output validation is syntactic, not semantic.** The prompt asks for an allowed intent and a 40-character format (`src/index.ts:273-282`), but acceptance only checks lowercase alphanumerics/hyphens and length (`src/index.ts:297-304`). A syntactically valid but policy-invalid name is accepted.
- **The initial rename can be low-information.** Plugin initialization schedules a rename before any activity signal exists (`src/index.ts:371-378`); the heuristic then defaults to `feat` when no signal matches (`src/index.ts:400-408`, `src/index.ts:184-195`).
- **The advertised uniqueness strategy is not present in the reviewed source.** README describes branch, directory, time, and numeric disambiguation (`README.md:151-171`), but the implementation’s tag inference is a fixed keyword scan over accumulated signals (`src/index.ts:197-204`, `src/index.ts:400-407`) and has no branch/session collision check.

## Security and privacy lessons

- **Prefer argv-based process execution.** Git and Zellij calls use `execFileSync` with argument arrays, and renaming uses `spawn` with an argument array rather than shell interpolation (`src/index.ts:124-145`, `src/index.ts:214-220`, `src/index.ts:325-330`). This materially reduces shell-injection risk when event-derived paths or commands are involved.
- **Validate event-derived input and bound memory.** `isValidEvent`, `isValidPath`, per-signal truncation, and the ring-buffer cap provide useful defense-in-depth (`src/index.ts:112-114`, `src/index.ts:339-349`).
- **Treat repository guidance as untrusted prompt input.** The plugin reads `AGENTS.md` from three locations and includes extracted content in the Gemini prompt (`src/index.ts:72-102`, `src/index.ts:284-290`). The code limits guidance to 400 characters, but this remains prompt-controlled content and should not be treated as an instruction authority. User instructions are explicitly appended as taking precedence (`src/index.ts:288-290`).
- **Privacy claims need precise alignment with implementation.** README says only command names and conversation snippets are sent, not full conversation history or command output (`README.md:173-192`). The implementation actually forwards recent event message content and full command strings, each up to 200 characters before the five-signal/100-character AI projection (`src/index.ts:343-347`, `src/index.ts:430-444`, `src/index.ts:271-275`). That is bounded, but can include sensitive arguments or message text and should be documented as such.
- **Path-prefix checks are fragile.** The code uses `realPath.startsWith(resolvedCwd)` for AGENTS and package paths (`src/index.ts:80-86`, `src/index.ts:228-234`). A component-boundary check or `relative()`-based containment test is safer; the current check is not a general path-traversal proof.
- **Do not log secrets, but avoid overclaiming.** API keys are read from environment variables and are not included in the debug configuration object (`src/index.ts:261-269`, `src/index.ts:369-369`). However, debug logs can include paths, event-derived context, and AI error text (`src/index.ts:97-99`, `src/index.ts:303-307`), so debug mode still deserves privacy guidance.

## Testing lessons

- The checked-in test command reports **39 passing tests**, but `src/index.test.ts` does not import `src/index.ts`; it defines local copies of `inferIntent`, `buildSessionName`, `sanitize`, configuration loading, prompt construction, and signal buffering (`src/index.test.ts:1-4`, `src/index.test.ts:283-400`). The passing suite therefore does not establish that the shipped plugin behaves as tested.
- There are no tests for the actual exported factory, OpenCode event dispatch, debounce/cooldown state, Zellij discovery, process spawning, Gemini fallback/timeout, or error paths. The repository guidance recommends integration tests for event-flow changes (`AGENTS.md:95-111`), but the current suite is unit-only and disconnected from production code.
- Several tests encode behavior that differs from production: the test helper uses `OPENCODE_ZELLIJ_*` names while production uses `OPENCODE_ZN_*` (`src/index.test.ts:329-337`, `src/index.ts:34-44`), and the helper permits 48-character names while production’s AI rule and builder use 40 (`src/index.test.ts:61-65`, `src/index.test.ts:298-309`, `src/index.ts:311-317`).
- The CI pipeline correctly orders typecheck, tests, and build (`.github/workflows/ci.yml:20-30`), but local validation in this clone produced `bun test` success and a typecheck failure: TypeScript could not resolve `@google/generative-ai` even though it is declared in `package.json` (`package.json:38-44`) and `package-lock.json` (`package-lock.json:11-24`). This is a concrete install/environment or dependency-materialization gap that CI should catch from a clean checkout.

## Packaging and release lessons

- The package has a conventional ESM entrypoint and declaration output (`package.json:5-12`, `tsconfig.json:1-15`), publishes only `dist`, README, license, and changelog (`package.json:49-54`), and requires Node 18+ while declaring Bun as a peer dependency (`package.json:35-47`). The narrow `files` list is a good way to avoid shipping source and repository metadata.
- `prepublishOnly` builds before publishing (`package.json:9-12`), and the release workflow installs, builds, tests, then publishes with npm provenance (`.github/workflows/publish.yml:20-35`).
- There are two publish paths: CI publishes on every successful push to `main` and suppresses publish failure with `continue-on-error: true` (`.github/workflows/ci.yml:32-54`), while the release workflow publishes on a GitHub release (`.github/workflows/publish.yml:1-5`, `:34-35`). This can create duplicate/ambiguous release semantics and can make a failed main-branch publish appear green.
- CI uses `bun-version: latest` (`.github/workflows/ci.yml:16-18`), which reduces reproducibility. The package lock pins the npm dependency version, but the runtime/toolchain itself is not pinned.
- Documentation is generally operationally useful: install/configuration, fallback behavior, privacy, troubleshooting, local plugin loading, and release instructions are all present (`README.md:22-37`, `README.md:173-257`). The main packaging lesson is to keep those instructions generated or tested against the actual environment-variable contract and entrypoint.

## Bottom line

The strongest reusable pattern is a small OpenCode factory with instance-local bounded state, deferred side effects, argv-safe subprocess calls, and an offline fallback. The highest-risk lessons are contract drift and false test confidence: the README, tests, and implementation disagree on configuration and limits, while the test suite passes without importing the shipped module. For a production OpenCode plugin, first connect tests to the exported factory and event flow, then make event triggers, timeout/configuration, privacy disclosures, and publish semantics agree with the implementation.
