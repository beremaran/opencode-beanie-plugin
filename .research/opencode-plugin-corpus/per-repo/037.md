## README and user-facing design

- The README describes the product as background capture, consolidation, and recall across OpenCode, Pi, and OMP (`README.md:62-76`). The setup wizard is the preferred install path and can disable host compaction, select harnesses, and configure models (`README.md:80-101`). Manual OpenCode setup adds the plugin and disables native compaction/pruning (`README.md:103-125`).
- The documented contract is important: `historian.model` is required for historian work, while dreamer/sidekick and embeddings are optional (`README.md:114-127`). A configuration that parses but lacks the historian model therefore gives a loaded plugin with failed background work, not a cleanly disabled feature.
- Conflict detection is a deliberate safety behavior. The plugin disables itself when another context manager or incompatible native compaction path is active, rather than double-compressing history (`README.md:137-153`). This is a reusable compatibility pattern, but it also means installation can appear successful while runtime behavior is intentionally absent.

## OpenCode integration patterns

- The server factory is typed as `Plugin`, receives the OpenCode context, migrates config before loading it, and initializes storage policy/SQLite tuning before the first database open (`packages/plugin/src/index.ts:1-11`, `71-101`). This ordering prevents legacy config and process-wide storage settings from being applied too late.
- The returned plugin object registers tools, an event handler, the message transform, system transform, command hook, chat-message hook, tool-definition hook, tool-execution hook, text-completion hook, and a config hook (`packages/plugin/src/index.ts:555-673`). The `chat.message` hook lazily preloads the tokenizer and captures provider/model/agent context so later `tool.definition` events can attribute token measurements (`packages/plugin/src/index.ts:627-666`).
- The main context operation is attached to `experimental.chat.messages.transform`; the outer wrapper receives a live getter, fail-closed controller, internal-child-session exemptions, compaction mode, and a storage re-open callback (`packages/plugin/src/index.ts:606-617`). This separates host lifecycle wiring from the feature runtime and permits storage recovery without rebuilding the wrapper.
- The implementation preserves the legacy loader contract by exporting only the default plugin factory from the entry module. The repository documents that OpenCode invokes every exported function in a legacy module as a plugin factory; exporting helper functions caused whole-plugin load failure, so helper builders live elsewhere (`packages/plugin/src/agents/hidden-agent-registrations.ts:3-23`). This is a particularly important packaging/entrypoint pitfall for OpenCode plugins.
- Hook construction is disabled cleanly when config says `enabled !== true`, and otherwise passes the whole config into the runtime rather than maintaining a brittle field-by-field map (`packages/plugin/src/plugin/hooks/create-session-hooks.ts:19-33`, `36-71`, `74-110`). The comment records that the old mapping silently dropped newly added fields, a useful maintenance lesson.

## Configuration and security

- Configuration is shared across harnesses, with project config overriding user config; the documented files are `<project>/.cortexkit/magic-context.jsonc` and `~/.config/cortexkit/magic-context.jsonc` (`CONFIGURATION.md:1-16`). The loader parses JSONC, substitutes variables, rejects prototype-pollution keys, preserves warnings, and reports parse/I/O/schema-recovery outcomes instead of silently treating all failures as valid config (`packages/plugin/src/config/index.ts:103-161`).
- The strongest security pattern is treating repository config as untrusted input. The project-security module explicitly strips escalation/exfiltration fields before merge, including hidden-agent prompts/permissions/tools, embedding destinations, SQLite PRAGMAs, storage permissions, model selection, prompt-surface text, and user-only fail-closed/update controls (`packages/plugin/src/config/project-security.ts:3-14`, `187-227`).
- Project thresholds are constrained so a cloned repository may raise thresholds but cannot force earlier historian work or increase user-paid background work (`packages/plugin/src/config/project-security.ts:46-51`, `packages/plugin/src/config/project-security.ts:148-180`). Hidden agents also have fixed allow-lists and step caps; dreamer is locked to `ctx_memory` for its curate role and cannot regain shell/edit tools through overrides (`packages/plugin/src/agents/hidden-agent-registrations.ts:96-123`).
- Storage defaults to owner-only `0700` directories and `0600` files. The documented shared-group escape hatch is user-config-only and explicitly warns that every group member can read all stored session content and memories (`CONFIGURATION.md:29-41`). This is a good example of documenting a security downgrade as an operational deployment decision.
- Diagnostics redact credentials and sanitize user paths. Secret detection uses segment-aware key matching to avoid redacting numeric token counts while still masking credential-shaped values (`packages/plugin/src/shared/redaction.ts:7-49`, `74-108`), and path sanitization replaces home/user paths (`packages/plugin/src/shared/redaction.ts:110-123`).

## Failure handling and correctness lessons

- The message-transform boundary distinguishes intentional loud failures from transient database contention and ordinary bugs. `SQLITE_BUSY`/`SQLITE_LOCKED` returns unmodified messages for retry, ordinary failures are logged and surfaced in session metadata, while fail-closed/context-limit errors are rethrown (`packages/plugin/src/plugin/messages-transform.ts:20-82`, `233-260`). This keeps a transient SQLite lock from crashing the prompt loop without hiding deterministic inoperability.
- When storage schema/migration failure makes the enabled runtime unusable, the plugin arms a fail-closed controller and blocks primary transforms until storage recovers or the build is upgraded (`packages/plugin/src/index.ts:221-258`). Tests verify the recovery command/version message, child/title/summary bypasses, and re-probe recovery (`packages/plugin/src/plugin/messages-transform.test.ts:109-212`).
- Compaction-off is intentionally different: fail-closed blocking becomes passthrough, restoring the host’s native compaction ownership (`packages/plugin/src/plugin/messages-transform.ts:94-100`, `126-150`). This mode distinction should be made explicit in any plugin that can hand ownership of context management back to OpenCode.
- The architecture prioritizes cache stability: deferred passes replay persistent mutations deterministically, while pending work rides a later cache-busting pass (`ARCHITECTURE.md:34-67`). This is a sophisticated but fragile invariant; changes to message ordering, synthetic messages, or mutation timing need byte-level tests rather than only semantic assertions.

## Pitfalls and adoption guidance

- Do not export helper functions from a legacy OpenCode plugin entrypoint; keep the entry module’s export surface to the loader-compatible factory (`packages/plugin/src/agents/hidden-agent-registrations.ts:6-23`).
- Do not trust project configuration merely because it is local JSONC. Strip privilege, model-spend, endpoint, prompt, filesystem-permission, and resource-exhaustion controls before merging it over user configuration (`packages/plugin/src/config/project-security.ts:187-227`).
- Do not treat a successful import as proof of a valid package. Validate the packed tarball, TUI subpath, lazy tokenizer, WASM/bundle assets, and both Bun and Node host branches (`.github/workflows/ci.yml:65-97`).
- Do not broadly swallow errors without an observability path. This project preserves unmodified messages for ordinary failures, persists a session error indicator, retries transient locks, and throws only intentional fail-closed/context-limit failures (`packages/plugin/src/plugin/messages-transform.ts:45-82`, `233-260`).
- The design is complex and tightly coupled to OpenCode experimental hooks, prompt-cache byte identity, SQLite schema fences, and hidden-agent semantics (`ARCHITECTURE.md:7-16`, `34-90`). Adopt the separation and testing patterns selectively; copying the full architecture without equivalent host-version and E2E coverage risks silent prompt corruption or disabled functionality.
