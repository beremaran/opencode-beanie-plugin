## OpenCode integration patterns

### Thin entrypoint and compatibility shape

- `src/index.ts` is deliberately a thin re-export shell: it exports `NotificationPlugin`, the default export, and selected consumer types (`src/index.ts:1-11`).
- The default export is an object with an `id` and `server` function, while the named plugin remains available for tests/consumers (`src/plugin-core.ts:475-482`). This is a useful compatibility pattern when plugin loaders have changed shape.
- The plugin catches initialization failures and returns `{}` instead of preventing OpenCode from starting (`src/plugin-core.ts:77-84`). Configuration errors additionally attempt a TUI toast and continue to auto-update handling (`src/plugin-core.ts:93-113`).

### Event lifecycle and routing

- Session state is tracked in a `Map`, and `session.created` records SDK session metadata before later events need it (`src/plugin-core.ts:136-145`, `src/plugin-core.ts:228-239`). This supports duration, title, parent-session, and session-type enrichment.
- `message.updated` events accumulate assistant token data by message ID and overwrite streaming intermediates rather than double-counting them (`src/plugin-core.ts:293-345`). Project aggregation is updated by deltas for repeated updates (`src/plugin-core.ts:322-343`).
- SDK events are converted to an internal `EventPayload`, with runtime handling for events not present in the SDK union such as `question.asked`, `permission.updated`, `session.status`, `command.executed`, `file.edited`, and `todo.updated` (`src/event-mapper.ts:48-197`). Missing session context becomes `unknown`, making event races observable and filterable (`src/event-mapper.ts:14-23`).
- Notifications are filtered by session type after token aggregation, defaulting to `main` sessions (`src/plugin-core.ts:393-405`; `src/types.ts:17-20`). This is a practical way to avoid subagent noise while retaining an opt-in path.

### Channel abstraction and lazy loading

- `ChannelSender` abstracts `send(unknown)` and `close()`, while `ChannelFormatter` converts generic subject/body text into channel-native structures (`src/types.ts:228-247`). The architecture guide documents the same sender/formatter separation and the required registration points for a new channel (`docs/channels/channel-development.md:94-112`, `docs/channels/channel-development.md:138-174`).
- Sender factories are registered in one map and dynamically imported only when the first event is handled (`src/handler.ts:49-54`, `src/handler.ts:160-207`). This prevents optional SMTP/webhook code from delaying plugin load and avoids top-level `nodemailer` conflicts (`src/email.ts:1-23`).
- The handler builds the template variable map once, records it, then applies per-channel event filtering, template rendering, formatting, and sending (`src/handler.ts:209-356`). Sender failures are isolated per channel, and `close()` closes all cached senders (`src/handler.ts:359-364`).
- DingTalk and Feishu use built-in fetch/Web Crypto, HMAC signing, payload limits, and channel-specific formatting (`src/dingtalk.ts:15-33`, `src/dingtalk.ts:64-75`, `src/feishu.ts:15-39`, `src/feishu.ts:59-69`). The shared webhook helper centralizes JSON POST timeout handling (`src/utils/webhook.ts:40-62`).

### Configuration and persistence

- Configuration supports project and global files, with project config taking precedence and channels merged by name (`src/config.ts:125-160`, `src/config.ts:267-285`). Unsupported channel types are warned and removed, and disabled channels are filtered before validation (`src/config.ts:40-53`, `src/config.ts:163-169`).
- When no file channel is configured, a default local JSONL channel is injected and enabled for all supported event types (`src/config.ts:296-357`). This gives a useful no-remote-channel fallback, but it is also an implicit data-retention behavior users must understand.
- Custom variable keys and values are constrained before template expansion (`src/config.ts:97-121`), and template substitution is a simple single-pass `{{word}}` replacement with missing values becoming empty strings (`src/template.ts:5-12`).
- Token persistence uses JSONL with latest-per-session deduplication, line-aware rotation, corrupted-line skipping, and normalized project-path aggregation (`src/session-cache.ts:69-109`, `src/session-cache.ts:139-180`). DB recovery is read-only and uses parameterized SQLite queries for existing session IDs (`src/session-cache.ts:261-310`).
- The recorder and logger are intentionally non-fatal: they ensure directories, rotate, and log failures rather than breaking event delivery (`src/recorder.ts:39-45`, `src/recorder.ts:86-113`; `src/logger.ts:104-145`).

## Security and operational pitfalls

- **Webhook secrets are exposed by debug logging.** DingTalk appends the access token and signature to `targetUrl`, then logs the complete URL (`src/dingtalk.ts:190-204`). With debug enabled, a credential-bearing webhook URL can enter the persistent log. Log only an origin/path or redact query parameters.
- **Webhook destination validation is weak.** DingTalk and Feishu accept any string beginning with `http://` or `https://` (`src/dingtalk.ts:162-172`; `src/feishu.ts:162-172`). This is adequate for user-configured webhooks but does not defend against malicious project configuration or internal-network targets. Consider URL parsing, an explicit HTTPS policy, and documented trust boundaries.
- **Sensitive host and project data is recorded by default.** The handler always calls `recordEventVariables()` independently of configured channels (`src/handler.ts:304-316`), and the variables include username, hostname, local IP, project path, process ID, token data, and custom-variable expansions (`src/handler.ts:268-301`). The recorder writes plaintext JSONL under the data directory without encryption or opt-out (`src/recorder.ts:30-37`, `src/recorder.ts:86-110`).
- **Custom variables can override built-ins.** This is documented and implemented (`src/handler.ts:304-313`; `docs/configuration.md:122-130`), but it can silently replace safety-relevant fields such as `projectPath`, `hostname`, or event fields in notifications and recordings. Reserve protected names or make override behavior explicit in validation.
- **Automatic updates are enabled by default.** The plugin schedules `runAutoUpdate(ctx, config.auto_update ?? true)` on the first main session (`src/plugin-core.ts:255-267`), fetches npm metadata, invalidates package directories/lockfiles, and invokes `bun` or `npm` with `shell: true` (`src/updater.ts:485-501`, `src/updater.ts:560-587`, `src/updater.ts:353-370`). This is a high-impact supply-chain and availability surface. Pinning disables installation but still permits update checks/toasts (`src/updater.ts:495-501`). Prefer opt-in updates, strict executable resolution, no shell, signature/integrity verification, and narrow deletion scope.
- **File output is configurable to arbitrary paths.** The file sender takes `config.filePath` directly and writes buffered JSONL (`src/file.ts:69-105`). This is useful operationally, but a project-level config can redirect sensitive notifications to shared or privileged locations. Validate path policy and document permissions.
- **Silent failure can hide delivery loss.** Sender implementations catch and log errors without rethrowing (`src/email.ts:176-201`; `src/dingtalk.ts:203-228`; `src/feishu.ts:203-228`), and the developer guide makes silent failure a contract (`docs/channels/channel-development.md:106-112`). This protects OpenCode availability but needs observable metrics/health reporting so notification loss is not mistaken for success.

## Packaging and release lessons

- `package.json` declares ESM, `dist/index.js`/`dist/index.d.ts`, a CLI binary, explicit exports, and `prepublishOnly: npm run build` (`package.json:1-21`, `package.json:46-52`). The `files` allowlist ships only `dist`, `README.md`, and `examples` (`package.json:41-45`), keeping the npm artifact small but excluding the detailed `docs/` tree and tests.
- TypeScript uses strict NodeNext resolution, declarations, and `dist` output (`tsconfig.json:1-15`). Relative source imports consistently use `.js` extensions, which is necessary for the emitted ESM package and is explicitly documented (`docs/channels/channel-development.md:364-376`).
- `dist/`, logs, coverage, and environment files are ignored (`.gitignore:1-8`), while `package-lock.json` is committed and the package scripts use npm for build/lint/typecheck but Bun for tests (`package.json:46-52`). Keep the package-manager story consistent in CI and release documentation.
- The README gives a direct OpenCode install snippet and CLI smoke commands (`README.md:47-61`, `README.md:150-156`), plus channel-specific docs and troubleshooting (`README.md:158-191`). A release checklist should additionally verify that package exports, generated declarations, CLI path, and the documented `projectName`/custom-variable behavior match the built artifact.

## Bottom line

The strongest reusable pattern is a thin OpenCode plugin entrypoint backed by a typed event-payload pipeline, lazy sender factories, pure channel formatters, per-channel isolation, and explicit persistence boundaries. The most important hardening work is to remove credential-bearing debug URLs, constrain webhook/file destinations, make plaintext recording opt-in or redacted, and make auto-update opt-in and non-shell. Before release, install dependencies and fix the current test isolation/path failures; the repository’s own planning metadata shows that final verification was not yet closed.
