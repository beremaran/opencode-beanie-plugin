# 074: Opencode Telemetry

## Scope and identity

- Manifest index 74 is `https://github.com/agostinilabsrl/opencode-telemetry`; the audited clone is `.research/opencode-plugin-corpus/repos/agostinilabsrl--opencode-telemetry` at commit `864c93df2b392968531a83586199f90d2fa83ab2` (`.research/opencode-plugin-corpus/repo-map.json:1132-1144`). No manifest subdirectory is selected; analysis covers the clone root.
- The README positions the project as local-first, historical session telemetry persisted to SQLite, with no collector or external infrastructure (`README.md:1-13`). It explicitly distinguishes passive cross-session history from on-demand telemetry plugins (`README.md:15-36`).

## OpenCode patterns

- The entrypoint follows the bare-plugin shape: it initializes commands and the database, creates handlers, and returns `event`, `tool.execute.before`, and `tool.execute.after` hooks (`src/index.ts:6-15`). It also exports both `server` and default forms for loader compatibility (`src/index.ts:18-20`).
- Session and message events are reduced to structural telemetry. `session.created` records parent ID, timestamps, directory/worktree, and server URL; user messages seed the agent; completed assistant messages become turns with token counts, model/provider, reasoning, latency, and finish reason (`src/handlers.ts:47-61`, `src/handlers.ts:62-132`). `session.idle` finalizes aggregate values, while deletion is intentionally ignored to preserve history (`src/handlers.ts:133-139`).
- Tool correlation uses an in-memory `Map` keyed by call ID, with a time-window fallback for orphan calls. This is a useful pattern when before/after event correlation is imperfect (`src/handlers.ts:17-45`, `src/handlers.ts:142-203`). Message IDs are deduplicated in a process-local `Set`, and turn counters are reseeded from SQLite after restart (`src/handlers.ts:19-44`, `src/handlers.ts:73-82`).
- The plugin records byte sizes rather than message bodies in the normal path. The README documents that the metrics DB excludes prompt content and that content is fetched only by `--content` and cached locally (`README.md:164-177`). The code enforces this separation by keeping SDK fetching in the CLI bridge rather than event handlers (`src/sdk-bridge.ts:1-3`, `src/sdk-bridge.ts:49-86`).
- Slash commands are installed into the current project’s `.opencode/commands` directory at plugin startup. The generated commands invoke packaged report/inspect scripts and instruct the model to emit output verbatim (`src/commands.ts:4-35`). This demonstrates a practical way to ship commands with a plugin, but it is also a runtime filesystem side effect.

## Data, configuration, and reliability lessons

- Bun’s built-in SQLite keeps the runtime dependency surface small. Initialization creates the data directory, enables WAL/NORMAL sync/foreign keys, applies idempotent schema DDL, then runs migrations (`src/db.ts:1-5`, `src/db.ts:229-238`). Prepared statements are cached for writes (`src/db.ts:240-280`).
- The database schema separates sessions, turns, tool calls, and metadata, with indexes for common historical queries (`src/db.ts:8-90`). Session idle recomputes totals from child rows, which is a useful self-healing strategy after missed or duplicated incremental updates (`src/db.ts:282-293`).
- The migration history contains an explicit warning about the original v2 bare-`try/catch` ALTER pattern and repairs it with `PRAGMA table_info` checks in v3-v5 (`src/db.ts:93-187`). The general lesson is to verify column existence before ALTER and only advance the schema marker inside the same transaction as the migration (`src/db.ts:189-203`).
- Every handler and DB write is wrapped in error handling and logs a warning instead of propagating failures into the user session (`src/handlers.ts:137-139`, `src/handlers.ts:160-163`, `src/db.ts:332-355`). This is appropriate for observability code, but it can hide data loss unless health/diagnostic reporting is provided.
- Configuration has explicit defaults, partial deep merge, dot-notation access, an allowlist of writable keys, and server-mode cache disabling (`src/config.ts:23-33`, `src/config.ts:40-69`, `src/config.ts:79-127`). The paths honor XDG locations and provide a Windows LOCALAPPDATA branch for the database (`src/paths.ts:4-11`).

## Pitfalls and security considerations

- `message.updated` handling depends on `time.completed`, inferred reasoning/mode, and specific SDK token shapes. The implementation preserves several uncertainty notes and uses heuristic fallbacks for skill arguments and tool error metadata (`src/handlers.ts:75-89`, `src/handlers.ts:147-197`). These assumptions should be verified against the target OpenCode SDK/event payloads, not treated as a stable public contract.
- The process-local dedupe set and pending-call map are not bounded or persisted (`src/handlers.ts:17-24`). Long-lived plugin processes could accumulate message IDs, and process termination can leave tool calls without durations. A bounded cleanup policy and restart-aware reconciliation would improve robustness.
- Content-cache path components are built directly from `sessionId` and `messageId` (`src/content-cache.ts:13-18`). If either identifier is ever attacker-controlled or contains separators/traversal segments, cache writes could escape the configured base directory. Validate identifiers or resolve and enforce that the final path remains beneath the cache root before reading/writing.
- The SDK bridge’s timeout uses `Promise.race`, so it bounds the caller’s wait but does not cancel the underlying SDK request (`src/sdk-bridge.ts:63-70`). Repeated timed-out inspections could leave work in flight; an abort-capable client/request signal would be safer.
- The read-only SQL command accepts SQL beginning with `SELECT`, `WITH`, `EXPLAIN`, or `PRAGMA` and executes user-provided query text (`src/cli/sql-cmd.ts:23-38`). The read-only database handle helps, but the prefix guard is not a complete SQL parser and explicitly permits PRAGMA. Treat this as a trusted-local-user diagnostic command, or enforce a stricter single-statement/read-only policy.
- Generated slash commands interpolate absolute script paths into shell blocks (`src/commands.ts:10-30`). JSON stringification protects quoting, but the generated command still asks OpenCode to run a shell command and print its output verbatim. Packaging and project trust boundaries should be documented, especially for shared repositories.
- The README says no external data is sent and no prompt content is stored in the metrics DB (`README.md:164-177`), but opt-in `--content` deliberately stores compressed prompt/tool content on disk (`src/content-cache.ts:1-4`, `src/sdk-bridge.ts:81-82`). The privacy boundary is clear; cache permissions, retention, and identifier sanitization remain operational concerns.

## Testing lessons

- The repository has 50 passing tests across seven files in the audited checkout (`bun test`, run during this review). Handler tests cover session parent mapping, completed-message filtering, deduplication, sequential turns, reasoning inference, orphan linking, tool duration/error handling, skill extraction, and fail-silent behavior (`tests/handlers.test.ts:89-283`).
- Configuration tests cover defaults, persistence, dot-notation lookup, unknown-key rejection, and reset (`tests/config.test.ts:19-54`); argument tests cover command/subcommand parsing and flag defaults/coercion (`tests/args.test.ts:4-41`). Analytical modules have focused tests for composition, deltas, distributions, and report-query regressions (test inventory in `tests/composition.test.ts:17-50`, `tests/deltas.test.ts:16-64`, `tests/distribution.test.ts:28-108`, `tests/report-bugs.test.ts:117-260`).
- The test suite is mostly unit-level with mock DB calls. It does not appear to exercise real OpenCode event streams, SQLite migrations against legacy databases, cache traversal/permissions, CLI SQL rejection, command generation, or the packed npm artifact. Those are the highest-value additions for production confidence.
- The checked-in tests intentionally assert that telemetry failures resolve without throwing (`tests/handlers.test.ts:260-283`). This protects the primary session, but a complementary test should verify that failures become observable through the health command or another diagnostic surface.

## Packaging and release lessons

- `package.json` declares the plugin entry as TypeScript (`main: src/index.ts`), exposes `octm` and `opencode-telemetry` through `bin/cli.js`, and includes source, commands, queries, scripts, migrations, docs, and release documentation in the package (`package.json:5-21`). The peer dependency on `@opencode-ai/plugin` avoids bundling the host plugin API (`package.json:47-53`).
- The CLI JavaScript and report/inspect scripts are generated during `prepack`; the build explicitly targets Node and externalizes `bun:sqlite` (`package.json:38-45`). Because the bin field points at generated `bin/cli.js` while the source checkout contains `bin/cli.ts`, a raw checkout is not necessarily runnable as an installed package until the build runs.
- The smoke workflow tests the important distribution boundary: typecheck, build, `npm pack`, fresh-directory install, `octm --help`, no-DB report, health failure behavior, and missing-session handling (`.github/workflows/smoke.yml:25-62`). This is a strong packaging pattern for plugins with generated artifacts.
- The release workflow uses frozen Bun installation, typechecking, automated patch versioning, npm provenance, and a dry-run mode (`.github/workflows/release.yml:14-18`, `.github/workflows/release.yml:43-47`, `.github/workflows/release.yml:49-93`). It grants contents and OIDC write permissions, so branch protection and workflow review remain important supply-chain controls.
- `.npmignore` excludes internal design/agent notes and the smoke script but leaves runtime source and operational docs selected by `files` (`.npmignore:1-8`, `package.json:11-21`). Keeping the package allowlist explicit is safer than relying only on ignore rules.

## Reusable takeaways

1. Keep telemetry hooks fail-silent and body-free by default; isolate any content retrieval behind an explicit, user-invoked path.
2. Persist raw child rows and periodically recompute aggregates so missed events do not permanently corrupt rollups.
3. Treat event payload shapes, parent-child attribution, and tool correlation as compatibility surfaces; add diagnostic fixtures and live-shape verification.
4. Make migrations idempotent and schema-marker updates transactional; never hide arbitrary ALTER failures behind a blanket catch.
5. Test the packed artifact, not only TypeScript modules, when package metadata points to generated binaries.
6. Validate all user/config/server-derived path components and define cache retention and permissions before enabling prompt-content caching.
