# Repository 075: OpenCode Throughput

## Identity and scope

- Manifest index: `75`, name `OpenCode Throughput`.
- Repository: `https://github.com/howardzhangdqs/opencode-throughput`.
- Inspected clone: `.research/opencode-plugin-corpus/repos/howardzhangdqs--opencode-throughput`.
- Manifest-recorded commit: `0497a162496637c4c274757b11b2f53c586cdbe2`.
- The clone is a TypeScript OpenCode plugin. Its documented purpose is real-time TTFT, TPS, latency, token, and cost monitoring, with toast output, JSONL persistence, and an agent-queryable benchmark tool (`README.md:1-14`).

## Repository shape and OpenCode integration

- `src/index.ts` is a deliberately small public entrypoint: it exports the named and default plugin plus the public `LogEntry` and `ModelStats` types (`src/index.ts:1-3`).
- The plugin is implemented as an async `Plugin` factory, receiving `client` and `directory`, and returns a `tool` plus an `event` handler (`src/plugins/throughput.ts:242-264`). This is a useful minimal pattern for combining OpenCode tools and event subscriptions.
- The implementation listens to `message.part.updated` to capture the first text-part start and to `message.updated` to finalize assistant-message metrics (`src/plugins/throughput.ts:264-287`, `src/plugins/throughput.ts:373-380`; `README.md:79-85`).
- It guards assistant-only processing (`src/plugins/throughput.ts:265-268`), handles message removal and session errors by clearing pending timing state (`src/plugins/throughput.ts:359-371`), and ignores non-text parts for TTFT (`src/plugins/throughput.ts:373-380`).
- The repository also provides a project-local forwarding entrypoint at `.opencode/plugins/throughput.ts:1`, re-exporting the source plugin. This supports local `.opencode` discovery without duplicating implementation.
- The plugin installation example uses the npm package name in `opencode.json` (`README.md:16-27`); the repository's own `opencode.json` only declares the OpenCode schema and does not register itself (`opencode.json:1-3`).

## Evidence-backed implementation patterns

### Metrics and persistence

- Model identity is normalized as `providerID/modelID` (`src/plugins/throughput.ts:17-19`, `src/plugins/throughput.ts:292-300`). The log schema retains provider/model, session/message identifiers, timing, token categories, cost, and finish state (`src/types.ts:1-18`).
- TTFT is measured from message creation to the first text-part start; TPS uses output tokens divided by generation duration, and returns `null` when there is no positive generation interval or no output (`src/plugins/throughput.ts:285-290`). Missing token/cost fields default to zero (`src/plugins/throughput.ts:303-312`).
- Each completed assistant response is appended synchronously as one JSON object per line under `~/.opencode/throughput.jsonl` (`src/plugins/throughput.ts:8-15`, `src/plugins/throughput.ts:82-86`). The same event can append a human-readable project-local `.opencode/throughput.md` when a project directory is supplied (`src/plugins/throughput.ts:247-256`).
- The benchmark tool reads logs, supports case-insensitive partial model matching and a trailing `last` slice, then aggregates latency, TTFT, TPS, tokens, and cost by model (`src/plugins/throughput.ts:110-141`, `src/plugins/throughput.ts:143-238`). This is a practical pattern for exposing historical observability through an OpenCode tool rather than requiring a separate CLI.
- User-facing feedback is sent through both `client.tui.showToast` and `client.app.log`, with failed notification calls intentionally swallowed (`src/plugins/throughput.ts:319-352`). Error finishes use warning-level app logging and a warning toast (`src/plugins/throughput.ts:319-330`).

### Testing patterns

- The test suite exercises the complete event sequence, missing/invalid timing, non-text parts, user messages, error finishes, missing tokens/model IDs, cleanup events, multiple models, and benchmark filtering/aggregation (`test/throughput.test.ts:87-224`, `test/throughput.test.ts:227-488`, `test/throughput.test.ts:514-679`).
- Tests use a lightweight mock client and invoke the returned event/tool hooks directly (`test/throughput.test.ts:14-21`, `test/throughput.test.ts:59-63`). This isolates plugin behavior without requiring a running OpenCode process.
- The tests verify persisted output by snapshotting the real `~/.opencode/throughput.jsonl` length and removing newly appended lines afterward (`test/throughput.test.ts:23-41`, `test/throughput.test.ts:65-85`). This demonstrates the persistence contract, but it also creates test isolation and parallel-execution concerns.

## Pitfalls and correctness risks

- `readLogs()` parses every nonblank line with an unguarded `JSON.parse` (`src/plugins/throughput.ts:101-108`). A truncated write, manual edit, or unrelated malformed line makes the benchmark tool reject instead of skipping bad records or reporting a controlled error.
- Event persistence uses synchronous filesystem calls in the event handler (`src/plugins/throughput.ts:82-86`, `src/plugins/throughput.ts:253-256`). Large logs, slow disks, or first-use directory creation can block plugin/event processing. The same handler performs two awaited client calls afterward (`src/plugins/throughput.ts:324-352`).
- There is no completed-message deduplication. Any repeated `message.updated` event with `time.completed` can append another record; the timing maps are cleared after the first completion, so a duplicate can be logged with missing TTFT (`src/plugins/throughput.ts:275-317`, `src/plugins/throughput.ts:354-356`). A processed-message set or explicit event/idempotency policy would be needed if OpenCode can emit repeated updates.
- Timestamp validation only rejects falsy values and does not reject negative or nonsensical durations (`src/plugins/throughput.ts:275-290`). The implementation can therefore produce negative latency or TTFT if upstream timestamps are inconsistent.
- `info` and `part` are cast to `any` at the event boundary (`src/plugins/throughput.ts:266`, `src/plugins/throughput.ts:374`), weakening the strict TypeScript configuration (`tsconfig.json:2-14`) exactly where upstream event-shape drift matters most.
- `stats` is updated for every response but never used by the benchmark tool or returned from the plugin (`src/plugins/throughput.ts:242-243`, `src/plugins/throughput.ts:315`; benchmark aggregation is recomputed from disk at `src/plugins/throughput.ts:126-201`). This is unnecessary in-memory state and can mislead maintainers into thinking it is the source of displayed statistics.
- `last` is not validated. Because selection uses `args.last ? filtered.slice(-args.last) : filtered`, zero means “all” rather than zero and negative values have JavaScript slice semantics (`src/plugins/throughput.ts:141`).
- Log append errors are not caught, unlike toast and app-log errors (`src/plugins/throughput.ts:316`, `src/plugins/throughput.ts:324-352`). A permissions or disk-full failure can interrupt completion handling.

## Security and privacy lessons

- The global JSONL record persists `sessionID` and `messageID` alongside provider/model, token counts, and cost (`src/types.ts:1-18`; construction at `src/plugins/throughput.ts:296-313`). This is useful correlation data but potentially sensitive metadata; the README documents the file location but does not describe retention, redaction, permissions, or rotation (`README.md:39-45`, `README.md:54-77`).
- The plugin writes to a fixed home-directory path (`src/plugins/throughput.ts:8-15`) and creates it with default filesystem permissions (`src/plugins/throughput.ts:11-14`). A production plugin should make privacy expectations explicit and consider restrictive file modes, bounded retention, and an opt-out/configuration mechanism.
- The benchmark `model` argument is used only for in-memory substring filtering (`src/plugins/throughput.ts:132-139`), not shell/database execution, so it does not create an evident injection path. The output nevertheless includes stored model names and timestamps, which should be treated as user-visible data.
- Broad empty catches around UI logging hide operational failures (`src/plugins/throughput.ts:324-352`), reducing observability of permission or API problems. If failures must be nonfatal, they should at least be surfaced through a safe diagnostic path.

## Packaging and release lessons

- The package is ESM, exports TypeScript source directly, and declares `@opencode-ai/plugin` as a peer dependency (`package.json:2-10`, `package.json:36-43`). The package files list includes only `src` (`package.json:11-13`).
- `build` emits `dist`, and `prepublishOnly` runs it, but `dist` is not included in the published `files` allowlist (`package.json:11-17`). Consequently the release build output is not packaged; consumers are expected to load the shipped TypeScript source. That may be intentional for OpenCode's loader, but it is a packaging mismatch worth making explicit or correcting.
- The build targets Node with Bun and strict typechecking is configured (`package.json:14-17`; `tsconfig.json:2-14`). The documented local-development plugin URL points directly at `src/index.ts` (`README.md:86-101`), consistent with source-based loading.
- CI installs with Bun and checks type safety and build output (`.github/workflows/ci.yml:9-30`), but does not run the existing Bun tests. A regression in event handling or benchmark output can therefore pass CI while typecheck/build remain green.
- Release execution is gated on a manual workflow dispatch, version change, and absent tag, then creates a GitHub release and publishes with npm provenance (`.github/workflows/release.yml:12-18`, `.github/workflows/release.yml:25-59`, `.github/workflows/release.yml:116-129`). The workflow requests `contents: write` and `id-token: write` (`.github/workflows/release.yml:8-10`), so the manual-release trust boundary and npm token handling should be protected accordingly.
- The README's publish command uses npm despite the development/build workflow using Bun (`README.md:103-107`). That is workable, but release instructions and automated release behavior should remain aligned.

## Overall assessment

This is a focused, understandable OpenCode plugin pattern: a small exported factory, event-derived metrics, a tool for querying durable history, and direct tests against mocked hooks. Its strongest lessons are to use the first text-part event for TTFT, keep event state keyed by message ID, expose observability through both UI and agent tools, and test event edge cases directly. The main production concerns are synchronous and globally scoped persistence, malformed-log failure, lack of completion idempotency, privacy/retention ambiguity for identifiers, and a CI pipeline that omits the test suite.
