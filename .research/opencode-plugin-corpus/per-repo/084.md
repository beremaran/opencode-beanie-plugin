## OpenCode Integration Patterns

### Event-driven plugin surface

The plugin uses the OpenCode `Plugin` type and client/event SDK types (`src/notify.ts:25-31`). Its factory loads configuration and detects the terminal once at startup (`src/notify.ts:555-568`), then returns the two relevant hooks: `tool.execute.before` for the `question` tool and `event` for runtime events (`src/notify.ts:949-1003`). This is a focused pattern for notifications: no conversation tools or prompt injection are added, consistent with the README's stated behavior (`README.md:112-117`).

Handled events are explicit: session readiness/idle, session errors, permission events, and question events (`src/notify.ts:966-1000`). The implementation normalizes untrusted event values before use, for example session IDs and errors (`src/notify.ts:304-311`, `src/notify.ts:975-987`).

### Noise control and lifecycle state

Parent-session filtering is opt-in for child notifications; if the session lookup fails, the implementation chooses to notify rather than silently miss a potentially important event (`src/notify.ts:429-447`, `src/notify.ts:472-490`, `src/notify.ts:222-230`). Quiet hours support overnight windows by treating a start time later than the end time as a wraparound interval (`src/notify.ts:198-216`). Focus suppression is limited to macOS, while questions intentionally skip the focus check (`src/notify.ts:183-191`, `src/notify.ts:530-548`).

Short deduplication windows prevent repeated question, ready, and permission notifications. Keys are derived from session/call/request IDs and expired entries are pruned during each check (`src/notify.ts:251-331`, `src/notify.ts:334-383`, `src/notify.ts:895-947`). The cmux status path also coalesces pending writes per session and drains them serially (`src/notify.ts:710-799`). This is a useful pattern when OpenCode can emit overlapping status events and the side effect is external.

### Degraded delivery paths

The backend prefers cmux when a trusted executable and cmux workflow are available, then falls back to desktop notification delivery if the command fails or returns false (`src/notify/backend.ts:1-5`, `src/notify/backend.ts:95-109`). macOS uses `alerter`; other platforms use the injected `node-notifier` callback (`src/notify/backend.ts:82-93`). The README documents the platform prerequisites and fallback behavior (`README.md:51-69`).

External commands are passed as argument arrays rather than shell command strings. cmux execution has a 1.5-second timeout, kills the process on timeout when possible, and converts failures into a false result (`src/notify/cmux.ts:37-44`, `src/notify/cmux.ts:146-179`). This bounds plugin latency and preserves the primary notification path when an optional integration is unavailable.

## Security and Reliability Lessons

- **Trust executable resolution before running it.** cmux resolution requires an absolute path, rejects paths inside the working directory and temporary directories, resolves symlinks, and checks the cmux environment before returning a command (`src/notify/cmux.ts:59-123`). This is a strong defense for a PATH-discovered executable, although the missing imported `canUseCmuxWorkflow` file prevents this snapshot from being independently buildable.
- **Use argv boundaries for user/event content.** Notification title, body, subtitle, and sound are passed as separate arguments to `alerter` and cmux (`src/notify/backend.ts:34-49`, `src/notify/cmux.ts:125-143`). The shared shell utility additionally rejects null bytes and escapes Bash, AppleScript, and batch metacharacters (`src/kdco-primitives/shell.ts:11-15`, `src/kdco-primitives/shell.ts:36-43`, `src/kdco-primitives/shell.ts:68-105`, `src/kdco-primitives/shell.ts:129-138`).
- **Avoid hanging subprocesses.** Git project-ID discovery is also bounded to five seconds and kills the process on timeout before falling back to a path hash (`src/kdco-primitives/get-project-id.ts:124-171`). The cmux path uses the same timeout utility and documents that a timeout alone does not cancel the underlying promise (`src/kdco-primitives/with-timeout.ts:24-32`, `src/kdco-primitives/with-timeout.ts:58-83`).
- **Fail soft for optional UX integrations.** Config parse errors fall back to defaults (`src/notify.ts:107-130`), frontmost-app/AppleScript failures return no focus information (`src/notify.ts:137-149`, `src/notify.ts:183-191`), and notification backend failures fall through rather than taking down event handling (`src/notify/backend.ts:101-109`).
- **Be careful with persisted caches.** Project IDs are cached in `.git/opencode`, but cache contents are validated as either a 40-character Git SHA or 16-character fallback hash before reuse (`src/kdco-primitives/get-project-id.ts:111-122`). Worktree `.git` files and shared `commondir` resolution are handled explicitly (`src/kdco-primitives/get-project-id.ts:76-109`).

## Testing and Verification Gaps

No tests are tracked, and there is no test runner or package manifest in the clone. That is especially risky for the event-to-notification matrix, deduplication keys/windows, overnight quiet hours, parent-session fallback, focus suppression, cmux fallback, timeout/kill behavior, and executable trust checks. The backend is structured with injected runtime functions (`src/notify/backend.ts:15-29`, `src/notify/cmux.ts:40-48`), which is testable, but the repository provides no tests demonstrating those seams.

The missing registry target and missing imported modules are packaging blockers that should be caught by a clean typecheck/build or a smoke test importing the published target. The README also says manual installation requires users to install `node-notifier` and `detect-terminal` themselves (`README.md:155-159`), while `registry.json` declares those dependencies for OCX installation (`registry.json:7-15`); release validation should verify that the selected distribution mechanism actually supplies the declared runtime dependencies.

## Packaging and Maintenance Lessons

- Keep registry source paths, generated target paths, README manual-install paths, and tracked files in one automated consistency check. Here they disagree (`registry.json:11-15`; `README.md:137-153`).
- Publish a complete facade or make the monorepo source the only install surface. The README correctly identifies the facade/monorepo ownership boundary (`README.md:165-175`), but the facade snapshot still needs a reproducible build artifact or a verified file export.
- Declare runtime dependencies at the distribution boundary. The registry does this for `node-notifier` and `detect-terminal` (`registry.json:10`), while manual installation leaves dependency setup to the user (`README.md:155-157`). Document and test both paths.
- Keep shared primitives narrowly scoped and reusable: logging integrates with OpenCode's UI and falls back to `console.warn` (`src/kdco-primitives/log-warn.ts:13-18`, `src/kdco-primitives/log-warn.ts:32-50`), and `Mutex.runExclusive` releases in `finally` (`src/kdco-primitives/mutex.ts:91-120`). These patterns reduce failure propagation and async race risk in plugin side effects.

## Bottom Line

The strongest OpenCode pattern is a startup-configured, event-hook plugin that aggressively suppresses noise, deduplicates side effects, and treats cmux/desktop notifications as optional bounded integrations. The strongest engineering lesson is equally concrete: this facade's published metadata and source snapshot are not self-consistent, and the absence of tests/build metadata leaves both packaging and security-sensitive subprocess behavior unverified.
