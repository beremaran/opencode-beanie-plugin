## What the plugin does

The plugin is a privacy/redaction layer. README claims that configured sensitive strings are replaced before provider requests, restored after model completion, and restored before local tool execution (`README.md:14-20`). It additionally redacts historical tool inputs/outputs before later requests because OpenCode stores the real executed arguments/output (`README.md:20`). The implementation registers exactly those integration points plus response completion: request message transformation, `experimental.text.complete`, and `tool.execute.before` (`src/index.js:43-142`).

### Request and tool lifecycle

- `experimental.chat.messages.transform` obtains a session ID from the first message, cleans its mapping, redacts non-ignored text and reasoning parts, and redacts tool state input/output/error/raw in place (`src/index.js:44-121`). This is a useful defense-in-depth pattern: ordinary prompts, reasoning, pending calls, completed output, and errors are all considered possible leak paths.
- Tool arguments are restored recursively immediately before execution (`src/index.js:137-142`; `src/deep.js:11-45`). The traversal handles arrays/plain objects and uses `WeakSet` cycle detection (`src/deep.js:18-44`). It deliberately skips class instances and other non-plain objects (`src/deep.js:4-9`, `35-36`), which reduces surprising mutation but leaves a coverage boundary.
- Completed model text is restored only in `experimental.text.complete` (`src/index.js:123-135`). The README explicitly documents that placeholders can briefly appear during streaming and are restored at `text-end` (`README.md:113-115`).
- All lifecycle mutations are in-place: message text, reasoning, tool state, and output arguments are directly assigned (`src/index.js:65-68`, `75-79`, `93-111`, `src/deep.js:28-40`). This is simple and avoids copies, but callers must tolerate shared objects being changed.

### Placeholder/session design

Each OpenCode session ID gets one `PlaceholderSession`; sessions are held in a plugin-local `Map` (`src/index.js:27-40`). A session gets a random 32-byte secret, maps original-to-placeholder in both directions, and generates a 12-hex-character HMAC-SHA256 prefix (`src/session.js:22-39`, `80-87`). The HMAC is preferable to a plain hash because the provider cannot precompute the value without the per-session secret. Repeated occurrences of the same original reuse the same placeholder (`src/session.js:90-99`). A hash collision gets an `_N` suffix (`src/session.js:107-138`), and categories are sanitized before entering the token (`src/session.js:3-9`).

The session has TTL cleanup and an oldest-entry cap (`src/session.js:41-65`, `100-105`), with example defaults of one hour and 100,000 mappings (`vibeguard.config.json.example:5-8`). Important operational caveat: the plugin-level session `Map` itself has no removal/TTL, so a long-lived process can retain one session object per distinct session ID even after its mappings expire (`src/index.js:27-40`; `src/session.js:41-49`).

## Configuration and security lessons

- Safe opt-in default: missing, invalid, or disabled configuration normalizes to `enabled=false`, making the plugin a no-op (`src/config.js:26-31`, `75-86`; `README.md:40-42`). A malformed earlier candidate is skipped and the loader continues to later candidates (`src/config.js:77-83`), which is operationally forgiving but can make an unexpected lower-priority config take effect.
- Search order is explicit: environment path, project root, project `.opencode`, then global config (`src/config.js:57-67`; `README.md:81-90`). The environment path is resolved relative to the OpenCode directory (`src/config.js:64-65`), so operators should not assume it is always interpreted relative to the shell working directory.
- The example combines exact keyword rules, custom regexes, built-ins, and exact-string exclusions (`vibeguard.config.json.example:9-20`). Built-ins intentionally trade precision for coverage: IPv4 does not validate 0-255 ranges (`src/patterns.js:74-80`), and README describes the broad privacy goal rather than a formal detector guarantee.
- Regex rules are compiled at redaction time with `new RegExp` and no local try/catch (`src/engine.js:73-77`). A bad user-supplied pattern can therefore throw during request processing; configuration parsing itself only does light validation (`src/config.js:70-74`). A production implementation should validate patterns at load time and define fail-open/fail-closed behavior.
- Redaction detects keyword and regex spans, excludes exact configured values, sorts/merges overlapping spans, and replaces from right to left (`src/engine.js:55-121`). The overlap handling is a strong correctness pattern because replacement offsets remain valid. However, keyword matching is case-sensitive (`src/engine.js:57-70`), and exclusions compare the complete matched original only (`src/engine.js:82-84`, `src/patterns.js:131`), so users need to configure case/variant behavior explicitly.
- Debug logging claims not to print plaintext and only logs config path/counts (`README.md:99-111`; `src/index.js:19-21`, `118-120`, `132-134`). The implementation does not interpolate matched values, which supports that claim. The config path itself can still reveal filesystem information, so the documented debug mode is not entirely metadata-free.
- Restoration intentionally leaves unknown placeholders unchanged (`src/restore.js:3-12`). This avoids destroying provider-generated text, but means an evicted/expired mapping cannot be recovered locally. The placeholder regex is based on a configurable escaped prefix and accepts broad category characters (`src/session.js:142-145`), so a custom prefix should be chosen to avoid collisions with normal content.

## Testing and verification

`package.json` defines `npm test` as `node --test` and runs it before packing (`package.json:13-16`). The tracked inventory contains no tests, fixtures, or test runner configuration, so the repository provides no regression coverage for overlap resolution, collision suffixes, TTL/eviction, malformed regexes, cyclic tool arguments, stream completion, or provider/tool hook payload shapes. README only documents running `npm test` (`README.md:92-97`).

Recommended minimum tests, based on the implementation’s risk surface:

- Hook contract tests for all three event handlers, including absent/malformed session IDs and missing message parts (`src/index.js:44-50`, `123-142`).
- Property-style redaction/restoration tests for overlapping keyword/regex matches, repeated originals, collision suffixes, unknown placeholders, Unicode, and right-to-left offset correctness (`src/engine.js:90-121`; `src/session.js:107-138`).
- Configuration tests for precedence, invalid JSON, invalid regex, zero/negative limits, and environment-relative paths (`src/config.js:57-86`).
- Deep traversal tests for cycles, arrays, plain objects, class instances, and nested tool args (`src/deep.js:18-44`, `55-81`).
- Leakage tests that assert plaintext is absent from every transformed historical tool state, including pending, error, and completed states (`src/index.js:82-113`).

There is also no declared `engines` constraint despite the README publishing a Node badge (`README.md:6`; `package.json:1-34`), so supported runtime versions are not enforced by metadata.

## Overall assessment

This is a focused, security-motivated plugin with a good lifecycle model: redact before provider submission, scrub historical tool records, restore only at the local execution boundary, and use per-session HMAC tokens rather than reversible provider-visible values. The strongest reusable patterns are explicit no-op defaults, deep cycle-safe traversal, overlap-aware right-to-left replacement, and bounded mapping state.

The main risks are lack of actual tests, uncaught invalid regexes, unbounded growth of the outer session map, in-place mutation assumptions, incomplete coverage for non-plain tool argument objects, and a streaming window where placeholders are visible. Those should be treated as review gates before relying on the plugin as a complete secret-leak prevention boundary.
