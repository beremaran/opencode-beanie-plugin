# Repository 110: `@spoons-and-mirrors/subtask2`

## Scope and identity

- Manifest index 110 resolves to `https://github.com/spoons-and-mirrors/subtask2`; the audited clone is `.research/opencode-plugin-corpus/repos/spoons-and-mirrors--subtask2` and has no separate `analysisPath` subdirectory (`repo-map.json:1672-1684`).
- The package describes itself as an OpenCode plugin for return context and prompt chaining and publishes version `0.3.5` (`package.json:3-8`).

## OpenCode patterns

- **Small exported factory, broad hook surface.** The entrypoint only re-exports `createPlugin` (`index.ts:1-13`). The factory initializes the manifest/config/client and registers command, task-tool, message-transform, config, and session-idle integration points (`src/core/plugin.ts:16-51`). This keeps OpenCode registration discoverable while isolating behavior in feature modules.
- **Use command hooks to rewrite execution inputs.** `command.execute.before` handles inline `/subtask`, applies model/agent overrides, starts loops, resolves `$TURN`, splits piped arguments, and registers parent-session mappings (`src/hooks/command-hooks.ts:34-95`, `src/hooks/command-hooks.ts:134-165`, `src/hooks/command-hooks.ts:192-260`). Replacing `output.parts` with a generated subtask part is a useful pattern for adding syntax without requiring users to create command files (`src/hooks/command-hooks.ts:88-94`).
- **Use task hooks for lifecycle correlation.** `tool.execute.before` identifies task sessions, maps child prompts to parent sessions, registers result capture, and resolves turn references (`src/hooks/tool-hooks.ts:43-97`, `src/hooks/tool-hooks.ts:141-171`). `tool.execute.after` correlates call IDs, captures only `output.state.output`, and defers loop/return handling until task completion (`src/hooks/tool-hooks.ts:178-239`, `src/hooks/tool-hooks.ts:265-309`). The deliberate choice not to scan all session messages avoids mixing results from concurrent subtasks (`src/hooks/tool-hooks.ts:216-228`).
- **Represent orchestration as explicit per-session state.** The implementation centralizes maps for return queues/stacks, pending prompts, child-parent relationships, model/agent overrides, and named results (`src/core/state.ts:9-68`). A return stack enables nested inline-subtask return chains (`src/core/state.ts:143-241`), while `executeReturn` dispatches slash-prefixed items as commands/subtasks and plain items as prompt messages (`src/features/returns.ts:71-81`, `src/features/returns.ts:183-271`).
- **Let the main model evaluate conditional loops.** Loop state tracks max iterations and deferred returns (`src/loop.ts:3-17`); only an explicit `<subtask2 loop="break"/>` terminates evaluation, so absent/continue output safely consumes the iteration budget (`src/loop.ts:25-33`). The README documents the resulting orchestrator-decides workflow and max-iteration safety net (`README.md:133-155`).
- **Flatten parallel work before handing it to OpenCode.** Nested parallel commands are expanded into subtask parts, with visited-command cycle detection and a depth cap of five (`src/features/parallel.ts:18-25`, `src/features/parallel.ts:68-75`, `src/features/parallel.ts:117-145`). Argument precedence is explicit: piped argument, frontmatter argument, then main arguments (`src/features/parallel.ts:81-86`).
- **Support both project and user command discovery.** The manifest scans `~/.config/opencode/command` and the project `.opencode/command`, recursively reading Markdown frontmatter and storing both basename and path keys (`src/commands/manifest.ts:14-57`). Resolution falls back across direct, basename, hyphenated, and slashed names (`src/commands/resolver.ts:7-27`).
- **Expose an ad-hoc command through the config hook.** The plugin adds `/subtask` with `$ARGUMENTS` and `subtask: true` at config time (`src/core/plugin.ts:37-45`), while README installation is a single plugin entry in OpenCode config (`README.md:19-25`).

## Security and operational pitfalls

- **Global mutable state has a documented leak risk.** State is held in module-level Maps/Sets, including many session-keyed structures (`src/core/state.ts:19-68`). The repository’s TODO explicitly says there is no cleanup on session end and warns that long-running OpenCode processes can leak memory (`TODO.md:5-21`). A production plugin should register an end/close cleanup path or use bounded TTL/LRU state.
- **Startup writes to the user’s global configuration.** If `~/.config/opencode/subtask2.jsonc` is absent or invalid, `loadConfig` writes a default file (`src/utils/config.ts:62-93`). This is surprising startup mutation and can fail in read-only environments; it should be opt-in or use a clearly reported fallback. The JSONC stripping is also regex-based (`src/utils/config.ts:67-75`), so it is not a general JSONC parser.
- **Logs may expose prompts and result content.** Logging serializes arbitrary objects and writes to `process.cwd()/.logs/subtask2.log` (`src/utils/logger.ts:4-5`, `src/utils/logger.ts:53-61`). Hook logs include prompt prefixes and model/agent details (`src/hooks/tool-hooks.ts:63-65`, `src/features/returns.ts:132-150`). Redaction, configurable levels, permissions, rotation, and an explicit opt-in are appropriate for sensitive repositories.
- **The plugin depends on an undocumented SDK escape hatch.** It stores the v1 client and directly PATCHes an internal HTTP client to make synthetic message parts visible (`src/core/plugin.ts:24-26`, `src/hooks/message-hooks.ts:36-45`, `src/hooks/message-hooks.ts:73-96`). This is version-fragile and should be isolated behind a compatibility adapter with capability/version checks; failures are currently logged and swallowed.
- **LLM-generated workflows are executable orchestration.** Experimental auto mode injects README instructions into a subtask, parses a generated `<subtask2 auto>` result, and recursively executes it (`src/features/auto.ts:9-15`, `src/features/auto.ts:24-52`, `src/features/returns.ts:39-69`). The feature is explicitly marked unsupported/POC (`src/features/auto.ts:9-15`), but deployments should treat generated commands, prompts, model choices, and loops as untrusted control input and require clear policy boundaries.
- **Prompt/result data is persisted and propagated across sessions.** `$TURN` and `$RESULT` intentionally move conversation and subtask output into later prompts (`README.md:240-287`, `README.md:290-334`). This is useful but creates confidentiality and prompt-injection surfaces; callers need scope, size, and sensitive-data controls.

## Testing lessons

- Unit tests are organized by parsing, hooks, loop, utilities, features, and state; the loop suite uses Bun’s test runner and covers signal variants, case-insensitivity, default continuation, state transitions, and max bounds (`test/loop.test.ts:1-13`, `test/loop.test.ts:15-61`, `test/loop.test.ts:63-188`). Representative feature-area suites include parsing, hook, utility, and state tests (`test/parsing/frontmatter.test.ts:1-5`, `test/hooks/session-idle-hook.test.ts:1-5`, `test/utils/prompts.test.ts:1-5`, `test/core/state.test.ts:1-5`).
- Hook tests verify inline model/agent/loop override application and consumption of pending overrides (`test/hooks/command-hooks.test.ts:12-85`). Result-capture tests specifically cover SDK message shape using `info.role: "assistant"` (`test/hooks/tool-hooks-results.test.ts:28-50`), documenting an important compatibility regression case.
- Configuration tests cover valid/invalid JSONC, type validation, defaults, and restoration of the user config file (`test/utils/config.test.ts:46-139`). This is good hygiene, but the tests mutate a real path under `$HOME` (`test/utils/config.test.ts:7-8`, `test/utils/config.test.ts:47-67`), which is unsafe under parallel test runs or an interrupted process.
- The repository’s own feature plan marks return chains, inline subtasks, loops, parallelism, named results, `$TURN`, piped arguments, auto mode, and integration scenarios as unchecked; it distinguishes existing parser unit tests from missing feature and E2E tests (`PLAN.md:7-21`, `PLAN.md:25-159`, `PLAN.md:173-179`). Claims in README therefore exceed verified automated coverage. Add mocked hook lifecycle tests and at least one real OpenCode smoke suite for concurrency, session-idle ordering, and SDK-version behavior.

## Packaging and release lessons

- Build output is declaration/source-map enabled TypeScript targeting ES2022 with strict checking and bundler resolution (`tsconfig.json:3-21`). `prepublishOnly` builds after cleaning `dist` (`package.json:9-12`), and the package exposes `dist/index.js` plus declarations (`package.json:7-8`).
- The published file allowlist is appropriately narrow: `dist/`, README, and LICENSE (`package.json:45-49`). `.npmignore` additionally excludes source, local OpenCode config, logs, media, and TypeScript files (`.npmignore:1-10`). This reduces accidental distribution of development artifacts, but excluding `src/` makes source-level debugging dependent on source maps and repository access.
- The plugin declares `@opencode-ai/plugin` as a peer dependency while depending on the SDK and YAML parser (`package.json:31-43`). The peer range is pinned to `^1.0.216` while dev tooling uses `^1.0.217` (`package.json:31-40`); because implementation relies on v1 internals, release CI should test the minimum peer and the current supported OpenCode version.
- The license is `PolyForm-Noncommercial-1.0.0` (`package.json:27`), and CONTRIBUTING requires automatic copyright/IP assignment with possible relicensing (`CONTRIBUTING.md:7-21`). This is a material contributor and downstream-adoption constraint that should be prominent in release documentation.

## Bottom line

Subtask2 demonstrates a practical OpenCode orchestration architecture: use lifecycle hooks for interception, explicit session correlation for asynchronous task results, and bounded flattening for concurrency. Its main risks are lifecycle state cleanup, side-effectful global configuration, sensitive verbose logging, undocumented SDK coupling, and a large gap between README feature claims and checked feature/E2E tests. Those risks should be addressed before treating the plugin as a stable automation substrate.
