## What it demonstrates

This is a focused OpenCode TUI plugin. Its entrypoint is the default export in `tui.tsx`, typed as `TuiPluginModule`; the module selects a development-only id and a package id based on whether it is running from `node_modules` (`tui.tsx:182-184`). The implementation is Solid/OpenTUI UI rather than an ordinary command/tool plugin.

### SDK imports and registration

- It imports `TuiPlugin` and `TuiPluginModule` from `@opencode-ai/plugin/tui` (`tui.tsx:3-6`), and `TuiThemeCurrent` from the same TUI surface (`ui.tsx:3`).
- The plugin is an async function receiving the TUI API (`tui.tsx:13`), then registers commands through `api.command.register(() => [...])` (`tui.tsx:20-162`). The callback is useful because command visibility and labels read current route/KV state when commands are enumerated.
- It registers a rendered extension point with `api.slots.register`, placing a `home_bottom` slot at order `100` (`tui.tsx:164-179`).
- It explicitly disables the built-in home tips with `api.plugins.deactivate("internal:home-tips")` (`tui.tsx:14`). This is a concrete pattern for replacing, rather than overlaying, a native UI feature.

### Lifecycle, events, and context mutation

There are no event hooks, message transforms, auth hooks, provider hooks, or lifecycle cleanup handlers. Initialization loads custom data once (`tui.tsx:16`), creates Solid signals (`tui.tsx:17`), and installs commands/slots. Runtime mutation is local reactive state (`customQuotes`, `selectedQuote`) plus OpenCode KV state (`tips_hidden`, `quote_source`) (`tui.tsx:17-18`, `tui.tsx:22-28`, `tui.tsx:38-50`). It does not mutate prompts, messages, sessions, or model context.

The view reads KV state and quote source through `createMemo` values on each slot render (`tui.tsx:168-175`) and passes the current theme from `api.theme.current` (`tui.tsx:176`). `ui.tsx` uses the theme, terminal dimensions, and a selected/random quote to render centered wrapped text (`ui.tsx:20-49`, `ui.tsx:54-71`).

### Commands and user interaction

The command palette exposes show/hide, source selection, add, remove, and explicit quote selection (`tui.tsx:20-162`). Commands are home-route-only through `hidden: api.route.current.name !== "home"` (`tui.tsx:26-27`, `tui.tsx:35-36`, `tui.tsx:58-60`, `tui.tsx:98-100`, `tui.tsx:142-144`). Dialogs use `DialogSelect` and `DialogPrompt`; invalid input and filesystem failures are surfaced with error toasts (`tui.tsx:61-90`, `tui.tsx:110-135`).

### Configuration and persistence

There is no user-facing JSON schema or plugin config object. The plugin uses OpenCode's supplied config path, `api.state.path.config`, and stores `quotes.json` there (`tui.tsx:16`, `utils.ts:17-20`, `utils.ts:44-47`, `utils.ts:77-80`). KV values provide lightweight settings with defaults: tips visible and source `both` (`tui.tsx:22`, `tui.tsx:38`, `tui.tsx:168-175`). The local development config loads the repository as a TUI plugin via `.opencode/tui.json:1-4`.

Input parsing requires the form `"quote" - author`, with non-empty trimmed fields (`utils.ts:7-15`). JSON loading filters entries by string `quote` and `author` fields (`utils.ts:22-31`, `utils.ts:80-94`), while source selection supports built-in, custom, or deduplicated combined quotes (`utils.ts:100-111`).

### Auth, providers, process boundaries, and concurrency

- Auth/provider wiring: none. The package declares no provider integration and makes no network calls.
- Process boundaries: none. It uses in-process Solid/OpenTUI rendering and Node `fs/promises` for local persistence (`utils.ts:1-2`).
- Concurrency: there is no lock, queue, transaction, or atomic rename. Add and remove both read then rewrite `quotes.json` (`utils.ts:17-41`, `utils.ts:44-64`), so concurrent OpenCode instances or overlapping commands can lose updates. The in-memory list is updated only after a successful write (`tui.tsx:75-85`, `tui.tsx:119-129`), which is a good local consistency rule but does not solve cross-process races.

## Strengths

- Minimal integration surface: typed TUI API, one entry module, one rendering slot, and explicit command registration (`tui.tsx:3-6`, `tui.tsx:20-179`).
- Good replacement behavior: deactivating `internal:home-tips` avoids duplicate home content (`tui.tsx:14`).
- Reactive rendering is cleanly separated from plugin orchestration: `View` owns layout while `tui.tsx` owns API/state wiring (`tui.tsx:11`, `ui.tsx:54-71`).
- User data is kept local to the OpenCode config directory, and malformed/missing files degrade to an empty list rather than crashing startup (`utils.ts:77-98`).
- UI adapts to terminal width and uses theme values instead of hard-coded colors (`ui.tsx:29-49`).
- Duplicate combined-source entries are removed deterministically, preserving the first occurrence (`utils.ts:66-75`).
- Packaging is explicit: ESM, exported `./tui` entry, included source files, OpenCode engine constraint, and peer dependencies for host-provided UI packages (`package.json:24-55`).
- Release automation publishes only on published releases, uses npm provenance, and grants narrowly scoped workflow permissions (`.github/workflows/publish.yml:3-15`, `.github/workflows/publish.yml:17-29`).

## Pitfalls and anti-patterns

- `saveCustomQuote` silently treats invalid JSON as an empty file and overwrites it, and all filesystem exceptions are collapsed to `false` (`utils.ts:21-41`). This preserves availability but can destroy recoverable user data and hides actionable diagnostics.
- Read-modify-write persistence is not atomic or concurrency-safe (`utils.ts:17-41`, `utils.ts:44-64`). Use a lock/serialized writer and temp-file-plus-rename for multi-session state.
- `quote_source` is cast rather than validated (`tui.tsx:38`, `tui.tsx:171`); corrupted KV data can produce behavior outside the declared `QuoteSource` union. Validate persisted settings at the boundary.
- The add path accepts arbitrarily long quote/author strings and appends duplicates (`utils.ts:7-15`, `utils.ts:36-37`). Add size limits, normalization, and duplicate checks if this pattern is reused for user-controlled persisted data.
- `removeCustomQuote` removes every matching duplicate, while the UI presents one selected item (`utils.ts:57-59`). That may be surprising if duplicate records are intentional.
- `wordWrap` assumes a positive usable width and space-delimited text (`utils.ts:116-164`). Very narrow terminals or long unbroken words can produce poor layout; callers should clamp width and test edge cases.
- The TypeScript project includes only `tui.tsx` and `quotes.ts` (`tsconfig.json:23`), despite `tui.tsx` importing `ui.tsx` and `utils.ts`. The declared typecheck therefore does not independently validate all shipped source files.
- There are no test files and no test script (only `typecheck`) (`package.json:37-39`; repository inspection found no `*test*` files). Parsing, persistence recovery, wrapping, command behavior, and rendering are unverified.
- The package uses broad wildcard peer dependencies (`package.json:43-47`) and a dev dependency pinned to a specific OpenTUI version (`package.json:50-54`), which can permit host-version incompatibilities without a compatibility matrix.
- The README documents installation and commands but not the `quotes.json` schema, config path semantics, supported OpenCode/TUI versions, or recovery behavior (`README.md:9-27`).

## Reusable development-bible lessons

1. For a TUI-only extension, use the TUI-specific SDK types and expose a single typed module entrypoint; keep host API wiring separate from UI components (`tui.tsx:3-13`, `ui.tsx:54-71`).
2. Replace native UI deliberately by deactivating the known internal plugin before registering a replacement slot (`tui.tsx:14`, `tui.tsx:164-179`).
3. Use OpenCode KV for small settings and `api.state.path.config` for durable user data, but define validation and migration rules for both (`tui.tsx:22-28`, `utils.ts:77-98`).
4. Register commands with route-aware visibility and use dialogs/toasts for a complete interaction loop (`tui.tsx:20-162`).
5. Treat local JSON persistence as a storage subsystem: validate records, preserve errors, serialize writes, and use atomic replacement when multiple sessions are possible.
6. Test every shipped source file, especially filesystem recovery and terminal-width edge cases; a narrow `tsconfig` is not a substitute for runtime tests (`tsconfig.json:23`, `package.json:37-39`).
7. Publish plugins with explicit exports, host engine/peer constraints, release-triggered automation, and provenance where supported (`package.json:24-60`, `.github/workflows/publish.yml:3-29`).
