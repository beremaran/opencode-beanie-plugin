## OpenCode Patterns

- **Plugin shape and registration.** The package exports a default `{ id, server }` plugin object, with `BobPlugin` implementing the OpenCode `Plugin` function (`src/index.ts:120-124`, `src/index.ts:454-459`). Its `hooks.config` mutates the host config to set subagent depth, upgrade native agents, apply prompts/models/permissions, and merge validated MCP entries (`src/index.ts:199-218`, `src/index.ts:332-374`). This is a useful pattern for plugins that need both runtime hooks and host-visible agent/MCP registration.
- **One initialization boundary.** Plugin startup loads config, initializes browser defaults, agents, hooks, memory, client adapters, background management, LSP, telemetry, and shell environment before returning hooks (`src/index.ts:120-195`). Disposal reverses long-lived resources and releases the logger/console guard (`src/index.ts:433-440`).
- **Composable hook pipeline.** Hook points are explicitly enumerated and multiple handlers are chained sequentially (`src/hooks/index.ts:46-58`, `src/hooks/index.ts:70-97`). Normal errors are converted to bounded DTOs, deduplicated, and capped, while `BlockingHookError` propagates immediately (`src/hooks/index.ts:98-125`; `src/hooks/errors.ts:10-15`, `src/hooks/errors.ts:36-84`). This cleanly separates recovery/observability hooks from safety-critical stops.
- **Agent specialization with deny-by-default task delegation.** Agent definitions distinguish primary, subagent, hidden, model, prompt, temperature, and thinking settings (`src/agents/index.ts:41-118`). Task permissions allow Bob to call Manager/workers, Manager to call workers, and leaf agents to call no workers (`src/permissions.ts:86-120`). The entrypoint applies these permissions to every registered agent (`src/index.ts:332-357`).
- **Completion as state machine, not prompt advice.** Writes/edits/patches record changed files, LSP calls clear the diagnostics-pending flag, and todo events update incomplete-work state (`src/features/completion-controller/index.ts:133-180`). Unknown actor types deliberately fall through without self-approval, preventing a closure payload from bypassing review (`src/features/completion-controller/index.ts:197-218`).

## Security Lessons and Pitfalls

- **External-directory access is broad by default.** Eight internal agents receive `external_directory: "allow"`; Bob and Vision are excluded (`src/permissions.ts:1-27`, `src/permissions.ts:122-137`). This supports cross-project inspection but is a material data-access boundary. Explicit `agent_restrictions.<agent>.external_directory=false` overrides it (`src/permissions.ts:146-162`). Consumers should audit this default rather than assuming all agents are project-root confined.
- **Read-only auto-allow must stay narrow.** The legal gate auto-allows only a fixed read-only tool set for external-directory permission requests (`src/hooks/legal-gate.ts:214-233`), while writes, edits, shell, web fetch, and deploy-like actions are routed through `permission.ask` (`src/hooks/legal-gate.ts:235-240`). Tests verify read tools allow and write/edit/bash remain `ask` (`src/hooks/index.test.ts:63-101`, `src/hooks/index.test.ts:179-235`).
- **Hard blocking plus contextual blocking is preferable to keyword-only filtering.** The gate blocks unambiguous military, ransomware, credential theft, C2, exfiltration, and non-consensual PII scraping, while dual-use terms require offensive intent (`src/hooks/legal-gate.ts:18-30`, `src/hooks/legal-gate.ts:160-212`). Tests cover both malicious denials and defensive SQL-injection/0-day/XSS/security-review passes (`src/hooks/legal-gate.test.ts:162-223`).
- **Tool ownership is enforced at execution time.** Browser tools accept only `vision` and `general`, rejecting unknown agents and other specialists (`src/tools/agent-browser/index.ts:11-25`). This is stronger than relying solely on agent prompt instructions or config restrictions; the corresponding tests exercise allowed and rejected agents (`src/tools/agent-browser/index.test.ts:75-99`).
- **Avoid shell-string execution for user-controlled tool arguments.** Browser commands are split into argv and passed to `Bun.spawn`, rather than concatenated into a shell command (`src/tools/agent-browser/index.ts:27-39`, `src/tools/agent-browser/index.ts:116-136`). The splitter has quote-preservation tests (`src/tools/agent-browser/index.test.ts:133-155`). This reduces shell injection exposure, though the custom splitter is not a complete shell parser and should remain limited to the intended CLI syntax.
- **Bound output and UI error surfaces.** Browser subprocess output is capped and drained, with timeout/kill handling (`src/tools/agent-browser/index.ts:71-114`, `src/tools/agent-browser/index.ts:120-163`). Completion reasons remove paths, stack frames, IDs, and tokens and cap length at 240 characters (`src/features/completion-controller/index.ts:20-72`). Hook errors discard stacks/raw payloads and retain at most 10 bounded entries (`src/hooks/errors.ts:20-40`, `src/hooks/errors.ts:43-84`).
- **Configuration secrets are intentionally out-of-band.** The README says provider credentials belong in OpenCode Connect, not `bob.json` (`README.md:208-239`), and env loading logs only key/source, never values (`src/config.ts:36-48`, `src/config.ts:105-123`). The repository guidance also warns against raw API keys, but the schema permits arbitrary string values in `auth` (`config/hiai-opencode.schema.json:19-21`), so schema validation alone is not a secret scanner.
- **Auto-export can write into the host workspace.** Startup best-effort exports static MCP config for host versions that only inspect files (`src/index.ts:199-205`). The documented controls include `if-missing`, `always`, and `off` (`README.md:134-141`). The export tests specifically verify refusal to overwrite non-managed files unless force mode is selected, an important packaging/integrity behavior (`src/features/mcp/auto-export.test.ts`, test name/output observed during `bun test`).

## Packaging and Configuration

- The package is explicitly ESM, publishes `dist/index.js` plus declarations, and exposes a CLI through `bin` (`package.json:1-15`). The `files` allowlist includes runtime output, skills, assets, config, operator docs, defaults, and the env template (`package.json:17-27`). This is a good defense against accidentally publishing the full source tree, but it makes build/package checks essential.
- Build and release gates are layered: bundle, declaration emission, bundle verification, typecheck, tests, lint/check, dry-run packing, and a `prepublishOnly` chain (`package.json:72-88`). The package requires Node 20+ and Bun 1.3+ (`package.json:125-128`); the README consistently documents Bun installation/runtime (`README.md:7-9`, `README.md:61-65`).
- The minimal host config is intentionally only the plugin registration (`config/opencode.json:1-4`), while the separate JSON Schema is strict at the top level (`config/hiai-opencode.schema.json:1-6`). The schema still has deliberately loose areas such as `caveman` and `loop` (`config/hiai-opencode.schema.json:23-30`), which is convenient for evolution but weakens typo/contract detection there.
- TypeScript uses strict mode, bundler resolution, declaration output, and excludes test files from the declaration build (`tsconfig.json:1-20`). This is a sensible plugin packaging baseline, but runtime dependencies must be installed before tests that import memory/tool registries can execute.

## Recommendations for OpenCode Plugin Authors

1. Keep the plugin export minimal and put host mutation in `hooks.config`; initialize external clients/resources once and provide an explicit `dispose` path.
2. Chain hooks through a common wrapper that distinguishes blocking safety errors from bounded, serializable diagnostics.
3. Enforce sensitive tool ownership in the tool executor, not only in prompts or agent config.
4. Treat external-directory permission defaults as a security decision and test both default access and explicit denial.
5. Test host-facing contracts, negative/error paths, config precedence, packaging allowlists, and subprocess timeouts.
6. Run tests from a dependency-complete checkout and report missing dependencies separately from behavioral failures; do not “fix” a corpus clone during analysis.
