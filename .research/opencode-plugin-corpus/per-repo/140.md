## Executive summary

Conductor is a TypeScript OpenCode plugin that turns project-management prompts into a context-driven workflow: setup, track specification/plan, implementation, status, review, and revert. The README describes the intended lifecycle as Context -> Spec -> Plan -> Implement and advertises native slash commands, a dedicated `@conductor` agent, permissions, Git-aware revert, and first-run bootstrap (`README.md:5-21`, `README.md:25-41`).

The strongest reusable pattern is to keep large workflow instructions in versioned prompt assets, then compose a small amount of runtime environment context into command templates. The active entrypoint recursively snapshots only `.json` and `.md` files beneath the project `conductor/` directory and injects their paths/content into selected command prompts (`src/index.ts:18-56`, `src/index.ts:67-125`). The command factory offers a second, tool-oriented version of the same idea: load JSON/TOML directives, substitute named values, and return a stable JSON envelope `{ directives: ... }` (`src/utils/commandFactory.ts:18-84`, `src/utils/commandFactory.ts:87-109`).

The important caveat is that the repository contains more capability than the active entrypoint exposes. `src/index.ts` returns only a `config` hook that adds six commands (`src/index.ts:66-127`), while delegation, background-task, bootstrap, and state-manager modules are exported but have no import/use path from the entrypoint (`src/tools/delegate.ts:4-52`, `src/tools/background.ts:45-266`, `src/utils/bootstrap.ts:9-52`, `src/utils/stateManager.ts:8-38`). This makes source-level claims about delegation and zero-config bootstrap conditional on another integration path that is not present in this snapshot.

## OpenCode patterns worth reusing

### 1. Runtime context injection into commands

The plugin receives standard plugin inputs including `project`, `client`, shell `$`, `directory`, and `worktree` (`src/index.ts:11-17`). It computes project-local Conductor state once during plugin initialization, including a setup marker at `conductor/setup_state.json` (`src/index.ts:58-64`). Commands then receive directory, setup status, and a relative file tree in their templates (`src/index.ts:67-125`). This is a practical way to make a slash command aware of the current project without requiring every prompt to rediscover basic context.

The setup prompt also explicitly tells the model to use `.opencodeignore` or `.gitignore` rather than Gemini-specific files (`src/index.ts:100-110`). That is a useful migration pattern when adapting a workflow from another agent ecosystem: put the host-environment override directly beside the injected context.

### 2. Prompt assets as a stable command protocol

Commands are represented as checked-in JSON prompt assets, imported by the entrypoint (`src/index.ts:4-9`). The command factory supports both converted JSON and legacy TOML, trying the legacy path first and then the generated JSON path (`src/utils/commandFactory.ts:23-28`, `src/utils/commandFactory.ts:32-40`). It extracts a prompt and description, applies replacement variables, and returns `JSON.stringify({ directives: prompt })` (`src/utils/commandFactory.ts:50-77`, `src/utils/commandFactory.ts:102-105`).

This separation keeps TypeScript glue small and makes workflow changes reviewable as prompt-only changes. It also provides a stable tool result shape for callers. The tests specifically assert the envelope and substitutions (`src/tools/commands.test.ts:51-59`, `src/tools/commands.test.ts:75-83`, `src/tools/commands.test.ts:99-122`).

### 3. Explicit tool schemas and narrow arguments

The command tools use `tool.schema.string().optional()` with descriptions for user-facing values such as track name, target, and description (`src/tools/commands.ts:16-26`, `src/tools/commands.ts:29-52`, `src/tools/commands.ts:61-84`). This gives the model a typed interface while keeping the actual workflow in prompt assets. The delegation tool similarly requires a task summary, target agent, and detailed prompt (`src/tools/delegate.ts:5-11`).

### 4. Session-based delegation

The delegation implementation creates a child session linked by `parentID`, sends the requested agent a prompt, disables recursive `conductor_delegate`, then reads the latest assistant text and returns the child session ID as metadata (`src/tools/delegate.ts:13-49`). Disabling the same delegation tool in the child is a concrete loop-prevention measure. The background implementation applies the same idea to asynchronous work and disables both background and delegation tools in child sessions (`src/tools/background.ts:60-100`).

### 5. Protocol-first agent behavior

The `@conductor` agent treats `conductor/` as the source of truth, requires an approved spec and plan before implementation, and includes a universal index/link/path resolution protocol (`src/prompts/agent/conductor.md:17-52`, `src/prompts/agent/conductor.md:54-67`). This is stronger than a generic "read the README" instruction because it defines deterministic resolution and requires existence verification (`src/prompts/agent/conductor.md:32-40`).

## Pitfalls and correctness risks

### Entrypoint wiring and documentation drift

The active plugin entrypoint exports `MyPlugin`, but it does not import or register `src/tools/commands.ts`, `src/tools/delegate.ts`, `src/tools/background.ts`, `src/utils/bootstrap.ts`, or `src/utils/stateManager.ts` (`src/index.ts:1-17`, `src/index.ts:66-127`). Consequently, the documented native commands are added through the `config.command` hook, but the separately implemented `conductor_*` tools and bootstrap function are not reachable from this entrypoint. The README claims automatic global installation and modern permissions (`README.md:13-20`), while the only visible active code does not perform either operation. Treat this as a release-gating integration test gap, not merely dead-code cleanup.

There is also naming drift: the README documents `/conductor:setup`, `/conductor:newTrack`, and `/conductor:implement` (`README.md:93-101`), whereas `INSTALL.md` later advertises `/c-setup`, `/c-new`, and `/c-implement` (`INSTALL.md:110-117`). The source entrypoint registers the `conductor:` names (`src/index.ts:68-125`). Installation documentation should be generated or tested against the actual registered names.

### Unbounded project-context ingestion

The entrypoint recursively traverses `conductor/`, follows directories with synchronous `statSync`, reads every `.json` and `.md` file in full, and concatenates all contents into one prompt (`src/index.ts:24-55`). There is no size cap, file-count cap, symlink policy, malformed-file handling, redaction, or explicit exclusion of secrets stored under that directory. A project-controlled markdown file can therefore inflate context or inject instructions. A production implementation should bound total bytes, reject or normalize symlinks, preserve deterministic ordering, and clearly separate untrusted project content from system directives.

### Global bootstrap overwrites user files

The bootstrap utility creates `~/.config/opencode/agent` and `command`, then unconditionally copies the packaged agent and every command over same-named files (`src/utils/bootstrap.ts:10-38`). The npm `postinstall` script independently performs the same unconditional copies (`scripts/postinstall.cjs:5-35`). This creates two installation paths with overwrite behavior and no backup, ownership marker, version check, or opt-out. It also writes into a global user configuration directory during package installation, which is a high-impact side effect for a plugin. If retained, it should be explicit, idempotent, collision-safe, and covered by tests using a temporary home/config root.

The postinstall script catches and logs setup failures without failing installation (`scripts/postinstall.cjs:20-38`). That improves install resilience but can leave a silently incomplete plugin; the runtime should expose a clear health/status signal rather than relying on console output.

### Background task lifecycle weaknesses

Background IDs are generated with `Math.random()` and held only in an in-memory `Map` (`src/tools/background.ts:45-47`, `src/tools/background.ts:73-90`). Tasks disappear on process restart, IDs are not cryptographically strong, and there is no persistence or collision check. Polling marks a task complete solely when the session status becomes `idle` (`src/tools/background.ts:130-155`), without checking whether the session ended in an error or whether a result message exists. The blocking output loop breaks only for `completed`, so failed/cancelled tasks wait until timeout (`src/tools/background.ts:225-232`). These semantics should be made explicit and tested for completion, failure, cancellation, timeout, and restart.

The cancellation path sends a user-visible prompt to the parent session but does not cancel or stop the child session itself (`src/tools/background.ts:111-127`). This can report cancellation while work continues. A true cancellation API, or at least a child-session cancellation attempt followed by state reconciliation, is needed.

### Error handling can turn failures into model-visible directives

Prompt-loading failures return a string beginning `SYSTEM ERROR` inside the normal JSON directives envelope (`src/utils/commandFactory.ts:42-47`, `src/utils/commandFactory.ts:78-83`). This is testable and avoids throwing, but it delegates a system failure to the model as if it were workflow content. Callers may continue with a broken directive. Prefer a typed error result or an explicit failed tool call when prompt assets are missing or malformed.

### Legacy path and generated-asset coupling

The build first converts legacy TOML files into `src/prompts/conductor/*.json`, then compiles and copies prompt/template assets into `dist` (`package.json:31-37`, `scripts/convert-legacy.cjs:5-25`). Because conversion writes into `src`, a build mutates the source tree and can create generated files not represented by the repository's normal source intent. The command factory also has a legacy-first resolution order (`src/utils/commandFactory.ts:23-28`), making stale legacy assets capable of taking precedence over current JSON assets. Pick one canonical source format or add a consistency check that compares generated output with checked-in assets.

## Security and trust boundaries

- The plugin reads project-controlled files and inserts them into LLM prompts (`src/index.ts:42-55`). Treat all `conductor/` content as untrusted data; do not present it as higher-priority instructions, and cap/validate content before injection.
- The plugin writes to a global OpenCode configuration directory during install/bootstrap (`scripts/postinstall.cjs:5-35`, `src/utils/bootstrap.ts:9-38`). This is a privileged filesystem boundary and should use explicit consent, restrictive file selection, and collision checks.
- Delegation accepts an arbitrary `subagent_type` and prompt from tool arguments and passes them to `client.session.prompt` (`src/tools/delegate.ts:8-10`, `src/tools/delegate.ts:24-33`). An allowlist or policy check is appropriate if the host exposes agents with materially different permissions.
- The agent front matter grants Conductor tools with `allow` (`src/prompts/agent/conductor.md:1-10`), but the active entrypoint does not register those tool names. Permission declarations and registration must be validated together to avoid false assurance.
- The repository's workflow prompt explicitly requires no hardcoded secrets and verification before completion (`src/templates/workflow.md:214-219`, `src/templates/workflow.md:141-146`), but these are model instructions rather than enforceable runtime controls.

## Testing lessons

The repository uses Vitest with Node environment, colocated `src/**/*.test.ts` discovery, and V8 text/JSON/HTML coverage configuration (`vitest.config.ts:1-19`). The existing suite is focused and useful for the command factory: it covers tool descriptions, optional arguments, replacement values, strategy selection, prompt-load errors, and standard template substitution (`src/tools/commands.test.ts:43-185`).

Coverage gaps are substantial relative to the advertised behavior:

- No tests cover `src/index.ts` command registration, setup-state detection, directory traversal, file filtering, ordering, or prompt-size behavior.
- No tests cover bootstrap or postinstall writes, overwrite behavior, missing asset directories, or toast failures (`src/utils/bootstrap.ts:20-51`, `scripts/postinstall.cjs:14-38`).
- No tests cover delegation child-session creation, recursive-tool disabling, missing responses, or API errors (`src/tools/delegate.ts:13-49`).
- No tests cover background polling, failed sessions, cancellation, timeout, parent notification, or multiple concurrent tasks (`src/tools/background.ts:111-187`, `src/tools/background.ts:221-251`).
- The documented `npm run test:watch` and `npm run test:coverage` commands are not defined in `package.json`, which only defines `test` (`README.test.md:13-31`, `package.json:31-38`).

The project workflow template advocates Red/Green/Refactor, running tests and coverage, and a target above 80% for new code (`src/templates/workflow.md:23-39`). That is a good project-level convention, but CI does not visibly run tests or coverage before release; the publish workflow installs, builds, and invokes semantic-release (`.github/workflows/publish.yml:24-42`). Add a test/typecheck gate before publishing and test the actual exported plugin surface.

## Packaging and release lessons

The package is an ES module with `dist/index.js` as its main entry and declarations at `dist/index.d.ts`; the published allowlist includes `dist`, `scripts`, and `legacy` (`package.json:1-5`, `package.json:20-30`). The build uses strict TypeScript, NodeNext resolution, declarations, and JSON module support (`tsconfig.json:1-15`). This is a solid baseline for a typed OpenCode plugin.

The package pins `@opencode-ai/plugin` exactly at `1.0.223` and publishes publicly to npm (`package.json:20-23`, `package.json:39-42`). The release workflow uses Node 20, recursive submodules, npm install, a build, and semantic-release with npm/GitHub credentials (`.github/workflows/publish.yml:18-42`). The workflow's explicit `id-token: write` permission is compatible with modern trusted publishing, but it still writes an npm auth token to `.npmrc` in the runner (`.github/workflows/publish.yml:12-16`, `.github/workflows/publish.yml:36-42`); limit its lifetime and ensure artifacts/logs cannot expose it.

The separate release-asset workflow archives the whole checkout except `.git` and `.github` (`.github/workflows/package-and-upload-assets.yml:23-40`). Because the archive is broad, review whether development-only files, historical assets, or generated content should be included. The package's `files` allowlist is safer for npm distribution than this tarball strategy.

The changelog records a recent migration from a submodule to a regular folder and a legacy-to-regular-folder conversion for OpenCode compatibility (`CHANGELOG.md:1-15`). That history explains the dual asset layouts and reinforces the need for a single-source build check during future migrations.

## Recommended takeaways for OpenCode plugin authors

1. Keep workflow policy in reviewable prompt assets, but keep runtime registration in one clearly tested entrypoint.
2. Inject only bounded, deterministic, project context; treat repository files as untrusted prompt data.
3. Make global bootstrap opt-in or collision-safe, and test it against a temporary configuration directory.
4. Disable recursive tools in child sessions and constrain delegated agent names.
5. Model background work as a real state machine with failure/cancellation semantics and persistence requirements.
6. Test the exported plugin registration, not only helper functions, and make documented test commands match `package.json`.
7. Gate release on tests and typecheck, and keep npm/package archives limited to intentional runtime assets.
