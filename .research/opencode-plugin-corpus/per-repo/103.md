## What It Demonstrates

`opencode-semantic-anchors` is a runtime steering plugin that checks chat messages and tool execution, and exposes three control tools (`README.md:13-31`, `README.md:94-110`). Its entrypoint follows a useful small-plugin composition: read `options.configPath`, load configuration, construct one rule engine, inject a logger, then return `tool.execute.before`, `chat.message`, and named tools (`src/index.ts:10-31`). The package targets the OpenCode plugin API through `@opencode-ai/plugin` and publishes ESM plus declarations (`package.json:5-16`, `package.json:45-56`).

Notable reusable patterns:

- Keep the OpenCode adapter thin. Hook factories translate hook input into domain events; the engine returns a `{ allow, contract, message }` verdict (`src/hooks/toolExecute.ts:8-29`, `src/hooks/chatMessage.ts:4-34`, `src/rules/engine.ts:5-23`).
- Make configuration declarative but validate it at the boundary. YAML is parsed and passed through a Zod schema before profile and contract resolution (`src/config/loader.ts:43-57`, `src/config/schema.ts:3-29`).
- Separate built-in profile resolution from user contracts. User IDs override profile IDs, while role-specific profile selection has explicit precedence (`src/config/loader.ts:62-83`, `src/config/loader.ts:109-127`, `src/rules/presets.ts:74-101`).
- Use focused custom tools for operational visibility and control: status reports role/counters/contracts, reload applies new configuration, and bypass grants an override (`src/tools/status.ts:4-25`, `src/tools/configReload.ts:5-13`, `src/tools/bypass.ts:4-12`).
- Build tests around layers and one real pipeline. The repository has matcher, engine, loader, hook, tool, and integration tests; the integration suite explicitly exercises YAML -> engine -> hook -> tool (`src/__tests__/integration.test.ts:1-17`, `vitest.config.ts:1-9`).
- Strict TypeScript settings (`strict`, no unused symbols/parameters, unchecked indexed access, declarations and source maps) provide a good packaging baseline (`tsconfig.json:2-22`).

## Findings and Pitfalls

### High: bypass limits are advertised but not enforced

The schema and README present `maxOverrides` as a limit, including a default and per-contract wording (`src/config/schema.ts:10-17`, `README.md:24-31`, `README.md:108-110`). In implementation, `incrementOverride()` unconditionally increments a single global counter (`src/rules/engine.ts:154-157`), and the bypass tool always grants it (`src/tools/bypass.ts:8-10`). Evaluation consumes that counter but never compares it with either `state.maxOverrides` or the matched contract's `maxOverrides` (`src/rules/engine.ts:117-125`). A caller can therefore issue unlimited bypasses, and one contract's bypasses are usable against another. The existing bypass test checks only that the counter increments (`src/tools/__tests__/bypass.test.ts:5-27`), so it would not catch this.

### High: state is not keyed by OpenCode session

`SessionState` is one mutable object inside one `RuleEngine` (`src/rules/engine.ts:25-51`). Both hooks receive `sessionID` but discard it (`src/hooks/toolExecute.ts:9-17`, `src/hooks/chatMessage.ts:5-20`). If the plugin instance serves multiple sessions, tool-call counts, roles, and override credits can bleed between sessions. This is especially important for a security/approval plugin because the README describes the override as session-scoped (`README.md:27`, `README.md:108-110`). Tests exercise only one session ID at a time (`src/hooks/__tests__/toolExecute.test.ts:31-33`, `src/hooks/__tests__/chatMessage.test.ts:31-35`).

### Medium: reload changes contract-priority semantics

The constructor deliberately orders BLOCK contracts before WARN contracts (`src/rules/engine.ts:53-61`). `loadConfig()` replaces the array without applying that ordering (`src/rules/engine.ts:159-163`). Since matching returns the first matching trigger (`src/rules/matcher.ts:3-27`) and the engine finds the contract owning that trigger (`src/rules/engine.ts:78-105`), a reload can make an earlier WARN contract win over a later BLOCK contract. The reload test verifies that reload is called and installed, but not that priority is preserved (`src/tools/__tests__/configReload.test.ts:7-49`).

### Medium: fail-open behavior silently disables enforcement

Malformed/missing configuration returns defaults, and all loader exceptions are swallowed (`src/config/loader.ts:43-57`, `src/config/loader.ts:97-101`). Hook evaluation exceptions also return without logging or blocking (`src/hooks/toolExecute.ts:15-20`, `src/hooks/chatMessage.ts:15-25`). Fail-open may preserve agent availability, but for a plugin whose purpose is to block dangerous operations it creates an invisible security failure. The tests explicitly encode this behavior (`src/hooks/__tests__/toolExecute.test.ts:67-87`, `src/hooks/__tests__/chatMessage.test.ts:76-97`); production deployments should at least emit an error and make fail-open/fail-closed a documented policy choice.

### Medium: configuration contracts do not constrain numeric values

`maxOverrides`, `count`, and `stepConfirmationInterval` are numeric but have no non-negative or positive bounds (`src/config/schema.ts:3-29`). A negative interval bypasses the intended `> 0` check and disables confirmation; negative override settings produce confusing status and policy behavior. Schema-level bounds would make invalid policy explicit before runtime.

### Low: adapter input is narrower than the API shape

The tool hook receives `_output.args`, but only `input.tool` is sent to the engine (`src/hooks/toolExecute.ts:9-17`). Consequently, contracts cannot inspect arguments despite the event type allowing `args` (`src/rules/engine.ts:12-16`). This is acceptable for name-only rules, but should be explicit because dangerous-operation policy often depends on target paths, destinations, or command arguments.

## Security Lessons

- Provide a private vulnerability-reporting path and define supported versions; this repository does both, including a 48-hour acknowledgement target (`SECURITY.md:3-21`).
- Treat configuration parsing, hook execution, and user-controlled contracts as separate trust boundaries; the security policy lists the first two in scope but excludes user-defined contract configurations (`SECURITY.md:23-35`). That exclusion should be reconciled with the fact that YAML directly controls BLOCK/WARN policy (`src/config/schema.ts:10-17`).
- Do not rely on a bypass reason as authorization. The tool accepts any string and grants credit without checking actor, contract ID, or a cap (`src/tools/bypass.ts:4-10`).
- Avoid returning sensitive policy details by default if status output is exposed to untrusted model context; status reveals all active descriptions and trigger patterns (`src/tools/status.ts:9-24`).

## Testing and Packaging Lessons

The test organization is strong in intent: unit tests cover matching and engine semantics, loader tests cover invalid YAML/schema and profile precedence, hook tests cover BLOCK/WARN/ALLOW and fail-open behavior, and integration tests exercise the complete path (`src/rules/__tests__/engine.test.ts:33-96`, `src/config/__tests__/loader.test.ts:45-82`, `src/hooks/__tests__/toolExecute.test.ts:15-87`, `src/__tests__/integration.test.ts:19-220`). Missing regression cases include per-session isolation, max override exhaustion through the public bypass tool, contract-specific limits, reload ordering, invalid numeric settings, and argument-sensitive rules.

Observed verification from the audited checkout:

- `bun test`: 81 tests ran, 65 passed and 16 failed. Failures were concentrated in integration/config loading and role-profile tests; the loader fell back to defaults in those runs.
- `bun run typecheck`: failed because Vitest and js-yaml declarations were unavailable and also reported Zod/type errors in `src/config/schema.ts` and `src/config/loader.ts`.
- `bun run build`: failed because `tsup` was unavailable in the checkout environment.

Packaging is intentionally minimal: only `dist` is included in the npm package, with ESM, declarations, and an export map (`package.json:9-20`, `package.json:15-16`). This keeps runtime artifacts small, but excludes README, SECURITY.md, and the example YAML from the published package. The build/test/typecheck/SBOM scripts are clearly named (`package.json:18-26`), and an SBOM is checked in (`sbom.json`), which is a useful supply-chain practice. Documentation is separately published through a GitHub Pages workflow with least-privilege contents read plus Pages and OIDC permissions (`.github/workflows/deploy-docs.yml:10-16`).

## Bottom Line

The repository is a good reference for a thin OpenCode hook adapter, declarative validated configuration, role/profile resolution, operational tools, and layered tests. Before treating it as a security control, fix or explicitly bound bypass accounting, isolate state by `sessionID`, preserve BLOCK precedence on reload, and make fail-open events observable. The current checkout also needs dependency/install and integration-test investigation before its CI claims can be considered reliable.
