## What it is

Pilot is a community automation daemon that polls GitHub, Linear, or generic MCP/CLI sources, evaluates readiness, and starts OpenCode sessions. The README explicitly separates it from the OpenCode team and describes polling, readiness, templates, and presets as the primary features (`README.md:1-12`). The shipped OpenCode plugin is a bootstrapper rather than the polling implementation: it reads the pilot port, checks `GET /health`, and starts or restarts the daemon (`plugin/index.js:14-33`, `plugin/index.js:65-101`).

## OpenCode integration patterns

### Thin plugin, external daemon

The plugin returns an empty hooks object and performs its work during initialization (`plugin/index.js:69-101`). It launches `npx opencode-pilot start` detached with ignored stdio, and stops it synchronously with a ten-second timeout (`plugin/index.js:36-63`). This is a useful pattern when polling/state management should not live in the OpenCode process, but it also makes daemon discovery and process lifecycle part of the plugin’s reliability/security surface.

### HTTP API over shelling out to OpenCode

Session creation uses `POST /session?directory=...`, then sends either a slash command to `/session/:id/command` or a normal prompt to `/session/:id/message` (`service/actions.js:820-921`). The code documents and integration-tests the important worktree invariant: the working directory is supplied at session creation, and the resulting session retains the sandbox directory while resolving the parent project ID (`service/actions.js:800-808`; `test/integration/real-server.test.js:113-170`).

The implementation also uses a response-header timeout and aborts the streaming body after acceptance (`service/actions.js:872-945`). This is a strong pattern for long-running OpenCode requests: distinguish “server accepted the request” from “the streamed agent response is complete.” If session creation succeeded but message delivery failed, it returns success with a warning to avoid reprocessing the item (`service/actions.js:953-969`), which is operationally pragmatic but should be surfaced clearly to operators.

### Worktree isolation and reuse

Worktrees are managed through OpenCode’s experimental API, using encoded `directory` query parameters for list/create operations (`service/worktree.js:19-39`, `service/worktree.js:57-99`). Named worktrees are reused when configured; missing names fall back to the base directory with an error (`service/worktree.js:223-277`). `SessionContext` keeps both project and working directories and treats unequal paths as worktree sessions (`service/session-context.js:41-68`). Worktree sessions deliberately skip ordinary session reuse to prevent cross-PR contamination (`service/actions.js:973-985`, `service/actions.js:1032-1038`).

### Configuration-aware model selection

Pilot reads `.opencode/opencode.json` and `.jsonc` from the target directory, preferring an agent-specific model over the global model (`service/actions.js:51-103`). It supports provider/model strings and converts them to the nested message payload expected by the API (`service/actions.js:32-41`, `service/actions.js:704-713`). Configuration normalization tracks explicitly supplied source fields so the effective precedence is source, repository, then defaults (`service/repo-config.js:219-248`; `service/poll-service.js:34-71`).

### Generic source normalization

The poller supports MCP transports (stdio, streamable HTTP, and SSE), environment-variable expansion for remote headers, and CLI commands (`service/poller.js:165-195`, `service/poller.js:235-273`). Source fields can be mapped by dotted paths or regex extraction while preserving original fields (`service/poller.js:32-65`). The polling loop enriches items for comments, mergeability, and stacked-PR branch references, then evaluates readiness, deduplicates, and records processed metadata (`service/poll-service.js:142-180`, `service/poll-service.js:183-235`, `service/poll-service.js:253-320`).

## Security and reliability pitfalls

- The daemon health server binds an HTTP endpoint and enables `Access-Control-Allow-Origin: *` for preflight requests (`service/server.js:44-70`). The endpoint is intentionally health-only, but the default unauthenticated localhost service and permissive CORS should be treated as a local trust boundary, especially if binding behavior changes or a browser can reach other local services.
- The plugin starts `npx opencode-pilot` rather than resolving the installed package executable directly (`plugin/index.js:39-46`). This can invoke npm resolution/network behavior and a different package version than the plugin that initiated it. Version checking helps detect mismatch, but it happens only after contacting the daemon (`plugin/index.js:73-91`).
- CLI sources ultimately use `child_process.exec` with a constructed shell command (`service/poller.js:242-273`). Array arguments receive partial quoting, but string commands interpolate configuration values directly (`service/poller.js:248-265`). Treat config and item-derived substitutions as trusted, or prefer `spawn`/`execFile` with argument arrays and explicit environment allowlists.
- Remote MCP headers expand `${NAME}` from the process environment (`service/poller.js:167-173`). This is convenient for tokens, but configuration and debug/error paths must not expose expanded secrets. The reviewed code does not show an explicit redaction layer.
- Repository discovery executes `git remote get-url` against every child directory under `repos_dir` (`service/repo-config.js:64-118`). This is useful for fork/upstream matching, but broad directory scanning and subprocess execution should be constrained when `repos_dir` is user-controlled or shared.
- Worktree resolution falls back to the base directory if a named worktree is missing (`service/worktree.js:263-277`). The error is returned, but callers must ensure that fallback is not silently accepted for jobs requiring isolation.

## Testing lessons

The project uses Node’s built-in `node:test` runner and `node:assert`; unit tests cover configuration, polling, readiness, actions, server behavior, and worktree URL/body construction (`CONTRIBUTING.md:18-40`; `test/unit/worktree.test.js:10-132`). Tests inject a custom `fetch` function, which makes HTTP API behavior deterministic and verifies encoded directory parameters (`test/unit/worktree.test.js:25-59`, `test/unit/worktree.test.js:101-132`). State tracking is tested with temporary directories and persistence across poller instances (`test/unit/poller.test.js:15-22`, `test/unit/poller.test.js:114-169`).

There is also a real-server integration suite that skips when OpenCode is unavailable and archives sessions after execution (`test/integration/real-server.test.js:1-19`, `test/integration/real-server.test.js:92-107`). This is valuable evidence for undocumented API behavior, particularly worktree/project identity, but it is environment-dependent. CI runs syntax checks and unit tests only; its own comment says the older Bash integration tests were removed pending conversion (`.github/workflows/ci.yml:30-41`).

## Packaging and release lessons

`package.json` exposes both the plugin entry (`main: plugin/index.js`) and the `opencode-pilot` executable, declares ESM, publishes publicly with npm provenance, and keeps runtime dependencies small (`package.json:1-13`, `package.json:24-40`). The package lock is committed, while CI currently runs `npm install` (`package.json:27-40`; `.github/workflows/ci.yml:27-29`). For reproducibility and supply-chain discipline, `npm ci` would better match the committed lockfile.

Releases use semantic-release on pushes to `main`, publishing npm provenance and GitHub releases without a version-bump commit (`.releaserc.cjs:1-33`; `.github/workflows/ci.yml:43-81`). The repository’s `AGENTS.md` explicitly says the committed package version is a stale placeholder and that npm plus git tags are the sources of truth (`AGENTS.md:3-8`), while `CONTRIBUTING.md` still says CI commits version bumps back to the repo (`CONTRIBUTING.md:83-93`). That documentation contradiction is a packaging/process pitfall: contributor guidance should match the active release policy.

The CLI accounts for both development and Homebrew layouts by searching `bin/../service` and `bin/../libexec` (`bin/opencode-pilot:25-39`). The README documents Homebrew and npm installation, config locations, CLI commands, source syntax, model precedence, session reuse, and worktree options (`README.md:14-17`, `README.md:35-71`, `README.md:82-141`, `README.md:155-176`). This is a good lesson for plugins with a daemon or service component: document the install topology, persistent config/state paths, lifecycle commands, and behavior when resources are reused.

## Reusable takeaways

1. Keep the OpenCode plugin entrypoint thin when the feature is a long-lived poller; make health/version checks explicit and testable.
2. Prefer OpenCode HTTP APIs with injected fetch clients over shell commands for session and worktree operations.
3. Preserve separate project and working directories, and disable session reuse when worktree identity is the isolation boundary.
4. Add real-server tests for API semantics that mocks cannot establish, while keeping CI’s default suite deterministic.
5. Treat generic CLI/MCP configuration as code execution and secret-handling input; use argument-safe process APIs, redaction, timeouts, and explicit trust boundaries.
6. Keep README, contributor instructions, release configuration, and package metadata consistent, especially when using ephemeral semantic-release versions.
