## OpenCode Integration Patterns

- The public entrypoint exports `LiteLLMPlugin`, `LiteLLMResponsesPlugin`, and the API types ([src/index.ts:1-2](../repos/yuseferi--opencode-litellm/src/index.ts)). The active plugin implements OpenCode's `config` lifecycle hook and mutates `config.provider` in place ([src/plugin/index.ts:178-212](../repos/yuseferi--opencode-litellm/src/plugin/index.ts)). The source explicitly records the compatibility lesson that the provider-model hook was not called for custom providers ([src/plugin/index.ts:154-160](../repos/yuseferi--opencode-litellm/src/plugin/index.ts)); the changelog documents the earlier hook reversal and why it was a breaking behavior change ([CHANGELOG.md:106-120](../repos/yuseferi--opencode-litellm/CHANGELOG.md)).
- Provider discovery is intentionally flexible: the plugin recognizes `litellm`, IDs beginning with `litellm-`/`litellm_`, and explicit compatibility flags in provider options ([src/plugin/index.ts:29-43](../repos/yuseferi--opencode-litellm/src/plugin/index.ts)). If no matching provider exists, it creates a default OpenAI-compatible `litellm` provider and then auto-detects localhost ports 4000, 8000, and 8080 ([src/plugin/index.ts:198-212](../repos/yuseferi--opencode-litellm/src/plugin/index.ts); [src/utils/litellm-api.ts:164-177](../repos/yuseferi--opencode-litellm/src/utils/litellm-api.ts)).
- Discovery separates a fast health check from the larger model fetch: health is capped at 3 seconds, each discovery request at 15 seconds, and the config work is raced against a 20-second lifecycle cap ([src/utils/litellm-api.ts:3-11](../repos/yuseferi--opencode-litellm/src/utils/litellm-api.ts); [src/plugin/index.ts:15-18,269-379](../repos/yuseferi--opencode-litellm/src/plugin/index.ts)). This is a useful non-blocking startup pattern, and the repository's contribution rules make the intended invariant explicit: network work must time out and never throw through the plugin lifecycle ([CONTRIBUTING.md:5-10](../repos/yuseferi--opencode-litellm/CONTRIBUTING.md)).
- `/v1/models` is enriched with best-effort `/v1/model/info` data. Existing model fields win, while missing limits, capabilities, and prices are filled from the info response ([src/plugin/index.ts:62-82](../repos/yuseferi--opencode-litellm/src/plugin/index.ts)). The info map tolerates aliases by indexing `model_name`, `model_info.key`, and the upstream `litellm_params.model` ([src/utils/litellm-api.ts:147-161](../repos/yuseferi--opencode-litellm/src/utils/litellm-api.ts)).
- The config-level builder filters embedding, image, and audio models, maps capabilities to OpenCode fields, converts LiteLLM USD/token prices to USD/million tokens, and creates reasoning-effort variants ([src/plugin/index.ts:94-151](../repos/yuseferi--opencode-litellm/src/plugin/index.ts)). Wildcard IDs are also rejected because they are access rules rather than callable model IDs ([src/plugin/index.ts:322-345](../repos/yuseferi--opencode-litellm/src/plugin/index.ts)). User-defined models are not overwritten ([src/plugin/index.ts:333-345](../repos/yuseferi--opencode-litellm/src/plugin/index.ts)).
- Reasoning transport is represented as a policy with explicit allow/deny lists and a model-ID/`mode` heuristic ([src/plugin/discover.ts:15-35,81-108](../repos/yuseferi--opencode-litellm/src/plugin/discover.ts); [src/utils/format-model-name.ts:163-189](../repos/yuseferi--opencode-litellm/src/utils/format-model-name.ts)). The V2 builder sets the per-model API ID, which is important because the adapter otherwise sends the provider ID upstream ([src/plugin/discover.ts:186-195](../repos/yuseferi--opencode-litellm/src/plugin/discover.ts)).

## Pitfalls and Consistency Risks

- There are two materially different implementations. The README calls `discover.ts` and `build-model.ts` “V2” and “unused by the config hook” ([README.md:425-437](../repos/yuseferi--opencode-litellm/README.md)). Nevertheless, that path remains source code and its builder emits zero costs and empty release dates regardless of LiteLLM pricing ([src/plugin/build-model.ts:8-17,56-77](../repos/yuseferi--opencode-litellm/src/plugin/build-model.ts)), unlike the active config path's real cost mapping ([src/plugin/index.ts:126-135](../repos/yuseferi--opencode-litellm/src/plugin/index.ts)). Keeping an unused alternate path risks future reactivation or refactors reintroducing stale behavior.
- The README says a discovered model is skipped if it exists under either provider ([README.md:227-230](../repos/yuseferi--opencode-litellm/README.md)), but the active config hook checks only the current provider's `models` map ([src/plugin/index.ts:266-267,333-345](../repos/yuseferi--opencode-litellm/src/plugin/index.ts)). Multiple matching providers can therefore produce duplicate model IDs or overwrite the intended cross-provider curation invariant.
- `Promise.race` returns on timeout but does not cancel `work()` ([src/plugin/index.ts:269-379](../repos/yuseferi--opencode-litellm/src/plugin/index.ts)). The underlying fetches have their own abort signals, but a delayed operation can still finish and mutate the config after the lifecycle hook has returned. A real cancellation signal or explicit settled-state guard would make the timeout semantics deterministic.
- The V2 path has weaker filtering than the active path: `discoverBucket` loops every returned model and calls `buildModelV2` without the active wildcard/non-chat rejection ([src/plugin/discover.ts:166-195](../repos/yuseferi--opencode-litellm/src/plugin/discover.ts); [src/plugin/build-model.ts:25-53](../repos/yuseferi--opencode-litellm/src/plugin/build-model.ts)). This is another reason to remove, test, or clearly isolate the legacy path.

## Security and Operational Lessons

- API credentials may come from configured `apiKey` or `LITELLM_API_KEY`/`LITELLM_MASTER_KEY`, and are sent as `Authorization: Bearer ...` ([src/plugin/index.ts:217-226](../repos/yuseferi--opencode-litellm/src/plugin/index.ts); [src/utils/litellm-api.ts:30-41](../repos/yuseferi--opencode-litellm/src/utils/litellm-api.ts)). The README correctly recommends environment interpolation so secrets do not enter committed config ([README.md:238-248](../repos/yuseferi--opencode-litellm/README.md)).
- Arbitrary `customHeaders` are copied into every health, model, and info request ([src/plugin/index.ts:46-59,226-233](../repos/yuseferi--opencode-litellm/src/plugin/index.ts); [src/utils/litellm-api.ts:30-41](../repos/yuseferi--opencode-litellm/src/utils/litellm-api.ts)). This enables gateway authentication, but it also means a header secret is sent to whatever endpoint the config selects; deployments should treat `baseURL` and headers as a trusted configuration boundary and use HTTPS for remote proxies.
- Remote model IDs and metadata are consumed from the proxy and used as config keys and wire model IDs ([src/plugin/index.ts:333-345](../repos/yuseferi--opencode-litellm/src/plugin/index.ts); [src/plugin/discover.ts:186-195](../repos/yuseferi--opencode-litellm/src/plugin/discover.ts)). The wildcard check is a concrete safety measure against literal `*` calls, but there is no schema validation for the broader response shape beyond TypeScript casts ([src/utils/litellm-api.ts:65-84](../repos/yuseferi--opencode-litellm/src/utils/litellm-api.ts)).
- Auto-detection is constrained to localhost, while explicit `baseURL` supports remote proxies ([src/utils/litellm-api.ts:164-177](../repos/yuseferi--opencode-litellm/src/utils/litellm-api.ts); [README.md:334-343](../repos/yuseferi--opencode-litellm/README.md)). That keeps the implicit probe narrow, but explicit remote endpoints still need normal SSRF, TLS, and egress controls at the host/application policy level.

## Testing and Verification Lessons

- No test files or test configuration are present in the clone. The README lists Vitest tests as roadmap work ([README.md:442-448](../repos/yuseferi--opencode-litellm/README.md)). CI only runs `npm ci` and TypeScript typechecking on Node 20 and 22 ([.github/workflows/ci.yml:9-30](../repos/yuseferi--opencode-litellm/.github/workflows/ci.yml)).
- The missing tests are consequential for a network/config plugin: URL normalization, auth precedence, timeout behavior, alias enrichment, pricing units, model filtering, idempotence, wildcard rejection, and transport precedence are all pure or mockable seams. In particular, tests should lock down the documented cross-provider merge rule and ensure late completion after timeout cannot mutate returned config.
- The project does have useful manual verification guidance: local linking, required runtime versions, prefixed logs, and a bug-report checklist asking for OpenCode/LiteLLM/runtime versions and a minimal reproducer ([CONTRIBUTING.md:12-35,45-53](../repos/yuseferi--opencode-litellm/CONTRIBUTING.md)).

## Packaging and Release

- `package.json` publishes TypeScript source directly: ESM package, `main`/`exports` at `src/index.ts`, and only `src` included in the npm fileset ([package.json:3-17](../repos/yuseferi--opencode-litellm/package.json)). The package has no runtime bundler/build step; `build` is an alias for strict typechecking and `prepublishOnly` runs it ([package.json:14-17](../repos/yuseferi--opencode-litellm/package.json)). Consumers therefore depend on an OpenCode/Bun/Node toolchain able to load TypeScript source.
- Runtime dependencies are `@opencode-ai/plugin` and `@opencode-ai/sdk`; semantic-release tooling is development-only ([package.json:41-50](../repos/yuseferi--opencode-litellm/package.json)). The repository intentionally limits runtime dependencies to keep the plugin small ([CONTRIBUTING.md:5-10](../repos/yuseferi--opencode-litellm/CONTRIBUTING.md)).
- Publishing is automated with semantic-release, npm provenance, and OIDC trusted publishing. The workflow grants only `contents: write` and `id-token: write`, installs with the lockfile, typechecks, then invokes semantic-release ([.github/workflows/release.yml:9-41](../repos/yuseferi--opencode-litellm/.github/workflows/release.yml); [.releaserc.json:2-25](../repos/yuseferi--opencode-litellm/.releaserc.json)). This is a strong secret-reduction pattern, though the workflow's Node 24 release environment differs from the Node 20/22 CI matrix ([.github/workflows/ci.yml:10-17](../repos/yuseferi--opencode-litellm/.github/workflows/ci.yml); [.github/workflows/release.yml:21-28](../repos/yuseferi--opencode-litellm/.github/workflows/release.yml)).
- The changelog records breaking OpenCode hook changes and operational fixes, but its comparison footer still starts `Unreleased` at `v0.5.0` while the package is `0.8.0` ([CHANGELOG.md:1-13,330-340](../repos/yuseferi--opencode-litellm/CHANGELOG.md); [package.json:3-4](../repos/yuseferi--opencode-litellm/package.json)). Release automation should be checked to ensure generated comparison links remain correct after repeated semantic-release updates.

## Bottom Line

The repository demonstrates a practical OpenCode model-discovery pattern: use the config hook, preserve user configuration, enrich a lean API response from a secondary endpoint, and bound all network work. Its main maintainability risk is the coexistence of an active config implementation and an unused V2 implementation with different pricing/filtering semantics. The largest verification gap is the complete absence of automated tests around those lifecycle, timeout, merge, security-boundary, and transport-routing behaviors.
