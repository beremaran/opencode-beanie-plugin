## Overview

`opencode-pty` is an OpenCode plugin for background and interactive pseudo-terminal sessions. The README positions it as a complement to synchronous `bash`, providing multiple sessions, buffered/paginated output, regex search, input, exit notifications, cleanup, and an optional React/WebSocket monitor UI (`README.md:3-28`). Its public tool surface is `pty_spawn`, `pty_write`, `pty_read`, `pty_list`, and `pty_kill` (`README.md:54-62`).

## OpenCode Integration Patterns

- Keep the package entrypoint minimal and export both a named plugin and a `server` alias. `index.ts` re-exports `PTYPlugin` from the source and aliases it as `server` (`index.ts:1-2`).
- Implement the plugin as an async factory receiving the OpenCode client and project directory, initialize shared services, and return hook/tool/config/event registrations (`src/plugin.ts:15-20`).
- Register tools under the `tool` result property and put command registration in the `config` hook. This lets slash commands be added without a separate static config file (`src/plugin.ts:47-66`).
- Use `command.execute.before` to intercept plugin-owned slash commands. The handler lazily starts the server, opens the browser or sends the URL back through `client.session.prompt`, then throws to mark the command handled (`src/plugin.ts:20-45`).
- Bind spawned PTYs to their parent OpenCode session and clean them up on `session.deleted`; this is a useful lifecycle pattern for resources that outlive one tool call (`src/plugin.ts:67-71`, `src/plugin/pty/tools/spawn.ts:49-61`).
- Put OpenCode-specific behavior behind small adapters. `pty_spawn` checks permissions, maps tool arguments to manager options, and returns structured tagged text for the agent (`src/plugin/pty/tools/spawn.ts:15-79`). The manager owns process lifecycle, buffering, callbacks, and notifications (`src/plugin/pty/manager.ts:70-159`).
- Use structured reminders in tool output when asynchronous completion changes agent behavior. `notifyOnExit` explicitly tells the agent to wait for `<pty_exited>` instead of polling with sleep/read loops (`src/plugin/pty/tools/spawn.ts:6-13`, `src/plugin/pty/tools/read.ts:9-17`).
- Preserve OpenCode session model and agent context when notifying the parent. The manager forwards the parent session and agent into lifecycle data (`src/plugin/pty/tools/spawn.ts:49-60`); notification behavior is separately encapsulated in `NotificationManager` and exercised by focused tests (`test/notification-manager.test.ts:42-160`).

## Security And Safety

### Positive Controls

- Spawn paths consult `permission.bash` before creating a process, including scalar and pattern-map configurations (`src/plugin/pty/permissions.ts:60-89`). Both REST creation and WebSocket creation call the same checks (`src/web/server/handlers/sessions.ts:31-46`, `src/web/server/handlers/websocket.ts:128-145`).
- `pty_write` re-checks parsed command lines before forwarding input, and supports explicit escape-sequence parsing for control characters (`src/plugin/pty/tools/write.ts:14-35`, `src/plugin/pty/tools/write.ts:72-83`).
- Invalid or dangerous-looking regexes are rejected before search. The implementation validates syntax and rejects several nested/repeated patterns intended to reduce catastrophic backtracking risk (`src/plugin/pty/tools/read.ts:78-93`, `src/plugin/pty/tools/read.ts:197-210`). This is only a heuristic, not a general ReDoS proof.
- PTYs have optional positive-integer timeouts that mark the session as timed out before killing it (`src/plugin/pty/session-lifecycle.ts:19-29`, `src/plugin/pty/session-lifecycle.ts:41-67`).
- The web server defaults to IPv6 loopback and a random port, which is a safer default for a local monitor (`src/web/server/server.ts:42-46`).
- Direct executable/argument spawning avoids implicitly invoking a shell (`src/plugin/pty/session-lifecycle.ts:100-108`), which is preferable to concatenating an untrusted command string.

### Risks And Pitfalls

- The web server has no authentication or authorization layer. It exposes session listing, buffer reads, process creation, kill, and input routes (`src/web/server/server.ts:47-72`), and WebSocket subscribe/read/input handlers are similarly open once a client connects (`src/web/server/handlers/websocket.ts:27-58`, `src/web/server/handlers/websocket.ts:148-167`). The loopback default helps, but `PTY_WEB_HOSTNAME` is configurable (`src/web/server/server.ts:43-46`); binding beyond loopback should be treated as a trusted-network-only deployment unless authentication is added.
- Existing-session input through the web API bypasses the command-permission recheck: REST `sendInput` calls `manager.write` directly (`src/web/server/handlers/sessions.ts:69-81`), and WebSocket `input` does the same (`src/web/server/handlers/websocket.ts:108-110`, `src/web/server/handlers/websocket.ts:148-150`). This is materially different from the agent-facing `pty_write` path, which parses and checks command lines (`src/plugin/pty/tools/write.ts:75-81`). A user who can reach the web interface can therefore drive an already-authorized PTY without that check.
- External-directory handling is incomplete in source. `external_directory: 'deny'` is enforced, but `'ask'` is a TODO with no prompt or explicit allow/log behavior (`src/plugin/pty/permissions.ts:91-115`). The README documents “ask” as allow (`README.md:255-259`), so documentation and implementation should be reconciled before relying on that policy.
- The project-directory test is string-prefix based rather than path-boundary based: `/project-other` starts with `/project` and can be accepted (`src/plugin/pty/permissions.ts:96-101`). Canonical path resolution plus a separator-aware containment check would avoid this edge case.
- Input permission parsing is line-oriented and splits commands on whitespace (`src/plugin/pty/tools/write.ts:37-54`). It is not a shell parser, so quoted arguments, multiline shell syntax, aliases, and commands embedded in interactive programs may not map cleanly to OpenCode bash permission patterns. Treat the check as defense-in-depth, not equivalent shell-policy evaluation.
- The web JSON handlers cast request bodies and validate only a few fields. For example, `createSession` validates the command but accepts optional fields before the manager performs deeper timeout validation (`src/web/server/handlers/sessions.ts:12-29`, `src/plugin/pty/session-lifecycle.ts:19-29`). Strong runtime schemas would make the HTTP boundary less permissive.
- The ring buffer truncates by JavaScript string length, despite the README describing a maximum number of lines. The README advertises `PTY_MAX_BUFFER_LINES` (`README.md:230-236`), while the implementation reads `PTY_MAX_BUFFER_SIZE` and truncates characters (`src/plugin/pty/buffer.ts:1-2`, `src/plugin/pty/buffer.ts:17-20`). This is both a configuration/documentation mismatch and a potential memory/retention surprise.

## Testing Lessons

- The repository has a layered test strategy. Unit tests cover tool formatting, argument mapping, invalid sessions, regex handling, and the ring buffer (`test/pty-tools.test.ts:8-12`, `test/pty-tools.test.ts:161-240`, `test/pty-tools.test.ts:352-403`).
- Process-level tests exercise real PTY spawning and echo behavior (`test/pty-spawn-echo.test.ts:6-21`, `test/spawn-repeat.test.ts:19-82`), while manager integration tests cover output broadcasting, lifecycle, cleanup, and timeout behavior (`test/pty-integration.test.ts:6-20`, `test/pty-integration.test.ts:114-274`).
- HTTP and WebSocket behavior are tested separately, including routes, invalid timeouts, subscriptions, malformed messages, and unknown message types (`test/web-server.test.ts:11-16`, `test/web-server.test.ts:35-176`, `test/websocket.test.ts:13-20`, `test/websocket.test.ts:69-200`).
- Permission enforcement has direct regression tests for both REST and WebSocket spawn paths, asserting that `manager.spawn` is not called on denial (`test/web-permissions.test.ts:58-107`). A missing high-value test is the corresponding REST/WebSocket input case, which would expose the bypass described above.
- Packaging is tested as a first-class behavior. One test checks that `npm pack` includes built HTML and hashed JS/CSS (`test/npm-pack-structure.test.ts:34-58`); another installs the tarball into a temporary workspace and verifies compiled source, web assets, server startup, and asset serving (`test/npm-pack-integration.test.ts:31-170`).
- Playwright is configured for Chromium and Firefox, with worker parallelism, CI-only retries, and a global setup fixture (`playwright.config.ts:8-23`, `playwright.config.ts:25-47`). The broad E2E suite includes UI, live streaming, extraction/serialization, and server consistency scenarios (paths under `test/e2e/`).
- Test infrastructure explicitly disposes servers, clears sessions, and removes callback registrations (`test/utils.ts:151-174`). This is important for global singleton managers and prevents cross-test process/callback leakage.

## Packaging And Release

- The package ships only `dist`, is ESM, exposes the compiled root and wildcard subpaths, and declares OpenCode compatibility through `engines.opencode` (`package.json:30-59`, `package.json:98-105`). Consumers therefore depend on the build producing all referenced source and web artifacts.
- `prepack` runs the production build; the build compiles TypeScript, copies `.txt` tool descriptions, and builds the Vite web UI (`package.json:61-70`). This is a good guard against publishing source-only packages, but it makes packaging dependent on the complete toolchain.
- The local development instructions document lint, formatting, typecheck, both test layers, and development builds (`README.md:305-317`). The lockfile and explicit versioned dependencies improve reproducibility (`package.json:76-106`, `bun.lock`).
- The release script checks for Bun, Git, and npm, refuses a dirty working tree, bumps the package version, commits, and pushes to the current branch (`release.sh:104-125`, `release.sh:127-190`). The script has a dry-run and confirmation mode (`release.sh:6-13`, `release.sh:76-86`), but it still mixes Bun-based inspection/build conventions with npm versioning and should be run only with deliberate branch/remote review.
- The packaging tests invoke `npm pack` even though the project otherwise standardizes on Bun. That is intentional coverage of the npm distribution contract, but CI must have npm, tar, and the native PTY/build prerequisites available (`test/npm-pack-structure.test.ts:34-58`, `test/npm-pack-integration.test.ts:61-104`).

## Practical Takeaways

1. A small OpenCode plugin factory plus a dedicated manager is a scalable shape for long-lived resources.
2. Parent-session identifiers and `session.deleted` cleanup are essential when tools create background processes.
3. Agent-facing output should encode lifecycle state and completion semantics, not merely return a process ID.
4. Permission enforcement must cover every control plane, including UI REST and WebSocket operations on existing sessions, not only spawn and agent tools.
5. Local-only web binding is a useful default, but configurable host binding requires authentication or an explicit trusted-network threat model.
6. Packaging tests that install the actual tarball catch missing compiled modules and static assets that typechecks cannot detect.
7. Configuration names and semantics need tests or a single source of truth: the documented line limit and external-directory behavior currently diverge from the implementation.
