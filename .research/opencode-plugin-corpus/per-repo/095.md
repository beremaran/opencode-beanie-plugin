## OpenCode patterns

- **Event hook with output mutation:** The plugin exports an async factory returning a `chat.params` handler, receiving `{ model }` and the mutable `output` object (`src/index.js:30-32`). It changes only `output.temperature` (`src/index.js:34-37`), which is a small, focused way to apply provider/model-specific request defaults.
- **Provider plus model matching:** Matching normalizes both `providerID` and the model identifier to lowercase (`src/index.js:12-15`), requires an exact provider match, and applies a regular-expression model rule (`src/index.js:16-19`). The fallback from `modelID` to `model.api.id` makes the matcher tolerant of either model shape (`src/index.js:14`).
- **Rule-table extensibility:** Behavior is data-driven through `TEMPERATURE_RULES`, with provider, regex, target, and baseline fields (`src/index.js:3-10`). The README explicitly directs contributors to add entries there (`README.md:22`).
- **Respect explicit configuration:** The handler returns unless the current temperature is absent or is within `1e-3` of the configured baseline (`src/index.js:1`, `src/index.js:22-28`, `src/index.js:32-36`). This preserves an explicit non-baseline agent setting rather than unconditionally overwriting it, as documented (`README.md:17-20`).
- **Install-only configuration:** Users enable the package by adding its npm name to the OpenCode `plugin` array (`README.md:7-15`). No project-local OpenCode config or command/tool registration is needed.

## Pitfalls and design limits

- **Documentation drift:** The implementation is JavaScript at `src/index.js`, but the extension guidance says to extend `src/index.ts` (`README.md:22`). This would send contributors to a nonexistent file.
- **Environment values are parsed without validation:** `target` and `baseline` are created with `Number(...)` at module initialization (`src/index.js:7-8`). An invalid target is safely ignored because the handler checks `Number.isFinite(rule.target)` (`src/index.js:33`), but an invalid baseline makes the rule effectively inapplicable for any defined current temperature: `isDefaultTemperature` returns only `current === undefined` when baseline is non-finite (`src/index.js:23-25`).
- **Regex matching is intentionally broad:** `/gemini-3-pro/` is not anchored (`src/index.js:6`), so any Google model ID containing that substring matches. This is convenient for variants but can silently include future or unintended IDs.
- **Only one rule is shipped:** The README describes support for only Google Gemini 3 Pro at `0.35` (`README.md:3`), and the source contains one rule (`src/index.js:3-10`). There is no documented precedence behavior if future rules overlap; `findRule` selects the first match (`src/index.js:16-19`).
- **Baseline semantics depend on the upstream default:** The default baseline is `1` (`src/index.js:8`), and an absent output temperature is always treated as default (`src/index.js:26`). If OpenCode or a provider changes its implicit default, the plugin may apply a target unexpectedly unless the environment baseline is updated.
- **Mutation contract is implicit:** The handler assumes `output` is present and writable (`src/index.js:31-36`), and there is no defensive check or test documenting the OpenCode hook payload contract.

## Security lessons

- **Small attack surface:** The package has no dependencies or network/filesystem/process operations in its manifest or source (`package.json:1-7`, `src/index.js:1-38`). Its behavior is limited to reading two environment variables and mutating a request parameter.
- **Environment is a control plane:** Anyone able to control the process environment can change the target or baseline (`src/index.js:7-8`; `README.md:17-20`). The finite-target guard prevents nonnumeric or infinite target values from being written (`src/index.js:33`), but finite malicious values are still accepted. Deployments should treat these variables as trusted configuration.
- **No secret handling:** The README and implementation expose no credentials, tokens, or external services (`README.md:1-22`, `src/index.js:1-38`). This is a useful default for parameter-only plugins.

## Testing and validation lessons

- **No automated tests are included:** The clone contains no test directory or test files, and `package.json` defines no `scripts` entry (`package.json:1-7`). The matching, baseline epsilon behavior, malformed environment values, fallback model shape, and output mutation are therefore unverified by repository tests.
- **High-value test matrix:** Tests should cover Google versus non-Google providers, matching and nonmatching model IDs, `modelID` versus `api.id`, undefined/current baseline/explicit temperatures, values just inside and outside `1e-3`, invalid target and baseline environment values, and overlapping rule order. These cases map directly to `src/index.js:12-37`.
- **Manual installation evidence is limited:** README usage documents only the OpenCode config snippet (`README.md:7-15`); it does not show a smoke test, expected event payload, or verification command.

## Reusable takeaway

For a narrowly scoped OpenCode parameter policy, return an event handler from an async plugin factory, match provider and model explicitly, and mutate only the relevant output field. Preserve user intent by changing values only when the upstream value is absent or still equal to a known baseline (`src/index.js:30-37`). Add finite-value validation and tests around environment configuration, keep model patterns precise, and ensure README paths match the shipped entrypoint.
