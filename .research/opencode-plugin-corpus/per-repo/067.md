## Repository shape and OpenCode integration

- This is a single-package, ESM OpenCode plugin. The package entrypoint is `src/index.ts`, which exports `providerAlias` as a `Plugin` (`src/index.ts:1-6`). The package publishes `dist/index.js` as both `main` and `module` and includes only `dist` in the package payload (`package.json:21-26`).
- The plugin validates its tuple options with Zod before doing any work, then loads the model registry once and returns an async `config` hook (`src/index.ts:6-14`). The hook initializes `config.provider`, iterates configured aliases, skips aliases whose provider is absent, and replaces only existing provider entries (`src/index.ts:15-30`). This is a useful non-invasive OpenCode pattern: plugin options select existing configuration rather than silently creating providers.
- Options are a record keyed by local provider ID. Each value is either a target provider string or an object with optional `provider`, `includes`, and local model-alias mappings (`src/options.ts:3-19`). Invalid nested values fail early with `Invalid options` (`src/index.ts:7-10`; `src/index.test.ts:438-448`).
- README usage reinforces the required split between plugin configuration and the existing OpenCode `provider` definition: the plugin reference is under `plugin`, while `npm`, `name`, and credentials/options remain under `provider` (`README.md:24-58`).

## Implementation patterns

- Registry loading prefers `~/.cache/opencode/models.json`; if absent, it fetches `https://models.dev/api.json`, sanitizes it, creates the cache directory, and writes JSON (`src/model-registry.ts:42-56`). Provider-level `id`, `env`, and `doc` are removed, while model-level fields are retained except `experimental` (`src/model-registry.ts:17-39`).
- Model references support either `provider/model` or a short model ID resolved against the configured fallback provider (`src/model-registry.ts:59-77`). Empty provider/model components resolve to an empty object rather than throwing (`src/model-registry.ts:64-76`).
- Inclusion is deliberately two-phase: positive patterns select from the union of base and user model IDs, then `!` patterns remove matches (`src/model-registry.ts:79-131`). Exact strings are added directly, while wildcard patterns use `Minimatch` (`src/model-registry.ts:89-110`). This makes exclusions order-independent relative to positive entries, matching the README’s documented behavior (`README.md:117-128`).
- Provider merging starts with models.dev metadata, overlays the user provider configuration, and gives user fields precedence (`src/provider-config.ts:17-32`, `src/provider-config.ts:48-52`). For models, aliases are hydrated first, local model overrides are merged afterward, and aliases are finally re-applied (`src/provider-config.ts:36-45`, `src/provider-config.ts:64-78`). Explicitly setting `{ id: modelID }` preserves a local alias ID instead of leaking the target model ID (`src/provider-config.ts:36-44`; `src/index.test.ts:241-271`).
- The implementation filters `experimental` from hydrated model metadata and strips provider-level registry identity/environment/documentation fields, while preserving equivalent fields supplied by the user (`src/model-registry.ts:17-39`; `src/index.test.ts:408-436`, `src/index.test.ts:450-496`). The changelog records these as shipped fixes in versions 1.0.1 through 1.0.4 (`CHANGELOG.md:3-24`).

## Security and operational lessons

- The plugin does not read provider secrets itself; README examples keep API keys in OpenCode options via `{env:OPENAI_API_KEY}` (`README.md:45-54`, `README.md:90-97`). The merge path preserves those user options rather than replacing them with registry data (`src/provider-config.ts:48-78`).
- Remote metadata is fetched and persisted without an explicit HTTP status check, timeout, schema validation, or atomic file write (`src/model-registry.ts:49-55`). A production derivative should validate the response shape, handle non-2xx responses and network failures, bound latency, and avoid leaving a partially written cache. The current implementation also trusts any parseable JSON already present in the user cache (`src/model-registry.ts:43-47`), so cache integrity and permissions matter.
- Registry provider `id`, `env`, and `doc` fields are intentionally discarded before merging (`src/model-registry.ts:31-39`), reducing accidental propagation of models.dev provider metadata into runtime config. Model `env` and `doc` are retained, however (`src/model-registry.ts:17-24`; `src/index.test.ts:450-477`); consumers should treat hydrated registry metadata as data, not as executable configuration.
- The plugin’s skip-if-missing behavior limits unexpected config mutation, but it does not validate that the target provider exists in the loaded registry: an unknown target simply contributes an empty base config (`src/provider-config.ts:23-25`). A stricter plugin could warn or fail on unresolved target providers if misconfiguration must be visible.

## Testing lessons

- Tests use `createOpencodeServer` and `createOpencodeClient`, install the plugin from the repository path, and inspect the resulting provider through `client.config.providers()` (`src/index.test.ts:16-50`). This verifies the actual OpenCode config hook rather than only helper functions.
- Coverage includes inheritance, explicit model selection, glob/exclusion rules, model aliases, short references, preservation of provider/model overrides, missing-provider non-creation, metadata sanitization, and invalid option rejection (`src/index.test.ts:52-199`, `src/index.test.ts:202-238`, `src/index.test.ts:273-406`, `src/index.test.ts:408-496`).
- The integration helper supports optional basic authentication using `OPENCODE_SERVER_USERNAME` and `OPENCODE_SERVER_PASSWORD`, injecting the Authorization header into client requests (`src/index.test.ts:16-35`). This is a reusable pattern for testing secured OpenCode servers without hard-coding credentials.
- Tests are not hermetic by default: plugin initialization loads `~/.cache/opencode/models.json` or fetches models.dev (`src/index.ts:11`; `src/model-registry.ts:42-56`). The repository’s test command is `rstest` (`package.json:30-38`), but in this audit `bun run test` could not start because dependencies were not installed (`rstest: command not found`). No pass/fail result for the suite is therefore claimed.
- The test server is closed in each test after assertions (`src/index.test.ts:77-82`, `src/index.test.ts:112-118`, and subsequent tests), which is important for a suite that starts real servers. The tests use empty API/base URL values for provider setup (`src/index.test.ts:64-73`), keeping provider initialization local.

## Packaging and release lessons

- Build uses Rslib to emit ESM targeting Node 18 with declarations disabled (`rslib.config.ts:3-10`). TypeScript is build-support only with `noEmit`, bundler resolution, isolated modules, and `src` as the root (`tsconfig.json:2-15`). Consumers should not expect published `.d.ts` files from this package.
- The package has explicit `build`, `test`, `check`, `format`, and Changesets release scripts (`package.json:30-38`). Only `dist` is published, while `dist/` and `node_modules` are ignored in git (`package.json:24-26`; `.gitignore:6-10`).
- The release workflow runs on pushes to `main`, installs with `bun install --frozen-lockfile`, runs Biome checks, builds, and then invokes Changesets version/publish (`.github/workflows/release.yml:1-5`, `.github/workflows/release.yml:25-45`). It grants repository contents, OIDC, and pull-request write permissions (`.github/workflows/release.yml:9-14`), so workflow changes deserve heightened review.
- Changesets are configured for public access, `main` as the base branch, and patch updates for internal dependencies (`.changeset/config.json:2-10`). The release process is therefore reproducible only when the lockfile, Bun version, Node version file, and Changesets state remain aligned (`.github/workflows/release.yml:19-31`).
- The README documents the consumer workflow (`bun install`, `bun run test`, `bun run build`) and the available development scripts (`README.md:183-197`), which lowers adoption friction but does not document the network/cache prerequisite for first-run tests.

## Bottom line

The strongest OpenCode pattern is a narrowly scoped async `config` hook that enriches only providers already declared by the user, preserves runtime provider options, and makes model selection/aliasing explicit. The principal pitfalls are external metadata loading without response/error hardening, a user-home cache side effect, and integration tests that depend on installed tooling plus network-or-cache availability. Packaging is clear and minimal, with ESM-only output and a Changesets-driven release workflow, but the workflow’s write permissions and the absence of a hermetic metadata fixture are important maintenance risks.
