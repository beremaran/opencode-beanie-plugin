## OpenCode patterns worth reusing

### Plugin composition

- The plugin factory receives OpenCode project/client/shell context and loads project configuration before constructing prompts (`src/index.ts:7-11`). This keeps prompt construction tied to the effective project configuration.
- OpenCode configuration is extended through the `config()` hook: the plugin registers a primary `review` agent, a `review:fixer` subagent, optional dimension subagents, and two commands (`src/index.ts:16-86`). This is a useful pattern for plugins that need both user-facing commands and internal agents.
- Tool registration is kept separate from the configuration hook and exposed as named tools (`review_changes` and `toggle_auto_review`) (`src/index.ts:88-94`, `src/tools/index.ts:1-2`). The tool factory for the toggle makes state access/set behavior injectable and easy to isolate (`src/tools/toggle-auto-review.ts:3-19`).

### Review orchestration

- The default design is a dispatcher agent that calls `review_changes`, spawns one dimension agent per enabled dimension with `task`, deduplicates same-location findings, and aggregates by severity (`src/agent.ts:101-146`). The design rationale explicitly aligns one agent per dimension with the user-configurable `dimensions` array (`openspec/changes/multi-agent-parallel-review/design.md:31-40`).
- Dimension registration is data-driven: duplicate configured dimensions are removed, unknown dimensions are filtered out, and agent names are generated as `review:dim-<dimension>` (`src/dimensions/index.ts:123-138`).
- The plugin provides a deliberate fallback to single-agent review when `parallel` is false (`src/agent.ts:94-99`, `src/config.ts:17-33`). This is a practical compatibility valve when subagent capacity or latency is a problem.
- The review agent is read-only for file mutation and has narrowly listed git read commands, while the fixer is explicitly a subagent with write/edit/read/search capabilities (`src/index.ts:20-53`). The separation of analysis and mutation is a sound baseline, even though the fixer permissions need tightening (see pitfalls).

### Configuration and UX

- Configuration layering is simple and predictable: defaults, then global `~/.config/opencode/review.json`, then project `.opencode/review.json`; nested `trigger` values are merged at each layer (`src/config.ts:17-33`, `src/config.ts:46-67`). Both files are read concurrently (`src/config.ts:49-55`).
- The configuration exposes language, dimensions, diff limit, idle trigger/cooldown, custom rules, and parallel mode (`src/config.ts:5-15`, `src/config.ts:17-33`). README examples document the project/global locations and supported values (`README.md:63-98`).
- Runtime toggling is intentionally session-memory-only: `/review:auto` delegates to `toggle_auto_review`, and restart restores the file value (`README.md:40-57`, `src/tools/toggle-auto-review.ts:12-18`). The OpenSpec design records that this state is shared by the single plugin instance across sessions (`openspec/changes/add-auto-toggle-command/design.md:30-45`).

## Pitfalls and security lessons

### Shell command construction

- `review_changes` executes constructed strings through `bash -c` (`src/tools/review-changes.ts:60-67`). The branch scope inserts `defaultBranch`, which is parsed from `git remote show origin` and interpolated into another shell command (`src/tools/review-changes.ts:31-35`, `src/tools/review-changes.ts:69-77`). Treat branch names and command fragments as untrusted: shell-argument APIs or a fixed command/argument interface would avoid injection and quoting failures.
- The tool catches every shell failure and returns an empty string (`src/tools/review-changes.ts:60-67`); the caller then reports “No changes found” for any empty diff (`src/tools/review-changes.ts:47-49`). This conflates no-change, missing repository, git failure, and command failure, making diagnosis and safe automation harder.
- `max_lines` is only typed as a number and is not range-checked (`src/tools/review-changes.ts:10-12`, `src/tools/review-changes.ts:16-18`). Negative, non-finite, or excessively large values should be rejected or bounded. Also, the tool defaults to literal `500` rather than reading the loaded `config.max_diff_lines` (`src/tools/review-changes.ts:16-18`, `src/config.ts:26`), so the documented `max_diff_lines` setting does not control tool defaults.

### Mutation and execution boundaries

- The fixer agent is given unrestricted `bash: true`, along with write and edit tools (`src/index.ts:40-52`). Because the fixer is instructed to act on model-generated issue messages (`src/agent.ts:267-320`), a safer production posture would constrain commands, require explicit user confirmation, or isolate/limit the fixer’s writable scope.
- Automatic review runs on `session.idle`, applies a process-level cooldown, and sends a prompt to the session client (`src/index.ts:96-118`). State is global to the plugin instance rather than keyed by session, so one session can suppress another during the cooldown; the design acknowledges shared state but does not address isolation (`openspec/changes/add-auto-toggle-command/design.md:44-45`).
- Both the automatic prompt and session event handling swallow errors (`src/index.ts:102-119`). This prevents user-visible crashes but also removes observability for failed reviews; structured logging or an explicit non-fatal error notification would make failures diagnosable.
- The README advertises automatic critical-issue fixing (`README.md:5-13`), while the prompts require the dispatcher to spawn a fixer and wait for it (`src/agent.ts:79-91`, `src/agent.ts:243-264`). That behavior should be treated as a privileged workflow, not just a review feature, because it can modify the checked-out tree without a separate confirmation step.

### CI workflow boundary

- The workflow grants `contents: read`, `pull-requests: write`, and `issues: write` (`.github/workflows/opencode-review.yml:7-14`), checks that the PR is non-draft and originates from the same repository, and then checks out the PR head before invoking an external action (`.github/workflows/opencode-review.yml:8-27`). The same-repository condition reduces fork exposure, but the workflow still combines write tokens, unpinned third-party action references (`actions/checkout@v6`, `Svtter/opencode-actions/review@v2`), and execution on checked-out PR code. Pinning trusted actions to immutable SHAs and minimizing permissions are important hardening steps.

## Testing lessons

- There are no test files in the tracked source tree. The only test script is a deliberate success stub, `echo "TODO: add tests" && exit 0` (`package.json:7-9`). This means configuration precedence, prompt generation, dimension filtering, diff truncation, branch fallback, toggle state, and idle cooldown have no automated regression protection.
- The OpenSpec task list marks implementation work complete but leaves all integration verification unchecked, including parallel/fallback review, fixer chaining, partial dimensions, bilingual output, and idle triggering (`openspec/changes/multi-agent-parallel-review/tasks.md:30-37`). This is useful process evidence: the highest-risk behavior is acknowledged but remains manual/unverified.
- Small pure-function tests would cover much of the code without starting OpenCode: `loadConfig` merge precedence (`src/config.ts:46-67`), `getDimensionPrompts` deduplication/filtering (`src/dimensions/index.ts:130-138`), prompt language/fallback behavior (`src/agent.ts:27-34`), and toggle transitions (`src/tools/toggle-auto-review.ts:12-18`). Integration tests should exercise each git scope, truncation and error paths (`src/tools/review-changes.ts:22-56`), and idle cooldown/session behavior (`src/index.ts:96-119`).

## Packaging and release lessons

- The package declares version `0.2.0`, but the lockfile root metadata still says `0.1.0` (`package.json:2-4`, `package-lock.json:1-13`); the standalone `VERSION` file agrees with `0.2.0` (`VERSION:1`). Release metadata should be updated atomically and checked in CI.
- `@opencode-ai/plugin` is declared as `latest` (`package.json:19-21`), which makes reproducible installs depend on registry time. The lockfile currently resolves version `1.15.4` (`package-lock.json:99-102`), but the manifest remains floating.
- The lockfile’s resolved URLs point to `https://npm.my-nas.lan/...` (`package-lock.json:15-18`, `package-lock.json:99-102`). That private registry host is not a portable public-install assumption and can make clean installs fail outside the author’s environment. A distributable package should use a reachable canonical registry or document the required mirror.
- The README recommends symlinking `src/index.ts` into an OpenCode plugins directory and labels npm installation “coming soon” (`README.md:15-38`). This is an effective development workflow, but it is not a packaged distribution contract; a release should define build/publish artifacts, supported runtime, and whether TypeScript source loading is guaranteed.
- The repository ignores generated JavaScript, declarations, and source maps (`.gitignore:1-7`) while TypeScript is configured to emit them (`tsconfig.json:8-12`). If publishing compiled output, the package needs an explicit build script and `files`/exports policy; if source installation is intentional, that should be stated as a runtime prerequisite.

## Overall assessment

`opencode-review` demonstrates a clear OpenCode plugin shape: configuration-driven registration, narrowly scoped read-only review agents, explicit tool boundaries, and a useful parallel-to-single-agent fallback. Its strongest reusable idea is dimension-specific subagent orchestration with structured severity aggregation. The main risks are operational rather than conceptual: no meaningful automated tests, silent command failures, shell-string construction, a highly privileged fixer, process-global auto-review state, and unreconciled/non-portable package metadata. These should be addressed before treating the plugin as a reliable or broadly distributable review-and-fix automation.
