## Summary

This is a substantial TypeScript OpenCode provider plugin. It implements Google OAuth/PKCE, exposes two auth methods, loads multi-account credentials, and returns an auth loader whose `fetch` method intercepts Google Generative Language requests. The interceptor selects accounts and quota pools, refreshes tokens, transforms requests/responses, retries/fails over endpoints, and supports Claude/Gemini-specific behavior. It also registers a `google_search` tool and an event handler for update checks, child-session toast filtering, and session recovery (`src/plugin.ts:1213-1387`, `src/plugin.ts:1388-1466`).

## Evidence-Based Patterns

### SDK imports, registration, and lifecycle

- Uses the official plugin helper `tool` from `@opencode-ai/plugin` (`src/plugin.ts:1-3`) and derives the client type from `PluginInput["client"]` (`src/plugin/types.ts:1,42`).
- Exports named plugin factories from the package entrypoint (`index.ts:1-14`). The main factory receives `PluginContext` (`client`, `directory`) and returns `PluginResult` (`src/plugin.ts:1213-1215`; `src/plugin/types.ts:44-47,92-100`).
- Registration is returned declaratively: `event`, `tool.google_search`, and `auth` with provider, loader, and methods (`src/plugin.ts:1383-1389`; `src/plugin/types.ts:92-100`).
- Startup initializes config, runtime config, logging, remote version discovery, health/token trackers, optional disk signature cache, session recovery, and update checking (`src/plugin.ts:1216-1266`).

### Events, hooks, and context mutation

- The event callback forwards every event to an auto-update checker, detects root versus child sessions from `session.created`, and handles recoverable `session.error` events (`src/plugin.ts:1268-1332`).
- Recovery uses the OpenCode client to inject synthetic tool results and optionally send a resume prompt; TUI notifications are best-effort and scoped to root sessions by default (`src/plugin.ts:1304-1327`; `docs/ARCHITECTURE.md:135-169`).
- The auth loader mutates provider model costs to zero and stores `getAuth` for tool access (`src/plugin.ts:1390-1394,1444-1449`). This is a concrete example of provider-context mutation, but it is global/module-sensitive rather than purely request-local.

### Auth and provider wiring

- The provider loader returns `apiKey: ""` and a custom `fetch` implementation, allowing OpenCode's provider pipeline to use OAuth rather than a static API key (`src/plugin.ts:1452-1456`). Non-target requests pass through to global `fetch` (`src/plugin.ts:1455-1457`).
- OAuth is PKCE-based: authorization state carries the verifier and project ID, and code exchange sends `code_verifier` to Google (`src/antigravity/oauth.ts:92-113,201-229`). Token exchange resolves user email and managed project context, with endpoint fallback and a ten-second request timeout (`src/antigravity/oauth.ts:116-195,232-260`).
- Auth registration includes `OAuth with Google (Antigravity)` and a manual API-key method; the OAuth method branches between browser/local callback and headless/manual flows (`src/plugin.ts:2502-2520,2990-3200`; `src/plugin/types.ts:77-83`).
- The plugin supports repeated login for account pools, quota checks, account enable/disable, verification, and destructive account management through the auth prompt flow (`src/plugin.ts:2520-2568,2628-2648,2892-2894`).

### Tools and request transformation

- `google_search` uses `tool.schema` for typed arguments (`query`, optional URLs, optional thinking), receives an abort signal, obtains current auth, refreshes expired access tokens, and returns user-readable errors instead of throwing for expected auth failures (`src/plugin.ts:1334-1380`).
- The request pipeline classifies target URLs, resolves model family/header style, prepares Antigravity payloads, transforms SSE responses, and retries endpoint/account combinations (`src/plugin.ts:1452-1490,2470-2498`; `docs/ARCHITECTURE.md:55-88`).
- Transform modules are separated by model family and concern: Claude/Gemini transforms, model resolution, cross-model sanitization, and shared types are re-exported from a barrel (`src/plugin/transform/index.ts:1-69`).
- The documented schema allowlist removes unsupported JSON Schema fields and converts `const` to a singleton enum (`docs/ARCHITECTURE.md:171-182`). This is a reusable compatibility pattern when an upstream API accepts only a restricted schema subset.

### State, concurrency, and process boundaries

- Account state is persisted under the OpenCode config directory, with versioned storage migrations through V4 and validation/deduplication on load (`src/plugin/storage.ts:145-231,576-682`).
- Credential writes use `proper-lockfile`, temporary files, atomic rename, mode `0600`, and a separate replace operation for deletions so merge logic cannot resurrect deleted accounts (`src/plugin/storage.ts:385-440,693-747`).
- Proactive refresh is an interval-based background queue. It skips disabled/expired accounts, serializes refresh iterations with `isRefreshing`, refreshes accounts serially, and logs per-account failures without stopping other accounts (`src/plugin/refresh-queue.ts:61-75,128-207,230-259`).
- Account rotation combines rate-limit state, health score, token bucket, LRU, stickiness, and jitter (`src/plugin/rotation.ts:54-161,207-228,231-260`; `src/plugin/accounts.ts:46-123`).
- The OAuth callback is a local Node HTTP server with timeout, callback-path validation, clean close, and secure localhost default. Remote/WSL/container heuristics may select `0.0.0.0`, while `OPENCODE_ANTIGRAVITY_OAUTH_BIND` can override the bind address (`src/plugin/server.ts:106-133,140-167,300-365`).
- Browser launch crosses a process boundary with platform-specific `exec` calls (`src/plugin.ts:245-267`).

### Configuration

- Configuration uses Zod defaults and validates user/project JSON files, with project config overriding user config (`src/plugin/config/schema.ts:12-22,64-106`; `src/plugin/config/loader.ts:57-139`). Paths are `~/.config/opencode/antigravity.json` and `.opencode/antigravity.json` (`src/plugin/config/loader.ts:23-50`).
- The generated JSON schema is published as an asset and tested against defaults/documentation (`assets/antigravity.schema.json`; `src/plugin/config/schema.test.ts:6-47`). README/configuration docs provide copy-paste plugin/provider/model setup (`README.md:43-82,150-241`; `docs/CONFIGURATION.md:1-23`).
- Configuration controls recovery, account strategy, quota routing, debug sinks, signature caching, and proactive refresh (`docs/CONFIGURATION.md:31-106,156-215`).

### Error handling and security

- Expected provider failures are classified into quota, rate-limit, capacity, server, and unknown categories with bounded backoff and jitter (`src/plugin/accounts.ts:46-123`).
- OAuth fetches use abort timeouts and endpoint fallbacks; storage load/migration degrades to null with structured logging (`src/antigravity/oauth.ts:118-195`; `src/plugin/storage.ts:589-690`).
- Sensitive account files are explicitly gitignored and permission-hardened (`src/plugin/storage.ts:21-31,360-380`; `docs/ARCHITECTURE.md:194-200`). README prominently warns that the unofficial proxy violates Google's terms and can cause account bans (`README.md:27-39`).
- The callback server defaults to loopback and validates the callback path, but an operator-controlled bind override and remote heuristics can expose it beyond localhost (`src/plugin/server.ts:106-133,307-317`).

- Package metadata targets Node >=20, ESM, emits declarations/source maps to `dist`, and publishes only `dist`, README, and LICENSE (`package.json:1-35`; `tsconfig.build.json:1-13`). `prepublishOnly` runs the build (`package.json:36-46`).
- Runtime dependencies are narrowly identifiable: OpenCode plugin SDK, OpenAuth PKCE, Zod, file locking, and XDG path support (`package.json:48-65`).
- Vitest runs colocated `src/**/*.test.ts` tests in a Node environment (`vitest.config.ts:1-10`). The repository includes tests for storage, account rotation, refresh queues, request/response transforms, OAuth/auth behavior, config/schema, errors, logging, and UI (`src/plugin/*.test.ts`, `src/plugin/transform/*.test.ts`, `src/plugin/config/*.test.ts`).
- The refresh queue tests explicitly cover disabled, undefined-enabled, expired, and not-yet-expiring accounts (`src/plugin/refresh-queue.test.ts:17-174`). Build/typecheck and model/regression E2E scripts are declared in package metadata (`package.json:36-46`).
- Installation is direct OpenCode config registration using `opencode-antigravity-auth@latest` or `@beta`, followed by `opencode auth login` (`README.md:58-81`).

## Strengths

- Uses the OpenCode auth loader's custom-fetch contract effectively, preserving pass-through behavior for unrelated requests.
- Strong separation of provider registration, OAuth, transformation, storage, account selection, recovery, and configuration modules.
- Good operational resilience: endpoint fallback, quota-aware account rotation, bounded retries/backoff, proactive refresh, and session recovery.
- Credential persistence is unusually careful for a plugin: lockfile coordination, atomic writes, `0600`, migrations, deduplication, and delete-safe replacement.
- Documentation covers installation, model routing, architecture, configuration, multi-account behavior, troubleshooting, and legal/security risk.
- Broad colocated unit coverage tests both pure transformations and stateful edge cases.

## Pitfalls and Anti-Patterns

- `src/plugin.ts` is a 3,451-line god module with many unrelated responsibilities, making lifecycle reasoning and regression isolation difficult (`src/plugin.ts:1-3451`). A development bible should prefer smaller registration, transport, auth, and UI modules.
- Module-level mutable state (`activeAccountManager`, child-session flags, toast maps, warmup sets) can leak across plugin instances or concurrent sessions (`src/plugin.ts:73-93,123-169`). Prefer instance-scoped state returned by the factory unless process-wide sharing is intentional.
- Browser launching interpolates an OAuth URL into shell commands (`src/plugin.ts:245-265`). Even if the URL is generated internally, use an argument-safe spawn API rather than shell parsing.
- Several best-effort paths intentionally swallow errors, including TUI prompts and recovery continuation (`src/plugin.ts:1315,1327,1399-1402`; `src/plugin.ts:245-267`). This avoids crashes but can hide operational failures; structured debug context and metrics should accompany suppression.
- The configuration schema documents many environment overrides, but the shown loader only applies schema defaults plus JSON files and explicitly reads environment variables for path selection (`src/plugin/config/schema.ts:72-125`; `src/plugin/config/loader.ts:23-37,121-139`). Verify the separate runtime/environment handling before copying this contract.
- `loadAccounts` parses JSON and performs manual checks rather than validating the full persisted object with Zod (`src/plugin/storage.ts:595-659`). Malformed optional fields can survive farther into account logic.
- Auto-update is enabled by default and startup performs a remote version lookup (`src/plugin.ts:1229-1230,1263-1266`; `docs/CONFIGURATION.md:156-164`). This increases network and supply-chain surface; make update checks explicit, observable, and policy-controlled in production plugins.
- The plugin intentionally emulates third-party client headers and warns of terms-of-service/account-ban risk (`CHANGELOG.md:37-53`; `README.md:27-39`). This is not a generally reusable integration pattern without legal and security review.

## Reusable Lessons for a Development Bible

1. Register auth, events, and tools in one returned `PluginResult`, but keep each implementation in focused modules.
2. For provider adaptation, return a pass-through custom `fetch`; intercept only narrowly identified URLs and preserve the caller's `RequestInit`/abort behavior.
3. Put provider compatibility logic behind explicit transforms and allowlists; test request and streaming response transforms independently.
4. Treat OAuth refresh tokens as secrets: lock and atomically replace files, use restrictive permissions, migrate versions deliberately, and make destructive writes non-merging.
5. Make retry classification explicit, respect `Retry-After`, cap waits, add jitter, and distinguish account rotation from endpoint fallback.
6. Background intervals need idempotent start/stop behavior, serialized work, disabled-resource checks, and non-fatal per-item failures.
7. Scope mutable state to the plugin instance; if module globals are unavoidable, document lifecycle and concurrency assumptions.
8. Test the generated configuration schema alongside runtime defaults, and test auth, storage migration, quota selection, recovery, and transformations at their boundaries.
9. Default local callback servers to loopback and use safe process APIs for browser launching; treat bind overrides and remote exposure as explicit security decisions.
