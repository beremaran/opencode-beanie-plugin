## OpenCode integration patterns

- **Use both supported provider-loading paths when compatibility matters.** The plugin implements a `config` hook that eagerly discovers models for older OpenCode versions and a `provider.models` hook for newer versions (`src/plugin.ts:43-65`, `src/plugin.ts:120-145`). This is a useful migration pattern, but it also means model generation and metadata preservation must remain consistent across two lifecycle paths.
- **Keep auth setup in the OpenCode auth hook.** The plugin advertises an API-key method for provider `omniroute` and delegates credential loading to `loadProviderOptions` (`src/plugin.ts:150-160`). The loader rejects missing/non-API credentials with an actionable `/connect omniroute` message (`src/plugin.ts:163-174`).
- **Return a provider-specific fetch interceptor rather than globally patching fetch.** The loader returns `apiKey`, `baseURL`, and `fetch: createFetchInterceptor(config)` (`src/plugin.ts:195-199`). The interceptor merges request and init headers, adds authorization only for the configured base URL, and passes unrelated URLs through unchanged (`src/plugin.ts:871-909`).
- **Preserve user configuration while adding generated compatibility metadata.** The plugin stores raw user metadata in both a symbol and a serializable internal option, then merges user entries before generated entries (`src/plugin.ts:375-400`, `src/plugin.ts:479-524`). This addresses lifecycle cloning/serialization and first-match-wins behavior, but the internal option names become part of the effective provider options and should be treated as compatibility surface.
- **Shape dynamic models into OpenCode provider models.** `toProviderModel` supplies provider identity, API URL/npm adapter, modalities, capabilities, costs, limits, status, and variants (`src/plugin.ts:767-851`). The explicit defaulting policy is important: tools and temperature default to supported unless explicitly false, while vision/reasoning require positive evidence (`src/plugin.ts:778-786`).
- **Expose a separate runtime entrypoint.** `runtime.ts` exports model/cache/combo utilities and constants while the root entrypoint exports the plugin and types (`runtime.ts:1-33`, `index.ts:1-12`). This gives consumers an official programmatic API without making utility exports part of the root plugin loader contract.

## Source and reliability lessons

- **Validate untrusted API response shapes at runtime.** `/v1/models` responses are checked for an object with an array `data`, invalid model entries are filtered by string `id`, then normalization, deduplication, variant grouping, and enrichment run in sequence (`src/models.ts:316-342`). This is stronger than relying on the TypeScript response interface alone.
- **Use layered cache fallback.** The model cache is keyed by base URL, API key, and relevant models.dev configuration (`src/models.ts:35-50`); fresh cache is used within TTL, expired cache is returned after fetch failure, and built-in defaults are the last resort (`src/models.ts:275-364`). Clearing the model cache also clears combo state (`src/models.ts:376-387`).
- **Always clean up request timers.** Both model and combo fetches use `AbortController` plus `finally` to clear timers (`src/models.ts:296-308`, `src/models.ts:365-368`; `src/omniroute-combos.ts:71-81`, `src/omniroute-combos.ts:113-118`). The models.dev pipeline applies the same pattern per attempt (`src/models-dev.ts:144-217`).
- **Treat external metadata as optional enrichment.** models.dev fetches classify timeout/network/retryable HTTP/parse/structure failures, retry only transient classes, and use stale cache when all attempts fail (`src/models-dev.ts:83-98`, `src/models-dev.ts:131-139`, `src/models-dev.ts:220-293`). This avoids making a secondary catalog outage fatal to model discovery.
- **Normalize provider/model aliases before matching.** The model path reads camelCase, snake_case, and capability-object variants with explicit precedence (`src/models.ts:53-98`), deduplicates known aliases while preserving unknown prefixes (`src/models.ts:102-145`), and groups reasoning suffixes into OpenCode variants (`src/models.ts:171-225`). These transformations are directly reflected in tests (`test/models.test.mjs:286-354`, `test/models.test.mjs:356-415`).
- **Use conservative combo capabilities.** Combo enrichment resolves underlying models and calculates lowest-common capabilities after models.dev enrichment (`src/omniroute-combos.ts:256-316`, `src/omniroute-combos.ts:339-388`). This prevents advertising a capability that only one route supports, though unresolved models are excluded and only warned (`src/omniroute-combos.ts:284-305`), so operators should monitor those warnings.

## Security and pitfalls

- **Good: constrain auth interception by URL prefix.** The interceptor normalizes the base URL with a trailing slash before prefix matching, avoiding a simple sibling-path/domain-prefix mistake (`src/plugin.ts:875-883`). It also preserves caller headers before overriding authorization/content type (`src/plugin.ts:887-897`).
- **Good: do not log API response bodies or keys in the main model path.** Failed model requests log only status/status text and fallback state (`src/models.ts:310-313`, `src/models.ts:352-364`). Logging is asynchronous and disabled for debug unless `OMNIROUTE_DEBUG` is exactly `1` (`src/logger.ts:48-65`).
- **Good: sanitize Gemini tool schemas without mutating the caller payload.** The interceptor clones JSON before recursively removing schema keywords and only applies this to Gemini requests on chat/responses endpoints (`src/plugin.ts:922-965`, `src/plugin.ts:991-1044`).
- **Pitfall: cache keys contain the API key.** `getCacheKey` embeds the raw key in an in-memory string (`src/models.ts:35-50`). It is not written to disk by this code, but heap dumps, diagnostic tooling, or accidental cache-key logging would expose it. A keyed hash or per-credential object identity would reduce this exposure.
- **Pitfall: custom models.dev URLs are not validated like OmniRoute base URLs.** `getBaseUrl` permits only HTTP(S) for the primary endpoint (`src/plugin.ts:277-299`), but `modelsDev.url` is accepted as any non-empty string (`src/plugin.ts:324-350`) and fetched directly (`src/models-dev.ts:227-231`, `src/models-dev.ts:153-157`). A hostile or accidental config can therefore make the plugin contact arbitrary internal or local HTTP(S) endpoints. Validate scheme/host policy if this runs in a sensitive environment.
- **Pitfall: default capability assumptions can over-advertise.** Unknown models are treated as supporting tools and temperature unless explicitly false (`src/plugin.ts:779-784`). This improves compatibility but can cause request failures for providers whose metadata omits unsupported features; an explicit opt-in policy would be safer for heterogeneous backends.
- **Pitfall: secondary fetches add startup latency.** models.dev may perform three attempts at the configured timeout with 250 ms and 500 ms backoff, with the documented worst-case cold path around 15.75 seconds (`src/models-dev.ts:220-225`, `src/models-dev.ts:245-280`). Because the config hook eagerly fetches models when credentials are available (`src/plugin.ts:53-65`), this can affect plugin/config startup.
- **Pitfall: logging is best-effort and depends on an existing OpenCode log file.** The logger discovers the newest `.log` file and silently returns when the directory/file is absent or writes fail (`src/logger.ts:12-40`, `src/logger.ts:48-65`). This avoids disrupting OpenCode, but it can make production diagnosis incomplete.

## Testing lessons and gaps

- The project uses build-then-Node's built-in test runner (`package.json:23-29`). Tests cover config defaults, auth header scoping, model metadata overrides, Gemini schema sanitation, provider-hook discovery, cache behavior, fallback behavior, normalization, aliases, variants, and models.dev retry/stale-cache behavior (`test/plugin.test.mjs:57-170`, `test/plugin.test.mjs:172-354`, `test/models.test.mjs:63-147`, `test/models.test.mjs:286-354`, `test/models-dev.test.mjs:55-283`).
- Logger tests isolate `XDG_DATA_HOME`, use cache-busting imports, verify format/debug gating, missing directories, rotation, and permission failures (`test/logger.test.mjs:21-54`, `test/logger.test.mjs:54-172`, `test/logger.test.mjs:174-260`). This is a strong pattern for modules whose environment is captured at import time.
- `type-compat-test.ts` makes assignability to the OpenCode SDK `Model` type an explicit compile-time check (`type-compat-test.ts:1-5`). The TypeScript configuration enables strict mode, declarations, source maps, and NodeNext ESM (`tsconfig.json:1-27`).
- A notable gap is that `package.json` declares `@opencode-ai/plugin` only as a wildcard peer dependency and does not show a lockfile (`package.json:51-60`; `.gitignore:1-5`). Reproducible CI would benefit from a committed package-manager lockfile and a matrix or pinned compatibility test against supported OpenCode/plugin versions.
- The checked-in tests exercise the compiled `dist` tree and the test command builds first (`package.json:27-29`, `test/plugin.test.mjs:7-9`). That verifies the published-shaped output, but test discovery can be brittle if a consumer runs individual tests without the build step; the repository's `AGENTS.md` explicitly documents the required build-first workflow (`AGENTS.md:10-18`).
- There is no direct test shown for custom `modelsDev.url` validation, API-key absence in logs/cache diagnostics, URL edge cases involving query/fragment/base-path boundaries, or all combo endpoint response variants. These are high-value additions given the security and reliability concerns above.

## Packaging and release lessons

- The package is ESM, points `main`/`types` to `dist`, and uses explicit conditional exports for both root and `./runtime` (`package.json:2-16`). The published file list is intentionally narrow: `dist`, `README.md`, and `LICENSE` (`package.json:18-21`).
- `check:exports` enforces that the default and every root export are functions, matching the plugin loader constraint (`package.json:28-29`). `prepublishOnly` cleans, builds, and runs this validation (`package.json:29`). This is a useful packaging gate for OpenCode plugins, where an accidental root type/value export can prevent loading.
- The release documentation specifies PR/CI checks, annotated tags, GitHub releases, npm identity verification, prepublish validation, publish, and post-release npm/GitHub checks (`docs/release-process.md:1-64`). The README also documents the npm plugin config and restart/cache troubleshooting path (`README.md:21-55`, `README.md:376-385`).
- The declared Node floor is `>=20` (`package.json:58-60`), while the repository's development instructions use npm/Node commands (`AGENTS.md:10-18`). Consumers should verify that the OpenCode runtime's module loader and Node version satisfy this floor before relying on the package.

## Bottom line

This is a comparatively mature OpenCode provider/auth plugin pattern: it handles both provider lifecycle generations, scopes request interception, validates and normalizes dynamic model data, provides stale/default fallbacks, and tests the important integration seams. The main lessons for reuse are to preserve user config across lifecycle cloning, make published exports loader-safe, and treat enrichment as optional. The main risks to carry forward are raw API keys in cache-key strings, unrestricted custom metadata URLs, startup latency from eager retries, and optimistic capability defaults.
