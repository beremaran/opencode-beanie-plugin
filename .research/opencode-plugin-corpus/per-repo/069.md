## Architecture and OpenCode Patterns

### Minimal plugin composition

`PlanPlugin` is an intentionally small composition root: it obtains the bundled-skill config hook, registers the tool factory, and spreads system hooks into the returned plugin object (`index.ts:11-19`). Tool registration is centralized in `createTools`, which maps stable public names to per-tool factories carrying the shared context (`tools/index.ts:6-18`). This is a useful OpenCode pattern: keep SDK-facing wiring thin and isolate behavior in modules.

The shared context narrows the runtime surface to the project directory and the plugin shell helper (`types.ts:6-10`). Tool implementations import the SDK `tool` helper and schema builder directly, so descriptions and argument validation are exposed through OpenCode’s tool interface (`tools/create-plan.ts:6-20`).

### Filesystem-backed state with a stable Markdown format

Plans and specs are ordinary Markdown files below `docs/plans` and `docs/specs`; the README documents the layout and naming convention (`README.md:149-161`). `formatPlan` gives plans stable frontmatter, an idea section, an implementation list, and marker-delimited required specs (`utils.ts:65-83`). `formatSpec` gives specs a name heading and explicit scope (`utils.ts:91-98`). This makes state inspectable and editable outside the plugin while preserving enough structure for tool parsing.

The tools consistently check existence before create/update, create parent directories, write with `Bun.write`, and verify that a created file exists (`tools/create-plan.ts:33-42`, `tools/create-spec.ts:27-38`). `markPlanDone` preserves the existing plan body while normalizing frontmatter and changing only status (`tools/mark-plan-done.ts:25-39`).

### Prompt and skill integration

The system hook listens to `experimental.chat.system.transform`, enumerates plans, extracts the first eight lines of frontmatter, and appends an `<available_plans>` block to the system prompt (`hooks/system.ts:19-35`). This is a practical pattern for making repository-local workflow state discoverable without requiring the model to call a listing tool.

The bundled skill is packaged as Markdown and registered through the plugin config hook. Its resolver handles both compiled-local and source-relative locations (`skills/bundled.ts:23-37`), and registration merges/deduplicates paths into both `config.skills.paths` and `config.skill.paths` (`skills/bundled.ts:40-50`). The entrypoint returns this hook as `config` (`index.ts:11-17`). The skill itself encodes sequencing rules, including reading a plan before major work and performing `appendSpec` calls sequentially (`skills/plans-and-specs/SKILL.md:21-38`).

### Defensive merge logic

`appendSpec` uses explicit start/end markers and a shared parser rather than rewriting an entire plan semantically (`tools/shared.ts:8-42`). `writeWithMerge` retries up to five times, rereads the file before each merge, avoids duplicate links, writes, and rereads to verify that the requested spec is present (`tools/shared.ts:52-79`). The tool description also tells agents not to batch these calls (`tools/append-spec.ts:11-17`). This is a useful best-effort approach for concurrent agent writes, although it is not an atomic compare-and-swap.

## Security and Reliability Findings

### High: linked spec names are not revalidated before path resolution

User-facing tool arguments are validated with `validateName` before calls to `getPlanPath`/`getSpecPath` (`tools/append-spec.ts:19-33`, `tools/read-plan.ts:17-23`). However, `readPlan` parses arbitrary spec names from the plan’s marker block and passes each directly to `getSpecPath` (`tools/read-plan.ts:36-45`). `getSpecPath` sanitizes filesystem separator characters, resolves the path, and checks that it starts with the base directory (`utils.ts:31-44`), but it does not call `validateName`. A manually edited or malicious plan can therefore cause unexpected sanitized filenames to be read from `docs/specs` (and the prefix check is string-based rather than a path-boundary check). Lesson: validate parsed references against the same strict allowlist as tool input, and use a boundary-safe containment check such as `relative(base, target)`.

### Medium: prompt metadata is interpolated without escaping

Plan basenames and frontmatter descriptions are inserted directly into `<name>` and `<description>` elements (`hooks/system.ts:10-15`, `hooks/system.ts:27-34`). Although normal tool-created names are restricted, descriptions are free-form and plans are editable Markdown. A description containing markup can break the generated structure or inject additional prompt-like elements. Lesson: XML/HTML-escape values, or use a clearly delimited non-XML representation with a robust serializer.

### Medium: directory containment check is incomplete as a general utility

`getSecurePath` checks `target.startsWith(fullBase)` (`utils.ts:31-39`). This rejects ordinary traversal after the current sanitization, but it is not a complete containment test for sibling prefixes such as `/work/docs/plans` versus `/work/docs/plans-other`, and callers must remember to validate names separately. The repository guidance calls these helpers security-critical (`AGENTS.md:30-38`, `AGENTS.md:55-58`), so the utility itself should enforce the invariant rather than relying on every caller.

### Medium: writes can lose updates despite retry logic

The merge loop rereads and verifies, but the write is still a separate unconditional `Bun.write` with no lock or atomic rename (`tools/shared.ts:52-78`). Two writers can both read the same state and then overwrite one another; verification only proves that the last writer’s spec exists. The sequential-call instruction reduces agent collisions (`skills/plans-and-specs/SKILL.md:21-27`) but does not protect external or concurrent callers. Lesson: use an OS-level lock, atomic compare-and-swap strategy, or document the single-writer requirement as a hard runtime constraint.

### Low: format and behavior rules drift between prose and implementation

The tool description and bundled skill say descriptions must be 3-5 words (`tools/create-plan.ts:14-19`, `skills/plans-and-specs/SKILL.md:34-38`), while the implementation accepts 3-10 words (`tools/create-plan.ts:24-26`). The README’s example and workflow are otherwise consistent with the generated format (`README.md:86-147`). Lesson: keep agent-facing instructions and executable validation in one source of truth.

## Testing and Verification

- No test files are present in the tracked clone, and `package.json` defines no `test` script (`package.json:8-13`; tracked file inventory contains only source/config/docs/package files).
- The available check is `npm run lint`, which runs `tsc --noEmit`; strict mode is enabled in `tsconfig.json` (`package.json:8-13`, `tsconfig.json:2-12`). This provides type checking, not behavioral coverage.
- High-value missing tests include: traversal and sibling-prefix cases for path helpers; malformed/missing spec markers; duplicate and concurrent `appendSpec` updates; malformed frontmatter; XML-sensitive descriptions in system prompt output; missing linked specs; and bundled skill path resolution in both source and built layouts.
- The `readPlan` behavior of returning `(NOT FOUND)` for a missing linked spec is explicit (`tools/read-plan.ts:39-49`) and should be covered as a degraded-but-readable workflow.

## Packaging and Configuration

`package.json` declares an ESM package with `dist/index.js` and declarations as its public entrypoints, includes `dist`, `skills`, README, and LICENSE, and builds by compiling TypeScript then copying `skills` into `dist` (`package.json:1-12`, `package.json:28-35`). This correctly addresses the bundled-skill runtime dependency, provided the build is run before publishing. The source repository, however, has no tracked `LICENSE` file in the audited inventory even though `files` includes it; packaging should add the file or remove the stale inclusion.

The plugin depends on `@opencode-ai/plugin: latest` and uses latest TypeScript/Bun types (`package.json:34-40`), while the lockfile records older package metadata (`package-lock.json:1-20`). Pinning compatible release ranges and keeping one authoritative lockfile would improve reproducibility. Both `bun.lock` and `package-lock.json` are present, while `.gitignore` ignores `bun.lock` (`.gitignore:1-5`), indicating mixed package-manager history.

The checked-in `opencode.jsonc` is explicitly a developer-only configuration pointing at a machine-specific absolute path (`opencode.jsonc:1-5`). It is useful as a local example but should not be treated as a portable consumer configuration. The README’s package installation example is the portable path (`README.md:43-63`).

## Takeaways

- Keep OpenCode entrypoints declarative and delegate tool behavior to factories; this repository’s `index.ts` and `tools/index.ts` are a clean example.
- Markdown plus strict, documented markers is an effective inspectable persistence format for plans and specs.
- Bundled skills need explicit build-time copying and runtime path discovery; both are handled here, with dual config key registration for compatibility.
- Agent-facing sequencing instructions can reduce races, but should be backed by atomic filesystem coordination and tests.
- Treat every plan/spec file as untrusted input: validate parsed names, enforce path containment in the utility, escape prompt metadata, and test malformed hand-edited files.
- Publish only after checking package `files` against actual tracked artifacts, aligning lockfiles/version metadata, and removing machine-specific config from the distributable guidance.
