## Summary

This is a read-only OpenCode TUI sidebar plugin for OpenAI subscription quota, Z.AI/GLM quota, and DeepSeek balance. The server entrypoint is intentionally a no-op (`src/index.ts:1-8`); the user-visible behavior is exposed through the TUI plugin entry `usage-monitor:tui` (`src/tui.ts:407-410`). The design separates provider API parsing, normalized snapshots, credential resolution, refresh coordination, cache storage, and presentation. The strongest reusable pattern is a typed, validated provider boundary that prevents raw provider responses or credentials from reaching rendering and persistent cache.

## OpenCode Integration Patterns

- **Separate server and TUI exports.** `package.json:7-19` exposes `dist/index.js` as the main import, `dist/tui.js` as `./tui`, and declares the TUI plugin via `oc-plugin: ["tui"]`. The server plugin only returns `{}` (`src/index.ts:3-8`), while the TUI module registers sidebar content and a refresh command (`src/tui.ts:532-588`). This is a useful pattern for extensions whose functionality is entirely host-UI based.
- **Use the host lifecycle for cleanup.** The TUI registers `api.lifecycle.onDispose` to cancel debounced config reloads, close the filesystem watcher, unsubscribe refresh state, dispose the coordinator, and unregister the command (`src/tui.ts:523-530`). This avoids leaving timers, watchers, subscriptions, or in-flight provider work behind.
- **Register content through a sidebar slot.** The plugin registers `sidebar_content` with an explicit order (`src/tui.ts:532-558`), and calls `api.renderer.requestRender()` after state changes (`src/tui.ts:436-454`). It also catches render failures and emits a bounded in-TUI error (`src/tui.ts:548-554`).
- **Expose commands through the TUI API.** The refresh action has a stable value, slash name, category, keybind, success toast, and sanitized failure toast (`src/tui.ts:560-588`).
- **Watch configuration without rebuilding the plugin.** `usage-monitor.json` is watched and reloads are debounced by 100 ms (`src/tui.ts:491-499`, `src/tui.ts:592-606`); a fingerprint avoids work for equivalent settings (`src/tui.ts:457-461`, `src/config.ts:81-83`). The documented limitation is that only the dedicated file is watched, not the secondary `oh-my-openagent.json` source (`MAP.md:117-122`).
- **Use a normalized provider contract.** Provider adapters fetch and parse provider-specific data, then return `StandardUsageProvider` objects (`src/providers/types.ts:82-127`). The architecture explicitly keeps raw response shapes out of formatters, views, and TUI code (`MAP.md:30-42`).

## Configuration And Activation

- **Fail closed on configuration.** Only version 2 is accepted; v1-shaped fields are detected and rejected (`src/runtime-config.ts:174-192`, `src/runtime-config.ts:456-458`). Unknown keys, malformed provider entries, invalid refresh bounds, and invalid credential references produce structured issues (`src/runtime-config.ts:195-240`, `src/runtime-config.ts:256-295`, `src/runtime-config.ts:344-355`).
- **Provider presence is the activation switch.** The README states that presence under `providers` enables work and omission prevents credential, cache, and network activity (`README.md:170-172`). The TUI does not create a coordinator when config is invalid or empty, instead rendering a synthetic `config` provider row (`src/tui.ts:282-305`, `src/tui.ts:386-400`).
- **Reject interpolation and secret-like options.** Credential names are constrained to allowlisted patterns and reject `${...}` interpolation (`src/runtime-config.ts:267-295`). Recursive option validation rejects secret-looking fields and limits nesting (`src/runtime-config.ts:315-329`). This is a good defense for config-driven plugins that otherwise risk environment-variable or credential injection.
- **Bound refresh and UI resource usage.** Automatic intervals must be at least 60 seconds and timeouts/stale windows have explicit upper and lower bounds (`src/runtime-config.ts:61-71`, `src/runtime-config.ts:344-355`). UI width is also bounded to 20-120 (`src/runtime-config.ts:332-341`).

## Credential And Security Lessons

- **Resolve only provider-allowlisted sources.** The resolver checks both allowed source types and exact default candidate names before reading anything (`src/credentials.ts:180-205`). A configured reference cannot select an arbitrary environment variable or auth entry.
- **Treat OpenAI OAuth metadata as a separate contract.** OpenAI requires `type: "oauth"`, a non-empty access token, account ID, and a future expiry (`src/auth.ts:177-197`). The provider then rechecks source, variant, expiry, and account ID before making the request (`src/providers/openai.ts:87-104`). Refresh tokens are not selected by `extractToken` (`src/auth.ts:39-50`).
- **Sanitize auth data before use.** Auth JSON is parsed as a plain object and reduced to a fixed set of string fields, finite expiry, and string metadata (`src/auth.ts:253-287`). Auth paths require absolute OS-appropriate bases and deduplicate candidates (`src/auth.ts:53-85`).
- **Redact both known patterns and the active credential.** Error sanitization removes token/key/Bearer patterns and truncates to one line (`src/sanitize.ts:1-24`); credential-aware sanitization first replaces the exact arbitrary credential (`src/sanitize.ts:26-31`). Snapshot validation also rejects values containing the active credential (`src/snapshot-validation.ts:44-60`, `src/snapshot-validation.ts:91-95`).
- **Do not expose provider dumps.** Snapshot detachment rejects secret-bearing keys, unknown provider/window/detail fields, oversized/deep values, and non-plain objects (`src/snapshot-validation.ts:119-163`, `src/snapshot-validation.ts:190-201`, `src/snapshot-validation.ts:352-362`). The tests explicitly reject an `apiKey` detail and non-canonical windows (`src/__tests__/provider-contract.test.ts:51-79`).
- **Protect cache contents and identity.** Persistent cache scope is derived from non-secret account metadata and validated before use (`src/refresh-schedule.ts:126-149`). Null-scope data remains memory-only (`src/provider-cache.ts:123-142`). Disk writes require a private, user-owned temp-directory descendant, mode `0700` directory and `0600` files, `O_NOFOLLOW`, atomic replacement, and directory sync (`src/provider-cache.ts:264-275`, `src/provider-cache.ts:328-346`, `src/provider-cache.ts:370-426`).
- **Use epochs and commit gates against stale work.** Credential changes increment epochs (`src/credentials.ts:281-305`), refresh operations carry generation/request/credential/scope identity (`src/refresh.ts:332-367`), and commits are accepted only when the gate still matches current state (`src/refresh.ts:628-657`). Reconfiguration aborts operations and invalidates resolution sequences (`src/refresh.ts:103-133`, `src/refresh.ts:744-756`).

## Provider And Rendering Lessons

- **Use official endpoints and map into safe semantics.** OpenAI uses the ChatGPT WHAM usage endpoint with account ID headers (`src/providers/openai.ts:31-69`, `src/providers/openai.ts:105-138`); Z.AI uses the documented quota endpoint and enterprise headers when both IDs are configured (`src/providers/zai.ts:16-18`, `src/providers/zai.ts:96-136`); DeepSeek uses its balance endpoint (`src/providers/deepseek.ts:15-48`, `src/providers/deepseek.ts:62-85`).
- **Represent balance as balance, not a fake reset window.** DeepSeek emits no windows and uses typed currency details for total, granted, and topped-up balance (`src/providers/deepseek.ts:136-168`). The architecture documents this as a rule for balance-only providers (`AGENTS.md:46-53`).
- **Preserve partial data.** OpenAI and Z.AI return `partial` when parseable data is incomplete rather than failing the entire provider (`src/providers/openai.ts:221-233`, `src/providers/zai.ts:287-297`); DeepSeek likewise reports `partial` for missing balance or unavailable API access (`src/providers/deepseek.ts:136-159`).
- **Separate presentation from provider data.** Provider-specific view models are selected before formatting (`src/tui.ts:113-124`, `src/tui.ts:162-184`). The TUI provides collapsed panel, collapsed provider, and expanded detail states without mutating provider snapshots (`src/tui.ts:127-137`, `src/tui.ts:501-520`).

## Testing Lessons

- **The suite is broad and contract-oriented.** There are focused tests for auth, credentials, config, cache, layout, lifecycle, provider contracts/registry/catalog, refresh, snapshot validation, native providers, and views (repository files under `src/__tests__/`). Contract tests cover freezing accepted snapshots and rejecting invalid/secret-bearing data (`src/__tests__/provider-contract.test.ts:14-79`), while lifecycle tests verify balance rendering and actionable config errors (`src/__tests__/tui-lifecycle.test.ts:37-77`).
- **Test pure boundaries with deterministic fixtures.** Provider normalization functions accept explicit timestamps (`src/providers/openai.ts:188-191`, `src/providers/zai.ts:260-260`, `src/providers/deepseek.ts:136-136`), and the refresh coordinator accepts injected clock/timer abstractions (`src/refresh-schedule.ts:38-50`, `src/refresh.ts:764-769`). This makes timing, stale state, and refresh races testable without sleeping.
- **Run declared CI gates.** CI runs frozen Bun installation, typecheck, tests, then build; publish waits on all three (`.gitlab-ci.yml:9-14`, `.gitlab-ci.yml:15-46`). The package scripts similarly define `build:all`, `test`, and `typecheck` (`package.json:24-32`).
- **Observed verification caveat:** in this clone, `bun test` reported 214 passing tests but 3 failures/errors because `@opentui/solid` could not be resolved from `src/tui.ts`; `bun run typecheck` also reported missing `@opentui/solid` and `solid-js`. The package declares these as peer dependencies (`package.json:56-64`), so the repository’s local test/typecheck commands are not self-contained unless peer dependencies are installed. CI may obtain them through the project lockfile/environment, but this checkout did not.

## Packaging And Maintenance Pitfalls

- **Build output is intentionally split.** `build:all` builds the server entry, TUI bundle, and declarations (`package.json:24-30`), while `files: ["dist"]` restricts the npm payload (`package.json:21-23`). The root `tui.ts` re-exports `src/tui.js` for local/plugin compatibility (`tui.ts:1`).
- **Do not rely on `prepublishOnly` to build.** The package explicitly skips building during publish because CI is expected to provide `dist/` (`package.json:31-32`); this makes release ordering and artifact transfer a hard requirement.
- **Peer dependency completeness matters.** The TUI imports `@opencode-ai/plugin/tui`, `@opentui/solid`, and `solid-js`, and the keymap peer is declared for runtime integration (`src/tui.ts:1-5`, `package.json:56-60`). Missing peer installation prevents even unrelated TUI tests from loading.
- **Version documentation can drift.** `package.json` says version `2.0.1` (`package.json:3-5`), while repository guidance labels itself version `2.0.0` (`AGENTS.md:1-3`). Release documentation should derive version references from one source.
- **Private/unstable API dependency needs monitoring.** The README and architecture map call out the OpenAI WHAM response as private/undocumented (`MAP.md:117-120`), despite the provider maintaining a defensive parser. Provider API changes should be covered by fixtures and surfaced as `partial` rather than silently misrepresented.

## Bottom Line

The most transferable OpenCode pattern is a thin TUI integration around a strongly validated runtime core: versioned fail-closed config, allowlisted credentials, official API adapters, canonical typed snapshots, account-safe cache identity, cancellation/epoch commit gates, and lifecycle cleanup. The main operational weakness observed here is packaging/test ergonomics: peer dependencies required by the TUI are not installed in the analyzed clone, so the advertised `bun test` and `bun run typecheck` commands do not pass in that environment despite substantial passing coverage.
