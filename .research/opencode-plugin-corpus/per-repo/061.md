## OpenCode patterns

- **Loader-compatible module wrapper.** `src/plugin.ts:1-8` imports the package name, exports the plugin, and default-exports `{ id, server }`, satisfying the modern `PluginModule` shape. `package.json:5-20` provides ESM main/types fields plus `.`/`./server`/`./tags` exports. This is a useful pattern for plugins that need both OpenCode loading and public helper subpaths.
- **Hook-driven integration.** The plugin returns `config`, `chat.message`, `chat.params`, `tool.memory`, and `event` handlers (`src/index.ts:425-430`, `src/index.ts:540-585`). `chat.message` saves prompts, conditionally injects synthetic memory context, excludes the current session, and applies age/count limits (`src/index.ts:449-521`). `chat.params` records the active provider/model for later capture (`src/index.ts:540-551`).
- **Idle/compaction lifecycle.** `event` handles `session.idle` with a 10-second debounce, skips internal structured-output sessions, then runs capture/profile/cleanup (`src/index.ts:909-940`). `session.compacted` resolves the active agent before injecting memory with `noReply`, avoiding an agent reset (`src/index.ts:942-999`).
- **Explicit tool contract.** The `memory` tool exposes a finite `mode` enum and optional typed arguments for add/search/profile/list/forget/migrate/list-shards/export/import (`src/index.ts:554-585`). README examples document the same modes and scopes (`README.md:115-129`).
- **Configuration as a user-owned JSONC file.** Defaults are centralized, including project-scoped search, loopback web binding, bounded capture budgets, compaction, and chat injection (`src/config.ts:104-206`). The plugin creates `~/.config/opencode` and `~/.opencode-mem` at module load (`src/config.ts:8-21`), so import-time filesystem side effects are part of its operational contract.
- **Public interoperability helper.** The `opencode-mem/tags` export is intentionally documented for third-party plugins; it avoids incompatible hand-built shard tags (`README.md:427-458`, `package.json:13-20`).

## Security lessons and pitfalls

- **Treat client-derived shard identifiers as path input.** The repository's security audit records a prior critical traversal through unsanitized `containerTag` parsing and shard-path creation (`SECURITY_AUDIT.md:9-15`). The current guard requires a 16-character lowercase hex scope hash (`src/services/memory-scope.ts:1-11`, `src/services/memory-scope.ts:17-37`), and the connection layer has a regression test rejecting paths outside `storagePath` (`tests/turso-connection-manager.test.ts:114-123`). Validate at every boundary, including migration paths, rather than relying only on generated tags.
- **CORS is not authentication.** The audit explicitly documents that no `Origin` permits curl/local-process access and that CORS alone was insufficient (`SECURITY_AUDIT.md:17-23`). The current request path checks HTTP Basic Auth and then requires a generated API token for non-health `/api/*` requests (`src/services/web-server.ts:326-357`). No-origin requests remain allowed by the CORS predicate (`src/services/cors.ts:15-29`), which is acceptable only because the token/auth gates are enforced separately.
- **Fail closed for network exposure.** Non-loopback binding without either `webServerApiToken` or enabled Basic Auth throws at startup (`src/services/web-api-auth.ts:7-17`); the behavior is covered by tests for `0.0.0.0`, bearer tokens, and the custom token header (`tests/web-api-auth.test.ts:15-40`). README also tells users to keep the host on `127.0.0.1` unless deliberately exposing it (`README.md:129-133`).
- **Protect persisted secrets.** The generated token uses 32 random bytes, is stored under `~/.opencode-mem/.auth-token`, and is created with mode `0600` (`src/services/auth-token.ts:6-8`, `src/services/auth-token.ts:19-43`). `file://` secrets are read from disk with a permission warning when group/other bits are set; `env://` secrets are resolved without returning them through API handlers (`src/services/secret-resolver.ts:15-79`, `SECURITY_AUDIT.md:41-47`).
- **Bundle browser assets.** The audit identifies the former CDN/no-SRI issue and records the Vite-bundled UI as the mitigation (`SECURITY_AUDIT.md:31-35`). `package.json:22-31` makes the web build part of `build`, while the package allowlist publishes only `dist` and `package.json` (`package.json:81-84`).
- **Avoid recursive internal sessions.** Structured summary messages and tracked internal capture sessions are excluded from normal capture (`src/index.ts:38-46`, `src/index.ts:442-447`), and idle handling repeats the exclusion (`src/index.ts:916-921`). This is an important guard for plugins that create their own OpenCode sessions.
- **Residual risk documented by the project.** The audit notes that a LAN attacker who can read the token file or intercept the token injected into the HTML can still obtain it, and recommends an additional warning/refusal for non-loopback exposure (`SECURITY_AUDIT.md:49-51`). Gemini's API key is sent in a URL query parameter because that is the provider API's design (`SECURITY_AUDIT.md:37-39`); this remains a disclosure/logging consideration.

## Testing lessons

- **Test the host contract, not only business logic.** `tests/plugin-loader-contract.test.ts:21-64` checks JSON import attributes, ESM output, the `./server` export, default export shape, non-empty package-matching id, and callable `server`. It also checks hook keys when invocation succeeds (`tests/plugin-loader-contract.test.ts:66-109`).
- **Keep native-runtime tests deterministic.** The loader test marks the process-global warmup complete to avoid loading ONNX during contract assertions because Bun teardown can crash after the native addon loads (`tests/plugin-loader-contract.test.ts:72-80`). This separates cheap contract tests from embedding/runtime smoke tests.
- **Use focused regression tests for security and portability.** Coverage includes Basic Auth challenge and credential edge cases (`tests/web-auth.test.ts:54-153`), Windows path normalization (`tests/windows-path.test.ts:1-90`), foreign-key setup and storage-root containment (`tests/turso-connection-manager.test.ts:102-123`), config/provider validation (`tests/config.test.ts:26-229`, as indexed by the test file), and dependency invariants (`tests/package-dependencies.test.ts:4-24`).
- **Test published dependency constraints explicitly.** The dependency test prevents accidental replacement of libSQL/Transformers and enforces the direct plus override pin for `onnxruntime-node@1.20.1` (`tests/package-dependencies.test.ts:4-24`). The package repeats the rationale: nested OpenCode installs can ignore overrides and newer versions have Intel Mac/Bun teardown issues (`package.json:52-66`).
- **Verification caveat.** `SECURITY_AUDIT.md:53-56` reports typecheck and test verification, but also records environment-dependent failures involving permissions and missing `dist/plugin.js`. Consumers should run `bun run build` before tests that import built output; this follows the declared build/test scripts (`package.json:22-30`).

## Packaging and maintenance

- The package is ESM (`package.json:5`), builds declarations/maps into `dist` (`tsconfig.json:9-18`), and uses strict TypeScript checks including `noUncheckedIndexedAccess` and `noFallthroughCasesInSwitch` (`tsconfig.json:19-25`).
- `build` removes `dist`, runs `tsc`, then builds the web application; `typecheck`, `test`, formatting, and Husky preparation are all declared scripts (`package.json:22-31`). The pre-commit hook runs typecheck and lint-staged (`.husky/pre-commit:1`).
- Publishing is intentionally narrow (`dist` and `package.json` only) and public MIT metadata is declared (`package.json:43-50`, `package.json:81-84`). README points to an MIT license file (`README.md:473-478`), but no `LICENSE*` file was present in the inspected clone; release consumers should verify the published tarball contains the intended license text.
- Native dependencies need an explicit compatibility policy. The README explains the Intel `darwin/x64` pin, nested OpenCode cache behavior, and remote-embedding fallback (`README.md:235-237`, `README.md:419-425`). This is a strong example of documenting runtime-specific packaging constraints alongside the dependency pin rather than hiding them in lockfile state.
- The audit header identifies a different audited commit (`0998c69`) than the manifest-pinned clone head (`SECURITY_AUDIT.md:1-5` versus `repo-map.json:937-949`). Treat the audit as repository-provided historical/security evidence, but revalidate its claims against the manifest head before using it as a release attestation.

## Overall assessment

`opencode-mem` demonstrates a broad, well-factored OpenCode plugin architecture with practical lifecycle hooks, a constrained tool schema, explicit loader compatibility tests, and unusually visible security hardening. The main operational hazards are import-time filesystem setup, native ONNX/Bun/platform coupling, and the complexity of securing a web API that can be deliberately rebound to the LAN. Its strongest reusable lessons are to validate every identifier that can reach a filesystem path, separate CORS from authentication, test the actual published loader shape, and pin/document native dependencies with platform-specific smoke coverage.
