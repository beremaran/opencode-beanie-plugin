# Repository 014: Context Analysis

## Identity and scope

- Manifest index: `14`, name `Context Analysis`, URL `https://github.com/IgorWarzocha/Opencode-Context-Analysis-Plugin` (manifest `clone-results-0-48.json:198-208`).
- Clone path: `.research/opencode-plugin-corpus/repos/igorwarzocha--opencode-context-analysis-plugin/`; manifest reports no subdirectory and a successful clone at commit `3676b9f213298780cfbc0b8c5dbbb33980308885` (`clone-results-0-48.json:203-208`).
- The clone is small: README, `package.json`, `.opencode/command/context.md`, `.opencode/plugin/context-usage.ts`, tokenizer registry/config/type declaration, and one test. No separate OpenCode config file or lifecycle-hook implementation is present.

## SDK and registration

- The entrypoint imports the OpenCode `Plugin` type and `tool` helper from `@opencode-ai/plugin` (`.opencode/plugin/context-usage.ts:1-2`). It exports `ContextUsagePlugin` as an async `Plugin` factory receiving `{ client }` (`context-usage.ts:76`).
- Registration is returned from the factory as a `tool` map with one `context_usage` tool (`context-usage.ts:77-85`). The tool receives the current session context and falls back to `context.sessionID` when no explicit session is supplied (`context-usage.ts:86-90`).
- The tool calls the SDK client’s session-message endpoint with `{ path: { id: sessionID } }`, then tolerates either `response.data` or a direct response (`context-usage.ts:90-92`). This is a useful pattern for keeping the plugin focused on SDK access while normalizing response shape at the boundary.
- No hooks, events, middleware, or startup/shutdown handlers are registered. The only plugin surface is the returned `tool` object (`context-usage.ts:76-117`).

## Commands and tool behavior

- `.opencode/command/context.md` defines `/context` with a description and instructs OpenCode to call `context_usage` directly, without delegating (`.opencode/command/context.md:1-7`). It passes `$ARGUMENTS` into a requested bullet-summary format (`context.md:9`).
- Tool arguments are optional `sessionID` and integer `limitMessages` constrained to 1..10 (`context-usage.ts:81-85`). The default entry limit is 3 (`context-usage.ts:10`, `context-usage.ts:106-111`).
- The implementation categorizes system prompts, user text, assistant text, completed tool output, and reasoning (`context-usage.ts:128-140`). Tool output is grouped by tool name and accumulated across messages (`context-usage.ts:268-289`); text parts are trimmed and joined (`context-usage.ts:307-314`).
- It selects the latest assistant token telemetry with nonzero usage, then scales measured categories to provider-reported input/output/reasoning/cache totals (`context-usage.ts:316-359`). The rendered result includes category percentages, counts, total tokens, and up to ten top contributors (`context-usage.ts:515-585`).
- The README documents both standard and free-form verbosity arguments, session selection, and message limiting (`README.md:97-125`), but the command itself only forwards the argument text; the source tool only defines the two structured arguments (`context.md:9`, `context-usage.ts:81-85`). Consumers should not assume every README example is parsed into a dedicated option.

## Auth and providers

- There is no authentication flow or provider credential handling. Provider/model identifiers come from session message metadata (`context-usage.ts:18-25`) and are used only to select a tokenizer.
- The registry treats `openai`, `azure`, and `opencode` as OpenAI-compatible providers (`tokenizer-registry.mjs:7`, `77-86`). It otherwise resolves direct OpenAI aliases, transformer aliases, provider defaults, and finally a closest alias suggestion (`tokenizer-registry.mjs:88-107`, `136-145`).
- Provider defaults are loaded from `.opencode/plugin/tokenizer-aliases.json` and can also be inferred from model-name patterns for Anthropic, Meta, Mistral, DeepSeek, and Google (`tokenizer-registry.mjs:247-272`). The checked-in alias map provides concrete transformer hubs for those providers (`tokenizer-aliases.json:2-36`).
- Model/provider keys are normalized to lowercase, with whitespace/underscores converted to hyphens for model IDs (`tokenizer-registry.mjs:350-357`). OpenAI lookup also handles `-latest` and colon-qualified IDs (`tokenizer-registry.mjs:110-122`).

## State, processes, and dependencies

- Runtime state is process-local: tokenizer encoders, transformer tokenizers, and the registry are cached in module-level maps/promises (`context-usage.ts:71-74`, `tokenizer-registry.mjs:9-10`). There is no persisted session state or background process.
- The registry lazily reads vendored package metadata from `.opencode/plugin/vendor/node_modules`; it searches several known JSON paths and falls back to built-in OpenAI aliases or the checked-in manifest (`tokenizer-registry.mjs:288-307`, `379-388`).
- Token counting supports tiktoken, Hugging Face transformers, and an approximate four-characters-per-token fallback (`context-usage.ts:430-455`). Dynamic imports are resolved from each vendored package’s `module`, `main`, or `index.js` entry (`context-usage.ts:472-512`).
- `package.json` is minimal and declares only `@opencode-ai/plugin: latest`, with ESM enabled (`package.json:1-8`). The actual tokenizer libraries are intentionally outside package metadata and are installed under the plugin-local vendor directory (`README.md:134-145`, `149-154`).

## Configuration and installation

- Configuration is file-based rather than an OpenCode JSON schema: tokenizer aliases/providers live in `.opencode/plugin/tokenizer-aliases.json` (`tokenizer-registry.mjs:309-317`; `tokenizer-aliases.json:1-37`).
- Installation is a copy-based model: clone the repository and copy `.opencode` into a project, or copy it into the global OpenCode config directory (`README.md:13-27`, `66-82`). The README says no build step is required because TypeScript runs directly in OpenCode (`README.md:170-178`).
- The documented manual dependency command installs `js-tiktoken` and `@huggingface/transformers` with `--prefix .opencode/plugin/vendor` (`README.md:147-154`). The source’s missing-dependency error instead references `./context-command/install.sh` (`context-usage.ts:499-507`) and its user-facing tokenizer error references `./install.sh` (`context-usage.ts:592-607`); no such script is present in the inspected clone. This is an installation/documentation mismatch.
- The README’s global destination is shown as `~/.config/opencode/.opencode/`, while its copy command is `cp -r .../.opencode ~/.config/opencode/` (`README.md:75-89`). Users should verify the resulting layout rather than rely on the table wording.

## Errors and security/privacy

- Missing session IDs produce an explicit error; empty sessions return a useful message (`context-usage.ts:87-95`). Unknown tokenizer resolution is converted into a user-facing report listing observed models/providers (`context-usage.ts:97-105`, `592-609`).
- `TokenizerResolutionError` preserves model and provider evidence as arrays, which makes failures diagnosable without exposing full message contents (`tokenizer-registry.mjs:11-17`, `57-63`).
- Tokenizer loading falls back rather than failing for many runtime tokenizer errors: tiktoken uses `cl100k_base` if model encoding lookup fails, and both tokenizer paths use approximate counting if encoding fails (`context-usage.ts:458-469`, `430-455`). Reports should therefore be treated as estimates when the exact tokenizer is unavailable.
- The README explicitly claims token counting is local and that no data is sent to external services (`README.md:140-145`). However, Hugging Face `AutoTokenizer.from_pretrained(hub)` is invoked for transformer models (`context-usage.ts:479-489`), so model asset retrieval/network behavior depends on the transformer library/cache environment. The source does not add a network policy, integrity check, or explicit secret handling layer.
- Broad `catch` blocks intentionally convert dependency/file/tokenizer failures into fallbacks or nulls (`tokenizer-registry.mjs:311-317`, `320-330`; `context-usage.ts:481-489`, `499-507`). This improves resilience but can hide root causes; logging/diagnostic mode would be a reusable improvement.

## Tests and package/install evidence

- The only test file is `tests/tokenizer-resolution.test.mjs`, using Node’s built-in `node:test` and strict assertions (`tests/tokenizer-resolution.test.mjs:1-2`). It covers vendored OpenAI metadata, provider-derived transformer defaults, nearest-alias suggestions, and descriptive unknown-model errors (`tests/tokenizer-resolution.test.mjs:54-105`).
- Test setup deletes `.opencode/plugin/vendor/node_modules` and recreates fixture JSON before each test (`tests/tokenizer-resolution.test.mjs:18-52`). This makes the test self-contained but mutates the clone, so it was inspected rather than executed for this report in accordance with the no-clone-modification constraint.
- Tests cover the registry, not the OpenCode plugin factory, SDK response normalization, category aggregation, telemetry scaling, output formatting, command discovery, or missing-dependency UX. Those are the highest-value gaps for future regression coverage.

## Pitfalls and reusable lessons

- Keep plugin registration minimal and return a plain `tool` map from the factory; use the injected client and execution context instead of reaching for global OpenCode state (`context-usage.ts:76-117`).
- Normalize external model/provider identifiers and use a deterministic resolution order with explicit diagnostics (`tokenizer-registry.mjs:20-64`, `350-357`).
- Isolate optional/heavy dependencies in a plugin-local vendor directory and lazy-load/cache them (`context-usage.ts:458-512`). This reduces startup cost and avoids changing the host project’s dependency tree, but requires an accurate installer and clear failure path.
- Preserve exact provider telemetry where available, but label fallback/scaled counts as estimates. This implementation’s scaling and approximate fallback are practical, yet they can make visual precision look stronger than the underlying measurement (`context-usage.ts:316-397`, `430-455`).
- Keep command instructions aligned with actual tool arguments and shipped files. Here, free-form command guidance, missing install-script references, and limited test coverage are the main integration pitfalls (`context.md:5-9`, `README.md:101-125`, `context-usage.ts:499-507`).
