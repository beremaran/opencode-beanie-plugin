## What It Does

`opencode-snippets` expands `#name` references inline in user prompts, recursively composes snippets, supports frontmatter aliases, and can inject prepend/append/context blocks. The README explicitly distinguishes snippets from slash commands: slash commands remain first-class and snippets can occur anywhere in a message or command template (`README.md:21-31`). It supports both global and project-local singular/plural directories, with project snippets overriding global snippets and `snippet/` taking precedence over `snippets/` (`README.md:171-173`).

The package is deliberately a two-target integration. Installation is documented as wiring the package into both OpenCode's server plugin configuration and `tui.json` for autocomplete (`README.md:82-115`). The manifest exposes separate `.`/`server` and `./tui` exports (`package.json:5-20`), and the build produces both server and TUI bundles (`scripts/build.ts:10-30`).

## OpenCode Integration Patterns

### Register multiple concerns from one plugin

The server plugin returns a cohesive hook map: it mutates config to register a skill path and `/snippets` commands, then registers `command.execute.before`, `chat.message`, `experimental.chat.messages.transform`, `experimental.chat.system.transform`, and `tool.execute.after` (`index.ts:658-687`, `index.ts:744-856`). This is a useful pattern when a feature needs both prompt-time transformation and lifecycle/config integration, but the hook responsibilities are kept in named modules such as `commands`, `loader`, `skill-loader`, and `injection-manager` (`index.ts:5-27`).

### Process current input and persisted history defensively

The plugin transforms new user parts in `chat.message`, while the message transform handles historical user messages that have not already been marked as processed (`index.ts:687-707`, `index.ts:757-775`). It skips assistant, ignored, and synthetic content (`index.ts:687-690`, `index.ts:759-762`). The `snippetsProcessed` marker is important: it prevents repeated expansion as OpenCode re-runs transforms (`index.ts:703-707`, `index.ts:757-760`).

### Use synthetic/ignored messages for context without changing visible text

Optional `<inject>` blocks are tracked separately, rendered into injection marker messages, and positioned relative to recent conversation messages (`index.ts:723-741`). Skill loads are similarly represented as hidden synthetic text and inserted into the transformed message stream and, when needed, mirrored into the system prompt (`index.ts:825-851`). The implementation documents the invariant that the visible placeholder and model-facing payload need different representations (`index.ts:640-653`).

### Expose a package-owned skill through OpenCode's skill path

During the `config` hook, the plugin adds its bundled `skill` directory to `skills.paths`, refreshes the runtime skill registry, and registers commands (`index.ts:660-682`). This avoids copying a `SKILL.md` into the user's config. The entrypoint retains cleanup for an older install strategy and explains the migration rationale (`index.ts:39-64`).

### Provide TUI autocomplete as a separate optional peer integration

The TUI entrypoint uses `@opencode-ai/plugin/tui` and OpenTUI/Solid, while those packages are optional peer dependencies (`package.json:49-64`). The TUI normalizes names before creating drafts (`tui.tsx:159-166`) and sorts project results before global results (`tui.tsx:113-131`). This keeps server-only installation viable while allowing a richer prompt UX when the TUI peers are available.

## Implementation Lessons

### Recursive expansion needs explicit termination semantics

Expansion is recursive and repeats until no text changes. It tracks per-snippet expansion counts and stops after 15 expansions, leaving the unresolved hashtag in place and logging a warning (`src/expander.ts:5-8`, `src/expander.ts:101-181`). This is preferable to relying only on cycle detection: it bounds pathological growth even for complex graphs. The tests cover self-cycles, two-way and three-way cycles, longer chains, partial loops, independent loops, and nested loops (`src/expander.test.ts:137-249`).

Side-effect blocks are deduplicated by block type, snippet name, and content, while inline text can still replace every occurrence (`src/expander.ts:54-72`, `src/expander.ts:155-175`). That distinction is a useful model for prompt transforms where visible expansion and context injection have different multiplicity requirements.

### Separate parsing, registry, and rendering

Snippet loading parses Markdown frontmatter, normalizes aliases, and registers both canonical names and aliases against the same `SnippetInfo` (`src/loader.ts:117-185`). The loader applies global then project sources so project registrations override global ones (`src/loader.ts:51-69`). It accepts both `aliases` and legacy/singular `alias` metadata (`src/loader.ts:131-140`). This makes format compatibility local to the loader rather than spreading metadata concerns through expansion code.

### Normalize configuration at the boundary

The config loader accepts JSONC, boolean values, and the strings `enabled`/`disabled`, then merges defaults, global config, and project config in priority order (`src/config.ts:9-12`, `src/config.ts:135-155`, `src/config.ts:174-216`). Invalid structures and parse failures fall back to defaults with a warning (`src/config.ts:142-153`), and positive integer validation rejects non-finite or less-than-one values (`src/config.ts:127-132`). This produces a strongly shaped runtime config instead of making every hook handle raw optional values.

### Make reloads explicit and tolerate missing user directories

Missing or unreadable snippet directories are treated as normal and only logged at debug level (`src/loader.ts:79-107`). The plugin loads at startup but can reload on demand from the command path (`index.ts:111-115`, `src/commands.ts:130-143`). This is appropriate for user-editable prompt assets, where absence is not exceptional and edits should not require restarting OpenCode.

## Security and Reliability Pitfalls

### Shell substitution is arbitrary command execution

The plugin treats `!\`command\`` and `!>\`command\`` in processed text as commands and passes the captured string directly to `child_process.exec`, using only the project directory as `cwd` (`src/shell.ts:19-39`). There is no allowlist, confirmation gate, timeout, output-size limit, environment restriction, or sandbox. Because this runs from user-message text and snippet-expanded text (`index.ts:200-204`), enabling this feature means prompt content can execute arbitrary commands with the plugin process's privileges. Failure leaves the original syntax in place and logs the command (`src/shell.ts:40-47`), which is useful for debugging but does not reduce the execution risk.

The README presents shell substitution as a normal feature (`README.md:203-221`), so documentation should make the trust boundary prominent. A safer production design would require an explicit opt-in, constrain execution, bound resources, and distinguish trusted snippets from untrusted message text.

### External editor invocation parses user-controlled editor strings

The TUI derives `VISUAL`/`EDITOR` from the environment and splits non-Windows commands on whitespace before spawning (`tui.tsx:168-213`, `tui.tsx:237-255`). This is convenient but does not implement shell quoting, so paths or arguments containing spaces are misparsed; Windows uses a constructed `cmd /c` string (`tui.tsx:245-249`), which deserves careful quoting review. The code should treat the configured editor as a trusted executable configuration and test platform-specific argument handling.

### State is session-scoped but in-memory

Injection markers, pending skill payloads, and reload coordination are held in maps created inside the plugin instance (`index.ts:114-118`). This avoids global cross-session contamination, but state disappears on plugin restart and concurrent hook ordering is handled with promise queues rather than durable storage. The persisted-message lookup is intentionally guarded and falls back to an empty list on client failure (`index.ts:283-296`).

### Configuration creation has side effects during plugin startup

`loadConfig` always ensures the global snippets directory and config file exist (`src/config.ts:158-170`, `src/config.ts:185-187`). This is user-friendly, but plugin initialization can write under the user's home directory before any snippet is used. Applications adopting this pattern should document the side effect and handle permissions/read-only homes explicitly.

## Testing Lessons

The repository has broad unit and integration coverage rather than only testing pure expansion. The config suite redirects constant paths into temporary directories, restores them after each test, and checks defaults, file creation, JSONC comments, aliases for booleans, project-over-global precedence, malformed input, and invalid types (`src/config.test.ts:7-58`, `src/config.test.ts:60-203`). This is a practical technique for code whose production paths are derived from the home directory.

The top-level integration suite constructs mock OpenCode plugin contexts and clients, writes real project snippets, and invokes returned hooks directly (`index.test.ts:27-80`, `index.test.ts:90-129`). It verifies user-only processing and ignored-message behavior (`index.test.ts:166-216`) and separately exercises historical-message transformation (`index.test.ts:219-260`). The expansion tests assert exact output for composition and termination behavior (`src/expander.test.ts:31-83`, `src/expander.test.ts:85-135`, `src/expander.test.ts:137-188`).

The repository also includes a package lifecycle regression test: it verifies the published `prepare` script is included and succeeds from a temporary directory outside a Git checkout (`package.test.ts:18-38`). A dedicated smoke-testing skill warns that built `dist` output must be rebuilt before TUI testing and that visible placeholders alone do not prove model-facing injected context; stored session data should also be inspected (`.opencode/skill/smoke-testing-snippets/SKILL.md:13-24`, `.opencode/skill/smoke-testing-snippets/SKILL.md:31-46`). Those are strong examples of testing the actual OpenCode integration boundary, not just string transforms.

Coverage gaps suggested by the implementation include security tests for shell execution, command timeout/output limits, editor quoting across platforms, malformed frontmatter/alias types, and concurrent reload/injection ordering. The existing test inventory is strong on expected behavior but does not establish a security policy for the command runner.

## Packaging and Release Lessons

The package declares `type: module`, Node >=20, explicit server/TUI exports, and keeps OpenCode and TUI runtime packages external in the two Bun builds (`package.json:5-23`, `scripts/build.ts:10-30`). The `files` allowlist publishes only `dist`, `skill`, and the guarded prepare script (`package.json:84`), while `.npmignore` excludes development material (`.npmignore:1-10`). This sharply reduces accidental source/test publication while retaining the bundled skill and install lifecycle script.

The `prepare` script conditionally imports Husky only when `.git` exists, because package managers may run it in a clean pack directory without dev dependencies (`scripts/prepare.mjs:1-10`). The package lifecycle test locks that behavior down (`package.test.ts:18-38`). This is an important npm packaging pitfall: unconditional prepare-time dev-tool imports can break installation from a registry tarball.

CI separates format, build, and test jobs, pins Bun 1.3.14, and runs all three on Ubuntu 24.04 (`.github/workflows/ci.yaml:9-59`). Release automation rebuilds before generating notes and publishing, but uses `npm publish` after setting up Node (`.github/workflows/release.yml:21-30`, `.github/workflows/release.yml:93-100`). That mixed Bun-for-development/Node-for-publishing strategy is workable, though it should be validated against the package manager behavior the project wants to support.

## Reusable Takeaways

1. Register server and TUI targets as separate exports and make TUI peers optional when autocomplete is an enhancement rather than a server requirement (`package.json:7-20`, `package.json:49-64`).
2. Mark transformed parts and skip ignored/synthetic/assistant content to make hooks idempotent across OpenCode's current-message and history-transform paths (`index.ts:687-707`, `index.ts:757-775`).
3. Bound recursive prompt expansion and test multiple graph shapes, not only a self-reference (`src/expander.ts:123-145`, `src/expander.test.ts:137-249`).
4. Treat shell substitution as a privileged capability requiring an explicit threat model, not as a harmless text replacement (`src/shell.ts:25-47`).
5. Test package installation outside a Git checkout and use a publish allowlist to prevent lifecycle and artifact surprises (`scripts/prepare.mjs:3-8`, `package.json:75-84`, `package.test.ts:18-38`).
