## OpenCode Patterns

### Public SDK integration

- The plugin extracts the working HeyAPI transport from the plugin-provided v1 client via `input.client._client`, then constructs the v2 `OpencodeClient`; this is a deliberate compatibility bridge for v2 session/workspace parameters ([src/index.ts:67-75]).
- It uses `session.create`, `session.promptAsync`, `session.abort`, `session.status`, worktree/workspace APIs, event hooks, tool hooks, system-prompt transformation, compaction context, and shell environment injection rather than OpenCode internals ([src/index.ts:139-380]; AGENTS.md:16-31).
- `promptAsync` is fire-and-forget for spawn and delivery. Messages are persisted first, then delivery failures are handled asynchronously or retried from SQLite ([src/tools/team-spawn.ts:362-396]; src/messaging.ts:32-61; README.md:297-302).
- System prompt transforms keep the lead aware of member/task state, while compaction hooks restore the team context after context compression ([src/index.ts:341-360]; test/hooks.test.ts:361-446).

### Coordination model

- The task board is a coordination primitive: tasks have status, priority, assignee, and serialized dependencies; the README explicitly instructs callers to use IDs returned by `team_tasks_add` rather than inventing dependency IDs ([README.md:49-73]; src/schema.ts:39-54).
- Work is isolated by default using an OpenCode worktree and optional workspace binding; read-only `plan`/`explore` agents can opt out of worktrees ([src/tools/team-spawn.ts:89-110, 126-183]). The companion skill recommends a scout/build/reviewer shape and tells the lead to merge only after reading results and inspecting the diff ([skills/opencode-ensemble/SKILL.md:35-47, 49-58, 68-76]).
- Peer messages go directly through `promptAsync`; lead-bound messages are delivered through a wake-up prompt plus the system prompt, avoiding repeated polling and keeping full message content out of the wake-up signal ([src/index.ts:236-280]; test/integration.test.ts:226-266).
- A persistent SQLite source of truth plus an in-memory registry gives fast lookups while supporting plugin restarts and multiple plugin instances. Registry rehydration and SQLite fallback are explicitly tested ([src/recovery.ts:151-173]; src/hooks.ts:116-145; test/hooks.test.ts:682-877).

## Safety and Security Lessons

- Tool authorization is enforced in two layers: lead-only tools call `requireLead`, while general team tools resolve the caller's active team membership ([src/tools/shared.ts:32-50]; src/tools/team-shutdown.ts:22-27). Descendant sessions are blocked from `team_*` tools by walking parent relationships, with SQLite fallback for cross-instance state ([src/hooks.ts:96-145]; test/hooks.test.ts:269-355, 831-877).
- Spawned sessions receive explicit permission rules. Read-only agents are denied `edit` and `bash`; worktree paths are allowlisted, and team tools are explicitly allowed ([src/tools/team-spawn.ts:146-170]). This is a useful pattern for reducing teammate blast radius, although failed worktree creation falls back to the shared directory and only emits a warning ([src/tools/team-spawn.ts:99-123]). Consumers should treat that fallback as a degraded-isolation state, not as equivalent isolation.
- Message size is bounded by a UTF-8 10 KiB check before SQLite insertion ([src/messaging.ts:32-61]). Process execution passes an argument array to `child_process.spawn` with no shell interpolation, reducing command-injection risk ([src/process.ts:21-52]).
- Destructive archived-team purge uses a preview, a session-bound random token, exact approval/denial labels, a ten-minute TTL, project scoping, revalidation, and resource/branch namespace checks before deletion ([src/state.ts:146-213]; src/tools/team-cleanup.ts:419-450, 163-198). Tests cover denial, changed targets, active-team checks, dirty worktrees, shared resources, and unrelated branches ([test/tools/team-lifecycle.test.ts:500-1004]).
- Shutdown, timeout, recovery, and force-cleanup paths preserve a worktree branch before calling `session.abort`, preventing OpenCode's session cleanup from deleting committed work ([src/tools/team-shutdown.ts:54-129]; src/recovery.ts:34-50; src/watchdog.ts:197-218; src/tools/team-cleanup.ts:485-503). This is a critical lifecycle invariant documented by the repository ([AGENTS.md:38-60]).

## Pitfalls and Residual Risks

- **Spawn rollback violates the repository's own branch-preservation invariant.** If the initial fire-and-forget `promptAsync` fails after a worktree was created, the rollback calls `session.abort` directly before removing the workspace/worktree, without first preserving `worktreeBranch` ([src/tools/team-spawn.ts:362-396]). The documented invariant says every abort must preserve the branch first ([AGENTS.md:38-60]). A provider/transport failure at this point can therefore lose committed teammate work; this path needs a dedicated preservation test and implementation audit.
- Worktree creation failure silently degrades to a shared directory ([src/tools/team-spawn.ts:113-123]). For a build agent, the permission list then lacks the worktree-specific edit allow rule ([src/tools/team-spawn.ts:152-159]), so behavior depends on host permission defaults and may either prompt or fail unexpectedly. The result should make this degraded mode explicit or fail closed for write-capable agents.
- `checkWorktreeDirty` assumes clean when git status fails ([src/tools/shared.ts:21-29]), while cleanup treats dirty detection as a safety gate. A filesystem/git failure can therefore allow cleanup to proceed without proving that the worktree is clean. The tests cover true/false injected checks, but not command failure semantics ([test/tools/team-lifecycle.test.ts:425-498]).
- Configuration validates JSON field types but accepts arbitrary numeric values and uses `parseInt(...) || existingValue` for environment overrides, so malformed, negative, or unexpectedly large values are not rejected consistently ([src/config.ts:54-83, 99-107]). Tests cover precedence, invalid JSON, and zero disables, but not range validation ([test/config.test.ts:40-101]).
- The README's test badge says 666 passing while the development instructions say `bun test # 623 tests` ([README.md:7-12, 453-460]). This is documentation drift, not a runtime defect, but release-facing claims should be generated or checked.

## Testing Practices

- Tests use Bun's test runner and in-memory SQLite with migrations applied, keeping business logic tests deterministic and avoiding disk cleanup ([test/helpers.ts:1-14, 94-105]).
- Coverage is unusually broad for a plugin: unit tests cover config, state, database, rate limits, parsing, progress, hooks, dashboard contracts, recovery, watchdogs, and each tool; integration tests cover full lifecycle, concurrent spawning, message delivery, rollback, and multi-instance fallback ([test/integration.test.ts:16-216, 218-410]; test/hooks.test.ts:682-986).
- Concurrency and failure behavior are intentional test targets: four concurrent spawns, simultaneous messages, slow session creation, prompt failure rollback, and abort/status failures are exercised ([test/integration.test.ts:95-168, 302-409]; test/tools/team-lifecycle.test.ts:124-184).
- Migrations are versioned with `PRAGMA user_version`, run transactionally, enable WAL and foreign keys, and reject a database newer than the plugin ([src/schema.ts:191-217]; src/db.ts:100-110). The main gap is limited live-server coverage: the integration tests use a recorded mock client ([test/helpers.ts:17-91]), so SDK transport, server permission enforcement, and real worktree/session races remain partially unverified.

## Packaging and Operations

- Publishing is guarded by `prepublishOnly`, which runs typecheck, all tests, and the Bun build; the package ships `dist`, `src`, README, license, and social preview ([package.json:22-35]).
- CI runs frozen Bun installation, TypeScript typecheck, Biome lint, Bun tests, and the build on pushes and pull requests to `main` ([.github/workflows/ci.yml:1-35]). Runtime support is explicit: Bun >=1.0 and Node >=24 ([package.json:36-49]; README.md:171-176).
- Installation requires a pinned npm plugin version and a host permission allowlist for external worktree paths; the README explains both operational requirements and the OpenCode cache/update issue ([README.md:18-26, 167-226]).
- The npm package's `files` list does not include `skills/`, while the skill is installed separately through `npx skills@latest add ...` ([package.json:22-28]; README.md:125-133). This clean separation is appropriate, but the skill distribution is a second release surface and should remain tested independently, as the repository does with `test/skill-package.test.ts` ([test/skill-package.test.ts:22-66]).

## Transferable Lessons

1. Persist coordination state before asynchronous SDK delivery; use a minimal wake signal and reconstruct full content from durable state.
2. Treat every session abort as a data-preservation boundary. Centralize branch preservation and test every abort caller, including asynchronous rollback paths.
3. Default to isolated worktrees, explicitly mark read-only agents, and fail closed or clearly report when isolation setup degrades.
4. Enforce authorization at tool execution time and track descendant sessions, not just direct teammate sessions.
5. Make destructive cleanup two-phase and revalidate targets/resources after human approval.
6. Combine focused unit tests with mocked integration lifecycle/race tests, but add live-server smoke tests for transport and permission assumptions.
