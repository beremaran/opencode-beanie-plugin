## What the plugin does

The plugin provides a project-aware primary agent, `openspec-plan`, intended to separate architecture/specification work from implementation. The README explicitly frames the problem as premature implementation during planning and promises write access to selected specification files while keeping the rest of the codebase read-only (`README.md:7-27`).

The entrypoint follows a useful minimal activation pattern: it checks the workspace once, returns an empty plugin object for non-OpenSpec projects, and otherwise registers only a `config` hook (`src/index.ts:5-14`). Detection is intentionally filesystem-based and supports both the newer `openspec/config.yaml` marker and the legacy `openspec/AGENTS.md` marker (`src/utils/detection.ts:5-17`). This avoids changing unrelated projects and makes activation cheap, but it does not validate the contents or type of either marker.

The config hook re-checks activation before mutating configuration, then creates the agent and merges it into the existing `config.agent` object (`src/config.ts:5-16`, `src/config.ts:87-91`). The agent is primary, has a stable name and description, embeds a dedicated system prompt, and exposes a distinctive color (`src/config.ts:16-20`, `src/config.ts:84-85`).

## OpenCode patterns worth reusing

### Conditional config extension

Returning `{}` when inactive is a clean plugin composition boundary (`src/index.ts:5-14`). The config hook also preserves existing agents by starting from `config.agent || {}` and adding one named entry rather than replacing the whole map (`src/config.ts:87-90`). A production variant should retain this shape while using the SDK's concrete config types instead of `as any` (`src/config.ts:8`, `src/config.ts:88`).

### Defense-in-depth activation

The plugin detects at entrypoint time and again inside the hook (`src/index.ts:5-14`, `src/config.ts:7-13`). That second check is useful if the workspace changes between plugin initialization and config evaluation. The detection helper uses `join(ctx.directory, ...)`, avoiding string-concatenation path bugs (`src/utils/detection.ts:12-17`).

### Explicit agent permissions

The permission object makes the intended safety boundary inspectable: all reads are allowed, exploration and collaboration tools are enumerated, safety-sensitive `doom_loop` and `external_directory` are set to `ask`, and edit rules put a global deny before narrower allow rules (`src/config.ts:21-60`). The README also documents the same operational model and the exact agent name, which improves discoverability (`README.md:18-27`, `README.md:76-81`).

### Package-first distribution

The package publishes only `dist`, points `main` at `dist/index.js`, builds directly from `src/index.ts`, and runs that build from `prepublishOnly` (`package.json:6-14`). OpenCode installation is correspondingly simple: users add the package name to the `plugin` array and let OpenCode fetch it (`README.md:42-54`). Peer dependencies declare both `@opencode-ai/plugin` and `@opencode-ai/sdk` at compatible versions (`package.json:33-35`).

## Pitfalls and security lessons

### Prompt and permission policy conflict

The system prompt says “Do NOT generate or modify `*.spec.md` files directly” and directs the agent to ask the user to run `/openspec.proposal` (`src/prompts.ts:16-28`). However, the permission rules explicitly allow edits to `specs/**` and `openspec/**` (`src/config.ts:52-60`), while the README advertises creating and editing OpenSpec files (`README.md:20-27`). The effective tool permission can therefore permit actions the prompt prohibits. A safer design should make the prompt and permission policy agree, ideally denying direct spec edits if proposal generation is the intended workflow, or removing the contradictory prompt rule if direct editing is intended.

### Bash allowlist is broader than “read-only” claims

The code comments describe Bash as “deny all by default, allow read-only filesystem + git read” (`src/config.ts:62-63`), but the allowlist includes `openspec` and `openspec *` (`src/config.ts:64-66`). Arbitrary subcommands under that namespace may mutate files or execute project-specific behavior. It also allows `echo *`, `env`, and `printenv *` (`src/config.ts:67-81`); these are lower-risk individually, but environment inspection can expose secrets to the agent. If a strict planning sandbox is required, allow only documented, non-mutating subcommands and avoid broad environment-output permissions.

### Path rules need semantic validation

The edit policy allows `project.md` and `AGENTS.md` at the matching permission path, plus recursive `openspec/**` and `specs/**` (`src/config.ts:52-60`). The README presents these as safe specification files (`README.md:20-27`), but repository-specific permission glob semantics should be verified: an unanchored or basename-matching rule could authorize same-named files outside the intended root. The policy should be tested against representative paths, including nested implementation directories and traversal-like inputs.

### Detection is permissive

Presence of an empty or unrelated `openspec/config.yaml` or `openspec/AGENTS.md` activates the plugin (`src/utils/detection.ts:8-17`). This is robust to format evolution but can unexpectedly add a primary agent to projects that merely contain a similarly named file. Parsing and validating the marker, or requiring the expected directory/file shape, would reduce false positives.

### Type safety is weakened at the configuration boundary

The hook fabricates a partial context and casts it to `any` before reusing the detector (`src/config.ts:7-10`), then casts `config.agent` to `any` (`src/config.ts:87-90`). These casts hide SDK API drift and malformed config values. The plugin should use the actual `PluginInput`/config types and handle absent or non-object agent configuration explicitly.

## Testing and verification gaps

- No test script is defined in `package.json`; only `build`, `watch`, and `prepublishOnly` exist (`package.json:10-13`).
- No test files are present in the clone. There is consequently no automated coverage for positive/negative detection, config preservation, permission precedence, or prompt-policy consistency.
- The implementation uses synchronous `existsSync` inside an `async` detector (`src/utils/detection.ts:12-17`). This is acceptable for two tiny checks, but tests should still cover filesystem errors and unusual workspace paths.
- A minimal test matrix should cover: neither marker, each marker independently, both markers, pre-existing agents, inactive hook behavior, and exact permission outcomes for allowed and denied paths/commands. It should also assert that the generated agent is primary and carries the expected prompt.
- The repository's TypeScript configuration is strict and no-emit (`tsconfig.json:1-13`), while packaging relies on Bun's bundler (`package.json:11-13`). A CI check should run the type checker and production build without relying solely on `prepublishOnly`.

## Packaging and maintenance lessons

The package is ESM (`package.json:5`), has a single bundled entrypoint, and excludes source files from the published file set (`package.json:6-14`). This keeps installation small, but it also means source maps, declaration files, and a `types` entry are not published. Consumers only need runtime JavaScript here, yet maintainers should decide explicitly whether debugging/type metadata is part of the package contract.

The dependency lock records OpenCode package `1.1.25` while the peer range starts at `^1.1.19` (`bun.lock:18-20`, `package.json:33-35`). This is reproducible for development but should be checked against the oldest supported OpenCode release, especially because permission schema and config-hook types can change. `bun-types` is pinned to `latest` in both manifest and lock metadata (`package.json:38-39`, `bun.lock:7-10`), which weakens reproducibility on future lock refreshes.

The ignore file excludes `dist`, `*.tsbuildinfo`, local `opencode.json`, and `AGENTS.md` (`.gitignore:1-6`). Ignoring local OpenCode configuration and generated build state is sensible; ignoring `AGENTS.md` is potentially risky if a repository-level agent instruction is intended to be versioned, so this should be a deliberate project policy rather than a package default.

## Bottom line

This is a compact example of an OpenCode plugin that conditionally injects a focused primary agent and uses explicit permission rules to reduce implementation damage. The strongest reusable pattern is the inactive no-op plus config-hook merge. The main production risks are the mismatch between prompt and edit permissions, the broad `openspec *` Bash allowance, permissive marker detection, and the complete lack of automated tests around the security boundary.
