This is an alpha TypeScript package that exposes both a native OpenCode plugin and a standalone OrgX peer. The README explicitly describes the peer as opening an authenticated WebSocket, receiving `task.dispatch`, running work in the local OpenCode subscription, and posting receipts/deviations back; it also emphasizes that local Work Graph records are compact and redacted (`README.md:1-10`, `README.md:97-110`).

## OpenCode integration patterns

### Native hook lifecycle

- The default exported plugin is a small factory with injectable `startPeer`, environment, and logger dependencies (`src/plugin.ts:17-30`). This makes startup behavior unit-testable without a real daemon or gateway.
- Startup is gated on `server.connected`, and the peer is memoized so repeated connection events cannot start multiple peers (`src/plugin.ts:35-66`; `src/plugin.test.ts:61-77`). Missing credentials produce one warning and leave OpenCode usable without the integration (`src/plugin.ts:41-49`; `src/plugin.test.ts:79-96`).
- The package entrypoint exports the driver, plugin, peer types, and Work Graph helpers, while `startPeer` is dynamically imported (`src/index.ts:1-20`). The test confirms the package entry loads without eagerly importing the peer runtime (`src/plugin.test.ts:122-128`). This is a useful cold-start and optional-dependency pattern.

### Local daemon driver

- `OpenCodeDriver` discovers the local daemon from `~/.opencode/state.json` on macOS/Linux and `%APPDATA%/opencode/state.json` on Windows, then probes `GET /status` on loopback (`src/OpenCodeDriver.ts:5-11`, `src/OpenCodeDriver.ts:87-115`, `src/OpenCodeDriver.ts:402-408`). The state path is injectable for tests (`src/OpenCodeDriver.ts:62-70`).
- Dispatch creates a fresh session with an idempotency key, streams NDJSON events, emits `task.started`, `task.step`, `task.completed`, or `task.failed`, and preserves first-response and token counts (`src/OpenCodeDriver.ts:142-219`, `src/OpenCodeDriver.ts:342-398`). The tests exercise healthy detection, missing state, normal dispatch, and error termination with a fake fetch (`src/OpenCodeDriver.test.ts:58-113`, `src/OpenCodeDriver.test.ts:249-275`).
- Skill rules are fetched once per peer boot and matched against file-edit/tool-call summaries. Dedupe is scoped by skill, rule fingerprint, and run ID (`src/peer.ts:311-362`; `src/OpenCodeDriver.ts:252-280`). This is a compact way to turn plan rules into auditable deviations without sending full transcripts.

### Resumable native questions

- Native `question.asked` events are parsed defensively from either `properties` or `data`, normalized, and ignored unless they have an ID, session ID, and at least one valid question (`src/attentionBridge.ts:40-65`). The plugin uses an active-ID set to avoid duplicate bridges (`src/plugin.ts:70-85`).
- Each question becomes a blocking OrgX attention record with an idempotency key, source event/session metadata, and `reply_in_place` continuation details. Answers are polled, translated from option IDs to labels, acknowledged as `resuming`, replied to through the local v2 SDK, then acknowledged as `resumed`; native reply failures become `resume_failed` (`src/attentionBridge.ts:73-181`). Tests cover multi-question answers and failed native replies (`src/attentionBridge.test.ts:40-133`).

### Passive local reconciliation

- Work Graph outbox records deliberately contain schema/source/client, run/session handles, cwd, timestamp, and a summary, but not raw event text by default (`src/workGraphOutbox.ts:29-49`; `src/OpenCodeDriver.ts:224-248`, `src/OpenCodeDriver.test.ts:115-174`). The outbox directory is created mode `0700`, and the JSONL file is requested mode `0600` (`src/workGraphOutbox.ts:51-69`).
- Terminal events trigger a best-effort private replay through the packaged reconciliation script; replay errors are captured rather than changing task outcome (`src/OpenCodeDriver.ts:180-221`, `src/OpenCodeDriver.ts:322-328`, `src/workGraphReplay.ts:14-61`). The script uses stable hashing/idempotency and explicitly excludes raw transcripts (`scripts/orgx-work-graph-reconcile.mjs:596-629`, `scripts/orgx-work-graph-reconcile.mjs:662-667`, `scripts/orgx-work-graph-reconcile.mjs:887-890`).

## Security and privacy lessons

- Credential isolation is explicit: `captureGatewayCredential` prefers and trims `ORGX_API_KEY`, falls back to `ORGX_GATEWAY_KEY`, then deletes both from the supplied environment; child environments also delete both aliases (`src/childProcessEnv.ts:3-23`). Tests verify both behaviors (`src/childProcessEnv.test.ts:8-27`).
- Transport error summaries cap text, redact Bearer tokens, bearer protocol credentials, and `oxk_` keys, and whitelist short error codes (`src/peer.ts:37-75`). The test verifies that a nested WebSocket target is not serialized and the secret does not survive (`src/peer.test.ts:61-78`).
- Sentry is opt-out, sampled, configured with `sendDefaultPii: false`, disables request/user/body/GenAI data collection, sanitizes sensitive key names and credential-like text, and removes user/request fields before sending (`src/sentry.ts:7-8`, `src/sentry.ts:59-95`). This is a strong baseline for an AI plugin handling prompts and tool activity.
- Context-pack hydration writes only after a successful authenticated response, creates `.opencode`, and enforces `0600` on the output (`src/contextPackHydration.ts:46-65`). The README also states that local Work Graph records omit prompts, transcripts, API keys, and tokens (`README.md:105-107`).

### Security pitfalls and review points

- The daemon is addressed over unauthenticated loopback HTTP. The driver sends a probe header but no local auth credential (`src/OpenCodeDriver.ts:87-105`, `src/OpenCodeDriver.ts:352-367`). Any local process able to impersonate the daemon could receive task prompts or influence completion events; a production implementation should rely on the daemon’s actual auth mechanism or authenticate the local channel.
- Remote skill rules are converted directly into `new RegExp(rule.match.pattern)` without validation or a safe-regex limit (`src/OpenCodeDriver.ts:252-260`). A malformed pattern can fail dispatch, and a pathological pattern can consume CPU. Validate/compile rules at fetch time and handle regex errors per rule.
- `cwd`, repo paths, event paths, summaries, and task descriptions are passed into local session requests or local records (`src/OpenCodeDriver.ts:147-162`, `src/OpenCodeDriver.ts:311-318`). The outbox intentionally omits raw summaries, but the local daemon still receives the rendered task description (`src/OpenCodeDriver.ts:352-363`). Treat these values as sensitive and validate path boundaries if tasks can be server-originated.
- The plugin starts telemetry during `startPeer` and uses a hard-coded default Sentry DSN (`src/sentry.ts:3-5`, `src/peer.ts:103-107`). The explicit disable flags and redaction are good controls, but users should be clearly informed that telemetry is enabled by default.
- `defaultInstallationId()` includes the OS user name (`src/peer.ts:307-309`), which is a stable local identifier and potentially personal data. Prefer an opaque persisted installation ID if cross-run correlation is needed.

## Testing and verification lessons

- The test suite is layered: Vitest covers plugin lifecycle, credential isolation, context-pack request construction, driver event translation, attention continuation, peer protocol selection, and continuity health (`src/*.test.ts`; representative assertions in `src/OpenCodeDriver.test.ts:78-113`, `src/attentionBridge.test.ts:86-133`, `src/continuityHealth.test.ts:5-55`). The reconciliation CLI has separate Node test-runner coverage for argument parsing, symlink direct-run detection, malformed JSONL, report shape, private posting, and credential-free dry runs (`scripts/orgx-work-graph-reconcile.node-test.mjs:39-131`).
- Dependency injection is used consistently for fake fetches, peer drivers, loggers, and replay functions (`src/OpenCodeDriver.test.ts:9-21`, `src/plugin.ts:17-20`, `src/peer.ts:78-97`). This avoids requiring a live OpenCode daemon, matching the repo guidance that daemon availability is not a cloud setup prerequisite (`AGENTS.md:13-25`, `.codex/README.md:17-29`).
- The declared CI sequence is install, type-check, test, build on Node 22 (`.github/workflows/ci.yml:9-20`). In the supplied clone, `npm test` could not start because `vitest` was absent, and `npm run type-check` failed because `@useorgx/orgx-gateway-sdk` and `@sentry/node` were unavailable; it then surfaced implicit-`any` errors in `src/peer.ts` and `src/sentry.ts`. No dependency installation or clone edits were made, so runtime verification remains pending a complete install.
- A notable coverage gap is that the tests do not exercise malformed NDJSON, a thrown skill regex, cancellation during polling, HTTP error bodies, `stop()` during an active dispatch, or the real manifest/heartbeat HTTP payloads. The driver intentionally skips malformed NDJSON (`src/OpenCodeDriver.ts:389-397`), so a test should confirm whether silent loss is acceptable.

## Configuration, metadata, and packaging

- `package.json` is an ESM package with `dist/index.js` and declarations as the library entry, plus two bins: the peer CLI and reconciliation CLI (`package.json:8-20`). The published file allowlist includes `dist`, `scripts`, README, LICENSE, and `plugin.manifest.json` (`package.json:22-27`).
- The manifest declares capabilities and the `opencode` driver, but its fingerprint and signature are empty in the checked-in alpha/dev artifact; the note says npm prepublish populates them and unsigned builds are degraded (`plugin.manifest.json:1-15`). Runtime loading falls back to a dev placeholder if the manifest is absent (`src/peer.ts:202-225`). This fail-soft behavior keeps local development usable but should not be allowed to masquerade as a fully licensed release.
- The build is strict TypeScript with declarations, maps, source maps, `noEmitOnError`, and tests excluded from emitted output (`tsconfig.json:1-20`). `prepublishOnly` gates release on type-check, tests, and build; `pack` emits an artifact directory (`package.json:29-35`).
- The lockfile pins the gateway SDK to a GitHub commit rather than a registry version (`package.json:37-46`, `package-lock.json:11-24`). That provides reproducibility only while GitHub is reachable and makes clean/cloud installs dependent on GitHub access, which the repo documents (`.codex/README.md:17-22`). A published package should consider a registry release or a documented fallback.
- The publish workflow uses npm trusted publishing/OIDC, checks package/manifest version and release tag consistency, avoids republishing an existing version, selects `alpha` for prereleases, verifies registry visibility, and uploads the packed artifact (`.github/workflows/publish.yml:8-14`, `.github/workflows/publish.yml:44-88`). It uses Node 24 while CI uses Node 22 (`.github/workflows/publish.yml:18-21`; `.github/workflows/ci.yml:11-20`), so release-only runtime/toolchain differences should be intentional and tested.

## Overall assessment

This repository demonstrates a well-factored OpenCode plugin architecture: a small event hook, an injectable local-daemon driver, a separately controllable gateway peer, explicit credential scrubbing, summary-only persistence, and strong fake-transport tests. The most important operational risks are dependency-install reproducibility, unauthenticated loopback assumptions, untrusted regex rules, and silent failure/coverage around streaming and cancellation. Its packaging and release checks are unusually deliberate for an alpha plugin, especially the manifest/version gate and OIDC publish path.
