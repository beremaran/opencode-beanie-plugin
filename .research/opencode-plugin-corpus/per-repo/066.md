## What it does

OpenCode Plan Manager is a TypeScript/Bun plugin for persistent, filesystem-backed implementation plans. Its README positions the design around selective context loading, strict schemas, status directories, and cross-session plain files rather than a database (README.md:16-25). Plans are stored under `.opencode/plans/{pending,in_progress,done}/`, with `metadata.json`, `specifications.md`, and `implementation.md` (README.md:111-124). The public tool surface is four tools: `plan_create`, `plan_list`, `plan_read`, and `plan_update` (README.md:128-135).

## OpenCode integration patterns

### Plugin factory and agent prompt injection

The entrypoint exports a `Plugin` factory, logs initialization through `client.app.log`, returns a plugin name, registers four tools, and uses the `config` hook to inject Plan and Build prompts only when those agents do not already have a prompt (src/index.ts:1-5, 20-51). Preserving an existing prompt is a useful compatibility pattern: the README explicitly says custom prompts take priority (README.md:85-95).

### Schema-first tools

Each tool is created with `tool({ description, args, execute })`; create and update expose Zod object shapes as tool arguments, while read combines a string ID with the `PlanViewSchema` defaulting to `full` (src/tools/plan-create.ts:29-36; src/tools/plan-update.ts:30-37; src/tools/plan-read.ts:23-38; src/tools/plan-list.ts:25-44). The update schema rejects an empty update and disallows supplying both a replacement implementation and task updates (src/schemas/update-plan-input.ts:10-16, 17-53). This keeps invalid combinations out of tool execution rather than relying only on prompt instructions.

### Permission-aware writes with reviewable diffs

Create and update generate content, prepare a unified diff, and call `context.ask` before writing. `askPlanEdit` requests `edit` permission, passes the exact relative file patterns, includes `.opencode/plans/*` in `always`, and attaches the diff in metadata (src/utils/ask/askPlanEdit.ts:28-53). It classifies policy denial separately from user cancellation and returns explicit tool output for each case (src/utils/ask/askPlanEdit.ts:54-97). The diff helper works around OpenCode's one-diff-block limitation by combining spec and implementation into a virtual file when both change (src/utils/diff/prepareUnifiedPlanDiff.ts:35-43, 70-101).

### Tool output conventions

All operations return tagged strings such as `<tool-success>`, `<tool-warning>`, and `<tool-error>` through one formatter (src/utils/output/buildToolOutput.ts:1-7, 45-50). Errors commonly include a concrete `NEXT STEP`, for example asking callers to use `plan_list` after a missing plan (src/tools/plan-read.ts:44-52; src/tools/plan-update.ts:39-48). This is a practical pattern for agent-facing tools: distinguish outcome type and provide recovery guidance in the same response.

## State and filesystem design

The status directory is the state machine. `getPlanPaths` anchors all paths below `<cwd>/.opencode/plans` (src/utils/filesystem/get-plan-paths.ts:22-29), and `ensurePlanDirectories` creates all three directories idempotently and concurrently (src/utils/filesystem/ensure-plan-directories.ts:12-19). Resolution searches `in_progress`, then `pending`, then `done`, returning the first folder containing metadata (src/utils/filesystem/resolve-plan-folder.ts:8-12, 32-47). The transition table allows `pending -> in_progress`, `in_progress -> done`, and `in_progress -> pending`; `done` has no outgoing transitions (src/utils/metadata/is-valid-transition.ts:11-25).

`plan_create` checks for cross-status ID collisions, rejects duplicate phase and task names, writes metadata plus both Markdown files, and removes the folder if the write group fails (src/tools/plan-create.ts:38-67, 70-89, 124-141). `plan_update` treats done plans as immutable, validates replacement content, supports exact-match task checkbox updates, and restores original file contents if a file write fails (src/tools/plan-update.ts:56-72, 100-127, 130-185, 230-273). Status movement uses `rename()` on the same filesystem, which is atomic for the folder move itself (src/utils/filesystem/move-plan-folder.ts:8-36).

The lightweight metadata contract is a good read-path optimization: metadata is described as the single source of truth and intentionally cheap to parse (src/types.ts:55-60); list reads only metadata and reports folders it cannot read instead of silently dropping them (src/tools/plan-list.ts:25-30, 60-80, 104-115). Metadata is schema-validated both on read and before write (src/utils/metadata/read-metadata.ts:21-32; src/utils/metadata/write-metadata.ts:29-39).

## Configuration

Configuration has project-over-user-over-default precedence, with project config at `<project-root>/.opencode/plan-manager.json` and user config at `~/.config/opencode/plan-manager.json` (README.md:42-55; src/utils/config/get-config-paths.ts:18-40). `loadConfig` caches the merged result per working directory and warns, then continues with defaults, for malformed or unreadable config files (src/utils/config/load-config.ts:7-65). Files are parsed as JSON and checked against a partial Zod schema; invalid JSON, validation failures, and missing files are differentiated (src/utils/config/load-config-file.ts:26-32, 47-95). The only current setting is `outputFormat`, constrained to Markdown, JSON, or TOON (src/schemas/config.ts:10-17; src/constants.ts:7-12).

The cache is an important operational caveat: config changes during a process are invisible until `clearConfigCache()` is called (src/utils/config/load-config.ts:68-74). The implementation exposes that reset specifically for tests or reloads, but the public README does not document the runtime caching behavior.

## Security and reliability lessons

- Permission checks are performed immediately before writes, not merely documented. The README also tells users to grant `ask` or `allow` only for `.opencode/plans/*` (README.md:57-79), while `askPlanEdit` supplies the corresponding path scope (src/utils/ask/askPlanEdit.ts:36-52).
- Plan IDs are validated as lowercase alphanumeric words separated by hyphens or underscores (src/schemas/plan-id.ts:6-15). Because IDs are used as folder names, this blocks path separators and traversal strings at the tool schema boundary.
- Completed plans are immutable for content changes, and transition validation prevents arbitrary lifecycle jumps (src/tools/plan-update.ts:63-83; src/utils/metadata/is-valid-transition.ts:11-25).
- The write path has partial-failure handling, but it is not a full transaction. `plan_update` can move a folder first, then later fail while writing content or metadata; the file restoration block restores file contents but does not move the folder back (src/tools/plan-update.ts:74-98, 230-291). Similarly, metadata is written after content and status changes, so a metadata write failure can leave the new folder/content state in place (src/tools/plan-update.ts:284-291). A production hardening lesson is to define and test rollback semantics across the complete operation, not only per-file writes.
- `resolvePlanFolder` trusts the first status directory containing a metadata file and does not compare metadata's internal `id`/`status` with the path (src/utils/filesystem/resolve-plan-folder.ts:38-44). `readMetadata` validates the metadata schema, but callers can still encounter a path/status mismatch if files are manually edited. The status-directory layout remains authoritative for tool routing.
- Error classification in `askPlanEdit` detects config denial by checking for a `ruleset` property and treats every other thrown value as user cancellation (src/utils/ask/askPlanEdit.ts:54-65). This is pragmatic given the stated missing error types, but an unexpected transport/runtime error could be presented to an agent as a benign user rejection.

## Testing evidence

The repository has broad unit coverage across metadata, config, filesystem, parsing/rendering, output, diff, and general helpers, plus four end-to-end files (`e2e/plan-create.test.ts`, `plan-list.test.ts`, `plan-read.test.ts`, and `plan-update.test.ts`). Representative tests cover valid and invalid transitions, including the immutable `done` state (src/utils/metadata/is-valid-transition.test.ts:5-31), config precedence/caching behavior through mocked dependencies (src/utils/config/load-config.test.ts:65-123), and resolution priority when duplicate folders exist (src/utils/filesystem/resolve-plan-folder.test.ts:24-61). `askPlanEdit` tests both user cancellation and a ruleset-based security denial (src/utils/ask/askPlanEdit.test.ts:25-58).

The declared Bun coverage threshold is 85%, excluding schema files (bunfig.toml:1-5). CI installs with Bun and runs coverage on Ubuntu for pushes and pull requests (package.json:25-31; .github/workflows/test.yml:1-26). However, in this audited clone `bun test` ran 114 tests across 33 files: 107 passed, while 7 suites failed during module loading because `@toon-format/toon` and `diff` were unavailable. This prevents independent verification of the affected output/diff and e2e suites; it is an environment/dependency-installation failure rather than a source assertion failure. The repository's CI does run `bun install` first, but the local audit did not modify the clone to install dependencies.

Testing gaps visible from the inspected surface include no successful full tool integration run in this environment, no test demonstrating rollback after a status move followed by a later write/metadata failure, and no test asserting that metadata identity/status agrees with its containing directory. The existing `movePlanFolder` tests verify movement and missing-source behavior, but not collision handling at the target path (src/utils/filesystem/move-plan-folder.test.ts:23-58).

## Packaging and maintenance

The package is ESM, exposes `dist/index.js` as both `main` and `module`, publishes only `dist`, and builds `src/index.ts` for the Node target with Bun; publishing triggers a minified build (package.json:19-31). Runtime dependencies are `@opencode-ai/plugin`, `@toon-format/toon`, and `diff`, while linting/formatting/testing tooling is development-only (package.json:33-59). `bun.lock` and `mise.toml` pin the tool family to Bun, with `mise.toml` requesting the latest Bun (mise.toml:1-2). The package metadata includes repository, license, keywords, and a MIT license file (package.json:1-18; LICENSE).

The `files: ["dist"]` restriction is a useful packaging safeguard: source, tests, examples, and development files are not included in the published package. The corresponding pitfall is that prompt text imported from `src/prompts/*.txt` must be bundled into `dist` by the build; the package's source imports those assets from the entrypoint (src/index.ts:3-4), so build/package smoke tests should verify the generated artifact contains the prompt content. The README's install, config, permissions, API examples, development commands, and example plan folders make the package reasonably discoverable and operationally explicit (README.md:29-79, 98-107, 128-198).

## Reusable takeaways

1. Use a plugin config hook to provide defaults without overwriting user-defined agent prompts (src/index.ts:29-45).
2. Put strict Zod schemas at the tool boundary, including cross-field invariants, then retain domain validation for duplicate names and lifecycle transitions (src/schemas/update-plan-input.ts:17-53; src/tools/plan-create.ts:59-67).
3. Pair permission requests with a focused path list and a reviewable diff before filesystem mutation (src/utils/ask/askPlanEdit.ts:36-53).
4. Keep list operations cheap by reading small metadata records, and report corrupt/skipped entries explicitly (src/tools/plan-list.ts:60-80, 104-115).
5. Treat multi-step filesystem operations as transactions in design and tests. Folder rename, content writes, and metadata writes currently have separate recovery behavior and can diverge on late failure (src/tools/plan-update.ts:74-98, 230-291).
6. Make CI install dependencies before coverage, and add a release smoke test for the exact published `dist` contents because the package publishes only the build output (package.json:20-31; .github/workflows/test.yml:18-26).
