# Repository 047: open-plan-annotator

## Identity and availability

- Manifest index 47 is `open-plan-annotator`, from `https://github.com/ndom91/open-plan-annotator`, described as “Annotate LLM plans like a Google Doc!” (`.research/opencode-plugin-corpus/manifest.json:365-369`).
- The clone is available at `.research/opencode-plugin-corpus/repos/ndom91--open-plan-annotator`.
- The package is version `1.10.9`, ESM, and declares `opencode/index.js` as its OpenCode entry point (`package.json:1-4`, `package.json:20-26`).

## Architecture and OpenCode patterns

### Thin adapter over one shared runtime

The OpenCode plugin registers one `annotate_plan` tool and delegates execution to `runPlanReview` (`opencode/index.js:190-205`). The bridge resolves a platform runtime and launches the same compiled binary used by the Claude hook path (`opencode/bridge.js:9-22`; `docs/architecture.md:3-7`). It sets host-specific environment variables, including `OPEN_PLAN_HOST=opencode`, and detaches the child after receiving a valid decision (`opencode/bridge.js:12-22`; `shared/planReview.mjs:149-167`).

**Reusable lesson:** keep host integration small and normalize different host protocols at a single boundary. Here, the bridge synthesizes a Claude-shaped `PreToolUse` event with `ExitPlanMode` and the plan text (`shared/planReview.mjs:22-35`), allowing the UI/server and decision serialization to remain shared across Claude Code and OpenCode.

### Tool output carries explicit workflow state

The plugin injects system instructions that define `DISCOVERY`, `PLAN_DRAFT`, `AWAITING_PLAN_DECISION`, `EXECUTION`, and `DONE`, plus `plan_status` and `explicit_replan` flags (`opencode/index.js:33-64`). After approval, the tool returns explicit execution instructions and suppresses another annotation call unless the user explicitly replans (`opencode/index.js:209-229`). Rejection returns feedback and a single revised-draft instruction (`opencode/index.js:232-241`).

**Reusable lesson:** tool results should state the next state and the allowed follow-up action, rather than returning only a boolean. This reduces ambiguity for an LLM-driven caller.

### Conditional system-prompt injection and handoff

The plugin avoids injecting its instructions into title-generation sessions and checks the current user agent before deciding whether to inject; subagents and the configured implementation agent are excluded (`opencode/index.js:110-142`, `opencode/index.js:175-187`). Approval can issue a no-reply session prompt to switch to a configured implementation agent (`opencode/index.js:144-171`).

**Pitfall:** the handoff is an implicit side effect of approval. The implementation agent defaults to `build` and handoff is enabled by default (`opencode/config.js:5-7`, `opencode/config.js:60-73`). A project or global config can change it, with project values taking precedence (`opencode/config.js:60-79`). Consumers should document this behavior prominently and test failure/warning behavior, not just successful review.

## Configuration and packaging

- The main package explicitly includes the OpenCode adapter, hooks, commands, skills, and shared runtime files through the npm `files` list (`package.json:28-50`). It depends on `@opencode-ai/plugin` and declares four platform runtimes as optional dependencies (`package.json:75-90`).
- Runtime packages constrain supported OS/CPU and publish only `bin/` and `README.md` (`packages/runtime-darwin-arm64/package.json:1-24`; `packages/runtime-linux-x64/package.json:1-24`). The resolver maps `darwin/linux` plus `arm64/x64` to the corresponding package and rejects unsupported combinations before attempting installation (`shared/runtimeResolver.mjs:7-35`).
- The build compiles one server entry into four platform binaries in parallel (`scripts/build-platforms.mjs:11-16`, `scripts/build-platforms.mjs:36-62`). The UI must already exist as `build/index.html`, and the server embeds it at compile time (`scripts/build-platforms.mjs:20-25`; `server/index.ts:1-3`).
- CI runs frozen dependency installation, typecheck, lint, tests, a build smoke test, and a package smoke test (`.github/workflows/ci.yml:19-43`). `pack:check` uses `npm pack --dry-run` to assert required runtime files are present in the published package (`scripts/check-package-files.mjs:33-64`).
- Release metadata is duplicated across the root package, runtime packages, Pi package, and Claude marketplace metadata; the release process updates all of them together (`docs/release.md:17-22`).

**Packaging lesson:** platform-specific optional packages keep the main package small while preserving automatic host selection. The explicit `files` list and pack smoke test address a common plugin failure mode: source works in a checkout but the published package omits the entrypoint, hook, skill, or resolver.

## Security and reliability observations

### Good controls

- Runtime installation fetches the exact version from the npm registry, requires both tarball URL and `dist.integrity`, hashes the downloaded buffer, and rejects mismatches before extraction (`scripts/install-runtime.mjs:81-95`, `scripts/install-runtime.mjs:222-243`). It extracts to a temporary directory, verifies the expected binary exists, then moves it into place and sets mode `0755` (`scripts/install-runtime.mjs:97-126`).
- Logs are deliberately sent to stderr because stdout is reserved for the host hook protocol (`scripts/install-runtime.mjs:16-16`; `server/index.ts:62-69`, `server/index.ts:116-137`). This is important for JSON hook integrations.
- The child process is spawned without a shell and with an explicit working directory resolution path (`shared/planReview.mjs:103-143`). The resolver handles a file path as a cwd by switching to its parent (`shared/planReview.mjs:105-116`).
- Hook output is parsed and validated for an object, a decision, and the required reason on denial; if stdout contains extra lines, the parser searches individual lines for valid JSON (`shared/planReview.mjs:41-62`, `shared/planReview.mjs:70-99`).
- Approved `PreToolUse` decisions are cached and replayed for `PermissionRequest`, preventing the browser from opening twice (`server/index.ts:84-90`, `server/index.ts:145-155`; `server/runtime/decisionCache.ts` is referenced by those lines).

### Risks and pitfalls

- The local server binds to `localhost` on an ephemeral port, but the API has no authentication or request-origin check (`server/index.ts:110-117`; `server/api.ts:4-6`). Any local process able to discover the port can call `/api/approve` or `/api/deny`; a browser page or local tool could potentially race or force a decision. This is a meaningful security boundary for a localhost approval UI, even though the product is intentionally local.
- `/api/deny` casts parsed JSON directly to `{ annotations: Annotation[] }` and passes it to `serializeAnnotations` without checking that the body is an object, that `annotations` is an array, or that each annotation has the expected shape (`server/api.ts:55-62`). Malformed input can produce a 500 or unexpected serialization. By contrast, `/api/settings` performs an explicit boolean check (`server/api.ts:19-44`).
- Hook stdin is cast to `HookEvent` after JSON parsing; validation is limited to finding a non-empty plan, with no schema checks for event name, tool name, or nested fields (`server/runtime/input.ts:71-93`). The shared bridge validates returned decision shape, but does not verify `hookEventName` before interpreting `permissionDecision` (`opencode/bridge.js:24-33`; `shared/planReview.mjs:41-62`).
- History is written under a config-derived path using a session key and is only removed after approval; denied plans remain for future review (`server/runtime/history.ts:17-18`, `server/runtime/history.ts:28-67`, `server/runtime/history.ts:69-79`). This is useful for iteration but means plan content can persist locally. The reportable privacy behavior should be explicit in documentation and ideally covered by retention tests.
- The installer follows redirects up to five times and verifies the final bytes against the registry-provided integrity value (`scripts/install-runtime.mjs:175-209`, `scripts/install-runtime.mjs:229-241`). Integrity protects content authenticity, but redirect policy and registry availability still affect install behavior; installation failure causes the Claude hook path not to work until a later session (`scripts/install-runtime.mjs:134-142`).

## Tests and verification

- OpenCode-specific tests cover approved/rejected plain-text tool results and use module mocking to isolate the bridge (`opencode/index.test.ts:22-53`). Configuration tests cover defaults, global config, project-over-global precedence, malformed JSON fallback, and cleanup of temporary fixtures (`opencode/config.test.ts:24-109`).
- Shared tests cover plan-review protocol helpers, runtime resolution, CLI behavior, update messages, package-manager detection, and Pi integration; server tests cover feedback, input, history keys/lifecycle, and update checks. The visible test inventory includes these files, but there is no visible `opencode/bridge.test.*`, `server/api.test.*`, or installer test (`opencode/`, `shared/`, `server/`, and `ui/` test file inventory).
- CI’s required verification command is `bun run typecheck`, `bun run lint`, and `bun test` (`docs/operations.md:15-21`), with build and package smoke tests added in CI (`.github/workflows/ci.yml:30-43`).

**Testing lesson:** pure helper tests plus package/build smoke tests provide useful coverage for an agent plugin, especially around protocol text and packaging. The largest remaining gaps are the subprocess boundary, HTTP decision routes, installer integrity/error paths, and end-to-end approval/rejection lifecycle. Those are the areas most likely to regress without an integration harness.

## Overall assessment

This is a strong example of a multi-host OpenCode integration: the OpenCode surface is a small SDK tool, the UI/runtime is shared, workflow results are explicit, and publication is guarded by platform manifests and pack checks. The main reusable patterns are protocol normalization, stderr-only diagnostics, explicit stateful tool responses, optional platform runtimes, and CI that verifies the actual package shape. The principal cautions are the unauthenticated localhost decision API, unchecked denial payloads, shallow hook-event validation, and limited integration coverage around the bridge and installer.
