## What it is

`opencode-goal-plugin` implements a session-scoped `/goal` workflow that persists a goal, auto-continues on idle, and stops on completion, blockers, or safety limits (`README.md:9-13`). It exposes both a plugin factory and a default descriptor: `GoalPlugin` is returned as `server` with id `opencode-goal-plugin` (`src/goal-plugin.js:6368-6392`). The package is ESM, declares Node `>=18` and OpenCode `>=1.17.15 <2`, and exports both the package root and `./server` (`package.json:5-18`, `package.json:59-61`).

## OpenCode patterns worth reusing

- **Treat host hooks as mutable, version-sensitive boundaries.** The command hook mutates the host-retained `output.parts` array in place because reassigning it may not affect what OpenCode sends to the model (`src/goal-plugin.js:300-324`). The compatibility policy documents that custom commands remain model turns rather than direct TUI rendering, and that command correctness must therefore be self-contained (`docs/compatibility.md:64-82`).
- **Register a complete hook surface, but make features opt-out.** The factory wires command, event, chat, tool, config, compaction, system-transform, and disposal behavior; `registerCommand` and `registerTools` selectively remove command/tool surfaces (`src/goal-plugin.js:6298-6318`). This is a useful pattern for plugins that need to support both slash-command and programmatic integrations.
- **Use synthetic metadata for provenance, not just text markers.** Command and continuation parts carry `metadata["opencode-goal-plugin"]` with a kind and nonce (`src/goal-plugin.js:273-334`). The chat hook only accepts a continuation while its exact runtime-issued nonce is in flight and treats unrelated user turns as interventions (`src/goal-plugin.js:4657-4685`).
- **Model lifecycle as a state machine with bounded budgets.** Defaults cover turns, duration, context tokens, cooldown, no-progress, tool-free turns, prompt failures, and result retention (`src/goal-plugin.js:71-89`). The README explains that token accounting uses peak context size rather than summing repeated context (`README.md:225-245`), a good guard against runaway autonomous loops.
- **Make completion evidence structured and locally validated.** `goal_complete` requires a summary and validates criteria, checks, changed files, and limitations before serialization; failed checks and empty evidence are rejected (`src/goal-plugin.js:3591-3609`, `src/completion-claim.js:20-25`, `src/completion-claim.js:57-109`). This keeps malformed or oversized claims out of persisted state and verifier prompts.
- **Keep independent verification least-privileged.** The native verifier is hidden, default-deny, and allowed only `read`, `glob`, and `grep`; shell execution and goal mutation tools are disabled (`src/native-agent-config.js:37-65`). The README also states that the built-in auditor fails closed by default (`README.md:378-402`).
- **Adapt SDK shapes without replaying mutations.** The session adapter remembers the successful argument shape per operation and only retries read-only operations after a shape-like `TypeError`; mutating calls are deliberately never replayed (`src/opencode-session-api.js:8-17`, `src/opencode-session-api.js:40-61`). This is a strong compatibility pattern for evolving generated clients.
- **Scope runtime state per plugin instance.** `AsyncLocalStorage` and runtime-bound collections avoid module-global state leaking across workspaces when OpenCode caches imported modules (`src/goal-plugin.js:91-163`). Hook and tool functions are rebound to the instance runtime, and disposal aborts continuations, flushes persistence, and releases leases (`src/goal-plugin.js:6321-6364`).

## Persistence and concurrency lessons

- State defaults to project-local `.opencode/goals/state.json`, then shards by SHA-256(session ID); state and ledger files are owner-only, and the append-only ledger supports recovery when state is missing or corrupt (`README.md:247-259`). This gives unrelated sessions concurrency without allowing same-session last-writer-wins behavior.
- Same-session processes use an immutable claim/lease protocol and passive mode. A contender retains ordinary chat but cannot read or mutate the goal workflow; recovered active goals load paused and require explicit resume (`README.md:260-267`, `docs/compatibility.md:29-54`).
- The lease implementation validates file types, rejects symlinks, bounds owner records, uses `O_NOFOLLOW` where available, and atomically writes JSON with mode `0600` (`src/persistence-lease.js:101-113`, `src/persistence-lease.js:144-192`, `src/persistence-lease.js:235-243`). These are concrete defenses for state-path tampering and races.
- A useful testable invariant is that terminal ledger entries are written before the state write, so completion/block outcomes survive a subsequent state-write failure (`README.md:257-260`).

## Pitfalls and residual risks

- The implementation depends on experimental OpenCode hooks and multiple SDK request shapes; the README explicitly requires retesting against the exact OpenCode build and provider/backend (`README.md:13`, `README.md:40-53`). Hook behavior can change without a compile-time signal.
- Custom command output still passes through the model, so visible responses can summarize or paraphrase plugin-generated control results (`README.md:408-418`). The plugin compensates with escaped control frames, tool blocking, parent correlation, and assistant suppression, but this is defense in depth rather than a direct-render guarantee.
- Auto-continuation increases the number of opportunities for already-authorized tools to run. The security policy correctly says the plugin is not a sandbox and relies on OpenCode permissions, provider trust, repository instructions, and the local account (`SECURITY.md:18-30`). Unattended use in untrusted workspaces remains risky.
- Persistence contains objectives, constraints, checkpoints, blockers, paths, and reported commands. Owner-only modes are not encryption, and rotated ledgers retain sensitive text until deletion (`SECURITY.md:42-46`). The repository `.gitignore` does not include `.opencode/goals/`, so users must add the state directory themselves (`.gitignore:1-4`, `README.md:247-248`).
- Completion markers remain model-authored when auditing is disabled; even the optional verifier is not cryptographic attestation and may share provider failure modes (`SECURITY.md:48-56`, `README.md:408-410`). Keep the default reject/fail-closed policy for higher-assurance workflows.
- The main entrypoint is very large (`src/goal-plugin.js`, 6,456 lines), increasing regression and maintenance risk despite extracted persistence, SDK, agent-config, and claim modules. The broad test surface mitigates this but does not remove the architectural cost.

## Testing lessons

- The project uses Node's built-in test runner and separates ordinary tests, coverage, mutation contracts, type contracts, smoke tests, packed-artifact contracts, behavior benchmarks, and verification (`package.json:37-50`). This is a useful layered model for plugin testing.
- CI covers Node 18/20/22/24, runs locked installs, and adds Linux/macOS/Windows filesystem tests (`.github/workflows/ci.yml:18-38`, `.github/workflows/ci.yml:73-101`). The test matrix explicitly exercises persistence leases, lifecycle, public-hook cancellation, and session concurrency.
- Tests assert host integration details rather than only helper outputs. For example, the packed-host contract requires all hooks and 11 tools, validates config-created agents, preserves the original parts-array identity, and checks synthetic command metadata (`scripts/packed-host-contract.mjs:26-38`, `scripts/packed-host-contract.mjs:121-166`).
- Concurrency tests spawn separate Node processes and verify independent session shards plus migration-lock serialization (`test/session-concurrency.test.js:17-65`, `test/session-concurrency.test.js:73-139`, `test/session-concurrency.test.js:142-160`).
- Cancellation tests cover duplicate idle-event coalescing and abort/dispose while an SDK read is pending, proving that no continuation is sent after invalidation (`test/public-hook-cancellation.test.js:72-125`, `test/public-hook-cancellation.test.js:127-140`). These are high-value tests for asynchronous hook code.
- The deterministic behavior benchmark covers successful completion, false completion, self-chat loops, interruption, compaction, and restart without requiring a provider call (`scripts/behavior-benchmark.mjs:140-253`). This is a strong way to test autonomy safety reproducibly.

## Packaging and release lessons

- `files` explicitly whitelists source, scripts, examples, demo, docs, declarations, policy files, and license; `exports` provides typed root and server paths (`package.json:8-35`). This reduces accidental package contents while preserving consumer documentation and contracts.
- The release gate runs syntax/unit tests, coverage, TypeScript consumer compilation, mutation testing, behavior benchmarks, source and packed smoke tests, production `npm audit`, and `npm pack --dry-run` (`package.json:41-50`).
- Release CI verifies that a `vX.Y.Z` tag matches `package.json`, runs the complete gate, builds the tarball, and uploads the exact artifact (`.github/workflows/release-check.yml:23-37`).
- The package includes a runtime `zod` dependency because the installed artifact must expose tool schemas without a separately installed OpenCode helper (`package.json:74-79`, `docs/compatibility.md:17-21`). The packed-tool contract is therefore important, not optional packaging polish.
- The declared `bin` points to `scripts/verify.mjs`, while the package's primary runtime remains the plugin entrypoint (`package.json:20-22`, `package.json:5-18`). Keeping verification available as an installed executable is a practical operational aid.

## Bottom line

The most transferable design is the combination of explicit hook provenance, bounded autonomous continuation, per-instance runtime isolation, session-sharded persistence with single-writer leases, structured completion claims, and fail-closed optional auditing. The main adoption risks are OpenCode's experimental host contract, model-mediated command rendering, sensitive local persistence, and the fact that auto-continuation amplifies the permissions already granted to the agent.
