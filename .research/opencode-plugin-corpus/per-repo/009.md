## Architecture And SDK Patterns

- The entrypoint is a typed async plugin export: `import type { Plugin, PluginInput } from "@opencode-ai/plugin"`, with `export const BeadsPlugin: Plugin = async ({ client, $ }) => ...` (`src/plugin.ts:12-15,95-96`). `PluginInput["client"]` is reused as a local client type (`src/plugin.ts:15`).
- The plugin registers three surfaces in the returned object: `chat.message`, `event`, and `config` (`src/plugin.ts:128-193`). This is a compact example of combining message interception, lifecycle events, and startup configuration mutation.
- `chat.message` injects context once per session. It uses `output.message.sessionID`, checks the resolved agent, checks existing messages for a `<beads-context>` marker, and sends a synthetic `client.session.prompt` with `noReply: true` (`src/plugin.ts:128-175`). Passing through `model` and `agent` explicitly avoids changing the active mode/model (`src/plugin.ts:78-87,166-171`).
- The `session.compacted` event rehydrates context after compaction by querying recent messages to recover the last user model/agent (`src/plugin.ts:177-186; getSessionContext at 27-51`). This is a useful pattern when an event lacks direct message context.
- `config` merges generated command and agent definitions rather than replacing existing configuration: `config.command = { ...config.command, ...commands }` and the equivalent for agents (`src/plugin.ts:189-192`).
- Commands and a subagent are loaded from vendored Markdown at plugin initialization (`src/plugin.ts:95-96; src/vendor.ts:153-199`). Frontmatter supplies descriptions and argument hints, while the Markdown body becomes the command template or agent prompt (`src/vendor.ts:18-66,182-196`). Commands are named `beads:<filename>` (`src/vendor.ts:185-196`); the README’s older `/bd-*` wording conflicts with the current implementation (`README.md:42-46,54-56`; `src/vendor.ts:185`).

## Context, Tools, And Process Boundaries

- The external beads CLI is invoked through OpenCode’s shell interpolation API, `$\`bd prime\`` (`src/plugin.ts:59-70`). The result is wrapped in explicit `<beads-context>` tags and combined with static operational guidance (`src/plugin.ts:72-76`).
- The injected guidance deliberately tells the model that no `bd` tool exists and to use the `bash` tool for CLI operations (`src/vendor.ts:87-110`). It also directs multi-command work to the `beads-task-agent` and reserves direct CLI use for atomic operations (`src/vendor.ts:132-151`).
- The plugin defines `beads-task-agent` as a `subagent` with a prompt assembled from CLI guidance, delegation context, and the vendored agent body (`src/vendor.ts:153-169`). The vendored task workflow requires claim-before-work, dependency linking, verification, and closure (`vendor/agents/task-agent.md:5-45`).
- Primary/all agents receive context; known subagents are skipped to avoid token waste and unintended `bd`/git work. The plugin queries `client.app.agents()` freshly, with `beads-task-agent` as an explicit exception (`src/plugin.ts:101-125`).
- There is no auth, provider, model registration, custom tool, command handler, persistent state store, or network API integration in the plugin. Its only process boundary is the `bd` subprocess; its only state is an in-memory `Set<string>` of injected session IDs (`src/plugin.ts:98,128-175`).

## Error Handling, Concurrency, And Security

- Most optional integration failures are intentionally fail-open and silent: message lookup, `bd prime`, prompt injection, and agent discovery catch errors and either skip or fall back (`src/plugin.ts:34-50,66-91,118-125,142-164`). This keeps OpenCode usable when beads is absent, but gives users no diagnostic path.
- `injectedSessions` is marked before the asynchronous injection completes (`src/plugin.ts:166-172`). A failed prompt therefore will not retry during that process lifetime. The set is process-local, so reloads/restarts lose it; the message-marker scan partly handles reload/reconnection (`src/plugin.ts:142-160`).
- `chat.message` and `session.compacted` can both race around compaction or repeated lifecycle delivery. The marker check helps, but the check-then-write sequence is not atomic (`src/plugin.ts:142-171`).
- The plugin executes `bd prime` in the workspace and injects its stdout into the model context without validation or size limiting (`src/plugin.ts:66-76`). Treat CLI output as untrusted prompt input; delimiters help readability but do not establish a security boundary.
- Vendor file reads catch all errors and return empty results (`src/vendor.ts:69-85`), so missing package assets silently remove commands/agents. The simple frontmatter parser only handles scalar `key: value` lines and quoted strings (`src/vendor.ts:23-66`), which is intentionally lightweight but can lose richer upstream metadata.
- The README recommends piping a remote installer directly to Bash (`README.md:14-20`). That is convenient but should be treated as a supply-chain risk; package installation and the runtime `bd` dependency should be documented with verification/version guidance.

## Packaging, Installation, And Maintenance

- The package is ESM and publishes `src`, `vendor`, and `README.md`; `main` points directly to `src/plugin.ts` (`package.json:2-5,19-20`). Dependencies include matching `@opencode-ai/plugin` and `@opencode-ai/sdk` versions plus `zod`, although this source does not directly use `zod` (`package.json:24-27`). Bun >= 1 is declared (`package.json:34-36`).
- Installation is an OpenCode config entry, optionally pinned to `opencode-beads@0.7.0`; the README explains unpinned startup fetching versus pinned caching (`README.md:22-40`).
- Upstream beads content is vendored and synchronized by a script that resolves the newest remote tag, shallow-clones that tag, replaces command/agent files, updates the changelog, then creates/pushes a branch and optionally opens a PR (`scripts/sync-beads.sh:8-24,31-67`). This keeps the plugin decoupled from upstream layout at runtime, but the script is network- and shell-tool-dependent and chooses the newest tag rather than a pinned source revision.
- Release CI uses frozen Bun installation, typecheck, `bun pm pack`, GitHub artifact attestation, and npm publish (`.github/workflows/release.yml:20-57`). CI actions are commit-pinned and checkout disables persisted credentials (`.github/workflows/release.yml:16-18,21,36,50`). PR/push CI only typechecks (`.github/workflows/lint.yml:1-34`).
- Versioning is semver-oriented and changelog-driven (`CHANGELOG.md:1-6`). The current unreleased section contains duplicate sync-style entries and the README still advertises `/bd-*` while generated commands use `beads:` (`CHANGELOG.md:19-24; README.md:42-46; src/vendor.ts:185`), indicating documentation drift worth testing in release checks.

## Strengths

- Small, clearly bounded integration surface that delegates domain behavior to the upstream beads project (`README.md:5-10`).
- Correctly preserves the active model/agent when creating synthetic context (`src/plugin.ts:78-87`).
- Handles compaction and plugin reload/reconnection rather than assuming one startup event (`src/plugin.ts:142-160,177-186`).
- Avoids polluting subagents and merges config instead of clobbering other plugins (`src/plugin.ts:115-125,189-192`).
- Vendoring plus explicit sync automation makes upstream command/agent content reproducible in published packages (`src/vendor.ts:13-16; scripts/sync-beads.sh:18-24; package.json:19-20`).
- Release workflow has strong modern supply-chain practices: frozen lockfile, commit-pinned actions, least permissions at lint, and provenance attestation (`.github/workflows/lint.yml:13-20; .github/workflows/release.yml:11-18,26-37`).

## Pitfalls And Reusable Lessons

- Add tests around lifecycle idempotency and concurrency. A durable marker or per-session promise/state machine is safer than setting a `Set` entry before the injection succeeds.
- Preserve user context when synthesizing messages: carry model and agent fields and use `noReply`/synthetic parts, as shown at `src/plugin.ts:80-87`.
- Make optional integrations fail soft, but expose debug logging or a status command; completely silent catches make missing binaries, permissions, and API regressions difficult to diagnose.
- Treat subprocess output as untrusted context. Bound output size, identify its source, and avoid assuming XML-like tags prevent prompt injection.
- Generate commands/agents from data files when upstream content changes frequently, but validate frontmatter and add a packaging smoke test that loads every published asset.
- Merge config namespaces rather than overwrite them, and explicitly define collision behavior for command/agent names (`src/plugin.ts:189-192`).
- Keep installation docs, generated command names, changelog, and package version synchronized; a simple documentation assertion would have caught the `/bd-*` versus `beads:` drift.
- Typechecking is not sufficient for plugin behavior. Add mocked client/`$` tests for `chat.message`, `session.compacted`, agent filtering, failed `bd`, malformed vendor files, and duplicate delivery.
- Pin or record the upstream vendor revision during sync instead of relying only on “latest tag”; review generated prompt changes as code because they alter agent behavior.
