- The README defines the project as an OpenCode plugin that loads `.envrc` variables at session start, with upward search from the project directory to a Git root and graceful skipping when direnv or `.envrc` is absent (`README.md:31-41`).

## SDK and registration

- The package is ESM and publishes `dist/index.js` plus declarations, while its source entrypoint is `src/index.ts`; the only build script is `tsc` (`package.json:2-14`).
- The source imports the OpenCode `Plugin` type and exports a named `DirenvLoader` plugin function receiving `{ client, $, directory }` (`src/index.ts:1`, `src/index.ts:50-53`). No default export is present in the inspected source.
- Registration is returned as an object with one `event` handler (`src/index.ts:160-195`). This is a minimal lifecycle registration pattern rather than a tool or command registration.
- The plugin casts the SDK client and shell helper to narrow local interfaces for TUI toast and shell operations (`src/index.ts:20-48`, `src/index.ts:52-53`). This keeps the implementation small but shifts API-shape validation to compile-time assumptions and casts.

## Hooks, events, and context

- The plugin listens for `session.created`, extracts the session ID from `event.properties.info.id`, and ignores other event types (`src/index.ts:161-165`).
- A process-local `Set<string>` prevents duplicate loading for a session ID (`src/index.ts:51`, `src/index.ts:166-170`). This is an effective idempotency guard within one plugin process, but it is not persisted across process restarts.
- The configured plugin `directory` is the search starting point. The implementation first runs `git rev-parse --show-toplevel`; failure is treated as “no Git root” (`src/index.ts:58-65`, `src/index.ts:113-118`).
- `findEnvrc` walks parent directories until the Git root, filesystem root, or a same-parent guard, returning the first `.envrc` it finds (`src/index.ts:68-101`). This makes repository-root configuration discoverable while allowing a nearer `.envrc` to win.
- The event handler uses `client.tui.showToast` for blocked files and successful loads (`src/index.ts:172-190`). There are no other hooks, message handlers, command handlers, or context/session storage mechanisms.

## Tools and commands

- No OpenCode tools or slash commands are registered. The only subprocess operation is the internal `direnv export json` call, run in the directory containing the discovered `.envrc` (`src/index.ts:125-134`).
- The shell abstraction supports `cwd`, `quiet`, and `text`; the plugin captures textual output and parses it as a string map (`src/index.ts:39-48`, `src/index.ts:131-138`).
- README installation is configuration-only: users add `@simonwjackson/opencode-direnv` to project or global `opencode.json`, after which OpenCode installs it (`README.md:55-77`).

## Auth and providers

- No authentication, credential storage, model provider, provider factory, or API integration is implemented. The package has only the OpenCode plugin peer dependency and TypeScript/Node development dependencies (`package.json:33-40`).
- The intended external dependency is the local `direnv` executable, which must be on `PATH` and is documented as version `>=2.0.0` (`README.md:45-51`).

## State and processes

- `direnv export json` is executed once per session event and its returned variables are assigned to the Node process environment with `Object.assign(process.env, envVars)` (`src/index.ts:166-184`). Child processes subsequently inherit those values, as the README explains (`README.md:132-144`).
- The implementation catches failures around Git detection, file discovery, command execution, and JSON parsing; absent direnv, absent `.envrc`, malformed output, and other failures generally produce no notification (`src/index.ts:106-157`; `README.md:156-162`).
- A blocked `.envrc` is detected by inspecting an error object's `stderr` for the literal text `"is blocked"`; the user receives a warning with the prescribed `direnv allow` remediation (`src/index.ts:139-150`, `src/index.ts:172-179`).
- The README explicitly documents single-load behavior, no unload, and persistence until the session ends (`README.md:166-173`). In implementation terms, assigning to global `process.env` means the state is process-wide rather than intrinsically session-scoped; the `Set` only controls when loading occurs.

## Configuration

- There is no plugin-specific configuration schema or environment-variable configuration. Behavior is controlled by the OpenCode plugin location, the supplied `directory`, Git ancestry, and direnv's own allow/cache state (`src/index.ts:50`, `src/index.ts:70-101`, `README.md:61-77`).
- TypeScript is configured for strict ES2022 NodeNext compilation with declarations and source maps, writing from `src` to `dist` (`tsconfig.json:2-17`).
- The repository includes a Nix development shell for Node 22, TypeScript, and `just` across Linux and Darwin systems (`flake.nix:4-24`), and ignores `.direnv` plus generated `dist` (`.gitignore:1-5`).

## Errors and security

- The plugin deliberately fails closed from a user-interface perspective: broad catches suppress missing executables, missing files, command failures, and parse failures (`src/index.ts:113-157`). This avoids startup disruption but also hides diagnostics beyond the blocked-file special case.
- `.envrc` is executable shell configuration, and this plugin executes it indirectly through `direnv export json` (`src/index.ts:129-137`). The security boundary is delegated to direnv's allow mechanism; the README calls manual approval a security feature and instructs users to run `direnv allow` (`README.md:166-172`).
- Exported values can include secrets and are copied into `process.env`, making them available to all later child processes in the host process (`src/index.ts:182-184`; `README.md:93-101`). Consumers should treat loading an allowed `.envrc` as granting that environment to every subsequent command, not only to a specific tool invocation.
- `JSON.parse` is performed on command output and is protected by the inner catch (`src/index.ts:133-151`), but the implementation does not validate the parsed value beyond a TypeScript assertion before assigning it to `process.env` (`src/index.ts:137`, `src/index.ts:182-184`).
- The fixed error-string match for `"is blocked"` is brittle across direnv versions/locales, and all other command diagnostics are discarded (`src/index.ts:141-156`).

## Pitfalls and reusable lessons

- Reusable pattern: a session lifecycle event plus a local session-ID set provides a compact once-per-session initializer (`src/index.ts:160-170`).
- Reusable pattern: use the OpenCode-provided working directory, discover repository boundaries with Git, and walk upward for project configuration (`src/index.ts:58-101`).
- Reusable pattern: use structured subprocess output (`direnv export json`) instead of parsing shell text, and isolate the subprocess working directory to the discovered configuration file (`src/index.ts:125-138`).
- Reusable pattern: pair silent handling for optional host capabilities with a targeted TUI notification for actionable user remediation (`src/index.ts:148-157`, `src/index.ts:172-190`).
- Pitfall: mutating `process.env` is global to the plugin process. It can leak variables between sessions or users sharing that process, and the plugin cannot unload overwritten/deleted variables; the README acknowledges persistence but not process-global isolation (`src/index.ts:182-184`; `README.md:166-173`).
- Pitfall: loading is tied to the plugin's initial `directory`, not a per-event session directory, so sessions rooted elsewhere may receive the same environment if one plugin instance serves multiple directories (`src/index.ts:50`, `src/index.ts:114-118`).
- Pitfall: broad catches and no tests leave regressions in path traversal, event payload shape, shell error formats, malformed exports, and environment collision behavior undetected (`src/index.ts:58-65`, `src/index.ts:139-157`; `.github/workflows/ci.yml:19-26`).
- Lesson for dependent plugins: this repository demonstrates a focused provider-free integration. It is useful as an event/context/environment pattern, but should be augmented with explicit diagnostics, schema validation, per-session isolation, and behavioral tests before being generalized for sensitive credentials.
