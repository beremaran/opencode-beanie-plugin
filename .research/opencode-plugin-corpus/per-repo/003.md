## Pattern Summary

### SDK, registration, lifecycle, and context

- Imports the plugin contract and tool definition type from `@opencode-ai/plugin` and exports a typed async plugin function (`src/plugin.ts:1`, `20`). The package exposes that source entrypoint through `main` and ships only `src` (`package.json:11-15`).
- Registration is return-object based: the plugin returns hooks plus a `tool` map containing three memory tools and, conditionally, three journal tools (`src/plugin.ts:48-78`). There is no command registration or separate server process.
- Uses `chat.message` as a lifecycle hook to mutate a closure-owned journal context with the active model/provider IDs (`src/plugin.ts:28-33`, `49-54`). Tool execution then records that context plus agent/session IDs from `toolCtx` (`src/tools.ts:70-74`, `90-107`). This is a simple per-plugin-instance context bridge, but it assumes the message hook runs before a journal write.
- Uses `experimental.chat.system.transform` to read blocks, render them, and mutate `output.system` with `splice`/`push` (`src/plugin.ts:56-69`). It inserts memory near the provider header for salience/cache stability and appends journal instructions separately.

### Context mutation and prompt design

- Memory is rendered as structured XML-like sections with instructions, metadata, scopes, character limits, read-only state, and line-numbered values (`src/prompt.ts:22-71`). Stable sorting puts canonical global/project blocks first and alphabetizes the rest (`src/memory.ts:154-173`), explicitly targeting prompt-cache stability.
- Descriptions escape `&`, `<`, and `>` before prompt insertion (`src/prompt.ts:35-40`), but block labels become element names and values are not XML-escaped (`src/prompt.ts:46-62`). Since blocks can be edited by the agent, prompt-format injection or malformed XML remains a risk.
- The prompt carries strong behavioral instructions adapted from Letta, including self-editing and scope semantics (`src/letta.ts:10-34`). Vendored attribution and source URL are documented (`src/letta.ts:1-8`).

### Tools and configuration

- Tools use the SDK `tool()` helper and `tool.schema` validators, with explicit descriptions and bounded enum/numeric/string arguments (`src/tools.ts:6-27`, `30-67`, `76-111`, `114-199`). Mutations default to project scope as the safer default; listing defaults to all scopes (`src/tools.ts:12-16`, `40-47`, `61-65`).
- Journal tooling is opt-in from `~/.config/opencode/agent-memory.json`; invalid/missing config degrades to `{}` and disables it (`src/plugin.ts:24-46`; `src/journal.ts:16-39`). Suggested tags are schema-validated and injected into journal instructions (`src/journal.ts:11-23`, `341-357`).
- Installation is a normal OpenCode npm plugin entry in `opencode.json`, with optional version pinning; local development uses a symlink to `src/plugin.ts` (`README.md:21-55`). The README documents global and project storage locations and the configuration example (`README.md:95-139`).
- There is no auth implementation, provider/model registration, or external API credential handling. Embeddings run locally with a dynamically imported Hugging Face pipeline (`src/embeddings.ts:1-21`); the first use may download/cache the model.

### Persistence, state, concurrency, and process boundaries

- Memory blocks are Markdown files with YAML frontmatter, stored globally under `~/.config/opencode/memory` or project-locally under `.opencode/memory` (`src/memory.ts:120-130`). First initialization seeds `persona`, `human`, and `project`, and creates a project `.gitignore` containing `*` (`src/memory.ts:176-197`, `141-152`).
- Frontmatter uses Zod validation and defaults for label, description, limit, and read-only status (`src/memory.ts:25-46`, `50-77`). Labels are constrained before direct reads/writes to prevent path traversal (`src/memory.ts:97-105`, `227-245`). Journal IDs receive a separate safe-character check (`src/journal.ts:130-137`, `221-231`).
- Writes are temp-file-plus-rename atomic replacements (`src/frontmatter.ts:37-47`), and mutation enforces read-only and character limits (`src/memory.ts:239-293`). There is no mutex or cross-process locking; concurrent writers can lose updates, and journal filenames can collide within the same millisecond (`src/journal.ts:72-81`, `170-190`).
- Journal entries are append-only Markdown plus optional `.embedding` sidecars. Search scans all entries, applies AND metadata filters, then semantic-scores or falls back to substring matching, with bounded pagination (`src/journal.ts:234-337`). This is easy to inspect and portable, but O(number of journal files) per search and synchronous per-entry file/embedding reads do not scale.
- Embedding/model failures are intentionally non-fatal: the journal entry remains saved and text search remains available (`src/journal.ts:192-204`, `255-263`).

### Error handling and security

- Expected validation and missing-resource errors are explicit (`src/memory.ts:227-258`, `269-283`; `src/journal.ts:221-229`). Invalid memory files are skipped silently during listing so one malformed file does not hide all blocks (`src/memory.ts:210-224`), but this also obscures corruption and gives no diagnostic path.
- YAML/JSON inputs are parsed and validated with `js-yaml`/Zod (`src/memory.ts:34-45`; `src/journal.ts:27-39`, `88-117`). Path traversal defenses cover labels and journal IDs, but direct filesystem edits remain trusted and there is no permission hardening for globally stored sensitive memory.
- Project memory is automatically ignored by Git (`src/memory.ts:141-152`), reducing accidental leakage. Journal metadata intentionally records absolute project path, model, provider, agent, and session (`src/tools.ts:98-106`; `src/journal.ts:177-187`), so users should treat journal files as sensitive local data.
- CI demonstrates a security-conscious baseline: minimal workflow permissions, pinned action SHAs, disabled checkout credentials, and a zizmor scan (`.github/workflows/test.yml:9-23`; `.github/workflows/zizmor.yml:16-43`).

### Testing, packaging, and versioning

- Tests cover seed/write/read memory behavior (`src/memory.test.ts:12-28`), config validation and journal metadata/read/path traversal/search filters/pagination/semantic path (`src/journal.test.ts:37-384`), and prompt structure/ordering/line numbering (`src/prompt.test.ts:5-139`). Embeddings are mocked to avoid model downloads and make tests deterministic (`src/journal.test.ts:7-31`).
- Package scripts are minimal (`bun test`, `tsc --noEmit`), with strict TypeScript and unchecked-index checking configured (`package.json:16-18`; `tsconfig.json:5-11`). At this snapshot, `bun test` passed 27 tests; `bun run typecheck` failed in the clone because `@tsconfig/bun/tsconfig.json` was unavailable, followed by a `moduleResolution: bundler` compiler-option error.
- CI separates tests and typecheck and uses frozen Bun installs (`.github/workflows/test.yml:25-34`; `.github/workflows/lint.yml:25-34`). Release builds a tarball, attests it, uploads the GitHub release asset, and publishes to npm using trusted-publishing-oriented permissions (`.github/workflows/release.yml:7-57`).
- Version `0.2.0` adds the optional journal; the changelog documents the initial memory architecture and hook (`CHANGELOG.md:19-46`). Package metadata pins the OpenCode SDK minimum dependency at `^1.0.115` and requires Bun >=1 (`package.json:20-24`, `36-38`).

## Strengths

- Small, idiomatic OpenCode plugin surface: one typed entrypoint, explicit hooks, and SDK-native tools.
- Clear separation between plugin orchestration, prompt rendering, file stores, frontmatter, and embedding/search concerns.
- Safe-by-default project mutation scope, path-safe identifiers, size limits, read-only blocks, atomic file replacement, and graceful embedding fallback.
- Strong local-first privacy story for semantic search, with portable human-readable Markdown persistence.
- Good test seams: store factories accept directories, config accepts an override directory, and embedding is mocked.
- CI supply-chain hygiene is unusually concrete for a small plugin: pinned action commits, least-privilege permissions, frozen lockfile, typecheck, and workflow linting.

## Pitfalls / Anti-Patterns

- Treating user/agent-editable content as XML without escaping values and labels can corrupt the injected structure or create prompt-boundary ambiguity (`src/prompt.ts:35-62`). Escape all dynamic fields or use a serialization format whose delimiters cannot be authored by memory content.
- Closure state updated by a separate lifecycle hook is ordering-sensitive and not concurrency-safe (`src/plugin.ts:28-54`). Prefer request/session-scoped context when the SDK provides it, or define behavior when model metadata is unavailable.
- Atomic rename prevents partial files but not lost updates; add locking/version checks if multiple OpenCode processes can mutate shared global memory (`src/frontmatter.ts:37-47`; `src/memory.ts:239-293`).
- Timestamp-only journal IDs can collide under fast/concurrent writes (`src/journal.ts:72-81`, `170-176`). Add a unique suffix or retry on `EEXIST`.
- Silently swallowing malformed block files and embedding errors improves availability but weakens observability (`src/memory.ts:216-220`; `src/journal.ts:200-204`). At least provide debug logging or a diagnostic tool.
- Full directory scans and one-file-at-a-time embedding loads are appropriate for an experimental local journal, not a large corpus (`src/journal.ts:240-337`).
- The release workflow does not run the full test suite before publishing; it runs typecheck and packaging only (`.github/workflows/release.yml:26-34`).

## Reusable Development-Bible Lessons

1. Make the plugin entrypoint boring: initialize state once, return hooks/tools, and keep feature-specific stores in separate modules.
2. Use SDK tool schemas and descriptions as part of the agent-facing API; choose conservative defaults for mutations.
3. Treat prompt injection as serialization: escape every dynamic field, keep stable ordering, and preserve cache-friendly static chunks.
4. Separate durable local state from OpenCode config, validate both at the boundary, and make optional subsystems fail closed or degrade explicitly.
5. Combine atomic writes with an explicit concurrency strategy; atomicity alone does not prevent lost updates.
6. Test tool-adjacent stores with temporary directories, mock heavyweight model/process boundaries, and include traversal, malformed-input, pagination, and fallback cases.
7. Ship plugins as directly consumable source packages with a documented `opencode.json` entry, local symlink workflow, pinned-version guidance, and CI that verifies tests, types, package contents, and workflow security.
