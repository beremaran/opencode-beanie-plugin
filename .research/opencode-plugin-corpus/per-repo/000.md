## Pattern Inventory

### SDK imports, registration, and lifecycle

- The entrypoint imports `Plugin`, `PluginInput`, and `Hooks` types from `@opencode-ai/plugin`, SDK event/session types from `@opencode-ai/sdk`, and exports only the default plugin function (`src/index.ts:1-22`, `src/index.ts:57-60`, `src/index.ts:230-243`). The repository explicitly tests the bundled default-only export contract (`src/build.test.ts:22-52`).
- The async plugin factory loads configuration, initializes shared state, conditionally constructs hooks, and returns the OpenCode hook object (`src/index.ts:57-127`). This is a useful composition boundary: construction owns dependencies; individual hooks remain small.
- Supported lifecycle surfaces include `config`, `tool.execute.after`, `chat.params`, experimental `session.compacting`, and `event` (`src/index.ts:119-226`). The event dispatcher switches on typed session/LSP events and delegates background tracking before event-specific work (`src/plugin/event-handler.ts:185-239`).
- `session.created`, `session.idle`, and `session.deleted` are used for banners, TODO reminders, task completion polling, and cache cleanup (`src/plugin/event-handler.ts:59-131`, `src/plugin/event-handler.ts:201-237`; `src/tools/lib/background-manager.ts:1556-1579`). Unknown events are deliberately ignored and tested (`src/integration.test.ts:175-195`).

### Context mutation and agent registration

- The `config` hook mutates the supplied OpenCode config in place: it defaults `default_agent` to `monarch`, registers enabled shadow agents, augments `experimental.primary_tools`, and applies built-in agent overrides (`src/plugin/config-handler.ts:49-100`, `src/plugin/config-handler.ts:205-249`).
- Agent definitions are data-driven, typed against the SDK `Agent` shape, and include mode, model, prompt, steps, permissions, and options (`src/agents/shadows.ts:1-18`, `src/agents/shadows.ts:39-76`). The config hook resolves user/model/AUTO fallbacks and records AUTO decisions in runtime cache (`src/plugin/config-handler.ts:100-151`).
- Permission policy is explicit per shadow, including file, network, and execution capabilities (`src/agents/shadows.ts:47-74`, `src/agents/shadows.ts:730-784`). The implementation also prevents recursive delegation by adding Arise delegation tools and `task` to primary tools (`src/plugin/config-handler.ts:85-97`).

### Tools and commands

- Tools are built from a central map and filtered by configured disabled tools before being returned as `hooks.tool` (`src/tools/index.ts:32-79`). The tool set covers synchronous summoning, background launch/status/output/cancel, model listing, continuation, debugging, git summary, and collaboration (`src/tools/index.ts:37-61`).
- Tool schemas are Zod-backed and descriptions are treated as agent-facing behavioral instructions, not merely UI text (`src/agents/shadows.ts:92-149`, `src/agents/shadows.ts:153-235`). `tool2` supplies an explicit return type to avoid non-portable inferred Zod declaration types (`src/types/types-opencode.ts:80-91`).
- Synchronous delegation creates or reuses an isolated session, resolves a model, sends `session.prompt`, then retrieves the last assistant message (`src/tools/arise-summon.ts:71-141`, `src/tools/arise-summon.ts:143-180`, `src/tools/arise-summon.ts:241-290`). Background delegation returns task and session identifiers while routing execution through `BackgroundManager` (`src/tools/arise-summon.ts:203-239`).
- The package also ships a Bun CLI. `bunx @bluelovers/opencode-arise install` registers the plugin and creates a default config; `doctor` diagnoses registration/config state (`README.md:18-41`, `src/cli/index.ts:53-137`, `src/cli/index.ts:139-220`).

### State, concurrency, and process boundaries

- Background state is an in-memory `Map<string, IBackgroundTask>` owned by one `BackgroundManager` instance (`src/tools/lib/background-manager.ts:46-69`). Tasks record parent/session IDs, explicit background status, shadow, timing, retries, errors, and tool permissions (`src/tools/lib/background-manager.ts:900-930`).
- Fire-and-forget work uses SDK `session.promptAsync`; completion is checked by scheduled polling and eagerly rechecked on `session.idle` (`src/tools/lib/background-manager.ts:981-1043`, `src/tools/lib/background-manager.ts:1059-1119`, `src/tools/lib/background-manager.ts:1556-1579`). Cancellation calls SDK `session.abort` but records cancellation as task error (`src/tools/lib/background-manager.ts:1521-1545`).
- Retry/auto-resume has layered runtime overrides, config gates, permanent-error suppression, target filtering, retry limits, and delay/backoff settings (`src/tools/lib/background-manager.ts:234-337`, `src/config/schema.ts:118-192`). Manual retry creates a new session and updates task state (`src/tools/lib/background-manager.ts:1594-1685`).
- The plugin uses OpenCode SDK sessions as the process boundary rather than spawning child processes. There is no plugin-owned durable queue or cross-process persistence; runtime cache/task state is process-local (`src/index.ts:94`, `src/tools/lib/background-manager.ts:46-69`, `src/utils/session/session-cache.ts:1-80`).

### Configuration and provider/model wiring

- Configuration is loaded from global `~/.config/opencode/opencode-arise.json` and project `{worktree}/.opencode/opencode-arise.json`, with project values overriding global values through deep merge (`src/config/io.ts:500-565`, `src/config/paths.ts:155-176`, `README.md:133-193`).
- Zod validates the merged config with safe fallback to generated defaults on invalid input (`src/config/io.ts:430-454`). The schema covers disabled agents/hooks/tools, per-agent model overrides, output shaping, compaction, polling/retry, auto-resume, and safety prompts (`src/config/schema.ts:118-192`, `src/config/schema.ts:231-260`).
- Model wiring is OpenCode-native: model strings are resolved into provider/model bodies and passed to `session.prompt`/`promptAsync` (`src/tools/arise-summon.ts:147-159`, `src/tools/arise-summon.ts:250-258`, `src/tools/lib/background-manager.ts:944-957`). `arise-list-models` queries configured providers/models through the SDK (`src/tools/arise-list-models.ts:62-161`). There is no independent OAuth/API-key provider implementation in this repository; authentication is delegated to OpenCode/provider configuration.

### Context mutation and output safety

- `chat.params` caches the active model and session metadata; `session.deleted` clears model cache (`src/index.ts:168-192`, `src/plugin/event-handler.ts:43-50`).
- The `tool.execute.after` hook mutates `output.output` to preserve complete errors or retain head/tail content when output exceeds a configured limit (`src/index.ts:149-159`, `src/hooks/output-shaper.ts:21-141`).
- The compaction hook appends explicit preservation/pruning rules for TODOs, decisions, touched paths, commands/errors, delegations, and verbose output (`src/index.ts:201-207`, `src/hooks/compaction-preserver.ts:12-35`).

### Error handling and security

- Non-critical TUI/event operations are guarded and logged through OpenCode toast/log helpers; TODO enforcement catches SDK failures without failing the event loop (`src/plugin/event-handler.ts:88-130`). Tool/session failures return formatted error strings and preserve session IDs for diagnosis (`src/tools/arise-summon.ts:121-141`, `src/tools/arise-summon.ts:291-325`).
- Configuration parsing isolates invalid/missing files and falls back to defaults (`src/config/io.ts:523-565`). CLI registration normalizes npm names and supports legacy-name detection (`src/config/io.ts:112-153`, `src/cli/index.ts:94-125`).
- Security-relevant controls are per-agent permissions and disabled shadow/tool lists (`src/agents/shadows.ts:47-76`, `src/tools/index.ts:63-79`). However, some SDK/config casts use `any` and the default primary-agent permission set is broad; permission changes should be reviewed as policy changes, not implementation details (`src/plugin/config-handler.ts:143-151`, `src/types/types-opencode.ts:88-91`).

### Testing, packaging, and installation

- Tests are Bun tests, with integration coverage for plugin construction, returned hooks, config mutation, agent modes, compaction, output shaping, missing config, and unknown events (`src/integration.test.ts:33-195`). Tool behavior and config/schema/path behavior have dedicated tests (`src/tools/tools.test.ts:1-150`, `src/config/io.test.ts`, `src/config/schema.test.ts`, `src/config/paths.test.ts`).
- One comprehensive tool-registration integration test is skipped, leaving the complete active-tool set less directly verified (`src/integration.test.ts:72-95`). Build-output tests require pre-existing `dist` artifacts and therefore are not standalone unit tests (`src/build.test.ts:4-15`, `src/build.test.ts:55-69`).
- CI installs from the lockfile, runs typecheck, build, and tests (`.github/workflows/ci.yml:9-29`). The package builds bundled plugin/CLI output plus declarations, exposes `dist/index.js` and `dist/index.d.ts`, and includes the schema, dist, and banner asset in the published package (`package.json:29-44`, `package.json:52-61`).
- Release gates run tests/build before publishing; the CLI is exposed as `opencode-arise` (`package.json:37-39`, `package.json:62-77`). README installation is both CLI-assisted and direct plugin registration (`README.md:18-41`).

## Strengths

- Clean OpenCode composition: one async default factory owns dependency creation and returns standard hook/tool surfaces.
- Strong agent/tool typing plus runtime Zod validation, generated defaults, and explicit model resolution.
- Practical orchestration lifecycle: isolated sessions, task IDs, status/output/cancel tools, polling, idle-event acceleration, retry gates, and permanent-error handling.
- Good operator ergonomics: install/doctor CLI, global/project config precedence, logs/toasts, and output/compaction safeguards.
- Tests cover the plugin contract and important mutation/error paths, while CI checks type safety, bundling, and runtime tests.

## Pitfalls and Anti-Patterns

- State is process-local. Restarting OpenCode loses `BackgroundManager.tasks` and runtime cache; durable orchestration would need persisted state and recovery (`src/tools/lib/background-manager.ts:46-69`, `src/utils/session/session-cache.ts:1-80`).
- `setTimeout` polling and event-triggered polling can overlap without an evident per-task lock; concurrent completion checks should be guarded if SDK calls or state transitions are not idempotent (`src/tools/lib/background-manager.ts:1118-1119`, `src/tools/lib/background-manager.ts:1570-1575`).
- The code mixes the documented `FakeBun.file` async path with direct `fs-extra` synchronous reads/writes for config and CLI operations (`src/config/io.ts:9-16`, `src/config/io.ts:466-496`, `src/config/io.ts:523-552`). This complicates sandbox portability and makes the stated abstraction incomplete.
- Broad `any`/`@ts-ignore` casts weaken the contract precisely where OpenCode config and tool registration are mutated (`src/index.ts:139-140`, `src/plugin/config-handler.ts:143-151`, `src/types/types-opencode.ts:88-91`).
- Error-pattern detection for output preservation is heuristic and can retain unexpectedly large output up to 2x the configured limit (`src/hooks/output-shaper.ts:61-121`). Treat output limits as approximate, not a hard memory/token boundary.
- The skipped tool-registration test and build tests coupled to `dist` create gaps in fresh-checkout verification (`src/integration.test.ts:72-95`, `src/build.test.ts:4-15`).
- Auto-resume and manual retry create new sessions and mutate task records in several paths; explicit state-transition/duplicate-trigger tests are important (`src/tools/lib/background-manager.ts:234-337`, `src/tools/lib/background-manager.ts:1594-1709`).

## Reusable Development-Bible Lessons

1. Export exactly one runtime plugin value from the package entrypoint; keep public type exports type-only and enforce the bundled export shape in tests (`src/index.ts:230-243`, `src/build.test.ts:22-52`).
2. Treat `config` as an in-place OpenCode mutation hook: initialize absent nested objects, preserve user config, make precedence explicit, and test resulting agent/tool policy.
3. Build tools from a typed registry, use Zod schemas for runtime input validation, and write descriptions as behavioral contracts because agents consume them as instructions.
4. For delegation, isolate work in SDK sessions and return stable task/session identifiers; pair `promptAsync` with both polling and lifecycle events, plus cancellation and bounded retry policy.
5. Keep task state transitions explicit (`running`, `completed`, `error`, `cancelled`), record error text safely, and prevent duplicate retries with a pending flag and idempotent guards.
6. Separate model/provider selection from authentication. Resolve provider/model IDs through the OpenCode SDK and let OpenCode own credentials unless the plugin has a concrete auth feature.
7. Make config resilient: support JSONC, global/project precedence, schema validation, generated defaults, and a diagnostic CLI, but use one filesystem abstraction consistently.
8. Preserve debugging signal when shaping context/output: retain errors, tracebacks, commands, decisions, and touched paths while pruning repetition and bulk output.
9. Test the plugin boundary itself: factory return shape, hook names, config mutation, tool registry, lifecycle events, error paths, and packaged export artifacts. Do not skip the test that verifies the complete registry.
10. Treat permissions, primary tools, external-directory access, and delegation recursion controls as security policy. Review them explicitly whenever adding an agent or tool.
