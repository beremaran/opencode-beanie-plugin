## Shape and OpenCode integration

OpenCodeRAG is a local-first semantic code/image retrieval system. The README describes
vector indexing, AST chunking, hybrid vector/keyword search, incremental indexing, tool
injection, a read override, and optional MCP/CLI operation as one product surface
(`ReadMe.md:1-5`, `ReadMe.md:32-52`). This is a useful pattern for plugins that need both
in-process OpenCode ergonomics and reuse outside OpenCode.

The package exposes a narrow, explicit plugin entry module: `id` is
`opencode-rag-plugin`, `server` is the `ragPlugin` factory, and the default export repeats
that `{ id, server }` contract (`src/plugin-entry.ts:1-18`). The package points `main`,
`module`, `types`, and the root export at the built entrypoint, while separately exporting
library, TUI, UI, and MCP surfaces (`package.json:6-36`). The plugin factory registers
semantic search, file skeleton, usages, image description, quirk-memory tools, and chat
hooks; its resource maps are bounded/cleared and shutdown uses a one-time `beforeExit`
handler (`src/plugin.ts:46-94`, `src/plugin.ts:555-594`, `src/plugin.ts:939-943`).

The MCP implementation is deliberately optional and uses stdio by default. Tool schemas
constrain query/path arrays and `topK` with Zod, errors are returned as MCP error results,
and the returned instance has an explicit `close()` that closes the server, store, keyword
index, and pooled HTTP connections (`src/mcp/server.ts:22-37`, `src/mcp/server.ts:40-75`,
`src/mcp/server.ts:123-157`). The README also makes the architectural distinction clear:
OpenCode tools run in-process, while MCP is for external clients (`ReadMe.md:175-194`).

## Configuration and runtime patterns

Configuration is workspace-oriented: the loader searches `opencode-rag.json`,
`.opencode/opencode-rag.json`, then `.opencode/rag.json` (`src/core/config.ts:871-889`).
Loading strips a UTF-8 BOM, reports missing/invalid JSON distinctly, and merges defaults
by section; nested `hybridSearch`, context optimization, `autoIndex`, memory decay, and
similar sections are explicitly merged to avoid losing defaults (`src/core/config.ts:892-1024`).
Validation is warning-oriented rather than a hard schema gate: unknown top-level keys,
invalid provider/URL/limits, bad ports, and experimental batching produce warnings
(`src/core/config.ts:727-868`). This is friendly for incremental config evolution, but
callers should not mistake `valid` warnings for enforcement.

The example configuration demonstrates conservative local defaults: Ollama endpoints,
excluded dependency/build/state directories, package-lock exclusion, hybrid retrieval,
disabled auto-indexing, and disabled MCP (`opencode-rag.example.json:1-65`,
`opencode-rag.example.json:100-107`). It also shows that image description and memory can
send source/image content to configured providers, so “local-first” depends on provider
selection rather than being an unconditional privacy guarantee (`ReadMe.md:80-86`,
`opencode-rag.example.json:66-89`, `opencode-rag.example.json:109-125`).

Public API operations use `try/finally` to close stores, close keyword indexes, and destroy
pooled connections after search/index work (`src/api.ts:85-119`, `src/api.ts:129-160`).
The repository’s own agent guidance elevates this into a project invariant for every
create/open/new operation and bounded maps (`AGENTS.md:42-49`). This is a strong lesson for
long-lived plugin processes, where per-workspace resources otherwise leak across reloads.

## Security and safety lessons

The MCP file handlers defend against basic absolute and `..` traversal by resolving both
root and candidate and rejecting relative paths that are `..`, begin with `../`, or become
absolute (`src/mcp/handlers.ts:15-36`). The defense is covered by unit and integration
tests for normal paths, absolute outside paths, deep escapes, and null-byte-like input
(`src/__tests__/mcp/handlers.path.test.ts:13-75`, `src/__tests__/mcp/handlers.path.test.ts:77-122`).
That is a good minimum pattern for tools that read arbitrary workspace files.

However, the containment check is lexical: it uses `resolve`/`relative` and does not call
`realpath`. A path inside the worktree that traverses a symlink to an outside file could
therefore evade the intended “under worktree” policy. The test explicitly labels a
`node_modules` path “symlink-resolvable” but only checks the returned lexical path
(`src/__tests__/mcp/handlers.path.test.ts:64-67`). If the threat model includes hostile
workspace symlinks, resolve the real root/candidate and apply the containment check after
realpath, with an explicit policy for nonexistent files.

The image-description tool accepts a user-controlled `systemPrompt` and sends image data
to the configured vision provider (`src/mcp/server.ts:123-138`). This is useful but should
be treated as an outbound-data boundary: document it, gate it with an explicit opt-in,
and avoid assuming Ollama/local defaults when users configure OpenAI/Anthropic/Google.
The example keeps image description enabled while MCP is disabled, illustrating that
these are independent controls (`opencode-rag.example.json:66-75`,
`opencode-rag.example.json:100-102`).

## Testing and verification

Testing is broad and layered. `npm test` discovers unit tests while excluding integration,
plugin, and watcher-integration files; `test:integration` runs those dedicated suites
(`package.json:55-61`). The tree contains focused tests for plugin behavior, API exports,
config, bootstrap, retrieval, vector stores, watcher locking, MCP handlers/server, image
and read tools, embedders, and many language chunkers. The plugin suite checks disabled vs
enabled workspace config, hook presence, registered tools, filters, formatted retrieval,
and log behavior (`src/__tests__/plugin.test.ts:117-145`, `src/__tests__/plugin.test.ts:147-216`).
API tests separately verify public exports and skip the Ollama-dependent call in CI
(`src/__tests__/api.test.ts:4-45`).

TypeScript uses strict mode, `noUncheckedIndexedAccess`, unused-local/parameter checks,
declarations, and source maps (`tsconfig.json:1-21`). The build config excludes tests and
the UI from the backend compilation (`tsconfig.build.json:1-8`), while the package build
also invokes Vite for the UI (`package.json:48-56`). The practical lesson is to keep fast
unit tests deterministic, isolate provider/runtime integration tests, and make typecheck,
backend build, UI build, and integration test gates explicit.

## Packaging and release

The npm package is ESM, ships `dist` plus WASM and setup assets, exposes a CLI binary, and
declares `@opencode-ai/plugin` as a peer dependency while pinning it for development
(`package.json:2-5`, `package.json:38-47`, `package.json:84-127`). The package allowlist names
`README.md`, but this clone’s documented file is `ReadMe.md` (`package.json:38-44`,
`ReadMe.md:1`). On case-sensitive package tooling/filesystems that capitalization mismatch
can omit the README; packaging checks should inspect the actual staged tarball, not only
the repository tree.

Postinstall runs only for global npm installs, rewrites Windows command shims, then imports
and executes runtime setup (`scripts/postinstall-setup.js:1-13`, `scripts/postinstall-setup.js:15-21`,
`scripts/postinstall-setup.js:60-82`). This provides a polished global install, but install
scripts are executable supply-chain behavior and should remain minimal, transparent, and
safe to rerun. The postbuild script fails if the CLI loses its shebang, copies the local
OpenCode type declaration into `dist`, and removes source maps to reduce package size
(`scripts/postbuild.js:8-23`, `scripts/postbuild.js:25-36`).

Release automation is intentionally dry-run capable, but the non-dry path pushes `main`,
runs `npm version patch`, pushes the tag, writes temporary release notes, and invokes
`gh release create` (`scripts/release-patch.js:6-12`, `scripts/release-patch.js:30-56`).
Because it builds shell commands containing git-derived tag/commit text, release scripts
should validate/quote all external values and ideally separate argument arrays from shell
strings. The `.gitignore` appropriately excludes `.env`, `.opencode` state, logs, npm
config, package tarballs, and local `opencode-rag.json` (`.gitignore:1-32`).

## Reusable takeaways

- Keep the OpenCode entrypoint tiny and stable; expose separate library/MCP/CLI exports for
  reuse (`src/plugin-entry.ts:6-18`, `package.json:9-36`).
- Bound session caches and close stores, indexes, servers, and HTTP pools on every exit path
  (`src/plugin.ts:46-81`, `src/api.ts:94-118`).
- Validate tool arguments at the transport boundary and add explicit workspace path tests
  (`src/mcp/server.ts:53-62`, `src/__tests__/mcp/handlers.path.test.ts:15-75`).
- Treat provider configuration, image prompts, and image/code payloads as data-egress
  controls, not merely implementation details (`src/mcp/server.ts:123-138`).
- Test the actual package contents and case-sensitive filenames; run release scripts in dry
  mode before allowing network/git mutation (`package.json:38-44`, `scripts/release-patch.js:6-12`).
