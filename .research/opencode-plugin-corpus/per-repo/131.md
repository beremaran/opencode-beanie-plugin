## What it does

- The plugin exports an async `FormatTables` plugin factory and registers the `experimental.text.complete` hook. The hook validates that `output.text` is a string, then replaces it with `formatMarkdownTables(output.text)` (`index.ts:9-24`). This is a minimal, useful OpenCode pattern for post-processing generated text without introducing a separate server or tool.
- Formatting scans contiguous pipe-delimited lines, validates that there are at least two rows, that every row has the same number of cells, and that some row matches the separator syntax (`index.ts:27-58`, `index.ts:60-90`). Valid tables are rebuilt with normalized spacing, inferred alignment, and padded cells (`index.ts:92-140`). Invalid runs are retained and annotated with an HTML comment (`index.ts:44-49`).
- Alignment is derived from colon placement in separator cells: left, center, or right (`index.ts:109-115`, `index.ts:143-151`). This directly supports the README's documented `:---`, `:---:`, and `---:` forms (`README.md:36-45`).
- Display width is computed with `Bun.stringWidth`, after protecting inline-code contents and repeatedly removing non-code emphasis, strike, image, and link syntax (`index.ts:153-198`). A width cache is cleared after more than 100 operations or 1,000 cached entries (`index.ts:221-232`). The concealment-aware separation between source text and visual width is a good pattern for terminal/TUI rendering.

## Evidence-backed OpenCode patterns

- **Use a narrow lifecycle hook for presentation-only changes.** `experimental.text.complete` receives session/message/part identifiers and a mutable text output, so the plugin can be purely transformational and leave the rest of the host workflow alone (`index.ts:11-24`). The README clearly tells users to install it in the OpenCode plugin list and restart OpenCode (`README.md:5-13`, `README.md:61-68`).
- **Keep formatting failure non-fatal.** The hook catches formatter exceptions and preserves the original text while appending a diagnostic HTML comment (`index.ts:17-22`). Invalid table structures likewise remain visible rather than being discarded (`index.ts:44-49`). This is appropriate for a cosmetic plugin, though the diagnostic behavior needs the caveat below.
- **Separate semantic alignment from rendering width.** The implementation calculates alignment from the separator row but calculates padding from concealment-visible width, then emits a canonical table (`index.ts:109-140`, `index.ts:163-198`). The README also explicitly documents code-block preservation, Unicode, emojis, and empty cells as intended behavior (`README.md:36-53`).
- **Bound process-global cache state.** The cache is module-global, but it has explicit operation and entry thresholds and a full clear path (`index.ts:5-7`, `index.ts:221-232`). This is a simple defensive pattern for a long-lived plugin process.

## Pitfalls and correctness risks

- **Pipe parsing is not Markdown-aware.** Table detection and cell extraction use `split("|")` (`index.ts:60-89`, `index.ts:98-103`). Escaped pipes and pipes inside inline code or link destinations will be treated as column separators, even though the width routine separately understands inline code. The implementation therefore can reject or corrupt otherwise valid Markdown tables. A parser or a stateful split that honors escapes/code spans would be safer.
- **The inline-code regex is narrower than the claims.** Code protection uses ``/`(.+?)`/g`` (`index.ts:170-175`), which does not cover empty code spans, multiline spans, or longer backtick fences. The README claims nested Markdown and code-block preservation (`README.md:41-43`, `README.md:55-59`), but the actual algorithm only handles a subset of inline-code forms.
- **The formatter can change content on malformed input.** A contiguous run is classified as table-like solely by leading/trailing pipes (`index.ts:32-40`, `index.ts:60-63`). If the run is invalid, the plugin adds an HTML comment to the model output (`index.ts:44-49`); if an unexpected exception occurs, it also appends the exception message (`index.ts:17-22`). For a presentation hook, injecting diagnostics into user-visible/model-visible text can be surprising and may expose implementation details. Logging through an appropriate host diagnostic channel or silently preserving text would reduce this risk.
- **The catch assumes an `Error`.** `(error as Error).message` is used without checking the thrown value (`index.ts:19-22`). JavaScript permits throwing strings and arbitrary objects, so the fallback comment can contain `undefined` or itself fail while handling the original failure. Normalize unknown errors before rendering diagnostics.
- **Bun is an undocumented runtime dependency in the package contract.** The source declares `Bun` and calls `Bun.stringWidth` (`index.ts:3`, `index.ts:197`), while `package.json` declares `node >=18.0.0` (`package.json:38-40`) and does not declare Bun as an engine. The plugin may be safe in an OpenCode Bun runtime, but the published package metadata overstates portability. Either document Bun/OpenCode as a hard requirement or use a runtime-neutral width dependency.
- **The hook is experimental and version claims disagree.** The package peer dependency says `@opencode-ai/plugin >=0.13.7` (`package.json:35-37`), while the README requires OpenCode `>= 1.0.137` (`README.md:76-79`) and the changelog says the hook is unpublished (`CHANGELOG.md:31-37`). Consumers need one tested compatibility range; otherwise installation can succeed while hook registration or typing fails on an older host.

## Security and privacy

- The plugin has no network access, subprocess execution, filesystem writes, credential handling, or dynamic code evaluation in the reviewed source. Its direct security surface is therefore small (`index.ts:1-232`).
- The main content-safety concern is diagnostic text injection: source/model text can receive an HTML comment containing an exception message (`index.ts:17-22`) or an invalid-structure marker (`index.ts:44-49`). Even if current failures are local parsing failures, error text should be treated as untrusted and should not be inserted into generated content without sanitization or an opt-in debug mode.
- The plugin rewrites model output in place (`index.ts:18`). Any host consumer observing the same output object receives the modified text, so this hook should be tested for ordering and interaction with other completion hooks. The implementation does not use the input identifiers (`index.ts:11-14`), which is fine for stateless formatting but means there is no session-specific policy boundary.

## Testing lessons

- There is no test implementation in the clone, and the only test script deliberately exits with an error: `"test": "echo \"Error: no test specified\" && exit 1"` (`package.json:32-34`). The changelog's statement that the release supports emojis, Unicode, empty cells, long content, nested Markdown, and cache cleanup is therefore not backed by repository tests (`CHANGELOG.md:8-29`).
- The highest-value tests would call the formatter through the exported hook and cover: valid left/center/right alignment; uneven rows and missing separators; escaped/code-span pipes; nested emphasis; links/images; Unicode display width; empty cells; multiple tables in one completion; thrown non-`Error` values; and cache reset thresholds (`index.ts:27-58`, `index.ts:143-232`).
- A host-level smoke test should verify that the actual OpenCode version exposes and invokes `experimental.text.complete`, because the changelog explicitly identifies that hook as unpublished (`CHANGELOG.md:31-37`). The package currently has strict TypeScript settings (`tsconfig.json:1-20`), but type checking alone cannot validate runtime hook availability or Markdown semantics.

## Packaging and maintenance

- The package is an ES module whose entrypoint is the TypeScript source itself (`package.json:25-30`). Its published file allowlist includes only `index.ts`, `LICENSE`, and `README.md` (`package.json:27-31`), which is compact and avoids shipping repository clutter. There is no build script; the only npm script is the failing test command (`package.json:32-34`). Consumers therefore depend on the host/package loader accepting TypeScript directly.
- `bun.lock` records `@opencode-ai/plugin` 1.0.132 and development dependencies, plus `tree-sitter-markdown` and `web-tree-sitter` (`bun.lock:4-18`, `bun.lock:21-42`), but those parser dependencies are not declared in `package.json` and are unused by `index.ts`. This suggests an abandoned parser direction or stale lock metadata; dependency declarations and lockfile should be reconciled to keep installation and supply-chain review clear.
- The repository includes a TypeScript build configuration with declarations and declaration maps (`tsconfig.json:1-20`), but no build command and no `dist` output in the package allowlist. Adding a reproducible typecheck/build or intentionally documenting source distribution would make releases easier to verify.
- `.npmignore` excludes common tests and development files (`.npmignore:1-34`), while `package.json` already uses a positive `files` list (`package.json:27-31`). The allowlist is the stronger packaging control; the redundant ignore rules should be kept aligned with it if tests or fixtures are later added.
- The release metadata is inconsistent: the checked-out package is version `0.0.6` (`package.json:1-4`, git tag `v0.0.6`), but `CHANGELOG.md` documents only `0.1.0` (`CHANGELOG.md:8-12`). Release automation or a corrected changelog would prevent consumers from inferring features from the wrong version.

## Bottom line

This is a focused and conceptually useful presentation plugin: it demonstrates a small OpenCode completion hook, non-fatal formatting, concealment-aware width calculation, alignment handling, and bounded caching. Before treating it as a production reference, resolve the Bun/runtime and host-version contract, replace naive pipe splitting with Markdown-aware parsing, stop inserting raw exception text into output, reconcile package/lock/release metadata, and add executable unit plus host smoke tests.
