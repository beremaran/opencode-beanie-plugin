## What it does

`index.js` exports an async `NotificationPlugin` receiving `project`, `client`, `$`, `directory`, and `worktree` (index.js:1). It maintains one in-memory session ID, start timestamp, and latest user-message preview (index.js:18-20). The event handler accepts a session ID from three possible event locations, then records session start on `session.created` (index.js:23-30).

The plugin sends notifications for four situations:

- `session.idle`: project/worktree-derived title, elapsed time, and a 60-character user-message preview (index.js:47-55).
- `session.error`: project-derived error title and a fixed body (index.js:57-60).
- `permission.asked`: tool/type-derived approval body (index.js:63-66).
- `tool.execute.before` when the tool is `question`: the first question's header or text (index.js:68-74).

The README documents the same four user-visible cases (README.md:7-11), install options for npm and copying the entrypoint into global or project plugin directories (README.md:22-42), and Linux/macOS support (README.md:13-18).

## OpenCode patterns worth reusing

### Small event-driven plugin surface

Returning an object containing `event`, `permission.asked`, and `tool.execute.before` keeps the integration localized and maps behavior directly to OpenCode lifecycle/tool hooks (index.js:22-75). This is a useful pattern for notification-only plugins: the hook handlers do not alter tool results or session state beyond the data needed for a notification.

### Fetch context through the client only when needed

On `message.updated`, the plugin calls `client.session.messages` for the active session and scans backward for the latest user-role message (index.js:32-43). It then normalizes newlines and truncates the preview before notification (index.js:36-41). This demonstrates using the supplied client to enrich an event rather than assuming the event contains the complete conversation.

### Cross-platform command selection

The implementation selects AppleScript on Darwin and freedesktop D-Bus elsewhere (index.js:6-14); the README states the corresponding runtime prerequisites (README.md:15-18). The platform-specific command is isolated inside `send`, which makes the notification call site independent of the operating system (index.js:4-16).

### Minimal publishable package metadata

`package.json` declares ESM (`type: "module"`), points `main` at `index.js`, includes discoverability keywords, and lists only the runtime entrypoint and documentation in `files` (package.json:2-13, package.json:21-25). The repository and MIT license metadata are explicit (package.json:15-20; LICENSE:1-21).

## Pitfalls and security lessons

- **Shell-command construction needs a stricter boundary.** Notification content is interpolated into `osascript` and `dbus-send` command templates; the code manually escapes backslashes and double quotes on macOS, and double quotes on the other branch (index.js:7-14). This is fragile for shell/AppleScript metacharacters, apostrophes, newlines, and control characters. A safer implementation would pass structured arguments through the shell API without embedding user text in a quoted script, or use a platform library with argument APIs. The current code also silently discards all notification-command failures (index.js:4-16).
- **The non-Darwin branch is broader than the documented support.** Every platform other than `darwin` invokes `dbus-send`, while the README only claims Linux and macOS (index.js:6-14; README.md:13-18). Unsupported systems therefore fail through the swallowed catch rather than producing an explicit unsupported-platform result.
- **State is global to one plugin instance, not keyed by session.** A single `currentSessionID`, `sessionStart`, and `lastUserMessage` is used (index.js:18-20). Starting another session replaces the first session's state (index.js:26-30), so concurrent or interleaved sessions can lose timing/previews. Approval notifications are not filtered by session at all (index.js:63-66).
- **Event ordering and repeated events are assumed.** `session.idle` computes elapsed time from `sessionStart` without checking it exists (index.js:47-51), and every matching idle event sends another notification (index.js:47-55). There is no cleanup or terminal-state guard after idle/error (index.js:47-60).
- **Notification content can disclose user input.** The last user message is deliberately placed in a desktop notification body after truncation (index.js:36-41, 52-54). That is consistent with the README's preview feature (README.md:7-9), but projects using sensitive prompts should treat desktop notification visibility as a privacy setting and should consider opt-out/redaction.
- **Failures are invisible to operators.** Both message retrieval and notification sending use empty catches (index.js:15, 34-45). This prevents plugin failures from disrupting OpenCode, but it also hides missing `dbus-send`, malformed command arguments, client/API incompatibilities, and debugging information.
- **Question notifications are intentionally lossy.** Only the first question is used, preferring `header` over the full question text (index.js:69-73). Multi-question prompts and a header that lacks enough context will not be represented accurately.

## Testing and verification lessons

There is no test script, test file, CI workflow, or development dependency in the tracked inventory; `package.json` contains metadata and packaging fields but no `scripts` section (package.json:1-25). The repository therefore provides no automated evidence for event payload compatibility, elapsed-time formatting, session concurrency, command escaping, or platform behavior.

High-value tests should invoke the returned hook object with representative `session.created`, `message.updated`, `session.idle`, `session.error`, `permission.asked`, and question-tool inputs, while mocking `client.session.messages` and `$`. They should specifically cover missing session IDs, missing message parts, repeated/interleaved sessions, message text containing quotes/newlines/control characters, empty question arrays, and rejected client/notification commands. Platform-specific tests should assert command arguments for Darwin and Linux and verify unsupported-platform handling.

## Packaging and documentation lessons

- The package is straightforward to consume because `main`, ESM mode, repository metadata, keywords, and an explicit `files` allowlist are present (package.json:2-25).
- The allowlist omits the screenshot even though README references it at the top (README.md:1; package.json:21-25). If the package is consumed from its npm tarball, the README image may be missing. Include `screenshot.png` or remove the README reference.
- The README gives both npm and local-copy installation instructions and states the external Linux daemon requirement (README.md:15-18, 22-42), but it does not document supported OpenCode versions, runtime requirements for the ESM entrypoint, configuration/disable options, or troubleshooting when notification binaries are absent.
- The MIT license is present and matches the package metadata (package.json:16; LICENSE:1-21), which is a good minimum for redistribution.

## Overall assessment

This is an intentionally small, useful notification adapter: its strongest pattern is a direct mapping from OpenCode hooks to one isolated notification function, with lightweight session context and explicit package metadata. Its main production risks are untested hook payload assumptions, single-session in-memory state, silent failures, broad platform fallback, and embedding potentially sensitive/user-controlled text into platform command strings.
