## What it does

This is an OpenCode authentication/provider plugin that uses ChatGPT OAuth and rewrites OpenAI Responses API traffic to the ChatGPT Codex backend. The README explicitly limits intended use to a personal Plus/Pro subscription and recommends the OpenAI Platform API for production or multi-user applications (`README.md:59-74`).

The entrypoint registers an `auth` provider, ignores non-OAuth credentials, extracts `chatgpt_account_id` from the JWT payload, and returns a custom SDK `fetch` implementation (`index.ts:95-147`). That fetch pipeline refreshes tokens, rewrites the URL, transforms the request, injects OAuth/account headers, calls the backend, logs the response, and converts successful non-streaming SSE responses to JSON (`index.ts:163-225`).

## OpenCode patterns worth reusing

- **Provider loader plus custom fetch:** Returning `apiKey`, `baseURL`, and a custom `fetch` from the provider loader is a practical way to adapt OpenCode's OpenAI-compatible client without replacing the client surface (`index.ts:144-166`).
- **Keep OAuth lifecycle inside the provider:** The plugin exposes automatic and manual OAuth methods, starts a local callback server, opens the browser, waits for the callback, and falls back to manual URL paste when binding fails (`index.ts:228-293`; `lib/auth/server.ts:16-80`).
- **PKCE and state:** Authorization URLs include an S256 PKCE challenge and random state, with the callback server rejecting state mismatches before accepting a code (`lib/auth/auth.ts:16-18`, `lib/auth/auth.ts:178-194`; `lib/auth/server.ts:17-35`).
- **Preserve host model keys while normalizing API IDs:** Configuration lookup uses the original model name, then the request model is normalized for the backend. This allows per-variant options to work even when the backend receives a family slug (`lib/request/request-transformer.ts:428-447`).
- **Explicit request contract adaptation:** The transformer forces `store: false`, `stream: true`, model-specific instructions, encrypted reasoning inclusion, and removes unsupported token fields (`lib/request/request-transformer.ts:448-453`, `lib/request/request-transformer.ts:503-530`).
- **Stateless multi-turn handling:** It removes unsupported `item_reference` entries and strips IDs while retaining message/tool history; encrypted reasoning content is required to preserve continuity (`lib/request/request-transformer.ts:288-330`, `lib/request/request-transformer.ts:521-524`). Orphaned tool outputs are converted to messages rather than dropped, preserving context (`lib/request/request-transformer.ts:495-500`).
- **Compatibility switch for prompt/tool semantics:** `CODEX_MODE` has a documented precedence of environment variable, config file, then default; enabled mode removes the OpenCode system prompt and adds a bridge prompt, while disabled mode adds a tool-remapping prompt (`lib/config.ts:45-59`; `lib/request/request-transformer.ts:486-493`).
- **Use JSONC-aware installation:** The installer parses and edits JSONC with `jsonc-parser`, preserves comments, backs up existing config, merges provider/model data, and prefers `opencode.jsonc` over `.json` (`scripts/install-opencode-codex-auth.js:141-177`, `scripts/install-opencode-codex-auth.js:287-415`).

## Security and privacy lessons

- **Good baseline:** OAuth uses PKCE, binds the callback server to `127.0.0.1`, validates state, and the project documents token handling and personal-use boundaries (`lib/auth/auth.ts:178-194`; `lib/auth/server.ts:46-49`; `SECURITY.md:14-30`).
- **JWT handling is deliberately non-verifying:** `decodeJWT` only base64-decodes and parses the payload; it checks shape but not the signature or issuer (`lib/auth/auth.ts:100-114`). This is acceptable only as metadata extraction after OpenCode has authenticated/stored the credential, not as an authorization decision. A plugin copying this pattern must not trust payload claims for access control.
- **Debug logging can expose sensitive data:** When enabled, `logRequest` writes arbitrary request/response data to `~/.opencode/logs/codex-plugin/` (`lib/logger.ts:26-57`). The fetch path logs the full original and transformed request bodies and response headers (`lib/request/fetch-helpers.ts:119-154`; `index.ts:211-217`), while SSE conversion can log the complete stream (`lib/request/response-handler.ts:45-54`). The privacy documentation correctly warns that logs may contain prompts and responses (`docs/privacy.md:40-48`), but operators should treat this as sensitive data and enable it only briefly.
- **Secrets are removed from inherited headers:** The custom header builder deletes `x-api-key` before setting the OAuth bearer token and account ID (`lib/request/fetch-helpers.ts:173-195`).
- **Installer has broad local side effects:** Normal installation edits the global OpenCode config, backs it up, and clears the OpenCode plugin cache (`scripts/install-opencode-codex-auth.js:46-60`, `scripts/install-opencode-codex-auth.js:234-249`, `scripts/install-opencode-codex-auth.js:377-420`). `--uninstall --all` removes auth, plugin config, logs, and cached instruction files (`scripts/install-opencode-codex-auth.js:251-285`, `scripts/install-opencode-codex-auth.js:362-365`). A package using this pattern should make scope, backups, dry-run behavior, and destructive cleanup conspicuous.
- **Remote prompt supply-chain dependency:** The request path fetches model-specific Codex instructions before transforming requests (`lib/request/fetch-helpers.ts:113-139`). The documented design says these are fetched/cached from GitHub with fallback, so updates to a remote release can alter prompt behavior. Pinning, integrity checking, bounded cache behavior, and clear offline fallback are important operational controls.

## Testing lessons and gaps

- Tests are organized by module and use mocked data/no real API calls, covering OAuth parsing/PKCE, configuration precedence, model normalization, input filtering, SSE conversion, installer JSONC behavior, browser selection, and usage-limit error mapping (`test/README.md:7-15`, `test/README.md:33-81`; `test/install-script.test.ts:32-147`).
- The installer tests are particularly useful: they verify comment preservation and custom config retention, JSONC preference, creation of a new config, selective uninstall, and artifact cleanup in isolated temporary homes (`test/install-script.test.ts:32-147`).
- CI runs typecheck, tests, and build on Node 20 and 22, with npm lockfile installation (`.github/workflows/ci.yml:9-38`). TypeScript is strict and emits declarations/source maps (`tsconfig.json:1-31`).
- Request-transformer tests encode compatibility behavior, including stripping all item IDs, preserving matched tool-call pairs, converting orphan outputs, bridge-vs-remap behavior, and model-specific reasoning clamps (`test/request-transformer.test.ts:252-344`, `test/request-transformer.test.ts:1092-1186`, `test/request-transformer.test.ts:1188-1283`).
- A notable test/documentation drift exists: `test/README.md:85-89` claims CI tests Node 18, 20, and 22, but the workflow only declares 20.x and 22.x (`.github/workflows/ci.yml:14-17`). The development testing document also contains older expected normalization examples that conflict with current tests/source, which now map legacy GPT-5 names to GPT-5.1 (`docs/development/TESTING.md:24-29`, `test/request-transformer.test.ts:18-45`, `lib/request/request-transformer.ts:32-112`). Treat executable tests/source as current evidence and keep scenario docs synchronized.
- Unit tests do not exercise the complete OAuth callback server lifecycle, real token exchange/refresh, remote instruction fetching/cache invalidation, or the full entrypoint fetch pipeline. Those areas merit integration tests with local HTTP fixtures and redacted logging assertions.

## Packaging and configuration lessons

- Package metadata exposes compiled `dist/index.js` and declarations, ships `dist/`, assets, config, scripts, README, and license, and requires Node 20+ (`package.json:30-53`). The build explicitly copies `lib/oauth-success.html` into `dist/lib/`, a required non-TypeScript runtime asset (`package.json:30-32`; `lib/auth/server.ts:7-10`).
- The package provides a CLI binary for install/update/uninstall and leaves the plugin entry unversioned by default so updates pull latest (`package.json:38-47`; `config/README.md:79-81`). This is convenient but trades reproducibility for freshness; production or team setups should pin a version and review updates.
- Modern config uses six base models with variants, while legacy config expands reasoning levels into separate model entries (`config/README.md:5-12`, `config/README.md:26-35`). Both encode `store: false`, encrypted reasoning inclusion, image input, and model limits (`config/opencode-modern.json:6-16`, `config/opencode-modern.json:17-35`; `config/README.md:37-43`).
- The installer merges template options over existing OpenAI options/models (`scripts/install-opencode-codex-auth.js:86-115`). That is simple and testable, but template updates can override user values; the backup and JSONC tests are important safeguards.

## Bottom line

The strongest reusable pattern is a narrowly scoped provider loader with a well-tested custom-fetch adapter: refresh auth, normalize/transform the request, inject only required headers, and translate the backend response back to the SDK contract. The main pitfalls are sensitive full-body logging, trusting unsigned JWT payload data beyond metadata extraction, mutable remote prompt inputs, unpinned installation, and documentation drift between evolving model mappings and test expectations.
