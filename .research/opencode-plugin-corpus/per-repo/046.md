## OpenCode patterns

- The adapter uses `chat.message` to detect workflow, `ultracode`, and `/deep-research` intent, then rewrites the outgoing text with either an embedded result, a daemon-started workflow notice, or a native-subagent fallback directive ([packages/opencode-plugin/src/index.js:317-395](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/index.js)). This is a strong pattern for transparent orchestration: preserve the host conversation while delegating the expensive work.
- It exposes explicit tools for planning, running, status, listing workflows, and toggling per-project ultracode state ([packages/opencode-plugin/src/index.js:398-487](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/index.js)). Tool arguments use the OpenCode SDK schema helpers, and long results are bounded to 24,000 characters for `odw_plan` ([packages/opencode-plugin/src/index.js:399-415](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/index.js)).
- Embedded execution routes each agent through OpenCode’s configured model by omitting `body.model`, only setting it for an explicit `provider/model` override ([packages/opencode-plugin/src/host-provider.js:68-79](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/host-provider.js)). This avoids duplicate provider keys and preserves host model configuration.
- Each embedded invocation creates a fresh child session, tracks it, and bulk-deletes sessions during `dispose()` rather than deleting immediately. The source explains that fresh sessions prevent cross-agent context contamination and deferred deletion avoids a verified OpenCode async deletion race ([packages/opencode-plugin/src/host-provider.js:24-36](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/host-provider.js), [packages/opencode-plugin/src/host-provider.js:41-65](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/host-provider.js), [packages/opencode-plugin/src/host-provider.js:111-119](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/host-provider.js)).
- A module-level child-session set and synchronous `embeddedActive` guard prevent recursive `chat.message` triggering and concurrent embedded runs from producing a session storm ([packages/opencode-plugin/src/index.js:206-219](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/index.js), [packages/opencode-plugin/src/index.js:317-359](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/index.js)).
- The adapter degrades deliberately: missing embedded dependencies fall through to daemon/directive paths, a daemon `401` is distinguished from offline, and host protocol failures with empty text become retryable errors ([packages/opencode-plugin/src/index.js:229-237](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/index.js), [packages/opencode-plugin/src/index.js:295-313](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/index.js), [packages/opencode-plugin/src/host-provider.js:93-108](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/host-provider.js)).

## Pitfalls and security lessons

- Trigger matching needs both positive and negative patterns. The adapter avoids treating ordinary Git/CI/release workflows as ODW requests unless the explicit `workflow:` form is used ([packages/opencode-plugin/src/index.js:27-59](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/index.js)).
- Local daemon calls still need authentication. The client reads `ODW_DAEMON_TOKEN` or `~/.odw/daemon.token`, sends a Bearer header even on GETs, uses request timeouts, and surfaces unauthorized separately ([packages/opencode-plugin/src/index.js:64-104](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/index.js)). The documented default is loopback port 7345, but configurable ports and home directories are supported ([packages/opencode-plugin/src/index.js:80-137](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/index.js), [.env.example:5-9](../repos/suraj1235--open-dynamic-workflows/.env.example)).
- Writing ultracode state is a direct filesystem mutation under the project’s `.opencode/state/odw` directory; it creates parent directories recursively and writes JSON without an atomic temp-file/rename step ([packages/opencode-plugin/src/index.js:140-158](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/index.js)). A crash during write could leave malformed state, though reads fail closed to `false` ([packages/opencode-plugin/src/index.js:146-151](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/index.js)).
- The host backend intentionally has a degraded fallback that reuses a caller-provided session if child-session creation fails; the source explicitly warns that this accumulates history and loses isolation ([packages/opencode-plugin/src/host-provider.js:61-66](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/host-provider.js)). Consumers should treat this as a safety/performance tradeoff, not equivalent behavior.
- Security tests cover SSRF scheme/private-address/DNS-pinning cases, command allowlists, force-push and hard-reset blocking, and secret scanning is enforced in CI ([packages/daemon/test/security.test.js:15-79](../repos/suraj1235--open-dynamic-workflows/packages/daemon/test/security.test.js), [packages/daemon/test/security.test.js:95-169](../repos/suraj1235--open-dynamic-workflows/packages/daemon/test/security.test.js), [.github/workflows/ci.yml:38-54](../repos/suraj1235--open-dynamic-workflows/.github/workflows/ci.yml)). The VS Code dashboard separately tests HTML escaping of workflow prompts ([packages/vscode-extension/test/manifest.test.js:57-66](../repos/suraj1235--open-dynamic-workflows/packages/vscode-extension/test/manifest.test.js)).

## Packaging and operational lessons

- Keep the OpenCode adapter thin and self-contained where possible: its source documents a dependency-light drop-in mode and lazy-imports the embedded engine so missing dependencies can degrade cleanly ([packages/opencode-plugin/src/index.js:1-17](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/index.js), [packages/opencode-plugin/src/index.js:229-237](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/src/index.js)).
- Separate host integration from the orchestration engine. The workspace package depends on `odw-core` and `odw-daemon`, while OpenCode remains a peer host dependency ([packages/opencode-plugin/package.json:13-24](../repos/suraj1235--open-dynamic-workflows/packages/opencode-plugin/package.json)). This supports multiple adapters but makes installation and workspace linking essential for tests.
- Treat README claims as operational requirements: the documented setup is clone, `npm install`, `npm run setup`, then daemon start ([README.md:74-103](../repos/suraj1235--open-dynamic-workflows/README.md)). The same README states that OpenCode native mode should use the host model with no second key and that `ODW_MAX_AGENTS`, `ODW_HOST_MODEL`, and `ODW_DEBUG` control embedded behavior ([README.md:195-212](../repos/suraj1235--open-dynamic-workflows/README.md)).

## Bottom line

The most reusable OpenCode pattern is a thin `chat.message`/tool adapter around fresh child sessions, with recursion guards, host-model inheritance, bounded outputs, explicit daemon authentication, and a meaningful native fallback. The principal deployment pitfall is workspace coupling: the OpenCode package is not independently runnable from this clone without the linked `odw-core`/`odw-daemon` packages and native dependencies. CI’s cross-platform matrix and security/manifest tests are strong evidence-backed practices, but the failed uninstalled snapshot prevents claiming end-to-end readiness here.
