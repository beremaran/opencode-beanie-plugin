## What it does

`@openhax/codex` is an OpenCode provider/auth plugin that routes the OpenAI SDK-compatible provider through ChatGPT’s Codex backend, using a ChatGPT Plus/Pro OAuth subscription rather than Platform API credits (`README.md:7-8`, `package.json:1-8`). The README’s minimal configuration registers the plugin under the `openai` provider and sets `store: false`, encrypted reasoning inclusion, and model options (`README.md:15-43`).

The entrypoint exports an async `Plugin` and returns an `auth` integration for provider `openai` (`index.ts:25-35`, `index.ts:67-80`). Its loader rejects non-OAuth credentials, decodes the access-token JWT to obtain `chatgpt_account_id`, merges global and per-model provider options, warms caches, fetches Codex instructions, and returns a dummy API key, Codex base URL, and custom `fetch` implementation (`index.ts:84-145`). The plugin also exposes OAuth and API-key auth methods, although the custom backend path fundamentally depends on the OAuth account claim (`index.ts:147-174`).

## OpenCode integration patterns

- Use the SDK’s `Plugin`, `PluginInput`, and `Auth` types at the boundary rather than defining a parallel plugin contract (`index.ts:25-26`, `index.ts:67-84`).
- Return the provider override from the auth loader, including `apiKey`, `baseURL`, and `fetch`; this lets existing OpenAI SDK/OpenCode provider machinery call the backend without replacing the host runtime (`index.ts:141-145`).
- Preserve host configuration layering by passing `provider.openai.options` and `provider.openai.models` into a separate `UserConfig`; model-specific values are resolved later (`index.ts:96-103`, `test/config.test.ts:31-53`).
- Keep startup-only concerns explicit: logger configuration, a loopback dashboard, cache warming, and instruction loading happen during plugin initialization/loader setup (`index.ts:67-78`, `index.ts:113-128`). Cache warming failure is non-fatal and logged before request handling continues (`index.ts:115-125`).
- Intercept requests through a custom fetch that accepts the standard `Request | string | URL` forms, rewrites `/responses` to `/codex/responses`, transforms the body, adds OAuth/account headers, executes the request, and normalizes the response (`lib/request/codex-fetcher.ts:97-168`, `lib/request/fetch-helpers.ts:84-97`, `lib/request/fetch-helpers.ts:215-237`).

## Source behavior and pitfalls

`transformRequestBody` forces the backend contract: it normalizes the model, sets `store: false` and `stream: true`, injects Codex instructions, ensures a prompt-cache key, normalizes tools, filters input IDs/system prompts, adds either the CODEX bridge or legacy tool-remap message, applies reasoning/text settings, includes encrypted reasoning, and removes unsupported output-token fields (`lib/request/request-transformer.ts:101-159`). `CODEX_MODE` defaults on, can be overridden by `CODEX_MODE=1|0`, and has a documented config-file fallback (`lib/config.ts:7-21`, `lib/config.ts:76-90`).

Useful correctness patterns include model-specific option merging and API-compatible reasoning clamping. Tests verify global/per-model precedence, Codex `minimal` to `low`, Codex Mini lower bounds, and GPT-5.2 `xhigh` behavior (`test/config.test.ts:31-53`, `test/config.test.ts:55-162`). Tool normalization handles string tools, nested function definitions, native tools, object maps, disabled entries, and removal of an empty tool set (`test/request-transformer-tools-normalization.test.ts:19-179`).

The stateless design is intentional: every transformed request sets `store: false` and carries encrypted reasoning content; the documentation explains that `store: true` causes unresolved `item_reference` behavior with newer AI SDK versions (`lib/request/request-transformer.ts:121-155`, `docs/configuration.md:138-162`). A consumer must therefore not treat the provider options as ordinary OpenAI defaults.

The main data-handling pitfall is logging. Before/after transformation logs include the complete request body, and error handling logs the complete enriched error body (`lib/request/fetch-helpers.ts:145-154`, `lib/request/fetch-helpers.ts:177-188`, `lib/request/fetch-helpers.ts:331-350`). Non-tool SSE conversion can also persist the complete stream when logging is enabled (`lib/request/response-handler.ts:45-56`). The logger only removes nullish fields; it does not redact prompts, responses, account IDs, or arbitrary configuration (`lib/logger.ts:336-341`). The privacy document correctly warns that logs may contain prompts and model responses (`docs/privacy.md:40-48`), but the implementation’s request logging means the opt-in setting should be treated as sensitive-data access, not ordinary debugging.

The OAuth flow has several good controls: cryptographic random state, PKCE S256, fixed HTTPS authorization/token endpoints, and a callback bound to `127.0.0.1` with state validation (`lib/auth/auth.ts:19-20`, `lib/auth/auth.ts:174-190`, `lib/auth/server.ts:22-60`). The callback server stores the accepted code in an in-memory `_lastCode` and polling returns it without clearing it (`lib/auth/server.ts:43-69`). It is local and state-protected, but a one-time consume/close behavior would reduce replay exposure during the callback window. JWT decoding is deliberately only decoding, not signature verification (`lib/auth/auth.ts:102-118`); this is acceptable only because the token itself is obtained from the OAuth exchange and should not be treated as a general-purpose JWT trust boundary.

The dashboard binds to loopback and uses an ephemeral port, which limits remote exposure (`lib/server/dashboard.ts:6-7`, `lib/server/dashboard.ts:139-150`). It has no authentication, however, and exposes recent request metadata and cache metrics to any local process that can connect (`lib/server/dashboard.ts:95-133`). Its browser rendering escapes displayed values before using `innerHTML`, a useful local UI defense (`lib/server/dashboard.ts:50-81`).

Codex instructions are fetched from the latest OpenAI Codex GitHub release, cached with ETags and a 15-minute freshness policy, and reused from disk or a bundled fallback on failure (`lib/prompts/codex.ts:16-18`, `lib/prompts/codex.ts:97-195`, `lib/prompts/codex.ts:248-280`). This improves freshness and resilience but makes a remote GitHub response part of the prompt/trust chain; there is no signature or allowlisted-content verification in this path. More concretely, `loadBundledInstructions` reads `lib/codex-instructions.md` (`lib/prompts/codex.ts:85-94`), but no file with that name was present in the inspected clone, so the ultimate fallback appears unable to work unless generated outside the repository.

## Tests and verification

The repository has a broad Vitest suite covering authentication, browser/server callback behavior, plugin wiring, configuration, request transformation/tool normalization, response handling, logging, sessions, metrics, and caching (`test/README.md:7-15`, `test/README.md:33-84`). Tests mock network and file I/O rather than calling external services, and the stated CI philosophy is to run on pushes/PRs across Node 18, 20, and 22 (`test/README.md:86-100`). Authentication tests cover state uniqueness, PKCE URL parameters, JWT decoding, token exchange, and malformed input (`test/auth.test.ts:30-181`). The callback tests cover valid code capture and state mismatch timeout (`test/server.test.ts:95-131`).

The test strategy is strongest around pure transformation logic and mocked initialization. Gaps worth carrying forward are: replay/second-use behavior of the callback code, real port binding failure/port contention, dashboard access policy, log redaction under full request/response payloads, remote instruction validation and the missing bundled asset, and end-to-end compatibility with the actual OpenCode SDK. The test documentation says the suite is mock-only (`test/README.md:86-91`), so passing unit tests cannot establish those integration properties.

## Packaging and release lessons

- The package is ESM with `dist/index.js` and declarations as its public entrypoints; it declares `@opencode-ai/plugin` as a peer dependency and builds with strict TypeScript, ES2022, bundler resolution, declarations, and source maps (`package.json:2-8`, `package.json:53-75`, `tsconfig.json:1-33`).
- The build command has a non-TypeScript asset step, copying `lib/oauth-success.html` into `dist/lib/`; omitting that step would break the callback page (`package.json:30-32`, `lib/auth/server.ts:8-10`). This is a good example of packaging runtime assets explicitly, but the separate `codex-instructions.md` fallback asset is not visible in the clone and is not copied by the build script (`lib/prompts/codex.ts:85-94`, `package.json:30-32`).
- The npm `files` allowlist publishes only `dist/`, `README.md`, and `LICENSE`, while `.npmignore` excludes docs, CI files, and lockfiles (`package.json:48-52`, `.npmignore:1-14`). That keeps the package small, but configuration examples under `config/` and the detailed privacy/configuration docs are repository-only and must remain mirrored in README guidance.
- The repository contains both `package-lock.json` and `pnpm-lock.yaml`, while scripts consistently invoke `pnpm` for formatting/linting but `npm` is implied by the package metadata and README prerequisites (`package.json:33-46`, `README.md:11-14`). A release process should choose one installer and ensure CI/build documentation matches it.
- `package.json` lists `hono` as a runtime dependency and an override even though no TypeScript source import of Hono was found; the README simultaneously describes the runtime as having only `@openauthjs/openauth` (`package.json:77-83`, `README.md:87-92`). This is dependency-hygiene and reproducibility debt, not evidence that Hono is exploitable.
- The package metadata says version `1.0.0`, while the checked-in release analysis describes a `0.1.0` next version (`package.json:1-3`, `release-analysis.json:3-15`). Release automation should derive version truth from one authoritative source.

## Reusable lessons

1. An OpenCode auth loader can be a narrow compatibility layer: preserve provider configuration, return a custom fetch, and keep backend-specific request/response rules outside the host (`index.ts:84-145`, `lib/request/codex-fetcher.ts:97-168`).
2. When adapting a stateless backend, enforce required invariants in the transformer instead of relying solely on user JSON (`lib/request/request-transformer.ts:121-155`).
3. Opt-in request logging still needs field-level redaction and a documented threat model when it can persist prompts, responses, and transformed payloads (`lib/request/fetch-helpers.ts:145-188`, `lib/logger.ts:336-341`, `docs/privacy.md:40-48`).
4. Loopback-only servers and PKCE/state are strong defaults, but callback codes should be consumed once and local dashboards should expose only deliberately non-sensitive metrics (`lib/auth/server.ts:39-69`, `lib/server/dashboard.ts:95-133`).
5. Test transformation edge cases extensively, then add a small integration gate for packaged assets, real callback binding, and the actual OpenCode SDK; mock-only coverage cannot detect those release failures (`test/README.md:86-100`, `package.json:30-32`).
