- The project is an OpenCode plugin intended to enforce a minimum work duration, inject behavioral instructions, and prevent early task termination (`README.md:1-3`, `README.md:7-23`).

## OpenCode patterns

- **Plugin factory and tools:** The entrypoint exports a `Plugin`-typed async factory and returns a `tool` map (`src/index.ts:1-2`, `src/index.ts:195-218`). Each tool uses a Zod-like schema; the start tool bounds duration to 0.5-1440 minutes while accepting decimals (`src/index.ts:220-228`). This is a useful pattern for keeping tool argument validation at the plugin boundary.
- **Command registration through config mutation:** Markdown command files are discovered from a directory adjacent to the built entrypoint, parsed with a small front-matter convention, and copied into `config.command` (`src/index.ts:195-216`, `src/index.ts:322-334`). This makes commands data-driven and lets a package ship command templates separately from TypeScript.
- **Lifecycle hooks:** The plugin uses `experimental.chat.system.transform` to prepend a system prompt when a timer is active (`src/index.ts:336-357`), `tool.execute.before` to block selected shell commands (`src/index.ts:360-369`), and `tool.execute.after` to append a warning when output matches end-of-task phrases (`src/index.ts:372-412`). The pattern demonstrates how OpenCode hooks can add policy without replacing the underlying tool implementation.
- **State across messages:** Timer state is persisted outside process memory and keyed by process ID (`src/index.ts:9-10`, `src/index.ts:152-175`). This survives messages in one OpenCode process and avoids collisions between simultaneous processes, matching the documented multi-process goal (`CHANGELOG.md:60-66`).
- **Prompt-backed workflow:** A shipped `/workaholic` command instructs the model to call the start tool, check status, and finish through checkout (`src/command/workaholic.md:16-39`, `src/command/workaholic.md:23-34`). The README documents the same tool-oriented workflow (`README.md:25-70`). The command still uses the older dotted spelling in its examples, which is part of the compatibility drift noted below.

## Pitfalls and security lessons

- **Tool-name compatibility must be treated as an API contract.** The changelog records that dotted names failed newer OpenCode validation and were changed to underscore names (`CHANGELOG.md:3-8`). Documentation still shows dotted names in several places, including the README tool examples (`README.md:33-50`) and the command template (`src/command/workaholic.md:17-34`), while the implementation uses underscores (`src/index.ts:219-220`, `src/index.ts:256-257`, `src/index.ts:279-280`). Keep generated docs and prompts synchronized with the actual registered names.
- **Prompt enforcement is not a security boundary.** The system prompt says never to use `workaholic_status` and to keep working (`src/index.ts:94-125`), while the status tool remains callable and only tracks repeated checks (`src/index.ts:256-277`). The after-hook only scans returned text for a finite list of phrases (`src/index.ts:376-411`), so semantic early exits or alternate wording can evade it. Use hooks for guidance, not as proof that an agent complied.
- **Shell blocking is narrow and bypassable.** The before-hook only examines `bash` calls and rejects commands containing `sleep` or matching `sleep` followed by digits (`src/index.ts:360-369`). It does not establish a general no-wait policy for other tools, aliases, scripts, or equivalent commands. If the policy matters, define the threat model and test command parsing explicitly.
- **Timer files lack ownership, permissions, and atomicity controls.** State is JSON in `/tmp`, written synchronously with default filesystem permissions and no lock or atomic rename (`src/index.ts:152-166`). A same-user process can read or overwrite another process's timer if it knows the PID, and concurrent writes can corrupt state. The code intentionally ignores malformed JSON (`src/index.ts:154-161`), which fails open by treating the timer as inactive.
- **The process-PID key is not session identity.** A PID avoids collisions between currently running instances (`src/index.ts:9-10`), but it is reused by the operating system over time and does not distinguish multiple sessions within one process. The Python helper uses a caller-supplied session ID instead (`scripts/timer.py:7-17`, `scripts/timer.py:25-33`), exposing an unresolved split in state design.
- **Checkout does not deactivate state.** Successful checkout only returns approval (`src/index.ts:283-309`); it does not call `saveTimer` to mark the timer inactive. The timer eventually reaches zero, but stale state remains on disk until stop or overwrite. A clear terminal-state transition would make lifecycle semantics less surprising.
- **CLI configuration edits are destructive on malformed input.** `getConfig()` catches any read/parse failure and returns `{ plugin: [] }` (`src/cli.ts:15-25`), then install can overwrite the user's config with only the recovered object (`src/cli.ts:31-45`). It also writes directly without a backup, atomic replacement, or permission handling (`src/cli.ts:27-29`). Installation tools should fail loudly on invalid JSON and preserve existing configuration.
- **The installer assumes one config shape.** The CLI operates on `plugin` singular (`src/cli.ts:9-12`, `src/cli.ts:31-40`), while the README examples use `plugins` plural (`README.md:94-108`) and the HTML installation page repeats that shape (`docs/install.html:523-553`). This can produce an installation that appears successful but is not loaded by the documented configuration format.
- **Unbounded behavioral pressure can cause waste or unsafe changes.** The rules explicitly say not to conserve tokens and to keep producing tangible work until exactly zero (`src/index.ts:94-125`). The command also instructs the model to create new work after todos are complete (`src/command/workaholic.md:41-53`). A production variant should provide cancellation, scope limits, and an explicit policy for avoiding needless or risky modifications.

## Testing and verification

- The repository has no committed test files; `git ls-files` contains source/configuration/docs but no `*.test.*` or `*.spec.*` files. Running `bun test` at the verified clone produced: `error: 0 test files matching ...` (observed during this review).
- The project nevertheless documents `mise run test` and `bun test` (`README.md:118-124`, `AGENTS.md:3-11`), and the mise task is only a direct `bun test` wrapper (`.mise/tasks/test:1-4`). This is a testing-process gap: the documented gate does not currently verify timer boundaries, hook behavior, command parsing, CLI config preservation, or tool-name compatibility.
- High-value tests should cover decimal/min/max duration validation (`src/index.ts:220-230`), expiration and checkout boundary behavior (`src/index.ts:283-309`), corrupted and concurrent timer files (`src/index.ts:152-175`), command front matter and missing command directories (`src/index.ts:177-216`), shell-command false positives/escapes (`src/index.ts:360-369`), end-pattern matching (`src/index.ts:376-412`), and install/uninstall against valid, missing, malformed, and `plugins`-shaped configs (`src/cli.ts:15-57`).
- TypeScript is configured in strict, no-emit mode with Bun types and bundler resolution (`tsconfig.json:2-12`); the typecheck task runs `tsc --noEmit` (`.mise/tasks/typecheck:1-5`). ESLint treats Prettier violations and console usage as errors (`eslint.config.js:33-41`), although the CLI intentionally uses console output (`src/cli.ts:41-86`), so the lint task should be verified against the current source rather than assumed green.

## Packaging and release lessons

- `package.json` exposes the bundled plugin and CLI through `main`, `types`, `bin`, and `exports` (`package.json:11-22`), and publishes only `dist` plus `scripts` (`package.json:36-42`). The build copies `src/command` and `scripts` into `dist` after bundling both entrypoints (`package.json:40-42`, `.mise/tasks/build:1-9`). This is a practical pattern for runtime-loaded command assets, but it should be accompanied by a package-content smoke test because missing copied assets make command registration silently disappear (`src/index.ts:199-216`).
- The package pins the OpenCode plugin API to `1.0.85` and uses Zod as a runtime dependency (`package.json:43-58`). Pinning the host API can improve reproducibility, but the changelog shows that host validation changes directly affect loadability (`CHANGELOG.md:3-8`), so compatibility testing against supported OpenCode versions is important.
- Release metadata enables public npm publishing and provenance (`package.json:32-34`). The release process documents Release Please and npm Trusted Publishing through GitHub Actions/OIDC (`RELEASE.md:1-32`, `RELEASE.md:125-153`), avoiding long-lived npm tokens. The publish task disables provenance locally and enables it only in GitHub Actions (`.mise/tasks/publish:35-52`), a sensible separation that should remain enforced in CI.
- The package includes a Python script in the published `scripts` directory (`package.json:36-42`, `.mise/tasks/build:6-9`), but the TypeScript plugin uses `/tmp/workaholic_timer_<pid>.json` while the script uses `/tmp/workaholic_timers/<session>.json` (`src/index.ts:9-10`, `scripts/timer.py:7-11`). Shipping both implementations without a documented relationship increases maintenance and security-review surface; remove unused artifacts or test them as supported interfaces.
- The README offers `bunx opencode-workaholic@latest install` and manual plugin configuration (`README.md:73-108`), while the CLI writes a different config key (`src/cli.ts:7-12`, `src/cli.ts:62-74`). Installation documentation, CLI behavior, and package metadata should be validated together in a clean temporary home directory.

## Reusable takeaways

1. Prefer explicit, validated tool schemas and small lifecycle hooks, but keep policy enforcement separate from security guarantees.
2. Treat OpenCode tool names, hook names, and config keys as versioned integration contracts; update source, prompts, docs, and changelog together.
3. Persist only the minimum timer state, use a real session identifier, secure/atomically write state, and define corruption and cancellation behavior.
4. Make installation fail-safe: preserve malformed user config, use the canonical config key, and test install/uninstall idempotence.
5. Ensure the package's copied runtime assets are present and executable, and remove or explicitly test alternate implementations included in the tarball.
6. A documented test command is not a test suite. Add focused hook, timer, CLI, packaging, and compatibility tests before treating lint/typecheck/build as release confidence.
