## What it does

Harness Memory is a local-first OpenCode plugin that captures tool/conversation evidence, consolidates it into candidate memories, requires review before activation, and selectively injects approved memories into prompts (`README.md:6-10`, `README.md:24-68`). It uses SQLite through `sql.js`, lexical search, embeddings, and the OpenCode SDK (`README.md:155-162`).

## OpenCode patterns

- **Use the package metadata as an explicit plugin contract.** `package.json` declares `opencode.type: "plugin"` and the supported hook names, including chat, system transform, tool before/after, and session idle (`package.json:73-82`). The published plugin entry is the `./plugin` export (`package.json:42-46`), which is a one-line re-export (`src/plugin/index.ts:1`).
- **Keep the hook surface narrow and adapt to domain code.** The plugin defines small OpenCode-compatible input/output types, initializes one `OpenCodeAdapter`, and returns hook functions rather than coupling the whole domain to OpenCode types (`src/plugin/opencode-plugin.ts:43-125`, `src/plugin/opencode-plugin.ts:544-579`). This is a useful pattern when the adapter also needs a standalone test harness.
- **Inject at the system-transform lifecycle point.** The transform hook calls `beforeModel`, computes query/activation mode, appends returned system sections, and logs activation details (`src/plugin/opencode-plugin.ts:1251-1285`). The adapter separates cacheable baseline content from dynamic context content (`src/adapters/opencode-adapter.ts:307-371`), which is a practical prompt-cache optimization.
- **Capture tool context on both sides of execution.** `tool.execute.before` stores call arguments and evaluates policy/activation (`src/plugin/opencode-plugin.ts:1326-1354`); `tool.execute.after` joins those arguments with title/output/metadata, records evidence, buffers a conversation summary, and persists the database (`src/plugin/opencode-plugin.ts:1357-1408`, `src/adapters/opencode-adapter.ts:420-436`).
- **Use idle/compaction for non-user-blocking work.** Session idle and compacted hooks save state, launch summary generation without awaiting it, and run background extraction (`src/plugin/opencode-plugin.ts:1414-1454`). This avoids adding LLM consolidation latency to normal responses.
- **Make initialization lazy and recoverable.** The database is created/migrated at plugin load, while the heavier adapter, embedding service, repositories, and global-memory database are initialized once on demand (`src/plugin/opencode-plugin.ts:548-587`). Embedding warmup failures fall back to lexical search (`src/plugin/opencode-plugin.ts:590-592`), and global DB load failures are warned without disabling project memory (`src/plugin/opencode-plugin.ts:594-609`).

## Security lessons and pitfalls

- **Scan before prompt injection, not only at write time.** Activated memories are filtered through `scanMemoryContent` immediately before formatting (`src/adapters/opencode-adapter.ts:312-321`). The scanner normalizes NFKD/confusables, scans each field and the cross-field boundary, checks Base64-decoded credential content, and marks only block threats unsafe (`src/security/scanner.ts:309-381`). Tests cover invisible Unicode, prompt injection, credentials, exfiltration commands, sensitive files, and severity behavior (`test/security-scanner.test.ts:36-199`).
- **Keep safety filtering fail-closed for block findings but distinguish warnings.** Oversized/repetitive/non-printable content produces warnings while prompt injection/credential/malicious-instruction patterns block (`src/security/scanner.ts:267-307`, `src/security/scanner.ts:373-381`). The adapter test confirms an unsafe memory can still be selected by retrieval but is omitted from advisory text (`test/opencode-adapter.test.ts:73-105`), preserving auditability without exposing it to the model.
- **Bound evidence and activation payloads.** Tool evidence is serialized and truncated to a configurable maximum (`src/adapters/opencode-adapter.ts:386-437`), and adapter tests assert bounded memory count/payload behavior (`test/opencode-adapter.test.ts:44-71`). This is important for both token cost and hostile/accidental oversized tool output.
- **Do not let observability failures break the request.** Audit and file logging are wrapped in defensive helpers; file logging is explicitly non-critical (`src/plugin/opencode-plugin.ts:694-717`). Every lifecycle hook also catches and warns rather than throwing (`src/plugin/opencode-plugin.ts:1200-1235`, `src/plugin/opencode-plugin.ts:1327-1411`). The tradeoff is that production hook failures can become invisible unless logs are monitored.
- **Protect the sql.js stale-copy boundary.** CLI slash commands can mutate the database in a subprocess, so the after-tool hook reloads from disk before skipping its own evidence capture (`src/plugin/opencode-plugin.ts:1368-1375`). Without this ordering, a later save could overwrite CLI changes.
- **Installer trust boundary is broad.** `install` writes project `opencode.json`, creates `.opencode/commands`, creates both project and home-directory databases, imports bullets from `CLAUDE.md`/`.cursorrules` as active policy memories, and may execute `npm install` in `.opencode` (`src/cli/install.ts:146-163`, `src/cli/install.ts:193-215`, `src/cli/install.ts:218-265`). This is convenient, but should be reviewed before running in an untrusted repository or with a locked-down configuration.
- **Avoid floating runtime dependencies for reproducibility.** The installer writes `"harness-memory": "latest"` into `.opencode/package.json` (`src/cli/install.ts:226-251`). A release can therefore change without a project diff; a pinned version or lockfile policy would be safer.
- **Prompt command generation needs shell-quoting care.** Generated slash commands interpolate a database path directly into shell snippets (`src/cli/install.ts:50-80`). Paths with shell metacharacters could produce invalid or unsafe command text; use robust argument encoding if paths are not controlled.

## Testing and evaluation

- The default Vitest config includes `test/**/*.test.ts` but excludes embedding and benchmark-tier2 suites (`vitest.config.ts:3-14`). The package advertises 316 tests and separate benchmark commands (`README.md:161-177`), so CI should explicitly run the excluded suites when they are part of release confidence.
- Core unit coverage is broad: repository lifecycle/deduplication is tested (`test/memory-core.test.ts:23-77`, `test/memory-core.test.ts:104-120`), adapter session/injection/policy/evidence behavior is tested (`test/opencode-adapter.test.ts:23-71`, `test/opencode-adapter.test.ts:140-162`, `test/opencode-adapter.test.ts:247-260`), and promotion security is tested (`test/memory-promote-security.test.ts:21-67`).
- The test harness uses fresh in-memory sql.js databases and closes them after each test (`test/opencode-adapter.test.ts:11-20`). This isolates stateful plugin behavior without requiring a real project database.
- The repository includes an end-to-end packed-install verifier that packs the package, installs it into a temporary consumer, verifies exports, runs CLI commands, and checks generated artifacts (`scripts/verify-packed-install.mjs:53-119`). This is a strong packaging lesson because it validates the published shape rather than only source imports.
- No runtime tests were executed during this corpus review because the clone has no `node_modules/` directory; installing dependencies would modify the clone, which was out of scope. This is a review limitation, not a reported test failure.

## Packaging and configuration

- ESM-only packaging is explicit (`package.json:6-12`), while `tsup` emits bundled ESM entrypoints, declarations, sourcemaps, and separate CLI/plugin paths (`tsup.config.ts:3-55`). Externalizing `sql.js`, Transformers, and the OpenCode SDK avoids bundling large/runtime-sensitive dependencies (`tsup.config.ts:45-56`).
- The `files` allowlist publishes only `dist` and `README.md` (`package.json:48-54`). Because runtime migrations and evaluation assets are loaded relative to `dist`, build/copy verification is essential; the runtime helper expects bundled SQL under `dist/db/migrations` (`src/runtime/package-paths.ts:5-33`).
- The README documents the minimal registration shape, `"plugin": ["harness-memory/plugin"]`, and the project-local database path (`README.md:145-153`). The installer also appends the plugin entry without overwriting existing plugin entries, while leaving invalid `opencode.json` untouched (`src/cli/install.ts:165-191`).

## Reusable takeaways

1. Put OpenCode lifecycle wiring in a thin adapter/plugin layer and keep the core engine testable without OpenCode.
2. Inject memory only at the system-transform boundary, with explicit count/byte budgets and separate static/dynamic sections.
3. Treat retrieved memory as untrusted prompt input: normalize and scan at the final disclosure boundary, then test both blocking and warning paths.
4. Use idle/compaction for background LLM work, but make failures observable because hook-level catch-and-warn otherwise degrades silently.
5. Validate the npm tarball in a clean consumer, including plugin resolution, CLI behavior, migrations/assets, and generated OpenCode commands.
6. Pin installer dependencies and quote generated shell arguments; convenience installers should minimize writes and avoid silently importing unreviewed content as active policy.
