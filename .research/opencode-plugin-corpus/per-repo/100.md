## What It Does

This is a source-distributed OpenCode plugin that appends an AI-model signature to GitHub PR/Issue bodies and commit messages. The README documents installation through the OpenCode `plugin` array and says the plugin operates automatically, without configuration (`README.md:20-29`, `README.md:54-56`, `README.md:199-201`). It supports named GitHub/MCP tools plus `bash` commands for `git commit` and `gh` operations (`README.md:74-105`).

The entrypoint exports both a named and default `Plugin` implementation (`src/plugin.ts:31-32`, `src/plugin.ts:95-97`). It tracks the current model from `chat.message`, then handles `tool.execute.before` (`src/plugin.ts:47-63`). MCP calls mutate `output.args.body`; bash commands are passed through independent Git and GitHub rewriters so a single command can contain both operations (`src/plugin.ts:64-91`).

## OpenCode Patterns

### Hook-local state and narrow interception

- Model state is scoped to one plugin initialization rather than global module state (`src/plugin.ts:31-34`).
- The plugin uses the model supplied on `chat.message` input and formats it before later tool interception (`src/plugin.ts:49-57`). This is a useful pattern when hook output does not carry the model context.
- Tool matching is explicit for the eight supported GitHub/MCP operation names (`src/plugin.ts:35-45`). Bash handling is limited to `input.tool === "bash"` and an available command string (`src/plugin.ts:79-82`), reducing accidental mutation of unrelated tools.
- Rewriters are composable and order-independent at the dispatch level: each receives the prior result and may return it unchanged (`src/plugin.ts:23`, `src/plugin.ts:84-91`).

### Conservative command rewriting

- The implementation scans a length-preserving masked copy of the shell command, while slicing and editing the original. Heredoc content is treated as data, preventing semicolons, `&&`, or option-looking text in commit messages from becoming shell syntax (`src/shell.ts:99-108`, `src/shell.ts:285-287`).
- It recognizes command boundaries, quotes, substitutions, assignments, redirects, pipelines, and heredocs instead of using a global string replacement (`src/shell.ts:154-188`, `src/shell.ts:209-285`, `src/shell.ts:314-342`). It rejects ambiguous cases rather than guessing (`src/git-commit.ts:37-41`, `src/git-commit.ts:114-125`, `src/git-commit.ts:234-235`).
- Message sources are handled according to when the text exists: inline `-m` is edited in place; files, stdin, and `--amend --no-edit` are routed through a runtime signing stage (`src/git-commit.ts:23-35`, `src/git-commit.ts:277-315`). This preserves working-directory-dependent paths and runtime-produced streams (`src/signed-message.ts:35-47`).
- Dynamic `gh --body` expressions are evaluated once and wrapped at runtime; file/stdin body options are intentionally unsupported so an unreadable file cannot become an empty successful body (`src/gh.ts:67-77`, `src/gh.ts:121-128`).

### Idempotence and shell safety

- A single stable marker is shared by generation and duplicate detection (`src/signature.ts:6-10`, `src/signature.ts:17-26`).
- Signature and rewritten static values are single-quoted with embedded apostrophes escaped, preventing shell expansion and preserving arbitrary message text (`src/shell.ts:439-445`). Runtime branches quote the message variable and signature (`src/signed-message.ts:18-31`).
- Blank inline/file/runtime messages remain blank so the underlying Git rejection is preserved rather than turning the signature into a commit message (`src/git-commit.ts:47-55`, `src/signed-message.ts:35-47`).
- The README explicitly documents unsupported cases such as editor-supplied messages, message reuse, `--squash`/`--fixup`, ambiguous globs, and uncertain parsing (`README.md:162-197`). This “no rewrite on uncertainty” policy is an important safety property for plugins that mutate commands.

## Pitfalls and Risks

- **MCP argument shape is assumed, not validated.** For a recognized MCP tool, any truthy `output.args.body` is sent to `.trim()` and `hasSignature()`; a non-string body would throw, and a falsy non-string body is replaced with the signature (`src/plugin.ts:64-75`). A production-hardening improvement would require `typeof body === "string"` or explicitly handle the SDK's typed argument shape before mutation.
- **The marker is broad.** `hasSignature` suppresses signing whenever the body contains `Generated with [OpenCode]`, regardless of URL, emoji, or model (`src/signature.ts:22-26`). This avoids duplicates but lets user-authored prose containing the marker opt out accidentally.
- **Model attribution is latest-message state.** The model is updated on every `chat.message` and reused for later tool calls (`src/plugin.ts:49-57`). If concurrent sessions share one plugin instance or tool execution is delayed, a signature could reflect a newer message's model. The code has no session-keyed model map.
- **The shell parser is intentionally partial.** It declines unsupported syntax, but supported syntax still depends on a hand-rolled parser for POSIX shell constructs (`src/shell.ts:1-8`, `src/shell.ts:504-547`). New shell forms or unusual quoting should be treated as compatibility-risk areas, not assumed to be covered by the broad feature list.
- **Supported GitHub/MCP names are hard-coded.** New server/tool naming variants are ignored unless added to `prIssueTools` (`src/plugin.ts:35-45`). The README's operation list should be kept synchronized with this array (`README.md:74-86`).
- **Runtime signing shells out to `cat` and `git log`.** These commands inherit the execution environment and PATH of the user's shell (`src/signed-message.ts:51-53`, `src/git-commit.ts:203-217`). The design preserves user command semantics, but tests and documentation should continue to make the shell/platform assumptions explicit.

## Testing Lessons

- The suite drives the actual OpenCode hooks, first reporting a model and then invoking `tool.execute.before`, rather than testing only private rewriter functions (`test/plugin.test.ts:11-33`). This verifies hook dispatch, model formatting, and rewriting together.
- Tests execute rewritten commands in throwaway Git repositories under `/bin/sh`, and use a stub `gh` executable to observe arguments (`test/plugin.test.ts:36-48`, `test/plugin.test.ts:55-85`). This is high-value coverage for command-transforming plugins because it tests resulting behavior, not just strings.
- Coverage includes quoting, heredocs, pipes, redirects, command substitutions, environment assignments, comments, chained commands, empty messages, duplicate signatures, unsupported options, GitHub/MCP bodies, and combined commit-plus-PR commands (`test/plugin.test.ts:136-191`, `test/plugin.test.ts:194-313`, `test/plugin.test.ts:333-412`, `test/plugin.test.ts:470-639`).
- The test contract requires `git`, `/bin/sh`, and a POSIX shell on PATH (`README.md:203-217`). The suite uses `/bin/bash` only for the here-string case (`test/plugin.test.ts:367-375`), so cross-platform CI should either preserve those prerequisites or mark platform-specific cases clearly.
- A remaining test gap is malformed runtime hook data, especially non-string MCP `body` values and model objects with missing/invalid fields. Those cases are accepted by the TypeScript casts in the test harness (`test/plugin.test.ts:16-33`) but not tested as runtime inputs.

## Reusable Takeaways

1. For OpenCode hooks that mutate commands, parse only the syntax needed, preserve the original text, and return it unchanged whenever semantics are ambiguous.
2. Defer transformation until runtime when the input is a file, stream, variable, or command substitution; this preserves working-directory, expansion, and exit-status behavior.
3. Test rewritten commands by executing them in isolated repositories and stub external CLIs, then assert the real Git/CLI result.
4. Keep duplicate detection centralized and quote every generated shell value, including model-derived text.
5. Validate runtime hook payloads at the boundary even when TypeScript types appear to guarantee the shape; plugin hooks receive external/tool data.
