The repository contains a TypeScript OpenCode plugin (`src/`), a Bash wrapper/CLI (`bin/opencode-memory`), tests, and GitHub workflows. The README says the design is a local Markdown compatibility layer shared bidirectionally with Claude Code (`README.md:3-10`, `README.md:112-123`).

## OpenCode Integration Patterns

1. **Use the plugin factory and hooks as the integration boundary.** `MemoryPlugin` receives `worktree`, `directory`, and `client`, initializes the resolved memory directory, and returns `config`, `event`, `chat.params`, `tool.execute.after`, `experimental.chat.messages.transform`, `experimental.chat.system.transform`, and five tools (`src/index.ts:497-550`, `src/index.ts:553-646`, `src/index.ts:648-751`). This is a useful pattern for keeping OpenCode-specific lifecycle behavior in one adapter while keeping CRUD and parsing modules independently testable.
2. **Register hidden helper agents through `config`.** The plugin adds a hidden recall agent and a hidden extraction agent only when absent (`src/index.ts:502-521`). Recall selection uses a child session, structured JSON schema output, a manifest, and allowlisted filenames; it deletes the child session in `finally` (`src/recallSelector.ts:108-149`, `src/recallSelector.ts:169-205`).
3. **Derive turn state from the current message list.** The transform reconstructs surfaced memory keys and completed tools from messages, builds a turn ID, and starts asynchronous recall prefetch (`src/index.ts:105-139`, `src/index.ts:571-611`). The system transform consumes the settled prefetch and injects the generated memory prompt (`src/index.ts:626-646`). This avoids relying solely on process-global turn state and lets compaction naturally reduce derived context.
4. **Implement explicit “ignore memory” behavior at both transforms.** The plugin recognizes an environment override and common user phrasings, removes existing `# Auto Memory` system parts, and omits the index and recalled section from the replacement prompt (`src/index.ts:40-49`, `src/index.ts:613-645`). Tests cover direct text, `parts[].text`, existing system messages, and the environment override (`test/index.test.ts:121-149`, `test/index.test.ts:179-260`).
5. **Keep extraction isolated and tool-restricted.** Native extraction reads the parent transcript, caps it at 60,000 characters while retaining the tail, creates a child session, disables all tools before enabling only `memory_save` and `memory_list`, applies a hard 120-second timeout, and deletes the child (`src/index.ts:371-401`, `src/index.ts:418-480`). It is opt-in off Windows and default-on there, with explicit environment overrides (`src/index.ts:485-495`).

## Storage, Security, and Reliability Lessons

- **Canonical worktree mapping is security-sensitive.** Memory paths use Claude-compatible sanitization and hashing, resolve Git worktrees through `.git`/`gitdir`/`commondir`, and validate both the worktree directory backlink and direct-child relationship before accepting the common root (`src/paths.ts:42-65`, `src/paths.ts:96-137`). The fallback is the discovered Git root when validation fails, rather than trusting an arbitrary redirect.
- **Validate every user/model-controlled filename before filesystem access.** The validator rejects separators, `..`, null bytes, dot-prefixed names, and the reserved `MEMORY` name; `readMemory`, `saveMemory`, and `deleteMemory` all call it before joining paths (`src/paths.ts:17-40`, `src/memory.ts:110-114`, `src/memory.ts:132-143`, `src/memory.ts:157-161`). This is the key path-traversal boundary and must not be bypassed for convenience.
- **Bound prompt and disk exposure.** Memory files are capped at 200 entries and 40,000 UTF-8 bytes, frontmatter is read within 30 lines, recalled content is capped at five memories/200 lines/4,096 UTF-8 bytes, and `MEMORY.md` is capped at 200 lines/25,000 characters (`src/paths.ts:9-15`, `src/recall.ts:14-16`, `src/recall.ts:40-59`, `src/memory.ts:142-148`, `src/memory.ts:234-271`). The tests exercise recursive scanning, malformed frontmatter, mtime ordering, and manifest formatting (`test/memoryScan.test.ts:38-187`).
- **Treat memories as stale data, not authority.** Recall includes an age warning after one day and instructs the model to verify current files before relying on a memory (`src/recall.ts:105-123`). The generated prompt separately tells the model to check named files/functions/flags and prefer current code or Git history for current state (`src/prompt.ts:99-121`).
- **There are still write-integrity pitfalls.** `saveMemory` writes the memory file and then rewrites `MEMORY.md` in separate non-atomic operations (`src/memory.ts:144-154`, `src/memory.ts:192-206`); an interruption can leave the index out of sync. The implementation also interpolates `name` and `description` directly into YAML-like frontmatter and Markdown index lines without escaping or a length check (`src/memory.ts:65-67`, `src/memory.ts:197-206`). Inputs should be constrained or safely encoded if memories can be created from untrusted transcript text.
- **The native extraction sandbox is a strong defense against prompt injection, but its scope is narrow by design.** Transcript/tool output is explicitly treated as untrusted and the child gets only memory tools (`src/index.ts:418-420`, `src/index.ts:450-465`). The Bash extraction path also instructs the model not to save code/config-derived or ephemeral facts (`bin/opencode-memory:309-347`). This reduces arbitrary tool execution, but memory writes themselves remain a durable prompt-injection channel and need review/cleanup controls.
- **Wrapper concurrency is project-scoped.** The Bash wrapper derives a Git-root project key and creates extraction/consolidation lock locations under temporary and Claude config directories (`bin/opencode-memory:281-303`). It supports foreground/background maintenance and validates numeric/boolean environment settings (`bin/opencode-memory:391-429`). The wrapper has more platform/runtime prerequisites than the plugin: `python3` is used for session and fork handling, and `jq` is documented for session counting (`README.md:34-42`, `bin/opencode-memory:22-25`).

## Testing Lessons and Gaps

- The test suite is broad and layered: CRUD/index lifecycle, prompt integration, recall formatting and caps, recursive scanning, selector child-session behavior, wrapper subprocess behavior, tool titles, and packaging/workflow smoke checks. The integration test covers save -> list -> search -> read -> recall -> delete and index update (`test/integration.test.ts:31-93`), while selector tests verify create/prompt/delete ordering and cleanup (`test/recallSelector.test.ts:67-131`).
- Tests use temporary directories and cleanup hooks instead of touching a developer’s real Claude memory (`test/integration.test.ts:11-25`, `test/memoryScan.test.ts:7-36`). Wrapper tests create fake executables, isolated `HOME`/`TMPDIR`, and a temporary SQLite session database (`test/opencode-memory.test.ts:22-71`, `test/opencode-memory.test.ts:73-132`). This is a good model for testing shell integrations without requiring a live OpenCode installation.
- CI pins Bun 1.3.11, runs a dedicated E2E regression test and the full suite, and grants read-only repository contents (`.github/workflows/ci.yml:8-27`). The repository’s acceptance report records 89 tests at an earlier snapshot (`REAL_ENV_ACCEPTANCE_REPORT.md:36-50`), whereas this audited clone’s local run produced `119 pass`, `0 fail`, across 12 files. The local result is direct verification of this clone; the report should not be treated as its current count.
- **Important coverage gap:** the unit tests validate behavior with fake clients and subprocesses, but the repository’s acceptance report says real-provider/runtime validation was performed separately (`REAL_ENV_ACCEPTANCE_REPORT.md:52-76`). A production change to OpenCode message shapes, session APIs, or permissions therefore still needs an isolated real-runtime smoke test, not only mocks.
- The suite does not appear to test atomic crash recovery between memory and index writes, permissions of newly created memory files, or adversarial frontmatter/index values. Those are the highest-value additions suggested by the implementation boundaries above.

## Packaging and Release Lessons

- The package publishes compiled TypeScript: `main`/`types` and conditional exports point to `dist`, `files` includes `dist`, and `prepack` runs the compiler (`package.json:6-23`). `tsconfig.json` uses strict TypeScript, ESM, bundler resolution, declarations, and Bun types (`tsconfig.json:2-14`).
- `@opencode-ai/plugin` is a peer dependency while `zod` is a runtime dependency (`package.json:55-64`). This keeps the host SDK supplied by OpenCode but makes the package’s compatibility dependent on the host’s plugin API; the peer range is currently `*`, so compatibility is not enforced at install time (`package.json:55-56`).
- Release automation uses semantic-release on `main`, checks out full history, installs Bun and Node, publishes with npm provenance, and requests write/id-token permissions (`.releaserc:1-9`, `.github/workflows/publish.yml:8-37`). The workflow is manually dispatchable and its publish permissions are deliberately broader than CI’s read-only permissions (`.github/workflows/publish.yml:3-15`).
- The published package also exposes `bin/opencode-memory` (`package.json:8-10`), while the package file allowlist is only `dist` (`package.json:18-20`). npm normally includes declared bin files, but packaging tests assert only the compiled entrypoint and release workflow (`test/publish-config.test.ts:16-45`); an explicit pack/install smoke test would better prove the CLI survives publication.
- Repository metadata is internally inconsistent: `AGENTS.md` says OpenCode consumes raw `.ts` with “no build step” (`AGENTS.md:1-3`), but the package, `prepack`, and publish tests clearly define a compiled `dist` artifact (`package.json:6-23`, `test/publish-config.test.ts:17-34`). Maintainers should keep contributor guidance aligned with the actual distribution path.

## Bottom Line

This is a strong example of an OpenCode plugin that combines narrow host hooks with independently testable local persistence. The most reusable patterns are child-session cleanup in `finally`, explicit tool allowlisting for transcript-derived agents, canonical Git/worktree resolution, bounded prompt loading, and an end-to-end test harness using isolated filesystem and fake runtime boundaries. The main risks are non-atomic file/index updates, unescaped metadata interpolation, broad peer-version compatibility, and insufficient published-CLI and crash-recovery tests.
