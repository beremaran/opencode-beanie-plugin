## OpenCode patterns

- The entrypoint exports a `Plugin`-typed async function and uses the plugin SDK's `tool` helper/schema (`src/index.ts:1-7`, `src/index.ts:51-52`). This is a direct, conventional package-level plugin entrypoint rather than a CLI wrapper.
- Configuration is parsed with Zod before hooks are created. Invalid configuration logs through `client.app.log`, optionally shows a TUI error toast, and returns an empty hook object; `enabled: false` likewise returns `{}` (`src/index.ts:52-77`). Defaults and the accepted option surface are centralized in `src/config.ts:3-26`.
- The plugin exposes a dynamically named tool. Its `level` argument is a string, while `persist` is optional and defaults to `false`; execution first resolves the active model's variants, rejects unsupported levels before prompting, then sends a synthetic, ignored prompt carrying the selected `variant` (`src/index.ts:214-257`). This is a useful pattern for changing request metadata through the existing session API without exposing a separate transport.
- Variant discovery is model-aware: it first uses the model passed to the transform, then falls back through the latest session message to provider metadata (`src/index.ts:79-83`, `src/index.ts:117-154`). Current-variant discovery also falls back to the newest relevant agent configuration when messages do not contain a model variant (`src/index.ts:172-212`).
- Two lifecycle surfaces keep behavior coherent: `experimental.chat.system.transform` appends one consolidated instruction containing the current and valid levels, and `session.idle` restores a temporary override (`src/index.ts:322-348`, `src/index.ts:286-320`). The README documents the temporary versus persisted semantics (`README.md:65-90`).
- Synthetic prompts preserve both the initiating agent and the currently selected model, including on reset (`src/index.ts:85-115`, `src/index.ts:241-255`, `src/index.ts:295-301`). The changelog explicitly identifies this as a fix for accidental fallback to agent/provider defaults (`CHANGELOG.md:3-13`).

## Pitfalls and security lessons

- Cached state must be validated against the current model. The transform only reuses cached or resolved variants when they are present in the current model's variant set (`src/index.ts:328-339`); otherwise it resolves a current value. This prevents a model switch from advertising or reusing an invalid effort level, a regression covered by the test at `src/index.test.ts:251-273` and documented in `CHANGELOG.md:27-31`.
- Session-local state can otherwise grow for the lifetime of the OpenCode process. The implementation uses a 500-entry LRU cache and evicts the oldest session (`src/index.ts:8`, `src/index.ts:18-43`); the eviction behavior is tested at `src/index.test.ts:328-340` and the rationale is recorded in `CHANGELOG.md:33-37`.
- Reset failure is deliberately retryable: a failed `session.idle` reset logs an error but leaves reset state available for a later idle event (`src/index.ts:302-318`). The three-idle recovery test verifies this behavior (`src/index.test.ts:390-417`).
- The tool rejects invalid levels before calling `promptAsync` (`src/index.ts:232-239`), limiting accidental state mutation and unnecessary requests; this is asserted at `src/index.test.ts:355-368`.
- Configuration accepts arbitrary strings for `toolName`, `toolDescription`, and `systemPrompt` with no length or content constraints (`src/config.ts:17-26`). That is flexible, but consumers should treat configuration as trusted: a custom system prompt changes agent instructions, and an unusual tool name can make the documented tool unavailable. The README documents these knobs but does not prescribe validation beyond type checking (`README.md:35-63`, `README.md:92-98`).
- The implementation does not invoke a shell, evaluate configuration, or handle credentials; it routes data through the OpenCode client (`src/index.ts:111-115`, `src/index.ts:137-154`). The remaining observable risk is operational: provider/session error payloads are JSON-stringified into logs (`src/index.ts:121-130`, `src/index.ts:137-145`, `src/index.ts:302-308`), so deployments should ensure OpenCode logs are appropriately protected if upstream errors can contain sensitive data.

## Testing lessons

- Tests use Vitest with a small mocked OpenCode client covering session messages, provider discovery, agent discovery, logging, toasts, and synthetic prompts (`src/index.test.ts:1-55`). This keeps plugin behavior testable without a live OpenCode server.
- The suite covers defaults, custom names/prompts, disabled and invalid configuration, preservation of agent/model identity, stale-cache invalidation, agent fallback, temporary/persisted semantics, LRU eviction, invalid input, provider lookup failure, and reset retry (`src/index.test.ts:96-417`). The test names provide a practical behavior matrix for similar lifecycle plugins.
- A notable gap is that the suite verifies mocked return values and calls but does not test against a real OpenCode runtime or provider. Error handling is therefore contract-level rather than integration-level evidence.

## Overall assessment

This is a focused, well-tested lifecycle plugin. Its strongest reusable patterns are validating model-dependent state at the point of use, preserving agent/model context in synthetic prompts, bounding session caches, and making failed cleanup retryable. Main residual risks are reliance on mocked SDK behavior, unrestricted trusted configuration strings, and logging of serialized upstream error data; packaging and CI are comparatively disciplined, with a clear build output allowlist, frozen-lockfile checks, provenance, and Changesets.
