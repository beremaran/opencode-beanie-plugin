## OpenCode patterns

- **Small plugin entrypoint with explicit lifecycle hooks.** The exported
  `HooksPlugin` receives `{ directory, client }`, loads configuration once, and
  returns `tool.execute.before`, `tool.execute.after`, and `event` handlers
  ([src/index.ts:129-141](../repos/romain325--opencode-hooks-plugin/src/index.ts#L129-L141),
  [src/index.ts:365-369](../repos/romain325--opencode-hooks-plugin/src/index.ts#L365-L369)).
  This is a useful pattern for keeping OpenCode wiring in one adapter while
  delegating configuration, event translation, matching, and execution to modules.
- **Use OpenCode hook mutation for pre-tool policy.** Before execution, the plugin
  converts the tool call into Claude-shaped input, runs matching handlers, throws on
  a block, and applies `updatedInput` to `output.args`
  ([src/index.ts:141-178](../repos/romain325--opencode-hooks-plugin/src/index.ts#L141-L178)).
  A hook-compatible JSON contract can therefore provide both deny and input-rewrite
  behavior without changing existing Claude settings.
- **Translate event shapes at a boundary.** `events.ts` builds stable
  `session_id`, `cwd`, `hook_event_name`, `tool_name`, and `tool_input` payloads
  ([src/events.ts:24-47](../repos/romain325--opencode-hooks-plugin/src/events.ts#L24-L47)).
  The architecture documents native mappings, slash-command stubs, and unsupported
  events separately ([ARCHITECTURE.md:109-145](../repos/romain325--opencode-hooks-plugin/ARCHITECTURE.md#L109-L145)).
- **Layer settings without inventing a new schema.** Global, project, and local
  Claude settings are read in order; hook arrays are appended and
  `disableAllHooks` uses local/project/global precedence
  ([src/config.ts:59-84](../repos/romain325--opencode-hooks-plugin/src/config.ts#L59-L84)).
  This provides a practical shareable/local override split, also documented for
  users ([README.md:99-107](../repos/romain325--opencode-hooks-plugin/README.md#L99-L107)).
- **Make matcher failure non-fatal.** Matchers support omitted/empty/`*` values,
  case-insensitive regular expressions, and invalid-regex rejection instead of
  crashing the plugin ([src/matcher.ts:8-21](../repos/romain325--opencode-hooks-plugin/src/matcher.ts#L8-L21)).
- **Run independent handlers concurrently, then aggregate outcomes.** Matching
  handlers are collected as promises and awaited together
  ([src/index.ts:22-47](../repos/romain325--opencode-hooks-plugin/src/index.ts#L22-L47)).
  The executor normalizes all handler types to `allow`, `block`, `error`, or `skip`
  ([src/types.ts:94-102](../repos/romain325--opencode-hooks-plugin/src/types.ts#L94-L102)).

## Pitfalls and security lessons

- **Post-tool failure detection is heuristic and loses available fields.** The
  adapter constructs `OpenCodeToolAfterEvent` with only session, tool, args, and
  output; it does not pass `output.title`, `output.metadata`, or an error flag
  ([src/index.ts:181-197](../repos/romain325--opencode-hooks-plugin/src/index.ts#L181-L197)).
  `detectToolFailure` then relies on string patterns such as `error`, `failed`, and
  `exit code` ([src/events.ts:50-79](../repos/romain325--opencode-hooks-plugin/src/events.ts#L50-L79)).
  This can misclassify ordinary output and miss structured failures; a plugin should
  prefer authoritative SDK status fields and test the exact runtime event shape.
- **Blocking semantics are inconsistent by event.** A `PreToolUse` block throws and
  prevents execution, but blocks from after-tool, session, and slash-command hooks
  are only logged ([src/index.ts:168-178](../repos/romain325--opencode-hooks-plugin/src/index.ts#L168-L178),
  [src/index.ts:214-221](../repos/romain325--opencode-hooks-plugin/src/index.ts#L214-L221),
  [src/index.ts:116-123](../repos/romain325--opencode-hooks-plugin/src/index.ts#L116-L123)).
  Documentation should distinguish advisory results from enforceable policy.
- **The documented `permissionDecision` is not enforced.** The type exposes
  `allow`, `deny`, and `ask` ([src/types.ts:77-83](../repos/romain325--opencode-hooks-plugin/src/types.ts#L77-L83)),
  but `outputToResult` only blocks on `decision: "block"`, `continue: false`, or
  `ok: false` ([src/executor.ts:27-44](../repos/romain325--opencode-hooks-plugin/src/executor.ts#L27-L44)).
  A hook returning `permissionDecision: "deny"` can therefore be reported as allow.
  Security-sensitive contracts must map every documented deny signal to the actual
  OpenCode enforcement mechanism.
- **Malformed handler output fails open.** Empty or invalid JSON is converted to
  `null`, and `null` becomes `{ action: "allow" }`
  ([src/executor.ts:17-24](../repos/romain325--opencode-hooks-plugin/src/executor.ts#L17-L24),
  [src/executor.ts:27-30](../repos/romain325--opencode-hooks-plugin/src/executor.ts#L27-L30)).
  That is convenient for notification hooks but unsafe for a safety hook; strict
  mode should treat malformed output and timeout as deny/error according to policy.
- **Command hooks are deliberately full shell execution.** Commands are passed to
  `bash -c` with inherited environment ([src/executor.ts:55-69](../repos/romain325--opencode-hooks-plugin/src/executor.ts#L55-L69)).
  This is compatible with Claude hooks but means project settings are executable
  code and global hooks can affect every project. The local settings file is
  specifically intended to be gitignored ([README.md:99-107](../repos/romain325--opencode-hooks-plugin/README.md#L99-L107));
  reviewers should treat committed hook configuration as a supply-chain boundary.
- **Secrets can be sent to external endpoints.** HTTP headers interpolate arbitrary
  uppercase environment variables and requests POST the complete hook input
  ([src/executor.ts:125-152](../repos/romain325--opencode-hooks-plugin/src/executor.ts#L125-L152)).
  There is no URL allowlist, redaction, or payload minimization. The feature needs
  explicit trust guidance, and potentially endpoint restrictions, before use with
  sensitive tool arguments.
- **Process-wide environment mutation is racy.** The plugin writes session and event
  values to `process.env` in each event path ([src/index.ts:155-158](../repos/romain325--opencode-hooks-plugin/src/index.ts#L155-L165));
  concurrent hooks can observe another event's values. Passing a per-process env
  snapshot to each child is safer than mutating global state.
- **Parallel aggregation does not implement the stated first-resolved policy.** The
  architecture says the first blocking result wins ([ARCHITECTURE.md:269-271](../repos/romain325--opencode-hooks-plugin/ARCHITECTURE.md#L269-L271)),
  but `Promise.all` waits for every handler and `findBlockResult` chooses array
  order, not resolution order ([src/index.ts:31-50](../repos/romain325--opencode-hooks-plugin/src/index.ts#L31-L50)).
  Slow or hanging handlers therefore delay a block, and conflicting updates are
  order-dependent.

## Testing lessons

- The repository has 120 passing tests across four files in the checked snapshot:
  `bun test` completed with 0 failures. Tests cover settings precedence and malformed
  JSON, event translation/failure heuristics, all four executors, timeouts, stdin,
  environment interpolation, and matcher edge cases
  ([README.md:209-221](../repos/romain325--opencode-hooks-plugin/README.md#L209-L221)).
- The test isolation is particularly strong for settings: each test uses temporary
  project and fake-home directories so the real user Claude settings cannot leak into
  results ([src/config.test.ts:23-60](../repos/romain325--opencode-hooks-plugin/src/config.test.ts#L23-L60)).
  HTTP and SDK calls are mocked while command tests exercise real Bash subprocesses
  ([README.md:220-222](../repos/romain325--opencode-hooks-plugin/README.md#L220-L222)).
- Missing coverage remains at the integration boundary: no test exercises the
  exported plugin against actual OpenCode hook callback shapes, `output.args` mutation,
  event registration, slash-command behavior, or concurrent conflicting handlers.
  The existing tests validate the helpers in isolation, for example event mapping
  and heuristic classification ([src/events.test.ts:16-61](../repos/romain325--opencode-hooks-plugin/src/events.test.ts#L16-L61),
  [src/events.test.ts:98-208](../repos/romain325--opencode-hooks-plugin/src/events.test.ts#L98-L208)).
- Add regression tests for structured `permissionDecision: "deny"`, malformed output
  under a security mode, authoritative tool failure metadata, timeout/child-process
  cleanup, and simultaneous event execution. These target the implementation risks
  above rather than adding more happy-path handler tests.

## Overall assessment

The strongest reusable idea is a narrow OpenCode adapter around a well-defined,
Claude-compatible hook contract, backed by isolated unit tests and explicit
unsupported-event warnings. The main production risks are fail-open parsing,
unenforced permission output, heuristic failure detection, process-global state, and
inconsistent blocking semantics. Before treating it as a security control, add an
integration test harness against the OpenCode SDK event shapes and make deny/error
behavior explicit for every handler and lifecycle event.
