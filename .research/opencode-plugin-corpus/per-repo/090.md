## What it does

The plugin incrementally summarizes visible conversation messages into a structured per-session Markdown file, injects compacted memory into the system transform every N user turns, and pushes memory into compaction context (`README.md:1-3`, `README.md:65-71`). It exposes both an `/stm` command and a `short_term_memory` agent tool with status, show, update, reset, logs, and settings actions (`README.md:44-63`; `src/session-memory.ts:398-405`, `src/tools.ts:19-31`).

## OpenCode patterns worth reusing

### Hook surface and factory shape

- Export a named and default async plugin factory from a tiny package entrypoint (`index.ts:1-2`; `src/index.ts:1-2`). The factory receives the OpenCode client and directory and returns the hook object (`src/session-memory.ts:68-74`).
- The returned object covers config mutation, generic events, tools, command interception, session lifecycle, message/chat hooks, system transformation, and compaction (`src/session-memory.ts:397-674`). This is a useful reference for composing a plugin around the current SDK hook names while keeping instance state inside the factory (`src/session-memory.ts:78-101`).
- Runtime payloads are handled through local permissive interfaces because the SDK does not fully type all runtime hooks (`src/types.ts:7-17`, `src/types.ts:79-103`). The code centralizes defensive session-ID extraction across payload variants (`src/memory-utils.ts:437-462`).

### Incremental state and prompt hygiene

- Store a per-session checkpoint containing the last processed message ID and only summarize messages after it (`src/message-collector.ts:61-70`, `src/message-collector.ts:73-130`). Save the checkpoint only after an atomic memory write (`src/memory-lifecycle.ts:181-197`).
- Sort upstream messages by creation time with ID fallback before applying the checkpoint (`src/message-collector.ts:101-127`). This avoids relying on an SDK response ordering contract.
- Filter internal/tool/reasoning/synthetic content before it reaches the model, and reject prior memory injections from being summarized again (`src/message-collector.ts:131-177`; `src/memory-utils.ts:485-549`). The configurable assistant-burst collapse is explicit and tested (`src/message-collector.ts:156-177`; `test/message-collector.test.ts:48-118`).
- Bound both upstream history (`maxDeltaMessages`) and each summarizer chunk (`maxUpdateInputLength`); an individual oversized entry is truncated with an explicit marker (`src/message-collector.ts:88-90`; `src/memory-lifecycle.ts:68-89`).
- The summarizer prompt labels existing memory and conversation as data, explicitly forbids following project instructions, preserves user instructions, and defines conservative incremental retention (`src/summarizer.ts:31-87`). This is a strong prompt-injection boundary, although it is not a substitute for isolating the summarizer session.
- Normalize model output to a versioned Markdown format, strip code fences, enforce the memory header, and reject malformed output before writing (`src/summarizer.ts:126-137`; `src/memory-lifecycle.ts:161-179`).

### Resilience and lifecycle handling

- Clean mode creates a separate SDK side session with `noReply: true`, a summarizer-only system prompt, selected model, timeout, and finally-based deletion (`src/summarizer.ts:176-279`). The 90-second abort also calls `client.session.abort` best-effort (`src/summarizer.ts:213-247`).
- Side-session IDs are tracked before prompting so a process crash can be repaired at startup; cleanup combines the tracking file with a live session scan and retains failed deletions for retry (`src/summarizer.ts:195-211`; `src/session-memory.ts:173-269`).
- Clean summarization has bounded retries and an opt-in active-session fallback; failure is surfaced through toast and structured logs rather than silently writing bad memory (`src/memory-lifecycle.ts:104-159`).
- The plugin defers config, directory, log, and orphan-cleanup I/O to background initialization, emits an opt-in startup timing marker, and fixes its completion flag in `finally` (`src/session-memory.ts:107-163`, `src/session-memory.ts:388-395`).
- Same-session updates are serialized with `updateInFlight` and a pending replay, while compaction waits for drain and records a stale-memory warning on timeout (`src/session-memory.ts:282-375`, `src/session-memory.ts:627-672`).
- File writes use per-path locks plus temp-file write, fsync, rename, retry, and cleanup (`src/memory-utils.ts:70-98`, `src/memory-utils.ts:124-161`). This is appropriate for concurrent event handlers and crash-sensitive checkpoints.
- Session deletion removes memory/checkpoint files and all in-memory parent/child, timer, LRU, and pending-update state (`src/session-memory.ts:534-570`). Sub-agents inherit a parent snapshot but never summarize independently (`src/session-memory.ts:495-515`, `src/session-memory.ts:296-303`).

## Pitfalls and security lessons

- **Treat conversation as hostile data.** The prompt uses XML-like delimiters and instructions to treat both inputs as data (`src/summarizer.ts:36-40`, `src/summarizer.ts:106-112`), but the conversation is still interpolated into a model prompt. A production derivative should retain the clean side-session isolation, keep strict output validation, and avoid trusting model-produced Markdown as executable configuration.
- **Do not log sensitive prompts by default.** Debug mode logs the complete summarizer prompt and injected system message (`src/memory-lifecycle.ts:95-102`; `src/injection.ts:71-79`). The default is safe (`debug: false`, `src/memory-utils.ts:32-49`), but enabling debug can persist user instructions, project content, and model context in `.opencode/memory/session-memory.log`.
- **Configuration paths are powerful.** `memoryDir` is normalized as a non-empty string but is otherwise accepted, including absolute or traversal-capable paths (`src/memory-utils.ts:204-233`, `src/memory-utils.ts:367-377`). A derivative should constrain or explicitly warn about paths outside the project and should consider permissions for memory and logs.
- **Model configuration is only syntactically parsed.** `parseModel` splits on `/` and returns provider/model IDs without provider allowlisting (`src/memory-utils.ts:566-571`). The model/API layer remains responsible for authorization and secret handling.
- **Sub-agent inheritance is a deliberate data propagation choice.** Parent memory is copied into child-session files when enabled (`src/session-memory.ts:495-513`), and compaction also pushes memory unless injection is disabled (`src/session-memory.ts:663-672`). Projects with sensitive context should default this off or define a redaction policy.
- **Environment isolation in e2e is security-relevant.** The harness redirects XDG config/data homes and strips server auth variables before spawning a local server (`test/e2e/harness.ts:144-173`), while symlinking the real auth file into the temporary data home (`test/e2e/harness.ts:66-87`). This avoids copying credentials but still makes the test process dependent on the developer's auth file; a safer CI setup supplies isolated credentials or mocks provider access.
- **Identifier sanitization prevents filename traversal but is not a storage namespace.** Session IDs are reduced to alphanumerics plus `_`, `.`, and `-` (`src/memory-utils.ts:422-424`). Collisions are possible for distinct IDs that normalize to the same filename, so a derivative needing strong isolation should use a collision-resistant encoding.
- **Compaction can intentionally use stale memory.** If drain attempts time out, the plugin logs and pushes the on-disk value (`src/session-memory.ts:635-672`). This is a reasonable availability tradeoff, but downstream consumers should understand that compaction context is not guaranteed to include the newest turn.

## Testing lessons

- Unit tests use Bun, temporary directories, fake clients, and deterministic prompt responders (`test/test-helpers.ts:29-88`; `test/memory-lifecycle.test.ts:67-83`). This keeps filesystem and SDK behavior testable without network access.
- Tests target the failure modes that matter for stateful plugins: multi-chunk preservation and oversized entries (`test/memory-lifecycle.test.ts:85-165`, `test/memory-lifecycle.test.ts:167-213`), retry exhaustion/fallback (`test/memory-lifecycle.test.ts:250-300`), checkpoints and upstream limits (`test/message-collector.test.ts:120-208`), noise filtering (`test/message-collector.test.ts:210-235`), and integration cleanup/injection (`test/integration-memory.test.ts:106-156`).
- Live e2e tests are gated on `OPENCODE_E2E=1` and binary availability (`test/e2e/harness.ts:24-38`), use a fresh temp project and XDG homes (`test/e2e/harness.ts:52-97`), and assert observable artifacts such as memory files, logs, side-session state, and startup timing (`test/e2e/README.md:62-82`). This separation is a useful pattern for testing plugin wiring without making ordinary unit runs depend on a live OpenCode server.
- The pre-commit gate runs lint-staged formatting, typecheck, and isolated tests (`.husky/pre-commit:1-3`).
- Verification in this analysis was limited by the clone intentionally lacking `node_modules`. `bun test --isolate` ran 23 tests across 17 files: 7 passed; 16 files failed during import because `jsonc-parser` was unavailable. No dependency installation was performed.

## Packaging and release lessons

- The package publishes only `dist/`, README, license, and the example config (`package.json:23-39`), exports ESM plus declarations, and requires Bun >= 1.0 (`package.json:19-32`). Keeping tests/scripts out of the published file set is appropriate.
- The build uses `tsup` from `index.ts`, emits ESM/source maps, bundles local code, and externalizes OpenCode SDK/plugin packages plus `jsonc-parser` (`tsup.config.ts:1-14`). Declaration output is generated separately by the package build script (`package.json:40-52`). Release validation is wired into `prepublishOnly` through build, typecheck, and isolated tests (`package.json:42-48`).
- The changelog records a practical runtime portability fix: build scripts invoke Bun explicitly so the host Node runtime cannot break the Rollup toolchain (`CHANGELOG.md:19-24`). It also documents the SDK migration away from spawned `opencode` binaries and temporary directories (`CHANGELOG.md:26-36`), a useful reduction in shell/process and environment risks.
- The README clearly distinguishes the unofficial status, gives a single CLI installation command, documents project/global/env precedence, and exposes operational limits such as memory size, delta count, debounce, retries, and fallback (`README.md:5-42`).

## Bottom line

This is a strong reference implementation for a stateful OpenCode plugin: encapsulated factory state, defensive hook payload handling, incremental checkpoints, bounded prompts, atomic persistence, isolated side sessions, cleanup recovery, and artifact-oriented e2e tests. The main adoption cautions are debug-log data exposure, unrestricted configured storage paths, parent-memory propagation, possible normalized-ID collisions, and the unavoidable model-prompt injection surface. Its packaging is disciplined, but full test verification requires installing the declared dependencies, which was intentionally not done for this no-clone-edit analysis.
