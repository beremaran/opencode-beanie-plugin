## What It Does

`opencode-synced` synchronizes global OpenCode configuration through a GitHub repository, with
optional secrets, session, prompt-stash, and machine-override support (`README.md:1-13`). The
README makes the destructive link behavior explicit: linking overwrites local config while
preserving the local overrides file (`README.md:43-53`).

## OpenCode Integration Patterns

- Export a typed plugin function and aliases/default export so the package can be consumed under
  multiple conventional names (`src/index.ts:112-115`, `src/index.ts:308-309`).
- Use the SDK `tool` helper and `tool.schema` for a single strongly constrained command interface.
  The enum prevents arbitrary command dispatch, while optional typed arguments cover repository,
  secret, session, and path options (`src/index.ts:116-181`).
- Return user-facing command errors rather than throwing them through the tool boundary. Known
  `SyncConfigMissingError` and `SyncCommandError` instances become their messages, with unknown
  errors formatted safely (`src/index.ts:182-267`).
- Register dynamic markdown commands during the plugin `config` hook. The loader recursively scans
  the packaged `command` directory, parses a small frontmatter subset, and maps nested paths to
  hyphenated command names (`src/index.ts:25-49`, `src/index.ts:61-109`, `src/index.ts:283-294`).
- Defer startup work by one second so the TUI is connected, and forward all plugin events to the
  service event handler (`src/index.ts:271-282`). This is a pragmatic startup integration pattern,
  but the fixed delay is timing-sensitive and should remain observable/testable in similar plugins.
- Apply local overrides in the `config` hook, mutating the runtime config only after loading the
  override file; failures are intentionally swallowed to avoid preventing OpenCode startup
  (`src/index.ts:295-303`).

## Configuration And Data Modeling

- Normalize configuration at the boundary. Secrets and MCP secrets are coupled, sessions default
  to Git, Turso intervals are validated/floored, and skills, `.agents`, and model favorites are
  enabled by default (`src/sync/config.ts:140-192`). The tests encode these defaults and the
  security invariant that MCP secrets cannot be enabled without secrets (`src/sync/config.test.ts:62-110`).
- Use JSONC parsing/writing for user-facing config and preserve a separate state file for sync
  timestamps and hashes (`src/sync/config.ts:203-253`). Deep object merge with replacement
  semantics for arrays is simple and explicitly tested (`src/sync/config.ts:255-279`,
  `src/sync/config.test.ts:19-32`).
- Resolve XDG, Windows, and OpenCode-specific paths centrally, including `opencode_config_dir`
  and `~` expansion (`src/sync/paths.ts:63-123`). Cross-platform path tests cover Linux, Windows,
  and custom config roots (`src/sync/paths.test.ts:7-41`).
- Represent synchronization as a plan of typed items with local/repository paths and flags for
  secret/config behavior. This keeps policy decisions in `buildSyncPlan` and execution in the
  apply layer (`src/sync/paths.ts:22-46`, `src/sync/paths.ts:173-249`).
- Extra paths are explicit allowlists normalized to absolute paths and mapped to hashed, filesystem-
  safe repository names (`src/sync/paths.ts:346-367`). Default paths are filtered from extras and
  secret extras are disabled unless secrets are enabled (`src/sync/paths.ts:306-333`;
  `src/sync/paths.test.ts:43-107`).

## Security And Reliability Lessons

- Enforce private repositories before ordinary secret sync. The GitHub CLI visibility response is
  parsed and non-private repositories are rejected (`src/sync/repo.ts:68-96`). This is an important
  defense, but it depends on the user having a correctly authenticated `gh` CLI as documented
  (`README.md:15-18`).
- Scrub MCP headers and OAuth client secrets by moving values to local overrides and replacing
  them with `{env:...}` placeholders (`src/sync/mcp-secrets.ts:10-45`). Authorization schemes are
  preserved while only the credential is replaced (`src/sync/mcp-secrets.ts:74-90`), with focused
  tests for API keys, existing placeholders, Bearer auth, OAuth, and other schemes
  (`src/sync/mcp-secrets.test.ts:5-127`).
- Validate external secret-backend configuration before use: only 1Password is supported, vault
  and both document names are required, and names must be unique (`src/sync/secrets-backend.ts:38-52`,
  `src/sync/secrets-backend.ts:94-132`). 1Password CLI availability and malformed JSON responses
  receive contextual errors (`src/sync/secrets-backend.ts:173-219`).
- Refuse to enable a secrets backend if the repository already tracks auth files, requiring history
  cleanup first (`src/sync/service.ts:175-200`). This prevents a configuration change from creating
  a false sense of secret removal.
- Serialize sync operations with an atomic `open(..., 'wx')` lock, include PID/hostname/timestamp
  diagnostics, and reclaim locks whose PID is dead (`src/sync/lock.ts:48-89`). `withSyncLock` releases
  in `finally`, and tests cover acquisition, contention, and stale lock recovery (`src/sync/lock.ts:92-108`,
  `src/sync/lock.test.ts:9-77`). The stale-PID heuristic is inherently imperfect across PID reuse or
  host changes, so lock metadata should not be treated as an authorization mechanism.
- Detect Git divergence before applying remote state and require explicit rebase resolution rather
  than silently merging (`src/sync/repo.ts:98-133`). Git operations are shell-quoted through the
  Bun/SDK shell tag and errors are converted to contextual command errors (`src/sync/repo.ts:49-66`,
  `src/sync/repo.ts:147-161`).
- Preserve file modes during copies and treat SQLite WAL/SHM sidecars as a bundle
  (`src/sync/apply.ts:212-243`). Session artifacts use `preserveWhenMissing` so an absent local
  database does not delete remote history (`src/sync/paths.ts:271-289`); the behavior is covered by
  integration-style filesystem tests (`src/sync/apply.test.ts:40-212`).
- Turso credentials are stored outside the sync repository and snapshot payloads have an explicit
  8 MiB base64 limit (`src/sync/turso.ts:11-23`, `src/sync/turso.ts:196-220`). The install path is
  noteworthy security risk: setup embeds `curl ... | bash`, so auto-install should be opt-in or
  clearly trust-bound and ideally checksum/version pinned (`src/sync/turso.ts:11-16`).
- The README's removal one-liner can delete the configured GitHub repository and local state
  (`README.md:268-303`). It is useful operational documentation, but should be treated as a
  high-impact command requiring deliberate confirmation and careful parsing of config.

## Apply/Synchronization Design

- Pull copies planned items, then applies allowlisted extras and local overrides
  (`src/sync/apply.ts:45-59`). Push parses config files, extracts MCP secrets, persists new local
  overrides, strips override values, and writes manifests for extra paths (`src/sync/apply.ts:61-111`).
- Repository config writes are skipped when the local effective config already equals the repository
  config plus overrides, reducing needless commits (`src/sync/apply.ts:159-176`).
- Extra-path pull validates the recorded source path against the current normalized allowlist before
  copying, and resolves relative repository paths under the repository root
  (`src/sync/apply.ts:277-300`). This is a useful path-traversal boundary, though future changes
  should retain the same repository-root containment checks for every manifest-derived path.
- A sync state hash avoids repeated secret-backend pushes when auth files have not changed
  (`src/sync/service.ts:217-231`).

## Testing

- The project uses Vitest with an explicit `src/**/*.test.ts` include (`vitest.config.ts:1-7`) and
  separates build input from tests by excluding test files in `tsconfig.build.json:14-15`.
- Tests cover pure normalization/path/repository parsing, lock behavior, MCP secret transformation,
  filesystem copy behavior, secret-backend validation, and Turso response/size helpers. Examples
  include repository URL validation (`src/sync/repo.test.ts:16-67`), path-plan policy
  (`src/sync/paths.test.ts:220-260`), and Turso payload limits (`src/sync/turso.test.ts:129-151`).
- The README documents a two-instance GitHub E2E harness using an ephemeral private repository and
  isolated OpenCode instances (`README.md:317-367`). This is a strong complement to unit tests for
  a distributed sync plugin.
- Residual testing gap: the inspected unit tests do not exercise the complete exported plugin hook,
  delayed startup path, dynamic command loading, or all service orchestration branches. Those are
  the highest-value candidates for mock-client/plugin-contract tests and deterministic timer tests.

## Packaging And Release

- The package is ESM, exposes `dist/index.js` plus declarations, publishes only `dist`, and pins
  the OpenCode plugin SDK dependency (`package.json:1-28`).
- `build` removes `dist`, runs TypeScript declaration-producing compilation, then explicitly copies
  markdown commands into the distribution (`package.json:40-49`). The copy step is essential because
  command discovery is runtime filesystem-based; a packaging test should assert that `dist/command`
  contains the command files.
- `tsconfig.build.json` emits declarations and excludes tests, while source imports use `.js`
  specifiers compatible with ESM bundler resolution (`tsconfig.build.json:2-15`, `src/index.ts:1-10`).
- `prepack` rebuilds the artifact, and README documents packed-tarball local testing
  (`package.json:41-44`, `README.md:369-386`). This is a useful defense against source-tree-only
  success.
- Release automation uses release-please on pushes to `main`, updates a `latest` tag, and dispatches
  package publishing events (`.github/workflows/release.yml:1-60`). Repository permissions grant
  contents and pull-request writes (`.github/workflows/release.yml:8-14`); protected branch and token
  policy should be reviewed when adopting this pattern.

## Reusable Takeaways

1. Build an explicit, inspectable sync plan before performing filesystem mutations.
2. Normalize configuration once at the boundary and test security-dependent defaults.
3. Keep secrets out of synced config by converting them to environment placeholders plus local
   overrides, and separately verify repository visibility.
4. Make concurrent sync behavior explicit with an atomic lock, divergence detection, and safe stale
   lock handling.
5. Treat packaging as part of runtime correctness when plugins load markdown/assets from `dist`.
6. Pair unit tests with an isolated two-instance E2E flow for synchronization, conflict, and auth
   behavior.
