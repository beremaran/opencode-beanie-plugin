# Repository 021: boxpositron/envsitter-guard

## Scope and availability

- Manifest index 21 is `Envsitter Guard`, sourced from `https://github.com/boxpositron/envsitter-guard` (`manifest.json:183-187`). The available clone is `.research/opencode-plugin-corpus/repos/boxpositron--envsitter-guard`; it was inspected without modification.
- The repository is an OpenCode-only TypeScript plugin. Its main implementation is `index.ts`; the only OpenCode registration file is `.opencode/plugin/envsitter-guard.ts`. No separate `manifest/` directory or manifest file was present in the clone. The `.opencode/` subdirectory is the relevant runtime/registration surface.
- The README describes the security goal as blocking direct `.env*` access while exposing key, fingerprint, shape, matching, validation, and mutation operations that do not return raw values (`README.md:1-3`, `README.md:41-89`).

## SDK and registration

- The package uses `@opencode-ai/plugin` types and the `tool` helper, and exports `EnvSitterGuard` as both a named and default export (`index.ts:1-2`, `index.ts:123-124`, `index.ts:916`). This is a conventional async plugin factory receiving `directory` and `worktree` context.
- The package loader entrypoint is `dist/index.js`, with declarations and ESM exports declared in `package.json` (`package.json:20-32`). The source plugin is compiled from `index.ts` by `tsconfig.build.json` (`tsconfig.build.json:2-10`).
- The project-level registration wrapper is intentionally minimal: it imports the implementation and re-exports it as default and named export (`.opencode/plugin/envsitter-guard.ts:1-4`). This keeps deployment wiring separate from plugin logic.
- The README gives both npm configuration (`plugin: ["envsitter-guard@latest"]`) and local/global `.opencode/plugin` installation paths (`README.md:13-26`, `README.md:318-347`). The local example also requires an `.opencode/package.json` dependency declaration (`README.md:320-341`), but no such package file exists in this clone; it is user installation guidance rather than a committed manifest.

## Hooks and tools

- The plugin registers fourteen tools under `tool`: key listing, fingerprints, matching, bulk matching, scanning, validation, copy, formatting/reordering, annotation, add/set/unset/delete mutations, and help (`index.ts:138-184`, `index.ts:273-380`, `index.ts:381-512`, `index.ts:512-889`). Tool schemas constrain enum operations, detection types, and write flags at the boundary.
- Every file-oriented tool routes through `resolveDotEnvPath`, which normalizes separators, rejects `.envsitter/pepper`, accepts only `.env`-style paths (with an exact `.env.example` exception), resolves relative to `directory`, and checks the lexical result remains under `worktree` (`index.ts:16-38`, `index.ts:99-121`). This is a reusable pattern: validate the user-supplied path before invoking the library and return a project-relative display path.
- Mutation and file-operation tools are dry-run by default and pass `write: args.write === true` to `envsitter`; outputs are explicitly assembled from status, issue, plan, key, and line-oriented fields rather than file contents (`index.ts:381-435`, `index.ts:438-473`, `index.ts:555-700`). The README makes the same behavior visible to agents (`README.md:73-76`).
- The `tool.execute.before` hook blocks standard `read` for sensitive `.env*` paths and blocks `edit`, `write`, `patch`, and `multiedit`; errors point to the safe EnvSitter alternatives (`index.ts:891-912`). `.env.example` remains readable because the sensitive-path predicate excludes it (`index.ts:20-28`).
- The help tool embeds a structured, topic-selectable guide inside the plugin and reiterates that only keys, booleans, line numbers, and plans are returned (`index.ts:703-887`). This is useful for agent-facing plugins: the safe workflow is discoverable without requiring a separate document lookup.

## Security lessons and pitfalls

- Strong design lesson: treat secret non-disclosure as an output contract, not merely a prompt convention. The implementation uses EnvSitter APIs and manually serializes safe result fields (`index.ts:153-163`, `index.ts:336-339`, `index.ts:377-379`); the README explicitly warns that accidental `.env` output can reach transcripts, logs, commits, and screenshots (`README.md:28-39`).
- Candidate values can still enter the process through explicit arguments, environment variables, or JSON, but matching results are booleans only. Candidate environment variables are resolved without returning their values (`index.ts:77-87`, `index.ts:288-339`). This is a useful outside-in comparison pattern for secret verification.
- Path handling normalizes Windows separators before matching and strips a leading `@` from tool paths (`index.ts:16-18`, `index.ts:40-42`, `index.ts:89-97`). The hook and tool paths therefore share a predictable cross-platform policy.
- Security caveat: the worktree boundary check uses `path.resolve` and `path.relative` but does not call `realpath`; a symlink inside `worktree` could potentially resolve to an external file while still passing the lexical containment test (`index.ts:114-120`). A production hardening step would resolve existing path components and enforce containment on canonical paths, especially before write operations.
- Security caveat: the hook extracts only `filePath`, `path`, and `file_path` from generic tool arguments (`index.ts:89-97`). It does not inspect generic `from`/`to` fields, so protection of multi-file operations depends on the dedicated EnvSitter tools using `resolveDotEnvPath` (`index.ts:394-405`). This should be verified against the exact argument shape of every OpenCode built-in that can read or write files.
- The hook blocks by throwing and deliberately produces no toast. The test asserts two blocked calls result in zero toast calls (`test/envsitter-guard.hook.test.ts:108-116`), and the changelog records the silent behavior as an intentional change (`CHANGELOG.md:13-17`). Silent blocking avoids prompt/UI pollution, but actionable errors are consequently the primary UX channel.
- The `.gitignore` protects local `.env*` files while allowing `.env.example`, and excludes build output (`.gitignore:1-12`). This is an important packaging baseline, but it does not itself protect `.envsitter/pepper`; runtime blocking covers that path (`index.ts:35-38`, `index.ts:106-108`).

## Testing and verification

- Tests use Node’s built-in test runner after TypeScript compilation (`package.json:38-45`; `.husky/pre-commit:1-5`). The compiler is strict, uses NodeNext ESM, and separates no-emit typechecking, publish builds, and test builds (`tsconfig.json:2-12`, `tsconfig.build.json:2-10`, `tsconfig.test.json:2-10`).
- Hook tests cover blocking `.env`, allowing `.env.example`, blocking edits and pepper, stripping `@`, and silent behavior (`test/envsitter-guard.hook.test.ts:61-116`).
- Tool tests cover redaction for keys, fingerprints, matching, bulk matching, scanning, validation, copy dry-run/write behavior, formatting, annotation, and rejection of outside-worktree and pepper paths (`test/envsitter-guard.tools.test.ts:141-394`). The tests assert both returned output and resulting file contents where mutation is expected, which is stronger than snapshotting tool strings alone.
- Coverage gap: the tool test file defines the API type only through `envsitter_annotate` (`test/envsitter-guard.tools.test.ts:24-87`) and has no direct tests for `envsitter_add`, `envsitter_set`, `envsitter_unset`, `envsitter_delete`, `envsitter_help`, or `envsitter_reorder`, despite those tools being registered (`index.ts:475-510`, `index.ts:555-889`). Add tests for their dry-run defaults, writes, redaction, and validation failures.
- Coverage gap: tests do not exercise symlink escapes, Windows-style traversal, malformed regex literals/flags, duplicate selector inputs, or hook handling of `path` and `file_path` aliases. These are high-value cases because they exercise the custom validation code (`index.ts:44-75`, `index.ts:89-120`, `index.ts:244-248`).
- No test command was run for this corpus review; findings above are based on the checked-in source and test cases. The clone was clean before report generation (`git status --short` produced no output).

## Packaging and dependency lessons

- `package.json` publishes only `dist/`, `README.md`, and `LICENSE`, exposes both ESM runtime and declarations, and runs typecheck/tests before publication (`package.json:25-45`). `prepack` builds, while `prepublishOnly` repeats typecheck, tests, and build, giving npm publication a useful local gate.
- Runtime dependencies are intentionally small: `@opencode-ai/plugin` and `envsitter`; TypeScript, Node types, and Husky are development dependencies (`package.json:46-53`). The lockfile pins resolved package integrity data (`package-lock.json:21-54`), supporting reproducible installs.
- Packaging pitfall: `package.json` declares version `0.0.4`, while the root lockfile metadata still says `0.0.3` (`package.json:2-3`; `package-lock.json:1-13`). The resolved `envsitter` dependency is already `0.0.4` (`package-lock.json:47-50`), but the root version mismatch can confuse release checks and should be synchronized before publishing.
- The repository uses a thin `.opencode/plugin` wrapper but publishes the root package entrypoint. Consumers installing from npm should use the package plugin declaration; consumers using a local wrapper must ensure OpenCode can install the package dependency as documented (`README.md:13-26`, `README.md:320-341`).

## Reusable OpenCode patterns

- Keep plugin registration as a small wrapper and export a typed async factory from the package root (`.opencode/plugin/envsitter-guard.ts:1-4`; `index.ts:123-138`).
- Centralize untrusted tool-path validation before all library calls; return relative, structured JSON and avoid passing raw secret-bearing objects through tool output (`index.ts:99-121`, `index.ts:162-181`).
- Prefer dry-run mutation APIs with an explicit opt-in `write: true`, and return a plan so an agent can inspect intended changes before applying them (`index.ts:411-435`, `README.md:201-217`).
- Test security properties directly: assert sensitive values are absent from output, assert filesystem effects only occur with explicit writes, and assert hook rejection messages are actionable (`test/envsitter-guard.tools.test.ts:171-186`, `test/envsitter-guard.tools.test.ts:333-380`, `test/envsitter-guard.hook.test.ts:61-105`).
- Keep typecheck, compiled tests, and publish build as separate scripts, then run all required checks from the pre-publish lifecycle (`package.json:38-45`).
