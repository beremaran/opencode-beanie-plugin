## OpenCode Patterns

### Boundary tools and validation

- The workspace plugin registers typed tools through `tool()` and validates plan content at the boundary with Zod schemas (`src/plugin/workspace-plugin.ts:L4-L5`, `src/plugin/workspace-plugin.ts:L12-L50`). It separates markdown extraction from validation, returns a discriminated `ParseResult`, and formats all Zod issues with paths (`src/plugin/workspace-plugin.ts:L53-L59`, `src/plugin/workspace-plugin.ts:L82-L147`, `src/plugin/workspace-plugin.ts:L149-L172`).
- `plan_save` requires a session, resolves the root session, creates a session-scoped storage directory, validates the full markdown plan, and writes `plan.md` only after validation (`src/plugin/workspace-plugin.ts:L548-L577`). `plan_read` treats ENOENT as the normal “No plan found” state while rethrowing other errors (`src/plugin/workspace-plugin.ts:L580-L600`).
- The plan schema encodes useful invariants: hierarchical task IDs, non-empty task content, one current task, ISO date formatting, valid phase status, and at least one task per phase (`src/plugin/workspace-plugin.ts:L12-L50`). Business validation rejects multiple current tasks and warns about multiple in-progress phases (`src/plugin/workspace-plugin.ts:L227-L251`).

### Session-scoped persistence and compaction recovery

- Workspace data is keyed by project ID and root session ID under `~/.local/share/opencode/workspace/<project>/<root-session>` (`src/plugin/workspace-plugin.ts:L515-L520`, `src/plugin/workspace-plugin.ts:L560-L572`). Root-session lookup is bounded to ten parent traversals, preventing an accidental cycle from becoming an infinite loop (`src/plugin/workspace-plugin.ts:L523-L544`).
- The system hook injects date awareness for all agents and targeted routing/delegation rules only for `plan` and `build` agents (`src/plugin/workspace-plugin.ts:L604-L620`). The compaction hook reloads the saved plan and extracts the current task into resumed context (`src/plugin/workspace-plugin.ts:L667-L702`). This is a strong OpenCode pattern for making state survive context compaction rather than relying on prompt history.
- The background delegation manager persists result artifacts as markdown, records status/timestamps/notification/retrieval metadata, and exposes deterministic read/list behavior (`src/plugin/background-agents.ts:L201-L233`, `src/plugin/background-agents.ts:L1262-L1300`, `src/plugin/background-agents.ts:L1303-L1373`). It uses readable IDs, bounded timeouts, terminal waiters, and a fallback summary when persistence is delayed (`src/plugin/background-agents.ts:L25-L31`, `src/plugin/background-agents.ts:L235-L239`, `src/plugin/background-agents.ts:L863-L883`).
- Delegation checks that the target agent exists and is read-only before creating a child session; write-capable agents are explicitly routed to native `task` for undo/branching support (`src/plugin/background-agents.ts:L1070-L1099`). Nested state-modifying tools are disabled in the child prompt (`src/plugin/background-agents.ts:L1139-L1155`).

### Worktree isolation

- The worktree plugin exposes `worktree_create` and `worktree_delete` tools and stores lifecycle state in SQLite with WAL mode and a five-second busy timeout (`src/plugin/worktree.ts:L1006-L1013`, `src/plugin/worktree/state.ts:L143-L187`). State rows are schema-checked with Zod and SQL uses bound parameters (`src/plugin/worktree/state.ts:L55-L77`, `src/plugin/worktree/state.ts:L261-L284`).
- Worktree creation forks the OpenCode session, copies the root plan and delegation artifacts, launches a terminal with the forked session, and removes the forked session if terminal launch fails (`src/plugin/worktree.ts:L404-L513`, `src/plugin/worktree.ts:L1086-L1136`). This gives a concrete pattern for preserving agent context across isolated git worktrees.
- Pending deletion is deferred until `session.idle`; pre-delete hooks run, changes are staged and committed as a snapshot, the worktree is removed, and state is cleared (`src/plugin/worktree.ts:L1163-L1198`). This is convenient but materially changes repository history and should be an explicit product choice.

## Security Lessons and Pitfalls

### Positive controls

- Git commands use `Bun.spawn(["git", ...args])`, never shell interpolation (`src/plugin/worktree.ts:L605-L627`). Branch names are validated against option injection, traversal/ref syntax, control characters, shell metacharacters, `..`, leading/trailing dots, and `.lock` (`src/plugin/worktree.ts:L83-L123`).
- File synchronization rejects absolute paths and traversal, resolves source paths through realpath checks, rejects symlinked target parents/files, and verifies the destination remains inside the worktree (`src/plugin/worktree.ts:L672-L721`, `src/plugin/worktree.ts:L723-L771`, `src/plugin/worktree.ts:L778-L823`). These checks are a useful defense-in-depth pattern for user-configured copy/symlink lists.
- Terminal argv is escaped per target shell, null bytes are rejected, and detached temporary scripts self-delete (`src/plugin/kdco-primitives/shell.ts:L11-L42`, `src/plugin/kdco-primitives/shell.ts:L45-L78`, `src/plugin/worktree/terminal.ts:L78-L97`). The terminal implementation also documents why detached processes must not use a `finally`-deleted temporary script (`src/plugin/worktree/terminal.ts:L616-L618`).
- Launch metadata is parsed and required fields are enforced before an OCX executable/profile is reused; executable paths are resolved and checked for existence and execute permission (`src/plugin/worktree/launch-context.ts:L36-L59`, `src/plugin/worktree.ts:L220-L253`).

### Risks and failure modes

- Configured worktree hooks are arbitrary shell strings executed with `bash -c`; the README-generated config explicitly demonstrates commands such as `pnpm install` and `docker compose up -d` (`src/plugin/worktree.ts:L878-L897`, `src/plugin/worktree.ts:L921-L952`). This is acceptable only as an explicitly trusted local-project feature. It must not be treated as safe for untrusted repository configuration, and hook output includes the full command in logs.
- Notification configuration is parsed with `JSON.parse` and then shallowly merged without schema validation, so malformed types can flow into runtime behavior while invalid JSON silently falls back to defaults (`src/plugin/notify.ts:L107-L130`). The same file imports `./notify/status` and `./notify/title`, but those files are not present in the clone’s tracked tree; therefore this facade cannot be compiled as-is from the checked-in sources (`src/plugin/notify.ts:L40-L45`; `git ls-tree -r --name-only HEAD`).
- `isPathSafe` rejects any path containing `..`, which is conservative but also rejects legitimate filenames such as `foo..bar` (`src/plugin/worktree.ts:L672-L692`). A more precise component-based traversal check would reduce false positives while retaining containment checks.
- Worktree deletion automatically runs `git add -A` and commits all changes, including potentially sensitive files copied or generated in the worktree (`src/plugin/worktree.ts:L1177-L1185`). The feature should document this clearly and consider an allowlist or confirmation policy for production use.
- Delegation fallback reads persisted markdown by interpolating an ID into a path. IDs are generated internally and normalized, but a persisted artifact lookup should still constrain IDs to a safe filename grammar before filesystem access (`src/plugin/background-agents.ts:L1306-L1322`, `src/plugin/background-agents.ts:L1478-L1486`).

## Testing and Verification Lessons

- No tests, test runner configuration, package manifest, or CI configuration are present in this clone. Although `worktree.ts` exposes selected helpers through `testInternals`, there is no checked-in test harness consuming them (`src/plugin/worktree.ts:L1203-L1215`). The facade therefore provides no repository-local evidence for runtime behavior, cross-platform terminal launching, path containment, schema validation, or cleanup.
- The source does make several behaviors testable by dependency injection: terminal launch functions, executable resolution, path existence, profile validation, and cleanup callbacks are injectable (`src/plugin/worktree.ts:L169-L178`, `src/plugin/worktree.ts:L352-L370`). This should be paired with tests for invalid branch names, symlink escapes, launch failures, fork cleanup, profile drift, and timeout races.
- Recommended minimum verification for a complete upstream package: compile each plugin entrypoint with the OCX-resolved dependencies; test `parsePlanMarkdown` and branch/path schemas; test SQLite migration and pending-operation replacement; test detached-script cleanup; test shell escaping on Bash, Batch, and AppleScript; and run integration tests for session fork/notification/compaction flows.

## Packaging and Maintenance Lessons

- Treat this repository as a generated/synced facade, not the source of truth. The README explicitly points maintainers to OCX monorepo files and says not to open issues or pull requests in the facade (`README.md:L111-L122`). A release pipeline must therefore verify synchronization and include all runtime-only dependencies from the upstream registry payload.
- The README claims four plugins, npm plugins, MCP servers, and orchestrator configuration, but those assembled components are not represented by a local manifest in this clone (`README.md:L24-L33`, `README.md:L62-L82`). Consumers need an OCX registry/profile layer to obtain the complete bundle; cloning this repository alone is insufficient.
- The duplicated `src/skill/` and `src/skills/` trees increase ambiguity and drift risk. Packaging should define one canonical source directory and make any generated mirror explicit, with a consistency check in CI.
- The README’s quick start is clear and operational, and it includes a direct-install fallback and ownership model (`README.md:L5-L20`, `README.md:L99-L109`). It should additionally state the required OCX version, runtime/dependency requirements, supported platforms, and how to verify that a profile contains all declared components.

## Reusable Takeaways

1. Use typed OpenCode tools with boundary schemas, discriminated results, actionable errors, and session-aware storage.
2. Persist long-running delegation output as addressable artifacts and send compact notifications containing stable retrieval IDs.
3. Disable recursive/state-modifying tools in delegated child sessions and enforce read-only versus write-capable agent routing.
4. For worktree features, combine argv-based process spawning, strict branch validation, realpath containment checks, SQLite WAL state, bounded retries, and cleanup on partial failure.
5. Keep generated registry facades visibly separate from authoritative source repositories, and do not imply that a source-only clone is independently installable.
6. Do not ship arbitrary shell hooks or automatic snapshot commits without prominent trust and data-loss/security documentation.
