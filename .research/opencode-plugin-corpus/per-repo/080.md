## What it does

This is a Bun/TypeScript OpenCode plugin that starts a local WebSocket and static-file server, registers each OpenCode process as an office character, and forwards selected OpenCode lifecycle/tool events to a browser canvas. The README describes the intended user experience as a real-time multi-agent pixel-art office and says that each project can persist a selected skin in `.opencode/viz-skin.json` (`README.md:28-35`, `README.md:118-123`).

The plugin export receives the OpenCode plugin context, initializes a project-local debug log and skin, starts the server, and retries the WebSocket connection up to 20 times (`index.ts:131-152`). It returns one generic event hook plus `tool.execute.before` and `tool.execute.after` hooks (`index.ts:166-180`). The generic hook deliberately filters events to a small allowlist before forwarding them (`index.ts:155-170`).

## OpenCode patterns worth reusing

### Small event adapter

The event bridge is intentionally narrow: `interestingEvents` includes session creation/status/deletion/idle/error/diff, message updates, and todo updates, while tool hooks forward only the tool name (`index.ts:155-180`). This is a useful pattern for UI/telemetry plugins: avoid serializing every event and define a stable, product-specific projection at the plugin boundary.

The event payload is sent as a JSON envelope containing a generated instance ID, event type, and properties (`index.ts:118-126`). This gives the frontend enough information to multiplex several OpenCode processes without coupling it to process-local state.

### In-process auxiliary service

The server is exported as `startServer()` and can also run standalone when `import.meta.main` is true (`visualizer/ocv-server.ts:98-104`, `visualizer/ocv-server.ts:190-202`). This is a practical reuse pattern for a plugin that wants a normal OpenCode installation path while retaining a separately runnable debugging/development path.

The server tracks plugin clients in a map and browser clients in a set, broadcasts only to open browser sockets, and removes clients on WebSocket close (`visualizer/ocv-server.ts:21-31`, `visualizer/ocv-server.ts:163-178`). It also sends a complete instance snapshot when a browser registers (`visualizer/ocv-server.ts:147-155`), which makes browser reconnects recoverable rather than dependent on replaying all prior events.

### Graceful lifecycle behavior

When the final plugin/browser client disappears, the server waits five minutes before stopping; in standalone mode it then exits, while an in-process server only clears its reference (`visualizer/ocv-server.ts:80-96`). The plugin clients use randomized reconnect jitter and attempt to become the new port leader after a server disconnect (`index.ts:94-110`). This demonstrates a simple, dependency-free failover strategy for multiple plugin instances.

### Static asset packaging

The browser UI is a single `visualizer/index.html` with an inline canvas application. It preloads all configured animation frames and the three texture files in parallel before opening the WebSocket and starting the render loop (`visualizer/index.html:128-173`, `visualizer/index.html:873-880`). The server maps `/` to `index.html` and serves files from the colocated visualizer directory (`visualizer/ocv-server.ts:106-123`). Keeping the frontend and its assets under one package directory avoids a separate web build/runtime dependency.

## Pitfalls and security lessons

### Localhost is a trust boundary, not authentication

The server binds to `127.0.0.1` (`visualizer/ocv-server.ts:100-105`), and the plugin connects to `ws://localhost:5173` (`index.ts:60-63`). That limits ordinary network exposure, but there is no authentication, origin check, schema validation, or authorization in the WebSocket protocol. Any local process able to reach the port can send `register`, `frontend.register`, or `event` messages; the server accepts and broadcasts them (`visualizer/ocv-server.ts:125-161`). For a visualizer this may be an acceptable explicit local-only tradeoff, but a plugin handling sensitive events should use an unguessable capability/token and validate message origins and shapes.

The server trusts client-provided `instanceId`, `cwd`, and `skin` values and stores/broadcasts them without validation (`visualizer/ocv-server.ts:132-142`). The browser then uses the supplied working-directory string as a visible label (`visualizer/index.html:692-719`). This is not a remote code execution path in the shown code, but it is an integrity/privacy issue for local co-resident processes: arbitrary labels and fake agent events can be injected, and project paths can be disclosed to every connected browser.

The static-file handler constructs a path from the request pathname and checks existence before serving it (`visualizer/ocv-server.ts:109-117`). It does not visibly enforce that the normalized result remains below `VISUALIZER_DIR`. The handler should canonicalize and containment-check decoded paths before serving package files, especially if the service ever binds beyond loopback or the browser protocol is exposed through a proxy.

### Reconnect races and failure ambiguity

On connection timeout/error, `connectToServer()` closes the socket and rejects (`index.ts:60-92`), while the socket's `onclose` independently schedules a delayed leader-election reconnect (`index.ts:94-110`). The startup loop also retries every 300 ms for up to 20 attempts (`index.ts:137-149`). These two retry mechanisms can overlap and create multiple sockets or excess reconnect traffic during a server outage. A single owned reconnect state machine would make cancellation and connection ownership easier to reason about.

`tryStartServer()` treats every failed `startServer()` call as the normal “another instance is leader” case in its log (`index.ts:22-34`). The server similarly catches all bind/start errors and returns `false` (`visualizer/ocv-server.ts:180-187`). This masks permission, malformed runtime, and other startup failures as port contention. Error classification would improve diagnostics and prevent clients from repeatedly trying a fundamentally broken setup.

The browser assumes that an `instance.event` message contains an object with a readable `type` (`visualizer/index.html:787-851`), while the server forwards `data.event` without validating it (`visualizer/ocv-server.ts:157-159`). A malformed local message can therefore throw in the browser message handler. Validate envelopes and event types at the server and frontend boundaries.

### Operational side effects and data persistence

Plugin startup creates `.opencode/ocv-debug.log` and appends timestamped connection/server messages (`index.ts:10-20`, `index.ts:131-146`). It also creates or reads `.opencode/viz-skin.json` and silently ignores filesystem/JSON errors (`index.ts:41-53`). This is convenient and resilient, but the debug log and project path labels should be treated as potentially sensitive. The README should ideally document retention and cleanup, and the implementation should consider bounded log rotation or an opt-in debug mode.

The plugin automatically launches a browser through platform-specific commands, including `open`, `cmd.exe /c start`, `google-chrome`, and `xdg-open` (`visualizer/ocv-server.ts:46-77`). Arguments are passed as arrays to `Bun.spawn`, which avoids shell interpolation for the URL, but browser availability and OS command behavior remain external runtime dependencies. Launch failures are logged and the user is told to open the URL manually (`visualizer/ocv-server.ts:59-75`).

## Testing and verification lessons

- No test files, test script, CI workflow, or build script are present in the inspected clone. `package.json` contains metadata, exports, runtime dependency, and dev dependencies only (`package.json:1-29`); the only `.github` file is a funding template (`.github/FUNDING.yml:1-15`).
- The most important untested behavior is the protocol/lifecycle state machine: registration, snapshot synchronization, duplicate IDs, close cleanup, leader takeover, five-minute shutdown, and reconnect races (`visualizer/ocv-server.ts:125-178`, `index.ts:94-110`). These should be covered with an injected port/server clock and WebSocket test doubles.
- Event mapping needs contract tests for every allowlisted OpenCode event and both tool hooks, including missing or unexpected `properties` (`index.ts:155-180`).
- Browser logic is a large inline script with no unit or browser tests. Useful deterministic tests would cover max-five agent handling, desk/coffee reservation release, path transitions, malformed WebSocket messages, and missing animation assets (`visualizer/index.html:235-264`, `visualizer/index.html:294-309`, `visualizer/index.html:761-870`).
- A smoke test should start the static server, request `/`, verify the asset paths, register a plugin client, register a frontend client, assert `state.sync`, and verify cleanup on close. This would catch packaging/server regressions without requiring a real Chrome window.

## Configuration and packaging

The repository's development config points OpenCode at the local entrypoint (`opencode.json:1-6`). The README documents both npm installation and a local source configuration (`README.md:39-82`). The package declares `index.ts` as its main entry, exposes `./server` as `./index.ts`, exposes `./tui` as `./tui.ts`, and includes `index.ts`, `tui.ts`, and the entire `visualizer/` directory in the published file set (`package.json:3-14`).

The `./server` export is a packaging smell: it points to the plugin entry (`index.ts`), not to `visualizer/ocv-server.ts`, even though that file contains the actual `startServer` export (`package.json:5-8`, `visualizer/ocv-server.ts:100-104`). Consumers expecting `psinetron-opencode-visualizer/server` to expose the server will receive the plugin module instead. Either remove the misleading export or point it at an intentional public server entry.

The package relies on Bun globals (`Bun.serve`, `Bun.spawn`, `Bun.file`) and the platform WebSocket implementation (`visualizer/ocv-server.ts:35-36`, `visualizer/ocv-server.ts:103-125`), while declaring only `@opencode-ai/plugin` as a runtime dependency (`package.json:18-23`). That is appropriate for OpenCode's bundled Bun runtime as documented by the README (`README.md:39-41`), but should be stated as a hard runtime requirement for consumers importing the package outside OpenCode.

The README gives useful installation, local-development, update/cache-clearing, and manual URL fallback instructions (`README.md:43-114`). It also accurately points users to the project-local skin file (`README.md:118-123`). The update instructions recommend deleting cache directories with `rm -rf` or PowerShell `Remove-Item -Recurse -Force` (`README.md:92-114`); those are operationally effective but destructive, so a safer diagnostic step would first print/verify the exact package path.

## Bottom line

The strongest pattern is a small OpenCode event projection feeding a reconnectable, snapshot-capable local UI service, with no frontend build dependency. The main production gaps are protocol trust and validation, reconnect-state ownership, static-path containment, misleading package exports, and the complete absence of automated tests/CI. Its localhost-only binding reduces exposure, but should be documented as a security assumption rather than treated as authentication.
