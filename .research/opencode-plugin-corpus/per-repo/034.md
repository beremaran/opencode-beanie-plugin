## OpenCode Patterns

- **Thin repo-local shim over a publishable package.** The checked-in OpenCode plugin files only re-export the built package entrypoints (`.opencode/plugins/kibi.ts:1-2`, `.opencode/plugins/kibi.tui.ts:1`). The package declares `dist/index.js` as its main entry, publishes only `dist`, and exposes separate `config`, `prompt`, `scheduler`, `file-filter`, and `tui` subpaths (`packages/opencode/package.json:2-40`). This keeps dogfooding wiring small while making the npm package the reusable integration boundary.
- **OpenCode hook surface is explicitly typed and capability-aware.** The adapter models `event`, `config`, `experimental.chat.system.transform`, and `chat.params` hooks (`packages/opencode/src/plugin.ts:142-152`). It registers the config hook only when the host capability is supported (`packages/opencode/src/plugin.ts:264-271`), and keeps `chat.params` as a deliberate no-op because that hook exposes model options rather than prompt text (`packages/opencode/src/plugin.ts:1504-1515`).
- **Prompt injection is idempotent and contextual.** The system-transform hook skips injection when a sentinel is already present, derives focus-file/worktree/session state, and builds guidance from recent edits, risk, posture, and KB freshness (`packages/opencode/src/plugin.ts:1054-1128`). This is a useful pattern for avoiding duplicate system content while still using the host's transform hook for dynamic context.
- **Events drive bounded background maintenance.** The event hook recognizes several tool-completion spellings for best-effort KB evidence, then handles `file.created`, `file.edited`, and `file.deleted` lifecycle events separately (`packages/opencode/src/plugin.ts:580-627`). Relevant file events are filtered and sent to a scheduler (`packages/opencode/src/plugin.ts:675-710`); the scheduler debounces triggers, prevents overlapping runs, and preserves one trailing rerun when edits arrive during an active sync (`packages/opencode/src/scheduler.ts:101-125`, `packages/opencode/src/scheduler.ts:186-198`).
- **Worktree state is a first-class scope.** Startup resolves branch from `KIBI_BRANCH` before falling back to Git, normalizes `master` to `main`, fingerprints `.kb/config.json`, and invalidates guidance caches when branch, posture, or configuration changes (`packages/opencode/src/plugin-startup.ts:67-93`, `packages/opencode/src/plugin-startup.ts:129-153`). Scheduler tests explicitly verify that parallel worktrees flush only their own work (`packages/opencode/tests/scheduler.test.ts:70-126`).
- **Enforcement degrades rather than pretending maintenance succeeded.** Startup latches causes such as sync disabled, scheduler failure, failed checks, or non-authoritative posture (`packages/opencode/src/plugin-startup.ts:155-205`, `packages/opencode/src/plugin-startup.ts:245-269`). Effective mode makes maintenance-degraded strict mode advisory, while hard mode is allowed only for authoritative root-KB postures (`packages/opencode/src/smart-enforcement.ts:43-53`, `packages/opencode/src/smart-enforcement.ts:70-92`).

## Security Lessons and Pitfalls

- **Do not treat prompt guidance as the enforcement boundary.** The README distinguishes advisory, strict, and hard modes and states that Git hooks and KB checks remain the durable boundary (`packages/opencode/README.md:49-62`). Consumers should retain an actual validation or hook gate for security- or integrity-sensitive behavior; injected instructions alone are not sufficient.
- **Hard-mode posture checks are a useful fail-closed pattern, but configuration matters.** Strict eligibility is limited to `root_active` and `hybrid_root_plus_vendored` when required, and maintenance degradation disables strict mode (`packages/opencode/src/smart-enforcement.ts:31-53`). The checked-in example opts into `mode: "hard"` (`.opencode/kibi.json:35-42`), so deploying this configuration outside an initialized authoritative workspace can silently fall back to advisory behavior rather than enforce.
- **MCP startup executes a shell command derived from the repository root.** The example OpenCode config invokes `sh -lc`, runs `git rev-parse --show-toplevel`, and then executes a repository-local Bun script (`opencode.json:4-13`). This is convenient for repo-local resolution, but shell startup expands the command surface and assumes a trusted Git checkout; a packaged configuration should prefer direct argv execution where the host permits it and should validate the resolved root.
- **Automatic updating is an integrity-sensitive feature.** The plugin checks npm, invalidates cached package directories and lockfiles, then runs `bun install` in an OpenCode cache/config workspace (`packages/opencode/src/auto-update.ts:406-455`, `packages/opencode/src/auto-update.ts:466-531`). Exact semver pins skip replacement, while unpinned entries can be installed automatically (`packages/opencode/src/auto-update.ts:507-525`). This should be opt-out or tightly pinned in controlled environments; the package documentation explicitly says the default updater checks npm on startup (`packages/opencode/README.md:25-40`).
- **Config validation is type-aware but not range-aware.** The loader accepts any number for debounce, TTL, reset, toast cooldown, and comment minimum-line settings (`packages/opencode/src/config.ts:138-157`, `packages/opencode/src/config.ts:170-218`). Negative or extreme values can create surprising scheduling or UX behavior. Add finite, non-negative bounds if configuration is operator- or repository-controlled.
- **Tool evidence and event processing intentionally fail open.** KB tool evidence is recorded best-effort and exceptions are swallowed so the event handler cannot crash (`packages/opencode/src/plugin.ts:599-619`). That is good availability behavior, but it means freshness evidence can be missing without stopping work; hard assurance must come from the later checkpoint/check boundary.
- **Local KB data and broad filesystem reads require a clear trust model.** The README says state remains in the repository `.kb/` directory and no external telemetry is sent (`README.md:16-24`), while the plugin reads files relative to the worktree to classify requirements and comments (`packages/opencode/src/plugin.ts:163-208`, `packages/opencode/src/plugin.ts:712-723`). Keep worktree roots constrained and avoid assuming that local files are non-sensitive merely because they are not uploaded.

## Testing Lessons

- **Test host-facing contracts, not just pure helpers.** The hook contract test invokes the actual plugin, runs system transformation, and asserts the required MCP/CLI safety guidance plus absence of obsolete briefing behavior (`packages/opencode/tests/hook-contract.test.ts:7-35`). The index tests similarly exercise event and transform hooks with temporary worktrees and clean them up (`packages/opencode/tests/plugin-index.test.ts:9-32`, `packages/opencode/tests/plugin-index.test.ts:34-57`).
- **Use deterministic clocks and injected runners for asynchronous hooks.** Scheduler tests inject fake timeouts, a fake clock, and `runSync`, then verify debounce and isolated worktree behavior (`packages/opencode/tests/scheduler.test.ts:15-49`, `packages/opencode/tests/scheduler.test.ts:128-159`). The scheduler API also exposes injectable sync/check runners and timers (`packages/opencode/src/scheduler.ts:44-54`), making race-prone behavior testable without sleeping or invoking real maintenance.
- **Cover the enforcement decision matrix exhaustively.** Smart-enforcement tests enumerate all repository postures and verify degraded, advisory, strict, and hard transitions (`packages/opencode/tests/smart-enforcement.test.ts:15-30`, `packages/opencode/tests/smart-enforcement.test.ts:37-133`, `packages/opencode/tests/smart-enforcement.test.ts:140-219`). This is a strong model for testing policy code as a table rather than relying on a few example cases.
- **Isolate environment and restore mocks.** Configuration tests replace `HOME` and `os.homedir`, create temporary global/project config files, and remove them after each test (`packages/opencode/tests/config.test.ts:22-69`). Startup tests restore spies and global state in `afterAll`/`afterEach` (`packages/opencode/tests/plugin-startup.test.ts:44-86`, `packages/opencode/tests/plugin-startup.test.ts:211-225`).
- **Run packaging and integration checks, not only unit tests.** The root scripts combine unit and local packed E2E tests, build every package, typecheck package tests, and pack each publishable workspace (`package.json:8-18`, `package.json:23-60`). CI installs SWI-Prolog and Bun, typechecks, builds, runs coverage/integration tests, packs all six packages, and runs packed regressions (`.github/workflows/ci.yml:32-89`, `.github/workflows/ci.yml:111-147`, `.github/workflows/ci.yml:149-199`).

## Packaging and Configuration Lessons

- **Separate the adapter from the required runtime.** The package README states that `kibi-opencode` does not ship the CLI or MCP server and requires `kibi-cli`, `kibi-mcp`, and `kibi-core` separately (`packages/opencode/README.md:3-9`). This keeps the plugin focused, but installation documentation and diagnostics must make those prerequisites explicit.
- **Keep host config and plugin config distinct.** `opencode.json` contains the host's MCP and Prolog LSP configuration while leaving the plugin list empty (`opencode.json:1-31`); plugin behavior is configured in `.opencode/kibi.json` (`.opencode/kibi.json:1-46`). The loader also supports global `~/.config/opencode/kibi.json` overridden by project `.opencode/kibi.json` (`packages/opencode/src/config.ts:225-252`).
- **Version and publish the adapter independently.** The adapter has its own version, exports, `prepack` build, and public publish configuration (`packages/opencode/package.json:2-18`, `packages/opencode/package.json:40-57`). The root release flow builds and publishes selected workspaces through changesets (`package.json:55-60`), and the README recommends exact versions while the project is beta (`README.md:299-303`).
- **Document lifecycle side effects.** Startup schedules a delayed notification and background auto-update check, with errors logged rather than propagated (`packages/opencode/src/plugin.ts:1519-1573`). A plugin with this behavior should state when network access, cache mutation, package installation, and restart requirements occur.

## Overall Assessment

Kibi presents a substantial OpenCode adapter pattern: keep the published plugin thin at the repository edge, model host hooks explicitly, scope mutable state by worktree/session, debounce maintenance, and make enforcement posture- and health-aware. Its main operational risks are the shell-based repo-local MCP command, startup package installation, and the gap between best-effort prompt/evidence processing and durable validation. The repository mitigates those risks with explicit configuration, extensive policy/scheduler tests, and CI that validates built and packed artifacts rather than only source-level unit behavior.
