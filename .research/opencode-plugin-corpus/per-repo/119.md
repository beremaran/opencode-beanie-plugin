## What it does

`opencode-wakatime` reports AI coding activity to WakaTime. Its README documents automatic CLI management, file/tool tracking, AI line-change metrics, one-minute project rate limiting, session-final heartbeats, and batch-tool support (`README.md:15-22`). Installation can be either the OpenCode package plugin (`README.md:51-62`) or a global npm CLI that copies a bundled plugin into OpenCode's plugin directory (`README.md:64-84`).

The plugin resolves the project identity from OpenCode's worktree, then project worktree, then process cwd. This is important for GUI/server launches whose cwd may be `/` (`src/index.ts:309-315`, `src/index.ts:330-335`). It initializes project-specific state, ensures `wakatime-cli` exists, and returns `chat.message` and broad `event` hooks (`src/index.ts:381-405`, `src/index.ts:397-411`).

## OpenCode patterns worth reusing

### Event handling and compatibility

- Use `message.part.updated` to observe completed tool parts, including tools run through the batch tool (`src/index.ts:409-417`).
- Require `state.status === "completed"` and deduplicate by `callID`, because a tool can emit multiple updates (`src/index.ts:419-426`). The set is bounded by deleting the oldest 500 IDs after it exceeds 1,000 (`src/index.ts:428-434`).
- Keep SDK event shapes local and narrow: the plugin defines only the event/tool fields it consumes (`src/index.ts:21-48`). This limits coupling, though the implementation still casts the SDK client to `any` to access its internal HTTP client (`src/index.ts:356-360`).
- Prefer OpenCode-provided worktree metadata over ambient process state (`src/index.ts:330-335`). This is a general integration lesson for server and desktop clients.

### Change extraction and batching

- Centralize tool-specific extraction in a pure function. `edit` uses `filediff` with a `filePath` fallback; `write` distinguishes new files using `exists`; `multiedit` consumes per-result diffs; `read` uses its title (`src/index.ts:93-147`, `src/index.ts:182-212`).
- For patch output, parse the reported file list and distribute the aggregate diff across files as an explicit approximation (`src/index.ts:149-179`). This is pragmatic but should not be mistaken for exact per-file accounting.
- Aggregate repeated changes in a `Map`, summing additions/deletions and preserving the write flag (`src/index.ts:291-306`). Send one CLI process per batch and put extra heartbeats in JSON on stdin (`src/wakatime.ts:110-166`, `src/wakatime.ts:226-246`).
- Clear the queue and update the rate-limit state before dispatching; force mode then waits for all in-flight batches (`src/index.ts:276-287`). Session idle/deletion invokes force mode (`src/index.ts:477-485`).

### Lifecycle and resilience

- Heartbeat processes are tracked globally, given a 30-second timeout, terminated with `SIGTERM`, escalated to `SIGKILL` after two seconds, and killed on host `exit` (`src/wakatime.ts:38-60`, `src/wakatime.ts:173-224`). This directly addresses orphaned child processes.
- `flushHeartbeats()` waits for all currently pending batches, including batches started before the current flush (`src/wakatime.ts:267-272`).
- Project rate limiting is persisted in a hash-named file under WakaTime's resource directory, isolating projects without exposing the full path in the filename (`src/state.ts:13-25`). The 60-second boundary is inclusive (`src/state.ts:52-67`; `src/__tests__/state.test.ts:239-249`).
- `WAKATIME_HOME` is normalized, including `~` and `~/...`, and is used consistently for config and resource paths (`src/wakatime-paths.ts:4-35`; `src/__tests__/wakatime-paths.test.ts:27-63`).

## Security and operational pitfalls

1. **Downloaded executable trust is implicit.** Missing or stale CLI binaries are downloaded from GitHub's latest-release API/download URLs without checksum, signature, pinned version, or an allowlist for redirect destinations (`src/dependencies.ts:24-30`, `src/dependencies.ts:162-174`, `src/dependencies.ts:177-203`, `src/dependencies.ts:250-289`). A compromised release, account, or redirect path becomes executable code in the user's WakaTime directory. A safer design would pin/verify release metadata and artifact hashes, reject unexpected redirect schemes/hosts, and use atomic replacement.
2. **Native archive extraction is not path-safe.** Unix `unzip` and PowerShell `Expand-Archive` receive the downloaded archive directly (`src/dependencies.ts:292-315`). Unlike the manual fallback, which uses `path.basename(fileName)` (`src/dependencies.ts:341-350`), native extraction is not visibly guarded against archive path traversal or unexpected files. Extract to a temporary directory, validate the single expected binary, and move it atomically.
3. **Shell command construction uses environment-derived paths.** `WAKATIME_HOME` controls `destDir`, and the Windows extraction command interpolates it inside single quotes while Unix extraction interpolates it inside double quotes (`src/dependencies.ts:292-309`; `src/wakatime-paths.ts:4-18`). Paths containing shell metacharacters or quotes can break the command or alter execution. Prefer a library/API or an argument-array process spawn.
4. **Sensitive data can enter logs.** Debug logging includes the complete WakaTime CLI argument string (`src/wakatime.ts:169-171`), and file paths/titles are logged during tracking (`src/index.ts:440-464`). The current arguments do not include the API key, but paths can contain sensitive workspace names. Make debug logging explicitly redactable and avoid logging full paths by default.
5. **Failure policy is intentionally lossy.** State reads/writes, logging, and many CLI-management errors are swallowed (`src/state.ts:27-45`, `src/logger.ts:56-65`, `src/dependencies.ts:82-99`). This keeps OpenCode usable, but can hide broken rate limiting, diagnostics, or installation. Surface actionable status while retaining non-fatal behavior.

## Testing lessons and gaps

The test suite is focused and mostly unit-level:

- `index.test.ts` covers project precedence and extraction for edit/write/patch/multiedit/read plus ignored search/bash/unknown tools (`src/__tests__/index.test.ts:4-20`, `src/__tests__/index.test.ts:22-307`).
- `wakatime.test.ts` mocks child processes and verifies batching, stdin JSON, timeout escalation, flushing, and exit cleanup (`src/__tests__/wakatime.test.ts:199-310`).
- `dependencies.test.ts` covers global/local CLI selection, platform/architecture mapping, environment override, and location caching (`src/__tests__/dependencies.test.ts:41-220`).
- `state.test.ts` covers invalid/missing JSON, project isolation, environment paths, write failures, and rate-limit boundaries (`src/__tests__/state.test.ts:52-249`).

Notable gaps are integration tests against actual OpenCode hook payloads, session isolation (module-level `fileChanges` and `processedCallIds` are shared across plugin instances), malformed event metadata, concurrent CLI installation, download integrity/redirect policy, archive traversal, and the install/uninstall CLI. The patch diff approximation is tested for even positive/negative distribution but not rounding remainder or misleading output lines (`src/__tests__/index.test.ts:129-175`).

At this checkout, verification could not execute because dependencies are absent: `npm run test:run` reports `vitest: command not found`. `npm run typecheck` also fails before compilation because `vitest` types are unavailable and then reports implicit-any errors in `dependencies.test.ts` table callbacks (`src/__tests__/dependencies.test.ts:185-219`). These are environment/check-out verification results, not changes to the clone.

## Packaging and release lessons

- The package is ESM, exposes `dist/index.js` and declarations, ships only `dist` and `bin`, and declares `@opencode-ai/plugin` as a peer dependency (`package.json:10-24`, `package.json:49-50`).
- `build` first runs TypeScript and then an esbuild bundle; the bundle keeps the OpenCode SDK external and injects the package version (`package.json:26-37`, `scripts/bundle.js:12-22`). This supports both normal package loading and a standalone manually installed bundle.
- The CLI checks that the bundle exists, creates `~/.config/opencode/plugin`, and copies it to `wakatime.js`; it has explicit install, uninstall, help, and unknown-option paths (`bin/cli.js:9-13`, `bin/cli.js:20-59`, `bin/cli.js:61-101`).
- CI separates commit lint, Biome lint, tests, typecheck, and build, and gates semantic release on all of them (`.github/workflows/workflow.yml:14-105`). Release uses npm provenance and commits changelog/package lock updates through semantic-release (`.releaserc.json:28-47`).
- The repository's operational history records fixes for batch heartbeats, idle flushing, process cleanup, worktree selection, and timeout termination (`CHANGELOG.md:1-10`). This is a useful example of turning lifecycle failures into explicit regression tests and release notes.

## Bottom line

This is a strong reference for an OpenCode telemetry plugin: use worktree context, narrow completed-event handling, call-ID deduplication, batched external work, durable per-project throttling, and bounded child-process cleanup. Its principal caution is the automatic executable supply chain: release verification, safe archive extraction, shell-free path handling, atomic installation, and security-focused tests should be treated as required before copying the dependency-management approach.
