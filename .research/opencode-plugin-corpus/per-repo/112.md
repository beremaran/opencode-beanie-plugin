## README and Product Pattern

The plugin is a debugging/inspection utility: it intercepts the system prompt before it is sent to the LLM and logs it (`README.md:3-12`). Installation is a single `opencode.json`/`opencode.jsonc` plugin entry, with OpenCode responsible for automatic installation and loading (`README.md:14-24`). The documented log payload includes session ID, provider/model IDs, and the full prompt, with multiple prompt fragments separated by `-----` (`README.md:26-40`).

## OpenCode Implementation Patterns

- **Use the system transform hook for prompt observation.** The exported async plugin factory returns `experimental.chat.system.transform`, giving the plugin access to both hook input and the mutable system-prompt output immediately before model invocation (`index.ts:3-7`). This is a focused interception point and avoids modifying message history or provider calls directly.
- **Keep the entrypoint thin and typed.** The implementation imports `Hooks` and `Plugin` as types and exports a single `SystemPromptLogger` factory typed as `Plugin` (`index.ts:1-3`). The returned object is cast to `Hooks`, making the supported hook shape explicit at compile time (`index.ts:5-21`).
- **Serialize repeated prompt parts deterministically.** It maps every string in `output.system`, prefixes each with a newline, and joins parts with `\n-----`; an empty system array produces an empty message (`index.ts:6-7`). This preserves prompt ordering while making boundaries visible in structured logs.
- **Use OpenCode structured logging rather than direct console/file output.** The hook calls `client.app.log` with a service name, info level, message, and `extra` metadata (`index.ts:8-19`). This delegates log routing and location to OpenCode; the README points users to `opencode debug paths` to locate logs (`README.md:35-47`).
- **Correlate logs with model and session context.** `input.sessionID` is retained with an empty-string fallback, while provider ID and model ID come from `input.model` (`index.ts:13-17`). This makes prompt changes attributable across sessions and model configurations without maintaining plugin state.

## Security and Operational Lessons

- **Full-prompt logging is a deliberate confidentiality risk.** The README explicitly promises the full system prompt (`README.md:28-34`), and the implementation passes the unredacted joined prompt directly as `body.message` (`index.ts:6-13`). System prompts may contain repository instructions, secrets accidentally embedded in configuration, user data, proprietary policy, or other provider context. A production derivative should make capture opt-in, provide redaction/sampling controls, and clearly document log retention and access.
- **The hook has no filtering or size bound.** Every element of `output.system` is logged without truncation, allowlisting, or sensitive-pattern handling (`index.ts:6-13`). Large prompts can create noisy logs and storage pressure; a bounded logger should define maximum bytes and behavior when content is truncated.
- **Logging is on the critical request path.** The transform awaits `client.app.log` before returning (`index.ts:5-8`). There is no local error handling, timeout, or fallback, so logging failure may reject or delay the transform and potentially affect message submission. The reliability tradeoff should be explicit: best-effort diagnostics generally should not block the user’s model request.
- **The API is experimental and version-sensitive.** The only runtime integration is `experimental.chat.system.transform` (`index.ts:5`), while the README requires OpenCode `>= 1.1.37` (`README.md:49-52`). Releases should verify the hook against the minimum supported OpenCode version and a current version, and should treat hook signature changes as compatibility events.
- **Metadata is useful but still potentially sensitive.** Session, provider, and model identifiers are emitted in `extra` (`index.ts:13-17`). These fields improve correlation but can reveal project/session activity; users should understand that enabling the logger increases observability beyond prompt contents alone.

## Testing and Verification Lessons

- **Static checks are the only declared automated checks.** `package.json` defines `biome`, `typecheck`, and `build`, but no test script (`package.json:24-28`). The repository root contains no test files in the audited clone, so prompt serialization, empty prompts, metadata, hook failures, and SDK compatibility are not covered by repository tests.
- **CI verifies types and formatting, not runtime behavior.** The CI job installs with `npm ci --include=dev`, then runs `npm run typecheck` and `npm run biome` (`.github/workflows/ci.yml:9-25`). A useful next layer would mock `client.app.log` and test: multiple system parts and separators; an empty `output.system`; missing session IDs; provider/model metadata; log rejection; and oversized/redaction behavior if those controls are added.
- **Build coverage is separate from CI’s test job.** The publish job builds only after the type/format job passes (`.github/workflows/ci.yml:26-47`). This catches TypeScript emission for tagged releases but does not test that the emitted module loads under OpenCode or that the published tarball contains the expected entrypoints.
- **The implementation’s simplicity makes contract tests high-value.** There is no state, filesystem, subprocess, or network logic in the plugin itself; a small mocked hook suite could exercise nearly all behavior and would protect the experimental hook contract more effectively than broad static checks alone (`index.ts:3-21`).

## Configuration and Packaging

- The package is ESM and exposes compiled JavaScript and declarations through `main: dist/index.js` and `types: dist/index.d.ts` (`package.json:18-20`). `files` restricts the published package to `dist` (`package.json:21-23`), while `.gitignore` excludes `node_modules` and `dist` from source control (`.gitignore:1-2`).
- TypeScript emits declarations into `dist`, uses bundler module resolution, targets modern ESNext, and enables strict/no-unused checks (`tsconfig.json:3-15`). The narrow `include` list contains only `index.ts` (`tsconfig.json:13-15`), which matches the one-file implementation but would need updating if source modules are added.
- The OpenCode plugin API is a peer dependency with minimum version `>=1.1.37`; Biome and TypeScript are development dependencies (`package.json:29-35`). Keeping the host API as a peer avoids bundling a second SDK copy and lets OpenCode provide the compatible runtime surface.
- The lockfile records npm lockfile version 3 and pins the development toolchain while preserving the same peer requirement (`package-lock.json:1-17`). The CI uses `npm ci`, making lockfile drift fail early (`.github/workflows/ci.yml:20-21`).
- Release automation is tag-gated: CI publishes only for `v` tags, after a successful test job, and requests npm trusted-publishing identity-token permission (`.github/workflows/ci.yml:26-47`). Renovate is configured for weekly updates, lockfile maintenance, grouped non-major updates, and automatic minor updates (`renovate.json:2-10`).
- The MIT license is included in the repository and grants broad reuse subject to retaining the copyright/license notice (`LICENSE:1-13`). The package metadata also declares MIT licensing (`package.json:13-18`).

## Overall Assessment

System Prompt Logger is a clear minimal example of an OpenCode plugin that observes the final system prompt through `experimental.chat.system.transform` and emits structured, model/session-correlated diagnostics. Its strongest reusable patterns are a typed single-factory entrypoint, deterministic handling of repeated prompt parts, and use of `client.app.log` rather than ad hoc output. Its primary risks are intentional unredacted prompt disclosure, unbounded log volume, and awaiting logging on the critical path. Packaging is disciplined and narrow, but the repository has only type/format/build checks; mocked hook tests and a published-artifact/runtime smoke test would materially improve confidence.
