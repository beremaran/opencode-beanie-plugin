## What it does

`@zenobius/opencode-skillful` implements an Anthropic Agent Skills interpretation for OpenCode. It discovers `SKILL.md` files, searches them with a Gmail-like query syntax, lazily injects selected skills, and reads indexed references/assets/scripts (`README.md:1-9`, `README.md:221-229`). The three runtime tools are `skill_use`, `skill_find`, and `skill_resource` (`src/index.ts:71-175`).

The design keeps discovery out of every prompt: initialization scans configured roots and tool calls wait for the registry before searching/loading (`src/index.ts:38-45`, `src/tools/SkillFinder.ts:34-54`, `src/tools/SkillUser.ts:3-30`). This is a useful OpenCode pattern for expensive asynchronous setup: register tools immediately, then gate execution with a shared readiness abstraction.

## OpenCode implementation patterns

### Plugin lifecycle and message injection

- The plugin obtains configuration and an API factory from the OpenCode `PluginInput`, starts registry initialization, and returns event/tool handlers (`src/index.ts:38-47`).
- `chat.message` events record provider/model IDs per message, while removal/deletion events clean the accounting state (`src/index.ts:48-69`). This enables model-aware formatting without querying the model on every tool call.
- Prompt injection uses `ctx.client.session.prompt` with `noReply: true`, the current session/agent, and a text part (`src/lib/OpenCodeChat.ts:3-15`). This is a concrete silent-insertion pattern for adding durable context without eliciting an extra assistant response.
- Tool schemas are declared with `tool.schema`, including an array for `skill_use` and a string-or-array union for `skill_find` (`src/index.ts:72-79`, `src/index.ts:108-114`). Outputs distinguish loaded/not-found skills and resource metadata (`src/index.ts:101-104`, `src/index.ts:168-172`).

### Async initialization

`ReadyStateMachine` exposes `idle`, `loading`, `ready`, and `error`, watcher unsubscribe functions, and a `whenReady()` barrier (`src/lib/ReadyStateMachine.ts:33-76`). Registry initialization transitions state, scans all existing roots, records parse statistics, and continues after malformed skills rather than aborting the whole catalog (`src/services/SkillRegistry.ts:160-231`, `src/services/SkillRegistry.ts:259-297`). This is resilient for user-controlled skill directories.

### Discovery, precedence, and search

- Default roots are derived from OpenCode/XDG paths, with project-local `.opencode/skills` appended at highest priority; paths are expanded, made absolute, and deduplicated (`src/config.ts:50-76`, `src/config.ts:142-170`, `src/config.ts:184-194`).
- Each `SKILL.md` is parsed with gray-matter and validated with a schema requiring a 20-character description; resources are indexed into maps during parsing (`src/services/SkillRegistry.ts:66-75`, `src/services/SkillRegistry.ts:369-405`).
- Search parses include/exclude terms, requires every include term to occur in tool name/name/description, filters exclusions, then ranks by name/description scores and alphabetical tie-break (`src/services/SkillSearcher.ts:48-74`, `src/services/SkillSearcher.ts:174-245`). The extensive tests cover query parsing, negation, ranking, tie-breaking, feedback, and larger result sets (`src/services/SkillSearcher.test.ts:6-151`, `src/services/SkillSearcher.test.ts:153-451`, `src/services/SkillSearcher.test.ts:602-769`).

### Model-aware rendering

The renderer factory keeps JSON, XML, and Markdown implementations behind one runtime selector (`src/lib/createPromptRenderer.ts:21-43`). Provider-plus-model keys take precedence over model-only keys, then the configured default is used (`src/lib/getModelFormat.ts:33-55`). This is a practical extension point when OpenCode deployments use heterogeneous providers/models.

## Security lessons and pitfalls

### Positive controls

- Resource access is allowlisted by enumeration: `SkillRegistry` records only files found under `scripts`, `references`, and `assets`, and the resolver performs a map lookup before reading (`src/services/SkillRegistry.ts:389-405`, `src/services/SkillResourceResolver.ts:43-65`). The tests explicitly exercise `../`, repeated traversal, absolute paths, and cross-skill escapes (`src/services/SkillResourceResolver.test.ts:80-152`).
- MIME types are derived from file extensions with an octet-stream fallback (`src/lib/SkillFs.ts:57-59`), and Markdown rendering escapes HTML-sensitive values (`src/lib/renderers/MdPromptRenderer.ts:123-137`).

### Risks and operational caveats

- The allowlist is built from filesystem enumeration, but there is no visible realpath/symlink containment check before storing `absolutePath` (`src/services/SkillRegistry.ts:409-420`). If the scanner follows symlinks, a resource symlink could point outside the skill tree. A production implementation should resolve and verify real paths, or explicitly reject symlinks.
- `allowed-tools` is parsed into the skill object but explicitly not enforced (`src/services/SkillRegistry.ts:67-75`, `src/types.ts:107-119`, `README.md:1079-1085`). Treating this field as informational must be clearly documented as a trust boundary: loading a skill does not sandbox or constrain tools.
- Skill bodies and resource content are inserted into the conversation as user messages (`src/lib/OpenCodeChat.ts:5-13`; `src/index.ts:93-99`, `src/index.ts:157-166`). Skills are therefore prompt content, not trusted policy. Repositories should treat installed skills as code/instruction supply-chain inputs and avoid presenting their metadata as enforcement.
- The README describes agents running scripts from the inventory (`README.md:103-129`), but the plugin exposes resource reading, not script execution; the architecture explicitly says `skill_exec` was removed (`README.md:723-730`). Documentation should avoid implying that merely indexing a script grants execution capability.
- Registry duplicate precedence is described as “last wins,” but `matchBasePath` uses `startsWith` and duplicate registration depends on scan order (`src/services/SkillRegistry.ts:234-240`, `src/services/SkillRegistry.ts:285-287`). Boundary-aware path comparisons and explicit root ordering would make precedence less ambiguous.

## Testing lessons

- The suite mixes `bun:test` and Vitest imports (`src/services/SkillSearcher.test.ts:1-4`, `src/config.test.ts:1-9`). The repository’s documented command is `bun test` (`AGENTS.md:3-9`), and CI runs lint, test, and build (`.github/workflows/pr.yml:31-36`).
- In this audited clone, running `bun test` produced 0 passing tests and 11 failing test files because `memfs` could not be resolved from `src/mocks.skillfs.ts`. No dependency installation or clone modification was performed. This is a reproducibility failure for the captured checkout, even though `memfs` is declared in `package.json` devDependencies (`package.json:31-44`).
- Tests are strongest around pure search/config/rendering functions and traversal rejection. There is less evidence in the inspected suite for end-to-end plugin registration, `chat.message`/event cleanup, message injection payloads, model-accountant behavior, initialization failure propagation, symlink handling, or package-consumer imports.
- The test task is permissive (`bun test || test $? -eq 1`), which preserves the same exit status rather than adding diagnostics or setup (`.mise/tasks/test:1-3`). CI still invokes it as a required step, so missing dependency resolution can block CI but is not self-healed.

## Packaging and release lessons

- The package declares ESM, OpenCode plugin dependency `1.0.85`, public npm publishing, and provenance (`package.json:1-14`, `package.json:21-29`). The PR workflow runs setup, lint, test, and build (`.github/workflows/pr.yml:24-36`).
- `files` includes `dist` and `src/version.ts`, while `main` points to `dist/index.js` and `types` points to `dist/index.d.ts` (`package.json:15-20`). The build task only runs `bun build ./src/index.ts --outdir dist --target bun` (`.mise/tasks/build:1-6`); it does not visibly emit declaration files. The declared `types` path should be verified against the published tarball, or removed/generated deliberately.
- Release Please updates versions/changelogs and dispatches a publish workflow (`.github/workflows/release.yml:15-48`, `RELEASE.md:19-29`). Publishing uses npm OIDC/provenance in GitHub Actions and disables provenance locally (`.mise/tasks/publish:35-52`), a good separation of trusted CI publishing from developer machines.
- The publish script builds, then publishes with a tag and public access (`.mise/tasks/publish:1-5`, `.github/workflows/publish.yml:35-50`). The `next` path mutates `package.json` to a commit-count prerelease before publishing (`.mise/tasks/publish:13-33`); this should be checked against release automation and workspace cleanliness expectations.

## Documentation/configuration inconsistencies

- The installation example says `~/.config/opencode/config.json` (`README.md:54-62`), while plugin-specific configuration is loaded through `bunfig` and `.opencode-skillful.json`/global plugin paths (`README.md:578-593`, `src/config.ts:32-37`, `src/config.ts:173-194`). Users need both OpenCode plugin registration and the separate plugin settings file, but the distinction should be sharper.
- README examples alternate between positional-looking calls such as `skill_find "git commit"` and named arguments such as `skill_resource skill_name=...` (`README.md:30-50`), while runtime schemas require an array for `skill_use` and an object with `skill_name`/`relative_path` for `skill_resource` (`src/index.ts:72-79`, `src/index.ts:134-141`). Examples should match actual OpenCode tool invocation serialization.
- The README claims “last path wins on duplicates” (`README.md:327-333`), while registry comments say duplicate handling can overwrite but the implementation’s actual ordering should be tested (`src/services/SkillRegistry.ts:34-38`, `src/services/SkillRegistry.ts:285-287`).

## Bottom line

The most reusable patterns are: a factory-wired plugin API, a shared readiness barrier around async discovery, project-over-global skill roots, pre-indexed resource maps, and model-aware prompt rendering. The main lessons are to verify filesystem boundaries beyond lexical map lookup, treat skill content and `allowed-tools` as untrusted/informational, align README examples with tool schemas, and make the package’s declaration-file and dependency reproducibility story verifiable before release.
