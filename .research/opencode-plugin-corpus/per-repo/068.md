## OpenCode integration patterns

### Separate server and TUI surfaces

The package advertises two OpenCode plugin entrypoints through `oc-plugin: ["server", "tui"]` (`package.json:26-29`). The main export is a V1 module with an explicit `id` and `server` function rather than a legacy object export (`src/index.ts:9-25`). The source comment records the reason: avoid OpenCode's legacy `Object.values` fallback, which can conflict with other legacy plugins (`src/index.ts:16-23`). The TUI entrypoint is a separate `TuiPluginModule` with the same stable id (`src/tui.tsx:984-999`).

This is a useful pattern for plugins that need both Web/server behavior and native TUI behavior: expose each surface in the package manifest and keep their runtime concerns separate, while sharing library code.

### Hook-driven, non-LLM output

The server plugin registers deterministic slash commands through `config`, handles `command.execute.before`, exposes a typed `quota_status` tool, and listens for `session.idle`, `session.compacted`, and `tool.execute.after` (`src/plugin.ts:1210-1231`, `src/plugin.ts:1233-1275`, `src/plugin.ts:1277-1318`). It refreshes configuration lazily before the first relevant event or tool call and exits early when disabled (`src/plugin.ts:1286-1316`).

For reports, it calls `session.prompt` with `noReply: true` and an ignored text part so the user sees output without triggering an LLM response or polluting future context (`src/plugin.ts:216-235`). The README explicitly presents this as “zero context window pollution” (`package.json:5`, `README.md:10`). This is an effective OpenCode-specific pattern for status/diagnostic plugins: use the session UI transport, but mark injected content ignored and avoid asking the model to summarize it.

### Bounded refresh and lifecycle management

The server defers retryable quota refreshes with increasing delays of 3 seconds through 5 minutes (`src/plugin.ts:174-203`, `src/plugin.ts:291-319`). It clears per-session timers when disabled or disposed (`src/plugin.ts:1290-1293`, `src/plugin.ts:1310-1313`). The TUI maintains resources per API/session using `WeakMap`, reference counting, disposal, periodic refresh, event-triggered refresh, and mount-recovery retries (`src/tui.tsx:154-179`, `src/tui.tsx:194-224`, `src/tui.tsx:231-253`).

The TUI listens only for events relevant to the session and schedules refreshes on updates, removals, and session selection (`src/tui.tsx:199-220`). This avoids one global polling loop per rendered component and is a strong model for multi-surface TUI plugins.

### Config-aware installation and command surfaces

Manual installation distinguishes global, project, and `OPENCODE_CONFIG_DIR` scopes (`docs/readme/manual-install.md:13-19`). It requires adding the server plugin to OpenCode config and, for TUI use, adding the TUI plugin to `tui.jsonc`/`tui.json` (`docs/readme/manual-install.md:21-47`). Configuration is kept in a dedicated `opencode-quota/quota-toast.jsonc` sidecar rather than mixed into the TUI config (`docs/readme/manual-install.md:49-80`, `docs/readme/manual-install.md:91-105`).

The installer/updater is preferred over hand editing, previews changes, preserves unrelated settings/comments/plugins, and supports `--dry-run` (`README.md:40-52`, `docs/readme/manual-install.md:109-118`). This reduces configuration damage and makes a multi-file plugin installation understandable to users.

## Security and reliability lessons

### Treat provider definitions as executable configuration

Custom `quotaProviders` are accepted only from trusted global files. Tests verify that workspace sidecars and workspace OpenCode files are rejected, SDK-provided definitions are rejected when file provenance is unknown, and trusted global definitions are accepted (`tests/lib.quota-providers.security.test.ts:27-116`). The test names and expected diagnostics make the threat model explicit: a repository's configuration must not be able to introduce arbitrary remote quota endpoints or credentials (`tests/lib.quota-providers.security.test.ts:37-68`).

Lesson: if a plugin loads provider URLs, environment-variable names, or other network behavior from config, establish provenance and do not automatically trust project-local config.

### Sanitize remote/provider text before display

The shared display sanitizer strips ANSI escape sequences and control characters while retaining newline/tab (`src/lib/display-sanitize.ts:1-28`). It sanitizes entries, errors, diagnostics, raw details, and model identifiers recursively before rendering (`src/lib/display-sanitize.ts:46-131`). Server injection and reset-notification toasts use sanitized text (`src/plugin.ts:228-235`, `src/plugin.ts:1184-1189`).

Provider-specific error handling also redacts secrets before showing API response text; for example, Kilo replaces the configured key in error messages and truncates sanitized output (`src/lib/kilo.ts:46-48`, `src/lib/kilo.ts:248-258`).

### Bound every remote transaction

`fetchWithTimeout` uses an `AbortController`, races the entire fetch/status/body-consumption transaction against a timer, aborts on timeout, and clears the timer in `finally` (`src/lib/http.ts:7-20`, `src/lib/http.ts:22-57`). The comment correctly emphasizes that parsing and status handling must occur inside the timed consumer (`src/lib/http.ts:16-18`).

### Avoid leaking credentials through diagnostics

The provider security tests protect config provenance, while provider implementations distinguish API keys and auth diagnostics. The Copilot implementation redacts both raw and sanitized token forms from REST error text (`src/lib/copilot.ts:706-745`). This should be treated as a required boundary whenever a plugin converts third-party failures into TUI toasts or transcript text.

## Testing practices

- Vitest runs Node-environment tests from `tests/**/*.test.ts` with a shared cleanup setup (`vitest.config.ts:1-9`, `tests/setup.ts:1-15`).
- The suite tests server command behavior, including lazy config loading before `session.idle`, disabled behavior, provider errors, and the guarantee that deterministic dialog output does not call `session.prompt` (`tests/plugin.quota-command.test.ts:29-57`, `tests/plugin.quota-command.test.ts:175-206`).
- Security behavior is tested as an explicit contract rather than inferred from implementation (`tests/lib.quota-providers.security.test.ts:27-116`).
- Package manifest tests inspect package metadata, workflow structure, scripts, README claims, TypeScript/tool versions, and packaging assumptions (`tests/package-manifest.test.ts:27-115`, `tests/package-manifest.test.ts:143-180`).
- The canonical verification command combines formatting/linting, version/history checks, typecheck, build, all tests, cross-surface tests, and package-content verification (`package.json:48-61`).
- CI runs `pnpm verify`, then creates and uploads the exact release artifact; a dependent matrix smoke-tests that artifact on Node 22 and 24 (`.github/workflows/ci.yml:8-66`).

The main lesson is to test OpenCode integration at boundaries: hook behavior, output injection semantics, config provenance, both server/TUI surfaces, and the packed artifact rather than only source modules.

## Packaging and release lessons

The package exposes typed server, server alias, and TUI exports, a CLI binary, and declares the OpenCode plugin surfaces in `package.json` (`package.json:7-29`). It limits published files to `dist`, `README.md`, and `LICENSE` (`package.json:30-34`). TypeScript emits declarations/source maps into `dist` with strict checking and bundler resolution (`tsconfig.json:1-23`).

The package-content verifier rejects files outside a strict root allowlist or `dist/`, and requires package entrypoints, the license/readme/package metadata, and bundled pricing data (`scripts/verify-package-contents.mjs:51-97`). The packed-package smoke test installs the tarball as a consumer, imports root/server/TUI exports, checks the compiled TUI output, validates dependency placement, exercises telemetry, runs real OpenTelemetry scenarios, and invokes CLI help (`scripts/smoke-packed-package.mjs:44-147`).

CI uses a frozen pnpm install and separates quality verification from runtime artifact smoke tests (`.github/workflows/ci.yml:22-31`, `.github/workflows/ci.yml:43-66`). This catches failures that source tests miss, such as omitted generated files, broken conditional exports, incorrect runtime dependencies, or an unusable CLI.

## Pitfalls and tradeoffs

- The package requires Node 22 at runtime but uses Node 24 for the primary CI quality job; compatibility is covered by the Node 22/24 runtime matrix rather than a single environment (`package.json:114-117`, `.github/workflows/ci.yml:17-20`, `.github/workflows/ci.yml:47-57`).
- The plugin uses a manually maintained minimal OpenCode client interface and casts the SDK client to it (`src/plugin.ts:69-124`, `src/plugin.ts:212-214`). This improves local compatibility but shifts SDK-shape drift detection to tests and release checks.
- The TUI intentionally disables an accessibility lint rule for static element interactions and a suspicious lint rule for implicit lets (`biome.json:85-97`). These exceptions are scoped, but they should remain justified and reviewed when the TUI changes.
- Remote providers and local auth sources create a large integration surface. The repository mitigates this with provider-specific tests and diagnostics, but external API drift remains an operational risk; the README directs users to `/quota_status` and provider troubleshooting (`README.md:225-233`).
- The package has both a `dependencies` entry for `@opentelemetry/api` and a development-only metrics SDK, with the packed smoke test explicitly checking that host-owned `@opentelemetry/sdk-metrics` is not published as a runtime dependency (`package.json:85-112`, `scripts/smoke-packed-package.mjs:78-103`). This is sound, but dependency ownership needs to stay aligned with the runtime telemetry contract.

## Reusable takeaways

1. Prefer explicit OpenCode V1 module exports with stable ids; avoid ambiguous legacy export shapes (`src/index.ts:16-25`).
2. Separate server and TUI registration while sharing pure provider/rendering libraries (`package.json:26-29`, `src/tui.tsx:984-999`).
3. Inject deterministic status text with `noReply` and ignored parts when the output must not consume model context (`src/plugin.ts:216-235`).
4. Treat project-local provider configuration as untrusted and require trusted global provenance (`tests/lib.quota-providers.security.test.ts:37-116`).
5. Sanitize and redact all provider-derived display/error text (`src/lib/display-sanitize.ts:18-28`, `src/lib/copilot.ts:706-745`).
6. Test the packed npm artifact on every supported runtime, not only the TypeScript source tree (`.github/workflows/ci.yml:30-66`, `scripts/smoke-packed-package.mjs:44-147`).
