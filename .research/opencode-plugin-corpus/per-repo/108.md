- This is a standalone TypeScript ESM OpenCode plugin. The README explicitly distinguishes it from OpenCode itself and describes multi-engine TTS, desktop/webhook notifications, reminders, focus suppression, and per-project sounds (`README.md:15-17`, `README.md:27-71`).

## OpenCode Patterns

- **Plugin entrypoint shape:** The default export is an async plugin factory receiving `project`, `client`, shell runner `$`, `directory`, and `worktree`, and returns `PluginHandlers` (`src/index.ts:55-64`). This is a useful baseline for plugins that need both the OpenCode client and platform command execution.
- **Return no handlers for a disabled plugin:** The factory checks boolean and string forms of `enabled`, optionally logs, and returns `{}` before registering events (`src/index.ts:72-91`). The event handler repeats the check so a hot-reloaded disable cancels pending work and skips future events (`src/index.ts:1193-1216`).
- **Event-driven notification coverage:** One handler handles user message activity, session lifecycle, idle/error notifications, permission request/reply events, and question ask/reply/reject events, with explicit compatibility for older and v2 event names (`src/index.ts:1224-1239`, `src/index.ts:1592-1658`, `src/index.ts:1712-1769`).
- **Stateful event correctness:** The implementation tracks seen user message IDs because `message.updated` can fire for modifications, only cancels reminders for new messages after idle, debounces duplicate `session.idle` events for five seconds, caches session lookups for 30 seconds, and cleans expired entries (`src/index.ts:126-154`, `src/index.ts:1241-1279`, `src/index.ts:1382-1415`). These are strong patterns for plugins reacting to noisy or repeated SDK events.
- **Sub-session filtering:** Idle and error notifications fetch session metadata and suppress child sessions with a `parentID`, while falling back to generic notification behavior if lookup fails (`src/index.ts:1397-1415`, `src/index.ts:1517-1532`). The e2e suite explicitly tests that child sessions do not notify (`tests/e2e/plugin.test.ts:144-166`).
- **Immediate side effect, deferred expensive work:** Idle and error flows show a toast, desktop notification, webhook, and sound before scheduling or generating AI/TTS content; the code comments explain that AI generation can take seconds and must not delay the immediate signal (`src/index.ts:1366-1377`, `src/index.ts:1434-1480`, `src/index.ts:1534-1578`).
- **Compatibility probing rather than version branching:** Session lookup first tries the v1 `{ path: { id } }` shape, validates the returned ID, then tries v2 `{ sessionID }`; toast calls similarly try flat v2 then wrapped v1 payloads and remember the successful shape (`src/index.ts:238-289`, `src/util/tts.ts:277-301`). This is a practical migration pattern when multiple SDK client versions exist in the field.
- **Batching and cancellation:** Permission and question requests are collected in short configurable windows, deduplicated, and flushed together; replies remove pending items and cancel timers/reminders (`src/index.ts:1597-1646`, `src/index.ts:1655-1709`, `src/index.ts:1282-1315`, `src/index.ts:1712-1739`).
- **Config as a user-facing contract:** The plugin generates a fully commented JSONC configuration, preserves user values with recursive object merging, treats arrays as replacements, adds new defaults, and rewrites only when fields or version change (`src/util/config.ts:39-64`, `src/util/config.ts:78-116`, `src/util/config.ts:977-1097`). Bundled sounds are copied without overwriting customized target files (`src/util/config.ts:941-974`).
- **Operational resilience:** Debug logging is opt-in and file-based, logging failures are swallowed so diagnostics cannot break notifications (`src/util/config.ts:19-37`, `src/index.ts:192-201`). Webhooks use an in-memory bounded queue, rate-limit handling, timeouts, and bounded retries (`src/util/webhook.ts:90-129`, `src/util/webhook.ts:387-501`, `src/util/webhook.ts:514-559`).

## Security and Reliability Pitfalls

- **Webhook SSRF surface:** Generic webhook validation accepts any `http:` or `https:` URL, not only Discord (`src/util/webhook.ts:200-225`), and the sender performs a direct `fetch` to that configured URL (`src/util/webhook.ts:387-419`). If configuration can be influenced by an untrusted party, this can reach internal services; constrain schemes/hosts or clearly treat the config directory as trusted.
- **Sensitive data propagation:** Context-aware AI can include project name, session title, and file/addition/deletion summary in prompts (`src/util/ai-messages.ts:108-137`), while AI and webhook endpoints are configurable (`src/util/ai-messages.ts:145-183`, `src/types/config.ts:116-124`, `src/types/config.ts:147-152`). Users need an explicit data-boundary warning, and logs should avoid endpoint URLs or generated content where secrets or private project names may appear.
- **Debug logs may expose content:** AI success logs include the first 50 characters of the generated message (`src/util/ai-messages.ts:203-216`), and webhook errors log response bodies (`src/util/webhook.ts:451-500`). These are opt-in, but generated text, server diagnostics, or webhook data can still be sensitive.
- **Shell/process execution is a trust boundary:** The plugin runs PowerShell, `say`, `osascript`, `caffeinate`, and Linux platform commands (`src/util/tts.ts:324-331`, `src/util/tts.ts:838-845`, `src/util/tts.ts:999-1023`). SAPI escapes text for SSML and writes a temporary script (`src/util/tts.ts:752-805`), but command construction should remain narrowly parameterized and every platform helper should be tested with hostile strings.
- **Unbounded external TTS request:** OpenAI-compatible TTS sends `fetch` without an abort timeout (`src/util/tts.ts:870-900`), unlike the AI and webhook paths. A hung endpoint can hold an event notification indefinitely and delay fallback; add a bounded timeout and ensure the fallback chain runs on abort.
- **Config file write race/validation tradeoff:** A malformed config is preserved and defaults are used, but a regex “peek” still extracts `enabled` from invalid content (`src/util/config.ts:1004-1033`). This honors the disable switch, yet regex parsing can disagree with actual JSONC semantics; keep it deliberately narrow and test malformed edge cases.
- **Reminder lifecycle risk:** The plugin maintains multiple maps, arrays, timers, and cached session data. It does clear them in `dispose` (`src/index.ts:1168-1190`), but timer/error paths are asynchronous and some batch timers invoke async callbacks in `setTimeout`; the dedicated tests should continue to cover teardown and late callbacks.

## Testing Lessons

- **Layered test suite:** Tests cover configuration/parser/merge behavior, platform helpers, TTS, webhook queues/rate limits, focus detection, and plugin e2e flows. The test setup creates an isolated `OPENCODE_CONFIG_DIR`, temporary assets, mock shell calls, and mock OpenCode clients (`tests/setup.ts:20-25`, `tests/setup.ts:50-85`, `tests/setup.ts:116-138`, `tests/setup.ts:164-199`). This is a good model for filesystem- and process-heavy plugins.
- **Behavioral e2e assertions:** Core tests verify disabled/enabled registration, notification modes, child-session suppression, duplicate idle debouncing, and distinct-session behavior (`tests/e2e/plugin.test.ts:38-61`, `tests/e2e/plugin.test.ts:63-166`, `tests/e2e/plugin.test.ts:168-231`).
- **Configuration edge cases are explicit:** Parser tests cover comments, URLs containing `//`, empty input, trailing commas, nested merge, array replacement, null/undefined, and circular user references (`tests/unit/config.test.ts:54-128`).
- **Run in CI with reproducible installs and coverage:** CI uses Bun, `bun install --frozen-lockfile`, and `bun test --coverage`, then uploads coverage (`.github/workflows/test.yml:14-35`). Bun’s config sets a 10-second test timeout and 50% line/function/statement thresholds (`bunfig.toml:4-23`).
- **Testing gap to preserve:** `tests/unit/v2-client-shape-compat.test.ts` is labeled as a red-phase suite and its comments say it is expected to fail against v1-only production code (`tests/unit/v2-client-shape-compat.test.ts:1-18`, `tests/unit/v2-client-shape-compat.test.ts:187-219`). The current implementation contains compatibility probing, so this test documentation is stale or the suite needs updating; CI should ensure compatibility tests are genuinely passing rather than intentionally red.
- **Type-safety gap:** Several tests begin with `// @ts-nocheck` (`tests/unit/config.test.ts:1`, `tests/e2e/plugin.test.ts:1`, `tests/unit/webhook.test.ts:1`). Production TypeScript is strict, but test type checking is weakened; typed test doubles would catch SDK-shape drift earlier.

## Packaging and Release Lessons

- **Correct package metadata:** The package is ESM, exposes `dist/index.js` and declarations, declares `@opencode-ai/plugin` as a peer dependency, and publishes only `dist/` and `assets/` (`package.json:2-7`, `package.json:36-39`, `package.json:52-65`). The README gives npm, GitHub, and local-file OpenCode plugin configuration examples (`README.md:73-109`).
- **Build is intentionally source-scoped:** `tsconfig.build.json` emits `src/**/*` to `dist` and excludes tests (`tsconfig.build.json:1-9`), while the default TypeScript config enables strictness, declarations, maps, unused checks, and unchecked-index checking (`tsconfig.json:1-33`).
- **Lockfile and artifact discipline:** The repository tracks `bun.lock`, ignores `dist/`, coverage, logs, caches, environment files, and local artifacts (`.gitignore:1-71`). This supports reproducible installs while keeping generated output out of source control.
- **Release workflow has useful gates:** Manual release input validates semver, installs from the lockfile, runs tests before version mutation, updates `package.json`, conditionally commits/pushes the bump, avoids duplicate tags, and creates a GitHub release (`.github/workflows/release.yml:1-22`, `.github/workflows/release.yml:29-81`, `.github/workflows/release.yml:183-200`).
- **Packaging pitfall:** `package.json` has no `prepublishOnly`/`prepare`/publish build script (`package.json:8-14`), yet the published file list contains only `dist/` and `assets/` (`package.json:36-39`). Release automation runs tests but not `bun run build` (`.github/workflows/release.yml:51-55`). A clean release can therefore omit `dist` unless it is built elsewhere; add an explicit build gate before publishing.
- **Release mutation risk:** The workflow commits and pushes a version bump before creating the tag/release (`.github/workflows/release.yml:62-81`, `.github/workflows/release.yml:193-200`). If later release steps fail, the repository can contain a pushed version commit without a corresponding release; a more transactional release process or recovery documentation would reduce this risk.

## Bottom Line

The strongest reusable design is the combination of a minimal async plugin factory, explicit event-state management, immediate user-visible signals before slow work, compatibility probing for SDK shape changes, and isolated filesystem/process tests. The most important follow-ups are tightening configurable webhook destinations, adding timeouts to every network-backed TTS path, treating context/log output as potentially sensitive, converting `ts-nocheck` tests to typed doubles, reconciling stale v2 test documentation, and making the release workflow build the exact `dist/` artifact that `package.json` publishes.
