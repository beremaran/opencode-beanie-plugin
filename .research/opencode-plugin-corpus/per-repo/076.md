## Repository Shape

This is a small multi-variant OpenCode plugin package. The README recommends a typed TUI plugin for a sidebar footer, while retaining an event-driven classic toast plugin and a polling real-time toast plugin (`README.md:9-29`, `README.md:58-102`). The package declares the classic JavaScript file as its main entrypoint and includes all three plugin files plus the README in its published file set (`package.json:5-8`). There is no separate build step; the JavaScript variants are directly consumable, while the TUI file is TypeScript/TSX and depends on OpenCode TUI and Solid imports (`token-tracker.tsx:17-20`).

## OpenCode Patterns

### Event-driven plugin lifecycle

The classic variant exports an async plugin factory receiving `{ client }` and returns an object with an async `event` handler (`token-tracker.js:103-110`). It gates work on `session.idle` and safely ignores events without a session ID (`token-tracker.js:110-114`). This is a useful minimal pattern for post-request instrumentation: read session state only after the request is idle, then call the TUI API with `client.tui.showToast` (`token-tracker.js:187-189`).

### SDK response-shape tolerance

Both collection helpers accept either a direct array or an SDK response with `data`, default missing responses to an empty value, and reject non-array results (`token-tracker.js:23-25`, `token-tracker.js:68-70`). The tests explicitly cover null, undefined, empty, wrapped, and non-array responses (`token-tracker.test.js:49-111`, `token-tracker.test.js:217-245`, `token-tracker.test.js:313-327`). This reduces coupling to response wrappers, but it can also hide an unexpected API shape rather than surfacing it.

### Message filtering and normalization

Collection is restricted to assistant messages with token data and at least one non-zero input/output/cache field (`token-tracker.js:27-41`, `token-tracker.js:72-82`). Numeric fields are normalized with `Number(...) || 0`, optional provider/model values are joined without producing a slash-only value, and latency is calculated only when both timestamps exist (`token-tracker.js:83-99`). The helper tests cover missing fields, cache-only usage, latency, model fallbacks, and finish values (`token-tracker.test.js:104-214`).

### Deduplication and subagent aggregation

The classic implementation keeps a per-session `Set` of message IDs and a per-session `Set` of processed child session IDs (`token-tracker.js:104-119`). It loads all main-session messages, discovers children, fetches only new child sessions in parallel, then filters the combined data by unseen message ID (`token-tracker.js:121-157`). This allows repeated idle events to be harmless and aggregates parent plus subagent usage. The suite verifies repeated requests, repeated idle events, child ID shapes, child failures, new children, and parent/child totals (`token-tracker.test.js:470-697`, `token-tracker.test.js:814-855`).

### TUI slot integration

The recommended variant registers a `sidebar_footer` slot and creates a component with the current session ID (`token-tracker.tsx:105-113`). It reads reactive session status and messages from the TUI API, refreshes a signal every two seconds, and clears the interval with `onCleanup` (`token-tracker.tsx:25-39`). It derives session totals and the latest assistant request, then renders busy/completed state and theme-aware text (`token-tracker.tsx:41-54`, `token-tracker.tsx:68-102`). The README correctly documents the TUI version and sidebar visibility requirement (`README.md:31-55`).

## Pitfalls and Correctness Risks

- **Realtime variant has process-global tracking state.** `seenMessages`, `currentSessionID`, `lastToastId`, and one timer live in the plugin factory rather than being keyed by session (`token-tracker-realtime.js:8-16`). Starting a second busy session clears the first timer and replaces the current session (`token-tracker-realtime.js:92-107`), so concurrent sessions can interfere with one another.
- **Realtime updates can overlap.** `updateToast` is async, but the initial call and interval callback do not await it (`token-tracker-realtime.js:101-107`). A slow messages request can therefore overlap with the next two-second poll.
- **The realtime `seenMessages` set does not affect totals.** Messages are added to the set (`token-tracker-realtime.js:62-63`), but collection sums every assistant message returned on every poll (`token-tracker-realtime.js:40-60`). This is harmless for the displayed cumulative total, but the state name suggests deduplication that is not actually used.
- **TUI “last request” count is hardcoded.** The footer computes `reqCount` for totals but renders `1 req` unconditionally (`token-tracker.tsx:45`, `token-tracker.tsx:78-80`). That is accurate only if a last assistant message exists and the intended label is always singular.
- **TUI data coverage differs from classic coverage.** The TUI totals include only input and output tokens and cost (`token-tracker.tsx:41-45`), whereas the classic plugin also reports reasoning and cache read/write tokens (`token-tracker.js:159-179`). Users can see materially different totals depending on the selected variant.
- **Classic state is unbounded for a long-lived process.** Per-session message and child ID sets are created and never removed (`token-tracker.js:104-119`, `token-tracker.js:190-194`). The README also states that there is no persistence across sessions (`README.md:144-149`), so this is in-memory deduplication, not durable accounting.
- **Errors are intentionally silent.** The classic event handler catches everything and discards the error (`token-tracker.js:115-193`); the realtime collector and toast update do the same (`token-tracker-realtime.js:32-72`, `token-tracker-realtime.js:75-89`). This protects the host session from plugin failures but makes broken API contracts and telemetry failures hard to diagnose.

## Security Lessons

- The plugin uses the host-provided OpenCode client for session reads and toast output; it does not introduce a server, shell execution, credential handling, or direct network endpoint (`token-tracker.js:103-189`, `token-tracker-realtime.js:8-146`). That keeps the attack surface comparatively small.
- The README installation instructions download executable plugin source directly from a moving `main` branch using `curl -sL` (`README.md:33-47`, `README.md:68-71`, `README.md:83-88`). A production-grade distribution should pin a release, verify provenance/integrity, or prefer the package registry rather than encouraging unpinned remote code installation.
- Provider/model IDs and finish reasons are interpolated into toast text (`token-tracker.js:169-185`). The implementation relies on the TUI toast renderer to treat the value as text; if a future renderer interprets markup, these fields should be escaped or passed through a structured text API.
- Silent catches avoid leaking errors into the UI, but they also suppress security-relevant diagnostics. A safer operational pattern would preserve redacted, opt-in diagnostics without displaying request contents or credentials.

## Testing Lessons

- The classic JavaScript path has unusually broad unit coverage for a small plugin: null/undefined responses, malformed shapes, token normalization, latency, model fallback, finish filtering, deduplication, child aggregation, failures, and toast formatting are all tested (`token-tracker.test.js:49-214`, `token-tracker.test.js:217-351`, `token-tracker.test.js:353-856`).
- Tests use Node’s built-in `node:test`, mock only the client surface needed by the plugin, and verify both helper return values and rendered toast bodies (`token-tracker.test.js:1-18`, `token-tracker.test.js:353-379`). This gives fast tests without requiring an OpenCode runtime.
- The repository’s test command passed 53 tests in this audit (`npm test`; package script at `package.json:9-12`). CI runs `npm ci` and `npm test` on Node 22 for pushes and pull requests (`.github/workflows/ci.yml:3-21`).
- There are no tests for `token-tracker-realtime.js` or `token-tracker.tsx`, no typecheck/build test for TSX, and no integration test against a real OpenCode TUI API. Those omissions leave the concurrency risk, hardcoded request label, dependency/runtime compatibility, and slot API contract unverified.

## Packaging and Release Lessons

- Package metadata is clear and minimal: ESM mode, Node >=18, MIT license, repository URL, keywords, and an explicit `files` allowlist (`package.json:1-21`). The allowlist includes source and documentation but excludes tests and CI configuration (`package.json:7`).
- The lockfile is valid lockfile version 3 but contains only the root package because runtime dependencies are not declared (`package-lock.json:1-15`). This matches the classic JavaScript entrypoint, but not the TUI source, which imports `@opentui/solid`, `@opencode-ai/plugin/tui`, `@opencode-ai/sdk/v2`, and `solid-js` (`token-tracker.tsx:17-20`). Consumers therefore need an external TSX-capable OpenCode environment and the package does not provide a reproducible typecheck/build path.
- CI publishes after tests only when the ref starts with a version tag, using npm’s public access and an `NPM_TOKEN` secret (`.github/workflows/ci.yml:23-38`). This is a useful basic release gate, but there is no explicit version/tag consistency check, provenance configuration, artifact inspection, or test of the published tarball.
- The README offers copy-to-plugin installation for each variant and clearly states restart and compatibility requirements (`README.md:31-55`, `README.md:106-110`). It does not document a package-manager installation flow despite the repository having npm publish metadata.

## Practical Takeaways

1. Prefer `session.idle` for post-request accounting and isolate plugin failures from the host event loop (`token-tracker.js:110-115`, `token-tracker.js:190-193`).
2. Normalize SDK response wrappers and optional numeric fields at one boundary, then test malformed and partial responses (`token-tracker.js:23-59`; `token-tracker.test.js:49-214`).
3. Key deduplication by session and message identity when aggregating repeated event snapshots; include child-session identity if subagents are part of the product model (`token-tracker.js:104-157`).
4. Treat polling timers as lifecycle resources, await or serialize asynchronous polls, and key state by session when concurrent sessions are possible (`token-tracker-realtime.js:8-16`, `token-tracker-realtime.js:92-117`).
5. Keep all shipped variants under the same contract, and add typecheck/integration coverage for TUI slot plugins before recommending them as the primary distribution (`token-tracker.tsx:17-20`, `token-tracker.tsx:105-115`).
