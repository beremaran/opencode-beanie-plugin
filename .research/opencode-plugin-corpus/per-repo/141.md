## OpenCode patterns

- The plugin follows the SDK entrypoint shape: `src/index.ts` exports a default `Plugin`, loads custom configuration, creates tools, and returns `tool`, `config`, and `event` hooks (`src/index.ts:1-10`, `src/index.ts:48-89`). This is a useful minimal integration surface for an OpenCode plugin.
- Agent registration is centralized in a literal registry with a derived union and type guard (`src/agents/index.ts:7-23`). The plugin merges its agents into host-resolved agents rather than replacing them, and copies each entry so other plugins' permissions and mutations survive safely (`src/index.ts:19-29`, `src/index.ts:69-71`).
- Tools are assembled through focused factories, with session, question, response, push-question, and brainstorm tools combined in one exported constructor (`src/tools/index.ts:13-20`). Tool definitions use `@opencode-ai/plugin/tool` schemas and return user-readable strings for success and failure (`src/tools/session.ts:1`, `src/tools/session.ts:107-145`).
- The orchestrator prompt explicitly documents the intended tool protocol, including separate state and browser session IDs and the prohibition on bypassing `create_brainstorm` (`src/agents/octto.ts:20-55`). This makes tool sequencing part of the agent contract, but it remains model-adherence dependent.
- Host lifecycle ownership is handled by wrapping `start_session`, extracting created session IDs, and stopping those sessions when OpenCode emits `session.deleted` (`src/index.ts:31-45`, `src/index.ts:73-85`). This is a strong pattern for cleaning plugin-owned resources without coupling session lifetime to process lifetime.
- The UI transport is a per-session Bun server bound to `127.0.0.1`, with `/` serving the bundle and `/ws` handling upgrades (`src/session/server.ts:116-142`). The session store supports blocking and non-blocking answer retrieval, timeouts, user-order retrieval, and explicit server shutdown (`src/session/sessions.ts:212-247`, `src/session/sessions.ts:250-300`, `src/session/sessions.ts:120-142`).

## Configuration and extensibility

- Configuration is schema-first: ports are constrained to integer `0..65535`, agent overrides constrain temperature and max steps, and fragment keys are restricted to known agents (`src/config/schema.ts:5-25`). `OCTTO_PORT` takes precedence over file configuration, with invalid environment values ignored (`src/config/loader.ts:20-38`).
- The loader handles partially invalid configuration by warning and salvaging valid top-level models and individual agent overrides (`src/config/loader.ts:62-99`, `src/config/loader.ts:115-128`). It applies top-level model first, then per-agent overrides, and clones agent objects before prompt mutation (`src/config/loader.ts:140-169`).
- Global fragments and project `.octto/fragments.json` are appended in that order and rendered as a `<user-instructions>` block (`src/hooks/fragment-injector.ts:22-46`, `src/hooks/fragment-injector.ts:49-67`, `src/hooks/fragment-injector.ts:118-133`). Unknown agent names produce nearest-name suggestions (`src/hooks/fragment-injector.ts:99-115`, `src/hooks/fragment-injector.ts:135-148`).

## Security and reliability lessons

- The local server has meaningful browser attack-surface defenses: it binds only to loopback (`src/session/server.ts:123-125`), rejects non-loopback `Host` values, and requires a matching loopback origin for WebSocket upgrades (`src/session/server.ts:20-37`, `src/session/server.ts:48-60`). Tests cover foreign origins, DNS-rebinding-style host mismatches, loopback binding, and no-origin clients (`tests/session/server.test.ts:139-177`).
- WebSocket input is parsed as `unknown` and validated with Valibot before reaching session state; malformed JSON and schema failures return structured errors rather than throwing through the socket handler (`src/session/server.ts:83-114`). Corresponding tests cover both failure classes (`tests/session/server.test.ts:25-103`).
- Persisted session IDs are constrained to alphanumeric, underscore, and hyphen characters before being joined into filenames, preventing traversal through the session identifier (`src/state/persistence.ts:59-67`). The tests explicitly exercise `../`, slashes, dots, and valid IDs (`tests/state/persistence.test.ts:107-145`).
- Project fragment files are parsed and schema-checked, but fragment contents are intentionally inserted into agent system prompts without escaping or trust separation (`src/hooks/fragment-injector.ts:22-29`, `src/hooks/fragment-injector.ts:49-66`). Treat project/global fragment files as privileged prompt-instruction sources, especially when repositories or configuration can be modified by untrusted contributors.
- Question configurations deliberately use loose objects and many `any()` fields to preserve type-specific payloads (`src/tools/factory.ts:19-58`, `src/tools/session.ts:68-105`). This is flexible for UI evolution, but shifts validation to the browser and downstream consumers. File/image answers carry base64-like content in memory (`src/session/types.ts:109-119`), so size, MIME, count, and retention limits should be enforced before accepting hostile or oversized payloads.
- Browser launch uses platform command arrays and waits for process exit, while suppressing stdout/stderr (`src/session/browser.ts:5-29`). This avoids shell interpolation, but silently hides launcher failures and does not verify that the opened browser is the intended one. The E2E notes document the operational requirement that `xdg-open` use the same Chrome profile as CDP (`e2e/README.md:67-75`).

## Testing lessons

- The repository combines focused unit tests, integration tests against a real Bun HTTP/WebSocket server, and a Docker E2E harness. The full-flow tests exercise pending, answered, timeout, user-order, blocking, and cleanup behavior (`tests/integration/full-flow.test.ts:17-145`).
- Configuration tests use temporary directories, restore warning spies, and cover defaults, precedence, invalid JSON, partial salvage, fragments, and environment-independent merges (`tests/config/loader-integration.test.ts:18-162`). Persistence tests likewise isolate filesystem state and clean it in `afterEach` (`tests/state/persistence.test.ts:10-21`).
- The E2E harness deliberately keeps the OpenCode runtime, plugin loading, Chromium, HTTP server, WebSocket round-trip, and UI real, while replacing only the model with a deterministic provider (`e2e/README.md:9-24`). A separate manual live tier addresses prompt-adherence failures that scripted tool calls cannot detect (`e2e/README.md:22-47`).
- CI runs frozen-lockfile installation, `bun run check`, and a build on every push/PR (`.github/workflows/ci.yml:8-30`). The check script combines Biome, ESLint, TypeScript, and Bun tests (`package.json:21-30`).
- Some test code undermines the repository's stated no-`any` rule: the plugin initialization fixture casts mock SDK objects and event payloads to `any` (`tests/index.test.ts:9-18`, `tests/index.test.ts:75-82`). WebSocket tests also use fixed sleeps (`tests/session/server.test.ts:39-45`, `tests/session/server.test.ts:80-84`) even though the project guidance prefers polling. These are test-harness maintainability risks, not production behavior defects.

## Packaging and documentation

- The package is ESM-only, exposes `dist/index.js` and declarations, and publishes only `dist` (`package.json:2-15`). Build bundles `src/index.ts` for Bun and emits declarations; `prepublishOnly` cleans, checks, and rebuilds (`package.json:17-30`).
- Release automation verifies quality and build before `npm publish --provenance --access public`, with npm trusted-publishing permissions (`.github/workflows/release.yml:9-16`, `.github/workflows/release.yml:32-42`).
- User installation is documented as adding `"octto"` to the OpenCode plugin array (`README.md:21-35`), while local development uses an explicit built absolute/local path in `.opencode/config.json` (`.opencode/config.json:1-3`). The E2E documentation records that absolute local plugin paths were required in practice and that the documented plugin directory did not load (`e2e/README.md:65-71`), an important packaging/distribution pitfall.
- Documentation drift is visible: `ARCHITECTURE.md` describes `src/session/manager.ts`, `context.ts`, a different agent model set, and design output under `thoughts/shared/designs/` (`ARCHITECTURE.md:27-35`, `ARCHITECTURE.md:62-70`, `ARCHITECTURE.md:223-227`), while the current tree uses `sessions.ts`, current agents use `openai/gpt-5.2-codex` (`src/agents/octto.ts:3-7`), and the README says `docs/plans/` (`README.md:91-99`). Generated or maintained architecture documentation should be checked as part of release review.

## Bottom line

Octto is a strong example of an OpenCode plugin that combines agent registration, tool factories, host lifecycle events, and a real local browser transport. The most reusable patterns are clone-before-merge agent configuration, schema validation at file/socket boundaries, loopback plus origin checks, explicit ownership cleanup, and a three-tier test strategy. The main risks are the trust model for prompt fragments, loose/large user payloads, hidden browser-launch failures, and stale architecture documentation that can mislead maintainers.
