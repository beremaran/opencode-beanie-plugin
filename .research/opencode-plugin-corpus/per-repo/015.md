# Repository 015: Context Analysis

## Identification and scope

- Manifest entry 15 is `Context Analysis`, URL `https://github.com/IgorWarzocha/Opencode-Context-Analysis-Plugin` (manifest.json:134-138).
- The inspected clone is `.research/opencode-plugin-corpus/repos/igorwarzocha--opencode-context-analysis-plugin/`.
- The clone contains `README.md`, `package.json`, `.opencode/command/context.md`, `.opencode/plugin/`, and `tests/`. There is no separate manifest-named subdirectory to inspect.

## OpenCode SDK and registration

- The entrypoint exports `ContextUsagePlugin` with the OpenCode `Plugin` type and imports the SDK `tool` helper ( `.opencode/plugin/context-usage.ts:1-2`).
- The plugin is an async factory receiving `{ client }` and returns a `tool` registration under the `context_usage` name (`context-usage.ts:76-80`). This is a minimal, direct SDK registration pattern.
- Tool arguments are declared with the SDK schema: optional `sessionID` and an integer `limitMessages` constrained to 1 through 10 (`context-usage.ts:79-85`).
- The command file is a Markdown command definition whose body explicitly calls `context_usage` without delegation, then asks for a bullet summary containing counts and percentages (`.opencode/command/context.md:1-9`). This couples a user-facing `/context` command to the registered tool.
- The README documents copying `.opencode` into a project or global OpenCode config and restarting OpenCode (`README.md:13-27`, `README.md:66-82`).

## Hooks, events, and context

- No event hook or lifecycle callback is implemented. The plugin returns only a `tool` registration (`context-usage.ts:76-118`).
- The tool gets the current session from `args.sessionID ?? context.sessionID` and fails if neither exists (`context-usage.ts:86-90`). This is a useful context fallback pattern for commands that can optionally target another session.
- Session data is fetched through `client.session.messages({ path: { id: sessionID } })`; the implementation accepts either `response.data` or the response itself (`context-usage.ts:90-95`).
- The source models message roles, system prompts, text, reasoning, and completed tool outputs locally (`context-usage.ts:13-45`, `181-314`). It aggregates tool output by tool name and limits displayed entries while retaining category totals (`context-usage.ts:155-174`, `268-290`).
- Actual assistant token telemetry, when present, is used to rescale locally counted prompt, assistant, and reasoning categories (`context-usage.ts:316-359`). This is a pragmatic correction for tokenizer approximation, but the code uses untyped `any` for token payloads (`context-usage.ts:23-24`, `316-345`).

## Tools and commands

- The only registered SDK tool is `context_usage` (`context-usage.ts:78-115`). It returns a human-readable visual summary rather than structured data (`context-usage.ts:515-610`).
- The command advertises `/context`, `/context detailed`, `/context short`, `/context verbose`, arbitrary verbosity text, `sessionID`, and `limitMessages` examples (`README.md:97-125`). In the implementation, only `sessionID` and `limitMessages` are actual tool arguments; the other modes are prompt text handled by the command layer (`context.md:5-9`, `context-usage.ts:82-110`).
- Output includes category bars, total tokens, top contributors, counts, and percentages (`context-usage.ts:529-572`). The output uses Unicode bar characters and bullets (`context-usage.ts:548`, `566`), which may be less portable in terminals or log consumers.

## Auth and providers

- There is no authentication flow, credential storage, provider login, or provider API call. The plugin reads existing session messages through the OpenCode client and counts locally (`context-usage.ts:90-104`, `430-513`).
- Provider handling is tokenizer selection rather than auth. OpenAI, Azure, and OpenCode provider IDs are treated as OpenAI-compatible (`tokenizer-registry.mjs:7`, `77-86`). Other providers can resolve through explicit provider defaults, model aliases, or inferred defaults (`tokenizer-registry.mjs:88-105`, `247-272`).
- Provider and model aliases are committed in `.opencode/plugin/tokenizer-aliases.json:1-37`, including Anthropic, Meta, Mistral, DeepSeek, and Google defaults.
- Resolution normalizes model/provider keys, checks direct aliases and common suffix/base forms, then uses a Levenshtein similarity suggestion threshold of 0.5 (`tokenizer-registry.mjs:20-63`, `110-145`, `350-357`). Unknown sessions produce `TokenizerResolutionError` with observed models and providers (`tokenizer-registry.mjs:11-17`, `57-63`).

## State and processes

- Runtime state is process-local: tokenizer registry loading is cached in a module-level promise, and tiktoken/transformer instances are cached in maps (`tokenizer-registry.mjs:9-10`, `66-75`; `context-usage.ts:71-74`).
- Tokenizer packages are dynamically imported from `.opencode/plugin/vendor/node_modules` by reading each package's `package.json` and selecting `module`, `main`, or `index.js` (`context-usage.ts:10-11`, `472-513`).
- Tokenizer resolution loads metadata concurrently and caches the resulting registry (`tokenizer-registry.mjs:66-70`, `189-207`).
- There are no background processes, subprocesses, persistent files, databases, network services, or cross-session state in the implementation. Transformer loading may cause the tokenizer library to fetch model data through the library, but the plugin itself does not expose a download or process manager (`context-usage.ts:479-489`).

## Configuration

- Configuration is file/layout based rather than `opencode.json` based: the plugin is discovered under `.opencode/plugin/context-usage.ts`, and the command under `.opencode/command/context.md` (`README.md:156-168`).
- `package.json` declares ESM mode and only `@opencode-ai/plugin` as a dependency (`package.json:1-8`). The tokenizer libraries are intentionally expected under a separate vendor prefix, as documented by the README (`README.md:134-154`).
- The command has no configurable front matter beyond its description (`context.md:1-3`). Runtime limits are hard-coded (`ENTRY_LIMIT = 3`) with a user override capped at 10 (`context-usage.ts:10`, `82-85`, `106-111`).

## Errors and security

- Missing session identity is rejected with a direct error (`context-usage.ts:87-89`); empty sessions return a non-error status string (`context-usage.ts:93-95`).
- Known tokenizer resolution failures are converted into an actionable text response with models/providers observed (`context-usage.ts:97-105`, `592-610`). Other errors are rethrown (`context-usage.ts:101-105`).
- Tokenizer failures generally fall back to an approximate `ceil(content.length / 4)` count (`context-usage.ts:430-455`), and failed transformer loads are cached as `null` (`context-usage.ts:479-489`). This improves resilience but can hide persistent tokenizer/configuration errors.
- The plugin processes session content locally, and the README explicitly claims no data is sent to external services (`README.md:140-145`). It does read arbitrary session messages and completed tool outputs, so installing it globally grants the plugin access to all sessions exposed through the OpenCode client.
- The implementation concatenates all completed output for each tool (`context-usage.ts:268-289`) without a byte/character cap. Very large tool output can increase memory use and tokenizer work.
- The source includes raw error/install guidance referring to `./context-command/install.sh` and `./install.sh` (`context-usage.ts:505-507`, `605-607`), but no install script is present in the inspected clone. This is a concrete operational pitfall.

## Tests, package, and installation

- The repository has one Node test file, `tests/tokenizer-resolution.test.mjs`, covering vendored OpenAI metadata, provider defaults, fuzzy alias suggestions, and descriptive failure errors (`tests/tokenizer-resolution.test.mjs:1-11`, `54-106`).
- Tests create and delete fixture files under `.opencode/plugin/vendor/node_modules` before each test (`tokenizer-resolution.test.mjs:13-52`). This is effective isolation for registry behavior but mutates the clone if run and does not test the main tool execution or formatting path.
- There is no test script in `package.json` (`package.json:1-9`), and the README instructs manual installation/testing in a project rather than providing an automated test command (`README.md:170-177`). The test uses Node's built-in test runner (`tokenizer-resolution.test.mjs:1-2`) despite the project README emphasizing direct TypeScript execution in OpenCode (`README.md:170-172`).
- The README's quick start says "2 Steps" but lists three steps (`README.md:13-27`). It recommends copying `.opencode`, while the package metadata does not declare the tokenizer dependencies that the runtime dynamically imports (`README.md:136-154`; `package.json:6-8`).
- The documented global destination is `~/.config/opencode/.opencode/` (`README.md:75-89`), which is potentially confusing because the command text says to copy `.opencode` into `~/.config/opencode/`; users should verify OpenCode's actual global discovery layout.

## Reusable lessons and pitfalls

- A focused OpenCode plugin can be distributed as `.opencode/plugin/*.ts` plus `.opencode/command/*.md`, without a build step (`README.md:156-177`).
- Register a narrow tool and let the command provide presentation instructions; this keeps SDK execution separate from user-facing prompt formatting (`context-usage.ts:76-118`; `context.md:5-9`).
- Use the tool execution context as the default session target and expose an optional explicit session ID (`context-usage.ts:82-90`).
- For model-dependent processing, use a layered resolver: vendored metadata, committed aliases/provider defaults, normalization, fuzzy suggestions, and a typed error carrying diagnostic details (`tokenizer-registry.mjs:20-63`, `189-207`, `275-306`).
- Keep expensive tokenizer modules and instances cached, but provide an explicit cache reset for tests (`context-usage.ts:71-74`; `tokenizer-registry.mjs:66-75`; `tests/tokenizer-resolution.test.mjs:49-52`).
- Reconcile measured provider telemetry with locally categorized counts when exact message-level tokenization is unavailable (`context-usage.ts:316-419`). Document that the resulting category allocation is scaled/estimated rather than independently authoritative.
- Before shipping, remove stale install-script references, add a package test script, test the exported plugin/tool end to end, cap aggregated tool output, and validate the documented global installation path. These gaps are evidenced by the absent script references (`context-usage.ts:505-507`, `605-607`), minimal package metadata (`package.json:1-9`), and narrow test scope (`tests/tokenizer-resolution.test.mjs:54-106`).
