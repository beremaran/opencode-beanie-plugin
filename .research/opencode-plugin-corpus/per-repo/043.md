## OpenCode patterns

- Keep the published plugin entrypoint small and typed. `packages/omo-opencode/src/index.ts` creates one `PluginModule`, exports its server as `omoPlugin`, default-exports the module, and exposes only selected config/error types (`packages/omo-opencode/src/index.ts:1-20`). The actual entry is therefore easy for OpenCode to load while implementation remains behind a factory.
- Treat initialization as an ordered pipeline. `createPluginModule()` installs compatibility shims, establishes config context, logs/migrates, validates config, checks duplicate plugins, injects server auth, initializes optional runtime services, then creates managers, tools, hooks, and the OpenCode interface (`packages/omo-opencode/src/testing/create-plugin-module.ts:159-240`, `:250-326`). This makes startup side effects and feature gates auditable.
- Use dependency injection at the production factory boundary to test startup without global module mocks. `PluginModuleDeps` enumerates startup dependencies and `createPluginModule(overrides)` merges test overrides with defaults (`packages/omo-opencode/src/testing/create-plugin-module.ts:56-122`, `:159-162`). The tests exercise locale, TUI self-healing, runtime skill startup failure, disposal, duplicate-plugin early exit, and migration behavior through that seam (`packages/omo-opencode/src/testing/create-plugin-module.test.ts:147-164`, `:167-224`, `:227-296`, `:322-359`).
- Keep OpenCode API coupling in one adapter layer. `createPluginInterface()` returns the `tool`, chat, command, transform, config, event, and tool execution hooks, while delegates receive context, managers, hooks, and filtered tools (`packages/omo-opencode/src/plugin-interface.ts:20-36`, `:39-108`). This is a useful boundary for extracting harness-neutral core packages without spreading OpenCode types everywhere.
- Compose optional behavior from configuration rather than registering every feature unconditionally. Startup builds `disabledHooks`, derives `isHookEnabled`, honors `experimental.safe_hook_creation`, and passes the resulting controls into hook composition (`packages/omo-opencode/src/testing/create-plugin-module.ts:276-317`). Team mode, tmux checks, OpenClaw, runtime security skills, and TUI setup are independently gated (`:240-279`).
- Route all internal session prompts through a gate. `promptAsyncInDirectory()` requires a session id, adds the target directory, dispatches through `dispatchInternalPrompt`, treats ambiguous post-dispatch failures as accepted, and rejects duplicate or skipped dispatches (`packages/omo-opencode/src/shared/session-route.ts:52-83`). The regression test proves a missing id never calls raw `promptAsync` and an immediate second prompt is deferred (`packages/omo-opencode/src/shared/session-route.test.ts:7-65`).

## Security and reliability lessons

- Restrict configuration-controlled environment expansion to an explicit allowlist. The Claude-compatible MCP loader documents `${VAR}` expansion as string replacement only, with `mcp_env_allowlist` restricting variables and secret patterns redacted from logs (`packages/omo-opencode/src/features/claude-code-mcp-loader/AGENTS.md:25-33`). The config merger preserves the allowlist from the user override rather than recursively merging project values (`packages/omo-opencode/src/plugin-config/config-merger.ts:4-24`).
- Defend recursive config merges against prototype pollution and validate hostile input. The test supplies a `__proto__` override, checks that prototypes remain unmodified, then loads an unsafe project file and expects invalid config without pollution (`packages/omo-opencode/src/plugin-config.prototype-pollution.test.ts:26-58`). This is a concrete pattern for testing both the merge primitive and the complete config-loading path.
- Avoid prompt races as a shared-state write problem. The route test checks that only one immediate dispatch occurs and that the directory query is preserved (`packages/omo-opencode/src/shared/session-route.test.ts:35-65`); the implementation's reservation/gate is initialized through the shared utility (`packages/omo-opencode/src/shared/prompt-async-gate.ts:1-28`). A plugin that injects continuation messages should test live, duplicate, and ambiguous-failure cases explicitly.
- Fail soft for optional runtime services, but make degradation visible. If the runtime security skill source cannot start, initialization warns and continues without its URL; the test asserts managers/tools/interface still initialize and the warning includes the cause (`packages/omo-opencode/src/testing/create-plugin-module.ts:240-249`; `packages/omo-opencode/src/testing/create-plugin-module.test.ts:250-277`). Disposal also stops the source (`create-plugin-module.test.ts:280-296`).
- Detect duplicate installations before wiring managers and hooks. On duplicate detection the plugin warns and returns `{}` before auth injection or feature construction (`packages/omo-opencode/src/testing/create-plugin-module.ts:207-216`). The test pins that no managers, tools, hooks, or interface are created (`packages/omo-opencode/src/testing/create-plugin-module.test.ts:322-359`).
- Bound subprocess-based security checks. The dependency audit uses direct `Bun.spawnSync` with piped output and a 60-second timeout, then asserts no timeout and a successful exit (`packages/omo-opencode/src/dependency-security.test.ts:62-94`). It also locks `picomatch` to the minimum patched version and checks that first-party code does not import `effect` directly (`:96-136`).
- Treat telemetry as a privacy and control-surface concern. The README says anonymous telemetry is enabled by default, is limited to once per UTC day per machine, hashes the installation identifier, does not create PostHog profiles, and documents config/environment opt-outs (`README.md:180-189`). A plugin adopting this pattern should make defaults and opt-out behavior prominent, test them, and avoid raw host identifiers.

## Testing lessons and gaps

- Use Bun's preload to enforce consistent test setup. `bunfig.toml` preloads `test-setup.ts` and explicitly excludes generated distributions, the web package, vendored Node packages, Codex plugin trees, and upstream skill assets (`bunfig.toml:1-6`). The exclusions are useful, but they mean `bun test` is not a complete test of every shipped subtree.
- Test startup behavior at the real production factory, not only isolated helpers. The startup suite verifies configured locale, TUI entry creation and suppression, optional skill source behavior, cleanup, duplicate suppression, and migration toasts (`packages/omo-opencode/src/testing/create-plugin-module.test.ts:147-224`, `:227-359`).
- Test installation in isolated fixture environments. `postinstall.test.ts` creates a temporary HOME/cache, runs the actual postinstall script, and verifies exactly one rename notice, exit status zero, and repeat-run idempotence (`postinstall.test.ts:20-36`, `:52-85`).
- Preserve structured given/when/then tests for concurrency and failure classification. The prompt route tests cover missing identifiers, duplicate reservation, directory routing, and ambiguous EOF acceptance (`packages/omo-opencode/src/shared/session-route.test.ts:12-92`).
- Remaining verification gap: this review did not execute `bun test`, typecheck, build, or a live OpenCode smoke test because dependencies were not installed in the clone. The repository's own guidance requires real OpenCode QA for OpenCode-connected changes, so release confidence still requires those environment-dependent gates.

## Packaging and distribution lessons

- Make the package boundary explicit. Root metadata declares ESM, `main`/types, a large workspace set, five CLI aliases, conditional exports, and a curated `files` allowlist (`package.json:1-107`). The allowlist ships the built plugin, launchers, postinstall, selected skills/commands, schemas, and selected MCP/Codex artifacts rather than the whole monorepo.
- Keep build and publication sequencing in scripts. `package.json` defines build, schema, binary, typecheck, test, `prepack`, `prepare`, `postinstall`, and `prepublishOnly` stages (`package.json:109-142`). The multi-package build makes publication reproducibility dependent on keeping workspace registration, generated artifacts, and `files` entries synchronized.
- Make platform selection and version skew diagnosable. `postinstall.mjs` detects platform/libc candidates, verifies a launcher resolves, compares the platform package version with the main package, invalidates matching OpenCode caches, and emits repair guidance (`postinstall.mjs:108-191`). It deliberately warns rather than failing installation when a platform package is missing (`:192-196`), which improves install survivability but can defer failure until CLI use.
- Test the soft-failure tradeoff. The postinstall tests require a zero exit even when platform resolution is unavailable (`postinstall.test.ts:64-73`), so consumers get a successful package install but a clear warning. This should be paired with a doctor/diagnostic command, as this project does in its documented CLI surface (`README.md:124-162`).
- Support staged cross-harness reuse without pretending all surfaces are identical. The README distinguishes the full OpenCode Ultimate edition from Codex Light and Senpi editions, including different installation commands and shipped capabilities (`README.md:112-141`, `:224-247`). The package's workspace and `files` declarations reflect that split (`package.json:8-38`, `:47-98`).

## Bottom line

The strongest reusable pattern is the combination of a minimal OpenCode entrypoint, a dependency-injected startup factory, a single adapter layer for OpenCode hooks, and explicit gates around internal prompts, environment expansion, duplicate installation, and optional services. The principal operational pitfall is scale: a curated multi-workspace package can ship stale or missing generated/platform artifacts unless build, `files`, postinstall, and fixture tests stay synchronized. Static and unit evidence is substantial, but this clone was not executable in the present environment and still needs dependency installation plus live OpenCode QA before treating the implementation as verified.
