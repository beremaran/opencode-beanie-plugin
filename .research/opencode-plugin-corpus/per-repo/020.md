## OpenCode integration patterns

- The entrypoint exports both a named and default `Plugin` implementation (`src/index.ts:483-608`). It receives `{ client, directory }`, captures startup state, and returns an object with `event`, `permission.ask`, and `tool.execute.before` handlers (`src/index.ts:483-510`, `src/index.ts:589-603`). This is a compact pattern for combining event-bus handling with hook-specific behavior.
- Client gating avoids duplicate desktop notifications by treating an unset or `cli` `OPENCODE_CLIENT` as CLI and returning an empty plugin for other clients unless `enableOnDesktop` is enabled (`src/index.ts:27-29`, `src/index.ts:486-490`). The README documents the same default and opt-in behavior (`README.md:169-170`).
- Configuration is loaded on every event through `getConfig`, rather than once at startup (`src/index.ts:492-493`, `src/index.ts:510-512`). This makes edits to the user config effective without restarting OpenCode, at the cost of repeated synchronous file reads.
- Project context comes from the plugin `directory`; by default only `basename(directory)` is exposed, with an explicit `showFullPath` opt-in (`src/index.ts:492-494`; `README.md:164-166`). This is a useful privacy-oriented default for notification text.
- Completion is derived from `session.idle`, delayed by 350 ms for non-CLI clients, and then classified using `client.session.get` as top-level versus child session (`src/index.ts:25`, `src/index.ts:375-417`, `src/index.ts:419-436`). CLI mode bypasses the timer because the process may exit before a delayed notification fires (`src/index.ts:545-557`).
- Event ordering is guarded with per-session sequence numbers, pending timer cancellation, busy/error suppression, and five-minute cleanup (`src/index.ts:31-35`, `src/index.ts:91-121`, `src/index.ts:290-317`). Permission event plus hook duplication is separately deduplicated globally and per session for one second (`src/permission-dedupe.ts:1-20`), with tests covering both paths (`src/permission-dedupe.test.ts:9-24`).
- The plugin uses the SDK client only when needed: it queries messages to calculate elapsed time and sessions to resolve title/child status (`src/index.ts:326-373`, `src/index.ts:447-480`). API failures degrade to `null`/top-level defaults instead of breaking event handling (`src/index.ts:348-351`, `src/index.ts:370-372`).
- Subagent handling is explicit: lifecycle events cache child session IDs, completion emits `subagent_complete`, and user-message notifications exclude cached subagents (`src/index.ts:513-536`, `src/index.ts:579-587`). Agent names are extracted defensively from a strict title suffix and non-string values return an empty string (`src/index.ts:138-145`; `src/index.agent-name.test.ts:5-29`).

## Configuration and packaging lessons

- The configuration model separates global defaults from per-event controls for sound, notification, command, and terminal bell (`src/config.ts:20-32`, `src/config.ts:50-120`). Boolean event shorthand is supported while preserving the default bell setting (`src/config.ts:221-243`), and the tests verify this compatibility behavior (`src/config.test.ts:121-146`).
- Missing config files and malformed JSON fall back to the complete default object (`src/config.ts:262-270`, `src/config.ts:392-394`). This is resilient for a user-facing plugin, but silently hides configuration errors and gives no diagnostic path.
- Numeric settings are normalized: timeout requires a positive number, minimum duration requires a finite nonnegative number, and volumes are clamped to `0..1` (`src/config.ts:300-329`, `src/config.ts:246-260`). The tests cover defaults, invalid JSON, negative duration, and placeholder interpolation (`src/config.test.ts:46-99`, `src/config.test.ts:280-343`).
- Config location is overrideable with `OPENCODE_NOTIFIER_CONFIG_PATH`; persistent turn state is written beside that config (`src/config.ts:209-219`). Turn loading and saving catch all errors (`src/index.ts:65-80`), which prevents notification failures but can make persistence failures invisible.
- The package is ESM, publishes `dist`, bundled `sounds`, and `logos`, and builds `src/index.ts` with Bun while externalizing `node-notifier` (`package.json:7-9`, `package.json:18-27`). It declares `@opencode-ai/plugin` as a peer dependency while using it as a dev dependency (`package.json:40-48`), a sensible way to avoid forcing one SDK version on consumers.
- `prepublishOnly` builds the distribution and separate `typecheck`/`test` scripts provide basic release gates (`package.json:23-27`). Strict TypeScript is enabled, declarations are emitted, and test files are excluded from the declaration build (`tsconfig.json:3-15`).
- README installation is minimal: add the published package to OpenCode’s `plugin` array and restart (`README.md:5-15`). Platform prerequisites and limitations are stated, including Linux notification/sound binaries and Windows WAV/full-path constraints (`README.md:28-49`).

## Security and reliability pitfalls

- Custom commands are intentionally powerful: configured `path` and `args` can execute arbitrary local programs, and the README demonstrates `/bin/bash -c` with a log append (`README.md:302-335`). This should be treated as trusted-user configuration; a safer guide should warn against copying untrusted config and should prefer a fixed executable plus separate arguments.
- Command execution avoids a shell by using `spawn(command, args)` with `stdio: "ignore"`, detached execution, and `unref()` (`src/command.ts:14-29`). This prevents shell metacharacters in substituted values from becoming shell syntax, but it does not sandbox the configured executable or prevent argument/data exfiltration.
- The macOS notification path passes title and message as `osascript` argv values rather than embedding them in the AppleScript (`src/notify.ts:231-237`, `src/notify.ts:284-287`). Tests explicitly protect this boundary with shell-like input (`src/notify.test.ts:46-60`). Ghostty OSC 9 fields strip semicolons and control characters before writing escape sequences (`src/notify.ts:32-49`), also covered by tests (`src/notify.test.ts:8-22`).
- Some focus operations still construct shell command strings with interpolated window IDs/search terms (`src/focus.ts:392-401`, `src/focus.ts:419-426`, `src/focus.ts:525-528`). These values are normally locally discovered identifiers, but using `execFile` argument arrays consistently would reduce injection risk and quoting bugs. The changelog specifically records safer argument-array execution for tmux/PowerShell paths (`CHANGELOG.md:104-107`, `CHANGELOG.md:145-148`), showing this was an active hardening concern.
- Focus detection deliberately fails open: exceptions return `false`, meaning “not focused” and therefore notification delivery continues (`src/focus.ts:356-389`; `README.md:432-438`). This is the right reliability default for alerts, but users should understand that unsupported compositors may produce notifications even when the terminal is visible.
- Notification and sound channels debounce by message/event for one second (`src/notify.ts:6-7`, `src/notify.ts:250-255`; `src/sound.ts:9-14`, `src/sound.ts:131-140`). This controls spam but uses process-global maps; it is not a durable or cross-process dedupe mechanism.
- Notification and sound failures are intentionally swallowed so one channel does not prevent another (`src/sound.ts:151-167`, `src/notify.ts:107-115`). Operationally this is robust, but troubleshooting is difficult without optional debug logging.

## Testing evidence and gaps

- The suite has focused unit tests for config defaults/merging, event shorthand, interpolation, CLI detection, agent-name parsing, permission dedupe, bell TTY behavior, Ghostty sanitization, notification parsing, AppleScript argument boundaries, focus detection, and Windows PowerShell integration (`src/config.test.ts:46-350`, `src/index.cli.test.ts:4-28`, `src/notify.test.ts:8-60`, `src/focus.test.ts:4-315`).
- Tests reset mutable state where needed (`src/permission-dedupe.test.ts:4-7`, `src/bell.test.ts:4-7`) and use platform guards for Windows-only integration (`src/focus.test.ts:183-228`). This is a good pattern for cross-platform plugins whose process APIs are difficult to mock.
- There is little end-to-end coverage of the actual exported plugin lifecycle: no test verifies the event routing from OpenCode events through `NotifierPlugin`, session API calls, timers, and emitted side effects. The tests mostly target pure helpers.
- There is no visible test for custom command spawning, command token substitution, state-file persistence, sound-player fallback ordering, package contents, or `bun build` output. These are high-value release tests because they cross process and packaging boundaries.
- Verification in this clone could not complete because dependencies were not installed. `bun test` reported 47 passing, 27 failing, and 3 errors across 74 tests; the failures/errors were caused by missing `is-wsl` and `node-notifier` imports. `bun run typecheck` reported the same three missing-module errors. These results are environment availability failures, not evidence of behavioral regressions.

## Reusable takeaways

1. Register both SDK event handlers and hook handlers in one returned plugin object, and keep client gating explicit.
2. Treat idle/completion events as race-prone: cancel timers, sequence asynchronous work, classify sessions through the client API, and prune state.
3. Make notification payloads data, not shell/script source: use process argument arrays and sanitize terminal escape payloads.
4. Keep high-frequency defaults quiet, expose per-event overrides, and test config merge semantics rather than only happy-path parsing.
5. Package runtime assets explicitly and run the build during publish; verify the packed artifact, not only TypeScript compilation.
6. Prefer fail-open behavior for alert suppression, but document platform support and expose diagnostics for swallowed subprocess/configuration failures.
