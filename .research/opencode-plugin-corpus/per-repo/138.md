## Repository shape and OpenCode integration

- This is a TypeScript ESM package whose runtime entry is `dist/index.js`, with a separate `opencode-supermemory` CLI binary at `dist/cli.js` (`package.json:2-10`). The package advertises itself as an OpenCode plugin and declares `chat.message`, `permission.ask`, and `event` hooks (`package.json:38-44`).
- The exported plugin captures the working directory, derives repository tags, keeps per-plugin session state, and logs whether credentials are configured (`src/index.ts:66-74`). It returns hook implementations for chat messages, permission checks, and events (`src/index.ts:113-114`, `src/index.ts:568-587`).
- `chat.message` filters text parts, skips empty messages, adds a synthetic “remember this” nudge when configured keywords match, and adds a synthetic reasoned-recall directive (`src/index.ts:114-163`). First-message handling can inject profile, personal search results, project memories, and update notices into the prompt (`src/index.ts:165-251`).
- The plugin exposes one structured `supermemory` tool with enum-constrained modes (`add`, `search`, `profile`, `list`, `forget`, `help`), memory types, scopes, and optional limits (`src/index.ts:258-290`). It validates required arguments and returns JSON success/error objects instead of throwing to the agent (`src/index.ts:291-303`, `src/index.ts:349-363`, `src/index.ts:398-455`).
- Recall searches are auto-approved only when the permission payload identifies Supermemory and `mode: "search"` (`src/index.ts:48-64`, `src/index.ts:568-578`). This is a useful narrow permission exception rather than globally allowing a tool.

## Configuration and data flow

- Configuration is read from `~/.config/opencode/supermemory.jsonc` or `.json`; environment `SUPERMEMORY_API_KEY` takes precedence over file credentials and browser credentials (`src/config.ts:7-12`, `src/config.ts:100-123`). The README documents the same location and precedence (`README.md:241-292`).
- Base URLs are restricted to absolute `http:` or `https:` URLs, with query/hash/trailing-slash normalization (`src/config.ts:125-151`). This supports local/self-hosted endpoints while preventing arbitrary protocols.
- Numeric settings are validated: compaction thresholds must be `(0, 1]`, capture cadence must be a non-negative integer, and invalid regex additions are discarded (`src/config.ts:68-97`, `src/config.ts:167-179`). Existing config changes defaults to eager recall and a three-turn capture cadence, while new installs default both off (`src/config.ts:172-179`, `src/config.ts:190-200`).
- The API client lazily constructs the SDK client, passes the API key and normalized base URL, sets an `x-sm-source` header, and enables server-side LLM filtering (`src/services/client.ts:151-165`). Search calls use a 30-second timeout, hybrid search, similarity threshold, and bounded result count (`src/services/client.ts:21-23`, `src/services/client.ts:169-209`).
- Repository identity is based on a normalized `origin` remote, hashed to a short stable suffix; absent Git identity falls back to the real project path (`src/services/tags.ts:111-140`, `src/services/tags.ts:252-260`; `README.md:294-301`). Equivalent HTTPS and SSH remotes are explicitly tested (`src/services/tags.test.ts:4-12`).
- Personal/project separation is represented by `sm_scope` metadata while using a unified canonical container, with legacy read tags retained for migration (`src/services/client.ts:82-90`, `src/services/client.ts:225-246`; `README.md:222-239`).

## Strong patterns and reusable lessons

### Privacy and security

- Private data is redacted with a case-insensitive `<private>...</private>` filter; content that becomes only `[REDACTED]` is refused for storage (`src/services/privacy.ts:1-12`). The `add` tool applies this before sending content and rejects fully private input (`src/index.ts:349-363`).
- Automatic capture excludes synthetic and ignored parts, rejects fully private turns, and redacts embedded private spans (`src/services/capture.ts:68-83`, `src/services/capture.ts:119-149`). Its tests verify that injected recall is not recaptured and that both fully private and partially private turns are handled (`src/services/capture.test.ts:91-117`).
- Credentials are stored under a dedicated home-directory directory created with mode `0700`; the credentials file is written with mode `0600` (`src/services/auth.ts:9-10`, `src/services/auth.ts:45-54`). Browser callback state uses a random token and rejects mismatches with HTTP 403 (`src/services/auth.ts:68-99`).
- Browser opening uses `execFile` argument arrays, not shell interpolation, and refuses non-HTTP(S) URLs (`src/services/openUrl.ts:1-15`).
- Status output masks API keys, identifies their source, and explicitly warns that full keys must not be printed (`src/cli.ts:512-533`, `src/cli.ts:573-595`; `src/cli.ts:209-224`).

### Lifecycle, reliability, and testing

- Capture is event-driven: snapshots refresh on `session.idle`, completed batches flush on `session.deleted`, and active sessions flush on `server.instance.disposed` (`src/services/capture.ts:326-377`).
- Per-session promise chaining serializes capture work and prevents duplicate concurrent lifecycle processing (`src/services/capture.ts:310-324`). Stable SHA-256 capture IDs make retries/idempotent lifecycle events safe and avoid putting session IDs in the remote custom ID (`src/services/capture.ts:197-206`; `src/services/capture.test.ts:73-89`).
- Tests cover cadence/remainder batching, stable ID limits, privacy/synthetic filtering, event-driven cadence, session-end flushing, and equivalent Git remote normalization (`src/services/capture.test.ts:58-210`, `src/services/tags.test.ts:4-19`).
- Compaction is guarded by a 50,000-token floor, configurable context threshold, per-session cooldown, and in-progress set (`src/services/compaction.ts:13-21`, `src/services/compaction.ts:332-376`). It obtains model limits from OpenCode providers at plugin startup and falls back to 200,000 tokens (`src/index.ts:76-101`, `src/services/compaction.ts:357-373`).

### Packaging and distribution

- The build emits bundled Node-targeted plugin and CLI JavaScript plus TypeScript declarations; typecheck and test scripts regenerate the runtime version first (`package.json:11-16`). Strict TypeScript settings include `noUncheckedIndexedAccess` and `noImplicitOverride` (`tsconfig.json:21-34`).
- The npm package is intentionally limited to `dist`, reducing accidental publication of source/config files (`package.json:46-49`).
- `src/version.ts` is generated from `package.json`, and the release script updates both together before commit/tag creation (`scripts/sync-version.mjs:3-10`, `scripts/sync-version.mjs:20-45`; `scripts/release.sh:41-49`).
- Release CI checks whether the package version is already published, runs typecheck/build, and publishes with npm provenance and least-privilege `contents: read` plus `id-token: write` permissions (`.github/workflows/release.yml:10-16`, `.github/workflows/release.yml:35-59`).

## Pitfalls and risks

- The plugin injects imperative model-facing text such as “MUST use the `supermemory` tool” and compaction instructions to preserve exact user requests (`src/index.ts:24-32`; `src/services/compaction.ts:69-99`). This is effective orchestration, but it is prompt-level control rather than enforcement; untrusted memory content or a malicious user can influence model behavior unless retrieved content is treated as data and tool execution is independently validated.
- The privacy boundary depends on users placing secrets in the exact `<private>` tag format. The client also sends the configured filter prompt to the remote service and captures completed conversations automatically when enabled (`src/services/client.ts:161-164`; `src/services/capture.ts:250-267`). Deployments should make consent, retention, remote processing, and failure behavior explicit.
- Compaction directly reads and writes OpenCode’s private on-disk message/part stores (`src/services/compaction.ts:10-12`, `src/services/compaction.ts:102-130`, `src/services/compaction.ts:220-234`). This is tightly coupled to storage layout and can break across OpenCode versions; the repository does not include compaction-specific tests in the inspected test set.
- The compaction hook writes synthetic messages before calling `session.summarize`, then schedules a detached `promptAsync` continuation after 500 ms (`src/services/compaction.ts:281-299`, `src/services/compaction.ts:394-437`). The delay and direct file mutation are timing-sensitive; failures in the detached continuation are swallowed (`src/services/compaction.ts:423-437`).
- The installer edits global OpenCode config and may rewrite JSONC using a regex over the `plugin` array (`src/cli.ts:256-308`). It also mutates Oh My OpenCode configuration to disable a competing compaction hook (`src/cli.ts:347-393`, `src/cli.ts:449-471`). Backups, atomic writes, schema-aware parsing, and explicit dry-run support would reduce operational risk.
- Documentation says the login command starts a local server on port 19877, but the implementation binds an ephemeral port with `server.listen(0, "127.0.0.1")` (`src/cli.ts:170-187`, `src/services/auth.ts:156-167`). The callback URL is correctly passed to the auth service, but the documented fixed-port behavior is stale or misleading.
- The auth callback accepts an API key from query parameters and persists it after only checking the `sm_` prefix (`src/services/auth.ts:101-122`). State protects the flow, but production hardening should also consider callback referrer/log exposure and stronger server-side validation.
- Logging is synchronous and writes arbitrary serialized data to `~/.opencode-supermemory.log` at module initialization and on every log call (`src/services/logger.ts:5-14`). Error objects or future metadata additions could leak sensitive values or block the plugin on filesystem I/O.
- The repository’s test command could not run fully in the audited checkout because dependencies were not installed: `bun test` reported `Cannot find package 'supermemory'` from `src/services/client.ts`; two tests passed before the import failure. CI does install dependencies, but a lockfile-only or dependency-availability check would make this failure mode clearer.

## Overall assessment

`opencode-supermemory` demonstrates a mature OpenCode plugin shape: typed hook registration, a constrained tool interface, scoped memory identity, bounded/time-limited network calls, privacy filtering, idempotent lifecycle capture, and a provenance-aware npm release path. Its main engineering debt is coupling compaction to OpenCode’s filesystem internals and relying on model directives for behavior that should be backed by explicit policy and tests. The most valuable patterns to reuse are stable repository identity, per-session serialized lifecycle work, deterministic capture IDs, strict credential file permissions, and tests that prove synthetic/private content never leaves the process.
