## Architecture And SDK Patterns

- The plugin uses a type-only `Plugin` import from `@opencode-ai/plugin` and exports both named and default plugin functions (`src/index.ts:1`, `535-537`, `767`). The factory receives the SDK `client` and returns an event handler object, or `{}` when disabled (`535-551`, `723-764`).
- Lifecycle integration is event-based: `message.part.updated` triggers an immediate keyword title and `session.idle` triggers AI refinement (`731-761`). Session operations use the SDK client for `session.get`, `session.update`, `session.messages`, `session.create`, `session.prompt`, and `session.delete` (`554-610`, `410-475`). There are no tools, commands, custom hooks, permissions, or context mutation APIs.
- AI generation creates a temporary OpenCode session, prompts it with bounded user/assistant excerpts, extracts the first text line, sanitizes it, and deletes the temporary session in cleanup (`376-479`). This is a useful process-boundary pattern: reuse the host SDK rather than spawning a CLI or managing a separate API client.
- Provider/model wiring is host-client based rather than auth based. It honors explicit `OPENCODE_AUTOTITLE_MODEL`, optionally filters by `OPENCODE_AUTOTITLE_PROVIDER`, prefers connected providers, then selects the first model matching ordered `fast`, `flash`, `haiku`, `mini`, etc. patterns (`157-235`, `27-40`). It does not implement authentication or credentials.

## State, Configuration, And Errors

- Runtime state is in-memory `Set`s for keyword-titled, AI-titled, and pending sessions plus a lazily cached model (`20-25`, `544-549`, `682-695`). The pending set prevents duplicate AI work, and `finally` clears it (`644-720`). The sets are never bounded or persisted, so a long-lived process can accumulate session IDs.
- Configuration is environment-only: model, provider, maximum length, disable flag, and stderr/file debug logging (`73-95`, `134-152`). Relative debug paths resolve against `process.cwd()` and parent directories are created (`101-115`). The README documents the same variables and zero-config defaults (`README.md:134-152`).
- SDK failures generally degrade gracefully: title reads/messages return undefined/null, update failures return false, provider discovery falls back, and AI failures retain the keyword title (`554-610`, `671-715`). Fire-and-forget event work attaches `.catch` handlers (`746-760`). Logging also forwards to `client.app.log` without awaiting it (`138-147`).
- Dynamic SDK responses are repeatedly cast to `any` and support multiple response shapes (`175-185`, `410-440`, `571-589`). This makes the plugin tolerant of SDK response drift but weakens compile-time guarantees.

## Strengths And Reusable Lessons

- Two-phase UX is strong: a local, immediate fallback followed by asynchronous refinement, with custom titles protected (`README.md:17-24`, `src/index.ts:612-641`, `643-715`). Design plugins so useful behavior remains available when model calls fail.
- The title safety boundary is explicit: default/timestamp titles and the plugin's own emoji titles may change, while other titles are treated as user-owned (`238-267`, `619-627`).
- Pure text/model/event helpers are exported and tested independently (`519-533`; `src/index.test.ts:17-368`, `452-567`). Tests cover parsing variants, configuration, model preference, and fallback behavior.
- The prompt imposes a hard character limit, asks for title-only output, and caps input excerpts (`391-402`, `385-389`). Sanitization removes punctuation and normalizes whitespace (`270-276`).
- Packaging is simple and reproducible: ESM, strict TypeScript, declarations/source maps, `dist/index.js` entrypoint, and an explicit published-file list (`package.json:1-15`, `48-61`; `tsconfig.json:1-19`). CI type-checks, tests, and builds on Node 18/20/22 (`.github/workflows/ci.yml:9-36`).

## Pitfalls And Anti-Patterns

- The `message.part.updated` path does not verify the part's role. It explicitly says the role is unavailable and triggers on the first text part of a new session (`731-749`), so an assistant/system text part could become the keyword title before the real user message.
- User-message handling is launched without awaiting and has no in-flight guard (`740-749`); repeated update events can race before `keywordTitledSessions` is updated. The AI path has a guard, but phase 1 does not.
- “Cheapest” is inferred from model-name regexes and array/provider order, not pricing or capability metadata (`27-40`, `42-70`, `207-227`). This should be labeled heuristic and validated against actual provider availability.
- The configured maximum length subtracts `2` for the emoji prefix (`630`), but JavaScript string length counts the emoji as two UTF-16 code units; the final title can still exceed the documented maximum (`270-276`, `630-637`).
- Cleanup is attempted both on successful extraction and again in `finally` (`454-476`). It is harmless only if deletion is idempotent; a single centralized cleanup path would be clearer.
- The plugin logs the first provider's structure and user/assistant excerpts in debug mode (`189-192`, `676-680`). Debug logs can expose project or conversation content, and arbitrary relative/absolute log paths are accepted (`101-115`). Document the sensitivity and avoid logging provider payloads by default.
- The install path pipes a remote shell script to `bash`, clones the default branch, runs package installation, and copies generated JavaScript into the global plugin directory (`README.md:39-56`; `install.sh:63-92`). This is convenient but lacks checksum/signature/version pinning and should be treated as a supply-chain risk.
- Verification in this checkout found a runner/dependency gap: direct `bun test` ran 88 tests with 78 passing and 10 failures because `vi.resetModules` is unavailable in Bun's test runner (`src/index.test.ts:370-380`), while the documented `bun run test`/`npm test` scripts could not find the `vitest` executable and `bun run typecheck` could not resolve Vitest types. CI explicitly uses npm/Vitest (`package.json:8-15`; `.github/workflows/ci.yml:26-36`), so install/runner parity should be checked before relying on local verification.

## Installation, Versioning, And Testing

- Recommended installation builds from a shallow clone and copies `dist/index.js` to `~/.config/opencode/plugins/opencode-autotitle.js`; OpenCode is documented as loading plugin files directly (`README.md:45-57`; `docs/install.md:34-57`).
- npm metadata is version `0.1.3`, Node `>=18`, ESM, with `@opencode-ai/plugin` as a dev dependency and Bun as a peer dependency (`package.json:1-15`, `43-61`). Publishing is release/workflow-dispatch driven and runs Bun build followed by public npm publish with OIDC permissions (`.github/workflows/publish.yml:1-44`).
- Tests are broad unit tests for pure behavior but do not exercise the plugin factory/event flow with a mocked SDK, concurrent event delivery, cleanup, provider failure, or custom-title races (`src/index.test.ts:17-567`). Those are the highest-value missing integration cases.

## Development-Bible Guidance

Use a typed plugin factory returning narrowly scoped event handlers; keep pure parsing and policy functions independently testable; provide a fast local fallback before network/model work; preserve explicit user-owned state; cache expensive discovery with an in-flight guard; and make cleanup/error paths idempotent. For production plugins, verify event roles, bound in-memory state, use actual capability/cost metadata for routing, avoid `any` at SDK boundaries, test the real supported runner, and pin or verify installation artifacts.
