## OpenCode Integration Patterns

- The plugin uses the `chat.message` lifecycle hook and mutates the hook's `output.parts` in place. It filters for text parts, sanitizes each non-empty `.text`, and leaves all other parts untouched ([src/index.ts:37-59](../repos/errhythm--opencode-log-sanitizer/src/index.ts)). This is the important integration choice: the README explains that `tui.prompt.append` is only a notification and that `chat.message` is the mutation point before forwarding to the LLM ([README.md:41-46](../repos/errhythm--opencode-log-sanitizer/README.md)).
- Configuration is passed through the loader's plugin options, merged once at initialization with defaults, and then reused on the hot path ([src/index.ts:18-27](../repos/errhythm--opencode-log-sanitizer/src/index.ts); [src/sanitizer.ts:16-23,36-39](../repos/errhythm--opencode-log-sanitizer/src/sanitizer.ts)). The exposed controls include threshold, detector flags, debug enablement, and debug-log path ([src/sanitizer.ts:1-14](../repos/errhythm--opencode-log-sanitizer/src/sanitizer.ts)).
- The sanitizer pipeline protects explicit `<no-redact>...</no-redact>` blocks with placeholders, applies detectors in a fixed order, then restores the protected blocks ([README.md:48-57](../repos/errhythm--opencode-log-sanitizer/README.md); [src/sanitizer.ts:203-245](../repos/errhythm--opencode-log-sanitizer/src/sanitizer.ts)). This ordering prevents the bypass content from being processed by later detectors and makes the behavior explainable.
- Fast prechecks avoid running detector regexes when their identifying marker is absent: JWT processing requires `eyJ`, bcrypt processing requires `$2`, and base64 processing requires `+` or `/` ([src/sanitizer.ts:215-234](../repos/errhythm--opencode-log-sanitizer/src/sanitizer.ts)). The base64 detector caches dynamically generated regexes by threshold ([src/sanitizer.ts:48-61](../repos/errhythm--opencode-log-sanitizer/src/sanitizer.ts)).
- Long quoted strings use an explicit linear scanner rather than a broad regex. It handles escapes, leaves unterminated strings unchanged, and preserves long HTML/JSX `class` and `className` attributes ([src/sanitizer.ts:120-187](../repos/errhythm--opencode-log-sanitizer/src/sanitizer.ts)). The README documents the rationale and the class-attribute exception ([README.md:50-57](../repos/errhythm--opencode-log-sanitizer/README.md)).
- The hook reports aggregate counts and detector-specific counts but does not log original message text. Debug output is sent both to `client.app.log` and JSONL on disk, with failures from either sink isolated using `Promise.allSettled` ([src/index.ts:53-77](../repos/errhythm--opencode-log-sanitizer/src/index.ts); [src/logger.ts:40-74](../repos/errhythm--opencode-log-sanitizer/src/logger.ts)).

## Pitfalls and Consistency Risks

- The `<no-redact>` feature is an intentional security bypass: its contents are restored verbatim regardless of length or content ([README.md:110-123](../repos/errhythm--opencode-log-sanitizer/README.md)). That is useful for debugging, but it means the plugin cannot promise that every secret is removed; users must treat the tag as an explicit opt-out and avoid putting untrusted prompt text inside it.
- Placeholder names are predictable (`__NR0__`, `__NR1__`, ...), and restoration replaces every matching placeholder token in the processed text ([src/sanitizer.ts:64-86](../repos/errhythm--opencode-log-sanitizer/src/sanitizer.ts)). A user-supplied literal placeholder can therefore be replaced with protected block content, or collide with a generated placeholder. Random or otherwise collision-resistant sentinels, or structured span scanning, would remove this ambiguity.
- The base64 heuristic deliberately requires `+` or `/`, so URL-safe base64, base64 values containing only alphanumerics, and some long encoded secrets will not be detected ([src/sanitizer.ts:48-50](../repos/errhythm--opencode-log-sanitizer/src/sanitizer.ts); [README.md:155-159](../repos/errhythm--opencode-log-sanitizer/README.md)). This is a documented false-positive tradeoff, not comprehensive secret detection.
- The JWT rule requires an `eyJ` prefix and three segments of at least ten characters, while bcrypt matching is format-based and does not identify arbitrary password hashes ([src/sanitizer.ts:41-50](../repos/errhythm--opencode-log-sanitizer/src/sanitizer.ts)). Consumers should frame this as noise reduction rather than a complete credential scrubber.
- Documentation and executable metadata drift. The README says `bun test` runs 38 cases and presents only four user-facing options ([README.md:81-107,182-191](../repos/errhythm--opencode-log-sanitizer/README.md)), while `SanitizerConfig` also supports debug settings ([src/sanitizer.ts:10-14](../repos/errhythm--opencode-log-sanitizer/src/sanitizer.ts)); `CONTRIBUTING.md` says the suite has 32 tests ([CONTRIBUTING.md:30-37](../repos/errhythm--opencode-log-sanitizer/CONTRIBUTING.md)). The package script uses Vitest, whereas the README's `bun run lint` depends on a mise task rather than a package script ([package.json:21-25](../repos/errhythm--opencode-log-sanitizer/package.json); [.mise/tasks/lint:1-3](../repos/errhythm--opencode-log-sanitizer/.mise/tasks/lint)).

## Security and Operational Lessons

- Sanitizing at `chat.message` provides a meaningful privacy boundary because the mutation happens before the stored/sent user message is consumed by the model ([README.md:41-46](../repos/errhythm--opencode-log-sanitizer/README.md); [src/index.ts:37-57](../repos/errhythm--opencode-log-sanitizer/src/index.ts)). The e2e test verifies the stored user message no longer contains the JWT, bcrypt hash, or base64 prefix ([src/e2e.test.ts:82-102](../repos/errhythm--opencode-log-sanitizer/src/e2e.test.ts)).
- Debug logging is disabled by default and writes only event metadata, lengths, counts, and detector names in the tested path ([src/sanitizer.ts:16-23](../repos/errhythm--opencode-log-sanitizer/src/sanitizer.ts); [src/index.ts:60-77](../repos/errhythm--opencode-log-sanitizer/src/index.ts); [src/index.test.ts:48-75](../repos/errhythm--opencode-log-sanitizer/src/index.test.ts)). When enabled, however, the plugin creates parent directories and appends to a user-configurable path ([src/logger.ts:34-43](../repos/errhythm--opencode-log-sanitizer/src/logger.ts)). That path should be trusted and permissioned like any other local diagnostic log.
- The logger sends the same structured metadata to OpenCode's application logger and the local file ([src/logger.ts:55-73](../repos/errhythm--opencode-log-sanitizer/src/logger.ts)). `Promise.allSettled` prevents observability failures from breaking message sanitization, but it also intentionally suppresses sink errors; operational monitoring must not assume that a successful hook means debug logging succeeded.
- The plugin has no network or shell execution in its runtime source; its side effects are part mutation and optional local logging ([src/index.ts:18-79](../repos/errhythm--opencode-log-sanitizer/src/index.ts); [src/logger.ts:1-43](../repos/errhythm--opencode-log-sanitizer/src/logger.ts)). This narrow capability surface is a good default for a prompt-processing plugin.

## Testing Lessons

- Unit tests cover each detector's positive and negative cases, boundary behavior, escaped quotes, malformed input, large-input timing, feature flags, no-redact preservation, and realistic multi-field JSON ([src/sanitizer.test.ts:53-350](../repos/errhythm--opencode-log-sanitizer/src/sanitizer.test.ts)). The explicit performance test and the linear scanner are a useful pairing for avoiding regex denial-of-service regressions ([src/sanitizer.ts:120-125](../repos/errhythm--opencode-log-sanitizer/src/sanitizer.ts); [src/sanitizer.test.ts:204-223](../repos/errhythm--opencode-log-sanitizer/src/sanitizer.test.ts)).
- Plugin-level tests verify loader configuration is honored, only enabled detectors act, per-detector counts are returned, and debug logging reaches both sinks ([src/index.test.ts:28-92](../repos/errhythm--opencode-log-sanitizer/src/index.test.ts)). These tests model the OpenCode input/output shape with a small fake `PluginInput`, keeping most lifecycle behavior fast and deterministic.
- The e2e suite builds the entrypoint, starts an OpenCode SDK server with the file plugin URI, submits `noReply` prompts, and inspects persisted user messages ([src/e2e.test.ts:35-80](../repos/errhythm--opencode-log-sanitizer/src/e2e.test.ts)). It also checks that text surrounding a long base64 blob survives ([src/e2e.test.ts:104-126](../repos/errhythm--opencode-log-sanitizer/src/e2e.test.ts)). This is the strongest evidence that the chosen hook affects actual OpenCode message persistence, not merely an isolated helper.
- Missing or under-tested seams remain: placeholder collision, nested/malformed no-redact blocks, URL-safe base64, debug-log permission failures, and behavior when `output.parts` contains unusual mutable/non-text shapes. The repository's contribution guide gives the right extension rule: every new detector should have positive, negative, and edge-case tests, and long-string regexes should avoid `.*`/`.+` ([CONTRIBUTING.md:42-55](../repos/errhythm--opencode-log-sanitizer/CONTRIBUTING.md)).

## Bottom Line

This repository demonstrates a focused OpenCode pattern: intercept `chat.message`, mutate only text parts, apply a deterministic redaction pipeline, and verify both pure behavior and persisted OpenCode messages. Its strongest lessons are the use of a linear scanner for untrusted long text, explicit detector tradeoffs, and e2e validation at the actual hook boundary. The main risks are that `<no-redact>` deliberately defeats the privacy guarantee, predictable placeholders can collide with user text, detection is heuristic rather than comprehensive, and package/docs metadata has drifted, including a fileset reference to a missing `src/version.ts`.
