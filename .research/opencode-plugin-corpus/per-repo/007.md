## What It Does

This is a Bun/TypeScript OpenCode plugin for launching and tracking shell background
processes. The README documents session-scoped and “global” processes, tags, filtering,
output inspection, and termination (`README.md:67-155`). The actual state is an in-memory
`Map` owned by a module-level manager (`src/index.ts:4-6`; `src/BackgroundProcessManager.ts:4-5`).

## OpenCode Integration Patterns

- **SDK/imports and registration:** Imports `Plugin` and `tool` from
  `@opencode-ai/plugin` and exports an async value typed as `Plugin`
  (`src/index.ts:1-6`). The returned object registers tools under `tool` and an `event`
  callback (`src/index.ts:71-94`). Package metadata pins SDK version `1.0.85`
  (`package.json:21-23`).
- **Tools:** Four schema-driven tools are defined inline: `createBackgroundProcess`,
  `getBackgroundProcess`, `listBackgroundProcesss`, and `killTasks`
  (`src/index.ts:7-69`). Arguments use `tool.schema` primitives, optional fields, arrays,
  and booleans. Tool execution receives `ctx.sessionID` and passes it into task creation
  (`src/index.ts:16-24`).
- **Lifecycle/events:** The event hook handles `session.deleted`; it takes the deleted
  session's `info.parentID` and calls `cleanupSessionTasks` when present
  (`src/index.ts:79-90`). No startup/shutdown hook or process signal handler is wired;
  `clearAllTasks` exists but is commented out at the call site (`src/index.ts:92`).
- **Context mutation:** There is no context mutation, prompt injection, message hook,
  provider hook, or auth integration. Context is used only to associate a created task
  with `ctx.sessionID` (`src/index.ts:16-24`).
- **Process boundary:** `execa(input.command, { shell: true, stdout: 'pipe', stderr: 'pipe' })`
  starts the command asynchronously (`src/BackgroundProcessManager.ts:7-18`). stdout and
  stderr data events are recorded, and promise completion changes status to completed or
  failed (`src/BackgroundProcessManager.ts:33-49`). Termination uses `process.kill(pid)`
  (`src/BackgroundProcessManager.ts:114-126`).
- **State/concurrency:** Tasks are mutable objects with a union status, timestamps, pid,
  session, tags, error, and output (`src/BackgroundProcess.ts:1-14`). A `Map` provides
  synchronous lookup/filtering; filtering matches any requested tag
  (`src/BackgroundProcessManager.ts:76-85`, `137-148`). Serialization limits detail output
  to the last 100 lines and list output to the last 10 entries
  (`src/BackgroundProcessManager.ts:60-73`, `88-103`).
- **Configuration:** Installation is a single plugin entry in the user's OpenCode JSON
  config (`README.md:7-15`). There are no plugin-specific config options or environment
  variables. Toolchain configuration pins Bun/npm through mise (`mise.toml:1-9`).
- **Errors:** Missing task IDs throw (`src/BackgroundProcessManager.ts:54-58`). Process
  failures normalize `unknown` errors and add an `[ERROR]` output record
  (`src/BackgroundProcess.ts:40-44`). Kill failures are recorded but not returned as a
  structured error (`src/BackgroundProcessManager.ts:121-125`).
- **Security:** The shell option intentionally permits shell syntax but means tool input is
  arbitrary command execution (`src/BackgroundProcessManager.ts:14-18`). There is no
  allowlist, confirmation, privilege boundary, timeout, resource limit, or output redaction.

## Strengths

- Minimal, readable integration boundary: each tool maps directly to a manager method and
  the session ID comes from OpenCode context rather than user input (`src/index.ts:7-24`).
- Explicit lifecycle model and normalized error capture make status/output useful to an
  agent (`src/BackgroundProcess.ts:4-12`, `40-49`).
- Filtering, tags, bounded serialized output, and session cleanup are practical primitives
  for concurrent agent workflows (`src/BackgroundProcessManager.ts:76-103`, `151-166`).
- Strict TypeScript, lint/test/build CI, pinned toolchain metadata, and automated release/
  provenance publishing are strong packaging practices (`tsconfig.json:2-12`,
  `.github/workflows/pr.yml:25-37`, `.github/workflows/publish.yml:16-46`).

## Pitfalls and Anti-Patterns

- **Documented persistence is not implemented:** “global” only skips session cleanup; all
  state and process handles live in the plugin process's memory, so restart persistence is
  absent (`README.md:95-99`, `src/BackgroundProcessManager.ts:151-165`).
- **Cleanup lifecycle is incomplete:** the README claims all processes are killed on close,
  but the close cleanup call is commented and there is no shutdown handler
  (`README.md:150-155`, `src/index.ts:79-94`).
- **Unsafe process model:** `shell: true` executes arbitrary interpolated shell input; killing
  only the recorded pid may leave child processes, and no timeout or resource control exists
  (`src/BackgroundProcessManager.ts:14-18`, `114-120`).
- **State races:** a killed subprocess can later resolve/reject and overwrite `cancelled`
  with `completed`/`failed`; `killTasks` can also cancel already-finished tasks
  (`src/BackgroundProcessManager.ts:43-49`, `106-148`).
- **Output handling is approximate:** each data chunk is treated as a line and retained
  without a storage cap; only response serialization slices it, despite README wording that
  output captures the last 100 lines (`src/BackgroundProcessManager.ts:33-41`, `60-73`).
- **Schema quality and naming need tightening:** status arguments are unconstrained strings,
  and exported/tool identifiers contain typos (`BackgroundProcesssPlugin`,
  `listBackgroundProcesss`) (`src/index.ts:6`, `37`, `75`).
- **Session deletion assumption is fragile:** cleanup uses `properties.info.parentID`, which
  may not be the deleted session's own ID (`src/index.ts:83-90`); this path has no test.
- **Repository metadata drifts from the clone identity:** the git remote is `zenobi-us`, while
  `package.json` advertises `airtonix` (`package.json:7-10`). Consumers and release tooling
  should use one canonical repository URL.

## Reusable Development-Bible Lessons

1. Type the plugin export, use SDK schemas at the tool boundary, and derive session identity
   from OpenCode context; keep operational logic in a separate manager
   (`src/index.ts:1-24`).
2. For background work, model explicit states, timestamps, IDs, bounded result views, and
   normalized unknown errors (`src/BackgroundProcess.ts:4-12`, `40-44`).
3. Treat process ownership as a lifecycle contract: define startup recovery, session deletion,
   application shutdown, child-tree termination, cancellation races, and restart persistence
   before advertising global processes.
4. Avoid `shell: true` unless shell semantics are essential and the trust boundary is explicit;
   otherwise pass an executable and argv separately, and add timeout/resource/security policy.
5. Test the plugin boundary and real lifecycle behavior in addition to mocked manager unit
   tests: registration, event payloads, filtering, output chunking/caps, cancellation races,
   subprocess trees, and restart/cleanup semantics.
6. Keep packaging reproducible: strict types, CI build/test/lint gates, explicit published
   files, conventional release automation, and provenance-aware publishing are reusable
   patterns (`package.json:11-20`, `.github/workflows/pr.yml:32-37`).
