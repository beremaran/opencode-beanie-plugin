# Repository 143: opencode-firecrawl

## Scope and identity

- Manifest index 143 resolves to `firecrawl/opencode-firecrawl`, with clone and analysis path `.research/opencode-plugin-corpus/repos/firecrawl--opencode-firecrawl` (`repo-map.json:2167-2178`).
- The repository describes itself as an OpenCode plugin that exposes Firecrawl web scraping, crawling, search, mapping, and agent capabilities through the Firecrawl CLI (`README.md:1-3`, `README.md:38-48`).

## OpenCode patterns

- The entrypoint exports both a named and default `Plugin`, using the package's `Plugin` type (`index.ts:1`, `index.ts:7`, `index.ts:32`). This is a minimal plugin surface with no command or tool implementation of its own.
- The `config` hook initializes missing instruction and skill-path collections before appending repository-relative assets (`index.ts:9-21`). Resolving paths from `import.meta.url` via `fileURLToPath` and `dirname` makes the packaged plugin locate its own `skills` directory independently of the process working directory (`index.ts:2-5`, `index.ts:16-21`).
- The plugin uses `@ts-expect-error` specifically because the `skills` configuration fields were not present in the installed OpenCode types (`index.ts:11-14`, `index.ts:20`). This is a useful migration pattern for a newly introduced host API, but it also means type checking cannot validate those fields until the host types catch up.
- The `shell.env` hook copies `FIRECRAWL_API_KEY` from the plugin process environment into shell command output environment (`index.ts:24-27`). This is a concise way to make credentials available to skill-invoked CLI commands without embedding them in instructions.

## Skill and configuration design

- The package registers an install rule as an instruction and exposes the whole `skills` directory as a skill path (`index.ts:16-21`). The package explicitly includes both `index.ts` and `skills` in its published files (`package.json:7-10`), so the runtime-relative paths have corresponding packaging support.
- The primary skill uses frontmatter for a name and description, then gives concrete CLI workflows and options (`skills/firecrawl-cli/SKILL.md:1-18`, `skills/firecrawl-cli/SKILL.md:100-211`). It documents output-to-file conventions under `.firecrawl/` to reduce context flooding (`skills/firecrawl-cli/SKILL.md:59-98`).
- The skill includes operational guidance for status checks, authentication, output formats, URL quoting, and parallel jobs (`skills/firecrawl-cli/SKILL.md:24-47`, `skills/firecrawl-cli/SKILL.md:213-232`, `skills/firecrawl-cli/SKILL.md:269-289`). These examples make the intended agent behavior concrete and reusable.
- The install rule separates installation, verification, authentication, error handling, command-not-found, and permission troubleshooting (`skills/firecrawl-cli/rules/install.md:7-92`). It also contains a Codex-specific command that differs from the preceding browser-login command (`skills/firecrawl-cli/rules/install.md:30-36`, `skills/firecrawl-cli/rules/install.md:94-96`), so platform-specific instructions should be verified against the actual CLI.

## Security and reliability pitfalls

- Forwarding `FIRECRAWL_API_KEY` to shell commands makes the secret available to every shell action in the relevant OpenCode execution context, not only Firecrawl invocations (`index.ts:24-27`). The design should be treated as a broad capability boundary: avoid logging command environments, constrain which commands receive the variable if the host allows it, and document the exposure model.
- The skill tells the agent to use Firecrawl for “any” internet task and to replace built-in web tools with “no exceptions” (`skills/firecrawl-cli/SKILL.md:6-17`, `skills/firecrawl-cli/SKILL.md:20-22`). That is a strong policy override, not merely a capability hint. It can cause unnecessary paid requests, reduce fallback availability, and route sensitive URLs or research through an external service.
- The documented commands accept arbitrary URLs and write generated paths under `.firecrawl/` (`skills/firecrawl-cli/SKILL.md:61-72`, `skills/firecrawl-cli/SKILL.md:98`). URL quoting is called out, but output-name construction based on query or URL examples still needs careful sanitization when an agent derives filenames. The repository does not implement validation or sandboxing itself.
- Installation depends on a globally installed, unpinned `firecrawl-cli` (`README.md:16-20`, `skills/firecrawl-cli/rules/install.md:9-13`). This creates version drift and a supply-chain/runtime availability dependency outside the plugin package. The package lock pins only development dependencies, not the CLI runtime (`package-lock.json:7-25`).
- Authentication instructions encourage automatically opening a browser and, after failure, asking for or interpolating an API key into a command (`skills/firecrawl-cli/rules/install.md:28-67`). This is operationally convenient but requires a trusted interactive environment and care to prevent keys from appearing in logs, shell history, or agent transcripts.

## Testing and quality

- There is no test directory, test script, or runtime test dependency. The only script is `check`, which runs TypeScript without emitting (`package.json:31-37`). Consequently, config hook behavior, path resolution after packaging, environment propagation, and skill discovery are not covered by automated tests.
- TypeScript checking is strict and targets Node ESM (`tsconfig.json:1-11`), which provides a useful static baseline for the entrypoint. `skipLibCheck` reduces dependency declaration checking, and the skill fields are explicitly exempted with `@ts-expect-error` (`tsconfig.json:5-8`, `index.ts:11-14`).
- The plugin mutates `input.instructions` and `input.skills.paths` with `push` (`index.ts:9-21`). If OpenCode invokes `config` more than once for the same input, duplicate instruction and skill paths could result; an idempotence test or membership check would make this behavior safer.
- The README documents installation, authentication, capabilities, links, and license, but does not document the `check` command, supported OpenCode version, CLI version compatibility, or test status (`README.md:5-58`).

## Packaging and maintenance lessons

- `type: "module"`, `main: "index.ts"`, and the explicit `files` allowlist form a compact package definition for a source-distributed OpenCode plugin (`package.json:2-10`). The allowlist is important here because the entrypoint references files relative to its installed location.
- Repository metadata is present for npm discovery and provenance, including keywords, repository, homepage, author, and ISC license (`package.json:11-30`). A lockfile records resolved development package versions and integrity hashes (`package-lock.json:17-40`).
- `.gitignore` excludes generated Firecrawl results, dependencies, build output, and TypeScript build metadata (`.gitignore:1-4`), matching the documented `.firecrawl/` output convention (`README.md:48`, `skills/firecrawl-cli/SKILL.md:59-61`).
- The minimal implementation is easy to audit, but its real behavior is mostly delegated to prose and a separately installed CLI. Maintenance therefore depends on keeping the skill syntax, authentication commands, CLI flags, and OpenCode skill/config APIs synchronized.

## Evidence-backed takeaways

1. Prefer package-relative asset resolution and publish those assets explicitly when a plugin is primarily a skill bundle (`index.ts:2-5`, `index.ts:16-21`; `package.json:7-10`).
2. Keep external credentials out of instructions, but treat shell environment injection as broad access and test/document its scope (`index.ts:24-27`).
3. Use detailed skill examples for operational workflows, output management, quoting, and rate/concurrency constraints (`skills/firecrawl-cli/SKILL.md:24-47`, `skills/firecrawl-cli/SKILL.md:59-98`, `skills/firecrawl-cli/SKILL.md:269-289`).
4. Add tests for config idempotence, packaged asset discovery, and secret propagation; this repository currently has only static checking and no tests (`package.json:31-37`).
5. Pin or otherwise compatibility-check external CLIs where the plugin has no implementation-level fallback (`README.md:16-20`; `package-lock.json:7-25`).
