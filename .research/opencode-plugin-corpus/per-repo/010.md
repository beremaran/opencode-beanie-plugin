## Hooks, events, and context

- The server composition root returns `tool`, `config`, `command.execute.before`, and `experimental.chat.system.transform` surfaces (`repos/zanzythebar--brhp/src/composition/create-server-plugin.ts:50-84`, `repos/zanzythebar--brhp/src/composition/create-server-plugin.ts:85-216`).

- `command.execute.before` ignores other commands, parses arguments, replaces output parts with user-facing usage errors for invalid input, resolves the current project path, and routes status/history/inspect/plan/resume (`repos/zanzythebar--brhp/src/composition/create-server-plugin.ts:85-117`, `repos/zanzythebar--brhp/src/composition/create-server-plugin.ts:118-195`). - The system transform resolves a session-aware worktree when possible, loads the instruction inventory and active plan, builds a prompt section, and appends it only when non-empty (`repos/zanzythebar--brhp/src/composition/create-server-plugin.ts:196-215`).
- Tool execution carries `context.sessionID`, `context.directory`, and `context.worktree` into project-path resolution, and passes `sessionID` plus `worktreePath` into runtime operations (`repos/zanzythebar--brhp/src/composition/create-planner-tools.ts:8-15`, `repos/zanzythebar--brhp/src/composition/create-planner-tools.ts:20-47`).
- Path resolution prefers client/session-derived project data, then runtime candidates and plugin paths; it normalizes candidates and avoids selecting a filesystem root when a concrete directory exists (`repos/zanzythebar--brhp/src/composition/resolve-project-worktree-path.ts:74-132`). Failed SDK lookups are intentionally treated as unavailable and fall back (`repos/zanzythebar--brhp/src/composition/resolve-project-worktree-path.ts:139-210`).
- The TUI registers a `sidebar_content` slot at order 300 and a command-palette refresh action. It registers disposal to close the runtime owner and unregister both registrations (`repos/zanzythebar--brhp/src/composition/create-tui-plugin.tsx:20-86`).

## Tools and commands

- Four LLM tools are registered with `@opencode-ai/plugin/tool`: `brhp_get_active_plan`, `brhp_decompose_node`, `brhp_validate_active_scope`, and `brhp_complete_leaf` (`repos/zanzythebar--brhp/src/composition/create-planner-tools.ts:1-18`, `repos/zanzythebar--brhp/src/composition/create-planner-tools.ts:158-192`).
- Tool schemas validate non-empty identifiers/text, child arrays and categories, and validation clause kinds/statuses. Each tool emits structured metadata before executing and returns pretty-printed JSON (`repos/zanzythebar--brhp/src/composition/create-planner-tools.ts:17-47`, `repos/zanzythebar--brhp/src/composition/create-planner-tools.ts:50-104`, `repos/zanzythebar--brhp/src/composition/create-planner-tools.ts:106-155`).
- The documented operator surface is deliberately narrow: `/brhp`, `/brhp status`, `/brhp history`, `/brhp inspect`, `/brhp plan <problem statement>`, and `/brhp resume <session id>` (`repos/zanzythebar--brhp/docs/operator-contract.md:7-20`). History is bounded to 25 events; inspect bounds frontier selections to 5 and several other projections to 10 (`repos/zanzythebar--brhp/docs/operator-contract.md:36-47`).
- Slash commands mutate only through `plan` and `resume`; planner tools expose narrowly scoped decomposition, validation, and leaf completion mutations. The architecture document records this boundary explicitly (`repos/zanzythebar--brhp/docs/architecture.md:90-104`).

## State, persistence, and processes

- Runtime construction is worktree-scoped: it opens a planning database, wraps it in a libSQL session store, injects a clock/UUID generator, and closes the database after each server operation (`repos/zanzythebar--brhp/src/composition/create-planner-runtime.ts:20-57`).
- The server uses short-lived runtime access per operation, whereas the TUI uses a longer-lived owner (`repos/zanzythebar--brhp/docs/architecture.md:58-63`). The owner deduplicates concurrent initialization, retries after failed initialization, and guarantees one close during disposal (`repos/zanzythebar--brhp/src/composition/create-planner-runtime-owner.ts:23-68`, `repos/zanzythebar--brhp/src/composition/create-planner-runtime-owner.ts:70-120`).
- Planner context binds state to both `worktreePath` and `opencodeSessionId`; create seeds instruction IDs and extracted instruction invariants, resume activates by session id, and mutations reload persisted state after applying changes (`repos/zanzythebar--brhp/src/application/services/planner-runtime.ts:40-85`, `repos/zanzythebar--brhp/src/application/services/planner-runtime.ts:110-160`, `repos/zanzythebar--brhp/src/application/services/planner-runtime.ts:163-249`).
- The README documents local persistence at `.opencode/brhp/brhp.db`, global/project instruction directories, and project config at `.opencode/brhp/config.yaml` (`repos/zanzythebar--brhp/README.md:38-53`).
- No auth/provider routing, background worker, subprocess execution, network client, or external model call was found in the inspected package/source. The operator contract instead lists recursive agents, a plugin scheduler, provider/model routing, and automatic code/action spawning as deferred work (`repos/zanzythebar--brhp/docs/operator-contract.md:97-113`).

## Configuration and instruction handling

- Configuration is YAML at `.opencode/brhp/config.yaml`; missing, empty, null, or non-object content becomes `{}`, while schema failures throw a path-specific error (`repos/zanzythebar--brhp/src/application/use-cases/load-planner-config.ts:7-42`). The server's initial config load catches failures and falls back to defaults (`repos/zanzythebar--brhp/src/composition/create-server-plugin.ts:219-227`).
- Zod strictly permits optional `temperature` from `0.001` to `1` and integer `maxDepth` from `1` to `10`; unknown keys are rejected (`repos/zanzythebar--brhp/src/domain/planning/planner-config.ts:3-23`). The example config documents defaults of `0.35` and `5` (`repos/zanzythebar--brhp/.opencode/brhp/config.example.yaml:1-13`).
- Instruction discovery uses `OPENCODE_CONFIG_DIR`, then `XDG_CONFIG_HOME/opencode`, then `~/.config/opencode`, plus the project `.opencode/brhp/instructions` directory (`repos/zanzythebar--brhp/src/application/use-cases/load-instruction-inventory.ts:60-75`). It recursively loads `.md`/`.mdc`, sorts files, merges global before project instructions, and records read/parse/disabled/empty failures instead of aborting the inventory (`repos/zanzythebar--brhp/src/application/use-cases/load-instruction-inventory.ts:20-57`, `repos/zanzythebar--brhp/src/application/use-cases/load-instruction-inventory.ts:78-168`).
- The bundled instruction file teaches the intended tool order: read the active plan before mutations, decompose one node at a time, validate after decomposition, and resolve blocking findings before continuing (`repos/zanzythebar--brhp/.opencode/brhp/instructions/planning-with-brhp.md:13-35`).

## Errors and security-relevant behavior

- Invalid slash-command syntax is converted to output text rather than thrown (`repos/zanzythebar--brhp/src/composition/create-server-plugin.ts:89-98`). Status and inspect separately classify instruction/runtime failures and render stack-free diagnostics while preserving a response (`repos/zanzythebar--brhp/src/composition/create-server-plugin.ts:240-305`).
- Runtime methods reject mutations without an active session and throw if persisted state cannot be reloaded after create, activation, decomposition, validation, or completion (`repos/zanzythebar--brhp/src/application/services/planner-runtime.ts:127-154`, `repos/zanzythebar--brhp/src/application/services/planner-runtime.ts:163-249`).
- Tool inputs are schema-constrained and state operations are scoped to the resolved worktree/session. This is useful isolation, but the inspected code does not document database file permissions, encryption, cross-process locking, or concurrent multi-session editing; the operator contract explicitly calls multi-session behavior internal and not yet specified (`repos/zanzythebar--brhp/docs/operator-contract.md:66-79`).
- Package entry resolution is checked to remain inside the package root in the package verifier (`repos/zanzythebar--brhp/scripts/verify-package.mjs:101-140`). No authentication or secret-handling path exists in this plugin, so deployments should not infer provider credential protection from this pattern.

## Pitfalls and reusable lessons

- Keep server and TUI entrypoints separate when their SDK contracts differ; advertise both with `oc-plugin`, explicit exports, and artifact smoke tests (`repos/zanzythebar--brhp/package.json:17-31`, `repos/zanzythebar--brhp/scripts/verify-package.mjs:39-63`).
- Bind persistent state to the resolved project worktree and OpenCode session, not merely process-global state; use a per-operation server handle and an explicit TUI owner (`repos/zanzythebar--brhp/src/composition/create-planner-runtime.ts:25-57`, `repos/zanzythebar--brhp/src/composition/create-planner-runtime-owner.ts:30-118`).
- Make command/tool contracts narrow and bounded. Separate human-facing projections from internal state and cap history/graph output to avoid unbounded responses (`repos/zanzythebar--brhp/docs/operator-contract.md:22-47`).
- Treat configuration and instruction loading as fallible integrations: validate config strictly, degrade missing/invalid operational inputs to safe defaults where appropriate, and preserve diagnostics instead of leaking stack traces (`repos/zanzythebar--brhp/src/application/use-cases/load-planner-config.ts:13-42`, `repos/zanzythebar--brhp/src/composition/create-server-plugin.ts:240-271`).
- Register resources transactionally. If TUI slot/command registration fails, unregister anything already registered and dispose the runtime owner; on normal disposal, close runtime and unregister in a deterministic order (`repos/zanzythebar--brhp/src/composition/create-tui-plugin.tsx:43-92`, `repos/zanzythebar--brhp/tests/unit/create-tui-plugin.test.tsx:73-173`).
- A notable limitation is packaging friction: the README requires both pnpm and Bun, and local development requires rebuilding after source changes (`repos/zanzythebar--brhp/README.md:64-99`). The package verifier also invokes npm for pack/install, so the release path depends on three package-tool ecosystems (`repos/zanzythebar--brhp/README.md:145-162`, `repos/zanzythebar--brhp/scripts/verify-package.mjs:185-214`).
