## README and Product Pattern

The product model is explicit: decompose a task, create Hive cells, spawn workers with file reservations, coordinate through Swarm Mail, review completions, and learn from outcomes (`README.md:65-77`). The README presents Hive as git-backed state in `.hive/`, Hivemind as semantic memory with FTS fallback, and Swarm Mail as actor-model coordination (`README.md:80-108`).

The local-first architecture is a strong pattern for an OpenCode plugin: libSQL is embedded, Hive state is git-backed, and Ollama is optional with FTS fallback (`README.md:170-177`, `README.md:204-221`). Event sourcing is the shared state model, with append-only events for registration, messaging, reservations, checkpoints, and outcomes (`README.md:179-190`).

The documented learning loop records duration, errors, touched files, and success; patterns mature through candidate/established/proven, anti-patterns are generated above a 60% failure rate, and confidence decays over 90 days (`README.md:194-200`). This is a reusable pattern for turning plugin telemetry into bounded prompt context rather than storing unstructured history.

The package README documents project initialization separately from installation: install the CLI, run `swarm setup`, initialize the target project with `swarm init`, then use `/swarm` (`packages/opencode-swarm-plugin/README.md:19-39`, `:83-103`). It also calls out a real marketplace failure mode: missing build artifacts require building the package and confirming `dist/` before reinstalling (`packages/opencode-swarm-plugin/README.md:71-81`).

## OpenCode Entrypoint and Runtime Hooks

The public library entry imports and aggregates namespaced tool groups for Hive, Swarm Mail, structured output, orchestration, worktrees, review, repository crawling, skills, mandates, Hivemind, observability, research, queues, and contributors (`packages/opencode-swarm-plugin/src/index.ts:23-71`, `:159-188`). It sets the project directory for Hive, skills, legacy Agent Mail, and embedded Swarm Mail from `PluginInput.directory`, avoiding accidental use of the plugin installation directory (`src/index.ts:96-113`).

The dedicated loader entry is intentionally minimal. `src/plugin.ts` documents that OpenCode calls all exports as functions and that exporting both named and default plugin functions causes double registration; it therefore exports only the default (`packages/opencode-swarm-plugin/src/plugin.ts:1-23`). This is an important OpenCode-specific loader rule and a useful packaging invariant to test.

The plugin uses lifecycle and tool hooks. On `session.idle`, it best-effort releases Agent Mail reservations and logs rather than throws if the external Agent Mail service is unavailable (`src/index.ts:115-157`, `:191-202`). The after-tool hook applies output guardrails and releases reservations after `swarm_complete` (`src/index.ts:287-333`). Eval capture is dynamically imported and explicitly non-fatal so telemetry cannot block user tool execution (`src/index.ts:370-417`).

Coordinator context is activated when an epic/decomposition or swarm worker task is started, then checked before tool execution (`src/index.ts:212-271`). The runtime guard rejects coordinator file edits, test execution, and file reservations rather than merely warning. The guard’s policy and tool lists are documented in `src/coordinator-guard.ts:1-17`, `:57-91`; the blocking behavior and actionable errors are implemented at `:139-205`.

## Evidence-Backed OpenCode Patterns

1. **Thin, loader-safe wrapper plus capable CLI.** The generated wrapper allows only `@opencode-ai/plugin`, `@opencode-ai/sdk`, and `node:*` imports, and shells out to `swarm`; it warns that importing the package can pull unavailable transitive dependencies and crash OpenCode (`packages/opencode-swarm-plugin/examples/plugin-wrapper-template.ts:11-29`, `:37-50`). The wrapper passes session, message, agent, and project context through environment variables (`:31-36`).
2. **Project-directory propagation.** Set all project-scoped adapters from `PluginInput.directory` at plugin initialization (`src/index.ts:96-113`) instead of relying on process cwd or the installed package path.
3. **Namespaced tools as a stable API.** The aggregate tool map groups capabilities by domain and retains explicit legacy aliases while marking newer Swarm Mail/Hive paths as recommended (`src/index.ts:74-88`, `:159-188`).
4. **Guardrails at the hook boundary.** Applying truncation in `tool.execute.after` centralizes context protection for every tool (`src/index.ts:287-297`). The default is 32,000 characters, with per-tool overrides and explicit skip lists for coordination protocols (`src/output-guardrails.ts:20-46`, `:85-169`).
5. **Schema-first tool contracts.** Decomposition and progress data use Zod schemas, require non-empty tasks/subtasks, bound effort/status values, validate timestamps, and require blockers when status is `blocked` (`src/schemas/task.ts:18-24`, `:39-83`, `:130-145`).
6. **Session cleanup is best effort.** Reservation release catches service failures and warns rather than breaking session lifecycle handling (`src/index.ts:122-157`).

## Security and Reliability Lessons

- **Do not import the published package from a global OpenCode wrapper.** The repository’s own generated template identifies the transitive-dependency crash mode and enforces a dependency allowlist (`examples/plugin-wrapper-template.ts:11-29`). Keep the wrapper dumb; keep dependency-heavy logic in the CLI.
- **Enforce agent-role boundaries, not just prompt them.** `CoordinatorGuardError` carries a violation type, payload, and suggestion (`src/coordinator-guard.ts:27-55`), and the plugin throws it before the prohibited tool call (`src/index.ts:242-257`). This turns coordination policy into a runtime safety boundary.
- **Bound untrusted or unexpectedly large tool output.** The output guardrail preserves JSON/code/Markdown boundaries while truncating (`src/output-guardrails.ts:201-240`), reducing context-exhaustion risk. The skip list is deliberate for protocol outputs but should be reviewed whenever new coordination tools are added (`:110-169`).
- **Use atomic writes for durable session/eval state.** The helper writes a UUID-named temporary file and renames it, cleaning up on failure (`src/hooks/atomic-write.ts:25-49`). Append mode is intentionally separate and is not atomic (`:30-33`), so callers should use it only where append semantics are acceptable.
- **Keep telemetry failure-isolated.** Dynamic eval capture catches parsing/import/capture failures and does not block tool execution (`src/index.ts:370-417`). This is safer than coupling optional analytics to the critical execution path.
- **Potential maintenance pitfall: stale terminology and compatibility surface.** The package description and keywords still mention “beads” (`packages/opencode-swarm-plugin/package.json:2-4`, `:94-104`), while the code and README promote Hive. Legacy aliases are intentional (`src/index.ts:78-81`, `:174-175`), but future changes must keep the compatibility boundary clear.

The OpenCode package contains targeted tests for coordinator guards, hooks, schema validation, compaction, regression detection, output guardrails, MCP bundling, worktrees, orchestration, and memory, as shown by the `src` test inventory.

The eval gate runs on non-draft pull requests, installs with Bun, builds `swarm-mail` and the plugin first, then runs the eval gate with `AI_GATEWAY_API_KEY` (`.github/workflows/eval-gate.yml:9-45`). Turbo makes tests and typechecks depend on upstream builds and passes selected environment variables into test tasks (`turbo.json:12-18`).

Testing lesson: separate fast deterministic protocol tests from filesystem/database integrations, and add a packaging/asset test layer. This repository’s tests include Claude asset and tarball-style checks, while the build pipeline has several generated output targets that warrant independent artifact verification.

## Configuration and Packaging

The package is ESM, publishes `dist`, CLI `bin`, Claude plugin assets, examples, global skills, and README, and exposes separate library/plugin/eval-capture/compaction-scoring entrypoints (`packages/opencode-swarm-plugin/package.json:2-38`). It declares public npm publishing metadata and a peer dependency on the OpenCode plugin API (`:40-43`, `:91-92`).

The build is configuration-driven. It builds the library, default plugin, auxiliary entrypoints, Hive/prompts, an MCP CommonJS bundle, a marketplace bundle, and finally the CLI (`packages/opencode-swarm-plugin/scripts/build.ts:9-42`). It distinguishes ordinary, CLI, and marketplace externals; notably it bundles `swarm-mail` for CLI and marketplace distribution to avoid missing modules/version mismatches (`:44-76`, `:176-181`). It then generates declarations and synchronizes Claude runtime assets and the MCP bundle (`:194-203`).

The root uses Bun workspaces and Turbo, with Changesets versioning and a CI publish script (`package.json:1-19`). The monorepo guide records the reason for running `bun update` after Changesets: stale `workspace:*` references can otherwise produce incorrect published versions. The package’s explicit `files` list and build-generated assets make pack inspection a required release check, not an optional convenience.

Packaging pitfalls:

- The CLI is a published `bin` entry and its runtime imports must be in `dependencies`, not only devDependencies; the repository calls this out in its monorepo guidance.
- The marketplace build must remain self-contained because it bundles `swarm-mail` and is designed for an environment without package `node_modules` (`scripts/build.ts:31-37`, `:67-76`).
- `src/plugin.ts` must remain default-only to avoid duplicate OpenCode registration (`src/plugin.ts:5-23`).
- `dist`, Claude assets, MCP bundle, examples, and declarations are all coupled outputs; CI should build and inspect them together (`scripts/build.ts:142-203`).

## Overall Assessment

This is a mature, broad OpenCode integration rather than a minimal plugin. Its strongest reusable patterns are the self-contained wrapper/CLI split, project-directory initialization, namespaced tool surface, runtime coordinator enforcement, output-size guardrails, schema validation, failure-isolated telemetry, and artifact-aware multi-target build. Its main risks are operational complexity and a large compatibility surface: many tools, legacy aliases, multiple published/runtime targets, embedded databases, optional services, and eval infrastructure all require disciplined release and integration testing.
