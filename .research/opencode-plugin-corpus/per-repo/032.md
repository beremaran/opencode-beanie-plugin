# Repository 032: hiai-opencode

## Scope and availability

- Manifest index 32 identifies `HiAi-gg/hiai-opencode`, described as a “Canonical 12-agent model with bundled skills, MCP, LSP, and ralph-loop” (`.research/opencode-plugin-corpus/manifest.json:427-432`).
- The clone is available at `.research/opencode-plugin-corpus/repos/hiai-gg--hiai-opencode/`. The manifest entry has no subdirectory field, and the clone is analyzed from its repository root. No clone files were edited.
- The repository contains a TypeScript/Bun OpenCode plugin, packaged CLI, configuration schema, bundled skills, source, and 73 test files in the inspected tree. The README advertises 10 model slots, 30 hooks, and 35 tools (`README.md:103-156`).

## OpenCode patterns

- **Plugin entrypoint and config-hook assembly.** The package exports `dist/index.js` and the default plugin entry is `src/index.ts` (`package.json:5-16`; `src/index.ts:454-459`). The plugin loads config and initializes services before returning OpenCode hooks (`src/index.ts:120-195`). Agent definitions are merged into `cfg.agent` in `hooks.config`, including native-agent upgrades, model resolution, permissions, prompts, and task permissions (`src/index.ts:199-357`). This is a useful pattern when a plugin must preserve host agent config while selectively overlaying behavior: each agent starts from `existing`, then applies plugin-owned fields (`src/index.ts:207-218`, `src/index.ts:332-357`).
- **Layered configuration with explicit precedence.** `loadConfig()` walks the project directory and ancestors, checking `bob.json`, `.opencode/bob.json`, and JSONC variants before global config; the first parseable file wins (`src/config.ts:339-380`). Tests cover first-match behavior and nearest-ancestor discovery (`src/config.test.ts:34-85`). `mergeConfig()` separately deep-merges models, MCP, LSP, restrictions, circuit-breaker settings, and disabled lists (`src/config.ts:385-504`).
- **Separate model/config sources.** `bob.json` is a concrete user-facing model map with fully qualified `provider/model` IDs and separate MCP/LSP toggles (`bob.json:1-6`, `bob.json:7-56`). Runtime defaults and restrictions live in `DEFAULT_CONFIG` instead of duplicating model defaults (`src/config.ts:126-245`). The architecture document explicitly calls out `bob.json` as the model source of truth and `DEFAULT_CONFIG` as the internal-default loader (`ARCHITECTURE.md:110-122`).
- **Agent capability boundaries.** `applyAgentPermissions()` maps permission-like keys to `permission.*` and tool-like keys to `tools.*=false` (`src/permissions.ts:29-68`, `src/permissions.ts:140-162`). Task delegation is deny-by-default for leaf agents; Bob can call Manager/workers, Manager can call workers, and workers cannot recursively call workers (`src/permissions.ts:86-120`). The tests verify both the mapping and the delegation topology (`src/permissions.test.ts:65-84`, `src/permissions.test.ts:104-120`).
- **Hook composition with blocking/non-blocking distinction.** Hook chains rethrow `BlockingHookError`, but sanitize ordinary errors into bounded DTOs, deduplicate them, and cap retained errors (`src/hooks/index.ts:95-126`). Disposal continues through all cleanup functions even if one throws (`src/hooks/index.ts:131-143`). Tests explicitly cover raw payload sanitization, deduplication, the cap, blocking propagation, undefined hook output, and cleanup continuation (`src/hooks/index.test.ts:320-521`).
- **Static MCP compatibility bridge.** The config hook best-effort exports `.opencode/.mcp.json` for host versions that inspect static config, then merges validated registry entries and passes through enabled user MCP entries not in the registry (`src/index.ts:199-205`, `src/index.ts:360-373`). This addresses a real host-version compatibility boundary without treating MCP servers as plugins, a distinction also documented in `ARCHITECTURE.md:55-58`.

## Security and safety lessons

- **Do not rely on prompts for completion controls.** The plugin combines critic approval, quality-command status, diagnostics, and other stateful gates; the README describes critic, quality, LSP, legal, circuit-breaker, and closure gates as enforced behavior (`README.md:143-152`). The config defaults require critic approval and enable completion control (`src/config.ts:226-241`). The practical pattern is to hold completion state in hooks/controller code rather than only instructing agents.
- **Use defense in depth for risky tools.** The legal gate blocks browser automation and prohibited military/malicious/exfiltration patterns before native permissions, while contextual dual-use terms require offensive intent (`src/hooks/legal-gate.ts:18-30`, `src/hooks/legal-gate.ts:254-299`). Read-only external-directory tools are auto-allowed, but bash/write/edit/patch/webfetch remain `ask` tools (`src/hooks/legal-gate.ts:214-247`, `src/hooks/legal-gate.ts:326-353`). Tests distinguish read-only auto-allow from write/edit/bash/webfetch approval prompts (`src/hooks/index.test.ts:63-317`).
- **Enforce browser-tool ownership at execution time.** The legal gate rejects Playwright/Puppeteer imports, APIs, package paths, and CLI use, while allowing the approved `agent_browser_*` tools (`src/hooks/legal-gate.ts:32-158`; `src/hooks/index.test.ts:561-765`). Config-level restrictions alone would be weaker because they can be bypassed by another execution path; the tests document that the Critic’s browser restriction is enforced by the hard gate instead (`src/permissions.test.ts:550-583`).
- **Keep secrets out of JSON and logs.** The example env file says model-provider credentials belong in OpenCode Connect and raw keys must not be placed in JSON (`bob.env.example:19-23`). Env loading preserves ordinary shell values, makes selected managed keys authoritative, and logs only key/source presence rather than secret values (`src/config.ts:36-48`, `src/config.ts:68-123`). A caveat is that `resolveEnvVars()` replaces missing `{env:...}` variables with an empty string, so schema/config validation should detect missing required secrets rather than silently accepting an empty value (`src/shared/env.ts:1-17`).
- **Sandbox path-sensitive tools.** The architecture documents an LSP sandbox that rejects paths outside `ctx.directory` and an agent-browser guard restricting browser tools to Vision/General (`ARCHITECTURE.md:246-254`). This is a reusable boundary: enforce filesystem and agent identity at the tool layer, not just in agent prompts.

## Testing lessons and observed pitfalls

- **Good unit/integration coverage shape.** Tests use Bun’s native test API, temporary directories, cleanup hooks, and a real plugin config-hook invocation (`src/config.test.ts:1-12`, `src/config.test.ts:34-85`; `src/permissions.test.ts:279-318`). This validates both pure permission mapping and actual `BobPlugin(...).config(...)` registration.
- **Tests encode regressions and negative cases.** Examples include preserving native `question` permission for the plan agent (`src/permissions.test.ts:490-504`), ensuring a read-only auto-allow is not overwritten by `ask` (`src/hooks/index.test.ts:295-317`), and ensuring hook failures do not leak huge raw objects (`src/hooks/index.test.ts:401-430`). These are stronger than happy-path-only tests because they target composition and ordering bugs.
- **Quality-gate matching is deliberately structural but heuristic.** The gate recognizes commands such as `bun test`, Biome, `tsc`, Vitest, and Jest, then scans output for failure markers while clearing the state on a passing run (`src/hooks/quality-gate.ts:6-28`, `src/hooks/quality-gate.ts:30-71`). This avoids tripping on benign “no error” text, but output-pattern gates can still miss novel runner formats or flag incidental text; tests should keep expanding with real tool output fixtures.
- **Observed clone test result is not a clean baseline.** Running `bun test` in the clone produced `966 pass`, `27 fail`, `3 errors`, and `1723 expect()` calls across 993 tests. The first unhandled error was `Cannot find package 'drizzle-orm'` from `src/memory/reconcile.ts`; related index/memory imports and config-hook integration tests failed as a dependency cascade. This is an availability/dependency-installation limitation of the supplied clone environment, not evidence that all 27 failures are independent code defects. No `bun install` was run, so the clone was not mutated.
- **Expected-error tests are noisy.** The test suite intentionally logs disposal, hook, and simulated controller errors while asserting recovery behavior (`src/hooks/index.test.ts:320-430`; `src/features/completion-controller/integration.test.ts` output observed during the run). CI/reporting should distinguish expected diagnostic logging from test failures.

## Packaging and release lessons

- **Build and publish gates are explicit.** The package builds a Bun bundle, emits declarations, verifies the bundle, and defines typecheck/test/lint/check/pack scripts (`package.json:72-88`). `prepublishOnly` runs typecheck, tests, build, and pack dry-run (`package.json:87-88`). This is a strong release pattern for a plugin whose runtime artifact differs from source.
- **The package surface is intentionally curated.** `files` includes `dist/`, `skills/`, `assets/`, `config/`, operator docs, license, README, model config, and env template, while source and lockfile are not listed (`package.json:17-27`). `.npmignore` further excludes source, dependencies, env files, runtime artifacts, and local MCP/config state (`.npmignore:1-23`). The lesson is to verify the packed tarball, not assume repository presence implies npm presence.
- **CLI registration is part of plugin usability.** The `bin` field installs `assets/cli/hiai-opencode.mjs` as `hiai-opencode` (`package.json:8-10`), and the README presents `doctor`, MCP status, and diagnostics as verification commands (`README.md:75-83`, `README.md:195-204`). A plugin with external services or generated config benefits from a machine-checkable doctor command and non-zero hard-failure exit status.
- **Runtime artifacts need safe overwrite policy.** The repository excludes generated MCP/config artifacts from the package and documents `if-missing`/`always`/`off` plus safe/force modes (`.npmignore:1-5`; `ARCHITECTURE.md:220-228`). The test output confirms the exporter refuses to overwrite a non-managed file unless force mode is selected. This reduces accidental clobbering of user-owned OpenCode config.

## Bottom line

The most reusable design is the separation of concerns: `src/index.ts` owns OpenCode registration, `src/config.ts` owns precedence/defaults, permission utilities define agent capability boundaries, hooks enforce runtime safety/completion, and package metadata controls the shipped surface. The main operational risk observed here is dependency-sensitive startup: without the declared `drizzle-orm` dependency installed, broad integration tests and entrypoint imports fail before exercising the plugin. The main security lesson is to keep high-impact controls executable and layered, while treating prompts and output heuristics as supplementary rather than authoritative.
