## What it does

`opencode-mystatus` is an OpenCode plugin for querying quota status across OpenAI, Zhipu AI, Z.ai, GitHub Copilot, and Google Cloud/Antigravity accounts. The README identifies the supported account stores and provider coverage (`README.md:7-21`, `README.md:160-165`). It exposes one `mystatus` tool and runs provider queries concurrently, then separates successful sections from per-provider errors (`plugin/mystatus.ts:26-55`, `plugin/mystatus.ts:59-89`).

The repository also ships a native slash-command definition. Its front matter supplies the description and its body tells the model to invoke the tool and return the result unchanged (`command/mystatus.md:1-5`). Installation documents both package-based configuration and copying the plugin/command files into the OpenCode config directory (`README.md:33-82`).

## OpenCode patterns worth reusing

### Narrow plugin surface

- The plugin imports `Plugin` and `tool` from `@opencode-ai/plugin`, returns a `tool` map from the async plugin initializer, and declares an empty argument object for a read-only status operation (`plugin/mystatus.ts:10-12`, `plugin/mystatus.ts:26-33`).
- It deliberately exports only `MyStatusPlugin`; internal collection and provider helpers are not exported, avoiding accidental plugin-loader discovery (`plugin/mystatus.ts:22-26`, `plugin/mystatus.ts:96-116`). This is a useful convention for plugin packages with multiple helper modules.
- The slash command is kept separate from the TypeScript tool and explicitly asks for unmodified tool output (`command/mystatus.md:1-5`). That makes the user-facing command thin and keeps formatting in code.

### Provider isolation and graceful degradation

- Each provider adapter returns `QueryResult | null`, where absent/invalid configuration is represented by `null` and request failures become `{ success: false, error }` (`plugin/lib/types.ts:15-19`, `plugin/lib/openai.ts:207-235`, `plugin/lib/zhipu.ts:185-205`).
- The aggregator uses `Promise.all` to query all providers concurrently, but collects each result independently so one provider failure does not discard successful sections (`plugin/mystatus.ts:48-75`, `plugin/mystatus.ts:100-115`).
- Zhipu and Z.ai share one implementation through a small `PlatformConfig` containing endpoint, error formatter, and account label (`plugin/lib/zhipu.ts:52-76`, `plugin/lib/zhipu.ts:185-227`). This is a compact pattern for API-compatible providers.
- Google accounts are also queried concurrently, and the adapter filters out accounts without email before making requests (`plugin/lib/google.ts:304-334`).

### Operational robustness and output

- All shared provider API calls except Google token refresh use an abort-based 10-second timeout; timeout cleanup happens in `finally` (`plugin/lib/types.ts:113-114`, `plugin/lib/utils.ts:84-105`).
- Output helpers clamp progress-bar percentages to 0-100 and handle empty maxima, reducing malformed display output (`plugin/lib/utils.ts:40-52`, `plugin/lib/utils.ts:112-118`).
- The tool detects Chinese versus English once and centralizes all user-visible strings in a typed translation object (`plugin/lib/i18n.ts:14-40`, `plugin/lib/i18n.ts:46-203`, `plugin/lib/i18n.ts:209-213`).
- The OpenAI adapter validates OAuth type/access token and checks the local expiry before sending a request (`plugin/lib/openai.ts:207-221`). Zhipu validates API-key account type/key before use (`plugin/lib/zhipu.ts:185-192`).

## Security and privacy lessons

### Positive controls

- The README clearly declares the two local credential files and the official endpoints contacted (`README.md:171-187`). It also claims read-only local access, no storage/upload/cache, and masked API-key output (`README.md:175-193`).
- Zhipu/Z.ai keys are masked before being included in rendered output (`plugin/lib/zhipu.ts:123-125`; masking implementation at `plugin/lib/utils.ts:124-135`).
- Google refresh tokens are sent only in a form-encoded POST body to the configured Google OAuth endpoint, and the resulting access token is used as a bearer token for the quota call (`plugin/lib/google.ts:90-96`, `plugin/lib/google.ts:162-183`, `plugin/lib/google.ts:193-212`).
- The optional Copilot PAT configuration is checked for required fields and an allow-listed tier before use (`plugin/lib/copilot.ts:122-149`).

### Pitfalls and risks

- The Google adapter contains a hard-coded OAuth client ID *and client secret* in source (`plugin/lib/google.ts:90-96`). Even if these are public-client credentials in the upstream integration, embedding a secret in a distributed plugin weakens secret-rotation and disclosure boundaries; a safer package should document why it is public or obtain provider-approved configuration without treating source-embedded material as confidential.
- The plugin reads raw auth JSON and forwards bearer/API credentials to multiple external services (`plugin/mystatus.ts:34-55`; provider requests at `plugin/lib/openai.ts:127-154`, `plugin/lib/zhipu.ts:81-105`, `plugin/lib/google.ts:162-212`, `plugin/lib/copilot.ts:157-176`). A security review should verify endpoint ownership, TLS assumptions, and least-privilege scopes rather than relying only on the README's "official" list.
- API error bodies are interpolated into user-visible errors (`plugin/lib/openai.ts:149-152`, `plugin/lib/zhipu.ts:94-103`, `plugin/lib/google.ts:178-180`, `plugin/lib/copilot.ts:171-176`). Provider responses can contain identifiers or diagnostic data, so production code should bound or sanitize error text before returning it to the model/user.
- The plugin parses JWT payloads locally only to display email/account ID; it does not verify the JWT signature (`plugin/lib/openai.ts:54-89`). This is acceptable for non-authoritative display/header selection if the token came from trusted local auth storage, but the parsed claims must not be treated as proof of identity.
- The Copilot path supports a user-created PAT file and places the username into a URL path without explicit URL encoding (`plugin/lib/copilot.ts:92-98`, `plugin/lib/copilot.ts:157-169`). Current GitHub usernames are constrained, but URL construction should still use `encodeURIComponent` and the config file should have documented permission expectations.
- The README says "No data is stored, uploaded, or cached," but the implementation makes outbound authenticated API calls by design (`README.md:189-193`; `plugin/lib/openai.ts:145-154`). The claim should be worded as no persistence by the plugin, not no upload, to avoid misleading users.

## Testing and validation lessons

- No test files are shipped in the inspected clone; the repository inventory contains source/config/docs but no `test`, `tests`, or `*.test.*` files. The package scripts provide typecheck, lint, build, and formatting only (`package.json:20-26`). This leaves parsing, timeout, response validation, masking, expiry, and aggregation behavior unprotected by automated regression tests.
- Runtime response validation is mostly structural TypeScript casts rather than schema validation: OpenAI, Google, and Copilot responses are cast directly from `response.json()` (`plugin/lib/openai.ts:149-154`, `plugin/lib/google.ts:207-212`, `plugin/lib/copilot.ts:171-176`). Tests should include malformed/partial provider responses and verify safe user-facing errors.
- The implementation has useful deterministic seams for unit tests: JWT parsing and display formatting (`plugin/lib/openai.ts:54-120`), progress/time/masking helpers (`plugin/lib/utils.ts:18-135`), provider config reuse (`plugin/lib/zhipu.ts:52-105`), and Copilot strategy fallback (`plugin/lib/copilot.ts:242-303`). Mocking `fetch`, filesystem reads, and time would cover most behavior without real credentials.
- The README documents the typecheck/build commands for npm and Bun (`README.md:206-218`), while CI only runs `npm install` and `npm run build` before publishing (`.github/workflows/publish.yml:20-27`). CI does not run the available lint script, typecheck script, or tests, and should add those gates if they are intended release criteria.

## Packaging and release lessons

- The package is ESM, exposes compiled plugin JS and declarations, and includes `dist`, `command`, README, and license in the published file set (`package.json:5-18`). The `files` list fixes the earlier packaging issue documented in the changelog, where the command directory had to be added for slash-command support (`CHANGELOG.md:28-33`).
- TypeScript emits declarations/maps into `dist` with `rootDir: "."`, but only `plugin/**/*.ts` is compiled (`tsconfig.json:1-18`). The command markdown is therefore correctly shipped as a package file rather than generated output.
- `@opencode-ai/plugin` is both a runtime dependency pinned to `1.1.27` and a peer dependency accepting `^1.1.0` (`package.json:51-66`). Consumers can therefore resolve the plugin API through the package while still receiving compatibility signaling, but the exact dependency pin should be kept current with the supported OpenCode runtime.
- The package declares Node `>=18`, while the release workflow builds on Node 20 and uses `npm install` rather than a lockfile-driven install (`package.json:67-69`; `.github/workflows/publish.yml:14-24`). A committed lockfile plus `npm ci` would improve reproducibility, and a publish check should inspect the packed artifact to ensure `dist/plugin/mystatus.js`, declarations, and `command/mystatus.md` are present.
- `prepublishOnly` runs lint and build (`package.json:24-27`), but the GitHub workflow invokes `npm publish` after a separate build (`.github/workflows/publish.yml:23-27`). The workflow therefore relies on npm lifecycle behavior for linting at publish time; making lint/typecheck explicit would make the release gate clearer.

## Bottom line

The strongest reusable design is a small OpenCode tool that fans out to isolated provider adapters, applies bounded timeouts, and returns partial results with per-provider errors. The main weaknesses are the absence of automated tests and response schemas, incomplete CI checks, potentially overbroad error-body disclosure, and source-embedded Google OAuth secret material. Any derivative plugin should preserve the narrow export/tool surface and graceful degradation while adding mocked provider tests, explicit credential/path handling, and reproducible packaging checks.
