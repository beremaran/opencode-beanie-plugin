## What It Does

`opencode-sessions` exposes one `session` tool with four modes: `message` for same-thread agent relay, `new` for a clean session, `compact` for summarization followed by a handoff, and `fork` for history-preserving exploration (`index.ts:293-377`). The README frames these as collaborate, handoff, compress, and parallelize workflows (`README.md:12-16`, `README.md:64-66`, `README.md:110-112`, `README.md:140-142`).

The plugin discovers primary agents from user/project markdown files, parses frontmatter with `gray-matter`, adds `build` and `plan` defaults, and removes agents disabled in the two supported `opencode.json` locations (`index.ts:32-47`, `index.ts:51-65`, `index.ts:67-149`). Discovery happens once while the plugin initializes, before the tool description is constructed (`index.ts:151-159`).

## Evidence-Backed OpenCode Patterns

### Defer same-session prompts until idle

The most important pattern is avoiding a nested prompt while the current tool invocation still owns the session. The `tool.execute.before` hook records a `message` request by `sessionID` (`index.ts:184-205`); the `session.idle` event removes that request and calls `ctx.client.session.prompt` only after the session is idle (`index.ts:207-235`). The README explicitly documents this as a five-step relay and identifies the benefit as avoiding deadlocks (`README.md:364-381`).

This is corroborated by the changelog: earlier releases specifically fixed hangs by not awaiting `session.prompt` and moved to the `session.idle` pattern (`CHANGELOG.md:72-84`). For plugins that need to cause another turn in the current session, event-driven deferral is safer than recursively prompting from `execute`.

### Preserve compaction context explicitly

Compact mode first reads the latest assistant message to obtain `providerID` and `modelID` (`index.ts:410-433`). It then injects a `noReply` marker before storing the request for processing after idle (`index.ts:434-456`). On `session.idle`, it calls `session.summarize` without awaiting it, tracks active state, and waits for `session.compacted` before sending the requested follow-up (`index.ts:237-260`, `index.ts:266-289`). The changelog records fixes for provider/model forwarding, session locks, races, and the switch from aborts to natural completion (`CHANGELOG.md:14-34`).

The practical lesson is to treat compaction as a multi-event state machine, not a single synchronous API call. The explicit `activeCompactions` map and cleanup on both summarize failure and completion illustrate that approach (`index.ts:175-182`, `index.ts:249-260`, `index.ts:268-275`).

### Use the SDK for session operations

New sessions, forks, prompts, messages, and summarization go through `ctx.client.session` (`index.ts:224-230`, `index.ts:251-257`, `index.ts:391-408`, `index.ts:468-482`). Forking uses the built-in `session.fork` API and then prompts the returned child, preserving history without manually copying messages (`index.ts:466-482`). This keeps plugin behavior aligned with OpenCode's session model.

### Make tool contracts self-describing

The tool uses a schema enum for the four modes, requires `text`, and makes `agent` optional (`index.ts:364-377`). Its description embeds the discovered agent list and concrete examples (`index.ts:293-362`). This is a useful pattern for agent-facing tools: constrain the operation space in the schema while explaining lifecycle behavior in the description.

## Pitfalls and Risks

### Agent names are advertised but not validated

The plugin discovers and displays available agents, but `args.agent` is only typed as an arbitrary optional string (`index.ts:364-377`). It is passed directly to `session.prompt` for message, new, compact, and fork flows (`index.ts:224-229`, `index.ts:279-284`, `index.ts:399-405`, `index.ts:474-479`). A typo or disabled/nonexistent agent therefore reaches the SDK and fails at runtime. A schema generated from the discovered list would improve feedback, but would need a refresh strategy because discovery is initialization-time only (`index.ts:151-159`).

### Pending state is keyed only by session ID

`pendingMessages`, `pendingCompactions`, and `activeCompactions` are plain maps keyed by `sessionID` (`index.ts:175-182`). A second message request before idle overwrites the first (`index.ts:194-200`), and a second compact request overwrites the pending compact state (`index.ts:450-456`). There is no queue, request identifier, timeout, or shutdown cleanup. The README promises a queued relay (`README.md:368-375`), but the implementation stores at most one pending item per session.

### Errors are hidden in important asynchronous paths

Message and post-compaction prompts catch errors and do nothing (`index.ts:231-233`, `index.ts:285-288`). Summarization also deletes state without reporting the failure (`index.ts:258-260`). This can leave users with a successful-looking tool result but no handoff. The outer tool handler does show a TUI error and returns an error string for synchronous SDK failures (`index.ts:484-497`), so the error policy is inconsistent. The repository's own guidance says to avoid silent failures and use a logging helper (`AGENTS.md:17-20`), but no such helper is present in the entrypoint at this revision.

### Filesystem discovery trusts local configuration

The plugin reads markdown files from both user and project agent directories and parses arbitrary YAML frontmatter (`index.ts:57-103`), then reads and JSON-parses user/project configuration (`index.ts:123-145`). This is expected for an OpenCode plugin, but malformed or very large files can affect startup, and frontmatter descriptions are inserted into the tool description without length or content limits (`index.ts:89-96`, `index.ts:154-159`). Parse failures are silently skipped, making configuration mistakes hard to diagnose.

### Global in-memory state has lifecycle limitations

The maps live in the plugin instance closure (`index.ts:151-182`). They are not persisted across reloads and are not bounded by age. Although normal success paths delete entries, failures in event delivery or an idle event that never occurs can retain state for the lifetime of the plugin. Concurrent sessions are isolated by key, but multiple requests within one session are not.

### Fixed timing is brittle

After `session.compacted`, the plugin sleeps for exactly 100 ms before prompting (`index.ts:266-285`). This may be enough for the observed lock race, but it is not an acknowledgement of lock release and can be too short or unnecessarily slow on different environments. The changelog shows the underlying issue was race/lock-sensitive (`CHANGELOG.md:21-34`); an explicit SDK readiness/event contract would be more robust than a fixed delay.

## Security Lessons

- The plugin has broad behavioral power: an agent can create sessions, fork history, select another agent, inject prompts, and trigger summarization (`index.ts:379-482`). Enablement should therefore be scoped to intended primary agents, as the README recommends (`README.md:223-232`).
- User/project agent files and configuration are inputs to startup behavior. Keep discovery confined to the documented paths, reject unexpected data shapes, and bound description size before embedding it into the tool schema (`index.ts:51-65`, `index.ts:81-96`, `index.ts:123-148`).
- Error messages are sent to the TUI and returned to the agent (`index.ts:484-497`). SDK errors may contain paths, identifiers, or provider details; production plugins should decide deliberately what to expose and what to log.
- The package publishes only `dist/`, `README.md`, and `LICENSE` (`package.json:34-37`), and `.npmignore` excludes the TypeScript source and tsconfig (`.npmignore:1-6`). This reduces shipped source/config surface, but makes the generated artifact and reproducible build especially important.

## Testing and Verification Lessons

- The repository explicitly records that it has no test suite (`AGENTS.md:3-8`), and the clone contains no test files. This leaves the most failure-prone behavior, event ordering, lock handling, and state overwrite semantics unprotected.
- Highest-value tests would mock the OpenCode client and verify: message prompts occur only after idle; compact calls `messages`, injects `noReply`, summarizes with the last assistant model, and prompts after compacted; summarize failures surface an error; fork/new use returned session IDs; and duplicate requests are either rejected or queued (`index.ts:216-289`, `index.ts:410-482`).
- Type checking is configured with `strict: false` (`tsconfig.json:1-20`), and the implementation uses an `as any` cast for agent configuration (`index.ts:131-138`). Enabling stricter checking would help expose malformed SDK/config assumptions, though runtime validation is still required.
- The documented checks are `npm run build` and `npm run typecheck` (`AGENTS.md:3-7`). CI's release path runs `npm ci`, build, and publish, but does not run typecheck or tests (`.github/workflows/release-please.yml:35-45`).

## Packaging and Release Lessons

- `package.json` points consumers to generated ESM output and declarations, requires Node 20, and declares `@opencode-ai/plugin` as a peer dependency while shipping the SDK and `gray-matter` as dependencies (`package.json:2-7`, `package.json:39-58`). This cleanly separates the host plugin API from runtime parsing/SDK dependencies.
- `prepublishOnly` builds TypeScript before publication (`package.json:42-45`), while `files` and `.npmignore` define a deliberately small npm artifact (`package.json:34-37`, `.npmignore:1-6`).
- npm provenance is enabled both in package metadata and the publish command (`package.json:14-16`, `.github/workflows/release-please.yml:43-47`). The workflow grants repository, pull-request, and OIDC token permissions (`.github/workflows/release-please.yml:8-11`) and uses Node 20 (`.github/workflows/release-please.yml:28-33`).
- Release Please is configured for a Node package and conventional-commit-driven changelog/versioning (`release-please-config.json:3-11`, `RELEASE.md:64-82`). A useful operational lesson is to keep the generated `dist/` out of git while making the release workflow build from the checked-out source.

## Bottom Line

This is a focused example of an OpenCode plugin that coordinates session lifecycle through hooks and SDK events rather than nested synchronous prompts. Its strongest reusable pattern is the idle/compacted state machine, backed by a history of fixes for deadlocks and races. Its main production gaps are absent tests, silent asynchronous failures, unvalidated agent names, single-item pending state, permissive startup input handling, and a timing-based compaction lock workaround.
