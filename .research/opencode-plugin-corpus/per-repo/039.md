# 039: Micode

## Scope and availability

- Manifest index 39 is `Micode`, repository `https://github.com/vtemian/micode`, described as a Brainstorm-Plan-Implement workflow plugin (`.research/opencode-plugin-corpus/manifest.json:302-309`).
- The dedicated clone is `.research/opencode-plugin-corpus/repos/vtemian--micode/`. It was available for inspection and had no reported worktree changes.
- The clone contains README, `package.json`, TypeScript source, configuration/lint files, and a substantial `tests/` tree. There is no nested `manifest*`, `opencode.json*`, or plugin-specific manifest file in the clone.

## OpenCode patterns

- **Single async plugin factory with lifecycle registration:** the package exports a `Plugin` implementation and performs dependency checks, user-config loading, hook construction, and optional PTY initialization before returning the plugin handlers (`src/index.ts:146-184`, `src/index.ts:250-258`). This keeps dependency injection through the host `ctx` rather than hiding the client in modules.
- **Config callback preserves host configuration:** plugin agents are merged with existing agent entries, built-in agents are demoted to subagents, MCP entries are merged with host entries, and commands are added in one `config` hook (`src/index.ts:326-356`). The merge order lets a host MCP entry with the same name replace the bundled entry (`src/index.ts:89-97`).
- **Composable lifecycle hooks:** the entrypoint wires prompt enrichment through `chat.params`, post-tool processing through `tool.execute.after`, message/system transforms, compaction, and event cleanup (`src/index.ts:358-539`). This is a useful pattern for cross-cutting behavior such as ledgers, context injection, truncation, indexing, and review without putting all logic in one handler.
- **Factories for stateful tools/hooks:** PTY state, Octto sessions, and review recursion state are created inside plugin initialization and cleaned on `session.deleted` (`src/index.ts:196-201`, `src/index.ts:266-307`). The PTY manager also associates sessions with parent sessions and exposes cleanup methods (`src/tools/pty/manager.ts:156-200`).
- **Safe-by-default AST rewriting:** `ast_grep_replace` is dry-run unless `apply=true`, and only adds `--update-all` when explicitly requested (`src/tools/ast-grep/index.ts:178-216`). This is a good mutation boundary for agent-facing tools.
- **Model-aware configuration:** the plugin reads JSON/JSONC, prefers `.jsonc`, validates provider/model data, and applies per-agent overrides over the OpenCode default while rejecting unavailable models (`src/config-loader.ts:49-83`, `src/config-loader.ts:219-280`). The README documents the same precedence and `provider/model` syntax (`README.md:105-162`).

## Pitfalls and security lessons

- **Critical: the plugin globally enables powerful permissions.** Its `config` hook unconditionally sets `edit`, `bash`, `webfetch`, and `external_directory` to `"allow"` (`src/index.ts:326-334`). A plugin should not silently widen the host's security policy. Prefer opt-in, preserve explicit host denials, and document the minimum permissions required by each feature.
- **Critical: PTY tools expose arbitrary process execution and environment control.** The tool accepts an arbitrary executable, arguments, working directory, and environment (`src/tools/pty/tools/spawn.ts:38-63`), then merges caller-provided environment values over the process environment (`src/tools/pty/manager.ts:138-145`). This is appropriate only for a trusted local agent, and should have explicit permission gating, session ownership checks, resource limits, and careful secret/environment redaction.
- **High: dynamically installed MCP commands are not pinned.** Context7 is launched with `npx -y @upstash/context7-mcp@latest`, and optional Perplexity/Firecrawl servers are also launched through `npx` (`src/index.ts:62-86`). `latest` makes runtime behavior and supply-chain inputs non-reproducible. Pin versions and consider integrity-verified installation or a user-supplied executable path.
- **Medium: host config is treated as an override surface.** The plugin deliberately allows same-name host MCP entries to replace bundled entries (`src/index.ts:89-97`), which is flexible but means a host or another plugin can redirect an agent's expected research server. Namespacing, explicit conflict diagnostics, and clear precedence documentation reduce surprises.
- **Medium: filesystem paths derived from manifest categories are joined without an explicit containment check.** `loadExamples` finds a category path from the parsed manifest and joins it to the mindmodel directory before reading (`src/mindmodel/loader.ts:46-64`). The manifest parser validates structure, but a defense-in-depth `realpath`/root containment check would prevent traversal if a project-controlled manifest contains `../` paths.
- **Operational pitfall: external dependencies degrade inconsistently.** AST-grep and BTCA availability are only warned at startup (`src/index.ts:148-157`), while SQLite is deferred and throws when initialized if unavailable (`src/tools/artifact-index/index.ts:323-353`). Feature-level capability reporting and consistent, actionable error responses would make partial installations easier to diagnose.
- **Operational pitfall: session cleanup failures are intentionally swallowed.** Reviewer and Octto cleanup uses `.catch` handlers that discard errors (`src/index.ts:240-246`, `src/index.ts:299-305`). Best-effort cleanup is reasonable, but at least debug/warn logging and bounded cleanup would help detect leaked processes or sessions.

## Testing lessons

- **Broad behavioral coverage:** the clone has 74 test files mirroring source areas, including hooks, agents, indexing, tools, PTY, Octto, configuration, and integrations. The package's quality gate runs Biome, ESLint, TypeScript, and the full Bun test suite (`package.json:14-26`).
- **Configuration tests use isolated temporary directories and cleanup:** tests inject a config directory, create files under a unique temporary path, and remove it in `afterEach` (`tests/config-loader.test.ts:19-35`). This is a reusable pattern for testing home-directory configuration without touching the developer's real OpenCode config.
- **Security-focused sanitization is tested:** tests verify that only safe agent properties survive and that `prompt`/`tools` supplied by user config are discarded (`tests/config-loader.test.ts:75-105`). The implementation explicitly picks an allowlist before Valibot parsing (`src/config-schemas.ts:44-65`).
- **Integration tests validate the shipped artifact, not only source modules.** The bundle test reads the actual build flags from `package.json`, builds with those flags, checks for static Bun-only imports, and loads the output under both Node and Bun (`tests/integration/bundle-runtime-compat.test.ts:21-49`, `tests/integration/bundle-runtime-compat.test.ts:56-95`). This is especially valuable for OpenCode Desktop/Electron compatibility.
- **MCP registration tests cover opt-out and host precedence:** tests verify default registration, feature disablement, API-key gating, replacement by a host entry, and host-only servers (`tests/mcp-servers.test.ts:27-79`).
- **Gap: several tests are source-text integration assertions rather than runtime behavior.** The index tests read `src/index.ts` and assert that strings and hook calls exist (`tests/index.test.ts:35-82`). These catch accidental removal but can pass while wiring is behaviorally broken. Add tests that instantiate the plugin with a fake client and exercise returned handlers.
- **Gap: PTY tests prove execution but not authorization/resource policy.** The spawn test starts `sleep` and checks formatted output (`tests/tools/pty/spawn.test.ts:39-55`), but there is no evidence here of tests for command restrictions, environment secret exposure, working-directory containment, process limits, or cross-session access.

## Packaging and maintenance

- The package publishes `src`, `dist`, and `INSTALL_CLAUDE.md`, with `dist/index.js` as both `main` and `module`; the build targets Node and externalizes `bun-pty`, `jsonc-parser`, and `ws` (`package.json:5-16`). Consumers therefore need compatible runtime dependencies, while the integration test protects the externalization contract.
- Type declarations are emitted from a strict, bundler-resolved TypeScript project with a `@/*` source alias (`tsconfig.json:3-21`). This is a clean setup for a multi-module plugin, but consumers rely on the generated declaration output despite `types` pointing at `src/index.ts` in the package metadata (`package.json:5-8`). Verify published-package type resolution against the packed artifact.
- `prepublishOnly` runs the full check and build, and the README provides both npm plugin installation and a local path workflow (`package.json:17-26`, `README.md:164-181`). The local workflow is useful for plugin development, but release reproducibility would improve with pinned runtime tool versions and pinned MCP package versions.
- Formatting and linting are enforced in CI-style scripts and staged-file hooks (`biome.json:11-77`, `lefthook.yml:1-10`). The repository's project rules also emphasize awaited promises and error-path tests, which aligns with the implementation's explicit cleanup and error handling (`CLAUDE.md:37-65`).

## Takeaways

1. Use a single plugin factory to construct stateful services, inject `PluginInput`, and return narrowly scoped lifecycle handlers.
2. Preserve host config by merging rather than replacing, but never broaden permissions globally without explicit opt-in.
3. Treat agent-facing process, filesystem, PTY, and MCP capabilities as security boundaries: authorize them, bound them, and test their failure modes.
4. Test the packed/bundled runtime under every supported host runtime, not just TypeScript source imports.
5. Keep configuration schemas allowlisted and tolerant of invalid optional input, while logging enough context to diagnose ignored settings.
