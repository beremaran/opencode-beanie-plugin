## OpenCode Integration Patterns

- The default export implements the plugin entrypoint, loads configuration using the OpenCode project directory, prefers `ctx.serverUrl`, and returns an event handler named `opentmux` [`src/index.ts:17-25`, `src/index.ts:29-49`, `src/index.ts:61-75`]. This is a small, direct integration pattern: keep OpenCode event handling thin and put lifecycle state in a manager.
- The event handler delegates to `TmuxSessionManager`, which accepts only `session.created` events with both an ID and `parentID`; this avoids opening panes for root sessions and ignores incomplete event payloads [`src/tmux-session-manager.ts:87-105`].
- Runtime activation is explicitly environment-sensitive: the manager enables itself only when configuration is enabled and `TMUX` is set [`src/tmux-session-manager.ts:42-47`]. The wrapper separately starts a tmux session when needed, while the plugin itself safely no-ops outside tmux [`src/bin/opentmux.ts:558-585`, `src/utils/tmux.ts:419-437`].
- Pane creation is serialized by `SpawnQueue`. Duplicate session IDs share one pending promise, items run one at a time, stale queued work is discarded, and failed spawns use bounded exponential backoff [`src/spawn-queue.ts:51-67`, `src/spawn-queue.ts:76-116`, `src/spawn-queue.ts:161-203`, `src/spawn-queue.ts:213-264`]. This is a useful pattern for event bursts and duplicate delivery.
- After panes exist, the manager polls `client.session.status()` every two seconds and closes panes when a session is idle, missing beyond the grace window, or older than the ten-minute timeout [`src/config.ts:67-69`, `src/tmux-session-manager.ts:141-157`, `src/tmux-session-manager.ts:171-231`]. Shutdown handling clears timers, stops the queue and reaper, and closes all tracked panes [`src/tmux-session-manager.ts:233-250`, `src/tmux-session-manager.ts:300-332`].
- Configuration is runtime-validated with Zod, including bounded layout, pane-size, retry, debounce, and column settings [`src/config.ts:3-20`, `src/config.ts:39-65`]. Project-local `opentmux.json` and `opencode-agent-tmux.json` are checked before the home configuration, and invalid/unreadable files fall back to defaults [`src/utils/config-loader.ts:10-27`, `src/utils/config-loader.ts:29-45`].

## Security and Reliability Pitfalls

- `attemptSpawnPane` builds a shell command string containing the server URL and session ID, then passes it as the tmux `split-window` command [`src/utils/tmux.ts:361-383`]. Although the outer Node process uses argument arrays, tmux executes that command through a shell; values should be strictly validated or shell-escaped before interpolation. The current code assumes server/session identifiers are safe.
- Several process helpers interpolate values into `execSync` shell strings, including `lsof` port queries, `ps` PID queries, `pgrep` patterns, and `ps` TTY queries [`src/utils/process.ts:8-31`, `src/utils/process.ts:49-76`, `src/utils/process.ts:113-124`]. Most current callers use numeric discovery results or constants, but the generic `findProcessIds(pattern)` path quotes a regex without shell escaping. Replacing these with non-shell process APIs or strict numeric validation would reduce injection risk.
- The reaper's server cleanup accepts any listener whose command contains `opencode`, `node`, or `bun`, then can terminate it after failed/empty status responses [`src/zombie-reaper.ts:428-449`, `src/zombie-reaper.ts:451-505`]. This is a broad ownership test and can affect an unrelated local service on ports 4096 onward. A PID identity check, explicit opt-in, and a server-specific marker would be safer.
- Automatic installation mutates the user's shell startup file by appending an alias and `OPENCODE_PORT` export [`src/scripts/install.ts:69-85`, `src/scripts/install.ts:128-158`]. The package's `postinstall` invokes this installer when the built file exists [`package.json:12-17`]. Installers should make this side effect explicit, preserve/backup existing configuration, and provide an uninstall path.
- The wrapper launches a detached updater by default, and the updater rewrites `~/.config/opencode/opencode.json`, migrates plugin names, and runs global `npm install -g <plugin>@latest` for configured plugins [`src/bin/opentmux.ts:41-57`, `src/scripts/update-plugins.ts:91-151`]. This is a high-impact supply-chain and configuration side effect; the opt-out exists (`OPENCODE_TMUX_DISABLE_UPDATES=1`) but is not the default behavior described to users.
- Config parse failures are silently ignored and indistinguishable from absent configuration [`src/utils/config-loader.ts:29-45`]. At minimum, a warning with the path and validation error would make operational failures diagnosable without exposing secrets.

## Testing Lessons

- Tests inject `spawnAsync` and mock `fetch`, making tmux and server behavior testable without requiring a real tmux session or OpenCode server [`src/__tests__/tmux.test.ts:23-40`, `src/__tests__/tmux.test.ts:67-73`, `src/__tests__/tmux.test.ts:84-115`]. The suite covers first-attempt success, retries, exhaustion, and empty pane IDs [`src/__tests__/tmux.test.ts:117-226`].
- Queue tests verify sequential processing, retry timing, inter-item delay, pending counts, callbacks, and request timestamps [`src/__tests__/spawn-queue.test.ts:29-77`, `src/__tests__/spawn-queue.test.ts:79-153`, `src/__tests__/spawn-queue.test.ts:155-219`]. These are good examples of testing asynchronous state machines through controlled promises rather than sleeps alone.
- Reaper tests cover URL filtering, active/zombie classification, grace-period behavior, repeated scans, and manual global reap behavior [`src/__tests__/zombie-reaper.test.ts:36-59`, `src/__tests__/zombie-reaper.test.ts:61-95`, `src/__tests__/zombie-reaper.test.ts:122-205`]. Missing high-value cases include malicious session/server strings, unrelated listeners on the scanned ports, malformed config diagnostics, shell-escaping, and shutdown while a spawn is in flight.
- `package.json` defines build and typecheck scripts but no test script; CI's publish workflow installs, builds, and publishes without running tests [`package.json:12-17`, `.github/workflows/publish.yml:34-39`]. A release gate should run the test suite and typecheck before publishing.

## Packaging and Distribution

- The package is ESM, exposes `dist/index.js` and declarations, provides the `opentmux` binary, and publishes only `dist` [`package.json:2-17`]. `tsup` emits the plugin, wrapper, installer, and updater as separate ESM entries and generates declarations only for the plugin entry [`tsup.config.ts:3-20`].
- The README's install path is global npm installation followed by adding `opentmux` to the OpenCode plugin list [`README.md:15-23`, `README.md:28-49`, `README.md:53-72`]. The package also includes a public-access publish configuration [`package.json:27-39`].
- Releases are triggered by published GitHub releases, use Bun to install/build, and publish to npm with provenance and OIDC-oriented permissions [`.github/workflows/publish.yml:3-14`, `.github/workflows/publish.yml:15-41`]. The workflow's build-before-publish ordering is sound, but it should add automated tests and avoid printing decoded OIDC claims unless there is a specific diagnostic need [`.github/workflows/publish.yml:29-39`].

## Overall Assessment

OpenTmux demonstrates a practical OpenCode plugin architecture: a minimal event adapter, validated configuration, serialized side effects, dependency injection for tmux tests, and bounded cleanup policies. Its main production risks are not the pane lifecycle itself but privileged local automation: shell interpolation, broad process ownership heuristics, automatic shell/config mutation, and silent global plugin updates. Those behaviors should be opt-in, narrowly scoped, and covered by release-gating tests before wider installation.
