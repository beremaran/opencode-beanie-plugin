This is a Bun/TypeScript OpenCode plugin that adds Google Antigravity OAuth, account rotation, a Google search tool, Gemini/Claude request translation, and session recovery. The package is published as a small source package: `package.json` exposes `index.ts` and `src` through its `files` field (`package.json:23-27`).

## OpenCode Integration Patterns

### Provider auth loader and OAuth method

The plugin returns the OpenCode plugin result with an `auth` extension for provider `google`, a loader, OAuth authorization method, and a tool (`src/plugin.ts:245-269`, `src/plugin.ts:270-401`). The loader receives OpenCode's `getAuth`, leaves non-OAuth records untouched, sets model costs to zero, and supplies a custom `fetch` implementation rather than an API key (`src/plugin.ts:248-268`). This is a useful pattern for adapting an existing provider without duplicating the provider SDK.

The OAuth method detects headless environments from SSH/OpenCode environment variables and falls back from a local browser callback to manual redirect URL entry (`src/plugin.ts:274-280`, `src/plugin.ts:108-215`). The README documents both the plugin registration and the local callback behavior (`README.md:22-36`).

### Event hook and recovery

The plugin uses the event hook to inspect `session.error`, identify recoverable thinking-block ordering errors, repair stored message parts, and prompt the session to continue (`src/plugin.ts:402-435`). Recovery is opt-out through `ANTIGRAVITY_SESSION_RECOVERY=0` (`src/plugin.ts:240-244`). The recovery module limits handling to assistant errors, extracts a message index when available, aborts the session before mutation, and guards concurrent processing with a `Set` (`src/plugin/recovery/index.ts:140-216`). This demonstrates a narrowly scoped event repair loop rather than treating every provider error as recoverable.

### Tool registration as an API workaround

`google_search` is registered through `tool()` with schema-defined query, URL, and thinking arguments (`src/plugin.ts:78-105`). Its implementation makes a separate upstream request using only native Google Search and URL Context tools (`src/plugin/search.ts:198-237`), matching the README's explanation that native search tools cannot coexist with custom function declarations in one Gemini request (`README.md:77-94`). The tool returns source links, retrieved URL status, and search queries (`src/plugin/search.ts:87-118`, `src/plugin/search.ts:151-179`).

### Fetch interception and protocol translation

The loader-installed fetch wrapper detects only Generative Language API URLs and routes them through Antigravity translation (`src/plugin/request.ts:50-61`; `src/plugin.ts:263-268`). The request layer handles model aliases, streaming SSE transformation, tool-call normalization, error rewriting, usage extraction, and Claude/Gemini transforms (`src/plugin/request.ts:28-48`, `src/plugin/request.ts:64-105`). Endpoint fallback is explicit and ordered daily, autopush, then production (`src/constants.ts:40-59`), with tests covering URL replacement for strings, `URL`, and `Request` inputs (`src/plugin/request.test.ts:151-184`).

### Multi-account state

Account state is separated from OpenCode auth details. `AccountManager` supports model-family-specific rate limits, paid-account preference, sticky current-account selection, rotation, and minimum wait calculation (`src/plugin/accounts.ts:24-40`, `src/plugin/accounts.ts:141-184`, `src/plugin/accounts.ts:247-261`). The plugin persists a combined refresh representation while keeping email and tier metadata in a separate JSON file (`src/plugin.ts:336-377`; `src/antigravity/oauth.ts:246-257`).

## Security and Privacy Lessons

- The OAuth client ID and client secret are hard-coded in source (`src/constants.ts:3-6`) and sent during both authorization-code exchange and refresh (`src/antigravity/oauth.ts:197-209`, `src/plugin/token.ts:75-85`). A distributed client secret is not confidential; maintainers should confirm the OAuth client's intended public-client posture, restrict redirect origins/scopes, and avoid representing it as a recoverable secret.
- Requested OAuth scopes include `cloud-platform`, profile/email, `cclog`, and experiments/configuration access (`src/constants.ts:8-14`). The scope set is broad relative to login and should be documented and minimized where possible.
- Refresh tokens and project IDs are written as plaintext JSON under `$XDG_DATA_HOME/opencode/antigravity-accounts.json` or the Windows roaming data directory (`src/plugin/storage.ts:80-93`, `src/plugin/storage.ts:195-205`). The README tells users where the file is stored and allows up to ten accounts (`README.md:49-58`). File permissions, OS keychain integration, and a clear threat model are not evident in this clone.
- The local callback server binds to `127.0.0.1`, validates the callback path, times out after five minutes, and closes after receiving a callback (`src/plugin/server.ts:23-40`, `src/plugin/server.ts:185-227`). That is a good baseline, but callback query validation is limited to presence of `code` and `state` before exchange (`src/plugin.ts:152-166`); state decoding validates the PKCE verifier shape but does not visibly bind state to a server-side session (`src/antigravity/oauth.ts:57-73`).
- The search tool accepts caller-supplied URLs and forwards them to provider URL context (`src/plugin.ts:81-84`, `src/plugin/search.ts:204-216`). URL retrieval, prompt injection from fetched pages, sensitive URL handling, and exfiltration boundaries should be treated as security concerns in documentation and tests.
- Debug logging is intentionally rich around tool parts and response metadata (`src/plugin/request.ts:120-220`). The code summarizes arguments rather than logging raw values in this area, but the wider logging path should be audited to ensure tokens, prompts, URLs, and response bodies never enter logs.
- The README explicitly warns that Google may block accounts and that the cited Antigravity terms prohibit third-party products (`README.md:13-18`). This is an important operational/legal disclosure for an auth plugin, not merely a troubleshooting note.

## Testing Lessons and Gaps

- Unit tests cover account initialization/rotation/rate-limit expiry and model-family isolation (`src/plugin/accounts.test.ts:7-155`), storage migrations from v1/v2 to v3 and invalid-state handling (`src/plugin/storage.test.ts:28-204`), OAuth tier detection across fallback responses (`src/antigravity/oauth.test.ts:17-142`), endpoint/model transformation and Claude thinking headers (`src/plugin/request.test.ts:6-149`), and thought-signature/tool-schema behavior (`src/plugin/transform/signature.test.ts:30-220`). These tests encode compatibility behavior rather than only happy-path authentication.
- The integration suite starts a real OpenCode server and exercises Gemini and Claude models with and without `google_search` (`tests/integration/setup.ts:18-24`, `tests/integration/google-search.test.ts:17-220`). It skips in CI and has a five-minute timeout (`tests/integration/google-search.test.ts:12-16`), which makes it appropriate for opt-in live validation but not a deterministic release gate.
- The package scripts make the distinction explicit: `test:unit` runs `src/**/*.test.ts`, while `test:integration` sets `CLAUDECODE=1` and uses a 300-second timeout (`package.json:5-8`). A useful practice is to retain separate deterministic and credential/network-dependent commands.
- No direct tests were observed for the local callback server, OAuth state tampering, token exchange error redaction, plaintext storage permissions, search URL abuse/prompt injection, session recovery mutations, or actual multi-account persistence through the complete OAuth callback flow. Those are the highest-value additions for a security-sensitive plugin.

## Packaging and Release Lessons

- The package uses Bun's module entrypoint and ESM mode, pins OpenCode SDK/plugin dependencies in the package manifest, and declares TypeScript as a peer dependency (`package.json:1-10`, `package.json:29-40`). Strict TypeScript settings include `strict`, `noUncheckedIndexedAccess`, `noFallthroughCasesInSwitch`, and `noImplicitOverride` (`tsconfig.json:17-27`).
- `files` keeps the npm payload focused on the root entrypoint and source tree (`package.json:23-27`), while `.gitignore` excludes dependencies, build output, coverage, logs, caches, and environment files (`.gitignore:1-29`).
- Release automation compares package versions, avoids duplicate tags, creates a GitHub release, and publishes with npm provenance (`.github/workflows/release.yml:28-55`, `.github/workflows/release.yml:112-126`). The workflow grants `contents: write` and `id-token: write` (`.github/workflows/release.yml:9-12`), so those permissions should remain narrowly scoped and protected by branch/release controls.
- The release script refuses a dirty worktree, supports dry-run and semantic bump selection, and checks for Bun, Git, and npm (`release.sh:60-125`). However, it invokes npm for versioning/publishing while the project otherwise documents Bun; keeping the toolchain intentional and testing the release script in CI would reduce drift.
- The README documents local file-URL loading, provider model configuration, debug logging, image modality requirements, tool-name sanitization, known plugin incompatibility, and cache-clearing update steps (`README.md:230-245`, `README.md:337-424`). This is strong operational documentation for a plugin whose behavior depends on OpenCode provider configuration.

## Practical Takeaways

1. Use OpenCode's provider `auth.loader` to inject a custom fetch path while preserving the provider's model catalog.
2. Keep OAuth, account rotation, persistence, protocol transforms, and recovery in separate modules with focused tests.
3. Treat persisted refresh tokens, broad OAuth scopes, local callbacks, and web-search URL ingestion as first-class security surfaces.
4. Separate fast unit tests from live OpenCode/provider integration tests and make the latter explicitly opt-in.
5. Publish only the entrypoint and source needed by the plugin, and pair version/tag checks with provenance-aware npm publishing.
