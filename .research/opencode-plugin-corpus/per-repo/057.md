## OpenCode patterns

- The plugin uses the server-plugin surface: it exports a stable `id`, an async `server` function, and a default object containing both ([index.js:4-4](../repos/zaradacht--opencode-host-notify-bridge/index.js#L4), [index.js:295-295](../repos/zaradacht--opencode-host-notify-bridge/index.js#L295), [index.js:539-542](../repos/zaradacht--opencode-host-notify-bridge/index.js#L539-L542)). Package metadata declares `oc-plugin: ["server"]` ([package.json:28-32](../repos/zaradacht--opencode-host-notify-bridge/package.json#L28-L32)).
- Runtime hooks are narrowly targeted: `tool.execute.after` records task/subagent session metadata, while `event` handles OpenCode events ([index.js:463-467](../repos/zaradacht--opencode-host-notify-bridge/index.js#L463-L467)). This is a useful pattern for avoiding notifications from task sessions by tracking output metadata (`sessionId`/`sessionID` and `background`) ([index.js:279-292](../repos/zaradacht--opencode-host-notify-bridge/index.js#L279-L292), [index.js:444-460](../repos/zaradacht--opencode-host-notify-bridge/index.js#L444-L460)).
- Event handling separates clearing an existing attention state from deciding whether to notify. Reply events clear all matching outstanding markers, abort errors clear all attention, and blocked/unknown events return before notification ([index.js:386-424](../repos/zaradacht--opencode-host-notify-bridge/index.js#L386-L424), [index.js:474-486](../repos/zaradacht--opencode-host-notify-bridge/index.js#L474-L486)). Cooldown, terminal bell, title updates, and a fallback endpoint loop make delivery best-effort rather than blocking OpenCode indefinitely ([index.js:489-535](../repos/zaradacht--opencode-host-notify-bridge/index.js#L489-L535)).
- Configuration is plain JSON from `~/.config/opencode/host-notify-bridge.json`; malformed or unreadable configuration silently falls back to defaults ([index.js:194-216](../repos/zaradacht--opencode-host-notify-bridge/index.js#L194-L216)). Endpoint precedence supports plugin options, singular/plural config values, and container-oriented defaults ([index.js:219-243](../repos/zaradacht--opencode-host-notify-bridge/index.js#L219-L243)).

## Pitfalls and design lessons

- The documented default event set is only `permission.asked`, `question.asked`, and `session.idle` ([README.md:28-32](../repos/zaradacht--opencode-host-notify-bridge/README.md#L28-L32)); however, the implementation also defaults to `session.error` and `session.failed` ([index.js:6-12](../repos/zaradacht--opencode-host-notify-bridge/index.js#L6-L12)), and the server allowlist includes them ([bin/opencode-host-notify-server.mjs:20-26](../repos/zaradacht--opencode-host-notify-bridge/bin/opencode-host-notify-server.mjs#L20-L26)). The repository guidance repeats the narrower three-event policy ([AGENTS.md:28-36](../repos/zaradacht--opencode-host-notify-bridge/AGENTS.md#L28-L36)). This is configuration/documentation drift that can cause unexpected alerts.
- The plugin’s `enabled` default depends on container detection, so an ordinary host session is disabled unless explicitly enabled, while a container-like environment enables it ([index.js:96-103](../repos/zaradacht--opencode-host-notify-bridge/index.js#L96-L103), [index.js:295-302](../repos/zaradacht--opencode-host-notify-bridge/index.js#L295-L302)). This is convenient for the target use case but should be made explicit in installation diagnostics.
- Notification delivery is intentionally fail-soft: each endpoint is attempted with an abort timeout, failures are swallowed while trying the next endpoint, and the final fallback is only a terminal bell ([index.js:245-265](../repos/zaradacht--opencode-host-notify-bridge/index.js#L245-L265), [index.js:523-534](../repos/zaradacht--opencode-host-notify-bridge/index.js#L523-L534)). Operators should not interpret an HTTP success from the plugin as proof that a desktop notification was displayed.
- The host process treats `allowedEvents` as an allowlist unless it is empty, and applies blocked events first, including wildcard prefixes ([bin/opencode-host-notify-server.mjs:151-163](../repos/zaradacht--opencode-host-notify-bridge/bin/opencode-host-notify-server.mjs#L151-L163)). Keeping filtering at both the plugin and host boundary is a useful defense against configuration mistakes.

## Security

- The server defaults to listening on every interface (`0.0.0.0`) and defaults to an empty token ([bin/opencode-host-notify-server.mjs:9-13](../repos/zaradacht--opencode-host-notify-bridge/bin/opencode-host-notify-server.mjs#L9-L13)). Authentication is only enforced when a non-empty token is configured ([bin/opencode-host-notify-server.mjs:187-193](../repos/zaradacht--opencode-host-notify-bridge/bin/opencode-host-notify-server.mjs#L187-L193)). On a reachable network this can expose an unauthenticated notification/speech trigger; bind to loopback or require a token before exposing the port.
- The request body is accumulated without a size limit before JSON parsing ([bin/opencode-host-notify-server.mjs:195-205](../repos/zaradacht--opencode-host-notify-bridge/bin/opencode-host-notify-server.mjs#L195-L205)). A reachable unauthenticated or token-compromised listener is therefore susceptible to memory/connection exhaustion. There is also no rate limit beyond the client-side event cooldown ([index.js:489-494](../repos/zaradacht--opencode-host-notify-bridge/index.js#L489-L494)).
- Host-side commands are spawned with argument arrays and detached stdio rather than through a shell ([bin/opencode-host-notify-server.mjs:59-69](../repos/zaradacht--opencode-host-notify-bridge/bin/opencode-host-notify-server.mjs#L59-L69)). The AppleScript fallback still interpolates request-derived title/body values into a script, with escaping for backslashes, quotes, and newlines ([bin/opencode-host-notify-server.mjs:72-100](../repos/zaradacht--opencode-host-notify-bridge/bin/opencode-host-notify-server.mjs#L72-L100)); this boundary deserves regression tests for control characters and AppleScript syntax.
- The client sends the configured shared token in `x-opencode-token` and allows arbitrary configured HTTP endpoint URLs ([index.js:245-260](../repos/zaradacht--opencode-host-notify-bridge/index.js#L245-L260), [index.js:219-240](../repos/zaradacht--opencode-host-notify-bridge/index.js#L219-L240)). Configuration permissions and endpoint trust are therefore security-sensitive, especially because example configuration places the token in a plain JSON file ([examples/host-notify-bridge.json:1-8](../repos/zaradacht--opencode-host-notify-bridge/examples/host-notify-bridge.json#L1-L8)).

## Testing

- No automated test files or test configuration are present in the repository tree. The repository’s own minimum verification is manual: import the plugin, boot the host server, POST a sample payload, and load it through an OpenCode `file://` plugin path ([AGENTS.md:68-79](../repos/zaradacht--opencode-host-notify-bridge/AGENTS.md#L68-L79)).
- README supplies a manual `curl` request with JSON and the token header ([README.md:175-187](../repos/zaradacht--opencode-host-notify-bridge/README.md#L175-L187)), but there is no evidence of automated coverage for event filtering, cooldowns, endpoint fallback, attention clearing, malformed JSON, auth failures, payload limits, or command escaping.
- The most valuable tests would isolate the exported server hook with mocked `fetch` and timers, then exercise the HTTP server separately with loopback binding. They should assert default/blocked events, subagent/background suppression, reply/abort clearing, token enforcement, malformed/oversized requests, and safe handling of notification text.
