## OpenCode patterns

- **Minimal loader entrypoint.** The public entrypoint only re-exports `ModelDiscoveryPlugin` (`src/index.ts:1`), while the plugin factory returns the `config` and `event` hooks expected by the host (`src/plugin/index.ts:9-35`). Keeping the loader surface small makes the integration point easy to test and keeps implementation details private.
- **Startup config mutation with bounded waiting.** The config hook validates input, injects helper commands, starts `enhanceConfig`, and races it against a timeout (`src/plugin/config-hook.ts:31-75`). The timeout is at least five seconds and expands to the largest configured provider timeout (`src/plugin/config-hook.ts:11-21`). This is a useful pattern for startup work that must finish early enough to affect the active config without making a hung provider block OpenCode indefinitely.
- **Provider-level configuration boundary.** Discovery is selected from `provider.<id>.options.modelsDiscovery`; compatibility is inferred from the npm package, `/v1` URL, or an explicit endpoint, and `enabled` can force discovery (`src/plugin/enhance-config.ts:215-240`, `src/utils/openai-compatible-api.ts:119-139`). The README explicitly documents the migration away from plugin-global options (`README.md:75-126`).
- **Preserve user configuration while replacing generated state.** The implementation tracks injected model object identities, removes only previously injected models on refresh failure, and merges discovered models before matching explicit models (`src/plugin/enhance-config.ts:52-70`, `src/plugin/enhance-config.ts:264-287`, `src/plugin/enhance-config.ts:335-403`). This avoids treating generated inventory as authoritative over user-owned model definitions.
- **Graceful enrichment.** Generic discovery succeeds independently of optional models.dev, LiteLLM, Bifrost, vLLM, OmniRoute, or LM Studio metadata enrichment; failed enrichment logs a warning and leaves capability fields unset (`src/plugin/enhance-config.ts:292-333`, `README.md:171-221`). This is a good failure-isolation pattern for best-effort metadata.
- **Host auth fallback.** Credential precedence is explicit API key, resolved OpenCode provider key, then `/connect` auth-store key (`src/plugin/enhance-config.ts:165-198`); host selection distinguishes OpenCode and Mimocode data directories (`src/plugin/enhance-config.ts:113-131`). The README documents the same precedence and host behavior (`README.md:231-254`).
- **Non-destructive command injection.** The plugin adds `/models-discovery:config` and, for legacy config, `/models-discovery:migrate`, but leaves an existing user command unchanged (`src/plugin/commands.ts:190-238`). The migration template also tells the assistant not to edit managed config or duplicate credentials (`src/plugin/commands.ts:6-60`).

## Security lessons and pitfalls

- **Treat configured endpoints as a trust boundary.** Discovery builds a URL from provider-controlled `baseURL` and `endpoint` and sends the resolved API key as a Bearer header (`src/utils/openai-compatible-api.ts:27-30`, `src/utils/openai-compatible-api.ts:75-108`). This is appropriate for user-configured providers, but a malicious or accidentally wrong endpoint can receive credentials; deployments that consume untrusted config should restrict schemes/hosts or require explicit consent.
- **Response buffering is unbounded.** `requestJson` concatenates every response chunk into a string before parsing and has no maximum body size (`src/utils/openai-compatible-api.ts:45-63`). A reachable provider can therefore consume substantial memory during discovery. A production hardening lesson is to cap response bytes and abort oversized responses while retaining the existing timeout.
- **Cache writes are defensively handled.** Provider IDs are URI-encoded into one filename component (`src/plugin/provider-model-store.ts:82-84`), state is accepted only when version, identity, timestamp, and model IDs validate (`src/plugin/provider-model-store.ts:26-53`), and writes use a private directory, mode `0600`, temporary file, and rename (`src/plugin/provider-model-store.ts:127-149`). The store recursively removes credential-like fields before persistence (`src/plugin/provider-model-store.ts:56-79`).
- **Do not let stale inventory resurrect models.** Expired cache entries trigger a refresh; if refresh fails, generated stale models are removed while explicit models remain (`src/plugin/enhance-config.ts:256-287`). The regression test covers this behavior (`test/plugin.test.ts:770-796`). This prevents a cache from silently presenting unavailable or revoked models as current.
- **Protect secrets from logs and cache.** The code forwards keys only in request headers and logs discovery metadata such as provider, URL, and endpoint rather than the key (`src/utils/openai-compatible-api.ts:81-89`, `src/plugin/enhance-config.ts:262-273`). The cache sanitization is defense in depth, but arbitrary model metadata still deserves scrutiny because the sanitization list is name-based rather than schema-based (`src/plugin/provider-model-store.ts:56-73`).
- **Configuration validation is partial by design.** Validation rejects malformed timeout, cache, and field-filter shapes and warns about filters placed at the wrong level (`src/utils/validation/validate-config.ts:4-46`, `src/utils/validation/validate-config.ts:49-126`), but the main config is typed as `any` and provider fields are not comprehensively schema-validated (`src/plugin/config-hook.ts:31-40`). Consumers should not treat plugin validation as a full OpenCode config validator.

## Packaging and maintenance

- The package is ESM, exports the TypeScript source entrypoint, publishes only `src`, requires OpenCode `>=1.4.0`, and declares `@opencode-ai/plugin` as a peer dependency (`package.json:3-12`, `package.json:41-60`). `prepublishOnly` runs the build, which chains typecheck and tests (`package.json:14-27`). This is simple packaging, but publishing source TypeScript makes consumer/toolchain compatibility part of the contract.
- Strict TypeScript and declaration/source-map generation are enabled (`tsconfig.json:1-17`). The clone contains both `bun.lock` and `package-lock.json`, while CI installs with Bun (`.github/workflows/publish.yml:25-40`); maintainers should keep both lockfiles synchronized or standardize on one installer.
- Publishing is gated by a package.json change or manual dispatch, installs dependencies, runs `bun scripts/release.ts publish`, and requests `contents: write` plus npm trusted-publishing `id-token: write` (`.github/workflows/publish.yml:3-17`, `.github/workflows/publish.yml:39-51`). The release workflow separately prepares a version-bump PR after `bun install` (`.github/workflows/release.yml:20-58`).
- **Release-script footgun.** `prepareRelease` runs `git status`, then `git add -A` before committing the version bump (`scripts/release.ts:228-237`). Running it in a dirty checkout can commit unrelated user changes, so release automation should either require a clean worktree or stage only the intended manifests.
- The release script runs `npm run build` before both prepare and publish and checks for existing remote tags and npm versions before creating/publishing (`scripts/release.ts:228-251`, `scripts/release.ts:257-300`). Those checks improve rerun safety, although the workflow still relies on external GitHub/npm credentials and mutable `bun-version: latest` (`.github/workflows/publish.yml:25-34`).

## Overall assessment

`opencode-models-discovery` is a strong example of a startup-config OpenCode plugin: it uses a small loader, provider-scoped settings, bounded asynchronous discovery, non-destructive model merging, explicit auth precedence, and a carefully validated cache. Its best reusable lessons are to isolate optional enrichment from core behavior, preserve explicit user config, test actual request contracts and cache security, and make host lifecycle timing explicit. The main residual risks are credential forwarding to arbitrary configured endpoints, unbounded HTTP response buffering, incomplete schema validation, and release automation that can stage unrelated worktree changes.
