## OpenCode integration patterns

### Plugin shape and tool registration

- The entrypoint imports `Plugin` and `tool` from `@opencode-ai/plugin`, creates one async plugin factory, and returns a hook map (`index.ts:10-13`, `index.ts:811-812`, `index.ts:1711-1712`, `index.ts:1765`).
- Tools are registered under `hooks.tool` and are conditionally constructed from environment feature flags, allowing the installation to expose only enabled capabilities (`index.ts:57-61`, `index.ts:866-870`, `index.ts:1098-1099`, `index.ts:1178-1179`). This is a useful pattern when an expensive or side-effecting capability must be opt-out rather than always active.
- `tool.definition` appends runtime notes to the tool description. The notes disclose the active session-directory path behavior, read-only restrictions, and missing credentials at the point where the model sees the tool (`index.ts:379-427`, `index.ts:1282-1287`).
- A system-transform hook adds a de-duplicated routing hint that distinguishes large/scattered edits, exact replacements, new files, local exploration, and public-repository exploration (`index.ts:1289-1301`, `index.ts:434-471`). The packaged policy makes the same distinction explicit and says it belongs in always-on `instructions`, not a skill (`instructions/morph-tools.md:1-8`, `instructions/morph-tools.md:16-30`).

### Hook lifecycle and message mutation

- The plugin uses `chat.message` for a `/morph compact` command, `chat.params` to capture the model context limit, `experimental.session.compacting` to arm native compaction, `experimental.chat.messages.transform` to pre-compress selected history, and `event` to clear stale state after `session.compacted` (`index.ts:1386-1468`, `index.ts:1691-1708`). This demonstrates composing several narrowly scoped hooks around one OpenCode lifecycle rather than attempting to implement compaction in a tool call.
- The transform mutates `output.messages` in place with `splice` or a push loop. The source explains that OpenCode reads the original array after triggering the hook, so assigning a replacement array would silently fail (`index.ts:268-295`). This is an important hook-contract pitfall to verify against the OpenCode version being targeted.
- Compaction state and forced-compaction flags are keyed by session ID, preventing a parent session from contaminating a subagent or sibling session (`index.ts:118-155`, `index.ts:1527-1535`). The plugin degrades to no-op when it cannot recover a session ID rather than risking cross-session state use (`index.ts:1527-1531`).
- The native compaction path preserves OpenCode's persisted-summary mechanism: Morph compresses the selected messages, then OpenCode continues its native summary path (`README.md:83-94`, `index.ts:1463-1524`, `index.ts:1688-1707`).

### Tool behavior

- `morph_edit` resolves relative paths against the active plugin/session directory, reads existing files, supports complete content for missing files, and refuses marker-based creation (`index.ts:938-969`). The README and instruction policy also teach that new files should use native `write` (`README.md:144-148`, `instructions/morph-tools.md:20-27`).
- The edit tool blocks `plan` and `explore` agents by default, with an explicit opt-in override (`index.ts:64-69`, `index.ts:919-936`). This is a concrete safety boundary for tools that write to disk.
- For local search, the plugin passes the session worktree as `repoRoot`, not merely the current directory (`index.ts:405-408`, `index.ts:1124-1132`). For public search, it requires exactly one of `owner_repo` or `github_url`, validates the host and path, performs a bounded GitHub lookup, and offers suggestions on resolution failure (`index.ts:608-705`, `index.ts:714-753`, `index.ts:1229-1271`).
- TUI output is customized through `tool.execute.after`, with titles for success, failure, no-result, and safety-block cases plus provider/version metadata (`index.ts:1304-1384`). This keeps user-facing presentation separate from tool execution while making safety outcomes visible.

## Security and reliability lessons

- Credentials are sourced from `MORPH_API_KEY` or a config field, with the environment variable taking precedence; missing credentials disable remote tools and produce a warning rather than crashing plugin initialization (`README.md:33-50`, `index.ts:16-19`, `index.ts:840-864`). The reportable risk is that the README explicitly permits a secret in `opencode.json`; deployments should ensure that config is protected and excluded from version control.
- The edit path has layered data-loss defenses: mandatory markers for files over ten lines, a warning for smaller unmarked replacements, marker-leakage detection, and a dual threshold for catastrophic shrinkage (>60% character loss and >50% line loss) before any write (`index.ts:972-995`, `index.ts:1022-1071`). The write occurs only after those checks (`index.ts:1073-1079`).
- The tool description warns that omitting markers deletes surrounding code and requires unique context anchors (`index.ts:878-897`). This is a strong model-facing mitigation for partial-file merge APIs, but the API remains capable of writing arbitrary paths supplied to `Bun.file`; callers should rely on OpenCode agent permissions and workspace policy for path authorization (`index.ts:938-959`, `index.ts:1073-1078`).
- GitHub requests use a fixed `github.com` host check, standard Accept/User-Agent headers, and an abort timeout (`index.ts:665-705`, `index.ts:707-721`). Search suggestions are capped at five entries (`index.ts:24-26`, `index.ts:756-807`).
- SDK logging uses `client.app.log` and falls back to stderr, avoiding stdout pollution that could corrupt machine-readable OpenCode output (`index.ts:811-827`; the changelog records the motivation at `CHANGELOG.md:93-105`).
- Error paths return actionable text and log timing/status instead of throwing through the tool boundary (`index.ts:1013-1017`, `index.ts:1163-1173`, `index.ts:1266-1271`). Compaction failures preserve the prior/stable or native path (`index.ts:1518-1524`, `index.ts:1618-1625`, `index.ts:1679-1685`).

## Testing lessons and gaps

- The test suite is broad and regression-oriented. It tests marker normalization, marker leakage, truncation thresholds, serialization, cache-key stability, compaction decisions, runtime hooks, path resolution, malformed search contexts, falsy errors, and Bun async-generator behavior (`index.test.ts:123-204`, `index.test.ts:206-387`, `index.test.ts:541-757`, `index.test.ts:776-910`, `index.test.ts:921-1092`, `index.test.ts:1094-1198`).
- Packaging guidance is tested as content: the instruction file must contain routing rules and the README must document tools, credentials, compaction, and config (`index.test.ts:87-120`). This guards against a shipped package whose runtime and model-facing setup instructions drift apart.
- Runtime tests use cache-busting dynamic imports and temporarily restore environment variables (`index.test.ts:29-51`), and mock SDK prototypes for deterministic compaction/search tests (`index.test.ts:969-987`, `index.test.ts:1094-1113`). These are practical patterns for module-level environment configuration and network-backed SDKs.
- The repository's recorded test command is `bun test` (`package.json:17-21`, `.github/workflows/ci.yml:21-31`), but running it in the audited clone failed before tests executed because `@morphllm/morphsdk` was not installed: `Cannot find module '@morphllm/morphsdk'`. Thus no runtime test result can be claimed from this clone. The CI workflow also lacks a matrix for multiple OpenCode SDK versions and does not show live API tests in CI.
- Some tests duplicate internal helper implementations rather than importing them (`index.test.ts:14-27`). That makes pure helper behavior easy to test, but can let the test copy diverge from production; exported helpers or integration-level assertions would reduce that risk.

## Packaging and release lessons

- `package.json` declares ESM, `dist/index.js` as `main`, declarations, an explicit export, and a narrow `files` allowlist including `dist`, README, license, and `instructions/` (`package.json:1-16`). The allowlist is particularly important because the OpenCode config points at the packaged instruction file (`README.md:59-71`).
- Build, test, typecheck, and CI scripts are explicit; TypeScript is strict and emits declarations (`package.json:17-21`, `tsconfig.json:1-15`). Dependencies include the Morph SDK and OpenCode plugin/SDK packages (`package.json:23-30`). A maintenance risk is the unbounded `@opencode-ai/plugin: "latest"` dependency (`package.json:25`), which can introduce API drift without a package change.
- CI validates both the package's own checks and installation from an actual packed tarball into clean npm and Bun consumers (`.github/workflows/ci.yml:33-69`). This catches a class of failures that unit tests and local workspace resolution miss, including omitted packaged files and dependency-resolution differences.
- Release automation runs tests/typecheck/build, bumps and commits the version, force-updates the tag, publishes with npm trusted publishing, and creates/updates a GitHub release (`.github/workflows/release.yml:18-89`). The workflow has broad write permissions (`contents: write`, `id-token: write`) and uses `git push ... --force` (`.github/workflows/release.yml:22-24`, `.github/workflows/release.yml:70-78`); this is operationally effective but deserves tight branch protection and review because a compromised workflow could rewrite release tags.
- The changelog documents several useful evolution patterns: moving away from duplicated skill/instruction guidance, adding packaged instructions, adding readonly protection, and adding corruption guards (`CHANGELOG.md:36-75`, `CHANGELOG.md:89-105`).

## Bottom line

This is a strong example of an OpenCode plugin that treats hooks as a lifecycle integration surface, keeps model-facing routing instructions close to the packaged tool, isolates mutable state per session, and validates remote edit output before writing. The highest-value lessons are to verify in-place hook mutation semantics, make write tools fail closed for readonly agents, add corruption guards around model-generated edits, test the packed artifact in both npm and Bun, and pin or deliberately manage OpenCode API dependencies. The primary audit limitation is environmental: `bun test` could not start because the clone's dependencies were absent.
