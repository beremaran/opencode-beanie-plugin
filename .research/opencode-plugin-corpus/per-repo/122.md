## What It Does

The plugin addresses a specific OpenCode worktree workflow: copying project memory from the main repository into a newly created worktree. The README describes the problem as worktrees receiving only empty `.opencode/memory/` frontmatter scaffolds and says synchronization occurs on every session initialization without overwriting existing changes (`README.md:3-12`). The documented installation is a package name in `opencode.json` (`README.md:14-23`).

The implementation follows that description by exporting a default async value typed as OpenCode's `Plugin`. It receives OpenCode's `directory`, resolves a main repository, conditionally syncs `.opencode/memory`, and returns an empty hook object (`src/plugin.ts:16`, `src/plugin.ts:111-126`). It does not register named event hooks; initialization-time behavior is achieved by doing the work while the plugin factory runs.

## OpenCode Patterns

### Minimal plugin entrypoint

The most reusable integration pattern is a small default export:

- Import the `Plugin` type from `@opencode-ai/plugin` (`src/plugin.ts:16`).
- Export `const plugin: Plugin = async ({ directory }) => { ... }` as the default (`src/plugin.ts:111-126`).
- Return `{}` when no event handlers are needed (`src/plugin.ts:123-124`).

This is appropriate for startup/session initialization side effects and keeps the OpenCode-facing surface narrow. The package points `main` directly at the TypeScript source (`package.json:5-8`), matching a Bun-oriented runtime/package workflow rather than committing compiled JavaScript.

### Worktree-aware startup behavior

The README's operational sequence is concrete: inspect `.git`, parse `gitdir:`, locate the main repository, inspect memory, then copy only when the destination is empty (`README.md:25-32`). The source separates these concerns into `getMainRepoDir`, `memoryIsEmpty`, and `syncMemoryDir` (`src/plugin.ts:30-49`, `src/plugin.ts:51-79`, `src/plugin.ts:81-109`). That separation makes the filesystem policy understandable and gives future tests natural unit boundaries, even though the helpers are currently private and untested.

### Dependency and compiler baseline

The package declares the OpenCode plugin type/runtime dependency, TypeScript, Node types, strict checking, ES2022 output, ES module syntax, and bundler resolution (`package.json:25-30`, `tsconfig.json:2-14`). This is a sensible baseline for a Bun-compatible TypeScript plugin. The only script is `typecheck`, invoking `tsc --noEmit` (`package.json:35-37`).

## Evidence-Based Pitfalls

### Destination emptiness is under-checked

The README says worktrees with existing memory content are skipped (`README.md:29-32`), but `memoryIsEmpty` reads only `dstMemory/project.md` and returns `true` if that file is absent or unreadable (`src/plugin.ts:88-109`). Consequently, a destination containing other populated memory files but no `project.md` is treated as empty. Even when `project.md` exists, content in other files is not considered. The subsequent copy writes every source regular file to the destination (`src/plugin.ts:114-120`, `src/plugin.ts:34-49`), so an existing file with the same name can be overwritten.

### The scaffold detector is permissive and format-coupled

The detector treats any non-frontmatter line beginning with one of five prefixes as scaffold metadata, without validating delimiters, values, or the complete frontmatter structure (`src/plugin.ts:88-105`). It is coupled to the exact keys produced by the assumed `ensureSeed()` format (`src/plugin.ts:82-87`). A future OpenCode memory schema change can cause false positives or false negatives; arbitrary project content such as `label: ...` is also classified as metadata.

### Worktree path parsing is platform- and format-sensitive

`getMainRepoDir` reads `.git` synchronously, requires a literal `gitdir:` prefix, splits the path on `/`, finds the last `worktrees` component, and reconstructs the parent using `dirname` (`src/plugin.ts:60-76`). This assumes POSIX separators and an absolute, canonical gitdir path. It does not resolve relative `gitdir:` values, normalize paths, verify that the referenced worktree metadata is valid, or ask Git for the common directory. The broad catch makes all parsing failures silently indistinguishable from a normal non-worktree directory (`src/plugin.ts:77-78`).

### Filesystem operations are not transactional

The plugin checks source existence and destination state before copying, then reads and writes files one at a time (`src/plugin.ts:34-47`, `src/plugin.ts:118-120`). Concurrent OpenCode processes or another writer can change the directory between the check and writes. A failed read/write can leave a partially synchronized directory, and there is no logging or error reporting at the plugin boundary. The use of `writeFile` also follows destination symlinks, so a malicious or accidentally linked destination file could redirect a write outside the intended memory directory (`src/plugin.ts:43-45`).

### Sync scope is intentionally shallow

`syncMemoryDir` copies regular files only and explicitly skips directories (`src/plugin.ts:38-45`). This matches the README's “memory files” use case but does not preserve nested memory content, permissions, timestamps, or symlink semantics. The behavior should be stated as a non-recursive copy rather than inferred from the high-level “copies all memory files” wording (`README.md:29-30`).

## Security Lessons

- Treat repository-derived paths as untrusted input even when the plugin is local. The current parser reconstructs a path from `.git` content and writes into a path derived from the active directory (`src/plugin.ts:60-76`, `src/plugin.ts:114-120`). Normalize and validate the common repository directory, preferably using Git's own path resolution or a robust path API.
- Avoid following destination symlinks for a synchronization tool. Use safe create/replace semantics or explicitly reject symlinked entries before writing; current `writeFile` behavior follows them (`src/plugin.ts:41-45`).
- Make the no-overwrite guarantee enforceable per file, not just a preflight heuristic. The current preflight checks a single `project.md`, then unconditionally writes source names (`src/plugin.ts:88-109`, `src/plugin.ts:41-45`).
- Keep failures observable. Silent catches in worktree detection (`src/plugin.ts:61-78`) are useful for avoiding startup crashes, but should be paired with bounded diagnostics for malformed paths or denied access so users can distinguish “not a worktree” from “sync could not run.”

## Testing Lessons

The pinned repository contains no tests or test script; `package.json` exposes only `typecheck` (`package.json:35-37`), and the tracked file set contains no test files. This leaves the central behavior unverified. A robust test suite should cover:

- Non-worktree directories and `.git` directories, not only `.git` files (`src/plugin.ts:60-66`).
- Absolute and relative `gitdir:` values, paths with spaces, and platform-specific separators (`src/plugin.ts:67-76`).
- A missing `project.md`, a populated non-`project.md` memory file, malformed frontmatter, and a changed scaffold schema (`src/plugin.ts:88-109`).
- Existing destination files, nested source directories, symlinks, empty source directories, and partial-copy failures (`src/plugin.ts:34-49`).
- The plugin factory's no-op behavior for ordinary repositories and its conditional invocation of synchronization (`src/plugin.ts:111-124`).

Because the helpers are private, tests would either need filesystem-level integration fixtures or a small refactor to export/test pure path and memory-state helpers. Either route should assert that existing user data is never overwritten, since that is the primary safety promise in the README (`README.md:9-12`).

## Packaging and Release Lessons

- The package is publishable as a public MIT package and includes repository metadata, keywords, author, license, and public access configuration (`package.json:1-24`).
- `files: ["src"]` restricts the published payload to source files (`package.json:7-8`), which is compact but means README/license inclusion should be confirmed with an actual package preview before release. There is no explicit `types` field or compiled `dist` artifact (`package.json:7-8`, `package.json:35-37`).
- `main: "src/plugin.ts"` and the Bun engine declaration make the runtime/toolchain assumption explicit (`package.json:5-8`, `package.json:32-34`). Consumers or registries that expect JavaScript entrypoints may not handle this equally; a release check should validate installation in the target OpenCode/Bun environment.
- The repository ignores all lockfiles (`.gitignore:1-3`) and contains no lockfile in the clone. That makes dependency resolution less reproducible, especially with ranges such as `@opencode-ai/plugin: ^1.0.0` and `typescript: ^5.8.0` (`package.json:25-30`). A published plugin should retain a lockfile for development/CI reproducibility or otherwise pin and verify the release toolchain.
- Typechecking is the only automated packaging gate (`package.json:35-37`). Add a package-content check, install smoke test, and runtime smoke test before publishing.

## Bottom Line

This is a clear example of the smallest useful OpenCode plugin: a typed default factory, access to `directory`, startup side effects, and an empty returned hook map (`src/plugin.ts:16`, `src/plugin.ts:111-126`). Its strongest product lesson is to make a narrowly scoped workflow fix that is inert outside worktrees (`README.md:25-32`). Its main engineering lesson is that a high-level “never overwrite changes” promise requires comprehensive directory-state detection, per-file safety checks, path normalization, observable errors, and tests; the current implementation supplies none of those beyond a single `project.md` heuristic and broad error suppression (`src/plugin.ts:88-120`).
