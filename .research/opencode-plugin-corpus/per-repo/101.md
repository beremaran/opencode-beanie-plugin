- **Scope:** The manifest's `analysisPath` is the clone root; no separate manifest subdirectory was specified.
- **Classification:** Bun/TypeScript CLI orchestrator, not an OpenCode plugin. The README describes it as a CLI wrapper and says “No plugins required” (`README.md:75-79`), while OpenCode is only the default selectable agent (`README.md:40-51`).

## Architecture And OpenCode Patterns

- The package exposes `ralph` through `bin/ralph.js`, which delegates to `ralph.ts` under Bun (`package.json:5-13`; `bin/ralph.js:1-13`). This is a useful compatibility shape for a Bun implementation that still gives npm users a conventional executable entrypoint.
- Agent integration is data-driven: built-in agent records provide command, argument builder, environment builder, output parser, and display name (`ralph.ts:58-65`, `ralph.ts:279-328`). OpenCode maps to `opencode run`, optionally adds `-m`, extra flags, and the prompt as a separate argument (`ralph.ts:138-145`). Passing an argument array to `Bun.spawn` avoids interpolating the prompt into a shell command (`ralph.ts:2578-2586`).
- OpenCode plugin isolation is explicit rather than implicit. When requested, Ralph reads user, project `.ralph`, and legacy `.opencode` configs, retains only plugin names matching `/auth/i`, and writes a generated config (`ralph.ts:1410-1448`). The generated config uses the current OpenCode schema URL (`ralph.ts:1436-1438`).
- The generated permission policy covers read/edit, search, shell, task, web, question, and LSP capabilities (`ralph.ts:1450-1470`). This demonstrates how a non-plugin harness can provide a deterministic OpenCode runtime configuration, but it is also a high-impact security boundary (see below).
- Loop state is repository-local under `.ralph`, including active state, context, history, task attempts, questions, and the Codex goal ledger (`ralph.ts:27-35`). The design treats files, git state, and logs as cross-iteration memory, and the goal-mode prompt explicitly tells the agent to use those sources of truth (`ralph.ts:1852-1857`).
- Completion is deliberately gated: a promise must be the final non-empty line, with a stream-JSON full-text fallback (`completion.ts:15-49`; `ralph.ts:1916-1925`). Tasks mode adds both checkbox completeness and per-task minimum-iteration checks (`ralph.ts:2665-2691`; `ralph.ts:1023-1039`).

## Evidence-Backed Lessons

### Reliability And UX

- Separate stream parsing from orchestration. `completion.ts` handles Claude/Qwen and Cursor JSON stream shapes, ignores tool-use blocks, and extracts user-visible text (`completion.ts:79-149`, `completion.ts:151-217`). This keeps promise detection from depending on raw provider formatting.
- Persist operational telemetry, not just a completion flag. Each iteration records agent/model, duration, exit code, completion status, tools, modified files, and errors (`ralph.ts:453-475`, `ralph.ts:2705-2722`). The status command surfaces recent iterations and repeated-error/no-progress indicators (`ralph.ts:595-633`).
- Graceful cancellation is implemented at three layers: abort stream reads, stop heartbeat output, and terminate the child process; state and pending questions are then cleared (`ralph.ts:2447-2482`). The catch path repeats cleanup and records a failed iteration, reducing orphaned-process and state-corruption risk (`ralph.ts:2930-2975`).
- Use controlled fake executables for integration tests. The suite creates temporary fake agents, captures arguments/prompts, tests inactivity retries, goal invocation, task gates, resume behavior, and SIGINT cleanup (`tests/ralph.test.ts:246-315`, `tests/ralph.test.ts:318-475`, `tests/ralph.test.ts:825-897`; `tests/sigint-cleanup.test.ts:99-146`). This is stronger than only unit-testing parser helpers.
- Test negative completion cases, not only success. The tests reject promises appearing early or with the wrong value, require at least one task, and verify incomplete checkboxes fail the gate (`tests/ralph.test.ts:15-103`). A model-error regression test also ensures benign project output containing “model not found” does not abort a successful run (`tests/model-error-detection.test.ts:38-77`; implementation rationale `ralph.ts:2776-2795`).

### Security And Safety Pitfalls

- The default is permissive: `allowAllPermissions` starts true (`ralph.ts:1088-1113`), the CLI documents auto-approval as the default (`README.md:227-250`), and OpenCode's generated policy allows shell and broad tool capabilities (`ralph.ts:1450-1467`). A safer deployment should require explicit opt-in, scope permissions, and make the effective policy visible before execution.
- Other backends receive equivalent bypass flags, including Claude `--dangerously-skip-permissions`, Codex full-auto, Cursor `--force`, and Qwen `--yolo` (`ralph.ts:146-185`). The wrapper therefore amplifies the security posture of every selected agent; prompts should not be treated as a trust boundary.
- Auto-commit can stage and commit every working-tree change after an iteration (`ralph.ts:2904-2917`). This is convenient, but can commit unrelated user work or generated secrets. The documented `--no-commit` mode should be the safer default for shared or dirty repositories (`README.md:246-249`; `docs/ralph-omx.md:102-114`).
- Context and question answers are written verbatim into `.ralph` files (`ralph.ts:654-663`, `ralph.ts:2821-2835`). Treat these files as sensitive because they can contain user-provided credentials, private paths, or instructions later injected into an agent prompt.
- Plugin filtering is heuristic: it keeps any plugin name containing “auth” (`ralph.ts:1440-1448`). This is not an allowlist or provenance check. A malicious or unrelated plugin name could bypass the intended filter, and generated config behavior should be tested against JSONC edge cases because parsing only strips basic comments (`ralph.ts:1414-1424`).
- The OMX integration intentionally defaults to `danger-full-access` and passes it to `omx exec` (`contrib/omx/README.md:38-49`; `contrib/omx/omx-codex-exec-for-ralph:22-29`, `90-96`). The adapter preserves arguments as arrays, which is good shell hygiene, but the configured binary and sandbox remain operator-controlled trust decisions.

### Testing Gaps And Pitfalls

- CI runs the full Bun test suite and a build/type check (`.github/workflows/ci.yml:23-30`), but `package.json`'s `test` script names only `./tests/ralph.test.ts` (`package.json:9-13`). Running `bun test` locally/CI covers more than `bun run test`; the scripts should not imply equivalent coverage.
- The repository tests use temporary directories and clean them in `finally` blocks, which is good isolation (`tests/ralph.test.ts:248-315`). However, several tests invoke the real top-level `ralph.ts` from the checkout and manipulate process signals/state files (`tests/model-error-detection.test.ts:42-59`; `tests/sigint-cleanup.test.ts:41-51`). Parallel test execution or a dirty checkout could make these tests contend for `.ralph` state; a dedicated subprocess cwd and stronger unique state isolation would reduce that risk.
- Completion fallback searches raw stream output for a promise anywhere (`completion.ts:41-49`). This is necessary for provider JSON, but it weakens the strict final-line guarantee for stream agents. Provider-specific parsing should be kept current, and tests should cover adversarial text that quotes or embeds promise tags.
- File snapshots combine `git status`, `git ls-files`, and content hashes (`ralph.ts:2189-2227`). Untracked files that are not present in the status output format expected by the parser, ignored files, renames, and paths with unusual quoting deserve explicit regression tests if “progress” drives operational decisions.

## Packaging And Distribution

- `package.json` includes a scoped package name, version, repository metadata, license, binary mapping, explicit published files, and a Bun lockfile (`package.json:1-27`, `49-61`; repository file `bun.lock`). The explicit `files` list helps avoid publishing tests and incidental checkout content, while intentionally shipping docs and the OMX contribution (`package.json:15-27`).
- The Node-compatible bin wrapper gives a useful error when Bun is unavailable (`bin/ralph.js:1-13`), and shell/PowerShell installers check Bun and at least one supported agent before linking (`install.sh:8-49`; `install.ps1:7-46`). The Unix installer uses `set -e`, but the runtime dependency remains Bun despite the npm-facing entrypoint.
- The OMX installer supports dry-run, symlink/copy modes, preserves existing config unless forced, and makes timestamped backups before replacement (`contrib/omx/install.sh:8-15`, `63-100`). This is a good pattern for user config mutation. The smoke test validates JSON, wrapper ordering, adapter argument rewriting, and dry-run behavior without running an editing agent (`contrib/omx/test-smoke.sh:20-76`).
- Packaging should document generated state and ignore it. The README enumerates `.ralph` state files (`README.md:668-686`), and `.gitignore` excludes loop state, generated OpenCode config, and the compiled binary while retaining `bin/ralph.js` (`.gitignore:75-83`).

## Bottom Line

Open Ralph is a strong example of an external OpenCode harness: use a stable CLI boundary, pass prompts as structured subprocess arguments, isolate generated runtime config, persist repo-native progress, and test provider behavior with fake binaries. It is not a plugin implementation and should not be copied as one. The key adaptations for a real OpenCode plugin are to replace the subprocess/config-file boundary with the plugin API, make permissions least-privilege by default, avoid automatic commits of unrelated changes, and preserve the repository's strict completion and cancellation tests.
