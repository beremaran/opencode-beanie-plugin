## OpenCode integration patterns

- The entrypoint uses the OpenCode `Plugin` type and receives `{ project, client, directory, worktree }` plus tuple options; it resolves configuration before doing telemetry work (`src/index.ts:1-1`, `src/index.ts:39-41`). This is a useful pattern for plugins that need project identity, UI logging, and project-relative resources without importing global OpenCode state.
- The plugin is always loadable but gates instrumentation on `OPENCODE_ENABLE_TELEMETRY`; disabled mode logs the reason through `client.app.log` and returns an empty hook object (`src/index.ts:44-51`). This keeps installation independent from collector availability.
- It returns named lifecycle/event hooks for `config`, `chat.headers`, `chat.message`, and `event`, and wraps asynchronous hook bodies in a `safe` adapter that reports unhandled errors instead of rejecting the host hook (`src/index.ts:192-225`, `src/index.ts:296-364`). Event dispatch covers session, message, permission, diff, command, and status events (`src/index.ts:296-363`).
- State is explicitly threaded through a `HandlerContext` rather than imported by handlers. The context contains instruments, correlation maps, trace providers, and configuration controls (`src/types.ts:87-114`). This makes handlers unit-testable and isolates OpenCode event adaptation from OTel setup.
- `chat.message` reconstructs prompt text from text, file, agent, and subtask parts, records prompt length, and optionally records the prompt itself (`src/index.ts:224-293`). Completed assistant messages update tokens/cost and finish the corresponding message span (`src/index.ts:324-357`; `src/handlers/message.ts:61-153`).
- `chat.headers` selectively injects W3C `traceparent`/`tracestate` into matching provider requests. Propagation is opt-in per provider or `*`, and the matching request is selected by session/message, agent, model, and provider (`src/handlers/chat-headers.ts:6-22`). The README explicitly avoids arbitrary headers and baggage for this feature (`README.md:219-229`).
- Session and subagent topology is represented with OpenInference agent spans; tool spans are children of the best available session/run context, and late events can reuse retained ended span contexts (`src/handlers/session.ts:95-113`, `src/handlers/message.ts:275-379`, `src/util.ts:42-68`). Tests cover remote parent context and late-child correlation (`tests/handlers/spans.test.ts:138-160`, `tests/handlers/spans.test.ts:233-255`).

## Configuration and operational lessons

- Tuple options have deliberate precedence: option, then matching `OPENCODE_*` environment variable, then default (`src/config.ts:140-160`, `src/config.ts:196-215`; `README.md:116-159`). Invalid protocols, intervals, and temporalities fall back safely; tests cover these cases (`src/config.ts:80-106`, `src/config.ts:109-115`; `tests/config.test.ts:128-147`, `tests/config.test.ts:206-220`).
- Plugin-specific variables are copied to the OTel SDK variables before initialization (`OPENCODE_OTLP_HEADERS` to `OTEL_EXPORTER_OTLP_HEADERS`, resource attributes, and metric temporality) (`src/config.ts:145-179`). Tests verify both copying and preservation of pre-existing SDK variables when plugin variables are absent (`tests/config.test.ts:149-183`, `tests/config.test.ts:222-242`).
- HTTP signal paths are built from a collector base URL rather than requiring callers to configure three paths (`src/otel.ts:61-65`, `src/otel.ts:92-106`). Startup performs a five-second TCP reachability probe and warns without aborting if the endpoint is unavailable (`src/probe.ts:6-18`, `src/probe.ts:21-41`, `src/index.ts:71-79`).
- Dynamic auth headers are fetched by an executable helper with a five-second timeout, JSON-object validation, single-flight refresh, and one refresh/retry after recognized auth failures (`src/headers.ts:52-119`, `src/headers.ts:261-284`). Static headers are merged first and helper values override same-name keys (`src/headers.ts:77-82`; `README.md:194-217`). This is a strong pattern for expiring collector credentials, but helper execution is a high-trust local-code boundary.
- Exporters use periodic/batch processing and providers are flushed on idle/error and shutdown; SIGTERM, SIGINT, and `beforeExit` are handled, avoiding asynchronous work on `process.on("exit")` (`src/index.ts:175-190`, `src/otel.ts:117-144`).
- Correlation maps are bounded to 500 entries and old entries are evicted FIFO-style (`src/types.ts:10-11`, `src/util.ts:30-40`). Session cleanup ends orphaned tool/message spans with error status and removes session-scoped pending state (`src/handlers/session.ts:132-158`; `tests/handlers/spans.test.ts:456-511`).

## Security and privacy findings

- Prompt contents are sensitive. Log capture is off by default, but trace spans always include prompt input when available; enabling `OPENCODE_CAPTURE_PROMPT_IN_LOGS` adds the full prompt to `user_prompt` logs (`README.md:100-114`, `src/index.ts:275-293`, `src/handlers/session.ts:67-75`, `src/handlers/message.ts:457-463`). Operators need trusted collectors and a separate trace-level redaction/disable policy; the README warns about secrets/PII but the implementation does not redact them.
- Tool parameters, tool output, and tool errors are placed into span attributes, including raw JSON/input and output text (`src/handlers/message.ts:283-299`, `src/handlers/message.ts:363-377`). This can expose credentials, file contents, or command output to telemetry backends. The design should be deployed with collector access controls and sampling/redaction considerations.
- OTLP auth headers are intentionally accepted from environment or tuple options and are not logged by the helper path; README warns not to commit or print them (`README.md:103-107`, `README.md:159`, `README.md:187-217`). Startup logs only boolean “set” indicators (`src/index.ts:54-69`), which is the safer observability pattern.
- The helper path supports `${PROJECT_ROOT}`, `${WORKTREE}`, and `${DIRECTORY}` substitution and is then executed as a Bun child process (`src/config.ts:218-229`, `src/headers.ts:91-119`). Absolute paths are recommended in the README (`README.md:194-208`), but project-relative expansion means a repository-controlled helper can execute with the user's OpenCode privileges if configured; this should be treated as code execution, not merely configuration.
- The repository has a responsible-disclosure policy with private email reporting and stated response targets (`SECURITY.md:12-27`). The supported-version table is stale relative to package version 1.5.1, listing only 0.4.x as supported (`SECURITY.md:3-9`), so release/security maintenance metadata should be kept synchronized.

## Testing lessons and gaps

- The test suite is broad at the unit/handler level: configuration precedence and parsing (`tests/config.test.ts:4-20`, `tests/config.test.ts:61-345`, `tests/config.test.ts:347-488`), dynamic headers/auth retry, endpoint parsing, OTel exporters, trace propagation, disabled signals, and handler behavior are represented by 15 test files in the clone. Disabled logs preserve metrics and disabled traces preserve independent signals (`tests/handlers/disabled-signals.test.ts:77-113`; `tests/handlers/spans.test.ts:514-635`).
- Tests specifically protect event-order and lifecycle hazards: out-of-order tool completion, orphan cleanup, concurrent LLM request contexts, remote trace parents, and span status/end times (`tests/handlers/spans.test.ts:258-345`, `tests/handlers/spans.test.ts:348-453`, `tests/handlers/spans.test.ts:456-511`). These are high-value cases for event-driven OpenCode plugins.
- CI runs frozen Bun installation, lint, JSDoc coverage, typecheck, and tests with read-only repository permissions (`.github/workflows/ci.yml:11-40`). Contributor guidance also documents direct source loading for manual OpenCode testing and a local collector smoke test (`CONTRIBUTING.md:16-27`, `CONTRIBUTING.md:55-64`).
- Verification in this analysis environment could not complete because the clone has no installed dependency tree: `bun test` reported 80 passing tests but 13 module-resolution errors, and `bun run typecheck` reported missing OTel/OpenInference modules. The CI workflow's `bun install --frozen-lockfile` is therefore required before these checks are meaningful (`.github/workflows/ci.yml:23-40`). No dependency installation was performed to preserve the clone.
- There is no evident end-to-end test against a real OTLP collector or a real OpenCode runtime in the inspected test inventory. The documented Docker collector smoke test is manual (`CONTRIBUTING.md:55-64`); adding an isolated collector/integration fixture would better validate exporter URLs, auth refresh, shutdown flush, and actual hook wiring.

## Packaging and release lessons

- The package publishes only `dist/`, declares ESM, and exposes both `.` and `./server` to `dist/index.js` plus declarations (`package.json:35-47`, `package.json:58-79`). `prepack` builds with Bun and emits declarations via `tsc` (`package.json:71-76`, `tsconfig.build.json:1-19`). Consumers therefore depend on the generated artifact even though the repository's development workflow loads `src/index.ts` directly (`CONTRIBUTING.md:18-27`). A release check should ensure `dist/` is actually present and matches the source.
- The package uses explicit OpenCode plugin metadata, `oc-plugin: ["server"]`, and depends on pinned OpenCode plugin/SDK ranges (`package.json:6-10`, `package.json:60-63`). Individual OTel packages are used instead of a Node SDK meta-package, keeping the dependency surface explicit (`package.json:6-25`; `AGENTS.md` repository guidance).
- Release automation is conventional-commit/Release Please based, and the changelog records recent fixes for plugin tuple options, short-lived-run flushing, W3C propagation, concurrent contexts, and moving TypeScript to devDependencies (`CHANGELOG.md:9-26`, `CHANGELOG.md:31-60`). This history highlights likely regression areas: event correlation, shutdown timing, and packaging dependency classification.

## Bottom line

`opencode-plugin-otel` is a strong reference implementation for a production-oriented OpenCode plugin: it uses the official plugin hook surface, keeps handler dependencies explicit, bounds state, preserves independent metric/log/trace controls, handles shutdown, and tests difficult event ordering. The primary deployment risks are intentional high-fidelity telemetry containing prompts/tool data, execution of a configured credential helper, and reliance on a generated `dist/` artifact that was not testable in this clone because dependencies were absent. The report itself is the only file changed by this analysis; the mapped clone was not edited.
