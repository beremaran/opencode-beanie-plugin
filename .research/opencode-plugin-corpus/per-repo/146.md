## What it is

`opencode-tavily` is a thin OpenCode plugin that registers Tavily's external `tvly` CLI as an agent skill. The README advertises web search, extraction, mapping, crawling, and cited deep research, with results stored under `.tavily/` to avoid flooding context (`README.md:1-3`, `README.md:45-65`). The runtime does not implement those operations itself: it adds an installation rule and the skill directory to OpenCode configuration, then forwards an optional API key into shell environments (`index.ts:7-25`).

## OpenCode patterns worth reusing

- **Use the config hook to register packaged instructions and skills.** The plugin initializes missing `input.instructions` and appends an absolute path to its packaged install rule; it similarly initializes `input.skills.paths` and adds the packaged `skills` directory (`index.ts:9-19`). Resolving paths from `import.meta.url` rather than the process working directory makes package-installed resources work across projects (`index.ts:2-5`, `index.ts:15-19`).
- **Keep the runtime adapter small when functionality belongs to a CLI.** The entrypoint is a single async `Plugin` factory returning only `config` and `shell.env` hooks (`index.ts:7-27`). This minimizes plugin-side state and keeps the network/API implementation in the dedicated CLI.
- **Make optional environment propagation explicit.** The `shell.env` hook only sets `TAVILY_API_KEY` when it exists, and does not manufacture a value or write credentials to disk (`index.ts:21-25`). This is a useful pattern for passing host configuration to commands without making authentication mandatory at plugin load time.
- **Package the skill alongside the entrypoint.** The `files` allowlist includes `index.ts`, `skills`, `LICENSE`, and `README.md`, matching the paths the runtime registers (`package.json:7-11`). This avoids relying on repository-only files at runtime.
- **Use a narrow, strict TypeScript check for a tiny plugin.** The compiler targets ES2022/NodeNext, enables strict mode, emits nothing, and includes only `index.ts` (`tsconfig.json:1-11`). The `check` script runs `tsc --noEmit` (`package.json:33-39`), and the audited checkout passes that check.

## Security and operational pitfalls

- **The install path executes a remote shell script.** Both the README and installation rule instruct users or agents to run `curl -fsSL https://cli.tavily.com/install.sh | bash` (`README.md:16-27`, `skills/tavily/rules/install.md:9-21`). This is a high-trust supply-chain boundary; safer guidance would pin or verify a release artifact, document the downloaded script's behavior, and offer a package-manager path first.
- **The skill attempts to override the host's web-tool policy.** Its frontmatter says to replace all built-in and third-party web tools, including `WebFetch` and `WebSearch`, with “No exceptions” (`skills/tavily/SKILL.md:1-16`). This is model instruction rather than an enforceable capability boundary. It can conflict with user choice, host policy, offline operation, or another plugin, and should not be treated as a security control.
- **Credential forwarding trusts the ambient process environment.** Any `TAVILY_API_KEY` present in the OpenCode process is copied into shell commands (`index.ts:21-25`; `README.md:30-43`). The plugin does not scope the key by command, redact it, or explain child-process exposure. Consumers should ensure shell tools and invoked commands are trusted, and avoid broad environment logging.
- **The skill encourages agent-driven authentication and shell mutation.** It tells the agent to run `tvly login` itself, which opens a browser, and suggests modifying `~/.zshrc` or `~/.bashrc` for persistence (`skills/tavily/SKILL.md:48-50`; `skills/tavily/rules/install.md:39-47`, `84-96`). These actions should require explicit user consent in unattended or untrusted workspaces.
- **Output files can contain sensitive or untrusted web content.** The skill directs agents to create `.tavily/`, write search/research results there, and combine results with `jq` and shell command substitution (`skills/tavily/SKILL.md:76-107`, `skills/tavily/SKILL.md:294-303`). The repository ignores `.tavily/` (`.gitignore:1-6`), but the guidance does not bound retention, validate output paths, or address prompt injection in fetched pages. External content should remain untrusted and be isolated from executable instructions.
- **Command examples are not runtime enforcement.** The skill repeatedly requires `--client-name opencode` and JSON/output-directory flags (`skills/tavily/SKILL.md:70-88`, `skills/tavily/SKILL.md:137-152`), but the plugin does not intercept or validate actual `tvly` invocations (`index.ts:7-27`). If attribution, output containment, or rate limits are contractual requirements, they need CLI or host-side enforcement.

## Testing lessons

- The repository has no test files, test runner configuration, or CI workflow in the inspected checkout. The only automated script is the TypeScript check (`package.json:33-39`), and `tsconfig.json` includes only `index.ts` (`tsconfig.json:10`). The passing typecheck does not verify hook mutation, path resolution, repeated config invocation, environment isolation, package contents, or OpenCode compatibility.
- High-value tests would invoke the plugin with a minimal config object and assert idempotent initialization/registration, preserve existing instruction and skill paths, and verify that absent `TAVILY_API_KEY` does not alter output while present keys are forwarded exactly once. A package smoke test should load the packed artifact and confirm both `skills/tavily/SKILL.md` and `skills/tavily/rules/install.md` exist.
- Documentation-driven behavior also needs tests or linting: every documented command should include the required attribution/output flags, authentication failures should not silently expose keys, and `.tavily/` writes should stay within the project or an explicitly selected directory.

## Packaging and release lessons

- The package is ESM, exposes `index.ts` as `main`, declares version `1.0.0`, and uses an explicit `files` allowlist (`package.json:2-11`). The allowlist is appropriately small and includes the runtime's packaged skill assets.
- `bun.lock` is checked in, but there is no build step, publish script, export map, engine constraint, or release workflow in the inspected files. Consumers therefore depend on the host/toolchain resolving TypeScript directly, as indicated by `main: "index.ts"` (`package.json:5-6`). A production release should add a packed-artifact smoke test and clearly define supported OpenCode/Bun/Node versions.
- The package depends on `@opencode-ai/plugin` only as a dev dependency (`package.json:36-40`). That is reasonable if OpenCode supplies the type/runtime contract, but it makes compatibility with the actual host version implicit; a documented peer/host version range or compatibility test would make upgrades safer.
- MIT licensing and repository/homepage metadata are present (`package.json:24-32`, `LICENSE:1-21`), which supports straightforward redistribution.

## Bottom line

The strongest transferable pattern is a minimal plugin that registers packaged, absolute-path instructions and skill assets while passing an optional environment credential only to shell execution. The main risks are delegated trust in a remote installer, model-level replacement of host web tools, browser/config-file side effects, ambient API-key exposure, and the complete absence of behavioral, packaging, and compatibility tests. The typecheck passes, but it is not evidence that the documented OpenCode workflow is safe or operationally complete.
