## Executive Summary

WithContext is a TypeScript MCP server for project-scoped Obsidian note management, exposed to OpenCode as a local MCP process rather than as a native OpenCode plugin. Its useful patterns are explicit MCP tool registration, per-tool Zod schemas, project-relative path validation, read-before-write protection, confirmation for destructive actions, safe dry-run/rollback organization, and CI/package gates. The principal risks are permissive development TLS defaults, process-global session state, broad filesystem/config inputs in some tools, and documentation/version drift.

## OpenCode Integration

- The README gives a correct local-MCP shape for OpenCode: `type: "local"`, an executable plus args, environment interpolation, and an explicit `enabled` flag (`README.md:34-57`). The checked-in example uses the array-form command `node` plus `./dist/index.js`, a 10-second timeout, and `enabled: false` (`opencode.jsonc:6-18`).
- The intended distribution entrypoint is a Node CLI: the source has a shebang and uses MCP stdio transport (`src/index.ts:1-18`), while `package.json` maps `with-context-mcp` to `./dist/index.js` (`package.json:5-13`). The server starts with `StdioServerTransport` and connects to the MCP server (`src/index.ts:965-979`).
- OpenCode-specific repository content is command markdown under `.opencode/command/`, not plugin hooks. Commands declare frontmatter such as `agent: general` and `subtask: true` (`.opencode/command/setup-notes.md:1-5`), call MCP tools with parsed flags (`.opencode/command/setup-notes.md:153-172`), and provide preview-only behavior where appropriate (`.opencode/command/preview-notes-delegation.md:30-51`, `147-153`). Both the top-level `plugin/` directory and `.opencode/plugin/` are empty in the clone, so there is no native OpenCode plugin entrypoint to reuse.
- The commands intentionally instruct agents to delegate scanning and mutation to tools instead of manually editing files (`.opencode/command/setup-notes.md:241-263`). This is a useful policy boundary, but it depends on the MCP tool actually enforcing the claimed safety properties.

## Architecture And Implementation Patterns

- `src/index.ts` owns MCP server construction, tool listing, dispatch, and protocol/error translation. The `ListTools` response advertises the tool surface, and `CallToolRequestSchema` dispatches by name (`src/index.ts:95-125`, `734-854`). This central switch is easy to audit, though it becomes a large merge hotspot as tools are added.
- Every ordinary tool exports a Zod schema and handler; dispatch parses inputs before invoking the handler (`src/index.ts:745-815`). Zod errors become protocol `InvalidParams`, while operational errors become tool-visible `isError` responses (`src/index.ts:940-961`). The response helper follows the MCP distinction between protocol errors and tool failures (`src/tools/utils/tool-response.ts:1-12`, `27-55`).
- Project context is cached in a singleton and can be explicitly set, overridden per operation, or inferred from the Git repository (`src/session-state.ts:12-58`). This makes repeated calls ergonomic and supports automatic project detection, but the singleton is process-wide rather than keyed by MCP session/client.
- The Obsidian client centralizes HTTP setup, authentication headers, timeout, response mapping, and custom connection/auth/not-found errors (`src/obsidian/client.ts:21-57`, `83-122`). `writeNote` implements read-modify-write for append/prepend and enforces a prior read for existing files (`src/obsidian/client.ts:124-199`).
- Configuration has two layers: environment-based server settings validated with Zod (`src/config/index.ts:11-31`) and project-local JSONC delegation configuration with defaults and semantic checks (`src/config/config-parser.ts:61-149`, `241-293`; `src/config/config-validator.ts:29-130`). The JSONC parser avoids stripping comment markers inside strings and removes trailing commas before parsing (`src/config/config-parser.ts:64-143`).

## Security And Safety Lessons

- Path handling is defense-in-depth: rejects empty/null-byte/absolute paths, recognizes filesystem-looking prefixes, normalizes traversal, rejects `..`, slugifies the filename, and constructs a `basePath/projectFolder/file` vault path (`src/security/path-validator.ts:36-59`, `61-151`, `153-208`). Tests cover traversal, absolute paths, Windows drives, Unix filesystem prefixes, and filename normalization (`tests/unit/path-validator.test.ts:8-73`, `76-149`).
- Destructive deletion requires `confirm: true`, validates and reads the target before deletion, and returns size/line/preview metadata (`src/tools/delete-note.ts:21-35`, `37-76`, `78-93`). This is a good confirmation and observability pattern, but the preview itself may expose note content to the caller (`src/tools/delete-note.ts:51-59`).
- Reorganization defaults to a dry-run path, can skip low-confidence suggestions, stops and rolls back completed operations on failure, and optionally updates links (`src/vault-organizer/vault-reorganizer.ts:45-57`, `88-150`). Move/rename is implemented as read, create at target, then delete source (`src/vault-organizer/vault-reorganizer.ts:169-228`), so it is not atomic against a remote API failure between operations.
- **High-risk default:** `ObsidianClient` defaults `allowInsecure` to `true`, disabling certificate verification when constructing the HTTPS agent (`src/obsidian/client.ts:25-49`). Callers generally pass `config.nodeEnv === 'development'` (`src/tools/write-note.ts:38-44`), which is safer than unconditional bypass, but a missing or misclassified environment can still make local TLS policy easy to misunderstand. README setup recommends HTTPS and the self-signed local API (`docs/getting-started.md:68-75`); production guidance should explicitly require verification.
- Environment examples correctly keep the API key as a placeholder and document the OpenCode auto-session flags (`.env.example:1-19`), while `.gitignore` excludes `.env` and coverage (`.gitignore:1-9`).
- `validate-config` accepts an absolute `configPath` by design (`src/tools/validate-config.ts:12-23`, `38-47`). If exposed to an untrusted tool caller, this expands validation outside the project boundary; callers should constrain it or require project-relative paths.

## Testing Lessons And Gaps

- The repository has substantial unit coverage for path validation, configuration parsing/validation, read-before-write, session management, tool responses, organization, and individual note operations. For example, read tracking tests verify normalization and lifecycle cleanup (`tests/unit/read-before-write.test.ts:4-13`, `15-67`), and graceful-degradation tests verify missing env vars do not crash module import (`tests/unit/config-graceful-degradation.test.ts:24-56`, `129-160`).
- Integration tests exercise MCP/tool workflows and path resolution, but the Vitest config excludes the legacy `tests/integration/test-*.js` files (`vitest.config.ts:3-10`). The standalone all-tools script spawns a built `dist/index.js`, speaks newline-delimited JSON-RPC, and performs real note CRUD operations (`tests/integration/test-all-tools.js:7-20`, `46-115`, `169-206`). This separation is useful, but the script is not part of `test:run` and requires an Obsidian service/environment.
- CI tests Node 18, 20, and 22, builds before running tests, and generates coverage on newer matrix entries (`.github/workflows/test.yml:9-42`). Lint is explicitly allowed to fail (`.github/workflows/test.yml:29-32`), weakening that quality gate.
- The checked-in test configuration injects a test API key and URL (`vitest.config.ts:9-16`), which is convenient for pure tests but reinforces the need for mocks around network clients. The clone had no `node_modules`, so `npm run test:run` was not executed during this review; no test result is inferred.
- A key gap is concurrency isolation: `SessionState` stores one current context and one read-file set (`src/session-state.ts:12-16`), and tests explicitly assert read tracking persists across project-context changes (`tests/unit/read-before-write.test.ts:70-95`). A multi-client or overlapping-session process could therefore authorize a write based on another context's read.

## Packaging And Maintenance

- Packaging is conventional and reproducible: strict TypeScript emits declarations, maps, and source maps to `dist` (`tsconfig.json:1-20`); `prepublishOnly` builds (`package.json:20-33`); and `files` limits the npm package to `dist`, README, and LICENSE (`package.json:15-19`). `.npmignore` additionally excludes source, tests, CI/editor/config files, and the unused `plugin/` directory (`.npmignore:1-41`).
- The publish workflow runs lint, build, tests, `npm pack --dry-run`, and publishes with npm provenance (`.github/workflows/publish.yml:9-44`). It also creates a GitHub release containing README, changelog, and license (`.github/workflows/publish.yml:46-55`). This is a strong supply-chain/package-content pattern.
- `package.json` declares version `3.0.7`, but the MCP server metadata logs `3.0.0` and startup output says `v2.1.0` (`package.json:1-6`; `src/index.ts:95-100`, `965-974`). The changelog calls the current release `3.0.7` (`CHANGELOG.md:8-18`). A single version source would avoid misleading diagnostics.
- The package lists `with-context-mcp` itself as a runtime dependency (`package.json:59-67`). This may be intentional for reuse or may be accidental self-dependency; it deserves verification because it can complicate installation and package resolution.
- README installation uses `npx -y with-context-mcp` and maps environment variables into OpenCode (`README.md:28-57`), while the checked-in OpenCode config uses `node ./dist/index.js` and is disabled (`opencode.jsonc:7-17`). Keeping the shipped example aligned with the documented consumer path would reduce setup ambiguity.

## Reusable Takeaways

1. Treat OpenCode integration as two separately testable layers: a small local-MCP config/command surface and a normal MCP server with strict tool contracts.
2. Validate and canonicalize every user-supplied vault path before constructing remote paths; test platform-shaped absolute paths, not only `../`.
3. Return operational failures as MCP tool errors with actionable messages, while reserving protocol errors for malformed requests and unknown tools.
4. Require explicit confirmation for deletion and default complex reorganizations to dry-run, confidence thresholds, and rollback.
5. Keep mutable session authorization keyed by actual MCP/client/session identity rather than a process-global singleton when concurrent clients are possible.
6. Make TLS verification, package version reporting, README examples, and publish metadata consistent across development and production paths.
