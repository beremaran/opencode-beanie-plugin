## What It Does

Simple Memory is a persistent OpenCode plugin. It stores typed memories in daily `.opencode/memory/YYYY-MM-DD.logfmt` files and keeps deletion/update audit records in `deletions.logfmt` (README.md, lines 21-27, 209-224). The public entrypoint re-exports the async `MemoryPlugin` as both named and default exports (index.ts, lines 1-2).

The plugin exposes nine tools: remember, recall, update, forget, list, export, import, compact, and context (README.md, lines 44-58; src/index.ts, lines 715-725). Each tool is built with `@opencode-ai/plugin`'s `tool()` helper and schema definitions, including enum validation for memory types and formats (src/index.ts, lines 438-447, 462-473, 609-614, 629-634, 697-706). The plugin returns the tools plus `chat.message` and `experimental.chat.system.transform` hooks (src/index.ts, lines 728-774).

Automatic load/save behavior is explicitly opt-in. Auto-save recognizes explicit `remember ...` requests, while auto-load ranks memories against the latest prompt and appends a bounded `Relevant Memory:` system block (README.md, lines 121-171; src/index.ts, lines 743-771). The default settings are deliberately off and the hooks fail open after a configurable timeout (README.md, lines 161-173).

## OpenCode Patterns Worth Reusing

### Plugin shape and distribution

- Keep the package entrypoint tiny and re-export implementation from `src/`; this makes the OpenCode config target stable while preserving a source-oriented layout (index.ts, lines 1-2; AGENTS.md, lines 14-19).
- Export an async plugin factory that satisfies the `Plugin` type and returns `tool` plus lifecycle hooks (src/index.ts, lines 728-774). This is a direct, discoverable integration point for OpenCode.
- Use `tool.schema` for argument contracts rather than relying only on prompt descriptions. The implementation constrains memory types, import/export formats, scope match modes, and context types at the boundary (src/index.ts, lines 439-447, 462-473, 609-614, 629-634, 697-706).
- Make potentially surprising behavior configurable through the OpenCode plugin tuple options. The README documents the tuple form, defaults, startup timing, and local `file://` development path (README.md, lines 139-207).

### Storage and hook behavior

- Resolve project storage from `ctx.directory`, not from process cwd, so the plugin follows the OpenCode project being served (src/index.ts, lines 728-730).
- Use a human-readable append-only format with compatibility-aware parsing. Records quote values only when needed, always quote content, and escape multiline content; parsing accepts older unquoted fields and restores escapes (src/index.ts, lines 58-145, 148-177; README.md, lines 219-224).
- Bound injected context by both result count and characters, and add an explicit instruction that the injected block is only relevant context and should not be mentioned unless asked (src/index.ts, lines 213-259, 755-771). This is a useful defense against unbounded prompt growth and accidental user-facing leakage of implementation details.
- Preserve destructive-operation accountability by appending deletion records before/alongside updates and after deletes (src/index.ts, lines 321-324, 516-528, 598-605). Export can optionally include those audit lines for logfmt (src/index.ts, lines 615-625).

## Pitfalls and Security Lessons

### High-value risks

- **Session cross-talk in automatic context.** `latestPrompt` is a single plugin-instance variable (src/index.ts, lines 733-734). Every `chat.message` overwrites it (lines 737-742), and a later system transform reads it without checking session identity (lines 755-767). If one plugin instance serves concurrent sessions, a system transform can search using another session's most recent prompt. Since memory content is then injected into system context, this can produce irrelevant or cross-session disclosure. Track prompts by session ID or use hook input/session correlation.
- **Timeout does not cancel side effects.** `withTimeout` races the operation against a timer and returns `undefined` on timeout, but it does not abort the underlying promise (src/index.ts, lines 298-309). The README correctly promises that hooks do not block normal responses (README.md, lines 165-169), but a timed-out save/load can continue reading or writing after the hook has returned. This is especially risky if the same store is compacted or updated concurrently. Use an abortable operation or explicitly serialize/coordinate writes if fail-open behavior is retained.
- **Unvalidated imports can create malformed memories.** JSON and JSONL imports cast parsed values directly to `Memory`; only `type` is checked before appending (src/index.ts, lines 639-659). Missing/non-string `scope`, `content`, malformed timestamps, non-array tags, or hostile tag values can enter the store and later break formatting, ranking, or filtering. Validate all fields and normalize strings/arrays before persistence. The logfmt path has stronger structural filtering because it goes through `parseLine` (src/index.ts, lines 132-145, 642-645).

### Additional correctness and operational risks

- **Concurrent rewrite operations can lose writes.** Update, forget, and compact read complete files and replace them via temporary-file rename (src/index.ts, lines 518-528, 598-601, 682-691), while remember/import append independently (src/index.ts, lines 317-323, 648-659). Concurrent tool calls can therefore overwrite each other's changes. A per-store mutex or transactional single-writer queue would make destructive operations safer.
- **Automatic save classification is heuristic.** Type inference is based on substring checks such as `prefer`, `decided`, `blocked`, and `always` (src/index.ts, lines 272-295). It is conservative about arbitrary conversation content, but ambiguous wording can be stored under the wrong type. This should remain documented as heuristic behavior, or the hook should require a more explicit syntax/schema.
- **Import data is trusted as content and metadata.** The plugin writes imported `scope`, `issue`, and tags into logfmt after only type filtering (src/index.ts, lines 649-658). The encoder escapes field syntax, which prevents straightforward logfmt field injection, but imported values still affect search and injected system context. Treat imported memory as untrusted content and consider size limits, normalization, and explicit provenance.
- **Memory is intentionally plaintext project data.** Files are written directly beneath `.opencode/memory` and are excluded from git by the repository's own `.gitignore` (src/index.ts, lines 312-356, 728-730; .gitignore, lines 4-5). That reduces accidental commits but does not provide encryption or protection from other local processes. Documentation should warn users not to store secrets, credentials, or sensitive personal data.

## Testing and Verification Lessons

- The repository has a focused Bun suite covering query ranking, latest-memory ordering, multiline/backslash compatibility, filters, targeted deletion, JSON round-tripping, compaction, context packing, and both automatic hook modes (src/index.test.ts, lines 45-288).
- Running `bun test` at the recorded clone passed: **13 tests, 0 failures, 31 assertions**.
- Running the documented `bun run typecheck` failed. The test suite's hand-built tool context omits required `directory`, `worktree`, `metadata`, and `ask` fields; several assertions treat `ToolResult` as a string; and system-hook test calls omit the required model input (src/index.test.ts, lines 9-14, 57-117, 223-243, 249-287). The package's script delegates directly to `tsc --noEmit` (package.json, lines 16-19), so this is a release-gating failure rather than merely an undocumented command issue.
- Tests do not exercise `memory_update`, `memory_list`, deletion-log export, logfmt export, malformed JSON imports, invalid memory fields, concurrent rewrites, timeout behavior, or cross-session automatic hooks. Those gaps map directly to the highest-risk code paths above (src/index.test.ts, lines 16-33, 45-288; src/index.ts, lines 497-567, 609-695, 298-309, 733-771).
- The tests use `as never` for plugin context construction (src/index.test.ts, lines 17, 224, 250, 271), which makes runtime testing convenient but prevents the fixture from exposing API drift. A typed test helper with the current `ToolContext` and hook input shapes would have caught the typecheck failures.

## Packaging and Maintenance Lessons

- `package.json` identifies `index.ts` as the Bun module entry and publishes only `index.ts` and `src/index.ts` (package.json, lines 1-4, 20-25). This is a minimal package surface and avoids shipping tests, examples, lockfiles, or repository metadata.
- The runtime dependency is only `@opencode-ai/plugin`; TypeScript is a peer dependency and Bun types are a dev dependency (package.json, lines 26-34). The lockfile pins the resolved plugin/sdk versions and integrity hashes (bun.lock, lines 18-33), improving reproducibility for development while the semver range remains compatible for consumers.
- The README gives both npm plugin configuration and local `file://` loading instructions, and explicitly notes that OpenCode does not auto-update cached plugins (README.md, lines 8-17, 29-42, 234-260). These operational instructions are important for plugin users because code changes may otherwise appear ineffective.
- `.opencode`, dependency directories, build artifacts, archives, environment files, caches, and coverage output are ignored (.gitignore, lines 1-31). This is appropriate for a project-memory plugin, but the plaintext-storage limitation should be made prominent because ignored data can still remain on disk.
- The MIT license and package metadata are present and consistent with the README badges (LICENSE, lines 1-21; README.md, lines 1-4; package.json, lines 5-8, 24).

## Bottom Line

This is a strong small-plugin pattern: a stable re-export entrypoint, typed OpenCode tools, project-relative storage, bounded opt-in hooks, compatibility-minded serialization, and useful audit records. Before treating it as production-hardening reference code, fix the typecheck suite and prioritize session-scoped hook state, abort/serialization semantics around timeouts and rewrites, and complete validation of JSON/JSONL imports. The plaintext memory model and system-context injection also warrant explicit user guidance against secrets and untrusted imported content.
