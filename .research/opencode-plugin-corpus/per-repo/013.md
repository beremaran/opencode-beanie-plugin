## SDK and registration

- The package entry is intentionally thin: `index.ts` re-exports `CommandInjectPlugin`, `createCommandInjectPlugin`, and its options (`index.ts:1-2`).
- The plugin uses the OpenCode `Plugin` type and returns an async plugin factory. Initialization receives OpenCode context, loads config against `ctx.directory`, and returns hooks built for that project (`src/plugin.ts:1`, `src/plugin.ts:42-79`).
- Runtime hook construction returns two OpenCode hooks: `config`, which mutates `config.command`, and `command.execute.before`, which prepends generated instruction text to command output (`src/plugin/command-inject.ts:104-106`, `src/plugin/command-inject.ts:156-197`).
- Package metadata publishes `index.ts` as an ES-module entry and includes `src` plus the generated JSON schema while excluding tests (`package.json:21-33`). This is a useful minimal package shape for an OpenCode plugin written directly in TypeScript.

## Hooks, events, and context

- The factory uses `ctx.directory` as the project root and creates a boundary logger backed by `console.warn` (`src/plugin.ts:42-48`). It loads configuration before deciding whether skill discovery is enabled (`src/plugin.ts:46-59`).
- The `config` hook ensures `config.command` exists, resolves dynamic collisions against commands already present in the host config, records only successfully injected names, and writes `{ template, description }` entries (`src/plugin/command-inject.ts:156-187`).
- The `command.execute.before` hook only acts on names recorded as injected. It looks up the catalog entry, replaces every `$ARGUMENTS` placeholder, and inserts a text part at the front of `output.parts` (`src/plugin/command-inject.ts:189-196`; `src/command-sources/template.ts:25-27`).
- Hook-local state is closure-scoped: `injectedNames` and `catalog` belong to one plugin instance rather than global state (`src/plugin/command-inject.ts:107-109`). This avoids cross-project/session leakage.

## Tools and commands

- The plugin does not register custom tools. It creates OpenCode slash commands from three pluggable `CommandSource` adapters; the source contract is `id` plus `load(context): Promise<CommandInfo[]>` (`src/command-sources/types.ts:3-30`).
- Makefile targets are parsed from simple `target: ...` lines, with `##` descriptions and target-name fallback, then rendered as `make <target>` shell templates (`src/command-sources/makefile-parser.ts:6-27`; `src/command-sources/makefile-source.ts:19-60`).
- Package scripts are exposed as `<runner>:<script>` commands. Runner detection prefers `packageManager`, then lockfiles, and finally `npm` (`src/command-sources/npm-scripts-runner.ts:12-21`, `src/command-sources/npm-scripts-runner.ts:41-69`; `README.md:45-61`). Scripts use `runner run script -- $ARGUMENTS` (`src/command-sources/npm-scripts-source.ts:55-80`).
- Skills become `skill:<name>` commands. Their templates wrap skill content in `<skill-instruction>` and `<user-request>` sections (`src/skills/load-skill.ts:6-14`, `src/skills/load-skill.ts:39-49`).
- Source adapters support configurable prompt replacement and prompt append variables (`src/command-sources/template.ts:10-22`). The supported variables are source-specific fields such as `name`, `description`, `command`, `instruction`, and `arguments` (`src/command-sources/makefile-source.ts:42-55`, `src/command-sources/npm-scripts-source.ts:63-77`, `src/command-sources/skill-source.ts:47-60`).

## Auth and providers

- No authentication, OAuth, API-key handling, model provider registration, or provider interception is present in the inspected package metadata/source. Dependencies are limited to `@opencode-ai/plugin` and `zod` at runtime (`package.json:35-48`).
- The plugin delegates execution to OpenCode shell command templates rather than calling an external provider itself (`src/command-sources/template.ts:4-8`).

## State and processes

- There is no database, cache, daemon, background worker, subprocess manager, or persistent runtime state in `src/`. Configuration is loaded at plugin initialization and command catalog state is held in hook closures (`src/plugin.ts:42-79`; `src/plugin/command-inject.ts:107-109`).
- Skill discovery recursively scans configured directories, follows directory symlinks, uses `realpath` to avoid revisiting the same location, and preserves the first root/name match (`src/skills/discovery.ts:57-86`, `src/skills/discovery.ts:117-143`).
- The default skill-root priority is project `.opencode/skills`, user OpenCode skills, project `.claude/skills`, project `.agents/skills`, user Claude skills, then user agents skills (`src/skills/discovery.ts:46-54`; `README.md:63-76`).

## Configuration

- Configuration is strict-Zod validated and supports top-level prefix disabling plus per-source disable, prompt, prompt append, and prefix settings (`src/config/schema.ts:3-29`; `src/config/types.ts:1-22`). The generated editor schema is produced by `scripts/generate-schema.ts:1-10`.
- An explicit `OPENCODE_COMMAND_INJECT_CONFIG` file path has highest precedence. Otherwise, `OPENCODE_CONFIG_DIR` is checked before XDG/home defaults, and project `.opencode/opencode-command-inject.jsonc|json` is merged on top (`src/config/loader.ts:8-21`, `src/config/loader.ts:93-126`; `docs/configuration.md:5-29`).
- `.jsonc` is supported by stripping comments before JSON parsing (`src/config/loader.ts:33-46`). Project overrides use recursive object merging, preserving unrelated user/source fields (`src/config/loader.ts:73-90`, `src/config/loader.ts:117-123`).
- Prefix behavior is deliberately layered: canonical prefixes are on by default, global disable removes them, and source-level `disable` or `value` can override the global setting (`src/command-sources/command-name-prefix.ts:16-55`; `docs/configuration.md:65-70`).

## Errors and security

- Optional files are recoverable: missing Makefile/package.json returns no commands, read/parse errors warn and return an empty result (`src/command-sources/makefile-source.ts:22-31`; `src/command-sources/npm-scripts-source.ts:24-44`).
- Invalid config is rejected with `safeParse`, logged, and replaced by an empty config; a missing explicit env path warns and falls back to normal lookup (`src/config/loader.ts:33-56`, `src/config/loader.ts:93-103`).
- Skill discovery skips missing roots, unreadable directories, invalid/unreadable skill files, blank bodies, and invalid entries while continuing other roots (`src/skills/discovery.ts:65-80`, `src/skills/discovery.ts:108-115`; `src/skills/load-skill.ts:21-37`).
- Collision handling is non-destructive. Existing/config-defined commands win; customized names first attempt canonical fallback, otherwise the first command is retained and a warning is emitted (`src/plugin/command-inject.ts:23-101`; `src/command-sources/aggregator.ts:37-109`).
- Warning prefixes are stable and distinguish source aggregation (`[command-sources]`) from plugin/config/injection warnings (`[command-inject]`) (`src/command-sources/aggregator.ts:77-100`; `src/plugin/command-inject.ts:67-92`).
- Security boundary: generated templates explicitly ask OpenCode to use shell (`src/command-sources/template.ts:4-8`), and Makefile/package script contents are project-controlled. The plugin does not sandbox or validate those commands; users should treat discovered commands as trusted project instructions.
- The shell template construction places `$ARGUMENTS` inside the generated shell instruction, so argument handling is delegated to the OpenCode execution path rather than escaped here (`src/command-sources/makefile-source.ts:42-55`; `src/command-sources/npm-scripts-source.ts:63-77`). This is a review point for consumers with untrusted command arguments.

## Pitfalls and reusable lessons

- Forward top-level config through every orchestration layer. The project records a prior bug where source adapters implemented global prefix behavior but the plugin failed to pass the top-level config; combined integration tests caught it (`docs/lessons/plugin-must-forward-global-prefix-config.md:11-21`).
- Preserve explicit file overrides above directory overrides. The loader lesson warns that adding `OPENCODE_CONFIG_DIR` must not outrank `OPENCODE_COMMAND_INJECT_CONFIG` (`docs/lessons/plugin-config-dir-override-must-not-beat-explicit-file-override.md:11-23`).
- Treat runtime metadata changes as cross-cutting contract changes. Adding `sourceId`, `canonicalName`, and `usedCustomizedName` required updating every adapter and exact-shape test (`docs/lessons/metadata-contracts-require-adapter-test-updates.md:11-21`; `src/command-sources/types.ts:3-10`).
- Keep collision policy explicit and observable: do not overwrite manual/config commands, preserve first discovered skills, and warn with stable prefixes (`src/plugin.ts:21-37`; `src/plugin/command-inject.ts:175-187`; `src/skills/discovery.ts:117-128`).
- Keep generated artifacts synchronized. CI regenerates and diffs the published schema, preventing source/schema drift (`.github/workflows/test.yml:31-41`). The repository’s retrospective also generalizes this into checking generated/planning artifacts rather than trusting a successful command alone (`docs/lessons/phase-complete-needs-artifact-consistency-check.md:11-21`).
- The implementation is intentionally adapter-oriented: add a new source by implementing `CommandSource`, returning `CommandInfo`, and registering it in the hook builder (`src/command-sources/types.ts:23-30`; `src/plugin/command-inject.ts:109-141`). Preserve ordering, metadata, recoverable warnings, and canonical collision fallback when doing so.
