## OpenCode Integration

The OpenCode package is an ESM workspace package named `odw-opencode`, exports `src/index.js`, requires `@opencode-ai/plugin >=1.2.0`, and keeps the host SDK as a development dependency pinned to `1.2.27` (`packages/opencode-plugin/package.json:1-26`). The root is a private npm-workspaces monorepo, requires Node >=20, and exposes workspace-wide test/lint/audit scripts (`package.json:1-31`).

The entrypoint is deliberately small in dependency surface: it imports the OpenCode `tool` helper plus Node built-ins, and documents both npm-plugin installation and a drop-in file installation (`packages/opencode-plugin/src/index.js:1-22`). It exports an async `OdwPlugin` factory and a default export (`packages/opencode-plugin/src/index.js:291-317`, `packages/opencode-plugin/src/index.js:486-490`). The plugin returns a `chat.message` hook and five tools: `odw_plan`, `odw_run`, `odw_status`, `odw_workflows`, and `odw_ultracode` (`packages/opencode-plugin/src/index.js:316-398`, `packages/opencode-plugin/src/index.js:398-485`).

### Useful patterns

- **Host-model execution before external orchestration.** When `client.session.prompt` is available, chat triggers and `odw_run` attempt the real engine through the already-configured OpenCode model, with daemon fallback when embedded dependencies or execution are unavailable (`packages/opencode-plugin/src/index.js:335-360`, `packages/opencode-plugin/src/index.js:418-438`). The README makes the user-visible distinction explicit: OpenCode runs inside the plugin without a daemon or second API key (`README.md:195-212`).
- **Fresh child sessions for agent isolation.** Every backend invocation creates a single-use session, reports it to the recursion guard, and defers deletion until `dispose()` to avoid conversation leakage and OpenCode deletion races (`packages/opencode-plugin/src/host-provider.js:24-36`, `packages/opencode-plugin/src/host-provider.js:41-65`, `packages/opencode-plugin/src/host-provider.js:111-121`).
- **Correct SDK response handling.** The backend omits `body.model` unless explicitly forced, sets the system prompt in `body.system`, defaults to a plain-text `title` agent, and accepts both direct and `{data:{parts}}` response shapes (`packages/opencode-plugin/src/host-provider.js:68-87`). It treats host errors and native tool-call turns as retryable protocol failures rather than silently passing empty output upstream (`packages/opencode-plugin/src/host-provider.js:93-108`, `packages/opencode-plugin/src/host-provider.js:124-127`).
- **Synchronous recursion/concurrency guard.** Module-level child-session tracking prevents ODW prompts from recursively retriggering `chat.message`; `embeddedActive` is checked and set without an intervening await, so concurrent triggers cannot pass the guard (`packages/opencode-plugin/src/index.js:206-220`, `packages/opencode-plugin/src/index.js:317-359`).
- **Conservative embedded fan-out.** Embedded runs default to 20 agents, support `ODW_MAX_AGENTS`, and cap inferred requested-worker expansion at 100 (`packages/opencode-plugin/src/index.js:163-164`, `packages/opencode-plugin/src/index.js:177-203`). The README documents the same safety override and optional model pin (`README.md:205-210`).
- **Commands as portable Markdown.** The package ships `/odw`, `/workflows`, and `/ultracode` command files with frontmatter and direct tool/trigger instructions (`packages/opencode-plugin/commands/odw.md:1-4`, `packages/opencode-plugin/commands/workflows.md:1-4`, `packages/opencode-plugin/commands/ultracode.md:1-6`).

## Security And Reliability

- **Local daemon authentication is explicit.** The client reads `ODW_DAEMON_TOKEN` first, otherwise a token file under `ODW_HOME` or `~/.odw`, strips BOM/whitespace, and attaches the bearer token to GET and POST requests (`packages/opencode-plugin/src/index.js:64-90`). A 401 is distinguished from connection failure and produces auth guidance instead of a misleading offline message (`packages/opencode-plugin/src/index.js:93-116`, `packages/opencode-plugin/src/index.js:295-313`).
- **Loopback-only transport reduces exposure.** The client hardcodes `http://127.0.0.1:<port>` and obtains the port from a validated positive environment value or local config, defaulting to 7345 (`packages/opencode-plugin/src/index.js:80-91`, `packages/opencode-plugin/src/index.js:126-138`). This is a useful default, but any future configurable remote endpoint would need TLS and token-handling review.
- **Failure containment is user-facing.** Chat triggers fall back to a structured native-subagent directive when the daemon is offline or embedded execution fails; daemon errors are truncated before insertion into chat output (`packages/opencode-plugin/src/index.js:276-286`, `packages/opencode-plugin/src/index.js:349-395`).
- **State is project-local but trusted.** Ultracode state is written beneath `<directory>/.opencode/state/odw/ultracode.json` with recursive directory creation and read failures treated as disabled (`packages/opencode-plugin/src/index.js:140-159`). The caller should therefore ensure `directory` is the intended project root before enabling the tool.
- **Sandbox boundary is outside the plugin.** The README says generated workflow scripts run in WASM-isolated QuickJS with only workflow primitives in scope (`README.md:54-70`), while contribution guidance says adapters must not import the daemon and communicate over localhost HTTP (`CONTRIBUTING.md:5-10`). Keeping that boundary avoids granting the OpenCode adapter direct engine/sandbox privileges.

Backend tests specifically cover session isolation/cleanup, response wrappers, model and agent overrides, missing sessions, upstream failures, native tool calls, and empty replies (`packages/opencode-plugin/test/host-provider.test.js:20-130`).

The repository CI runs `npm ci`, all tests, external tests, coverage, lint, high-severity audit, and a secrets scan on Ubuntu/macOS/Windows with Node 20 and 22 (`.github/workflows/ci.yml:8-25`, `.github/workflows/ci.yml:27-54`). Contribution guidance says runtime changes should include the crash-resume test and that core/daemon coverage is enforced at 80% (`CONTRIBUTING.md:21-25`).

Local verification in this isolated clone used:


The three failures were `plugin: odw_run tool prefers embedded OpenCode model and honors maxAgents`, `plugin: embedded OpenCode runs default to a twenty-agent safety cap`, and `plugin: explicit twenty-worker prompt lifts only the implicit embedded cap` (`packages/opencode-plugin/test/plugin.test.js:174-210`). Each received the daemon-offline fallback rather than embedded output because this clone has no `node_modules`; the lazy `import('odw-daemon/embedded')` therefore cannot resolve (`packages/opencode-plugin/src/index.js:229-237`). The daemon-stub, auth, trigger, shape, and backend tests passed. No clone installation or source changes were made.

## Packaging Lessons And Pitfalls

- Pin or tightly coordinate the host SDK used for live behavior. The package declares a broad peer range (`>=1.2.0`) but tests/development target `1.2.27`, while the source relies on observed response and session semantics (`packages/opencode-plugin/package.json:13-21`, `packages/opencode-plugin/src/host-provider.js:8-22`). A compatibility matrix or runtime capability checks are advisable for later SDK versions.
- Lazy importing `odw-daemon/embedded` enables the single-file/drop-in degradation path (`packages/opencode-plugin/src/index.js:222-237`), but it also means a missing workspace install is indistinguishable from a deliberately unsupported drop-in environment. Packaging and CI should test both the fully installed package and the drop-in fallback explicitly.
- The README says installation is from GitHub rather than npm and warns about an unrelated npm package name collision (`README.md:74-83`). Consumers need a clear release/package provenance story before this can be safely treated as a normal registry plugin.
- The plugin's `odw_plan`, `odw_status`, and `odw_workflows` tools remain daemon-gated, while `odw_run` prefers embedded execution (`packages/opencode-plugin/src/index.js:406-438`, `packages/opencode-plugin/src/index.js:442-475`). Command documentation that says “daemon” should remain aligned with this dual mode to avoid confusing offline behavior (`packages/opencode-plugin/commands/workflows.md:1-4`).
- The test suite is unusually strong on protocol edge cases and auth, but the failed embedded tests show a practical packaging gap: the isolated package cannot prove its primary OpenCode path without workspace dependencies installed. A dedicated test setup assertion or an install-aware test command would make this failure mode clearer.
