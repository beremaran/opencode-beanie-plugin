## What it does

Daytona's plugin runs each OpenCode session in its own remote Daytona sandbox, maps the session to durable local metadata, and optionally synchronizes sandbox commits to numbered local branches. The package README describes isolation, indefinite sandbox persistence, preview links, and git synchronization (`packages/opencode-plugin/README.md:1-10`). It explicitly warns that synchronization can overwrite locally made changes on the generated `opencode/*` branches (`packages/opencode-plugin/README.md:95-105`).

## OpenCode integration patterns

- **Minimal package entrypoint.** `index.ts` re-exports the default plugin from the Daytona implementation (`.opencode/plugin/index.ts:6-11`). This keeps the published entry stable while allowing the implementation to remain organized under `daytona/`.
- **Lifecycle hook composition.** The plugin initializes toast/UI state and returns three hook groups: custom tools, an event handler, and `experimental.chat.system.transform` (`.opencode/plugin/daytona/index.ts:47-53`). This is a useful pattern for keeping tool registration, event behavior, and agent instructions separate.
- **Context-bound tool factories.** `customTools` captures `ctx.project.id` and `ctx.project.worktree`, then passes them into all tool factories (`.opencode/plugin/daytona/plugins/custom-tools.ts:14-18`). The tool registry consistently obtains the session through `ToolContext.sessionID` before operating (`.opencode/plugin/daytona/tools.ts:23-40`; `.opencode/plugin/daytona/tools/read.ts:21-25`).
- **Replacing core operations in a remote workspace.** The plugin registers sandbox equivalents for `bash`, `read`, `write`, `edit`, `multiedit`, `ls`, `glob`, `grep`, and preview URLs (`.opencode/plugin/daytona/tools.ts:29-40`). The system transform tells the model that `/home/daytona/project` is authoritative and not to use the host working directory (`.opencode/plugin/daytona/plugins/system-transform.ts:12-25`).
- **Event-driven synchronization and cleanup.** `session.deleted` deletes the associated sandbox; `session.idle` ensures the sandbox exists and auto-commits/pulls changes (`.opencode/plugin/daytona/plugins/session-events.ts:16-48`). Idle failures are logged without rethrowing to avoid noisy duplicate notifications, while deletion failures are surfaced and rethrown (`.opencode/plugin/daytona/plugins/session-events.ts:24-31`, `:44-48`).

## Architecture and durable state

- `DaytonaSessionManager` keeps a per-process session cache and reloads lightweight `{ id }` records from disk when the project context changes (`.opencode/plugin/daytona/core/session-manager.ts:20-69`). It reconnects existing sandboxes, starts stopped ones, creates replacements only for confirmed `DaytonaNotFoundError`, and propagates transient errors so mappings are not lost (`.opencode/plugin/daytona/core/session-manager.ts:99-166`).
- Project state is stored under the XDG data directory, with a fallback to `~/.local/share`, and log/state paths are established once at module load (`.opencode/plugin/daytona/index.ts:39-45`). The README documents the resulting per-project JSON location and stored metadata (`packages/opencode-plugin/README.md:107-116`).
- Storage filenames use `encodeURIComponent(projectId)` to prevent path traversal and preserve round-trippable project IDs (`.opencode/plugin/daytona/core/project-data-storage.ts:28-35`). The migration path writes the destination and verifies it can be loaded before deleting the source (`.opencode/plugin/daytona/core/project-data-storage.ts:78-123`), and deletion uses a read-only lookup to avoid accidental migration (`.opencode/plugin/daytona/core/project-data-storage.ts:130-149`).
- Sandbox lifecycle failures are deliberately distinguished: a missing sandbox clears stale state, while authentication/network/provisioning failures preserve the mapping for retry (`.opencode/plugin/daytona/core/session-manager.ts:153-165`). This is a strong durable-state rule for integrations with an external service.

## Git synchronization patterns

- The host-side manager runs Git with `spawnSync` and an explicit argument vector, not a shell, specifically to prevent SSH URLs, refs, and remote names from becoming shell syntax (`.opencode/plugin/daytona/git/host-git-manager.ts:23-36`).
- Per-repository promise queues serialize operations sharing a canonical git common directory, including linked worktrees and symlink aliases (`.opencode/plugin/daytona/git/host-git-manager.ts:38-97`). This addresses races around remotes and `.git/config.lock`.
- Branch allocation scans `refs/heads/opencode/`, reserves the next number immediately with `update-ref`, and supports repositories with no commits by creating an empty reservation commit (`.opencode/plugin/daytona/git/host-git-manager.ts:112-163`, `:170-215`). The 50-attempt circuit breaker is a useful bound, though the fallback path still attempts one final allocation after the loop (`:137-163`).
- Pulling fetches into `FETCH_HEAD`, updates the numbered local ref explicitly, and hard-resets the working tree only when that branch is checked out (`.opencode/plugin/daytona/git/host-git-manager.ts:268-313`). This avoids fetching directly into a checked-out branch.
- Sandbox setup initializes Git with a fixed identity, auto-adds and commits changes, then resets/cleans to the pushed branch (`.opencode/plugin/daytona/git/sandbox-git-manager.ts:33-44`, `:46-77`). `SessionGitManager` disables sync when the host is not a repository but still creates the sandbox directory (`.opencode/plugin/daytona/git/session-git-manager.ts:59-77`).

## Security and reliability lessons

### Positive patterns

- The Daytona API key is read from the environment and missing credentials fail early with a user-facing error (`.opencode/plugin/daytona/index.ts:44-45`; `.opencode/plugin/daytona/core/session-manager.ts:82-94`).
- Host Git avoids shell interpolation (`.opencode/plugin/daytona/git/host-git-manager.ts:23-36`). This should be treated as mandatory whenever plugin inputs influence Git remotes or refs.
- Local state path construction is encoded and bounded to the configured storage directory (`.opencode/plugin/daytona/core/project-data-storage.ts:28-35`).
- Editing is conservative: empty replacements are rejected and each old string must match exactly once before upload (`.opencode/plugin/daytona/tools/edit.ts:23-42`; `.opencode/plugin/daytona/tools/multiedit.ts:27-52`). The multi-edit operation applies all validations before the single upload, giving it practical all-or-nothing behavior.
- Logging is best effort and bounded by byte size, with partial first lines removed after trimming (`.opencode/plugin/daytona/core/logger.ts:27-55`).

### Risks and pitfalls

- The remote tools accept arbitrary file paths for read/write/edit and arbitrary shell commands for `bash`; there is no plugin-level path confinement or command allowlist (`.opencode/plugin/daytona/tools/read.ts:17-25`, `write.ts:17-25`, `bash.ts:19-48`). Isolation is delegated to the Daytona sandbox, so the sandbox image, identity, network policy, and API authorization are part of the security boundary.
- The background shell path interpolates the fixed repository path into `cd ${repoPath}` (`.opencode/plugin/daytona/tools/bash.ts:28-47`). It is currently a constant, but this pattern should remain constrained if the path ever becomes configurable.
- `getSshUrl` embeds a short-lived SSH token in the URL (`.opencode/plugin/daytona/git/session-git-manager.ts:46-49`), while host Git logs the complete URL (`.opencode/plugin/daytona/git/host-git-manager.ts:225-231`). That can expose credentials in the local Daytona log; redact the token before logging.
- Sandbox Git constructs shell command strings, including branch interpolation (`.opencode/plugin/daytona/git/sandbox-git-manager.ts:19-30`, `:64-71`). Current branch names are generated numeric/constant values, but future externally sourced refs would need strict validation or an SDK/argument-vector API.
- `git clean -fd` and `reset --hard` intentionally discard sandbox-local files and changes (`.opencode/plugin/daytona/git/sandbox-git-manager.ts:64-71`). The README's overwrite warning should be prominent in installation UX, and sync tests should assert the exact destructive boundary.
- JSON state is parsed and cast without runtime schema validation (`.opencode/plugin/daytona/core/project-data-storage.ts:64-75`). Corrupt or manually edited files become a logged null result rather than a typed diagnostic; a Zod schema would make persisted-state compatibility explicit.

## Bottom line

This is a clear example of an OpenCode plugin that virtualizes the agent's workspace rather than adding one isolated tool: hook composition redirects tools, prompts, and lifecycle events into a per-session remote sandbox, while a durable mapping and serialized Git bridge restore usable local branches. The most reusable engineering practices are explicit host-process argument vectors, per-repository operation serialization, durable-state migration with write verification, and conservative edit semantics. The principal follow-ups are credential redaction, runtime validation of persisted state, explicit sandbox policy documentation, and a real test suite around lifecycle/error and destructive Git paths.
