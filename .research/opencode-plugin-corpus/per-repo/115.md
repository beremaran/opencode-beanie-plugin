## OpenCode patterns

### Server hook and prompt injection

- The plugin exports a `PluginModule` with id `opencode-toon-config-plugin`; its `server` receives OpenCode's `directory` and `worktree`, resolves options, locates the instruction file, and returns an empty hook set when none is found (`src/index.ts:4-7`, `src/index.ts:107-116`). This is a small, clear lifecycle boundary for plugins that need project context but do not need a long-lived external service.
- Lookup is deterministic: `directory/AGENTS.toon` wins, then `worktree/AGENTS.toon`; the first existing path is returned (`src/index.ts:40-47`). The README documents the same order and explicitly says the plugin does nothing when neither exists (`README.md:87-95`).
- The implementation uses `experimental.chat.system.transform`, pushes one string containing `Instructions from: <path>` followed by the complete file body, and optionally pushes a separate evaluation annotation (`src/index.ts:122-127`). The tests verify the header, full body, lookup precedence, and one-versus-two system entries (`tests/plugin.test.ts:45-95`, `tests/plugin.test.ts:155-203`).
- The README calls out coexistence behavior: built-in `AGENTS.md` loading remains active, so having both files injects both instruction sets (`README.md:97-102`). A plugin using a parallel instruction channel should document duplication and precedence rather than silently replacing OpenCode behavior.

### Cache and reload design

- Startup reads the file once and caches ready-to-inject content, SHA-256 of the raw body, mtime, size, and an approximate token count (`src/index.ts:21-28`, `src/index.ts:49-63`). On each transform call, unchanged mtime and size avoid a read; changed metadata triggers a read/hash, and identical content only refreshes metadata (`src/index.ts:65-94`). This is a practical two-stage invalidation pattern for per-turn hooks.
- If the file disappears after startup, the implementation catches `statSync` failure, logs a warning, and intentionally keeps serving the last known content (`src/index.ts:67-75`; `AGENTS.toon:23-25`). That behavior is explicit and tested indirectly through the stated cache contract, but it is a policy decision with security implications (see below).
- The README explains the same stat-then-SHA-256 strategy and its intended syscall/read tradeoff (`README.md:55-68`). The benchmark script measures full reads over 500 runs and stat checks over 2,000 runs, rather than presenting only an anecdotal timing (`scripts/compare-agents.ts:6-12`, `scripts/compare-agents.ts:22-23`, `scripts/compare-agents.ts:80-89`).

### Optional evaluation channel

- `evaluate` is resolved defensively from boolean or string `true`/`false`, defaults off, and logs an unrecognized value before falling back to false (`src/index.ts:96-105`). The README shows the OpenCode tuple plugin configuration for enabling it (`README.md:320-337`).
- The heuristic deliberately scores only token efficiency and structural quality, while leaving actionability, exactness, non-redundancy, and completeness to the LLM command (`src/heuristic.ts:1-12`). Its annotation is kept to two lines plus optional warnings because it is itself injected every turn (`src/heuristic.ts:194-203`). This separation is a useful pattern: do not imply static heuristics can validate subjective instruction quality.
- The packaged `/evaluate-toon` command uses a format-neutral rubric and instructs the model to cite specific entries for subjective scores (`commands/evaluate-toon.md:8-14`, `commands/evaluate-toon.md:97-125`). The command is an installable asset, not automatically registered by the plugin; users must copy it into `.opencode/commands` (`README.md:253-269`).

## Pitfalls and security lessons

- **Stale instructions after deletion:** serving cached instructions after the source file is deleted preserves availability but can violate a user's expectation that removing a rules file removes its authority (`src/index.ts:67-75`). A production variant should make this policy configurable or fail closed when instruction revocation matters, and should test deletion explicitly.
- **Prompt trust boundary:** file contents are inserted verbatim into the system transform, with no size limit, sanitization, or provenance beyond a filesystem path (`src/index.ts:49-54`, `src/index.ts:122-127`). Any actor able to modify the selected `AGENTS.toon` can alter model behavior; deployments should treat the project/worktree and instruction file as trusted inputs, restrict write access, and consider a maximum size.
- **Path disclosure:** the injected header includes the absolute path supplied by OpenCode (`src/index.ts:53`). That is useful provenance, but it may expose local usernames or workspace layout to the model/provider. Use a relative or redacted label if path privacy is a requirement.
- **Synchronous hook work:** `statSync`, `readFileSync`, and SHA-256 calculation occur in the server setup and transform path (`src/index.ts:49-62`, `src/index.ts:67-93`). The fast path is only a stat, but a changed file blocks the hook synchronously and a large file can cause repeated latency. Async filesystem APIs, bounded input, or a watcher may be appropriate for high-throughput use.
- **Cache race semantics:** after a successful stat, the file can change before `readFileSync`, and the implementation has no retry or atomic-snapshot handling (`src/index.ts:77-93`). For ordinary local edits this is acceptable; concurrently generated instruction files could yield a transient mixed version.
- **Heuristic limits:** token count is `ceil(text.length / 4)`, not tokenizer output (`src/index.ts:34-38`, `src/heuristic.ts:22-24`), and format detection is regex-based (`src/heuristic.ts:27-47`). The README labels counts as estimates (`README.md:104-115`), but consumers should not use the scores as a security gate or billing-grade measurement.
- **Command input is model-directed:** `/evaluate-toon` tells the model to read the path passed in `$ARGUMENTS` (`commands/evaluate-toon.md:1-6`). If the command is exposed to untrusted users, command/file-tool permissions must constrain what paths can be read; the command itself does not establish an authorization boundary.

## Testing lessons

- The test suite uses isolated temporary directory/worktree pairs and cleans them in `afterEach`, avoiding repository fixtures for path-resolution tests (`tests/plugin.test.ts:30-43`). It covers directory lookup, worktree fallback, precedence, missing-file behavior, exact injection shape, unchanged cache, content reload, and post-reload persistence (`tests/plugin.test.ts:45-153`).
- Option behavior is tested across boolean and string values, including annotation count/prefix and annotation refresh after a large content change (`tests/plugin.test.ts:171-236`). This is especially useful for OpenCode config tuple options, where values may be serialized differently by configuration layers.
- Heuristic tests cover all four format classifications, score ordering, depth/key penalties, warnings, and annotation shape (`tests/heuristic.test.ts:6-28`, `tests/heuristic.test.ts:30-87`, `tests/heuristic.test.ts:90-145`). The tests validate stated invariants rather than exact tokenizer counts.
- The repository declares separate `just check`, `just test`, focused suites, and a combined `just ci` recipe (`Justfile:12-20`, `Justfile:27-40`, `Justfile:52-58`). In this review, `bun tsc --noEmit` passed and `bun test tests/` passed with 35 tests across the two files.
- Gaps worth adding are explicit deletion/revocation tests, unreadable-file/error-path tests, large-file behavior, concurrent rewrite behavior, invalid option values, and a runtime smoke test against the actual OpenCode hook contract rather than only `any`-cast test doubles (`tests/plugin.test.ts:12-26`, `src/index.ts:68-75`).

## Packaging and maintenance

- The package uses a peer dependency on `@opencode-ai/plugin >=1.0.0` and pins the development plugin API to `^1.14.24`; TypeScript is strict with declarations and source maps enabled (`package.json:41-49`, `tsconfig.json:1-18`). Keeping the host API as a peer avoids bundling OpenCode internals into the plugin.
- `files` publishes `dist` and `commands`, while `prepublishOnly` removes and rebuilds `dist` (`package.json:14-21`). This makes the command asset available from npm, but README installation instructions still require a manual copy, so packaging and activation are intentionally separate (`README.md:253-269`).
- A pre-commit hook rebuilds and stages `dist`, and the repository guidance says generated output must not be edited directly (`scripts/pre-commit.sh:4-10`, `AGENTS.toon:34-40`). This keeps checked-in artifacts synchronized, but staging from a hook is a contributor-workflow side effect that CI should independently verify.
- The package metadata includes `main`, `types`, conditional `exports`, repository, homepage, bugs URL, keywords, and MIT license (`package.json:6-12`, `package.json:23-39`). The explicit exports/declaration layout is a useful baseline for a consumable ESM OpenCode plugin.

## Bottom line

This repository demonstrates a focused OpenCode integration: use the server context for directory/worktree-aware discovery, register a system transform, push instruction entries rather than replacing the host prompt, and cache file content with cheap metadata checks plus content verification. Its strongest engineering practices are explicit lookup semantics, isolated filesystem tests, focused heuristic tests, strict TypeScript packaging, and declared build/test recipes. The main production concerns are the deliberate stale-cache-on-delete policy, unbounded trusted-file injection, absolute-path disclosure, synchronous reload work, and lack of tests for deletion/error/concurrency boundaries.
