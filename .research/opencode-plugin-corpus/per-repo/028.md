## What the plugin demonstrates

### OpenCode entrypoint and compatibility

- The package exposes one object that is both a callable V1 plugin and a V2 definition: V1 setup is an async function, V2 setup is created with `V2Plugin.define({ id: "goopspec", setup })`, and the export combines them with `Object.assign` (`packages/opencode-plugin/src/index.ts:23-25`, `63-65`, `117-118`). This is a useful migration pattern because the host can select its contract without a user-facing config switch.
- V1 assembles context, hooks, tools, a config watcher, and disposal handling; initialization failures are logged and degrade to `{}` rather than crashing the host (`packages/opencode-plugin/src/index.ts:23-60`). V2 follows the same principle and logs setup failures (`packages/opencode-plugin/src/index.ts:65-91`).
- V1 is the canonical implementation. The V2 tool adapter iterates over `createTools`, converts the V1 Zod argument definitions to JSON Schema, and invokes the original V1 executor (`packages/opencode-plugin/src/core/tools-v2.ts:21-30`, `39-67`, `70-85`). The V2 hook adapter similarly creates the V1 hook set once and maps supported runtime events (`packages/opencode-plugin/src/core/hooks-v2.ts:1-5`, `263-300`). This avoids behavior drift between contracts.
- The SDK boundary is localized: V2 imports are intended to occur only in `v2-compat.ts`, which explicitly describes the beta API volatility and compatibility seam (`packages/opencode-plugin/src/core/v2-compat.ts:1-17`, `19-46`).
- The V2 adapter guards optional capabilities before use. Missing tool capability skips registration, missing session capability skips system-hook registration, and missing agent/catalog capabilities skip thinking-level transforms (`packages/opencode-plugin/src/core/tools-v2.ts:43-47`, `packages/opencode-plugin/src/core/hooks-v2.ts:218-227`, `285-298`). This is a practical host-version compatibility technique.

### Hook and tool composition

- Hook factories are registered declaratively in `DEFAULT_HOOK_FACTORIES`, then merged by event name. Same-event handlers are chained sequentially so mutations accumulate; tool maps are shallow-merged (`packages/opencode-plugin/src/hooks/index.ts:33-51`, `69-84`, `102-113`, `145-156`). This keeps feature hooks independently testable while preserving deterministic ordering.
- The README describes the plugin as a workflow orchestrator with SQLite state, specialized agents, tools, and runtime hooks (`README.md:17-29`). The implementation confirms the broad surface: the integration test constructs real context/subsystems and asserts a 38-tool inventory (`packages/opencode-plugin/src/integration.test.ts:90-172`).
- V2 deliberately omits `goop_compact` unless a real session summarize capability exists, rather than exposing a non-functional tool (`packages/opencode-plugin/src/core/tools-v2.ts:49-56`; coverage at `packages/opencode-plugin/src/core/tools-v2.test.ts:55-97`).

## Configuration and packaging lessons

- Installation is conventional OpenCode configuration: add `@goopspec/opencode-plugin` to `opencode.json`; local development can point at the package directory (`README.md:58-90`). The package declares `@opencode-ai/plugin` as both a dependency and peer dependency at `^1.18.0`, and requires Bun >=1.0 (`packages/opencode-plugin/package.json:34-50`).
- Configuration supports a checked-in example with enforcement mode, model selection, per-role thinking levels, and agent overrides (`goopspec.example.json:1-25`, `27-84`). The README documents project, `.goopspec`, global, and built-in precedence (`README.md:539-600`).
- The config watcher watches the parent directory, not the file, so atomic replacement does not detach the watch; it debounces edits, parses and normalizes before delivery, and disposes timers/watchers (`packages/opencode-plugin/src/features/setup/config-watcher.ts:18-25`, `33-55`, `57-76`). Tests cover normalization, debounce collapse, disposal, and repeated edits (`packages/opencode-plugin/src/features/setup/config-watcher.test.ts:31-107`).
- V1 and V2 have an explicit reload boundary: V1 updates future turns but requires restart for the agent menu, while V2 reloads transforms when the runtime supports it (`packages/opencode-plugin/src/index.ts:29-38`, `73-87`). The V1 behavior is also asserted by the entrypoint test (`packages/opencode-plugin/src/index.test.ts:120-141`).
- Packaging should be audited carefully. The plugin package points `main` and `exports` at `src/index.ts`, builds a Bun bundle into `dist`, but its `files` list includes only `src`, `agents`, `commands`, and `references` (`packages/opencode-plugin/package.json:6-18`). `templates` are present in the repository but excluded from that list, and `dist` is not listed. If publishing relies on the package manifest, runtime assets or the intended built artifact may be absent. This is a concrete packaging risk, not merely a documentation concern.
- Repository-level metadata is private and workspace-oriented (`package.json:1-20`), while CI runs typecheck and tests on Ubuntu and Windows with Bun latest (`.github/workflows/ci.yml:9-22`). There is no CI build, lint, package-content check, or published-install smoke test in that workflow.
- Documentation counts are inconsistent and should not be used as an API inventory: the README says 35 tools and 1,956 tests (`README.md:8-12`, `17-29`), while current integration and entrypoint tests assert 38 tools (`packages/opencode-plugin/src/integration.test.ts:104-154`, `packages/opencode-plugin/src/index.test.ts:143-163`). The entrypoint test itself has stale wording (“35 tools”) while expecting 38 (`packages/opencode-plugin/src/index.test.ts:143-149`). Prefer generated/emitted schemas and executable inventory tests.

## Security and reliability findings

- The orchestrator write boundary is enforced through the SDK `permission.ask` hook: implementation writes are denied, while `.goopspec` documentation writes pass (`packages/opencode-plugin/src/hooks/orchestrator-enforcement.ts:4-12`, `84-109`). This is stronger than prompt-only policy and is explicitly presented as such in the README (`README.md:122-128`).
- That enforcement is fail-open when `ctx.session.agent` is unavailable. The code comment says an unbound session conservatively allows the operation, and the handler returns immediately for a non-orchestrator/unknown identity (`packages/opencode-plugin/src/hooks/orchestrator-enforcement.ts:14-23`, `89-105`). This avoids blocking legitimate work but leaves a security gap during identity-binding races or failures. A consumer should monitor identity initialization and decide whether its threat model permits this tradeoff.
- V2 cannot provide equivalent enforcement for permission hooks. The adapter documents that permission, config, command, event, and compaction hooks remain V1-only, and logs that lazy autopilot is unavailable (`packages/opencode-plugin/src/core/hooks-v2.ts:263-278`). The README likewise says those features stay inert under V2 (`README.md:649-681`). V2 users therefore do not receive the same policy guarantees as V1 users.
- V2 tool before/after events do not carry a call identifier; the adapter pairs events using a per-tool FIFO queue (`packages/opencode-plugin/src/core/hooks-v2.ts:83-141`, `263-269`). Concurrent or reordered host events could associate lifecycle metadata with the wrong call. This is an interoperability limitation worth testing against the host runtime.
- V2 supplies a stub client and an intentionally failing shell runner because the V2 context lacks V1 equivalents (`packages/opencode-plugin/src/core/context-v2.ts:13-35`). This is safer than guessing, but any V1 feature depending on client/shell must be capability-gated, as compaction is. The adapter’s explicit omission demonstrates the right pattern (`packages/opencode-plugin/src/core/tools-v2.ts:49-56`).
- Loop detection records normalized arguments/output, rewrites repeated no-progress output at Tier 1, records chronicle/ADL evidence, and denies the associated permission request (`packages/opencode-plugin/src/hooks/loop-detection/index.ts:94-175`). Tests cover thresholds, varying output, interruption, disabled/malformed config, and exactly-once evidence writes (`packages/opencode-plugin/src/hooks/loop-detection/index.test.ts:74-184`, `186-234`). This is a useful defense against agent stalls, but it is session-wide module state (`index.ts:17-35`), so lifecycle/reset behavior deserves attention in long-lived or multi-tenant hosts.
- The plugin’s general error policy is graceful degradation: the repository guidance says operations should log and return fallback results rather than throw (`AGENTS.md:242-245`), and the entrypoint catches setup failures. This protects the host session, but it can also conceal partial feature loss unless diagnostics are surfaced and monitored.

## Testing lessons

- Tests are co-located and use shared temporary-environment and mock-context factories (`AGENTS.md:161-200`, `packages/opencode-plugin/src/integration.test.ts:39-45`). The suite spans unit tests for hooks/tools/features plus integration tests of context assembly, phase gates, routing, enforcement, and delegation (`packages/opencode-plugin/src/integration.test.ts:74-173`, `218-260`).
- Entrypoint contract tests validate identity of named/default exports, V1 callability, disposal, tool parity, executable registration, V2 registration, and V1/V2 output equivalence (`packages/opencode-plugin/src/index.test.ts:94-179`, `181-220`). This is a strong pattern for plugin migrations: test the host-visible contract, not only internal functions.
- Schema conversion is tested at the host boundary, including descriptions and required-array behavior (`packages/opencode-plugin/src/core/tools-v2.test.ts:99-133`, `163-178`). The adapter correctly uses the SDK-bundled `tool.schema` rather than a separate Zod instance to avoid losing descriptions (`packages/opencode-plugin/src/core/tools-v2.ts:21-30`).
- CI uses Bun latest (`.github/workflows/ci.yml:16-21`) while package metadata pins TypeScript and the OpenCode SDK ranges. Reproducibility would improve with a pinned Bun version and a build/package smoke test. The clone’s own guidance also warns that a wrapper can misreport Bun test counts and recommends `rtk proxy` (`AGENTS.md:25-27`); test-result reporting should be independently verified.

## Bottom line

GoopSpec is a substantial OpenCode plugin example with a particularly reusable migration architecture: one V1 source of truth, a narrow V2 compatibility seam, capability checks, host-visible contract tests, and explicit disposal. The main pitfalls are contract asymmetry (V2 lacks permission and other hooks), fail-open orchestrator identity, FIFO lifecycle pairing, and packaging/metadata drift. For a new plugin, copy the adapter and test-boundary patterns, but add explicit published-tarball validation, build checks in CI, and a documented security decision for missing identity/capabilities.
