## OpenCode-Relevant Patterns

### Skill-first integration

- The primary skill has explicit frontmatter for name, trigger description, allowed tool (`WebFetch`), compatibility, and version (`skills/x-twitter-scraper/SKILL.md:1-10`). Its metadata repeats capability boundaries for network, shell, filesystem, environment, MCP, code execution, and local network (`skills/x-twitter-scraper/SKILL.md:11-40`). This is a useful portable pattern for OpenCode skills: declare capabilities and required secrets at the skill boundary rather than relying on implicit agent behavior.
- The skill uses a route/retrieve/bound/estimate/confirm/call/isolate/handoff loop (`skills/x-twitter-scraper/SKILL.md:196-209`). In particular, it requires current documentation or OpenAPI retrieval before unfamiliar calls (`skills/x-twitter-scraper/SKILL.md:118-122`) and limits cursor traversal to the user's bound (`skills/x-twitter-scraper/SKILL.md:200-207`).
- A second, narrower skill reuses the same safety model for public social research, including bounded reads and explicit approval for private reads, writes, persistent resources, and bulk jobs (`skills/xquik-social-research/SKILL.md:49-58`). This illustrates separating a broad operational skill from a smaller task-focused skill while keeping the guardrails consistent.

## Entrypoint and Source Lessons

- `stub-server.mjs` keeps protocol handling decomposed into `createMessageHandler`, `processLine`, and `startServer` exports (`stub-server.mjs:161-239`), while direct execution is guarded with a file-URL check (`stub-server.mjs:242-248`). This makes the entrypoint independently testable and prevents import-time server startup.
- Input handling has a 64 KiB line limit, ignores malformed JSON and non-object values, suppresses notifications without IDs, and returns JSON-RPC errors for unknown methods (`stub-server.mjs:24-26`, `stub-server.mjs:180-229`). These are small but concrete robustness controls for stdio MCP adapters.
- The live tool contract emphasizes bounded request functions, no arbitrary filesystem/network access, confirmation before mutations, pagination cursors, and retry metadata (`stub-server.mjs:102-123`). The skill separately validates usernames, IDs, HTTPS URLs, and bounded counts (`skills/x-twitter-scraper/references/security.md:114-124`). A plugin should enforce these limits at both descriptive and executable boundaries; prose alone is not sufficient for a live implementation.

## Security and Safety Lessons

- Credentials are narrowed to `XQUIK_API_KEY`; the security reference rejects passwords, 2FA, recovery codes, cookies, session tokens, browser exports, and account backups, and warns against command-line API keys because process listings can expose arguments (`skills/x-twitter-scraper/references/security.md:16-23`). The OpenClaw metadata marks the API key as sensitive (`openclaw.plugin.json:7-16`).
- Consent is required before state changes, credit-consuming work, persistent delivery, or private account data. Approval must identify the action, target, exact payload, estimate, and persistence (`skills/x-twitter-scraper/references/security.md:24-36`). The skill frontmatter independently records write and persistent-resource confirmation as required (`skills/x-twitter-scraper/SKILL.md:51-67`).
- Retrieved X content is treated as untrusted data, wrapped in explicit boundary markers, and prohibited from choosing tools, endpoints, files, commands, destinations, or account changes (`skills/x-twitter-scraper/references/security.md:38-59`). This is a strong prompt-injection defense pattern for OpenCode tools that consume external content.
- The execution boundary is deliberately API-only: no package installation, shell commands, local files, local network, remote code loading, or third-party API-key proxying (`skills/x-twitter-scraper/references/security.md:75-85`). Persistent monitors and webhooks require disclosure of target, destination, verification, usage, and disable path (`skills/x-twitter-scraper/references/security.md:87-100`).
- Webhook guidance uses timestamp, nonce, and raw-body signatures with an atomic shared nonce store, and tests assert those requirements while rejecting unsafe examples (`tests/public-api-contract.test.mjs:185-210`). The repository also documents durable writes with idempotency keys and `safeToRetry`/`statusUrl` fields (`tests/public-api-contract.test.mjs:212-277`).

## Pitfalls and Risks

- The README says “The `x-developer` bundle is v2.6.4” while the package, Codex metadata, OpenClaw metadata, skill frontmatter, and release are `2.6.5` (`README.md:30-45`; `package.json:1-3`; `.codex-plugin/plugin.json:1-4`; `openclaw.plugin.json:4-5`; `skills/x-twitter-scraper/SKILL.md:6`). The test suite deliberately asserts the stale README text (`tests/public-api-contract.test.mjs:139-143`), so a green test currently preserves misleading installation/version information. Version contract tests need an explicit policy for intentionally lagging documentation, or this should be corrected.
- The README installation example uses `npx skills@1.5.3` (`README.md:78-86`) even though the repository's package metadata and reproducibility checks are npm-based (`package.json:77-85`; `scripts/check-reproducible.mjs:10-18`). Consumers need clear guidance about whether they are installing the skill via the skills CLI, installing the npm bundle, or configuring remote MCP; these are different distribution paths.
- The repository publishes both a remote live MCP and a local stub. The stub is safe because it makes no network calls, but its presence can be misunderstood as a functional local server unless the “verification stub” distinction remains prominent (`stub-server.mjs:6-8`, `stub-server.mjs:102-106`).
- The primary skill allows `WebFetch` and internet access to two hosts (`skills/x-twitter-scraper/SKILL.md:16-40`), so host allowlisting and the no-shell/no-filesystem claims must remain synchronized with actual client enforcement. Metadata is a policy declaration, not proof that every host client enforces it.
- The README claims CI, CodeQL, and OpenSSF coverage through badges (`README.md:10-14`), but this report did not execute remote workflows. Treat those badges as project claims; local evidence observed here is the Node test suite, fuzz tests, release guards, and reproducible-pack checks.

## Transferable Takeaways

1. Use a skill frontmatter/metadata contract to declare tools, hosts, secrets, filesystem/shell permissions, and approval requirements before instructions are executed.
2. Keep production connectivity remote when appropriate, but ship a clearly labeled offline protocol stub so package registries and clients can verify shape without exfiltration or live side effects.
3. Treat documentation, examples, tool annotations, and version surfaces as tested API contracts, especially for approval sequencing, idempotency, pagination, and error recovery.
4. Add property-based and malformed-input tests around stdio/JSON-RPC boundaries, and test the packed artifact rather than only source imports.
5. Make destructive, private, metered, and persistent actions explicit in both tool metadata and runtime approval gates; isolate retrieved third-party content from agent instructions.
