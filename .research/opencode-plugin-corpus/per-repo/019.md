# Repository 019: dodopayments/dodo-agent-plugin

## Scope and availability

- Manifest index 19 resolves to `https://github.com/dodopayments/dodo-agent-plugin`; the inspected clone is `.research/opencode-plugin-corpus/repos/dodopayments--dodo-agent-plugin` (`manifest.json:169-174`). The clone was available and was not modified.
- This is a multi-client Agent Plugins repository, not an OpenCode-only implementation. The root `plugin.json` and `mcp.json` are canonical Agent Plugins 1.0.0 artifacts; provider-specific manifests are compatibility shims (`README.md:8-10`, `README.md:324-335`).
- The OpenCode-specific subdirectory is `opencode-plugin/`, containing `README.md` and `index.js`. No directory named `manifest` was present; the relevant manifest/config files are the root `plugin.json`, root `mcp.json`, and generated `plugins/dodopayments/` bundle.
- The package provides seventeen vendored `SKILL.md` skills and two MCP servers (`README.md:12-16`, `README.md:205-212`). The explicit skill inventory and provenance are recorded in `.skills-source.json:2-35`.

## SDK and registration

- The npm package is ESM, exposes `opencode-plugin/index.js` as its sole package entrypoint, and declares `@opencode-ai/plugin >=1.0.0` as an optional peer dependency (`package.json:2-15`, `package.json:40-46`).
- The entrypoint uses JSDoc typing rather than a runtime SDK import: `@typedef {import("@opencode-ai/plugin").Plugin} Plugin` (`opencode-plugin/index.js:5-7`).
- The module exports exactly one default async function, `dodopayments`, returning the OpenCode plugin object (`opencode-plugin/index.js:65-76`). The source deliberately has no named exports because the documented loader behavior rejects non-function exports and silently skips the entire plugin (`opencode-plugin/index.js:9-21`; `opencode-plugin/README.md:27-30`).
- Registration is implemented through the `config` hook. It initializes `config.mcp`, then inserts each default server with `??=` (`opencode-plugin/index.js:66-73`). This makes project-level declarations authoritative and provides a minimal, composable registration pattern (`opencode-plugin/README.md:68-90`).

## Hooks, events, and context

- The only OpenCode lifecycle hook is `config`; there are no session, message, tool, command, or event handlers (`opencode-plugin/index.js:66-74`). The hook receives and mutates OpenCode’s config object; no client, directory, or session context is used.
- The hook runs before skill discovery cannot be repaired by setting `config.skills`: the README and source note that the skill index is built before config hooks, so users must configure `skills.paths` directly (`opencode-plugin/index.js:23-26`; `README.md:112-132`).
- There is no plugin-managed state, persistence, background process, cleanup, or in-process cache. The only conditional state is the caller’s environment at plugin initialization (`opencode-plugin/index.js:50-63`).

## Tools and commands

- The OpenCode plugin registers no OpenCode-native tools or slash commands. It registers two external MCP servers: `dodopayments-api` for live payments/billing operations and `dodo-knowledge` for documentation search (`opencode-plugin/index.js:37-48`; `opencode-plugin/README.md:42-47`). MCP tools are therefore supplied by the remote servers, not implemented in this package.
- OpenCode uses a local stdio wrapper command, `npx -y mcp-remote@latest <URL>`, for both endpoints (`opencode-plugin/index.js:37-47`). The canonical Agent Plugins config instead uses native `streamable-http` URLs (`mcp.json:1-12`); the compatibility `.mcp.json` uses the same `mcp-remote` bridge (`.mcp.json:1-24`).
- The two endpoint definitions are intentionally hand-written in `index.js`; `scripts/conformance.mjs` drives the real hook and compares registered endpoint URLs against canonical `mcp.json` (`opencode-plugin/index.js:31-35`; `scripts/conformance.mjs:198-226`, `scripts/conformance.mjs:234-270`).

## Auth and providers

- The API MCP uses browser OAuth on first use and requires no local credentials by default; the knowledge server requires no authentication (`README.md:14-15`, `README.md:205-212`; `opencode-plugin/README.md:42-47`). The plugin contains no provider factory or credential storage.
- Users can override the API server with a local stdio `dodopayments-mcp@latest` command and pass API, webhook, and environment variables in project `opencode.json` (`opencode-plugin/README.md:68-90`; `README.md:134-151`).
- OpenCode-specific disable controls are environment variables, selected because unknown top-level config keys are rejected by OpenCode’s strict schema (`opencode-plugin/index.js:50-55`). Accepted truthy values are `1`, `true`, `yes`, and `on`, case-insensitive; unset, empty, and other values leave the server enabled (`opencode-plugin/index.js:57-63`; `opencode-plugin/README.md:49-66`).

## State and processes

- The plugin does not spawn a process directly. Each enabled MCP entry asks OpenCode to launch `npx`, which then runs `mcp-remote@latest` against a Dodo HTTPS endpoint (`opencode-plugin/index.js:38-47`).
- Both servers are enabled by default. A disable flag skips registration entirely, while an explicit same-name project config wins through `??=` (`opencode-plugin/index.js:68-72`; `opencode-plugin/README.md:49-90`).
- Skill files are vendored as real files rather than symlinks so a plain clone works; a weekly workflow clones the upstream skills repository, applies the declared rename transform, refreshes provenance, rebuilds artifacts, and opens a PR (`.skills-source.json:2-16`; `.github/workflows/sync-skills.yml:27-80`, `.github/workflows/sync-skills.yml:105-120`).

## Configuration and manifests

- Installation requires adding `@dodopayments/opencode-plugin` to `plugin` in `opencode.json`; exposing the seventeen skills additionally requires a project-relative `skills.paths` entry pointing into the locally installed package (`opencode-plugin/README.md:7-30`; `README.md:99-130`).
- The root `plugin.json` declares the Agent Plugins schema, package identity, version, metadata, and provider extension namespaces (`plugin.json:1-42`). The nested `plugins/dodopayments/plugin.json` is a generated bundle copy with the same identity/version (`plugins/dodopayments/plugin.json:1-43`).
- `scripts/build.mjs` treats root `plugin.json`, `mcp.json`, and `overlays/*.json` as sources and generates provider manifests, legacy MCP config, package version, and a self-contained Codex bundle (`scripts/build.mjs:3-18`, `scripts/build.mjs:44-51`, `scripts/build.mjs:126-217`).
- The repository explicitly distinguishes canonical native Streamable HTTP config from legacy bridge config. This avoids putting legacy-only `enabled` fields into the closed canonical schema (`scripts/build.mjs:79-107`; `scripts/conformance.mjs:100-122`).

## Errors and security

- A malformed export is a high-impact silent failure: OpenCode can skip the plugin and consequently register neither MCP server. The repository documents this risk and tests the default-only export shape (`opencode-plugin/index.js:9-21`; `scripts/conformance.mjs:244-250`).
- Remote MCP URLs are HTTPS and are validated for transport, URL safety, and absence of fragments/userinfo by the conformance script (`mcp.json:4-10`; `scripts/conformance.mjs:100-122`). The script also checks that OpenCode’s URLs match canonical endpoints and rejects a non-Dodo hostname by boundary-aware matching (`scripts/conformance.mjs:210-220`, `scripts/conformance.mjs:258-270`).
- The default API path delegates authentication to browser OAuth. The local override path exposes API and webhook secrets through environment configuration, so project config and process environments must be protected (`README.md:134-151`; `README.md:214-235`).
- The use of `npx -y mcp-remote@latest` is convenient but resolves a mutable latest package at launch; pinning a version would improve reproducibility. This is an observed design tradeoff in the command definitions, not a reported failure (`opencode-plugin/index.js:38-46`).
- The README documents two operational pitfalls: OpenCode does not scan installed packages for skills, and non-existent skill paths are ignored silently (`README.md:112-132`). Older releases also used submodule symlinks, which failed on plain clones; current CI enforces zero symlinks (`README.md:64-66`; `.github/workflows/verify.yml:45-52`).

## Pitfalls and reusable lessons

- Export discipline matters: for plugins whose loader accepts only function exports, keep the module surface to a single default plugin function and test the actual imported module shape.
- Treat skill discovery timing as a separate lifecycle from config mutation. Document and test the user-facing `skills.paths` requirement rather than attempting to inject skills from a late config hook.
- Use `??=` for default config registration when users must be able to override individual entries without a competing merge policy.
- Maintain one canonical endpoint manifest and derive compatibility transports from it. If an OpenCode-specific registration cannot be generated, add a conformance test that imports and executes the real hook and compares endpoint sets.
- For silent-failure plugin ecosystems, prefer positive assertions: exact skill count, real files, zero symlinks, schema validation, package payload checks, and explicit generated-artifact drift checks (`scripts/conformance.mjs:5-12`, `scripts/conformance.mjs:125-181`; `.github/workflows/verify.yml:45-70`).
- Keep provider-specific generated files separate from hand-authored canonical files, and make version propagation a checked build step (`scripts/build.mjs:3-18`, `scripts/build.mjs:219-280`).
