## Scope and availability

- Manifest index 25 identifies `Froggy`, described as “Hooks and specialized agents,” at `https://github.com/smartfrog/opencode-froggy` (manifest.json:204-208; the candidate is the 25th array item).
- The clone was available at `.research/opencode-plugin-corpus/repos/smartfrog--opencode-froggy/`.
- The repository has no directory named `manifest` or other manifest-specific subdirectory in the inspected tree. It does contain `openspec/config.yaml` and a `package/` directory containing a vendored `@opencode-ai/sdk` package; the latter is package metadata, not the plugin's runtime entrypoint (package/package.json:1-54; openspec/config.yaml:1-20).

## Architecture and OpenCode patterns

- The package is an ESM TypeScript OpenCode plugin whose public entrypoint is `dist/index.js`; npm packaging includes compiled output plus `agent`, `command`, `skill`, `images`, and `README.md` (package.json:2-19). The plugin declares `@opencode-ai/plugin` as both a build-time dependency and a peer dependency (package.json:40-55), a useful compatibility pattern for OpenCode plugin APIs.
- The plugin factory loads bundled agents, commands, skills, and global/project hooks at initialization, then merges global hooks before project hooks (src/index.ts:87-102). The `config` hook injects loaded agents and commands and appends the bundled skill directory to `config.skills.paths` without overwriting existing paths (src/index.ts:282-309).
- OpenCode-native hooks are used for tool lifecycle, session events, and system prompt transformation. Tool-before hooks can block by throwing the configured reason; tool-after hooks receive the arguments captured by call ID (src/index.ts:324-367). Session-created/deleted/idle events drive hook execution and cleanup of per-session modified-file state (src/index.ts:369-409).
- Skill activation is implemented as an `experimental.chat.system.transform` hook that appends imperative instructions to call OpenCode's native `skill` tool, while the plugin exposes the skill directory through `config.skills.paths` (src/index.ts:412-420; src/skill-activation.ts:7-14). This separates discovery from activation and avoids embedding every skill body in the system prompt.
- Agents, commands, and skills use Markdown frontmatter. Agents default to `mode: all`, preserve optional model/temperature/maxSteps/tools fields, and normalize singular `permission` to `permissions`; skills are directory-based and require `SKILL.md`; commands use the filename as their command name (src/loaders.ts:9-50, 131-213). This is a simple extensibility contract for non-code contributions.
- Hook definitions are YAML frontmatter in `hooks.md`; valid events include session events and `tool.before.*`/`tool.after.*`, and multiple declarations preserve file order (src/loaders.ts:216-264). The project example runs `npm run test` only after code changes in the main session (`.opencode/hook/hooks.md:1-7`), demonstrating conditions as a guard against noisy automation.

## Testing lessons

- CI performs `npm ci`, strict typecheck, build, and the complete Vitest suite on Node 20 for pushes and pull requests (`.github/workflows/ci.yml:1-21`). The package scripts make these gates reproducible locally (`package.json:16-20`), although the repository guidance notes there is no dedicated lint configuration (AGENTS.md:21-33).
- Tests are colocated under `src/**/*.test.ts` and configured with Vitest globals (vitest.config.ts:1-8). The loader tests cover missing directories, malformed YAML, optional-field omission, permission-key precedence, ordering, invalid hook events, wildcard/specific tool events, and all supported action forms (src/index.test.ts:19-67, 70-209, 376-842).
- Shell execution has deterministic tests for exit codes, stdout/stderr, environment variables, JSON stdin context, timeout, working directory, and tool metadata (src/index.test.ts:843-1020). This is a strong pattern for testing integration boundaries without invoking the whole OpenCode runtime.
- Platform path behavior is tested by mocking `process.platform`, environment variables, and filesystem existence for XDG, macOS/Linux defaults, and Windows APPDATA fallback (src/config-paths.test.ts:19-95). The project also tests code-file extension gating, including case normalization and Go/Rust coverage (src/code-files.test.ts:4-27).
- Pure tool logic is factored into testable cores: agent promotion validation is tested independently of the OpenCode client (src/tools/agent-promote.test.ts:11-92), PDF conversion uses generated temporary PDFs and cleanup (src/tools/pdf-to-markdown.test.ts:72-120), and blockchain output uses deterministic fixtures rather than network calls (src/tools/blockchain/tools.test.ts:10-33, 70-138).
- Remaining test gap: the reviewed tests exercise loaders and isolated tool logic, but do not appear to test the full plugin factory's `config`, tool registration, hook blocking/continuation behavior, or system transform against a mocked OpenCode client. Those are high-value contract tests for regression protection around the integration layer.

## Security and operational pitfalls

- Hook bash actions are arbitrary shell commands executed with `bash -c`, the project directory as cwd, inherited `process.env`, and `OPENCODE_PROJECT_DIR`/`OPENCODE_SESSION_ID` added to the environment (src/bash-executor.ts:20-37). This is appropriate for explicitly trusted local configuration, but project/global `hooks.md` is a code-execution boundary and should be treated like executable configuration. The 60-second default timeout kills the child with SIGTERM, but does not show a process-group kill strategy for descendants (src/bash-executor.ts:18-18, 43-67).
- Hook action failures are logged and execution continues, while exit code 2 blocks only when the hook is running in a before phase (src/index.ts:157-245, 264-280). This makes automation resilient, but a malformed or failing enforcement hook can silently become non-enforcing outside a block-capable phase; the behavior should be explicit in documentation and integration tests.
- The logger writes JSON-serialized event data, including tool arguments and command strings, to a fixed file in the OS temp directory and suppresses all logging errors (src/logger.ts:1-16). Arguments can contain sensitive source text or secrets, and the predictable shared temp filename raises privacy/rotation/concurrency concerns. Logging should minimize/redact payloads and document retention.
- `gitingest` posts a caller-provided URL, filtering options, and implicitly requested repository content to `https://gitingest.com/api/ingest`; it returns the service's summary/tree/content directly (src/tools/gitingest.ts:16-34). This is an external data-disclosure and availability dependency, so users should understand that repository URLs/content may leave the local environment and callers should validate response size/content.
- The PDF tool accepts any absolute file path and reads it directly with no project-root restriction, sandboxing, size limit, or file-type preflight (src/tools/pdf-to-markdown.ts:4-17; src/tools/pdf-to-markdown-core.ts:193-207). In an agent context, path authorization is therefore delegated entirely to the model/user and filesystem permissions; a safer deployment should constrain paths and bound input size/pages.
- `agent-promote` mutates a module-level map and schedules `client.instance.dispose()` after changing agent mode (src/tools/agent-promote-core.ts:5-13; src/tools/agent-promote.ts:48-77). The map is process-local and not persisted, and disposal is a disruptive side effect that deserves explicit confirmation or a documented lifecycle contract. Validation does correctly restrict grades and agent names to known plugin agents (src/tools/agent-promote.ts:36-46).
- Blockchain RPC clients are cached by chain ID and created with viem's default public HTTP transport; unknown chain IDs fall back to mainnet (src/tools/blockchain/viem-client.ts:34-76). The fallback is convenient but potentially surprising or dangerous for queries, so callers should validate chain IDs or surface the fallback in results. Etherscan-related code also reads `ETHERSCAN_API_KEY` from the environment (src/tools/blockchain/etherscan-client.ts:25-51).

## Packaging and release lessons

- The `files` allowlist intentionally ships only runtime output and declarative plugin assets, excluding tests, source, config, and development files (package.json:8-15). Any runtime asset loaded through a path such as `agent`, `command`, or `skill` must remain in this allowlist; otherwise a correctly built npm package can load successfully in development but fail after publication.
- The release workflow verifies that the `v*` tag matches `package.json`, then installs, typechecks, builds, tests, publishes publicly, and creates release notes from `CHANGELOG.md` (`.github/workflows/publish.yml:1-36, 38-56`). This is a good release gate and prevents accidental version/tag drift.
- The workflow grants `id-token: write` and `contents: write` for npm trusted publishing/release creation (`.github/workflows/publish.yml:8-10`). These permissions should remain limited to the publish workflow and be reviewed whenever release automation changes.
- `package-lock.json` is committed and CI uses `npm ci`, while the repository guidance requires Node 18+ (AGENTS.md:15-20) and CI standardizes Node 20 (`.github/workflows/ci.yml:13-20`). The package's dependency range for the OpenCode plugin (`^1.4.6`) plus unrestricted peer range (`*`) trades compatibility flexibility for less precise runtime/API guarantees (package.json:45-55).

## Recommended takeaways

1. Keep the loader/configuration split: declarative Markdown assets, deterministic merging, and a small runtime entrypoint make plugin behavior easy to extend.
2. Preserve isolated core modules and boundary tests, then add mocked end-to-end plugin-factory tests for registration, hook blocking, and prompt transformation.
3. Treat shell hooks, arbitrary PDF paths, external ingestion, and verbose temp-file logging as explicit trust-boundary features. Add path/size controls, redaction, and clear user-facing warnings before enabling them in less-trusted environments.
4. Keep the npm `files` allowlist synchronized with runtime asset directories and retain tag/version plus typecheck/build/test gates in publishing automation.
